## 1. 目标与验收标准

### 1.1 一句话（解决什么问题）

把对话状态与工具循环的真源从 DeepSeek 网页收回 studio 宿主，使宿主成为模型引擎的调用方而非网页的点击方，从而消除「结果被掩盖 / 只显示最后一个 / JSON 偶发失败 / 靠纠偏补丁」这类结构性症状。

### 1.2 完成定义（DoD，可复现命令）

命令真实性声明：当前 package.json 实际脚本为 typecheck(=tsc --noEmit)、test(=vitest run)、build:inject(=node esbuild.inject.mjs)。用户示例中的 compile / eval:golden 尚不存在——eval:golden 由本计划 M0-3 创建。

阶段 A（当前可跑）：
```
npm run typecheck   # tsc --noEmit，0 错
npm run test        # vitest run，见 1.3 基线
npm run build:inject
```

阶段 B（M0 完成后启用）：
```
npm run typecheck && npm run test && npm run eval:golden
```

### 1.3 量化阈值（必须与实现常量对齐）

| 指标 | 阈值 | 对齐的实现常量（真值，已核实） |

## 5. 里程碑与顺序 + 数据裁决点

M0 基线基建 -> M1 引擎接口 -> M2 内核归位 -> M3 删纠偏

### 数据裁决点 D1：M0-2 的「工具回合需 nudge 率」决定 M2-3 激进程度
- nudge 率 < 5%：可直接做 M3 删纠偏。
- nudge 率 ≥ 5%：网页层仍有未定位完成检测缺陷，先补 web-engine.ts 完成检测再动 M3。
- 取数：M0-2 埋点，命令 npm run test -- tests/desktop/harness-events.test.ts。

### 数据裁决点 D2：M1-3 pi-agent-core 单 turn 接入成本决定「接 vs 自建」回退
- 接入 ≤ 3d 且不破坏现有 177 行 agent-loop 契约：继续接。
- > 5d 或契约冲突：回退为「仅借鉴 pi 的 transport 接口形状，自建薄 loop」（唯一允许的自建情形）。

## 9. 协同与接口边界

| 层 | 归属 | 契约冻结点 |
|---|---|---|
| dpp core/** | 复用（零修改 import） | dpp 快照 commit 187f6227 |
| dpp entrypoints/** / storage / alarms | 各自实现（绑 chrome.*，studio 不 import） | 不适用 |
| pi-agent-core | 外部依赖 | 锁版 0.83.0 |
| studio WebEngine transport | studio 独有 | 本文件 §4 M1-2 |
| golden fixtures | 共享（dpp M0 产出 = studio 复用） | 本文件 M0-3 |
| `src/inject/**`（页端注入脚本） | **DPP 宿主侧主开发**（与 `src/host/**` 同席维护） | DCD 裁定 20261017 §1.2；改动必须过 `npm run test` + `tools/audit/symbols.ts` |

边界铁律：core/** 能 import 的全 import；只重写依赖 chrome.* 的那层。
`src/inject/**` 与 `src/host/**` 是同一条"浏览器↔宿主"通道的两半（web-engine 完成检测依赖 interceptor 解析输出），跨席审批会让 bug 修复慢一个量级。

## 36. 并发治理层（AB）——「发出前」与「账号维度」两层缺失

### 36.1 为什么 §29 的 8 项还不够

把 §29 的设施与本部分的盘点合起来看，**缺口不在「怎么退避」，而在「谁有权说不行」**：

| 维度 | 现状 | 谁负责 | 缺什么 |
|---|---|---|---|
| 时间（间隔/退避/冷却） | RT-1~RT-4 会补齐 | 战术层 | — |
| 状态（作用域/就绪/partial） | DP-1~DP-3 会补齐 | 正确性层 | — |
| 空间（跨窗口/跨 bot） | RT-6/RT-7 会补齐 | 战术层 | — |
| **数量（日/时配额）** | **无** | — | 🔴 一天能打几千次，无人知晓 |
| **身份（账号维度）** | 只有指纹去重（同账号双窗阻断） | — | 🔴 **没有「这个账号今天已发 N 次」的账** |
| **决策点（发出前的许可）** | **无**：所有节流都在「发之后/发之间」 | — | 🔴 **没有统一入口可拒绝** |
| **熔断（连续失败后停）** | `slot-registry.cooldownUntil` 字段存在但**无写入者** | — | 🔴 空字段 |

⇒ §29 修完，仍然是「**每一次都发得出去**」，只是发得慢一点。**封号是「发出即计」，事后补救无效。**

### 36.2 目标：RequestGovernor（三层闸 + 一个入口）

```
src/host/request-governor.ts（新）  ← 全仓唯一允许说「不许发」的地方

  acquire(req: { kind: 'completion' | 'tool' | 'read', account?: string, botId?: string })
    → { allowed: true }
    | { allowed: false, reason: 'quota-day' | 'quota-hour' | 'min-interval'
                          | 'breaker-open' | 'in-flight-limit', retryAfterMs }

  三层约束：
    进程级：在飞请求数上限（默认 1，与 server.ts:172 一致）+ 全局 QPS
    账号级：日配额 / 小时配额 / 最小间隔 / 熔断状态（key = accountFingerprint）
    窗口级：单窗连发上限（把 MAX_LOOP=25 / MAX_NUDGES=8 纳管）

  观测：snapshot() → { inFlight, todayByAccount, breaker, lastRejects[] }
```

**三条设计铁律**：

1. **闸在发出前**：页面侧 `autoContinueWithPow` / `autoContinueNudge` 每次发请求前必须先 `acquire`；拒绝则不重试、不绕过、把 `reason` 落轨迹并停循环。
2. **闸是单例且跨窗口共享**：4 个 bot 窗口必须打同一份配额账（否则 RT-6 只是「同时只跑一个」，仍可轮流打满一天）。
3. **闸失败必须可见**：拒绝原因进 `/v1/diagnostics` 与轨迹，绝不静默（同 TJ-4 的教训）。

### 37.2 三档纵深 + 预算（借鉴 dpp 的 20% 预算，但改成按档）

dpp `trace-store.ts:16-25` 的做法值得抄：`TRACE_BUDGET_RATIO = 0.20`，超预算丢最旧，**并且注释写明「配额写满会让后续每一次写都失败」**。studio 没有 `chrome.storage` 的 10MB 硬配额，但**有同样的膨胀问题**——dpp 实测一条完整 trace 是 80–100KB。

| 档 | 内容 | 保留 | 单条上限 | 用途 |
|---|---|---|---|---|
| **L1 事件流** | 每轮 `engine.send` / 工具调用 / consent / 判停的结构化事件（**不含正文**） | 30 天 | 单行 ≤ 4KB | 统计、趋势（TL-6 消费） |
| **L2 回合轨迹** | 一个回合的完整时间线（prompt 摘要 / 工具参数摘要 / 结果摘要，**正文脱敏**） | 7 天滚动 + 失败永久 | ≤ 64KB，超限截断并标 `truncated:true` | 复盘（`DG-2` 直接读它） |
| **L3 失败快照** | 失败回合的**完整现场**（含原始响应；prompt 按 `D21` 决定） | 永久（按内容哈希去重） | ≤ 512KB | 归因（`DG-3`）、回归 fixture（`DG-4`） |

**三条硬约束**：

1. **正文默认不落盘**：L2 只落「摘要 + 哈希 + 长度」；要原文按 traceId 去 L3 取，L3 只在失败时写。
2. **预算先于写入**：写前检查本档配额，超限**删最旧**而不是写失败（防 dpp 那个「配额满后每次写都失败」的坑）。
3. **轨迹是旁路**：写失败不影响主流程，但**必须可见**（返回 boolean + 记 `trajectory-write-failed`，同 TJ-4 的教训）。

## 46. 第四问：类似开源 agent 有能整合进来的吗

> 分册 §2 已给出「三类整合、代价差一个数量级」的框架（MCP/ACP 协议层、评测层、编排层）。本节**不重复框架**，只给**当前可落的具体清单 + 一个反直觉结论**。

### 46.1 三类整合的取舍（复述结论，不重推）

| 类 | 代表 | 代价 | 建议 |
|---|---|---|---|
| **协议层**（最划算） | MCP（Anthropic，已事实标准）、ACP | 低：studio 已有 `mcp-controller.ts` | ✅ **做**——映射到 `OS-1~OS-3`（分册） |
| **评测层**（中等） | promptfoo（MIT，TS 原生可 npx）、Inspect AI（MIT）、SWE-bench 的 FAIL_TO_PASS 方法论 | 中：要接 driver | ✅ **只借方法论**——`C-7` 的字节级 golden + `DG-4` 的 replay 已经是这个形状，**不必引外部框架** |
| **编排层**（最贵） | LangGraph / CrewAI / AutoGen | 高：整套状态机 + 依赖链 | ⛔ **CUT**——studio 的 `task-loop.ts` 已是自研薄 loop（D2 已裁「不接 pi」），再引一套编排等于推翻既有决策 |

### 46.2 反直觉结论：**最该「整合」的不是 agent 框架，是三个小库**

| 需求 | 开源方案 | 为什么它比「引一个 agent 框架」更值 | 落点 |
|---|---|---|---|
| 版本化持久化 | **zod**（已在生态）+ 自研 `versioned-repo` | 引 LangGraph 要 20+ 依赖，而 `FS-9` 只需 200 行 | `FS-9` |
| 合并写队列 | 无成熟小库，自研 50 行 | 领域太窄，引库反而多一层 | `FS-8` |
| 脱敏 | 自研白名单（`TR-7`） | 引 PII 库会带来「它认不认中文手机号」的新不确定性 | `TR-7` |

**结论**：**没有「一个开源 agent 项目能整体搬进来」的选项**。dpp 本身已经是最好的参照（同架构、同目标），而 studio 缺的是**设施**（日志/遥测/轨迹/用量/持久化），这些都不在 agent 框架里，在**工程基建**里。

### 46.3 真正值得「看一眼」的四个开源项目（读设计，不引依赖）
