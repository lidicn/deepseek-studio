## 2. 比「落后」更严重：两套副本

studio 内有两份 dpp 逻辑：

| | 位置 | 文件数 | 状态 |
|---|---|---|---|
| **A. 快照副本** | `deepseek-pp/src/core/` | 340 | 53 过时、缺 19 |
| **B. 手工移植副本** | `src/inject/` + `src/shared/` | 7 | 与 dpp 同名文件哈希全部不一致 |

### 2.1 B 副本的落后是双重的

7 个移植文件：

| studio 文件 | 对应 dpp 源 | dpp 近 10 天是否已改 |
|---|---|---|
| `src/inject/step-control.ts` | `inline-agent/step-control.ts` | 是 |
| `src/inject/execution-policy.ts` | `inline-agent/execution-policy.ts` | 是 |
| `src/inject/streaming-tool-parser.ts` | `interceptor/streaming-tool-call-parser.ts` | 是 |
| `src/inject/message-anchor.ts` | `inline-agent/message-anchor.ts` | 待核 |
| `src/inject/markdown.ts` | `inline-agent/markdown.ts` | 待核 |
| `src/inject/trace-store.ts` | `inline-agent/trace-store.ts` | 待核 |
| `src/inject/render-code-runner.ts` | `inline-agent/render-code-runner.ts` | 待核 |
| `src/shared/continuation-prompt.ts` | `inline-agent/prompt.ts` | 待核 |

即：移植时取的是子集（二次简化），移植后源又变了（三次漂移）。

### 2.2 B 副本不是「不知情的重复造轮子」

7 个文件头注释均写明来源，例如：

- `streaming-tool-parser.ts`：本模块是上游 streaming-tool-call-parser 算法的等价移植（逐行复刻其「增量扫描 + 跨块保留未闭合标签尾部 + 解析 JSON 参数」行为），之所以不直接 import 上游源码，是因为 deepseek-pp 的 core 依赖 WXT/chrome 类型与自身更宽松的 lint 配置，无法在本项目严格 tsconfig 下编译。
- `continuation-prompt.ts`：移植自 deepseek-pp core/inline-agent/prompt.ts
- `step-control.ts`：移植自 deepseek++ step-control.ts

所以这不是「提醒去拿代码」能解决的问题——他们知道，且理由写在文件里。真正的问题是**移植后没有登记版本锚点、没有反向同步机制**。

## 3. 为什么不会自愈

### 3.1 覆盖式同步的「太顺」就是问题

`UPSTREAM.md` 规定 robocopy 覆盖式同步。后果：

- 同步永不冲突 → 永远「能跑」；
- 正因为能跑 → 没人有动机去同步；
- 落后只累积，不暴露。

### 3.2 漂移只在最贵的时刻暴露

表现为「同一个工具调用，studio 与 dpp 行为不一致」。此时已难定位是 53 个修改之一、还是 19 个新增之一。

### 3.3 已修的 bug 不会传播

dpp 在 `interceptor/` 修的解析层缺陷（跨块配对、SUPPRESSING 无出口），studio 快照与移植版都不会自动获得。
反之，studio 当前「不断流」也可能是缺陷在 Tauri 侧未被触发，不代表不存在。

## 4. 建议：三条机制（按成本递增）

### M1 · 移植文件补版本锚点（10 分钟，一次性）

在 7 个移植文件头注释追加一行：

```
@upstream-commit 187f6227 @upstream-path core/inline-agent/step-control.ts
```

作用：任何时刻可反查「基于哪个版本移植」，从而判断该不该重新移植。

### M2 · 漂移检测脚本 + 定期跑（30 分钟，一次性 + 每周 1 分钟）

写入 `scripts/check-upstream-drift.mjs`（Node，无需依赖）：

- 对 `deepseek-pp/src/core/**` 与 `E:/NAS/deepseek-pp/src/core/**` 做 SHA256 逐文件比对；
- 输出四类计数：`identical / modified-in-upstream / new-in-upstream / deleted-in-upstream`；
- 退出码：偏离数超过阈值（建议 30）→ 非 0，可直接进 CI。

绑定节奏：绑定 dpp 的 release tag，或每两周一次，人工跑一次并记录到本目录的漂移日志。

### M3 · 给 core/** 加不变量门禁（半天，一次性）

`UPSTREAM.md` 已声明 AGENTS.md 的不变量对 studio 同样生效：

- prompt bytes
- storage key
- runtime message 名
- 工具授权路径

建议：在 dpp 侧给 `core/**` 提交前跑这四类契约测试（dpp 已有 tests/** 273 文件含契约测试，可直接用）；studio 侧同步后先跑一遍 `npm run test`，失败即拒绝合并。

这是保护 studio 的必要成本：dpp 事实上是 studio 的上游库，但按 R4 覆盖率（inline-agent 78% / interceptor 45%）测试纪律尚不足「库」的标准。

## 5. 反对的做法（避免过度反应）

| 反对 | 原因 |
|---|---|
| 立刻把 `core/**` 改成 submodule 或 npm 包 | 改动面大；studio 现在依赖 WXT/chrome 类型不兼容的事实，直接 import 编译不过。先做 M1–M3，验证痛感是否真实，再决定是否升级为包。 |
| 把 7 个移植文件全部替换为 import | 同上，tsconfig 不兼容。且移植版普遍是子集（studio 不需要 DOM 渲染），全量替换会引入死代码。 |
| 每次 dpp 提交都同步 | 边际收益递减，且会淹没真实的破坏性变更。按 release / 双周节奏即可。 |

## 6. 可复现（本文件数字的来源）

在 `E:/NAS/deepseek-studio` 下执行（PowerShell）：

```powershell
$a='E:/NAS/deepseek-pp/src/core'
$b='E:/NAS/deepseek-studio/deepseek-pp/src/core'
$fa=@{}
Get-ChildItem -LiteralPath $a -Recurse -File -Filter *.ts |
  Where-Object { $_.FullName -notmatch 'node_modules' } |
  ForEach-Object { $fa[$_.FullName.Substring($a.Length+1)]=(Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256).Hash }
$fb=@{}
Get-ChildItem -LiteralPath $b -Recurse -File -Filter *.ts |
  Where-Object { $_.FullName -notmatch 'node_modules' } |
  ForEach-Object { $fb[$_.FullName.Substring($b.Length+1)]=(Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256).Hash }
$onlyA=@($fa.Keys | Where-Object { -not $fb.ContainsKey($_) })
$onlyB=@($fb.Keys | Where-Object { -not $fa.ContainsKey($_) })
$both =@($fa.Keys | Where-Object { $fb.ContainsKey($_) })
$diff =@($both | Where-Object { $fa[$_] -ne $fb[$_] })
"new-in-dpp=$($onlyA.Count) deleted-in-dpp=$($onlyB.Count) common=$($both.Count) modified=$($diff.Count)"
$diff
```

2026-10-18 实测输出：

```
new-in-dpp=19 deleted-in-dpp=0 common=340 modified=53
```

## 8. 关于「要不要提醒去 dpp 拿代码」

不需要。

理由：7 个移植文件头注释已写明来源、不 import 的理由；`UPSTREAM.md` 已写明快照机制与同步命令。**开发者是知情的。**

需要提醒的是本文件的三条机制：**登记版本、定期检测、门禁不变量。** 否则「有意识的移植」会退化成「无意识的分叉」。
