# v0.14.15 发版操作单（维护者用，不进发布页正文）

## 前置事实（本次为什么是 0.14.15，前面两个版本号都没能出包）

| 版本 | Release run | 红在哪 | 性质 |
|---|---|---|---|
| `v0.14.13` | `42724494390` | step 9，日志末行 `NSIS archive extracted but marker still missing: …\tauri\NSIS\Bin\makensis.exe` | **逻辑错**：zip 顶层目录名（`nsis-3.11/`）≠ 构建器期望的工具目录（`NSIS/`），旧写法把包原样解到工具根目录，marker 永不可能命中 |
| `v0.14.14` | `42834958003` | step 9，**只活 1 秒** | **语法错**：`release.yml` 里 `attempt $attempt:` 这种写法被 PowerShell 当成「驱动器:变量名」，整块编译不过；该写法在 `80d427c`（发版链加固）引入，因未被执行而一直潜伏 |

两条教训（都已落判据）：
1. **闸绿 ≠ 那条路能走通**：0.14.13 那次，发布脚本里的 fetch 分支因缓存命中**从未被执行过**，所以闸绿一整天也照不出来；0.14.14 那次，闸**根本不读 workflow 里的脚本内容**。
2. **未被执行过的分支不受任何闸保护** ⇒ 本版起新增「workflow pwsh 块真解析」编译闸（`tests/desktop/workflow-pwsh-compile.test.ts`），发布前会真实调用 `[System.Management.Automation.Language.Parser]::ParseInput`。

`v0.14.13` 与 `v0.14.14` 两个 tag 均保留、不删不重打（先例：0.14.10 弃用合并为 0.14.11）。**重跑已失败的 run 没有意义**：它跑的是 tag 里那份已知的坏代码。

## 版本号

四处同步（`Cargo.toml` 是 crate 号 `0.4.0`，不参与一致性校验，勿改）：

| 文件 | 行 |
|---|---|
| `package.json` | L3 |
| `src-tauri/tauri.conf.json` | L4 |
| `package-lock.json` | L3、L9 |

**抬号后必须重建注入包**：`esbuild.inject.mjs` L33 把 `package.json` 的 version 编成编译期常量 `__STUDIO_APP_VERSION__`，不重建则 `entry-freshness` 报「陈旧构建」。

```
npm run build:inject     # 双跑同值，报 entry.js 新锚
```

**抬号后的自检走解析口径，不许用 grep 计数**（计数法拦不住「多处都在但值不一样」，也拦不住「手改 JSON 把文件改坏」）：

```
node -e "const p=require('./package.json'),l=require('./package-lock.json'),t=require('./src-tauri/tauri.conf.json');console.log(p.version,l.version,l.packages[''].version,t.version)"
```

四值必须全等且等于目标版本号，进程退出码 0。

## 发布页正文

- 正文文件：`docs/release-notes-v0.14.15.md`，**必须先于 tag 入库**（workflow L312-322 是 fail-closed：文件不存在或纯空白 ⇒ 整条 release job 红）。
- 文件名由 tag 动态推导（L278 / L318 / L333 / L370 / L429 全部用 `$tag` 或 `github.ref_name`），**不需要改 workflow 里任何路径**。
- 正文只写用户可见行为；未在安装版上逐项手工验证的，必须写明「不作承诺、请把现场发我们」。
- `latest.json` 的 `notes` 是另一条链：剥 markdown → 截 500 字内最近「。」→ 应用内升级弹窗显示的是这份截断纯文本，与网页正文分别验收。

## 打 tag 前五查

```
git ls-tree <tag目标commit> docs/release-notes-v0.14.15.md      # 在树里
node -e "<版本四值全等>"                                          # 解析口径
npm run typecheck                                                # 0
npm run gate                                                     # 绿，两行与预期逐位同
git tag -l v0.14.15                                              # 空＝未占用
```

annotated tag：`git tag -a v0.14.15 -m "<不带因果陈述的说明>"`；tag 注释只作备份，工作流会 PATCH 正文并逐字校验。

## CI 与草稿

1. 三条 job：`gate` ×2、`cargo-check` ×2、`release` ×1。`release` 最慢（Rust 编译＋打包＋签名＋上传）。
2. **报数必须带时长与缓存命中态**；`cargo-check` 的 step 日志匿名取不到命中态时只报时长。
3. `release` 绿后才会有草稿（fail-closed：构建失败时页面上没有 Publish 按钮）。
4. 草稿核对五件：资产 5 枚（`.exe`／`.exe.sig`／`.msi`／`.msi.sig`／`latest.json`）全 200、正文与文件逐字等值、`draft=true`、`tag=v0.14.15`、三向版本一致。
5. **读数纪律**：step 级结论用 `GET /actions/runs/<id>/jobs` 取（匿名可读）；job 日志正文匿名 403，**取不到就说取不到，不许用"大概是同一处"交差**；报「读不到」前先查 `rate_limit.remaining`，**限流与故障分开判**；同一台机器上 `git` 通道与 `api.github.com` 通道可用性**分别判**，不写「GitHub 挂了」这种整句。

## Publish（用户的网页动作）

Releases → `v0.14.15 (Draft)` → Edit → 确认正文完整 → **勾上「Set as the latest release」** → Publish。
不勾 Latest ⇒ `releases/latest` 指针不推进 ⇒ 客户端收不到更新提示（已两次踩坑）。

## 发布后

- 查 `on: release` 的公开链路闸结论；若失败会把正式版打回 draft、latest 指针离开。
- 装新版前先退出旧实例（旧实例占 `127.0.0.1:8760`，两装并存新实例起不来）。
- 新版上补做真机取证：独立审批窗口首弹、`td05_*` 四枚 Rust 测试（端口空了才能跑）、MCP 调用重测、空白气泡与空气泡两条显示面。
