## 〇、结论先行

1. **`MAX_LOOP=25` 是「每批」预算，不是「每轮对话」预算**（`continuation-prompt.ts:L48`；
   `MAX_AUTO_CONTINUE=3` 在 `L60`，只封「无工具空转续轮」，两者不共用）。
2. **复位按 `finished` 切三分**：`finished:true`＝自然结束（2 处）／`finished:false`＝被守卫拦停（5 处）／
   `catch` 里的一处（`L3163`）请求根本没起来、属第六档。
3. **「用户不知道为什么又跑起来」这一格，只对 `L3063`／`L3111` 两枚成立**——其余四枚在收尾前
   已经写了原因（`appendError` 带 `code`+`message`）。#55 落地后**一枚都不成立**。
4. **#55 之后 T-3 剩下的真问题只有一个**：迟到工具结果重开新批，**该不该受「总预算」约束**。
   这是配额语义问题，不是 UX 问题。
5. 定性倾向：**每批预算看起来是有意设计**（会话级状态只在 `L2751` 清，批内预算按批清）；
   真问题是**「25 轮」在文案里像承诺、在实现里是每批预算**——**口径错位，不是执行错误**。

## 二、`finished` 三分（PM 裁的可操作定义，本文照此写）

- **`finished:true`＝自然结束（2 处）**：`L2558` terminate、`L3136` completed。
  复位合理：循环本来就该完，迟到结果再跑一批不违背任何守卫。
- **`finished:false`＝被守卫拦停（5 处）**：`L2579`／`L2986`／`L3019`／`L3063`／`L3111`。
  语义是「因为预算／故障，我们命令自己停」，**同一帧把计数器归零＝当场撤销这道命令**。
- **第六档（1 处）**：`L3163`（`catch` 分支，请求未发出）。
- **`L2751` 是会话边界**，不属于以上任何一档；它是唯一一处**真·复位**。

用 `finished` 切的好处：**这是代码自己写下的标志**，不靠语义感觉。用代码自己的标志做判据，
下一任读这枝的人不会因为措辞理解不同而重新分组——这正是今天三次同族误读（PM 的 `-State Listen`
坏表、我的半截分支、PM 把 `L3111` 划进自然结束）的共性：**都在用「感觉」而没用「标志」**。

## 三、迟到结果的重开路径（一条，五枚共用）

三个迟到守卫读的是**同一个** `loopDepth`：

- `L2478`（invalid-json 同步拒识后）
- `L2520`（宿主 `.then` 成功）
- `L2542`（宿主 `.catch` 失败）

三处条件形状完全相同：`!loopState.streamActive && loopState.lastChatBody && loopDepth < MAX_LOOP`
⇒ `scheduleAutoContinue()`。

还有第四个入口 `L2660`（`onStreamEnd` 补查）：
`if ((pending.length > 0 || loopState.streamHadTools) && lastChatBody && loopDepth < MAX_LOOP)`。

**⇒ 五枚复位过后，迟到结果看到的都是 `0 < 25`，合法地再开一整批 25 轮。**
重开路径只有一条，所以五枚现状锁的「重开」读数会**是同一个值**——
**总预算探针只建一枚**，其余五枚锁只用于「抓将来改动」。

**「25 轮」的真实语义**：单批上限 25；**批数由「迟到结果条数」约束，无硬上限**。

## 四、测试形态（一枚一守卫；红线见五）

### 4.1 现状锁 × 6（现在就能建，全绿）

每枚锁一个守卫，断言形状统一：

```
构造：该守卫被触发（loopDepth 顶到对应阈值 / 对应异常）
      → 断言该守卫的收尾已发生（finishStepFlow 被调 / trace 有 stopReason）
      → 记录 loopDepth 复位后值 === 0
```

**这六枚锁「抓不住」的变异**（判据 5 尾巴）：它们只记录「复位发生了」，
**抓不住**「复位时机错了但值仍是 0」；也**抓不住**「重开次数被别处限制」。
⇒ 它们的作用是**把现状钉死**，将来谁改复位语义，红态会告诉他改了什么。

### 4.2 总预算探针 × 1（与现状锁同源，改动任一枚都要回看它）

```
构造：触顶（loopDepth=25）
      → 投递 N 条迟到工具结果（N=3）
      → 断言「确实开了新一批」（现状）
      → 断言「总轮数 = 25 × (1 + N)」（= 无总上限的显式表达）
```

**要点**：第三行断言的是**「没有总上限」这件事本身**，不是「应该有上限」。
将来若引入总上限，这枚**必红**，迫使改动方承认这是语义变更、需要重新过产品关。

**这枚探针「抓不住」的变异**：它抓不住「上限存在但比 25×4 更大」的情况
（只能证明本次构造下无上限触发）。⇒ 换 N 时要重算期望值，不能照抄。

### 4.3 负控（red-first，红态五件式）

- **`L3062` 负控**：`#55` 落地后，**删掉补上的 `appendError('max-loop', …)` 那一行** ⇒ 验收断言必红。
  - 现状：该行**不存在**，「删掉必红」是**未来时**。设计稿按红态五件式写清「落地后补探针」，
    **不许 Verify 拿一个不存在的行做红态**。
- **`L3104` 负控**：同上形状。
- **总预算探针负控**：若给 `scheduleAutoContinue` 加一个「`stopReason==='max-loop'` 时不再调度」的锁，
  第 4.2 节的第三行断言必红 ⇒ 这说明「加了总上限」，属语义变更。

## 附：T-4 `mcpcall` 别名规格（2026-11-09 22:5x 只读定性，Core）

### A1 现场

装版 sidecar 日志 `L23398`：`extracted[53]: TVPilot","tool":"tv_system_state","args":{}}</mcpcall>`——
**JSON 载荷是 Studio 模板形状**（`main-world-interceptor.ts:L1189` 教的 `serverId/tool/args`），
**标签名是 DeepSeek 网页原生拼写 `mcpcall`**（无下划线）。

### A2 根因（比"解析器只认 `mcp_call`"深一层）

四个消费方全部从**同一个集合** `SUPPORTED_INVOCATION_NAMES`
（`tool-contract.ts:L211` `= Object.keys(MODEL_INVOCATION_TOOLS)`）取名：

| # | 位置 | 作用 | 漏掉后的表现 |
|---|---|---|---|
| 1 | `streaming-tool-parser.ts:L51` | 流式解析 `names.includes(open[1])` | 落入 `L80` 普通文本分支 ⇒ **原文流回对话** |
| 2 | `raw-tool-text.ts:L47` | 构造 pair/open 正则 | 收尾扫描不认 ⇒ **`L3052`/`L3057`/`L3123` 的残留原文告警不报** |
| 3 | `main-world-interceptor.ts:L2398` | `forward` 的 `isSupportedUpstreamTool` 闸 | 即使被解析到也 `skip` |
| 4 | `page-runtime.ts:L581` | `mapUpstreamToolInvocation` | 回执 `unknown-tool` |

**关键约束**：`L211` 与 `L226 MODEL_INVOCATION_DECLARED_NAMES` **是同一句 `Object.keys`**。
⇒ 把 `mcpcall` 当键塞进 `MODEL_INVOCATION_TOOLS`，它会**自动出现在模型声明面**
（能力提示词目录、续跑目录），撞 `L206-210` G-01 注释防的东西。
**⇒ 别名必须"可识别但不能被声明"。**

### A3 规格（我域部分：`src/shared/tool-contract.ts`）

1. 新增 `const INVOCATION_ALIASES: Readonly<Record<string, string>> = { mcpcall: 'mcp_call' }`
   （放 `MODEL_INVOCATION_TOOLS` 之外，**不进任何 `*_NAMES`**）。
2. `canonicalInvocationName(name: string): string` —— 命中别名返回规范名，否则原样返回。
3. `isSupportedUpstreamTool` / `mapUpstreamToolInvocation` —— **先 `canonicalInvocationName` 再查表**。
4. `SUPPORTED_INVOCATION_NAMES` / `MODEL_INVOCATION_DECLARED_NAMES` / `UI_ONLY_INVOCATION_NAMES` **一律不变**。
5. UI 侧两处（`streaming-tool-parser.ts` 的 `names`、`raw-tool-text.ts` 的 `buildRegexes`）
   把 `Object.keys(INVOCATION_ALIASES)` **并入匹配集**（只入匹配、不入声明）。

### A4 一条必须先定的副作用（我发现，不在 PM 原始卡面里）

`tool-call-dedupe.ts:L39` 的签名是 `${invocationName}:${stableSerialize(params)}`，
调用点 `main-world-interceptor.ts:L2407` 传的是**原始** `call.invocationName`。
⇒ 别名落地后，模型若在同一流里先写 `<mcp_call>{X}</mcp_call>`、再写 `<mcpcall>{X}</mcpcall>`，
**两个签名不同 ⇒ 同一次调用执行两次**（MCP 工具可能有副作用）。

**建议**：`L2407` 改传规范名（`canonicalInvocationName(call.invocationName)`），
或签名内部先归一再序列化。**归属**：`tool-call-dedupe.ts` 是我域，
但调用点 `L2407` 在 UI 域 ⇒ **改调用点只有一行，归 UI**；我不并发写。

**验收必须含这一条**：同一参数两种拼写 ⇒ 只执行一次（否则别名修好了这个、弄坏了那个）。
