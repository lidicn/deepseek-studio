## 1. 需求稿逐条摘录（先把要设计的东西钉死）

需求稿标题「M8 安全核心 · MiMo 需求稿」，目标一句话：把现有 consent 闸门从「一刀切 ask」升级为三级审批 + 可回滚 + Plan/Act 分离；硬前提是「纯函数包 + 宿主接线，不碰网页侧 DOM」。

目标（需求稿「一、背景与现状」）自述四条缺口：没有按工具风险分级、没有白名单、没有操作回滚、没有计划与执行分离。

要设计的三个模块：

- E1 审批三级（safe / ask / deny）：输入 toolId + params + policyMode；输出 safe（自动放行）/ ask（弹同意框）/ deny（直接拒绝）。规则含白名单文件 `~/.config/deepseek-studio/consent-whitelist.json`、条目 `{ toolId, pathPattern, action, ttl? }`、glob 匹配路径 + 精确匹配 action、safe 档列 file.read / search_files / web.fetch、ask 档列 file.edit / file.write / shell.exec、deny 档列 `rm -rf` / `format` / 系统敏感路径。
- E2 git shadow 回滚：每次 file.edit / file.write 前自动快照；快照 ID 可回滚；快照存 `<workspace>/.shadow/`，命名 `<file-path>.<timestamp>.shadow`，保留最近 10 次，提供模型可调的 `rollback(shadowId)`。
- E3 Plan/Act 分离：Plan 阶段只出计划不执行，用户确认后进 Act；Act 按 steps 顺序执行、每步失败就停；计划 JSON 形如 `{ steps: [{ tool, params, reason }] }`；提供 `plan_act` 工具，输入 `{ task: string }`，先调模型出计划再执行。

硬约束五条（需求稿「三」）：错误码复用 CONTRACTS §6.1；纯函数包不 import src/host（workspace context 除外）；工作区边界唯一入口 workspace.resolveWithin 且 fail-closed；不碰网页侧 DOM；Windows PowerShell 唯一 shell。

接口面五处（需求稿「四」）：policy.ts、desktop-host.ts、workspace.ts、capabilities/edit-engine.ts、shared/tool-error-envelope.ts。

验收清单 9 条（需求稿「五」）：tsc 0 错、单测全绿、file.read 不弹框、file.edit 弹框、`rm -rf` 被 deny、白名单第二次不问、edit 后 `.shadow/` 有快照、rollback 生效、多步任务先出计划。

交付物 4 项（需求稿「六」）：`src/host/consent-router.ts`、`src/host/shadow-store.ts`、`src/capabilities/plan-act.ts`、各模块单测 ≥8 例 + 接线进 desktop-host。

「不要做什么」需求稿没有单列成节，但从约束与验收可以反推四条硬边界：不改网页侧 DOM（含同意模态）、不绕过既有 consent 闸、不重复造工作区边界判定、不引入非 PowerShell 的 shell 路径。本稿在第 12 节把它扩成 12 条可执行的「不做」。

## 2. 需求稿说的 vs 代码实际的（14 处，逐条给证据与处理）

这一节是本稿的核心。需求稿是按「理想化的 policy 表」写的，与现读代码在档位、触发条件、工具清单、快照位置、Plan/Act 落点上都不一致。下面每条的格式是：需求稿主张 → 现读证据 → 处理方式。处理方式只有三种：按代码改需求（A）、按需求改代码并在本稿写清改动点（B）、需求本身不可实现需换设计（C）。

C1 需求稿认为存在 `policyMode=safe` 这一档。
证据：档位联合类型只有四个值 `'workspace' | 'ask' | 'auto' | 'full'`（policy.ts:32），`POLICY_MODES` 同四值（policy.ts:34），面板只暴露 `['workspace','auto','full']`（policy.ts:37），默认 `auto`（policy.ts:39）。代码里 `safe` 从来没出现过。
处理：A + B。`safe / ask / deny` 不是档位，是「判定结果」，本稿把它定义为 ConsentVerdict（见 5.2），档位词表不动。需求稿「policyMode=safe 时只读类 safe、写类 ask」这句改写为「mode=workspace 时写类硬拒、只读类放行」，落在路由表 5.3。

C2 需求稿认为 `policyMode=full` 时「全部 ask」。
证据：代码 full 的语义是「完全不问、只留审计」——注释写死在 policy.ts:7，实测行为是文件越界也 allow（policy.ts:215）、进程类无脑 allow 并如实记录 riskFlags（policy.ts:259-264）。
处理：A。保持 full = 放行。若把 full 反转成「全部 ask」，等于把现存的最高放开档降级，会打断 `policy.set`（tool-definitions.ts:223-229）与 `STUDIO_POLICY_MODE`（api/main.ts:117）两条既有通道，且与面板标签「完全放开」（policy.ts:46）直接矛盾。需求稿想要的「最严」已经由 workspace 档表达（policy.ts:214、231-238、269-271）。

C3 需求稿认为 `shell.exec` 每次都问。
证据：auto 档下，进程类只有在命中风险模式（policy.ts:254）或显式 cwd 越界（policy.ts:255）时才 require-consent，否则 allow（policy.ts:256）。
处理：A。这是既有设计，M8 不改；需求稿的诉求由 E1 的「显式 ask 清单」补齐（见 5.3 的 mode=ask 分支与白名单反选）。

C4 需求稿认为 `file.read` 每次都问。
证据：file.* 在工作区内直接 allow（policy.ts:203）；`requiresHumanConsent` 在策略分支里被整体覆盖而不是求或（desktop-host.ts:1134），所以 file.read 的 risk:'privileged'（tool-definitions.ts:66）根本走不到同意闸门。
处理：A。file.read 已经是「区内免问」，需求稿的验收 3 本来就成立；真正要补的是「区外能不能免问」——见 C6。

C5 需求稿验收 4「file.edit 弹同意框」。
证据：同上，file.edit 在工作区内 allow（policy.ts:203），且 file.edit 已在 FILE_TOOLS 里（policy.ts:94，注意 M5 稿当时的清单里还没有 file.edit，这是 M5 之后新增的）。
处理：A + B。区内 file.edit 默认不问；只对「越界」「命中敏感路径」「命中禁止规则」问或拒。这正是 E1 白名单能省掉的无意义弹框。

C6 需求稿把 `search_files` 列为 safe 只读类，但它现在是治理缺口。
证据三条：其一，`search_files` 不在 FILE_TOOLS（policy.ts:94）、不在 PROCESS_TOOLS（policy.ts:96）、不在 EXECUTION_TOOLS（policy.ts:102），所以策略直接落到 `{decision:'allow', reason:'not-governed'}`（policy.ts:274）；其二，它的 risk 是 `'read'`（tool-definitions.ts:116），低于 `CONSENT_MIN_RISK='insert'`（tool-registry.ts:46），`needsConsent` 返回 false（tool-registry.ts:49-51）；其三，宿主侧实现把 `params.root` 原样传下去（desktop-host.ts:339），而 search-files.ts 只校验「非空 + 是绝对路径 + 是已存在目录」（search-files.ts:85-94），不校验是否落在工作区内。
合起来的后果：模型调 `search_files` 并传 `root:'C:\\Users\\<name>'` 就能列目录、按内容检索任意位置的文件，全程无策略、无同意、无审计字段（执行成功仍会进 audit，但 reason 是空）。
处理：B，且这是 M8 必须一起修的（否则「safe 只读类」等于把洞写进设计）。三条改动：把 `search_files` 纳入受到治理的集合（本稿新增 `GOVERNED_TOOLS`），root 只允许工作区根或工作区内子目录（`workspace.resolveWithin(root)`，null 即 `outside-workspace`），并在 5.3 路由表里给它 read 类动作而不是 safe-免审计。

C7 工具 id 拼写不一致。
证据：需求稿写 `web.fetch`，代码是 `web_fetch`（tool-definitions.ts:122，实现 desktop-host.ts:360-369，能力 web-fetch.ts）；`search_files` 两边一致但语义如 C6。
处理：A。本稿全部用代码 id：`shell.exec` / `file.read` / `file.write` / `file.edit` / `file.list` / `file.stat` / `search_files` / `web_fetch` / `web_search` / `python.exec` / `mcp.*` / `workspace.set` / `policy.set`。

C8 白名单文件路径与既有配置目录一致，但权限语义在 Windows 上不成立。
证据：默认配置路径是 `path.join(homedir, '.config', 'deepseek-studio', 'config.json')`（workspace.ts:67-69），所以需求的 `consent-whitelist.json` 放同目录是顺的；但 `persistConfigPatch` 用 `writeFileSync(..., { mode: 0o600 })`（workspace.ts:258），Windows 上 mode 被忽略，0600 不等于「只有本人可读」。另外既有 session 放行是纯内存 + 10 分钟 TTL（bot/registry.ts:41-52、desktop-host.ts:292 取 DEFAULT_SECRET_GRACE_MS，host-token.ts:57 = 10 分钟），落盘白名单是新的持久面，威胁模型变了。
处理：B。白名单沿用同目录，但设计里写清：0600 只对 POSIX 生效，Windows 依赖用户目录 ACL；文件内容不含任何凭据；模型不可写（见 5.4 的写入通道约束）。

C9 快照目录 `<workspace>/.shadow/` 有四个现实问题。
证据：其一，仓库 `.gitignore` 只罩了仓根 `/*.txt`（.gitignore:44）以及若干具体文件，没有 `.shadow`，会把快照变成未跟踪文件，而当前工作树已经 89 条脏（见第 0 节）；其二，快照落进工作区后会被 `search_files`（且修好 C6 之后仍会）扫到，每次 grep 都把历史快照算进结果，形成自噪；其三，需求稿允许「用户同意后编辑工作区外文件」，那时快照里装的是工作区外文件的内容，落进工作区等于把外部文件内容搬进仓库；其四，`.shadow` 目录内的写操作本身又要过一遍策略，递归。
处理：B（改位置，不改语义）。默认放 `~/.config/deepseek-studio/shadow/<workspaceHash>/`，配置项 `shadow.location='config'|'workspace'`，默认 `config`；选 `workspace` 时同时要求 `.gitignore` 有对应条目，且工作区外文件的快照强制写 config 侧。详见 6.2。

C10 需求稿叫「git shadow」，但仓里没有任何 git 调用。
证据：在 `src/**` 全量搜 `git rev-parse` / `git status` / `spawn('git'` 均 0 命中；`package.json` 的 scripts 只有 typecheck/test/build/gate/eval 等，无 git 操作。
处理：A。名字改掉：这是「写前文件快照存储」，不是 git。若真要 git，需要引入 git 二进制依赖、仓库探测、以及把用户工作区的索引状态搅进去——与「只读、不动用户仓库」的审计纪律直接冲突，本稿明确不做。

C11 需求稿的 `plan_act` 工具（输入 task，先调模型出计划再执行）作为能力实现不可行。
证据四条：其一，能力的执行签名是 `execute(params, ctx?)`，ctx 只有 `allowOutsideWorkspace`（capabilities/types.ts:39-51），能力拿不到任何引擎句柄；`ModelEngine` 是宿主持有的接口（model-engine.ts:45-59）。其二，即便能拿到，在工具执行过程中再发起一次 `send` 会撞 `agent-busy`（agent-loop.ts:86 `if (active) throw new Error('agent-busy')`），而工具执行恰恰发生在 active 期间。其三，若想走 kernel 的 TaskLoop，它的工具路径直接调 `hostTools.get(name).execute()`（host-tools-adapter.ts:16-21），注释自己写着「consent 在 invokeTool 层已经做过了」（host-tools-adapter.ts:7），而这条路径上根本没有 invokeTool——等于绕闸。其四，TaskLoop 的记录回放会丢参数：`executeToolRecord` 调 `executor.execute(rec.tool)` 只传工具名（tool-bridge.ts:39）。
处理：C。Plan/Act 上移到宿主编排层：模型用 `plan.propose` 只登记计划（纯记录、无副作用），宿主持有 PlanGate，用户在面板确认后由宿主逐步调 `invokeTool` 执行。用户可见行为与需求稿一致（先看计划、确认后执行、逐步过闸），但落点从 `src/capabilities/plan-act.ts` 改成「纯校验模块 + 宿主 PlanGate」。详见第 7 节。

C12 需求稿「接线进 desktop-host」与 CONTRACTS §6.4 的字面冲突。
证据：CONTRACTS.md:160-163 规定辅助席交付「新模块 + 新测试文件两个新文件；禁止修改任何既有文件」，但它的适用范围在 §6 开头已限定为「主进程派给豆包辅助开发席的独立纯函数包」（CONTRACTS.md:131-133）。
处理：A。§6.4 不约束主进程接线；E1/E2 的纯函数部分按 §6.4 交（两个新文件、不改既有文件），接线部分单独立单、允许改 desktop-host.ts 等既有文件，并在交付说明里分开写。

C13 验收 1/2（tsc 0 错、vitest 全绿）本轮不可核，且基线是脏的。
证据：本轮被要求只读、不跑 build/typecheck/vitest；工作树 89 条未提交（第 0 节），77 条是文档删除——文档删除不会让 tsc 变红，但会让任何「按路径读文档」的脚本红（例如某些审计工具），所以「基线本来就绿」这个前提不能当已知条件用。
处理：A。验收 1/2 的判定权交回实现方，用 `npm run gate`（tools/gate/run.ts:28-35）在改动后现跑，并同时贴 `git rev-parse HEAD` 与 `git status --porcelain` 三个读数。本稿只给判据，不替它宣称结果。

C14 「错误码一律复用 CONTRACTS §6.1」按字面做不到，因为词表里没有「拒绝」类码，而宿主已经在给模型发非词表码。
证据：词表七个码（CONTRACTS.md:145）里没有 denied 语义；而 `executeTool` 的拒绝分支把 `policy-denied`（desktop-host.ts:1139）、`consent-unavailable`（:1154）、`consent-denied`（:1155）、`origin-denied`（:1112）、`unknown-capability`（:1099、:1107）、`malformed`（:1087）直接作为 `reason` 返回，这个 reason 又被 `page-runtime.ts:407` 原样塞进 `tool-call-result.error`，即模型看到的错误字符串。
处理：B。新增三个码并登记，其余按映射表收敛；同时把「既有漂移」列成清单一起修（第 8 节）。
## 3. 冲突裁决（每条只留一个结论，实现方不需要再选）

裁决 1：档位词表不动，新增的是「判定结果」而不是第五个档位。`safe/ask/deny` 属 ConsentVerdict，`workspace/ask/auto/full` 仍是 PolicyMode。
裁决 2：full 档保持「放行 + 如实记 riskFlags」，不改成「全部 ask」。
裁决 3：新增一条与档位无关的「硬拒绝地板」：磁盘格式化、电源控制、对盘根的递归删除、敏感路径写入，任何档位（含 full）都拒。理由见 5.3 的最后一段——这是唯一一处用户同意也不能覆盖的地方，必须显式写进设计而不是藏在正则里。
裁决 4：白名单是持久文件，但只能由面板通道与配置文件写，模型没有任何工具可以写它。
裁决 5：沿用「allow-session」只做内存 10 分钟，不把它升级成持久白名单（改一行代码就会让页面上一次点击变成磁盘上的长期权限，不能顺手做）。

## 5. E1 设计：审批路由（consent-router）+ 持久白名单

### 5.1 落点与分层

E1 新增两个文件：

- `src/host/consent-router.ts`：纯函数，输入策略结论与上下文，输出 safe/ask/deny。只允许 `import type` 引 policy 与 workspace 的类型，不引任何值、不碰 fs、不读 env。
- `src/host/consent-whitelist-store.ts`：白名单的解析与落盘，fs 全部注入（对齐 CONTRACTS §6.3 的可测性要求：文件系统经注入、单测用 mock 或临时目录，CONTRACTS.md:154-158）。

为什么不是 `src/shared/`：R3 规定 shared 不许 import host（tools/audit/boundary.ts:8），而这里必须用 `PolicyMode` / `PolicyReason` 的类型。为什么不是 capabilities：白名单是宿主策略资产，不能下发给能力层。

职责切法（关键）：路由层不重新判断「能不能访问」，它只回答「已有的策略结论要不要问人」。也就是说 `evaluatePolicy` 仍然是唯一的边界判定器（policy.ts:190-275），路由层是对它的补充而非替代。这样「工作区边界唯一入口」这条约束（需求稿硬约束 3）在结构上被保住：路由层拿到的 `resolvedPath` 必须由调用方用 `workspace.resolveWithin` 算好再传进来。

### 5.3 判定顺序与路由表

`routeConsent` 严格按下列顺序返回，先命中先返回（顺序本身就是安全语义，必须有测试钉住）：

1. `policy === 'deny'` → `deny / policy-deny`。策略拒绝不可被白名单、档位、用户同意覆盖。
2. 硬拒绝地板（见下）→ `deny / hard-deny` + `hardRule`。**这一条在 policy 为 allow 时也要执行**，即 full 档也拦。
3. `policy === 'allow'` → `safe / policy-allow`。
4. `policy === 'require-consent'`：
   4.1 `outside === true` → `ask / outside-workspace`（越界永不白名单）。
   4.2 白名单命中 → `safe / whitelist-hit`（带 matchedEntryId）。
   4.3 否则按 `whitelist-absent | whitelist-expired | action-mismatch` → `ask`。
5. 非治理工具（`evaluatePolicy` 返回 `not-governed`）→ `safe / not-governed`，保持既有行为不变。

档位×结果对照（把需求稿的意图翻译成代码语义）：

| mode | 区内文件读写 | 区外文件 | shell 无风险 | shell 命中风险 | 命中硬拒绝地板 |
|---|---|---|---|---|---|
| workspace | allow（safe） | deny（policy-deny） | deny（policy-deny） | deny | deny |
| ask | allow（safe） | ask（可被白名单免问，但越界条目不允许存在） | ask | ask | deny |
| auto | allow（safe） | ask | allow（safe） | ask | deny |
| full | allow（safe） | allow（safe） | allow（safe） | allow（safe，记 riskFlags） | deny |

硬拒绝地板的四条（全部基于 argv 或已 realpath 的绝对路径，不做字符串正则）：

- 磁盘级破坏：`argv[0]` ∈ {`format`, `mkfs`, `mkfs.ext4`, `diskpart`}，或 `argv` 形如 `dd if=...`（对应 policy.ts:127 的 notice 规则，这里升级为硬拒）。
- 电源控制：`argv[0]` ∈ {`shutdown`, `reboot`, `halt`, `Stop-Computer`, `Restart-Computer`}（对应 policy.ts:134）。
- 对盘根递归删除：`argv[0]` ∈ {`rm`, `rmdir`, `Remove-Item`, `del`, `erase`} 且目标解析后等于盘根或 `/`（对应 policy.ts:125，但只在目标是根时硬拒；普通递归删除仍走 ask）。
- 敏感路径写入：`realPath` 落在 `C:\Windows`、`C:\Windows\System32`、`C:\Program Files`、`/etc`、`/usr`、`/bin`、`/sbin`、`/System`、`/Library` 之下，以及 `~/.ssh`、`~/.aws`、`~/.gnupg`、`*.npmrc`、`*.netrc`（对应 policy.ts:129-130 的凭据/系统目录 notice，这里升级为硬拒）。

为什么第 2 步必须在 allow 之前：full 档的语义是「不再询问」，不是「允许格式化磁盘」。现有实现在 full 档对 `shell.exec` 无脑放行并记 riskFlags（policy.ts:259-264），也就是说今天一个 full 档用户让模型跑 `format` 是能跑的。需求稿要的 deny 档正是要堵这个洞，所以它必须是地板而不是提示。这是本稿唯一一处「用户同意也不能覆盖」的判定，必须在 UI/文档里说明，避免被误读为「M8 把 full 档改坏了」。

### 5.4 白名单的文件格式、匹配与写入通道

文件：`~/.config/deepseek-studio/consent-whitelist.json`（与 workspace.ts:67-69 同目录）。

```json
{ "version": 1,
  "entries": [
    { "id": "wl_1a2b3c4d", "toolId": "file.edit", "action": "edit",
      "pathPattern": "src/**/*.ts", "workspaceHash": "sha256:9f2c…",
      "createdAt": 1760800000000, "ttlMs": 86400000, "note": "面板添加" } ] }
```

约束（每条都要有测试）：

- `pathPattern` 必须是相对路径、posix 分隔符；拒绝绝对路径、盘符、以 `/` 开头、任何 `..` 段、含 NUL、长度 > 512。
- 匹配对象是 `relPath`（由 `workspace.resolveWithin` 的结果相对 `root` 得出，workspace.ts:176-179），不是用户传入的原始字符串——否则 `../../etc/*` 这类模式会在字符串层匹配成功。
- glob 只支持 `*`（不跨 `/`）、`**`（跨目录）、`?`（单字符），其余字符一律转义后整串锚定；不支持 `[]`、`{}`（避免 ReDoS 与歧义）。
- 大小写：`process.platform === 'win32'` 时两侧都小写化后比较，与 workspace.ts:111-118 的口径一致。
- `workspaceHash = sha256(realpath(root))` 的短形式；换工作区后旧条目一律不命中（同时由 `invalidateWorkspace` 主动清）。
- 上限：条目 ≤ 200 条、单条 pattern ≤ 512 字符、文件 ≤ 256 KiB；超限 `limit-exceeded` 且拒绝写入。
- 加载容错：JSON 坏、版本未知、字段非法 → 视为空白名单，**绝不部分采用**（部分采用会让一条坏条目把其余好条目一起拖成不可预测状态）。
- 写入：tmp + rename（与 edit-engine.ts:315-318 同一手法），`mkdirp` 后写，POSIX 上 mode 0600；Windows 上显式记录「mode 无效，依赖目录 ACL」。
- 并发：store 内部串行化（同一进程内 promise 队列），避免两个 add 互相覆盖。

写入通道只有两条，都不是模型工具：

1. 面板 ws 命令（新增 `whitelist-add` / `whitelist-remove` / `whitelist-list`），挂在 agent-channel 的 switch 上（agent-channel.ts:183-245 的现有形状），走与 `set-policy` 同级的 token 鉴权（desktop-host.ts:1289 `token: () => apiTokenRing.accepted`）。
2. 用户手改文件（重启后加载）。

明确不做「模型可调 `whitelist.add` 工具」：那等于让模型给自己发长期免问许可证。这一点写进第 12 节。

失效联动，照抄既有 QD-R2-08 的做法：`setPolicyMode` 已清空全部内存放行表（desktop-host.ts:960-962），`setWorkspaceRoot` 两处也清（desktop-host.ts:971-973、:982-983）。M8 在同两处追加 `whitelist.invalidateWorkspace(newHash)`，并且在 `setPolicyMode` 里不做删除（档位切换不该毁用户配置），只让 `mode=workspace` 的 deny 优先于白名单——这一点由 5.3 的第 1 步保证。

## 6. E2 设计：写前快照（shadow-store）+ `shadow.rollback`

### 6.1 落点

新增 `src/host/shadow-store.ts`（纯 IO 模块，fs 注入），新增工具 `shadow.rollback`，并在两个写能力上挂 `ShadowSink`。

为什么挂能力而不挂漏斗：漏斗（executeTool）手里只有原始 params，真正落盘的路径是能力自己算的（file.ts:41-51、edit-engine.ts:202-208）。在漏斗里再算一次就出现「两处路径解析」，任何一处漂移就会把快照写到错误文件上——这是最坏的一类 bug（回滚回错文件）。挂能力的代价是要改两个既有文件（file.ts、edit-engine.ts），收益是快照与被写对象在同一个作用域里确定。

### 6.2 签名与磁盘布局

```ts
// src/host/shadow-store.ts
export type ShadowError = 'invalid-argument' | 'outside-workspace' | 'not-found' | 'io-error' | 'limit-exceeded';

export interface ShadowRecord {
  readonly id: string;                 // sh_<base36 序号>_<8hex>
  readonly path: string;               // 绝对路径
  readonly relPath: string | null;     // 相对工作区根（posix）；外区为 null
  readonly workspaceHash: string;
  readonly toolId: 'file.edit' | 'file.write';
  readonly action: 'edit' | 'write' | 'append';
  readonly kind: 'existing' | 'absent';// absent → 回滚 = 删除该文件
  readonly bytes: number;
  readonly sha256Before: string | null;
  readonly createdAt: number;
}

export interface ShadowSink {
  capture(input: {
    toolId: 'file.edit' | 'file.write';
    action: 'edit' | 'write' | 'append';
    absolutePath: string;
    workspaceRoot: string | null;
    workspaceHash: string;
  }): Promise<{ ok: true; record: ShadowRecord } | { ok: false; error: ShadowError; detail?: string }>;
}

export interface ShadowStore extends ShadowSink {
  rollback(input: { id: string; workspaceHash: string; allowOutsideWorkspace: boolean }):
    Promise<{ ok: true; restored: ShadowRecord; redo: ShadowRecord | null } | { ok: false; error: ShadowError; detail?: string }>;
  list(filter?: { path?: string; limit?: number }): Promise<readonly ShadowRecord[]>;
  prune(): Promise<{ removed: number; freedBytes: number }>;
}

export function createShadowStore(options: {
  dir: string;                 // 默认 ~/.config/deepseek-studio/shadow
  maxPerPath?: number;         // 默认 10（需求稿口径）
  maxTotalBytes?: number;      // 默认 256 MiB
  maxSnapshotBytes?: number;   // 默认 16 MiB
  fs?: ShadowFs;               // readFile/writeFile/rename/mkdir/unlink/stat/readdir
  now?: () => number;
}): ShadowStore;
```

磁盘布局（一条记录两个文件，不做单一索引文件，避免索引损坏导致整库不可回滚）：

```
<dir>/<workspaceHash 前 12 位>/<relPath 的 sha256 前 12 位>/
    sh_7k2m9q_1a2b3c4d.json   记录元数据
    sh_7k2m9q_1a2b3c4d.bin    写前字节（kind=absent 时不存在）
```

保留策略：每个 `<relPathHash>` 目录内按 `createdAt` 保留最近 `maxPerPath`（默认 10）条，超出从最旧删；全局按总字节淘汰最旧。淘汰发生在 capture 成功后与启动时各一次。

### 6.3 生命周期与关键决定

capture：
1. 校验 `absolutePath` 是绝对路径；`workspaceRoot` 非空时要求它落在根内**或**调用方显式说明是越界授权写（把 `relPath` 记 null，`workspaceHash` 记当前 hash）。
2. `stat`：不存在 → `kind:'absent'`、`bytes:0`（新建文件场景，回滚 = 删除）。
3. 存在 → 读全量字节，超过 `maxSnapshotBytes` → `limit-exceeded`，**写操作被拦**（见下面的取舍）。
4. 写 `.bin`（tmp+rename）、写 `.json`（tmp+rename），最后 prune。

rollback：
1. 校验 id 形状 `^sh_[a-z0-9]{1,12}_[0-9a-f]{8}$`，不合法 → `invalid-argument`（防路径穿越：id 直接拼进了目录名，必须先卡形状）。
2. 读 `.json`；`workspaceHash` 不等于当前 → `outside-workspace`（换工作区后不能拿旧快照覆盖新工作区里同名路径）。
3. 目标仍在工作区内（或 `allowOutsideWorkspace && 记录 relPath===null`），否则 `outside-workspace`。
4. **先对当前内容再做一次 capture（redo 记录）**，然后原子写回。理由：回滚本身是写操作，如果不留痕，用户按错一次就永久丢掉中间状态。
5. `kind:'absent'` → `unlink`；文件已不存在 → 视为成功（幂等），但 `restored.kind` 仍为 absent。
6. 不删除被回滚的那条快照（保留审计），由 prune 统一收。

三个必须写进代码注释的取舍：

- 快照失败即写失败。需求稿说「每次写前自动快照」，若快照失败仍放行，那「可回滚」就是空承诺。因此 `capture` 返回 `ok:false` 时，`file.write` / `file.edit` 直接返回 `io-error` / `limit-exceeded`，不落盘。
- 因此 `file.write` 会新出现一个失败面：它现在没有任何大小上限（file.ts:100-111 直接把 content 写下去），而快照上限 16 MiB 会先把大文件写拦下来。这是安全性换来的行为变化，必须写进发布说明（第 11 节风险 3）。
- 不落进工作区。理由见 C9：会污染 git 状态（.gitignore 只有仓根 `/*.txt`，.gitignore:44）、会被 `search_files` 扫到形成自噪、会把外区文件内容搬进仓库。`shadow.location='workspace'` 作为显式选项保留，选它时要求 `.gitignore` 已含该目录，且外区文件快照强制走 config 侧。

| 场景 | 期望 |

## 7. E3 设计：Plan/Act 分离（`plan.propose` + 宿主 PlanGate）

### 7.1 为什么不是 `src/capabilities/plan-act.ts`

四条硬证据见 C11（能力无引擎句柄 capabilities/types.ts:39-51；重入撞 agent-busy agent-loop.ts:86；kernel 路径绕 consent host-tools-adapter.ts:7,16-21；回放丢参数 tool-bridge.ts:39）。补一条工程理由：这个项目里「工具 = 单次幂等动作」，而「计划」是跨多步的状态机，把它塞进 `execute()` 会让能力层第一次拥有跨调用状态，破坏 hostTools 表「无状态可替换」的性质（desktop-host.ts:328-336 就是靠这个性质做注入的）。

### 7.2 两阶段协议

Plan 阶段（模型发起，宿主只登记）：
1. 模型调 `plan.propose`，参数 `{ task: string, steps: [{ tool, params, reason }] }`。
2. 能力只做纯校验与规范化（`validatePlan`），把结果交给 PlanGate，返回 `{ ok:true, data:{ planId, steps, expiresAt, awaiting:'user-approval' } }`。
3. 不执行任何步骤；模型拿到的工具结果明确写「计划已登记，等待用户确认」。

Act 阶段（人发起，宿主执行）：
4. 用户在面板点确认 → 走 agent-channel 新命令 `plan-approve { planId }`（agent-channel.ts:183-245 的 switch 加一个 case，鉴权同 `set-policy`）。
5. 宿主逐个 `await invokeTool(step.tool, step.params, botId)`：每一步都会重走 grant 签发/消费、注册表、origin、策略、同意（desktop-host.ts:1266-1276 → 1068-1168）。
6. 任一步 `ok === false`（或 `isError === true`）即停止，后续步骤不执行，事件里带 `stoppedAt`。
7. 全部成功 → 完成事件。

状态机（每 bot 一份，键 `botId`）：

```
idle --plan.propose--> pending --plan-approve--> acting --(全 ok)--> done
                          |  ^                      |
                          |  +--(ttl/换档/换区/stop)--+
                          +--> discarded
                                         acting --(某步失败)--> failed(stop)
```

### 7.3 类型与签名

- `steps.length` ∈ [1, 12]；越界 `limit-exceeded`。
- 每个 `tool` 必须 ∈ `knownTools`（取自 `registry.list()` 的 id，tool-registry.ts:89-100），否则 `invalid-argument`。计划不能引入注册表里没有的工具。
- `params` 必须是可 `JSON.stringify` 的纯对象，序列化后 ≤ 8 KiB；`reason` ≤ 200 字符。
- 禁止 `tool === 'plan.propose'`（自嵌套）与 `tool === 'policy.set'` / `workspace.set`（计划里改闸门松紧等于自我提权）。
- `task` 非空、≤ 500 字符。

### 7.4 与 consent 的关系（关键裁决）

计划确认不等于同意。需求稿写「Act 阶段每步过 consent 闸门」，本稿严格执行：`plan-approve` 只解锁「开始执行」，不产生任何 grant、不改 policy、不写白名单。因此多步计划会连续弹多次同意框——这是刻意的，因为「一次点击批准五步写盘」等于把闸门削成一步。缓解手段是 E1 的白名单（用户先加条目，之后同类步骤免问），而不是批量授权。

同理，`plan.propose` 本身不弹框（risk `'read'`、无副作用），但它登记的计划在用户确认前不能执行——这两点合起来才等价于「先看计划再执行」。

### 7.5 边界情况表

| 场景 | 期望 |
|---|---|
| 模型不调 `plan.propose` 直接想执行 | 没有待确认计划，`plan-approve` 一律 `not-found`；不影响既有单步调用 |
| 计划里含未注册工具 | `invalid-argument`，整份计划不登记 |
| 计划 13 步 | `limit-exceeded` |
| 计划登记后用户改档位/换工作区 | 计划作废（`discard`），`approve` 返回 `not-found` |
| 计划 10 分钟后才确认 | 过期，`not-found` |
| 步骤 3 失败 | 步骤 4+ 不执行，返回 `stoppedAt:3` |
| 步骤 3 被用户拒绝（consent-denied） | 同上，视为失败停止 |
| 步骤里改 `policy.set` | 计划校验期就拒 |
| 用户在 Act 中按停止 | `signal` 在步骤边界生效；当前步骤不中途打断（见风险 6） |
| 同一 bot 再来一份计划 | 覆盖旧计划并丢弃旧的（一 bot 同时只有一个待确认计划） |

## 11. 风险点（按用户可感知影响排序）

1. 白名单匹配被绕过 = 长期静默免问。载体：UNC 路径（`\\?\C:\`、`\\server\share`）、Windows 8.3 短名（`PROGRA~1`）、结尾点/空格被系统忽略、大小写、软链接/联接点。缓解：匹配对象是 `resolveWithin` 之后的 `relPath` 且再比 realpath（workspace.ts:156-171 已有 realpath 逻辑）；`add` 阶段就把可疑 pattern 拒掉；每条绕过路径一个测试。残留：`realpath` 在目标不存在时 fail-closed 走词法判定，新建文件的越界判定仍可能被联接点父目录绕过——这条已有代码就这么写（workspace.ts:160-167），M8 不新引入，但白名单把它从「问一次」放大成「永久不问」，所以风险等级上升。
2. 硬拒绝地板误伤 = 正常工作被拦。例：项目本身在 `C:\Program Files\...` 下开发，则所有写入被拒。缓解：地板只拦「写入敏感目录」，读取不拦；报错文案给出具体命中的规则名；提供 `~/.config/deepseek-studio/config.json` 的 `hardDeny.extraAllow` 显式豁免（只允许加目录，不允许整体关闭）。
3. `file.write` 出现新的失败面：大文件写不下。现状无上限（file.ts:100-111），快照上限 16 MiB 会先拦。缓解：`limit-exceeded` 文案写清上限与配置项；`config.shadow.maxSnapshotBytes` 可调；发布说明单列一条。
4. 快照把敏感内容落盘。快照 = 文件字节副本，若用户编辑的是含密钥的配置，快照里也有。缓解：目录 0600（POSIX）、不写审计正文、`prune` 保留 10 条即删、支持 `shadow.disable` 但开启时每次写都提示「已留快照」。残留：Windows ACL 不受我们控制（C8）。
5. 磁盘占用失控。10 条 × 每文件 16 MiB × 上千文件。缓解：总预算 256 MiB 强制淘汰；`prune` 在启动与 capture 后各跑一次；面板显示占用。
6. Plan/Act 的超时不是取消。TaskLoop 的既有教训是「race 不取消底层 send」（task-loop.ts:190-199），M8 若给每步加超时也会得到同样性质：超时后底层写可能仍然落盘。裁决：Act 不设步骤超时，只在步骤边界检查 `signal`；否则会出现「界面说失败、文件其实写了」。这条要在代码注释里写明，避免后来人「顺手加个 timeout」。
7. 同意疲劳导致用户盲点允许。多步计划会连弹 N 次。缓解是白名单而不是批量授权（7.4）；同时面板在计划确认页明示「接下来会弹 N 次同意」。
8. 审计环形缓冲丢证据。audit 只留固定条数（audit.ts:11 的 200 条），密集计划会冲掉早期的拒绝记录。缓解：拒绝类 outcome 单独计数并暴露到 statePayload（不改变环形结构）。
