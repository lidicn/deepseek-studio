# DeepSeek Studio 设计稿

> 版本：v1.0  
> 定位：个人自用本地 harness，基于浏览器（DeepSeek 网页版）驱动的本地工具代理  
> 评审原则：**技术不是越多越好，是刚好够守住边界最好。**

---

## 1. 项目定位

Studio 是一个运行在本地的 harness：

- 底层通过浏览器使用 DeepSeek 网页版（非官方 API），行为与真人使用网页无异
- 上层提供本地工具能力：文件读写、命令执行、MCP 工具调用、长期记忆
- 使用场景：个人效率工具，低频、单会话、人工触发

**这不是一个通用 AI 平台，也不是对外服务。**

---

## 2. 能力边界（核心前提）

### 2.1 圈内：该做

| 能力 | 说明 |
|---|---|
| 单文件/短脚本生成与修改 | 质量可用，能落地 |
| 信息检索 + 汇总 | 检索、整理、摘要 |
| 代码审计（明显问题） | 能指出常见缺陷，深逻辑漏洞不可靠 |
| 固定流程自动化 | 步骤可枚举、顺序执行、失败即停 |
| 本地文件/命令/MCP 调用 | 工具编排 |

### 2.2 圈外：明确拒绝

| 能力 | 拒绝原因 |
|---|---|
| 多文件工程级重构 | 模型长上下文与推理深度不足 |
| 需要长链路推理的复杂规划 | 同上 |
| 深层逻辑漏洞挖掘 | 模型能力边界 |
| 开放式多步自主决策（ReAct 循环） | 请求密度不可控，偏离真人行为画像 |
| 并发 / 多会话 / 多账号编排 | 直接踩风控红线，且收益低 |

> **圈外的事不是做不到，是做不稳。做不稳还硬做，就是拿稳定性换演示效果。**

### 2.3 能力天花板

天花板由**模型本身**决定，不在 harness：

- harness 能补：工具调用、文件读写、记忆、检索
- harness 补不了：模型推理深度、长上下文能力

**因此：把 harness 做到极致，也不会让网页版变成更强的模型。往上堆技术不会变强，只会变复杂。**

## 3. 风险模型

### 3.1 风险分层

| 层级 | 性质 | 说明 |
|---|---|---|
| ToS 层 | 确定 | 网页拦截绕过官方 API 契约，账号被处置是平台权利 |
| 风控检测层 | 概率性 | 自动化指纹、请求节奏、会话异常、内容模式 |
| 工程脆弱层 | 必然 | 网页改版、反爬升级、接口字段变化 |

### 3.2 什么会改变风险

**只有改变“请求特征”的东西才是风险源：**

| 能力 | 请求特征影响 | 风险判定 |
|---|---|---|
| 上下文压缩 | 降低请求体积 | 正面，无风险 |
| 可观测/日志 | 不改请求 | 零风险 |
| 长期记忆 | prompt 可能变长 | 中性 |
| RAG | prompt 内容变化 | 中性 |
| 工具循环（自主） | 请求次数不可预测 | **⚠️ 真正的变化点** |
| 子 agent | 并发 + 多会话 + 无人类节奏 | **❌ 高危，明确不做** |
| 多账号 | 账号关联特征 | **❌ 风险换风险，不做** |

### 3.3 风险控制原则

- 单人低频、单会话，不并发多开
- 节奏加随机抖动，不做固定间隔的机械请求
- 账号隔离（试水用小号，主号不赌）
- 监控登录态失效/验证码，出现即降速

## 4. 技术取舍

### 4.1 必做（成本低、收益确定、无风险）

**P0 能力边界文档**

- 把第 2 节内容固化，作为所有后续技术选型的准绳
- 任何新能力先问：服务的任务在圈内吗？在，才做

**P1 错误分类 + 轻量日志**

把失败分成可定位的类别：

```
解析失败 / 登录态失效 / 限流 / 模型输出异常 / 工具执行失败
```

- 每类落一条日志（时间、类型、上下文摘要）
- 成本：约半天
- 收益：所有后续排障的基础，没有它连“哪儿挂了”都判断不了

**P2 交互层收敛**

把网页相关的脏活全部收进 2~3 个文件：

- SSE 解析
- cookie / 登录态管理
- 错误分类
- 页面元素选择器

业务层不直接碰这些细节。

- 成本：约半天到一天
- 收益：网页改版只修一处
- 验收标准：改版时能一句话说清“要改哪几个文件”

> 这不是 Provider 抽象，是“收拾房间”。

### 4.2 按需做（有明确触发条件才做）

**P3 上下文压缩**

- 触发条件：**会话经常变长到爆 / 质量下降**
- 做法：滑窗 + 摘要，保守上限，不上重型方案
- 不满足触发条件：不做

**P4 长期记忆**

- 触发条件：**任务经常接着上次的活干**
- 做法：会话摘要 + 关键事实抽取，轻量版，不上重型向量库
- 每次任务独立：不做

**P5 Provider 契约 + MockProvider**

- 触发条件：**决定用一年以上，且希望改版当天能修好**
- 只做几个月：不做，P1+P2 已足够

### 4.3 明确不做（评审结论）

| 项 | 结论 |
|---|---|
| 自主工具循环（ReAct） | ❌ 圈内任务步骤可枚举，顺序执行是最优解 |
| 子 agent | ❌ 圈外 + 高危（并发/多会话/无人类节奏） |
| 多账号 | ❌ 一个人用多号是风险换风险 |
| 对外 OpenAI 兼容 API | ❌ 把个人风险放大成服务风险 |
| RAG | ❌ 除非确有知识库问答需求，当前没有 |

## 5. Provider 契约（按需，P5）

### 5.1 定位澄清

**Provider 抽象 ≠ 换后端。** 在本项目约束下：

- 不是“为了接 OpenAI/Claude”，那会把风险从个人使用放大到批量调用
- 是“把浏览器这堆脏活关进一个盒子”：隔离易碎逻辑 + 可测试 + 浏览器内驱动方式可替换

### 5.2 核心接口

```ts
type Role = "system" | "user" | "assistant" | "tool";

interface Message {
  role: Role;
  content: string;
  tool_calls?: ToolCall[];
  tool_call_id?: string;
  name?: string;
}

interface ToolDef {
  name: string;
  description: string;
  parameters: JSONSchema;
}

interface ChatRequest {
  messages: Message[];
  tools?: ToolDef[];
  temperature?: number;
  maxTokens?: number;
  stream?: boolean;
}

type StreamEvent =
  | { type: "text_delta"; text: string }
  | { type: "tool_call_delta"; index: number; id?: string; name?: string; argsDelta?: string }
  | { type: "finish"; reason: "stop" | "length" | "tool_calls" | "error"; usage?: Usage }
  | { type: "error"; error: ProviderError };

interface Provider {
  readonly id: string;
  readonly capabilities: Capabilities;
  chat(req: ChatRequest, signal?: AbortSignal): AsyncIterable<StreamEvent>;
  countTokens?(msgs: Message[]): Promise<number>;
}
```

### 5.3 能力声明

```ts
interface Capabilities {
  nativeToolCalling: boolean;   // 网页版: false
  streaming: boolean;
  systemPrompt: boolean;        // 网页版: 需首条 user 消息模拟
  jsonMode: boolean;
  maxContextTokens: number | "unknown";
  tokenizerAvailable: boolean;
  vision: boolean;
  toolChoice: boolean;
}
```

### 5.4 浏览器 adapter 必须自己处理的三件事

开源模块通常假设底下是真正的 API，这三块必须自写：

1. **文本协议解析器**：网页版无原生 tool_calls，需从流式文本解析出标准 `tool_call_delta`
2. **上下文窗口探测**：网页版黑盒，保守估算或动态探测
3. **tokenizer 缺失降级**：用字符数/4 估算

这三块全在 adapter 内，业务层无感。

### 5.5 分层结构

```
┌─────────────────────────────┐
│  压缩 / 记忆 / 工具编排 / 日志  │  ← 只认 Message[]
├─────────────────────────────┤
│         Provider 契约         │  ← 分界线
├─────────────────────────────┤
│   浏览器 adapter（野路子）     │  ← 脏活全关在这里
└─────────────────────────────┘
```

## 6. 工具调用模式

### 6.1 当前模式：编排式（保留）

```
harness 写死：先调 A → 再调 B → 失败即停
```

- 请求数确定，模型只负责“填参数”
- 从风控看 = “一次输入 + N 个固定步骤”，像人按流程操作
- **风险极低，是优点不是缺陷**

### 6.2 自主式（不做）

```
模型 → 决定调什么 → 看结果 → 再判断 → ... → 最终回答
```

- 请求数不可预测（1~20 步）
- 单会话请求密度上升，风控面真正变化
- 只在“任务本身开放式、必须边做边看”时才有价值，而这类任务已在圈外

## 7. 落地路线

### 第一阶段（约两天）

```
P0  能力边界表（今天就能写完，零成本）        ★★★★★
P1  错误分类 + 轻量日志（半天）                ★★★★★
P2  交互层收敛（半天~一天）                    ★★★★☆
```

完成后：Studio 从“能跑但脆”变成“能跑且改得动”。

### 第二阶段（按需触发，不预先做）

```
P3  上下文压缩      ← 会话经常变长时才做
P4  长期记忆        ← 任务经常接续时才做
P5  Provider 契约   ← 决定长期维护时才做
```

### 第三阶段（不做）

```
自主工具循环 / 子 agent / 多账号 / 对外 API / RAG
```

---

## 8. 评审结论

1. **不要把“迭代”理解成“加能力”，把“迭代”理解成“把已有的能力守稳”。**
2. Studio 真正缺的不是压缩、记忆、agent，是“改版时改得动、出问题时查得到”这两个工程底线。
3. 技术不是越多越好，是刚好够守住边界最好。
4. **先花两天做完 P0~P2，然后停下来，用三个月。**
5. 三个月里如果没遇到“会话爆了”或“改版修不动”，说明 P3 以后的东西根本不需要。
6. 别为了“像个现代 AI 系统”去写不需要的代码。

## 附录：判断清单

任何新需求进来，依次问：

1. 这个任务在能力圈内吗？——不在，拒绝
2. 它会改变请求特征吗？——会显著改变，谨慎或不采纳
3. 它有明确的触发条件吗？——没有，不做
4. 不做它，会在什么场景下疼？——想不出具体场景，不做
5. 它的成本是几天？——超过两天且非 P0~P2，重新评估
