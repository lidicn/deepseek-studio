### 1.3.1 我原稿错在哪：只看 `:2498` 就下了结论

原稿（Core）读 `main-world-interceptor.ts:2498` 的 `parsed.prompt = continuationPrompt`，就断言"续跑轮把首轮注入的 head 整块丢掉了"，据此写下"判据 2/3 不成立"。**这个结论是错的**：`:2498` 只是**设置**了 prompt 字段，这次请求**还没发出去**；真正落盘的是后面那次 `send()`，而那次 `send()` 还会再走一遍注入。

**教训（写进文档防复发）**：

1. **注入链路上"谁最后一次改写 body"，要看 send 的落点，不能看赋值语句的位置。** 赋值 ≠ 落盘。
2. **断言必须打在真机口径上**（`body.prompt` 的字节），不能靠读代码推。Verify 自己也踩过同类的坑并已自纠（P33：首版拿整包 body 比，报出"首差 78 B"的假数字；改为按 prompt UTF-8 字节比较才得到 7,071 B）。
3. **head 必须按 prompt 口径测**：整包 body 的前 256 B **每轮都变**（JSON 头部字段 `chat_session_id` / `parent_message_id` 随轮变化）。拿 body 头判断"head 稳不稳"会得到"每轮都变 → 增量收益为零"的错误结论（Verify P32/F2）。

### 1.3.2 为什么今天 head 是在的（源码链路，PM 复核 + 我已独立验证）

```
续跑轮构造 body：      parsed.prompt = continuationPrompt        （:2498，不含 head）
续跑轮发请求：         xhr.send(bodyStr)                          （:2737）
  └─ xhr = new XMLHttpRequest()                                  （:2524）★ 用的是**被 patch 过的原型**
       └─ proto.send 被替换（:1516）→ prepareChatSend()           （:1545）
            └─ 唯一旁路守卫是 inFirstAttemptResend（:1553）
                 └─ 它只在 resendVerbatim 时为真（:2423），auto-continue 不走这条路 → 不旁路
            └─ prepareOutgoingBody(raw, pending, originalTask)   （:1075 / :1555）
                 ├─ :1128 stripCapabilityPromptFromText(prompt)  → 续跑 prompt 里没有 marker → 原样返回
                 └─ :1129 `${buildCapabilityPrompt(taskText)}${memoriesBlock}\n\n${cleanPrompt}`
                        ★★ 能力块（S1 + S2 MCP 目录）在这里被**原样拼回**
```

⇒ **续跑轮的 head 是「二次注入补回来的」**，不是"首轮带来的"。这正是 §6 风险 R8 要防的：**判据 2 目前是靠这个副作用成立的**，任何"顺手把重复注入当 bug 修掉"的改动都会静默破掉它。

### 1.4 现状的「请求表面积」形状（修订：head 每轮原样重发，真实冗余只有 S3）

以扁平协议的一轮 body 为例（键序以真机为准；Verify 已确认是 `prompt` 扁平形态）：

```
{ chat_session_id, parent_message_id, prompt: "<head><分隔><tail>", ... }

head = S1 能力块(4,495) + S2 MCP 目录(≤3,000) + [S5 技能段] + [S6 记忆段]
tail = 首轮：页面原文本 ｜ 续跑轮：S3(1,155) + V1 original_task + V2 tool_results + V3 续跑指令
```

- **head 在续跑轮里原样存在**（Verify：前 7,071 B 逐轮全等，首差字节恰好落在能力前缀末尾）——**不是被丢掉**；
- 每轮**重发**这 7,071 B **不是浪费**：Verify §117 明确——「任何『只发增量』方案只要不再重发这 7,071 B 前缀，head 就会变 → 会触发上游父链断一次。结论：增量方案必须连同前缀一起保持字节一致（或让服务端缓存前缀），否则要付一次断链代价。」→ **前缀必须继续原样重发，M1.5 不能改成"只发增量"**；
- **真实冗余只有 S3**：`TOOL_CATALOG_TEXT`（1,155 B）里的 10 个 studio 工具行，在 S1 的「## 可用工具」段（`:782-791`）里**已经有一份** → 纯重复，且位置在 head 之后、变动区之前 → **每轮白带 1,155 B**；
- 服务端仍会把整段历史拼在模型输入前面（dsh 实测：usage 估算 token 几乎不变），模型看到的是「历史 + 又一份历史」→ 有效上下文对折（dsh-webin 同源结论）。**这一条 M1.5 不解决**（要解决得改协议，见 §7.2）。

## 2. 拆链方案（**修订版：价值重估后大幅收缩**）

### 2.0 价值重估（诚实版：能省多少写多少，不能省的写"现状已满足，M1.5 无需改"）

| 目标 | 现状（Verify 真机基线） | M1.5 要不要动 |
|------|------------------------|--------------|
| 判据 1 · 目录段 ≤ 3,000 B | ✅ 已达标（2,447 / 2,275 B，逐轮恒定） | **不需要改**。只补一条回归护栏测试 |
| 判据 2 · 续跑轮 head 不变 | ✅ 已达标（prompt 前 4,096 B 逐轮全等；首差 = 前缀边界 7,071 B） | **不需要改**。但**必须锁死**——它靠"二次注入把 head 拼回来"这个副作用成立（§1.3.2），任何动这条链路的改动都会静默破掉它 |
| 判据 3 · 工具名集合相等 | ✅ 已达标（62 个 MCP 名 + 10 个 studio 名，两轮都是 72） | **不需要改**。只补一条回归护栏测试 |

**不能省的（明说）**：

- **7,071 B 的稳定前缀本身不能省**。Verify §117：任何"只发增量"方案只要不再重发这段前缀，head 就会变 → 触发上游父链断一次。→ M1.5 **不做**"只发增量"，前缀必须继续逐字节原样重发。
- `original_task` / `tool_results` / 续跑指令：模型语义必需，不动。
- 「历史 + 又一份历史」导致的有效上下文对折：M1.5 不解决（要改协议，见 §7.2）。
- 记忆段：真机实测恒 **0 B**（P1：`memory.select` 页面通道 149/166/170 ms > 120 ms 预算，PM 另开卡）→ M1.5 不涉及，且该 0 B 会让 tail 侧字节读数失真。

### 2.1 目标形态（修订：现状形态基本保留，只去冗余 + 定契约）

```
prompt = HEAD + "\n\n" + TAIL
         ├── 逐字节稳定       └── 每轮重建
```

- **HEAD 的归属（本次要写死的显式契约）**：
  - **唯一生成点**：`buildCapabilityPrompt(taskText)`（`main-world-interceptor.ts:976`）；
  - **唯一拼接点**：`prepareOutgoingBody` 的 prompt 分支（`:1129`）；
  - **续跑轮的 `parsed.prompt` 只能是"不含 head 的 tail"**（`:2498` 设的值不得再带 head）；
  - HEAD 的内容来源：今天 = 每轮按 `originalTask` 重算（因 `originalTask` 在轮间不变 → 字节稳定）。若采纳"会话内冻结"（可选增量）→ HEAD = 会话快照。
- **TAIL**：
  - 首轮 = 页面原文本（+ 记忆段/技能段按现状位置）；
  - 续跑轮 = **去掉 S3 之后**的 `V1 original_task + V2 tool_results + V3 续跑指令`。
- 与现状的**唯一差别**：续跑轮 tail 里**没有 S3 了**；其余形态不变（HEAD 仍然每轮原样重发——这是必须的）。
- **与 `prepareOutgoingBody` 的「剔旧再拼」层怎么共存（实现者最易拼错的地方，必须写死）**：
  `prepareOutgoingBody` 的 prompt 分支本来就是「**先剔旧块、再拼新块**」（`:1128` 剔、`:1129` 拼）。
  若续跑轮/任何调用方**自己也拼了一份 head**，就会与 `:1129` 的拼接触手 → **重复 head**（模型看到两遍能力块与目录）。
  → **二选一，本设计选第二种**：
  - 选项 ①（不选）：让 `:1129` 改用会话快照的 head，续跑轮仍带 head → 需要 `:1129` 知道"快照里已有 head 就不拼"，多一个判定分支，且 head 有两个来源。
  - **选项 ②（本设计）**：**head 只有一个拼接点 = `:1129`**；续跑轮 `:2498` 设的 `parsed.prompt` **只能是 tail**（不带 head、不带目录、不带技能/记忆段）；`:1128` 的「剔旧」保留（它服务"页面自己带的旧块"这一现实场景）。
  - 配套护栏（§2.3 改动 4）：若 `:1129` 发现 `cleanPrompt` 里已有 `[studio-tool-capability]` 标记 → 记 trace `m15.head_duplicated` 并只保留一份 → **重复 head 立刻暴露，而不是静默发出去**。

### 2.2 新增数据结构（**可选增量**，仅当采纳"会话内冻结"时才需要）

### 2.4 快照的建立与失效（**仅当采纳可选增量（会话内冻结）时才需要**）

#### 2.4.0 先判「工具意图」：寒暄首轮不许冻结一个偏掉的目录

**要防的产品级风险**：首轮若是一句寒暄（"你好" / "在吗" / "谢谢"），按 `taskText` 打分选 top-k 会选出一批与真实任务无关的工具；而快照**冻结整个会话** → 整个会话都带着一份偏掉的目录。这不是实现细节，是产品行为。

**默认取值**：首轮**先判工具意图**，再决定 S2 的形态。判定为「无工具意图」时，S2 **不选 top-k**，改用**纯名称索引形态**：62 个 MCP 工具名全部以 `### 其他工具（仅名称）` 形态列出（复用 `catalog-selection.ts:120-124` 的 `renderCatalogNameIndex`），**一条描述都不展开**；studio 工具仍在 S1 里。

**判定规则（写死常量，不许"看起来像"）**——两个条件**同时**满足才算「无工具意图」：

| 条件 | 判据 |
|------|------|
| 长度 | 归一化（去首尾空白、连续空白压成单空格）后 **≤ 12 个字符** |
| 动作词 | **不含**任何动作词（下表） |

动作词表（默认取值；落点建议 `src/shared/injection-blocks.ts`，与 `catalog-selection.ts` 同款「常量 + 单测」规矩）：

| 类别 | 词 |
|------|----|
| 文件类 | 文件、目录、文件夹、路径、读取、读一下、写入、写一下、新建、创建、编辑、删除、重命名、拷贝 |
| 命令类 | 命令、命令行、执行、运行、跑一下、脚本、终端、shell、powershell、bash |
| 检索类 | 搜索、搜一下、检索、查找、查一下、日志、报错、异常、堆栈、trace、崩溃 |
| 记忆类 | 记住、记一下、别忘了、记忆 |
| 工程类 | 代码、仓库、git、提交、分支、依赖、npm、pnpm、构建、编译、部署、数据库、sql、db |
| 英文补充 | read、write、edit、delete、search、grep、run、execute、script、fix、debug、build、deploy、commit、test |

**为什么选纯名称索引**：它对 `taskText` 不敏感 → ① 寒暄不会选出偏掉的目录；② head 照样能在会话内冻结（**判据 2 不破**）；③ 62 个名字仍然齐（**判据 3 不破**——名字在就能按名调用，描述只是锦上添花，见 `catalog-selection.ts:19-21` 的同源论证）。
代价：该会话内模型看不到 MCP 工具描述。**这是有意的取舍**——目录选错的代价（整个会话带偏目录）远大于看不到描述。

**回退口径**：

1. **纯名称形态若 > 3,000 B**（工具名异常长时的防御性兜底）→ 回到 **top-k 形态**（按当前 `taskText` 选），并在 §8 记一条已知限制「寒暄会话的目录可能与真实任务无关」。
   （按 62 个名字平均 12 字符估算，纯名称形态约 **950–1,050 B**，远低于 3,000 B → 该分支预计不会触发；**实测字节待 Verify 基线**。）
2. **判定为「无工具意图」后，同一会话内不升级**为 top-k——升级 = 改 head = 链断一次。真实任务若到第二轮才出现，目录保持纯名称形态（名字齐、可按名调用，只是没有描述）。
3. **误判方向代价不对称**：把真实任务误判成寒暄 → 只丢描述（名字仍齐，判据 3 仍成立）；把寒暄误判成有意图 → 冻结一份偏目录（整会话受损）。→ **阈值取保守侧**：长度上限放宽、动作词表取宽。
4. 长度阈值与动作词表的任何变更**必须有单测盯着**（照 `tests/desktop/catalog-budget.test.ts` 的规矩），否则词表一改就悄悄改行为。

#### 2.4.1 快照的建立 / 复用 / 失效

| 情形 | 默认取值 | 回退口径 |
|------|---------|---------|
| 首轮（`parent_message_id === null` 的新用户消息，`main-world-interceptor.ts:655`） | **建立**快照：先按 §2.4.0 判「工具意图」→ **有意图**：用当前 `taskText` 选一次 MCP 目录；**无意图**：纯名称索引形态（62 个名字，不展开描述） | 若此时 MCP 清单为空 → 快照里 S2 为空串，后续轮次**不再补**（补就会改 head）；若纯名称形态 > 3,000 B → 回退 top-k 形态（§2.4.0 回退口径 1） |
| 同一会话内后续轮次 | **复用**快照（不重选、不重建、不升级） | — |
| 会话切换（`chat_session_id` 变化） | **重建**快照 | 重建即新会话，链自然断开，无影响 |
| 会话内 MCP 工具清单刷新（`mcp.list` 返回新工具） | **不重建**（保住 head） | 新工具在会话内**不可见**；回退口径：提示模型"新工具需新会话"，或在下个**新会话**生效 |
| 会话内技能清单刷新（S5） | 只影响 tail | 无 |
| 记忆刷新（S6） | 只影响 tail | 无 |
| 快照缺失 | **回退到今天的行为**（旧 prompt 形态） | 保证任何情况下不发畸形 body；且**不得现场构建快照**（现场构建即改 head） |

**「续跑轮先于快照建立」的实际触发条件**（实现者据此决定要不要写这个分支——**要写**，且下列四条都是现实路径）：

1. **首轮走了「原样重发」旁路**：`loopState.inFirstAttemptResend` 为真时 `prepareChatSend` 直接用 `raw`、不跑注入（`main-world-interceptor.ts:1553-1555`），于是 `lastChatBody` 里**根本没有** stableHead；紧接着出现工具结果 → auto-continue 触发 → 续跑轮找不到快照。
2. **注入晚于首条消息**：页面先发了一条消息，Studio 的 entry.js 才注入（`STUDIO_DISABLE_INJECT=1` 的降级路径，或注入脚本加载晚于用户操作）。
3. **模块级快照被重置**：页面 reload / entry.js 重新求值 → `sessionSnapshot = null`，而页面仍带着旧的 `lastChatBody` 继续续跑。
4. **会话切换与建快照的竞态**：用户切会话后立刻触发续跑，`chat_session_id` 与快照 key 不一致 → 视为缺失。

→ 实现要求：快照缺失时，续跑轮走**旧形态**（今天的整体替换），并在 trace 记 `m15.snapshot_missing`；**禁止**在续跑轮现场构建快照（那等于改 head → 断链）。

### 2.5 为什么 S3（`TOOL_CATALOG_TEXT`）要从续跑轮删掉（**M1.5 的主交付**）

- **理由修订**：原稿写的是"补回缺失"（续跑轮缺目录所以要补），**错**——续跑轮的目录不缺，是 **head 二次注入时已经带上了**（§1.3.2）。
  正确理由是**纯重复**：S3 里那 10 个 studio 工具行，在 head 的 S1「## 可用工具」段（`:782-791`）里**已经有一模一样的一份**；
- 删掉 S3 后，续跑轮的工具名集合仍是 **72**（62 MCP 来自 head 的 S2 + 10 studio 来自 head 的 S1）→ **判据 3 不受影响**（Verify 已实测集合相等）；
- **省 1,155 B/轮**（`TOOL_CATALOG_TEXT` 实测 1,155 B，10 个工具名与 PM 实测一致）；
- 它位于 head 之后、变动区之前 → 每轮**纯白带**，是现状里唯一的真实冗余。

### 2.6 （可选增量）S2 冻结与「工具名集合相等」的关系

> 仅当采纳"会话内冻结"时才有意义。**现状（不冻结）已同时满足判据 2/3**（Verify 实测），冻结是**额外的稳定性收益**，不是判据要求。
>
> 冻结的真实价值：现状下 MCP 目录按 `taskText` 打分（`catalog-selection.ts:154`），
> 而 `taskText` 取 `originalTask`（`:1555`）→ **同一会话里用户发新任务时 originalTask 更新 → 目录重选 → head 变化**。
> Verify 运行 A 的相邻轮首差字节在 7,071 / 8,938 / 13,200 / 7,072 之间漂移，正是这个现象的读数证据。
> 冻结可让前缀长度恒定 → 上游缓存命中更稳。代价是会话内看不到新工具 + 寒暄偏差（§2.4.0）。

## 3. 三条判据的落地测法（**修订：三条已达标 → 本节是回归护栏**）

> **定位变化**：三条判据在 Verify 真机基线上**已全部达标**（§1.3）。因此本节不再是"验收新功能"的测法，而是
> **"锁死现状 + 证明删 S3 没把任何一条弄坏"**的护栏。
> 通用要求（路线图 §19.3 引 dsh 教训 ④）：**断言一律打真实入口**——不打私有函数，打「真机 body / 真机 prompt」。
> **口径纪律（Verify P33/F2）**：head 一律按 `body.prompt` 口径测；整包 body 的前 256 B 每轮都变（JSON 头部字段），拿 body 头判会得到假结论。

### 3.1 判据 1 · 目录段（口径 B）≤ 3,000 B

## 6. 风险（**修订：按修订后的方案重列**）

1. **删 S3 会不会让模型看不见 studio 工具？——不会，但要用负控钉住。**
   S1 的「## 可用工具」段（`:782-791`）已经列了同样 10 个 studio 工具（带参数说明），S3 是同一内容的**第二份副本**；Verify 已实测两轮集合都是 72（62 MCP + 10 studio）。
   但"集合相等"不等于"模型同等对待"——S1 那一行是能力声明，S3 那一段是目录标题。→ §3.3 的负控：断言续跑轮 prompt 里 `## 可用工具` 段**出现次数 == 1**，且 10 个 studio 名一个不少。
2. **head 目前靠"二次注入"这个隐式副作用成立（最需要防的一条）。**
   今天 head 出现在续跑轮里，是因为续跑轮的 XHR 也走 `prepareOutgoingBody`（§1.3.2）——**看起来像 bug，却正是判据 2 的承重墙**。
   任何"把重复注入当 bug 修掉"的改动（很合理：续跑轮明明已经设过 prompt，为什么还要再拼一次能力块？）都会**静默破掉判据 2**，且当场没有任何报错。
   → 必须有 §3.2 的回归护栏 + §2.3 改动 4 的重复 head trace 断言。
3. **不能改成"只发增量"**（Verify §117）：head 必须每轮**原样重发**；任何"省掉前缀"的优化都会付一次上游父链断链的代价。M1.5 不做这类优化。
4. **首差字节会前移（预期变化，不是回归）**：删 S3 后续跑轮的首差字节从 ≈7,071 B 前移到 ≈5,916 B。验收脚本要能区分"预期前移"与"真的坏了"——判据是**前 4,096 B 仍逐轮全等**。
5. **记忆段恒 0 B（Verify P1，PM 另开卡）**：`memory.select` 页面通道 149 / 166 / 170 ms 稳定超过 120 ms 预算 → 记忆从未被注入，迟到结果也没进后续轮。
   → M1.5 复测时**不要把 0 B 当成 M1.5 的成果或回归**；它会让 tail 侧字节读数失真（是"没有"，不是"小"）。
6. **head 口径必须是 prompt**：整包 body 的前 256 B 每轮都变（JSON 头部字段）→ 任何按 body 头做的缓存/增量判断都是假结论（Verify F2/P33）。
7. **首轮原样重发的逐字节幂等**（`:1553-1555`、`:2488-2494`）：动 `prepareOutgoingBody` 时别碰 `inFirstAttemptResend` / `resendVerbatim` 这条分支，否则重试不再幂等（F8 修复，勿破坏）。
8. **仅当采纳"会话内冻结"（可选增量）才有的风险**：① 目录冻结 → 会话内新工具不可见 + 寒暄偏差（§2.4.0 / §2.4.1）；② 记忆块若随冻结一起移位 → 模型对它的权重下降（默认口径：记忆块留在 head 之外、紧邻 head 的位置）。**不采纳冻结就没有这两条风险。**
9. **entry.js 需要重建**：实现卡改完 `src/inject/**` 后要重建 `src-tauri/inject/entry.js`（本卡明确不做）。
