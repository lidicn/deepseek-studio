**A（数据目录按发布形态隔离）+ C（出厂重置入口）并行实施**；B（首启不继承开发期字段）只覆盖「干净机首启」，**对已经脏过的机器无效**，因此只作 A 的配套、不单独做。

## 2. 首启写盘判据（干净机的可执行定义）

`src/api/config-loader.ts:172-197`：只有 `token`/`secret` 缺失时才写盘；写入内容是「磁盘原文件（不存在则 `{}`）+ `host/port/token/secret`」，`workspaceRoot` / `policyMode` **仅在非空时追加**。

→ **干净机首启后 `config.json` 必须恰好是四个键**：

```json
{ "host": "127.0.0.1", "port": 8760, "token": "<32>", "secret": "<32>" }
```

配套事实（已核）：
- **`apiKey` 不会被生成或写入**：只从 `DEEPSEEK_STUDIO_API_KEY` 环境变量读（`config-loader.ts:210-225`）；空 key 时 `main.ts:111` 不发起 ApiEngine 探测。
- `policyMode` 不写 → 运行时回落 `DEFAULT_POLICY_MODE`（`src/shared/policy-contract.ts:14` = **`auto`**），**不是开发期的 `full`**。
- `workspaceRoot` 不写 → `file.*` 能力不可用，`main.ts:168` 会打印明确提示（这是**预期**，不是故障）。

## 3. `workspaceRoot` 的性质（决定「装版默认该不该有」）

- 它是**用户工作区根**，不是开发专属字段：`src/host/workspace.ts:19`（`WORKSPACE_CONFIG_KEY`）→ `resolveWorkspaceRoot()`（env `STUDIO_WORKSPACE_ROOT` > config `workspaceRoot`）。
- 语义：工作区内自动放行、区外按策略（`createWorkspace()` 的 `lexicallyInside` 判定）。
- **缺失时**：`file.*` 不可用，并明确提示「请设环境变量或用户配置 workspaceRoot」（`src/api/main.ts:165-169`）。
- 结论：**装版默认应为空**，由用户在 UI 里选目录（`studio-project-picker.ts` 已有选择入口）；把开发树路径塞进去是**污染**，不是「默认值」。

## 4. 三个口径

### A. 按发布形态隔离数据目录（推荐，需改代码）

| 位置 | 现状 | 隔离后 |
|---|---|---|
| host 配置 `~/.config/deepseek-studio` | 硬编码 homedir（`config-loader.ts:82`，**不认** `STUDIO_CONFIG_DIR`） | 装版 → `%APPDATA%\com.deepseek.studio\config\`；dev 保持 `~/.config` |
| WebView profile `%LOCALAPPDATA%\…\EBWebView` | 与 dev 共用（同 identifier） | 主窗用 `WebviewWindowBuilder::data_directory()` 指到独立目录（**已有先例**：`main.rs:929` 给 bot 窗口这么干） |
| Rust 侧日志与 profile `%APPDATA%\deepseek-studio` | 与 dev 共用（`dirs::config_dir()`） | 注入 `STUDIO_LOG_DIR` 指到装版数据目录（见 §1.5 / §8 第 2 段） |
| host 运行时（app_data） | release 已用 `app_data_dir()`（`main.rs:1263-1269`） | 不变 |

**必须一起修的一处不一致（实测矩阵）**：全仓**7 个模块认 `STUDIO_CONFIG_DIR`**，**唯独 `config-loader.ts` 不认**（`:82` 硬编码 homedir），生产调用 `loadConfig()` 也不传 override。
→ 只加环境变量不改 `config-loader`，会出现「设置写进 A 目录、宿主从 B 目录读」的经典错位。**这是 A 方案的第一优先级前置修复**（完整矩阵见 §8）。

**代价**：
1. 改 Rust（注入 env）+ 改 `config-loader`（认 env）——约 2 处小改；
2. dev 与装版数据分离后，排障时容易看错文件 → 启动日志固定打一行 `[studio] config dir: <path>`；
3. **升级路径**：老用户数据在旧目录，需一次性迁移（拷贝不删除，失败可回滚）。

**迁移路径（PM 裁定：自动拷贝，不做弹窗询问）**：首启时若「新目录无 config.json」且「旧目录有」→ 拷贝 `config.json` / `memories.db` / `memories.db.audit.key` / `storage.json` / `shadow/` 到新目录（**不删旧**；`shadow/` 与 `memories.db` **必须同批次**拷贝，否则索引与内容错配），写 `migration.log` 到新目录，并在面板显示「已从旧目录迁移」。
理由：老用户换版不该丢记忆；拷贝无损、天然可回滚；不做会导致老用户数据「看起来消失」。**不弹窗询问**——这里没有需要用户权衡的取舍。

### B. 同目录 + 首启不继承开发期字段（只能当过渡）

- 机制：首次启动时只写四个键（这本来就是现有行为），并**忽略**磁盘上已存在的 `workspaceRoot` / `chatRooms` / `policyMode`。
- **硬伤**：本机这类「已经脏过」的机器 `config.json` 早就存在，**首启分支根本不会走到** → 要生效必须先删配置，等于 C。
- 另一个硬伤：**分不清「用户自己建的 chatRooms」与「开发期测试留下的」**——除非引入 `.dev-mode` 标记（开发时写、装版不认），那就退化成 A 的弱化版。
- 结论：**只适合作为 A 的配套（新目录首启自然满足），不要单独实施。**

### C. 出厂重置入口（PM 裁定：与 A 并行，放设置面板）

- 形态：设置面板「**恢复出厂配置**」→ **二次确认** → **自动备份**（`<dir>.bak-YYYYMMDD-HHmmss`，**面板必须显示备份路径**）→ 清理「可重建的开发期残留」。
- **独立入口**：「**清空会话历史**」是**另一个按钮**（只清 `storage.json`，不动配置与记忆），同样二次确认——两件事不能混成一个「重置」。
- 清理清单（只删这些）：
  `config.json.bak-*` / `memories.db.bak-*` / `memories.json` / `bot-windows.json` / 开发期 `mcp-servers.json` / `personas/` / `skills/example-skill` / `runs/`；并从 `config.json` 里删 `workspaceRoot`、`chatRooms`、`policyMode`（回落默认）。
- **绝不删**：`memories.db` + `memories.db.audit.key`、`storage.json`（会话历史）、`shadow/`。
- WebView 登录态：**进程内删不掉**（文件被占用）→ 要么在 A 之后「换一个全新 data_directory」，要么退出时标记、下次启动前清目录。

### 8.3 形态判定：`STUDIO_DISTRIBUTION`（第 2 段一并注入）

**为什么需要它**：装版与 dev 有四处行为必须分叉（`mcp-servers.json` 写不写示例、`skills/` 建不建、读不读 `~/.agents/skills`），而 Node 侧**不许自己猜**「我是不是装版」——那会与 Rust 判定不一致，重演「两个目录名来源不同」的同类问题。

**裁定口径（PM 终裁，2026-11-06）**：
- **注入**：Rust 在 spawn sidecar 时按**实际走的那条分支**注入 `STUDIO_DISTRIBUTION=installed|dev`，与 `STUDIO_CONFIG_DIR` / `STUDIO_LOG_DIR` **同一批算出、同一来源**。
- **载**体：`HostEntry` 加结构体字段（如 `distribution: Installed | Dev`）。三个构造点各自必须填对：`main.rs:1111` → `Dev`；`:1134` 与 **`:1154`** → `Installed`。**编译器强制**，将来新增分支漏填会被抓到，不靠「看代码走哪行」（重构一次就错位）。
- **判定**：`installed` ⇔ Rust 走 `:1130` 之后的任一 return（`:1134` 或 `:1154`）；`dev` ⇔ 走 `:1111`（Bundled）或 `:1127`（Tsx）。
- **fail-safe**：Node 读不到 `STUDIO_DISTRIBUTION` 或值非法 → **按 `installed` 处理**。理由 = **判错代价不对称**：dev 误判 installed → 开发者少个示例配置、自己立刻发现；installed 误判 dev → **用户机被写上假 MCP + 空技能目录，没人会发现**。
- **Node 侧铁律**：`ensureMcpConfig` / `ensureSkillsDir` / `resolveSkillsDir` 的分支**只读 `STUDIO_DISTRIBUTION`**，**不读 `cfg!(debug_assertions)`、不自己判断 exe/resource 路径**。

**两个目录怎么注入（实现口径，2026-11-06 施工批定）**：
- `STUDIO_CONFIG_DIR` = `<data_dir>/config`、`STUDIO_LOG_DIR` = `<data_dir>/logs`（`<data_dir>` = release 的 `app_data_dir()`；dev 两个都**不注入** → 开发期行为逐字节不变）。
- **⚠️ 只设子进程 env 是不够的**（施工中实际踩到）：`cmd.env(...)` 只作用于 **Node 子进程**；Rust **自己**的监管/崩溃日志若读父进程 `std::env::var("STUDIO_LOG_DIR")`，在装版里**永远 Err** → 回落 `dirs::config_dir()/deepseek-studio/logs`（目录 ④）→ 又出现「日志在旧目录」。
  → **正确做法**：Rust 侧直接用 `HostEntry.log_dir`（sidecar 的 `host_entry_log_dir()`），**与子进程同一个值，不存在两套 env**；**不用 `set_var`**（多线程下 unsound，Tauri 主线程 + 异步运行时是多线程）。
  → 回归用例：`sidecar::td_tests::supervisor_takes_log_dir_from_host_entry`（断言装版 `crash_log_path` 取自 `log_dir`，而不是回落 `~/.config` 那条）。

**不用什么（避免下次有人再提）**：
- **不用 `cfg!(debug_assertions)`**：它只分「debug 构建 / release 构建」，**分不了「release 构建但从仓库运行」**（`tauri build --debug` 跑在仓库根、或将来的便携版）→ 会把 dev 判成装版、砍掉开发期工作流。
- **不用 `looks_like_repo_root`（`main.rs:1025-1047`）**：它的语义是「往上找**能不能找到**开发树」，且 `:1050-1055` 注释明写 **release 完全不信任向上搜索**（`allow_repo_search = cfg!(debug_assertions)`，`:1270` 传参）——**回答的是「能不能找到」，不是「是不是」**。误判的具体后果：装版 exe 恰好装在含 `package.json` + `src-tauri/` 的目录树下 → 判成 dev → 又写回 `example-filesystem` + 建技能目录（与 `:1021-1024` 记录的 20261103 真机事故同类）。

**Rust 单测三条（全部落进第 2 段验收）**：
1. 像开发树（`package.json` + `src-tauri/` 都在）但 exe 位于 `resource_dir` 内 → **installed**；
2. debug 分支 → **dev**；
3. **`resource_dir` 内缺 `src/ui/agent.html` → 仍 installed**（依据 `main.rs:1149-1154`：缺面板时**也返回 Bundled**、只打 WARN）。**这条目前无人覆盖，是整批里最容易漏的一条**——漏了就会出现「缺面板的装版被当成 dev → 又写回 `example-filesystem`」。

## 9. 未决/风险（实施前须知）

1. **备份目录增长**：C 每次备份整目录（当前 49 MB），需限制保留份数（如保留最近 3 份），否则用户盘被备份吃满。
2. **`shadow/` 与 `memories.db` 一致性**：迁移时两者必须**同批次拷贝**，否则记忆索引与内容可能错配。
3. **dev 与装版数据分家后的排障**：启动日志必须固定打一行 `[studio] config dir: <path>`（A 的实施验收项）。
4. **WebView 目录更换后首次加载**：`data_directory` 换新 = 用户需重新登录一次；这是**预期**（干净），要在发版说明里写清，避免被当成缺陷。
5. **共享目录 `~/.agents/skills`**：改成默认不读后，开发期常用的技能在装版里不会自动出现——需要面板「添加技能目录」入口，否则用户会觉得「技能没了」。
6. **`profiles/` 397 MB 是最大单笔残留，但删除要用户点头**（§1.5）：四个 WebView2 profile 来自已封盘的多窗口路线，删了不丢在用功能；但它是破坏性操作，**不进 C 的默认清理清单**，需单独确认（并确认无实例占用；11-05 23:2x 实测 0 进程占用）。同时提示：`window-state.json` 与 `logs/` 在这个目录里是**真数据**，不能跟着 `profiles/` 一起删。
7. **日志有三处，别在面板上再写错**（2026-11-05 实测）：
   - Rust 监管/崩溃日志：`dirs::config_dir()/deepseek-studio/logs`（`sidecar.rs:483-489`，可用 `STUDIO_LOG_DIR` 覆盖）→ 装版是 `%APPDATA%\deepseek-studio\logs`；
   - 宿主 trace：`<cwd>/logs/trace`（`trace-log.ts:22`、`page-runtime.ts:460`）→ 装版 cwd = `%APPDATA%\com.deepseek.studio`；
   - 用户在面板上看到的「日志路径」必须指向**上面某一处真值**。第 2 段顺带注入 `STUDIO_LOG_DIR`，可以把前两处收敛到同一父目录下（如 `<appdata>\logs\sidecar`、`<appdata>\logs\trace`），**让面板只需展示一个目录**。
   - **`sidecar.rs:483-489` 的日志路径是「启动时算一次」**：只注入 `STUDIO_LOG_DIR`、不处置旧目录，首启后会出现「新日志写新目录、旧目录 22 份还在」的**双份状态，且两份都像真值**（用户排查时必看错）。处置清单必须显式写明「**迁移旧 logs 到新目录，或把旧目录标注为历史归档**」，不能只写「留 1 份」。

8. **测试会持续污染用户真目录（B 类未修前，2026-11-06 04:0x 实测）**：`host-side-tools` 的 `file.write` 用例 → `desktop-host.ts:2164` → `shadow-store.ts:122` capture → **写到 `~/.config/deepseek-studio/shadow/`**（`index.json` + `sh_*.bin`，mtime = 测试时刻）。因为 `shadow-store.ts:72` 只认 `deps.homedir`、**零 env 分支**，测试侧的 `setupFiles` 注入 `STUDIO_CONFIG_DIR` **堵不住它**（`desktop-host.ts:489` 传的是 `os.homedir()`）。
   → **后果**：每跑一次全量测试就往用户真目录写一次；**我们做「干净度」验收，测一次就脏一次**。
   → **处置**：B 类（`shadow-store.ts:72` 加 env 分支）修完即自动解决；修完前判据 7 必须在「产品验收之后、测试之前」执行（§6.1）。

9. **`ensureMcpConfig()` 会在装版首启写一台「示例 MCP 服务器」**（2026-11-06 定稿）：`desktop-host.ts:2460` 的 `start()` 调用它；`mcp-controller.ts:396-417` 在文件不存在时写入 `example-filesystem`（`command: npx`、指向 `~/projects`）。**用户什么都没配，第一次打开就出现一台服务器**——与「安装好应该是干净的」直接冲突。

   → **验收判据唯一**：装版首启后 `mcp-servers.json` **要么不存在，要么存在但 `servers` 为空且不含 `example-filesystem`**；旧目录不得残留 dev 版（带 Bearer token 那份）。
   → **硬约束**：**dev 树行为不变**（开发期仍要示例配置）→ 必须按 `STUDIO_DISTRIBUTION` 分支（§8.3），**不得一刀切改 `ensureMcpConfig` 本体**。

10. **装版干净度验收脚本的四目录覆盖曾经是纸面判据**（2026-11-06 04:0x 查出）：验收脚本初版只做 `~/.config/deepseek-studio` 与 `%LOCALAPPDATA%\com.deepseek.studio` 两个目录的快照，**`%APPDATA%\deepseek-studio` 与 `%APPDATA%\com.deepseek.studio` 完全没进差集** → 用户装完、脚本全绿，**`profiles/` 那 397 MB 不会被报**。
    → 已改为**四目录各自一次前后集合差**（§6.1）；② 与 ④ 的对应手段见 §8.1（**env 注入 ≠ 全覆盖**）。
    → **另记**：11-05 那轮清理只清了三个目录，**第 ④ 个（`%APPDATA%\deepseek-studio`）仍在**。

11. **行尾伪影（内容没变却显示 `M`）**（2026-11-06 实测，第二次栽）：
    - **现象**：用 PowerShell `Set-Content` 写文件（默认 CRLF）→ 工作树整份变 CRLF，而 `.gitattributes:4` 声明 `* text=auto eol=lf` → 提交时被归一化成 LF；**diff 里看似"整文件重写"，实际内容只改了几行**。2026-11-06 04:3x 在 `esbuild.inject.mjs` 上真实发生（CR=56/LF=56）。
    - **判定口径（写死，别用肉眼）**：断言对象是 **index 侧**，不是工作树侧 ——
      `git -c core.autocrlf=false ls-files --eol`；判红条件 = `i/crlf` 或 `i/mixed`；**`w/crlf` 只提示、不判红**（本地 `core.autocrlf=true` + `eol=lf` 声明下，Windows checkout 出现 `w/crlf` 是正常的，实测本仓有 320 个）。
    - **豁免**：读 `.gitattributes` 的 `eol=crlf` / `binary` / `-text` 声明，**不硬编码扩展名清单**（硬编码必然漂移）。
    - **覆盖范围（诚实说明）**：本仓 `* text=auto eol=lf` 会让文本文件在 `git add` 时归一化成 LF 进 index，故文本文件的 `i/crlf` 在正常路径下不会出现；这条闸真正抓的是**逃过 text 归一化的 CRLF**（二进制误声明 `-text` 却含 CRLF、或策略生效前的历史文件）。
    - **不要把 `w/crlf` 也拦**：那会在 Windows checkout 上假红 320 处；真实防法是「写文件别用 `Set-Content` 默认行尾」这条纪律 + git 归一化（已实测有效）。
