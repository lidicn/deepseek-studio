# 审批重设计 v1（2026-11-09）

> 出资人 08:2x 原话（**本稿的一切取舍以这两条为准，不再问**）：
> 1. 「做一个 agent 无法控制的审批界面【非当前原生弹窗】」
> 2. 「让审批边界范围正确：该整个对话就是整个对话。该某次放行就是某次放行。该完全放开，就彻底关闭审批。」

---

## 一、要解决的三个真缺陷（全部实测定位，非推断）

| # | 缺陷 | 证据 |
|---|---|---|
| D1 | **审批界面与被审批对象同处一个页面** | 审批弹窗是注入 `chat.deepseek.com` 的 DOM（`src/ui/consent.ts`）；而 `src/inject/main-world-interceptor.ts` 也跑在同一页的 main world ⇒ agent 可改写/删除/伪造该 DOM |
| D2 | **「一次对话审批一次」实际每次都重新审批** | 对话级放行 key = `principal\|workspaceHash\|policyMode\|conversationId\|toolId\|canonicalTarget`（`conversation-approval.ts:60-69`）⇒ 含 toolId 与 canonicalTarget；而 `python.exec`／`shell.exec` 的 canonicalTarget 天然每次都变 ⇒ **这类工具永远无法「一次对话一次」** |
| D3 | **「完全放开」在 always 类工具上毫无意义** | `always` 类 13 枚工具走 `authorization.ts:302-315` 的无条件人工确认分支，不受档位约束 ⇒ full 档仍每次弹框（用户 07:34 实测确认） |

D2 的成因是 C1 P1 安全批 R3-01 的副作用：当时把 `toolId + canonicalTarget` 塞进 key，修对了「点一次 file.read 放行同对话全部工具」的漏洞，**却打死了用户诉求**。借用 OpenCode 源码的一句设计注释：**「换一个容器不等于换一个语义」**。

## 二、参照原型（在线调研，源码已实测拉取）

**首选原型：OpenCode**（开源 agent，MIT 系）

| 他们的做法 | 我们的对应 |
|---|---|
| 权限内核 `packages/opencode/src/permission/index.ts`：`evaluate(permission, pattern, ...rulesets)`，**最后匹配优先**，无匹配默认 `ask` | 我们的档位判定应输出 `allow/deny/ask` 三态而非布尔 |
| ask 时工具**停在 `ctx.ask` 那一行**（`Deferred.await`），请求进 `pending` 表、发 `permission.asked` 事件，客户端回 `once/always/reject` | 我们的 `ensureConsent` 已是这个形状（挂起＋回执），保留 |
| `always` 把**模式**（如 `shell: git status *`）追加进 `approved` 表，**并顺带放行同会话内其他已全部满足的挂起请求** | 我们的「本对话始终允许」应对应 **conversation 粒度**，不绑具体目标 |
| TUI 授权框 `packages/tui/src/routes/session/permission.tsx`：三选项 `Allow once / Allow always / Reject`；**点 always 先展示「将被记住哪些模式」**（`permissionAlwaysLines`） | 窗口内页面照此三按钮＋先展示将记住什么 |
| `--auto` 模式：客户端收到 `permission.asked` 直接代回 `once` | 我们的 full 档＝彻底关闭审批（连询问都不发生） |

**次选参照：Claude Code 权限模式**（default／acceptEdits／plan／bypassPermissions）——印证「档位＝策略集合」而非单值开关。

## 三、界面：Studio 审批窗口（独立 Tauri 窗口）

### 3.1 为什么不是页内模态、也不是 MessageBox

- 页内模态：**agent 能碰**（D1）⇒ 否决。
- MessageBox：安全但**与产品两套语言**，且只有 Yes/No ⇒ 长时效授权（本次对话始终允许）**在框里没有位置**（`native-consent.ts:16-17` 自述）。
- **独立 Tauri 窗口**：不在 chat 的 webview 里 ⇒ main-world 注入脚本**进不去**；同时可用 Studio 自己的样式渲染 ⇒ 观感与产品统一。

### 3.2 现成基建（不必新建）

`src-tauri/src/main.rs:1357` 的 **MCP 设置窗口**就是完整先例：Rust 开 `WebviewWindowBuilder` 独立窗口 + `initialization_script` 注入 + `on_navigation` 白名单 + `inflight_begin/end` 单实例 + 宿主 8760 提供零秘密页面（`desktop-host.ts:200-210` 的 `mcpSettingsPage`）。

### 3.3 通道（**这是本设计最硬的一环，必须先解决**）

**现状**：node 宿主（sidecar 进程）与 Rust 主进程**没有 node→Rust 的上行 RPC**（`native-consent.ts:8-11` 自述）⇒ node 无法直接叫 Rust 开窗。

**方案：Rust 侧轮询 + 窗口内页面 HTTP 回执**

```
node 宿主（8760）
  ├─ GET  /v1/consent/pending   （Bearer + 回环 Origin 闸）→ 返回待审批请求（含 nonce、工具、参数摘要、档位）
  └─ POST /v1/consent/reply     （Bearer + 回环 Origin 闸）→ { callId, decision, nonce }
        ↑ 宿主侧校验：nonce 常数时间相等 + 一次性消费 + ownerId 绑定（沿用 page-runtime.ts:560-568 的既有逻辑）
Rust 侧后台线程
  └─ 每 200ms 轮询 /v1/consent/pending → 有新请求 ⇒ 开/复用单实例「Studio 审批窗口」
       窗口内页面（/consent，宿主 8760 提供）
         └─ 轮询同一端点取请求 → 渲染 → 用户点按钮 → POST /v1/consent/reply
```

**理由**：完全复用 MCP 设置窗口的 token / Origin / 导航白名单机制，不引入新的进程间通道；node→Rust 与 Rust→node 两个方向都由 HTTP 承担。

**诚实边界（必须写进台账）**：窗口内仍是 WebView（不是操作系统级原生 GUI）。它的安全性来自**独立 webview、无页面级注入**；理论上比 MessageBox 弱一档、比页内 DOM 强很多。**不宣称「操作系统级不可伪造」**。

### 3.4 窗口内页面要求

- 复用 Studio 现有视觉语言（**卡 I 已做好的页内模态组件可直接复用**：危险外观 `data-risk=high`、`高风险`徽标、风险原因行、档位与规范目标显形）⇒ **卡 I 的成果不浪费**。
- 三个按钮：**允许一次**／**本对话始终允许**／**拒绝**。
- 点「本对话始终允许」时**先展示将记住的范围**（照 OpenCode `permissionAlwaysLines`）——这是 D2 的正解：用户看得见自己批准了什么。
- 拒绝时可带反馈给模型（可选，OpenCode 有 `CorrectedError` 同族；**阶段三**再做，阶段一可不做）。
- 窗口不可用时 **fail-closed**：宿主侧直接 deny，**不得静默放行**、不得回退到页内。

## 四、边界语义（出资人第 2 条，三档各自的确切含义）

| 放行粒度 | 含义 | 生效范围 | 失效条件 |
|---|---|---|---|
| **某次**（once） | 只这一次调用 | 单次 tool-call | 调用结束 |
| **整个对话**（conversation） | 该对话内**所有后续调用**都放行，**不再逐次询问** | key = `principal\|workspaceHash\|policyMode\|conversationId`（**去掉 toolId 与 canonicalTarget**） | 换对话／换工作区／换档位／页端断开／宿主停止 |
| **完全放开**（full） | **彻底关闭审批**：不再发生任何询问 | 全局 | 换档位 |
| （硬拒） | hard-deny 地板与策略层 deny：**直接拒绝**，不是询问 | — | — |

### 4.1 与卡 H 的差异（**下一批要改**）

卡 H 当前实现（Core 已交卷）＝ full 档放行 always 类，但保留**两个例外**：`!outsideRequested`（越界仍逐次问）与 `FULL_MODE_STILL_ASKS=['memory.purge']`。

**出资人 08:2x 新指令「该完全放开，就彻底关闭审批」覆盖 07:34 那条（当时采纳的是我建议的 memory.purge 例外）** ⇒ 下一批追加：
- 去掉 `!outsideRequested` 限制；
- 去掉 `FULL_MODE_STILL_ASKS` 例外（`memory.purge` 在 full 档也不再询问）；
- **hard-deny 地板与策略层 deny 一律保留**（它们是**拒绝**，不是询问，与「关闭审批」不冲突）。

### 4.2 D2 的正解

对话级放行去掉 `toolId`／`canonicalTarget` ⇒ 「本对话始终允许」＝**该对话内全部工具不再询问**，这才是出资人说的「该整个对话就是整个对话」。

**安全代价必须写进台账（明示，不藏）**：一次「本对话始终允许」＝ 本对话内**任何**工具（含 `python.exec` 任意代码、`memory.purge`）都不再询问，直到换对话/工作区/档位。
**缓解**：① hard-deny 地板仍在（关机/格式化/盘根递归删除/敏感路径/内联代码直接拒）；② 越界访问不再受对话级放行覆盖（`outsideRequested` 时对话级 key 不命中——**注意：这条与 4.1 的 full 档无关，只作用于 conversation 粒度**）；③ 每次放行写审计；④ 设置页文案写清。

### 4.3 「完全放开」不是三档下拉，而是规则集合（阶段三，暂不做）

OpenCode 的模型是 `action × resource → allow/deny/ask` 规则表（最后匹配优先），能表达「git status 随便看、git push 永远不许」。我们现在的三档太粗。**阶段一/二不做**（工作量大），但**阶段二的授权层输出必须留出规则接口**，避免阶段三推倒重来。

| 阶段 | 卡 | 归属 | 内容 |

| 一 | **K2** | Core（`src/host/**`） | `/v1/consent/pending`＋`/v1/consent/reply` 端点（Bearer＋回环 Origin 闸）、待审批队列、nonce 一次性消费复用既有逻辑、审计留痕 |
| 一 | **K3** | UI（`src/ui/**`＋新页面资源） | 窗口内审批页：复用卡 I 的视觉组件、三按钮、「将记住什么」展示、渲染失败 fail-closed |
| 二 | **K4** | Core（`src/host/**`） | 边界语义重做：conversation key 去掉 toolId/target；full 档去掉两个例外；授权层输出留规则接口 |
| 三 | K5 | — | 规则表 UI（allow/deny/ask 模式编辑器）＋拒绝反馈 |

**阶段一验收（必须行为级，不接受"读代码断言"）**：
- 高风险询问**不再出现在页内 DOM**（断言页内 `consent-required` 计数 0）；
- **窗口出现**（真机取证：起实例触发一次高风险调用，**截图为 Studio 风格的独立窗口、不是系统 MessageBox**）；
- 窗口点「允许一次」⇒ 工具执行、审计 `outcome=executed`；
- 窗口点「拒绝」⇒ 工具不执行、审计 `outcome=denied`；
- **窗口不可用**（宿主不可达）⇒ fail-closed deny、审计 `degraded`；
- 页内模态**不再被高风险触发**（旧路径回归锁）。
