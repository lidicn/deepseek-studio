## 〇、结论（先给答案）

1. **推荐方案甲**：预 OPEN 窗口内**仍然丢弃**这三型事件，但**丢弃必须可数、可读**——按类型累计丢弃条数，连接建立后补一行 `[transport] preopen dropped <n> assistant-reply / <n> stream-delta / <n> finish-sentinel`（或按类型各一行）。
2. **默认取值＝甲**（PM 不回话也按甲走）。理由：改动面最小、**不引入新的串轮风险**、把"静默丢失"变成"可见缺失"，符合 AGENTS「缺失≠干净」。
3. **回退口径**：若甲在真机上仍无法把"这一轮为什么没有结论"讲清，则退回**零改动**——只在本设计稿里留档，本面不再投入；**不做乙**（除非真机读数证明这三型的丢失已经造成过用户可见故障）。
4. **前置判据（建议 PM 先定）**：本卡动工前应有**至少一条现场丢失读数**（例如 sidecar 里同一轮既无 `assistant-reply` 也无 `finish-sentinel`，而 `[web-engine]` 或页面显示该轮有输出）。**目前没有这种读数**——三型的丢失目前只在代码上成立，未在真机上被证实造成故障。按本仓"先取证再动工"的口径，**没有这条读数就不该开卡**。

## 一、现场（现读）

### 1.1 三型事件的产生点与投递点

| 事件 | 页端产生点 | 投递点（出口） | 宿端消费 |
|---|---|---|---|
| `assistant-reply` | `src/inject/main-world-interceptor.ts` 约第 3572 与 3661 行（auto-continue 收尾各一处 `onAssistantReply?.(cleanReply, loopDepth)`） | `src/desktop/entry.ts` 约第 604 行 → `src/desktop/host-client.ts` 约第 575 行 `assistantReply()` → `send()` | `src/host/page-runtime.ts` 约第 527 行 → `options.onAssistantReply` |
| `stream-delta` | 同文件约第 2401 行 `onStreamDelta?.(visible)`（SSE 可见文本增量） | `entry.ts` 约第 605 行 → `host-client.ts` 约第 578 行 `streamDelta()` → `send()` | `page-runtime.ts` 约第 530 行 → `options.onStreamDelta`（web-engine 的 delta 装配） |
| `finish-sentinel` | 同文件约第 2630 行 `finishSentinelEmit = options.onFinishSentinel` 后在流收尾处调用 | `entry.ts` 约第 608 行 → `host-client.ts` 约第 581 行 `finishSentinel()` → `send()` | `page-runtime.ts` 约第 533 行：写 `finishSentinels.set(botId, …)` ＋ `options.onFinishSentinel` |

协议定义：`src/host/protocol.ts` 约第 100／102／117 行（三型的 `PageToHostMessage` 分支）。

### 1.2 丢在哪一步

`src/desktop/host-client.ts` 的 `send()`（约第 195 行起）在 `ws` 不是 OPEN 时：

- 卡⑪ 引入的 `PREOPEN_QUEUE_TYPES` 只含 `log`／`trace`／`integrity-alert`；
- **其余类型一律 `return`**（保持改前的 fail-fast）——三型正好落在"其余"里。

断线结算 `failAllPending`（同文件约第 147 行）只遍历 `pendingToolCalls`／`pendingKv`／`pendingEnvelope` 三张表；**三型是 fire-and-forget，没有 pending 条目，所以断线时没有任何一处会为它们留下痕迹**。

### 1.3 为什么卡⑪ 没把它们放进队列（原始理由，现读同文件注释）

> `result`／`consent-decision`／`kv-*`／`runtime-envelope`／`debug-eval-result` 全挂着 pending＋超时，排队等于让宿主去答一个**已经过期**的请求；`assistant-reply`／`stream-delta`／`finish-sentinel` 驱动续跑循环，**迟到重放会串轮**。

三型的后果**不对称**，这点决定了方案必须分开看：

| 事件 | 丢一条的直接后果 | 是否会让宿主"以为还有流没结束" |
|---|---|---|
| `stream-delta` | 引擎少一段可见文本；若整轮都丢，引擎看到"空输出" | 否（引擎本就按轮等文本） |
| `assistant-reply` | 宿主收不到"模型答完了"，该轮按超时/断流结算 | 是（宿主侧只有超时兜底） |
| `finish-sentinel` | 宿主拿不到"本轮有无完成哨兵"⇒ 落 `undefined`，`m1c` 语义为**不判 interrupted** | 否，但会让"断流"被当成"答完" |

## 二、方案甲：按轮丢弃 ＋ 可见提示

### 2.1 做法

在 `host-client.ts` 的 `send()` 的"其余类型直接 return"分支里，对三型**各记一个计数器**；`socket.onopen` 里队列 flush 之后，若有计数则补发**一条** `log`：

```
[transport] preopen dropped 3 assistant-reply / 12 stream-delta / 1 finish-sentinel (since last open)
```

计数在每次补发后清零（"since last open"），**不跨连接累计**，避免数字越滚越大失去意义。

### 2.2 碰哪些文件

| 文件 | 改动性质 |
|---|---|
| `src/desktop/host-client.ts` | 计数器＋一行补发（**唯一业务改动**） |
| `tests/desktop/preopen-queue.test.ts` | 追加锁；**并需修改既有 ③ 的断言**（见 2.4） |

**不碰** `src/host/**`、`src/inject/**`、协议（`protocol.ts` 无新字段）。

### 2.3 需要的回归锁

1. 预 OPEN 期发 3 条 `stream-delta` ＋ 1 条 `finish-sentinel` ⇒ OPEN 后**恰好一条** dropped 行，数字为 `12`／`1`（示例按实际条数）；
2. 计数**不跨连接累计**：第二次 open 不重复报上一次的数；
3. OPEN 期间发送三型 ⇒ **零** dropped 行（不能给正常路径加噪音）；
4. 三型仍然**不被投递**（甲不改变投递语义，只改变可观测性）；
5. `finish-sentinel` 丢失后宿主侧仍是 `undefined` ⇒ 不判 interrupted（这条已有 `m1c` 语义，甲**不许改变它**）。

### 2.4 会破坏哪些现有测试口径（**需 PM 批**，不许自己改）

| 测试文件 | 现有断言 | 为什么会被甲撞到 |
|---|---|---|
| `tests/desktop/preopen-queue.test.ts` ③"不入队类型未 OPEN 时与改前逐字相同" | 断言 OPEN 后的出战消息里**没有** `stream-delta`／`assistant-reply`／`finish-sentinel` 等类型 | 甲会在 OPEN 后**多一条** `log`（dropped 行）。该断言必须改成"没有这三型本体，但允许一条 dropped `log`"——**这是口径改动，需 PM 批** |

其余六枚涉及哨兵/续跑的测试（`m1c-finish-sentinel-wiring`、`m1c-interrupted-term`、`r3-03-finish-sentinel`、`t2a-finish-reason`、`w0-continuation-sentinel-obs`、`web-engine-f1`）都在 **OPEN socket** 上跑，甲不改变它们的前提，**预期零改动**；但交卷时必须逐枚跑过并以读数证明"零改动"，不能只声明。

## 三、方案乙：带轮次 id 的幂等投递 ＋ 宿主侧超时结算

### 3.1 做法

1. 三型入队（或另建"短窗口缓冲"），但每条带**轮次 id**：`stream-delta` 与 `assistant-reply` 现在没有轮次字段，需扩协议（`stream-delta` 加 `round`；`assistant-reply` 已有 `loop` 可复用但语义是"第几步"不是"第几轮"，要另立 `round`）。
2. 宿主侧按 `(botId, round)` 幂等：重复投递只记一次；**迟到的旧轮次**（round < 当前轮）直接丢并计数。
3. 宿主侧为每一轮设**结算超时**：到点仍没收到 `assistant-reply`／`finish-sentinel` ⇒ 以"未收到"结算（而不是无限等）。

### 3.2 碰哪些文件

| 文件 | 改动性质 |
|---|---|
| `src/host/protocol.ts` | 扩字段（`stream-delta.round`、`assistant-reply.round`）——**跨层契约变更** |
| `src/desktop/host-client.ts` | 三型入队＋带 round |
| `src/inject/main-world-interceptor.ts` | 产生点补 round（**注入层**，另一席位域） |
| `src/host/page-runtime.ts` | 幂等表＋结算超时 |
| `src/host/engine/web-engine.ts` | delta 装配要能吃"乱序＋重复" |
| 4～5 个测试文件 | 新增幂等/超时锁；已有断言的**轮次归属**口径要重审 |

### 3.3 需要的回归锁

1. 同一 `(botId, round)` 的 `stream-delta` 重复投递 ⇒ 只装配一次；
2. 旧轮次迟到（round 小于当前）⇒ 丢弃并计数，**不得**混进当前轮文本；
3. 结算超时到点 ⇒ 该轮以"未收到"收口，且用户可见一条交代；
4. 正常路径（OPEN 直发）**逐字节等于改前**；
5. 断线重连后旧轮次不复活。

### 3.4 会破坏哪些现有测试口径（**需 PM 批**）

| 测试文件 | 现有断言 | 为什么会被乙撞到 |
|---|---|---|
| `tests/desktop/r3-03-finish-sentinel.test.ts` "每轮只发一次、round 严格 +1" | 断开发送次数与 round 增量 | 乙允许"同轮重复投递＋宿主幂等"，页面侧发送次数可能变多，**断言对象要搬层**（从"页面发几次"改成"宿主装配几次"） |
| `tests/desktop/w0-continuation-sentinel-obs.test.ts` | 断 `continuation.stream` 的 `sawSentinel` 与重发次数 | delta 乱序/重复会改变观测顺序 |
| `tests/desktop/m1c-interrupted-term.test.ts` | `undefined` ⇒ 不判 interrupted | 结算超时会把"未收到"从 `undefined` 变成显式终态，**语义面变了** |
| `tests/desktop/preopen-queue.test.ts` ③ | 断言三型不入队 | 乙正是要它们入队，**必须整条重写** |
| `tests/desktop/web-engine-f1.test.ts` | 引擎对空/断流的判定 | 幂等表与超时结算会影响"何时算空" |

**乙的断言改动面 ≥ 5 个文件、其中 3 条是语义面（不是措辞）**，这是我不推荐乙的主要理由之一。

## 四、对比

| 维度 | 甲（按轮丢弃＋可见提示） | 乙（轮次 id 幂等＋超时结算） |
|---|---|---|
| 改动文件 | 1 业务＋1 测试 | 5 业务（含协议＋注入层）＋4～5 测试 |

| 串轮风险 | 不引入 | 引入，需要幂等＋旧轮次丢弃＋超时三重约束才能堵住 |
| 丢失是否可见 | **是**（dropped 行） | 是（幂等/超时计数） |
| 用户可见交代 | 间接（宿主据 dropped 行可解释该轮） | 直接（超时结算给交代） |

| 现有断言改动 | **1 条**（preopen-queue ③） | **≥5 条，含 3 条语义面** |
| 前置证据要求 | 只需"确实丢过"的读数 | 还需要"丢了造成过可见故障"的读数 |
