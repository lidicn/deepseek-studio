## 一、评审结论摘要

**判决：不能照这份稿子施工。** 它的价值判断（守住边界、别为像现代 AI 系统而写代码、按触发条件决定要不要做）是对的，但整份文档是「取舍备忘」，不是「可施工设计稿」——同目录 `docs/设计稿/` 下 M5 编程工具链（三版）、M8 安全核心、智能体面板那几份有文件级接口、有迁移路径、有验收；这一份没有一条能落成工单。

**成熟度：草案（介于构想与草案之间），距可施工两级。** 依据四点，都可核：

1. 全篇没有一处指向现有 `src/` 的具体模块、接口或测试；P0–P2 只给到「半天~一天」的量级和一句形容词式验收。
2. 它列的第一阶段三项，其中两项在仓库里已经存在（下节逐条给 file:line），所以「第一阶段」实际是一次现状声明，不是计划。
3. 它的中心红线（不做自主循环、不做多会话）与已交付代码相反，且这些能力已有测试覆盖——照做等于回退，不做等于文档继续背离。
4. 阶段划分没有退出条件、没有依赖顺序、没有并行点、没有阶段末的可演示产物；`§7 落地路线` 只写了「约两天」「按需触发」「不做」三段。

**最大的三处风险（按会让方案流产的顺序）：**

- **R1 主矛盾选错。** 稿子把「稳定」定义为「少加能力」，于是 P1 落到「错误分类 + 轻量日志」。但分类这件事仓库里已经有了（`src/inject/response-classifier.ts` 170 行，ok/retryable/fatal 三档），真正缺的是**终态语义**：一轮对话结束之后，「这轮到底完了没有」在宿主侧只有四个取值，而且四个都只描述本地失败（`src/host/engine/model-engine.ts:20`），其中「模型没调工具」被直接当成成功（`src/host/kernel/task-loop.ts:200`），并且这个判断被测试锁死（`tests/desktop/task-loop-reply.test.ts:6`）。照稿子施工两天，系统照样会出现「界面说完成、正文是半截计划」，而新加的门禁一条都抓不到。
- **R2 红线与现状相反。** 稿子 §2.2 把「并发/多会话/多账号编排」「开放式多步自主决策（ReAct）」「对外 API」列为明确拒绝。仓库现状是：宿主侧 `MAX_LOOP = 25` 的多轮自主续跑（`src/shared/continuation-prompt.ts:48`）、`<task_complete>` 哨兵终止（同文件 `:87`）、多 bot 并行（`src/host/agent-channel.ts:8-9`，`:38-41`）、会话并发默认 4（`src/host/kernel/session-manager.ts:5`）、MCP（`src/host/mcp-controller.ts`）、长期记忆（`src/host/memory-store.ts`）、本地 HTTP API（`src/api/server.ts` 764 行）与可选局域网访问（`src/api/agent-lan-access.ts` 112 行，默认只放行 loopback，见 `src/api/main.ts:116`）。这一条不解决，后续所有评审都没有共同基准。
- **R3 验收不可证伪，且现有门禁是假绿。** 稿子 P2 的验收原话是「改版时能一句话说清要改哪几个文件」——不可数、不可判真假。而仓库现有门禁也不测真机终态：`tools/gate/run.ts:28-35` 六个阻塞步骤里没有 golden eval；`tsconfig.json` 的 `include` 只有 `src/**`、`tests/**`、`vitest.config.ts`，`tools/**` 压根不在类型检查范围内；`tools/audit/doc-drift.ts:20-25` 只校验 4 个硬编码符号，`docFile` 写死 `docs/架构文档/`，`docs/设计稿` 根本不在扫描范围，所以这份设计稿永远不会被「文档漂移审计」看到；`.github/workflows/ci.yml:12-18` 与 `npm run gate` 是两套不同清单，互相都不覆盖对方。

一句话给用户的判断：这份稿子回答了「该不该继续加功能」，没回答「怎么证明它现在是对的」。后者才是当前真正缺的。

## 二、设计稿提炼与假设核对

### 2.1 一段话说清它在讲什么

它要解决的是「个人 harness 的能力与风险边界怎么定」：以 DeepSeek 网页版为引擎、本地工具为执行面，用一张能力边界表（圈内/圈外）和一张风险分层表（ToS / 风控 / 工程脆弱）给后续所有技术选型设准绳，再按「成本低、收益确定、无风险」排序出 P0 能力边界文档、P1 错误分类 + 轻量日志、P2 交互层收敛三件事，主张两天做完就停手，P3 上下文压缩、P4 长期记忆、P5 Provider 契约一律挂触发条件，自主循环、子 agent、多账号、对外 API、RAG 一律不做。

做法上它靠三样东西：把风险归因到「是否改变请求特征」（§3.2），把要不要做归因到「有无明确触发条件」（§4.2），把成本卡在「超过两天且非 P0~P2 就重新评估」（附录第 5 条）。

### 2.3 成熟度判定与依据

判定为**草案**，不是**可施工**。四条依据：

1. **无可落点**：没有一处写出要新建或修改的具体文件、函数签名、数据结构。
2. **无判真假的成功标准**：唯一的验收句（P2）是「能一句话说清要改哪几个文件」，无法测量。
3. **无依赖与顺序**：P0/P1/P2 之间没有先后约束，也没有「谁先做才能做下一个」的理由。
4. **与代码库零接触**：全篇没有一行 file:line，而同目录 M5/M8 稿都给了接口与迁移顺序——说明作者写这份稿子时没打算施工，是写给「要不要继续投入」这个决策用的。

## 三、问题清单（按严重度）

### P0：会让方案流产

**P0-1 成功标准全是形容词，没有一条可判真假。**
- 现象：P2 验收「改版时能一句话说清要改哪几个文件」；§8 第 5 条「三个月里如果没遇到会话爆了或改版修不动，说明 P3 以后不需要」。
- 为什么会出事：「改不动」「爆了」没有阈值，任何一次卡顿都能被解释成「没遇到」，这个判据永远为真，于是永远是「不需要做」。
- 最小修法：每条判据换成「事件计数 + 阈值 + 测量方法」三件套。例：把「会话爆了」改为「一周内 `trimMessages` 实际丢弃过消息的会话次数 ≥ 3 次（数据源：`src/shared/context-budget.ts:53` 的裁剪结果 + `src/shared/harness-metrics.ts` 事件日志）」；把「改版修不动」改为「selector 类断链从发现到绿灯的耗时 > 2 小时/次，一个月内 ≥ 2 次」。

**P0-2 红线与已交付能力相反，且没有落成可执行约束。**
- 现象：§2.2 拒绝自主循环/多会话/对外 API；代码里全都有（A2–A7 证据）。
- 为什么会出事：文档活着但没人执行，下一次评审又要从头争论一遍；更糟的是有人照文档「回退」，会把 `agent-channel` 多 bot、`task-loop` 多轮续跑这些有测试的能力拆掉。
- 最小修法：把三条红线改写成三条**可执行的运行时约束**（不是禁令）：每任务请求上限 N、每分钟请求上限 M、超限即停并上报；把「不做」改成「做但有预算」。约束落在哪个模块、超限后什么行为，见 §5 M1 的可选交付物。

**P0-3 终态语义缺席——这是「更底层」的那一层，也是当前唯一能解释「显示完成但没有结果」的代码路径。**
- 现象一：宿主侧终态只有四个取值，且全部由本地失败定义——`src/host/engine/model-engine.ts:20` `CompletionStatus = 'complete' | 'truncated' | 'disconnected' | 'unknown'`，`:37-41` 注释明写 `truncated — 看门狗截断（timedOut 的语义化别名）`；判定函数 `src/host/engine/web-engine.ts:25-35` 只读 `timedOut` / `dispatchFailed` / `stopped`，`partial` 参数声明了但没参与判断。
- 现象二：完成检测靠 DOM 文本稳定，不靠协议终态——`src/host/engine/web-engine.ts:258-294`（`stableHits >= 2` 即认为说完），而页面层其实**已经算出了真终态**：`src/inject/deepseek-sse-frame-decoder.ts:134-150` `framesSignalStreamCompletion`（`response/status=FINISHED` / `quasi_status=FINISHED` / `event: close`），注释 `:123-132` 记录了「20 份真实抓包 DONE=False」的实测结论。两条判据来源互不相通，结算只用弱的那条。
- 现象三：「没调工具」被当成功——`src/host/kernel/task-loop.ts:196-202` `computeStop`：`if (toolCalls === 0) return 'no-tool-calls'`；而 `requireTaskLoopReply`（同文件 `:66-77`）的失败清单只有 `empty-response / timeout / aborted / max-rounds`，**不含 `no-tool-calls`**，所以「有正文 + 0 次工具调用」原样当成功返回。这条被测试正面锁死：`tests/desktop/task-loop-reply.test.ts:6` 断言 `stopReason: 'no-tool-calls'` 时返回 `'结论'`。
- 现象四：页面层在续跑轮上遇到「无哨兵」并不结算，直接交回外层——`src/inject/main-world-interceptor.ts:1601-1612`：非 auto-continue 的首轮走重发与 `escalateFirstAttemptFailure`，`if (loopState.inAutoContinue) return false;`（`:1612`）。首轮路径是有语义的（`:1592-1597` 三态：0 字节=no-stream、有字节无哨兵=truncated），续跑轮这句 `return false` 之后发生什么，本轮未核到（见 U1）。
- 为什么会出事：模型正在写「执行计划」时被上游提前收尾，宿主看到的是「文本不再变化 + 0 次工具调用」，于是判「说完了 + 没有工具」——两件事都合法，合成一个假成功。
- 最小修法：**不是加判断，是加一个真相源**——把页面层已经算出来的哨兵结论（`framesSignalStreamCompletion` 的返回值）作为唯一终态判据，沿链路带到宿主，让 `CompletionStatus` 增加一个「上游提前收尾」的取值，并让 `requireTaskLoopReply` 把它判失败。细节见 §5 M1。
- 必须说清的边界：**这个洞在代码上成立，但在现有样本里没有被观测到。** `logs/cdp-chat-capture/` 24 份 response-body 中，13 份是 chat/completion 流且 **13/13 都带 FINISHED**；另外 11 份是 406/407 字节的 PoW challenge（`/api/v0/chat/create_pow_challenge`）与 27 字节的 422 body，根本不是对话流。也就是说 studio 侧目前**零份「长流无哨兵」样本**，该通道的频率未知。这恰好证明 M0（先测量）必须排在 M1（再改）之前。

**P0-4 阶段划分不可执行：没有退出条件、没有依赖、没有并行点、没有可演示产物。**
- 现象：§7 只有「约两天 / 按需触发 / 不做」三段。
- 为什么会出事：两天到了没人能回答「过没过」，只能靠感觉；一旦第一项拖延，后两项没有降级路径。
- 最小修法：每个阶段补四件：出口判据（可数）、依赖（谁阻塞谁）、并行点（谁可以和谁同时做）、可演示产物（一句话能指着看的东西）。本方案 §4/§5 已按此给出模板。

### P1：显著拖慢或抬高成本

**P1-1 「半天做错误分类」低估了，且分类轴不对。**
- 现象：§4.1 P1 把失败分成「解析失败 / 登录态失效 / 限流 / 模型输出异常 / 工具执行失败」五类，成本「约半天」。
- 为什么会出事：三档分类已经存在（`response-classifier.ts:14-22`），再按五类重做一次是重复劳动；而真正缺的轴（这轮**有没有完成**，不只是**有没有报错**）这一版分类里没有。
- 最小修法：不重做分类，只补一条正交轴——「终态归属」，与现有 ok/retryable/fatal 组合使用（错误分类回答「要不要重试」，终态归属回答「能不能宣称完成」）。

**P1-2 「改版只修一处」对 6,334 行的 inject 层不现实。**
- 现象：P2 目标是把网页脏活收进 2~3 个文件，成本半天到一天。
- 为什么会出事：`main-world-interceptor.ts` 单文件 2,365 行，且它同时管换流、工具标签解析、auto-continue 结算、PoW 重放、trace——这些是互相纠缠的运行时状态，不是可以按文件切开的模块。
- 最小修法：把「收敛」缩小成两件事：一是 selector 注册表（把 12 个文件里的 `querySelector` 收进一张表），二是流泵（把 `:1019-1052` 那个主动泵单独成文件）。整体重构不做，只在 M4 按触发条件做。

**P1-3 现有门禁是假绿，稿子却把「门禁」当已解决的问题。**
- 证据四条：`tools/gate/run.ts:28-35` 无 `eval:golden`；`tsconfig.json` `include` 不含 `tools/**`；`tools/audit/doc-drift.ts:20-25` 只查 4 个符号且路径写死；`ci.yml:12-18` 与 gate 清单不一致（CI 跑 doc-drift/security/e2e，gate 不跑；gate 跑 contract/empty-files，CI 不跑）。
- 为什么会出事：任何「已修复」都可能只是没被检查。
- 最小修法：一个入口（CI 跑 `npm run gate`）、tools 纳入类型检查、eval 进阻塞级、doc-drift 覆盖 `docs/设计稿` 与 `docs/harness`。见 §5 M2。

**P1-4 风险模型漏掉「自身放大」这一项。**
- 现象：§3.2 只讨论「什么改变请求特征」，把工具循环列为唯一变化点。
- 为什么会出事：真实事故形态是重试风暴，不是稳态请求量。`src/inject/response-classifier.ts:4-11` 自己记了这段历史：原实现只识别 429，其余全落「空回复」分支被当成「模型没说完」继续 nudge，叠加续跑预算形成 33 连发。
- 最小修法：把「重试放大比」（实际请求数 / 用户意图轮数）列为一等指标，进 M0 的口径表。

### P2：影响效率，不致命

**P2-1 成本收益错配。** 稿子把最大投入（P2 收口，半天~一天，实际远不止）押在「改得动」，但没有改版频率基线，也没有「改一次要多久」的基线——收益无法核算。最小修法：先用 M0 拿到「近 3 个月 selector 断链修复耗时」记录（可从 `docs/Audit/` 与提交历史里抽），再决定要不要做 P2。

**P2-2 没有「一次任务」的定义，所有比例都没分母。** 稿子谈「请求密度」「会话变长」都是定性。最小修法：口径表里先定义 task = 一次用户消息触发的 1..N 轮，N 由 `MAX_LOOP` 截断；之后所有比率都写「分子/分母」。

**P2-3 失败样本不自采。** 已有 `logs/cdp-chat-capture/` 24 份，但不在任何流程里（不进 gate、不进 metrics、不落盘规范）；且如 P0-3 所述，长流无哨兵样本为 0，说明抓包只覆盖了成功或短错误路径。最小修法：给「无哨兵」加一个抓包开关，命中才落盘，避免全量留存。

**P2-4 没有定义「任务成功」。** 稿子通篇说「做稳」，但从没定义成功 = 什么。最小修法：定义一个三档判据（完成 / 有结果但被打断 / 无结果），M1 起所有统计都按它切。

## 四、新方案总览

一句话：把「稳定性」从「少做功能」重定义为「终态不说谎 + 失败率可数」，用五个阶段把这条口径落到代码、门禁和真机。

| 阶段 | 目标（一句话） | 主要交付物 | 核心验收（可数） | 闸门 / 不达标降级 | 工作量 |
|---|---|---|---|---|---|
| M0 | 把「完不成」变成三个可数的量 | 终态口径表、`tools/metrics/term-state.ts`、5 连跑基线表 | 7 个终态各有唯一判定点（7/7）；两个样本文件跑出不同分布；基线 5/5 条记录完整 | 口径表未过拍板 → 不做 M1 改码，只做只读统计 | 4–8 人时 |
| M1 | 让「被截断」不能结算成成功 | `task-loop.ts` 终态入参 + `interrupted`；`web-engine.ts` 判定；结算处改紧；UI 文案；单测与回放样例 | 单测新增 ≥6 条；变异验证删掉分支至少 2 条红；回放 1/1 得到 `interrupted`；真机 5 次假成功 0/5 | 误杀率升 → 开关 `STUDIO_TERM_STRICT=0` 回滚 | 12–24 人时 |
| M2 | 让「改坏了」在合并前就红 | gate 加 eval、tools 进 typecheck、CI 与 gate 合一、doc-drift 扩到设计稿 | 三处注入式破坏全部拦下（3/3）；gate 总时长 ≤ 300s；两套清单差异 = 0 | 超时 → eval 降为 pre-push；仍超时 → 只保留 10 条冒烟 | 8–16 人时 |
| M3 | 让真机失败率有数字，而不是有感觉 | `tools/metrics/live-task.ts`、5 条 e2e 剧本、抓包开关、7 天样本 | 连续 5 次判定一致 5/5；7 天 ≥20 次任务；假成功计数 0；长流无哨兵计数有值 | 样本不足 → 只出「同期对照」不出趋势 | 16–32 人时 |
| M4 | 只按数据做的卫生 | selector 注册表、流泵独立文件 | 触发条件满足才立项：selector 断链修复耗时 > 2h/次 且 月内 ≥2 次 | 不满足 → 不排期 | 8–24 人时（触发后才估） |

**关键路径（串行）：** M0 → M1 → M3。M1 的接口一改，M3 的脚本才写得对，所以 M3 的脚本编写必须在 M1 接口定稿之后。

**可并行项：**

- M2 与 M1 完全可并行：M2 只动 `tools/`、`tsconfig`、`ci.yml`、`tools/audit/doc-drift.ts`，与 M1 的 `src/host/**` 无交集，可两人同时做。
- M0 的「口径表」与「基线 5 连跑」可并行（一人写表，一人跑真机）。
- M3 的 5 条 e2e 剧本中，4 条可以先用现有 fixture 改（`tools/eval/fixtures/32-engine-completion-truncated.json`、`33-engine-completion-disconnected.json`、`31-task-loop-empty-response.json`、`30-task-loop-max-rounds.json`），只有「长流无哨兵」需要新造样本。

**里程碑与判定方式：**

- MS0（M0 结束）：能给出一张表，说明最近一次真机会话里每一轮的终态是什么。不能给出 → 回退，重做基线。
- MS1（M1 结束）：同一条提示词连跑 5 次，「界面宣称完成」与「`requireTaskLoopReply` 不抛错」的一致率 = 100%。
- MS2（M2 结束）：故意弄坏三处，三处都必须红。有一处不红 → 该门禁不算接上。
- MS3（M3 结束）：连续 7 天窗口内假成功 = 0，且各终态占比有数。

## 五、逐阶段详细方案

### M3 真机可复现（16–32 人时，其中约一半是跑批等待）

- M3-B：7 天累计 ≥ 20 次任务，term-state 分布有数（各终态占比 + 分母），写入报告。
- M3-C：假成功计数 = 0（定义见 M0 口径表）。
- M3-D：抓包样本中「长流无哨兵」计数有确定值（可以是 0，但不能是「没采」）。

**退出条件：** A–D 全绿。
**风险与回滚：** 服务端波动会让跨时段数字不可比 → 只做同期对照（同一小时窗内 ON/OFF 或改前/改后），不做跨周趋势；样本不足时明写「样本不足」，不拿趋势说话。

### M4 按需卫生（触发后才立项）

**目标：** 只在数据说疼的地方做重构。

**触发条件（必须都满足）：** `selector` 类断链从发现到绿灯耗时 > 2 小时/次，且一个月内 ≥ 2 次；或 `src/inject` 改动引发的回归 ≥ 2 次/月。

**交付物（触发后）：** 只做两件——`src/inject/selectors.ts`（把 12 个文件里的 `querySelector` 收成一张表，`src` 下该调用共 135 处，主要分布在 `tool-card-ui.redesign.ts` 19 处、`tool-card-ui.ts` 9 处、`step-flow-ui.ts` 8 处）；把 `main-world-interceptor.ts:1019-1052` 的主动泵（`start()` 里 `while (true)` 逐 chunk 读上游）抽成 `src/inject/stream-pump.ts`。**不做**整体拆分，**不做** Provider 契约重构（`ModelEngine` 已经在 `model-engine.ts:45-59`，再抽一层是重复）。

**退出条件：** 触发条件不满足就**不立项**，本阶段可以永远不做——这正是稿子「按需做」的正确用法。

## 六、第一周三件事（每件 ≤ 半天）

**第一件：跑 5 次基线，拿到第一张真机表（约 2.5 小时）。**

为什么值：现在 `complete` 有至少三个来源（`model-engine.ts:20` 的类型、`web-engine.ts:25-35` 的判定、`task-loop.ts:200` 的推断），谁说了算没人写下来。把它写下来只需要三小时，但它是 M1 能不能一次改对的前提。

## 七、需你拍板的决策点

**D2 「有正文 + 0 次工具调用」算不算成功（对应 P0-3 现象三）。**
