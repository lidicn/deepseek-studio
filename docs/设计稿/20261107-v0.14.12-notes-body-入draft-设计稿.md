# v0.14.12 设计稿：Release 页 body 从 notes 文件补齐

> **订正版**（群 PM 20:2x 复核出三处行为判据级错、已修正：①守卫假红不成立、②action 缺文件行为反了、③"已有断言"查无实据）

## 问题
GitHub Release **页面 body 为空**（v0.14.11 与 v0.14.8 均 0 字符，两次）。应用内更新弹窗有正文（读 `latest.json` 的 `notes`，来自仓库 `docs/release-notes-<tag>.md`）；但 Release 页 body 从未被填充——用户访问 releases/tag/v0.14.11 看不到说明。

## 根因
`release.yml` 的 `Create draft release` 步（`softprops/action-gh-release@v2`）只传 `draft: true`／`files:`／`tag_name:`，**不传 `body` 或 `body_path`**。`latest.json` 的 notes 在 `Compose latest.json` 步单独组装、作为 asset 上传；Release 页 body 是另一条独立链路、从未接上。

## 修法（一行＋配套前置断言＋正向锁）
`Create draft release` 步的 `with:` 块加 `body_path: docs/release-notes-${{ github.ref_name }}.md`。
- `action-gh-release@v2` 读该文件、设为 Release body；
- 文件在 tag commit 的 checkout 里存在（`docs(release)` 笔先于 tag 入库，裁定六十）；
- Release 页渲染 markdown——但我们的 notes 正文是纯文本（293 字符、零 `#`/反引号/`**`），显示为单段纯文本，与弹窗一致。

## 影响面（3 处）

### 1. `release.yml`
`Create draft release` 的 `with:` 加一行 `body_path`。**不动 `run:` 块、不动 Compose 步。**

### 2. `release-compose.test.ts` 守卫（新增正向锁、不调整现有注入锁）
**PM 复核订正**：现有 L54-56 注入锁 `compose.slice(runStart)` 不含 `${{ }}` 的 `step()` 取段逻辑只提取 **Compose latest.json** 步的正文（在下一个 `\n      - ` 处截断、长度 3,066），**不含 `Create draft release` 步的 `with:` 块**。⇒ **加 `body_path` 不会触发注入锁假红**——此前那条"slice 收窄"的改法**作废**（在不必要时削弱一枚注入锁，属验收口径上"改断言须先报批"的对象）。

**正确做法＝新增一枚正向锁**：断言 draft 步 `with:` 里确有 `body_path: docs/release-notes-${{ github.ref_name }}.md`。配平负控：删掉这行 ⇒ 正向锁必红。**现有注入锁不动。**

### 3. CI 行为
draft 创建时 body 被填充；Publish 后 Release 页可见正文。**不影响 `latest.json` 的 notes 管线**（那条在 Compose 步、独立）。

## 风险

### `body_path` 文件不存在时 action 行为（PM 复核订正）
**`action-gh-release@v2` 对 `body_path` 文件不存在只打 `warn`、然后回退到 `body` 输入**（源码：`catch(t){console.warn("⚠️ Failed to read body_path …(ENOENT). Falling back to 'body' input.")}return e.input_body`）。我们从不设 `body` ⇒ **Release body 空、CI 全绿**——正是这次要修的症状**静默复发**。

> **出处**（可复核）：仓库 `softprops/action-gh-release`、ref `v2`（tag）、文件 `dist/index.js`（788,217 B、minified 单行 bundle）。**主锚＝函数 `ap` 的代码原文**（标识符＋字面量，不随重建漂移）：`ap=e=>{if(e.input_body_path)try{return(0,mo.readFileSync)(e.input_body_path,"utf8")}catch(t){console.warn(\`⚠️ Failed to read body_path "${e.input_body_path}" (${t?.code??"ERR"}). Falling back to 'body' input.\`)}return e.input_body}`——`catch` 只 `console.warn`、不 `throw`，随后 `return e.input_body`（我们从不设 `body` ⇒ 返回 `undefined` ⇒ body 空）。**行号（登记时 L50）仅作旁证**——minified bundle 行号随 action 重新构建漂移、不作主锚。浏览：`https://github.com/softprops/action-gh-release/blob/v2/dist/index.js`；实测 raw URL：`https://raw.githubusercontent.com/softprops/action-gh-release/v2/dist/index.js`（HTTP 200、788,217 B）。

⇒ **必须自家加前置断言**（在 draft 步之前、`Compose latest.json` 步之后）：
```yaml
- name: Verify notes file exists
  run: |
    $f = "docs/release-notes-${{ github.ref_name }}.md"
    if (-not (Test-Path $f)) { throw "notes file not found: $f" }
```
**不许把 fail-closed 寄托在第三方 action 的行为上。**

- `body_path` 内容是纯文本而非 markdown ⇒ Release 页显示为无格式段落。若将来想要格式化，需另写一份 markdown 版给 `body_path`、弹窗版仍走纯文本管线（方案 A 两份来源分工）。

## 需要配套的新判据清单
1. **前置断言**：`body_path` 文件在 draft 步之前 `Test-Path` 通过（**新增**、不是"已有覆盖"——PM 复核：`tests/desktop/*.ts` 扫 `release-notes`/`notesFile` 0 命中，探针有牙：同尺在 `release.yml` 命中 L139/L141；现有 workflow 里的回落泛化串是 notes 非空检查、跟"draft 步能读到文件"是两件事）
2. **正向锁**：draft 步 `with:` 里确有 `body_path: docs/release-notes-${{ github.ref_name }}.md`（**新增**、配负控）
3. Release 页 body 非空（Publish 后从公开链 `GET /releases/tags/v0.14.12` 取 `body` 字段、长度 > 0）
4. `body` 内容与 `latest.json` 的 `notes` 同源（都来自 `docs/release-notes-<tag>.md`）

- 不动 `tauri.conf.json` 的 updater endpoints
