## 0. 威胁模型（先写实，否则设计没靶子）

被约束方 = **页面内的 JS**（含模型可以影响的 payload、注入脚本本身、以及任何能跑在该页面 origin 下的代码）。

它现在能做的事：**直接 `ws.send` 一条 `{type:'consent-decision', callId, decision:'allow-session'}`**。
因为 `callId` 是宿主下发给**本连接**的（`p.ownerId === id` 通过），伪造即成功 → 模型自己给自己授权。

**关键前提**：`callId` 必须是"只有本连接知道"的。若 `callId` 可能泄漏给页面外，则连 ownerId 绑定都不够。
本设计**不假设 callId 保密**（它经 `consent-required` 明文下发到页面），所以必须引入**页面拿不到的东西**。

因此判据：**只有当"决议"由页面之外的权威源产生、页面只做转发时，才不可伪造。**

---

## 1. 两个方向都设计

### 方向 A：宿主侧原生确认框（Host-native dialog）

宿主（Tauri 主进程 / Node host）**自己弹一个原生/独立窗**征求，页面完全不参与决议。

- 决议通路：`ensureConsent` → 宿主弹原生确认（Tauri `MessageDialog` 或独立 WebviewWindow）→ 用户点击 → 宿主本地得到 `ConsentDecision` → **不经过页面 WS**。
- 页面只收到结果通知（`consent-resolved`，仅供 UI 展示"已放行"），**不再收 `consent-decision`**。

| 维度 | 评估 |
|---|---|
| 侵入面 | `src-tauri/src/main.rs`（弹窗能力 + IPC）+ `src/host/desktop-host.ts`（ensureConsent 改走本地）+ `src/host/page-runtime.ts`（requestConsent 移除/降级）。**跨 host+tauri 两域**，inject 侧几乎不用改（去掉 showConsent 依赖） |
| UX 代价 | **高**：原生框样式与注入页脱离、无法显示 rich meta（风险标签/越界徽标/参数预览），要么退化要么再在原生里重画一套。多 bot 多窗时"哪个窗在问"难表达 |
| 可绕过性 | **最低**。决议根本不经页面，页面无渠道伪造 |
| 测试难度 | **中高**：需在无 GUI 的 CI 里 stub 原生框（注入一个可测试的 `askUserNative` 接口），但逻辑边界清晰、易写负控 |
| dev(tsx) 兼容 | 需 tauri 侧能力；纯 Node host（无 tauri）下要退化为方向 B 或拒绝 |

### 方向 B：宿主签发 nonce + UI 点击证明（Nonce-bound proof）

页面仍负责渲染模态，但**决议报文必须携带一个只有宿主能签发、且与本次 consent 一一绑定的 nonce**，并且该 nonce 的"使用"必须由一个**页面无法凭空生成的用户手势信号**触发。

具体设计见 §2。要点：
- 宿主 `requestConsent` 时生成 `nonce = random`，连同 `callId` 记录在 `pendingConsent`（现有结构加字段）；
- 模态渲染时，**用户必须真实点击按钮**（`pointerdown`+`click` 且 `isTrusted === true`）才允许取用 nonce；
- 页面回传 `{callId, decision, nonce, gestureProof}`，宿主校验：
  1. `nonce` 与 `pendingConsent[callId].nonce` 常数时间相等；
  2. `gestureProof` = 由"点击事件时间戳 + nonce"计算的、页面能在点击回调后取到但**无法在无点击时构造**的值——
     这里**必须诚实**：`isTrusted` 与点击事实本身由浏览器保证，但页面仍可监听同一 click 事件再伪造报文。**所以单靠 nonce+isTrusted 不足**。
- **补强（核心）**：宿主在 `consent-required` 里下发 nonce 后，**要求点击证明走一条独立回执通道**——即页端在被信任的点击回调里调用宿主暴露的**一次性确认函数**（`__studioConsent.confirm(callId, nonce, decision)`），该函数由**注入脚本（受信代码）**安装，且**只接受来自真实 `isTrusted` 事件调用栈的调用**（记录 `event.isTrusted` 并校验调用时机）。伪造方若直接 `ws.send`，缺 nonce 的"已消费"状态。

| 维度 | 评估 |
|---|---|
| 侵入面 | `src/host/page-runtime.ts`（nonce 生成/校验/一次性消费）+ `src/ui/consent.ts` + `src/desktop/host-client.ts`（点击回调取 nonce 并经确认函数回执）+ `src/host/protocol.ts`（报文加字段）。**跨 host+inject 两域**，不动 tauri |
| UX 代价 | **低**：复用现有模态，meta 展示不变 |
| 可绕过性 | **中**：比现状强很多（伪造需 nonce + 已消费标记 + 受信调用栈），但仍依赖"页内代码不可信"这条边界——若模型能执行任意页内 JS（它确实能通过工具回灌的内容影响 DOM），理论上仍可能在对的时机重放。**不能宣称零绕过，只能宣称"无用户手势则不可得 nonce"** |
| 测试难度 | **中**：nonce 绑定、一次性消费、缺 nonce 拒绝、nonce 复放拒绝，均可纯单测；"真实点击"难在 CI 模拟，用注入的 fake gesture 接口测 |
| dev(tsx) 兼容 | 完全兼容（纯 JS 逻辑） |

### 推荐：**方向 A（宿主侧原生确认框）做主，方向 B 做 dev 无-tauri 回退**

**理由**：本缺陷的根因是"决议来自被约束方"——**只有把决议搬到页面之外（A）才能从信道层面根除伪造**。B 无论怎么加固，决议报文终究经过页面 WS，只能是"提高伪造成本"，不能"消除伪造可能"。安全类缺陷应优先选从结构上消除成因的方案。

**但 A 的 UX 代价真实**：rich meta 丢失。缓解：A 的原生框最小化展示（工具名 + 一句话风险 + 允许一次/拒绝两个按钮），**把 `allow-session`/`allow-conversation` 这类长时效授权只放在 B 增强的页内模态**（短时效、逐次 can accept cost）；
即**混合策略**：
- **高风险/长时效授权**（`allow-session`、`allow-conversation`、hard-deny 邻近、越界）→ 方向 A 原生框（页面无法伪造）；
- **低风险、allow-once** → 方向 B（页内模态 + nonce 绑定），UX 顺滑。

## 2. 方向 B 的协议细节（若采纳/作为回退）

```
宿主 requestConsent(callId, tool, params, meta):
  nonce = base64url(crypto.randomBytes(16))
  pendingConsent[callId] = { ownerId, nonce, consumed:false, timer }
  send: { type:'consent-required', callId, tool, params, meta, nonce }

页端（受信注入代码）:
  showConsent(...) 渲染；按钮 onClick(e):
    if (!e.isTrusted) return;                  // 只认真实手势
    __studioConsent.confirm(callId, nonce, decision)

__studioConsent.confirm（注入脚本安装，宿主侧也是同一 contract）:
  ws.send({ type:'consent-decision', callId, nonce, decision })

宿主收到 consent-decision:
  p = pendingConsent[callId]
  if (!p || p.ownerId !== id) return;                 // 现有
  if (p.consumed) return;                             // 一次性
  if (!timingSafeEqual(msg.nonce, p.nonce)) return;   // nonce 绑定
  p.consumed = true; clearTimeout; resolve(decision)
```

**注意**：B 的 `nonce` 仍经 `consent-required` 明文下发到页面。所以 B 的强度完全依赖"页面拿到 nonce 也必须等真实点击才能回执"——而页面可以不等点击就直接发 `{callId, nonce, decision}`。**所以 B 单独不够**。B 的 `isTrusted` 检查必须发生在**回执产生的那一刻**且页面无法绕过（即回执必须由注入的受信函数在 click 栈内同步发出，且宿主信任该函数）。这要求**注入脚本本身不可被模型篡改**——而注入脚本与模型共享同一 origin，**这是 B 的天然上限**。

→ 因此 §1 的结论成立：**要根除必须用 A**。

## 3. 超时语义（默认取值 + 回退口径）

| 场景 | 现口径 | 本设计口径 |
|---|---|---|
| 用户点击前超时 | `consentTimeoutMs=60s` → `consent-abort(reason=consent-timeout)` → `deny` | **保持**：60s 超时 → deny（fail-closed）。A 方向：原生框超时 → 关框 + deny |
| **用户不在场（无页/无窗）** | `ensureConsent` 已 `consent-unavailable` → 拒 | **保持**：`consent-unavailable`（环境问题，与用户点拒绝区分，审计可分） |
| 用户离开（切走/最小化）| 无区别 | **保持现状**，不新增"离开即拒"（避免误伤长任务）；仅在超时上兜底 |
| 决议迟到（超时后又回执） | timer 已 fire、`pendingConsent` 已 delete → 迟到回执忽略 | **保持**；B 的 `consumed` + delete 双保险 |

**默认取值**：`consentTimeoutMs` 维持 **60s**；**回退口径**：任何"拿不到用户手势"的情形（超时、无窗、nonce 缺失、consumed 已用、isTrusted=false）**一律 deny**，绝不 fail-open。

## 4. 跨域触点清单

### `src/host/**`（Core）
- `page-runtime.ts`
  - `requestConsent`：A 方向→改为调用宿主本地确认接口（不 send `consent-required` 给页面 / 或只 send 通知）；B 方向→`consent-required` 增 `nonce`，`consent-decision` 增加 nonce + 校验 + `consumed`。
  - `pendingConsent` 结构加 `nonce`/`consumed`。
- `desktop-host.ts` `ensureConsent`：A 方向接本地确认接口；保持 `consent-unavailable` 与 generation 校验不变。
- `protocol.ts`：`consent-required`/`consent-decision` 报文加 `nonce` 字段（B）；A 方向可能加 `consent-resolved` 通知。
- 审计：`write_crash_log`/审计流记录"决议来源=宿主原生/页内nonce"，区分成因。

### `src/inject/**` / `src/ui/**`（UI 席位）
- `src/ui/consent.ts`：按钮点击回调须校验 `isTrusted`，并在 click 栈内同步回执（B）；A 方向则本模态在高风险档不渲染，改由宿主原生框。
- `src/desktop/host-client.ts`：`consent-required` 处理取 `nonce`；回执走 `__studioConsent.confirm`。

### `src-tauri/**`（若采纳 A）
- `main.rs`：提供"弹原生确认框"能力 + 把用户点击结果通过 IPC 回给 host 侧；bot 多窗时要能表达"给哪个 bot 问"。

## 5. 兼容（现有 consent 的三条路径在新机制下）

| 现有路径 | 新机制下的行为 |
|---|---|
| **自动放行区**（工作区内、`approvalClass=none`） | 不变：根本不进 `ensureConsent`，无 consent 交互 |
| **对话级放行**（`allow-conversation` 已登记） | 若已登记且 key 命中（principal+工作区+档位+对话+工具+目标），不再问；**首次登记**这次必须走新机制（A 原生 / B nonce） |
| **越界逐次问**（`outside` / 高风险） | **必须走方向 A 原生框**（本设计的核心收益） |

**关键兼容点**：三种 `ConsentDecision` 值（`allow-once`/`deny`/`allow-session`/`allow-conversation`）语义不变，变的只是"这个 decision 由谁产生、怎么验真"。

## 6. 测试与负控

### 必测负控（核心）
1. **页面伪造决议必须被拒**：
   - 构造：不需要真实用户，页端直接 `ws.send({type:'consent-decision', callId, decision:'allow-session'})`（**不带 nonce** / 带错误 nonce / 重复 nonce）；
   - 断言：宿主 `requestConsent` **保持 pending → 最终超时 deny**，绝不放行。这是**本卡的主负控**——把修法撤掉（回到现有 `ownerId===id` 就 resolve），此用例必红（变成 allow-session 成功）。
2. **nonce 一次性**：同一 nonce 第二次回执被忽略。
3. **isTrusted=false 的合成点击**不产生回执（B）。
4. **方向 A 的伪造面**：页面无论发什么 `consent-decision` 都不影响宿主原生框结果（A 下页面根本没有决议通道）。
5. **超时/无窗** 仍 deny（回归，不得 fail-open）。

### 测试落点
- 纯逻辑（nonce 生成/比对/consumed、超时语义）→ `tests/desktop/` 单测，直接 drive `page-runtime` 的 `requestConsent`（配 fake ws）。
- 原生框（A）→ 注入可测的 `askUserNative` 接口，单测其返回；真机归 Verify。

## 7. 给 PM 的裁决点

1. **方案取舍**：推荐"高风险走 A 原生框 + 低风险 allow-once 走 B nonce"的混合。若你要纯 A（最大安全、牺牲 UX）或纯 B（保 UX、承认非零绕过），请裁定。
2. **A 需要动 `src-tauri`**：是否接受本卡跨 host+tauri 两域？若否，则只能退 B，并接受"不能根除伪造、只能提高成本"的安全上限。
3. **原生框的最小信息集**：工具名 + 风险标签 + 允许一次/拒绝（不含参数全文），可接受否？
