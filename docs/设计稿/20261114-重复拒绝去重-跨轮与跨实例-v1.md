## 〇、结论（先给答案）

1. **建议：先取证，暂不实现 a/b/c 任一方案。** 三条理由都不是"感觉"，而是现读事实：
   - 现场那个「一轮 6–7 次 `memory_save`」的形态**已经被已入库的两层机制覆盖**（注入层封顶 + 本轮终局计数），跨轮/跨实例方案治不了它；
   - 「跨轮重发」目前**没有一条实证读数**，只有 VM 现场描述的形态（转述）；
   - 「跨进程并发」的前提（两个宿主 pid 同时活着）**未被证**，而应用已有单实例锁插件（现读）。
2. **若必须现在选一个做，选方案 a**（页内 per-conversation TTL 表，只缓存**轮次无关**的终局码）。理由是运维成本最低：一个 Map＋一个常量，不新增进程、不新增文件格式、不新增 IPC。
3. **无论做哪个方案，`memory-save-*` 三码一律不许跨轮缓存**（见 §2.2），这条与读数无关、现在就能定。
4. **方案 c（跨进程共享）不做**（PM 2026-11-14 裁定）。日后若读数确证两宿主并发，那是**单实例锁的缺陷**，按缺陷开卡查锁，**不许**用跨进程共享台账去绕开它。

## 一、现状（现读，带锚点）

### 1.1 两个计数器，两种寿命

| 层 | 落点（现读） | 计数器 | 计数对象 | 寿命 |
|---|---|---|---|---|
| 注入层（页面主世界） | `src/inject/main-world-interceptor.ts`，`MAX_SIG_REDELIVERIES = 3` | 同签名重复**投递**次数（n=1..4，第 5 枚起静默丢弃） | 「同一 `(tool, params)` 被反复投递」 | **一条回复流**：流开始时 `resetSignatures()`＋`cappedSigs.clear()` |
| 注入层（同文件 import 的 shared 模块） | `src/shared/continuation-prompt.ts`，`REPEAT_DENIAL_ALERT_THRESHOLD = 2` | 同 `(tool, 规范失败码)` **真实执行且被终局拒绝**的次数 | 「同一调用真跑过、真被拒」 | **一个 user turn**：只拿到本轮 `executions` 数组 |

签名口径：注入层用 `dupSignatureKey(invocationName, params)`（同文件），去重器本体在 `src/shared/tool-call-dedupe.ts`（`createToolCallDedupe().claimSignature`）。Core 侧没有 params，用**抽出的规范失败码**近似（`extractFailureCode`）。

### 1.2 事实订正：第二个计数器跑在**页端**，不在 node 宿主

路线图 §22.0.3 那张表把 Core 那层写作「Core 宿主层」。**现读结论：这个叫法会误导方案设计**——`buildContinuationPrompt` / `buildProtocolRepairPrompt` 的调用点**只有一处**，在 `src/inject/main-world-interceptor.ts`；`src/host/**` 对 `continuation-prompt` 只有注释级提及、零 import（今天核过两次）。

⇒ 两个计数器**都在页面主世界（webview 渲染进程）里**，都不在 node 宿主进程里。直接后果：

- 页面刷新／跳转／崩溃 ⇒ **两个计数器一起归零**；
- 不同 webview（多 bot 窗口）之间天然不共享；
- 想跨轮，其实**不需要跨进程**——页面在同一会话里本来就活着（跨轮只是换 `request.sent`）；真正需要落盘的是「页面重载后还记得」和「换进程后还记得」这两件更远的事。

### 1.3 宿主侧已有两件可复用的东西（这是方案 b 成本的关键）

1. **持久 KV**：`src/host/desktop-host.ts` 的 `kvGet`/`kvSet`，后端 `kvBackend.readAll()` / `writeBatch()` 落 `storage.json`；写入 **100ms 防抖批量**、读走内存缓存立即一致、`stop()` 前**显式 flush**（注释写明是为「退出前最后 100ms 的写入不静默丢失」）。页端聊天路径已经在用它存 `studio.execution.v2.session.<hash>` 会话键。
2. **进程内 per-conversation 台账**：`src/host/user-turn-ledger.ts`，`record/latest/clear`，TTL 30 分钟、上限 200 会话、LRU 淘汰，**纯内存**（宿主停止即清）。

⇒ 方案 b 所谓「宿主侧落盘小台账」**不是新基建**：落盘复用 KV，键形状复用 `studio.execution.v2.session.<hash>` 那一族即可（新键族必须与执行索引分开，别让 `emitExecutionIndex` 这类监听误触发）。
⇒ 会话标识也现成：`invokeTool`／`executeTool` 已经收 `conversationId`，宿主侧 `sessionId: conversationId ?? 'host-agent'`。

### 1.4 单实例锁**已存在**，但它证明不了现场那两个 pid

现读 `src-tauri/src/main.rs`：`tauri_plugin_single_instance::init(...)` 已接线（插件声明在 `src-tauri/Cargo.toml`，`tauri-plugin-single-instance = "2"`），回调行为＝**把已有主窗口 show／unminimize／set_focus**，注释原文「v0.30 单实例锁：第二个 deepseek-studio.exe 进程不再创建窗口」。另读 `src-tauri/src/sidecar.rs`：端口真相收敛在 `sidecar::health_port()`（env → `config.port` → 8760），且既有处理覆盖「端口已被健康宿主占着」的形态（既有测试名 `td05_alive_child_and_port_ok_is_healthy` 即为此场景）。

**这不是「已证事实」，只是「已有机制」。** 2026-11-14 复核后分两层收敛（v1 修订）：

**准确的前提句（写方案时用这句，不要用"单实例锁保证互斥"）**：

## 二、为什么现有两层都拦不住（三个具体形态）

### 2.1 形态一：同一轮内按 chunk 反复投递 —— **已覆盖**
同一条流里模型（或站点增量渲染）反复吐出同一标记 ⇒ 注入层封顶 3＋折叠回执＋终局提示；同时 Core 侧按本轮计数在第 2 次就出「已被终局拒绝 N 次」。2026-11-14 真机形态（562｜562 按 request 切段）就是这一类。

**读数出处（2026-11-14 17:0x 复核后补，避免"哪棵树"争议）**：那 1124 枚 `duplicate-tool-signature` 落在 **dev 仓** `logs/trace/trace-2026-11-14.jsonl`（首枚在 L41 附近）；同批 7 枚 `memory_save` 全 `ok=false` 出自 **dev 根** `~/.config/deepseek-studio/storage.json`（10:34:58–10:38:07）。**装版资源目录没有 trace 落点**（`logs\trace` 不存在），装版根 storage 最后写入停在 11-13 ⇒ 这批读数与装版无关。判断某轮读数出自哪棵树，看 **trace 落点＋storage 根**，不看装版 bundle 状态。

### 2.2 形态二：跨 user turn 连续重发 —— **未覆盖，且不是所有码都该覆盖**
换一轮用户消息后模型又发同一调用。两个计数器都在换轮时归零（Core 只拿本轮 `executions`；注入层换流即清）。

**但这里有一个必须先解决的正确性问题**：终局码分两类（现读 `src/shared/memory-write-gate.ts`，闸门判定的输入含**本轮用户的原文**）：

| 类别 | 码 | 跨轮缓存是否安全 |
|---|---|---|
| 轮次无关（真值只取决于装配态/策略） | `consent-denied`、`consent-unavailable`、`workspace-unconfigured`、`page-not-ready`、`unknown-tool`、`unknown-capability`、`tool-not-allowed-by-persona`、`outside-workspace`、`origin-denied`、`hard-deny` | **可以**缓存 |
| 轮次相关（真值取决于当前轮用户说了什么） | `memory-save-needs-explicit-instruction`、`memory-save-no-user-turn`、`memory-save-task-snapshot` | **绝对不行** |

反例具体到现场：第 1 轮用户说「查书房设备」⇒ `memory_save` 被拒（合理）；第 2 轮用户说「记住：我偏好客厅用 A 设备」⇒ 同样 `(memory.save, 同参数)` **这次是合法的**。若把第 1 轮的拒绝缓存到会话级，就会把用户明确授权的写入**误杀**——这是比原缺陷更糟的失败（静默丢记忆）。所以「跨轮去重」只能做**轮次无关码**那半张表。

> 注：`duplicate-tool-signature` 是注入层折叠回执，跨轮无意义（它的语义就是"同一流内"），不进任何跨轮台账。

### 2.3 形态三：跨实例（两个宿主各自重试） —— **前提未证**
现场 v1 记录称同时有 pid 26580／25692 两个宿主各自重试 `memory_save`（**转述**；同 §2.1 的出处结论，这批读数在 dev 树一侧，与装版无关）。若成立，两层都拦不住（都在页面进程内，各管各的 webview）。但如 §1.4：**GUI 层的单实例锁已证、宿主回路线待证**，而「遗留 sidecar／dev 与装版并存」这两条本来就在锁的覆盖面之外 ⇒ 「并存」仍需读数证明，不能拿转述当结论。

## 三、三个候选方案

### 3.1 方案 a：页内 per-conversation TTL 表

**做法**：在页面主世界加一个 `Map<conversationKey, Map<codeKey, {count, lastAt}>>`，`conversationKey` 取当前 `chat_session_id`（拦截器已有取真源 `getChatSessionIdFromBody` 一族），`codeKey = tool + 规范失败码`，只记 §2.2 表上半部分（轮次无关）。命中 ≥ 阈值时在 prompt 里追加一句「**本会话**该调用已被拒绝 N 次」，而不是「本轮」。

- 能拦：同一页面会话内、跨 user turn 的重发；页面重载前的一切跨轮形态。
- 拦不住：页面刷新/崩溃后（内存没了）、换 webview、两个进程。
- 崩溃一致性：无状态落盘 ⇒ 崩了就崩了，不会留脏数据；也正因为如此**不可审计**（事后查不到"上一轮拒过几次"）。
- 误伤风险：**低**，前提是严格按 §2.2 只缓存轮次无关码；另需给 `params` 的规范化（现在 `dupSignatureKey` 已是 tool+params 摘要，可复用同一口径）。
- 部署假设：无需任何额外假设；standalone／多实例都同构。
- 代价：一个文件＋一个常量＋一枚测试族；文案要新增「本会话」措辞并与「本轮」的计数句**互斥呈现**（否则模型看到两个 N，正是上一轮已经踩过的坑）。
- 主要缺点：**治不了「刷新后重来」**，而用户刷新页面恰好是高频动作。

### 3.2 方案 b：宿主落盘小台账（复用既有 KV）

**做法**：新键族（如 `studio.denial.v1.<conversationHash>`），值 = `{ [tool+code]: {count, firstAt, lastAt} }`，只存轮次无关码＋TTL；写入点放在**宿主**（`invokeTool` 拿得到 `conversationId` 与失败码），读取点两处可选：① 宿主在回传结果时就把「本会话已拒 N 次」作为结构化字段带回去（推荐，页端零 IPC）；② 由页端在构建 prompt 前主动查 KV。

- 能拦：跨 user turn **且跨页面刷新**、跨 webview（同一宿主）；进程重启后仍在（KV 落 `storage.json`，`stop()` 前 flush）。
- 拦不住：两个宿主进程并存（各自一份 KV？不——KV 是同一配置文件目录，会互相覆盖/掩盖，见下）；换机器自然没有。
- 崩溃一致性：有既有风险面——`storage.json` 是**整文件批量写**，两进程同时写会互相覆盖（今天的 KV 假设"单宿主"）。所以方案 b 与「多宿主」是互斥的：要么保证单宿主（方案 c 的仲裁），要么别用 KV 落盘。
- 误伤风险：同 §2.2 的约束；另加「TTL 定多长」这个产品问题（3 小时前的一句「记住」不能给现在当证据，这条 TTL 语义 `user-turn-ledger` 已经定过 30 分钟，可对齐）。
- 部署假设：必须假定**单宿主**；开发树＋安装版并用时会破坏这个假设。
- 代价：宿主侧写入点＋键族＋TTL＋一条把计数带回页端的通道。**通道成本要单算**：主世界拦截器现在没有直连宿主的出口（现读：该文件里对 8760／`/v1/` 零命中），页端↔宿主走的是 `src/inject/direct-bridge.ts` 一族与页端 UI 的 WS。走"宿主回传时附带"可以规避这条，但会改工具回执形状（要动 `src/inject` 与契约测试）。

### 3.3 方案 c：跨进程共享（命名管道／文件锁／单实例仲裁）

**做法**：三选一——① 单实例仲裁（已有插件，把它真正扩展成"第二个进程不启动工具回路"）；② 文件锁＋共享台账文件；③ 命名管道把"拒绝台账"做成一个小服务。

- 能拦：真并存的形态三。
- 拦不住：单实例锁没覆盖的判定差异（如 dev 与安装版不同 exe）。
- 崩溃一致性：文件锁要处理陈旧锁（进程被 kill 后锁文件残留），命名管道要处理服务端重启期间的行为——**都是分布式系统里最容易出隐蔽 bug 的一类**，而本项目到目前为止零这类基建。
- 误伤风险：同上，且多进程写同一台账时计数会被放大。
- 部署假设：Windows 单机、多用户？（同一用户的多实例才是现场）——这一层没有现成测试。
- 代价：最高。按「运维成本最低」这条口径，**不做**（PM 已裁）；且若现场真是并存，那是单实例锁的缺陷，先查锁（配置/清理残留路径），不要用新基建去绕。

### 3.4 对比表

| 维度 | a 页内 TTL | b 宿主 KV | c 跨进程 |
|---|---|---|---|
| 跨 turn | ✅ | ✅ | ✅ |
| 跨页面刷新 | ❌ | ✅ | ✅ |
| 跨 webview | ❌ | ✅（同宿主） | ✅ |
| 跨宿主进程 | ❌ | ⚠️ 会被 KV 互写破坏 | ✅ |

## 四、默认取值与回退口径

- **默认取值：暂不实现，先取证**（§1.4 那三枚读数 ≈0 成本）。理由：形态一已覆盖；形态二缺实证；形态三前提未证。**为凑方案而写代码会把面板做大而不解决任何已验证的现场。**
- **若 PM 要求「这一版必须有动作」**：取**方案 a**，且只做 §2.2 上半部分（轮次无关码）＋「本会话」措辞，不做落盘、不做 IPC。
- **若 PM 认为连 a 都不值得**：退回到**纯文案**——终局文案尾部追加一句「同一调用在本会话已被拒绝过 N 次」的**静态提示**（不带真实计数、不动计数结构、不动阈值），目的是让模型在跨轮重发时至少看到一句"可能是同一个坑"。缺点明写：它不是计数，只是提示，模型可能忽略。
- **无论选哪条**：`memory-save-*` 三码不跨轮（§2.2），这条现在就能定，不需要等读数。

## 五、依赖：哪些分支必须等真机 `pending-closure` 读数

`pending-closure` 是已入库的诊断线（注入层在 flush 时落 `pending-closure:closed(fences=N)` 或 `pending-closure:unclosed(fences=N)`，只对当前被认领的流），它判的是「同一流里重复投递的根因在闭合判定还是投递口」。

| 读数 | 含义 | 对本文方案的影响 |
|---|---|---|
| `duplicate ≤3` 且 `unclosed(fences=奇数)` | 重复根因＝**闭合判定/站点增量渲染** | **a/b/c 全都白搭**：真正的活是治闭合判定（另开卡）。本文只能落「不做」的结论 |
| `closed(fences=偶数)` 且仍有大量重复投递 | 投递口在宿主 flush 或被站点重发 | 形态一仍归已入库的两层；跨轮/跨实例才有讨论空间 |
| 同轮出现「两宿主并存」（进程启动时刻重叠） | 形态三成立 | 先查单实例锁为何没挡住（缺陷单），**再**谈方案 c |
| 跨轮重发的实证（同一 `chat_session_id`、两个不同 `turn` 各出现同码 ≥2 次） | 形态二成立 | 方案 a 从「可选」升为「该做」，且优先做 a 而非 b（因为跨刷新不是现场诉求） |

**本稿不把任何未取到的读数当已知结论**：§2.3 的「两个 pid 并存」标的是转述，§1.4 的「第二实例在起 sidecar 前退出」标的是未证。

## 六、明确不做

1. **不做**跨轮缓存 `memory-save-*` 三码（会把用户后续的合法授权写入误杀，§2.2）。
2. **不做**命名管道／文件锁（方案 c，PM 2026-11-14 裁定）；形态三若被读数坐实，按**单实例锁缺陷**开卡（清残留 sidecar／对齐 dev 与装版的 identifier 与 port），不用跨进程共享去绕。
3. **不改**注入层 `MAX_SIG_REDELIVERIES` 与 Core `REPEAT_DENIAL_ALERT_THRESHOLD` 的现有数值：两者的寿命（一条流／一个 turn）是**对的**，缺的是"跨轮"这第三根轴；改造方式是**新增**一根轴，不是改旧的两根。
4. **不把「本会话」的 N 与「本轮」的 N 同时塞进同一份 prompt**：上一轮已经因为"两个 N 会让模型不知道信哪个"把折叠回执排除出计数，这条判据同样适用。
