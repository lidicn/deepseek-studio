# M5 编程工具链设计方案

证据基线：E:\NAS\deepseek-studio 工作树现读，HEAD d933eb8（2026-10-18 20:27:51 +0800，131 commits，工作树 84 项未提交改动），Node v24.14.0，vitest.config.ts:6 只收 tests/desktop 与 tests/e2e，:10 串行执行。本文所有 file:line 指该基线；本次只读，未构建、未装依赖、未启动应用。

## 1. 结论摘要

三个工具的落点是：file.edit 做成宿主侧能力，核心是纯函数"字符串唯一匹配替换"，取代 src/host/kernel/edit-engine.ts 作为生产实现，路径一律经 workspace.resolveWithin 归一化，全部指令预校验通过后才落盘，任何一步失败原文件字节不变；test.run 做成宿主侧能力，只接受 package.json 的脚本键名或工作区内的测试范围，argv 化执行（永不经过 shell 解释器），红绿以退出码为准，失败细节结构化回灌并把完整日志落成工作区内的文件引用；debug 不做成模型可调用的独立工具，而是"所有工具失败都返回统一错误信封 + 宿主循环层做有限重试"，理由是没有工具能调试它自己看不懂的错误，重试决策必须在能看见失败的那一层做。三个工具都必须先登记进 tool-definitions 与 policy 名单、再在 tool-contract 登记上游调用名，否则模型发出的标签不会被拦截（tool-contract.ts:147-160）。

### 2.2 与需求稿不一致的四处（以代码为准）

1. 需求稿说"write 档已经是高危"。代码里档位是 read / insert / send / privileged（tool-registry.ts:21），file.write 就登记在 privileged（tool-definitions.ts:74）。正确表述是"file.write 已在最高档、已过同意闸门"，M5 不需要新造 write 档。
2. 需求稿说"TaskLoop 已经接管主路径"。send 一条腿确实切了（desktop-host.ts:716-727、753-760），但内核侧的工具执行桥没有接：createHostToolsAdapter 建好后被 `void kernelExecutor` 丢弃（desktop-host.ts:686-687），工具执行仍在引擎/页端拦截路径里经 invokeTool 完成。QD 守门席在 docs/DEV/主开发建议卡-QD守门席-20261018.md:140-176 已实测出同一批切换剩下四条腿未切：停止旗标在新主路永不复位（F-1）、busy 闸门失效（F-2）、回合事件无生产者（F-3）、覆盖面与主路错位（F-4）。M5 的工具必须挂在这个事实之上，不能假设主路已有取消、事件与并发闸门。
3. 需求稿说"file.read/file.write 已有整写能力"。整写确实有（file.ts:100-110），但它是"截断写 + mkdir -p + utf8 硬编码"，没有编码探测、没有原子替换、没有原文哈希，所以局部编辑不是"锦上添花"，而是唯一能避免整写丢编码与丢并发修改的路径。
4. 需求稿说"shell.exec 已有、能跑命令"。能跑，但硬上限 120s（shell.ts:18）且拒绝一切 shell 语法（shell.ts:133-139）。这两条直接决定 test.run 的实现形态：不能靠重定向把输出写文件，也不能把完整测试套件压进 120s，测试运行必须有独立于 shell.exec 的超时上限。

### 2.3 无法从静态代码判定的一处

需求稿描述"模型现在用 shell_exec（curl /dir/find）读文件"。代码面只能证明 file.read 已登记且上游名映射存在（tool-contract.ts:47-54、135-137），无法证明模型实际行为。这一条要真机跑一次看页端拦截日志与宿主审计记录才能定性，本方案不据此做任何取舍。

### 3.2 路径边界与归一化（判断点 10）

唯一入口是注入的 workspace.resolveWithin，实现里不再出现拼路径，这条与 workspace.ts:48-52 的契约注释一致。

规则（全部 fail-closed）：

1. 相对路径一律相对工作区根解析，不相对进程 cwd（workspace.ts:151-154）。
2. 词法包含判定 + 大小写归一化按既有实现（workspace.ts:111-134）。
3. 目标已存在时再做真实路径复核，软链接指向工作区外即判区外（workspace.ts:160-167）；realpath 抛错按区外处理（workspace.ts:165-166）。
4. edit 不创建文件，所以"目标不存在时词法允许"这条对 edit 无效：先 stat，不存在即 not-found。
5. 目标是目录、设备、FIFO 等非普通文件时回 invalid-argument（data.reason='not-a-file'）。
6. 追加拒绝：Windows 保留设备名（CON/PRN/AUX/NUL/COM1-9/LPT1-9）与备用数据流写法（路径首字符后有冒号），这些名字经 normalize 后仍可能指向设备，按 invalid-argument 拒。
7. UNC 路径（\\server\share）与设备命名空间（\\?\、\\.\）一律 invalid-argument，理由同 6，且本工具没有跨机语义。
8. 临时文件必须与目标同目录（同卷），创建前后都过同一条包含判定。

残余风险（记录不处理）：工作区内的硬链接指向区外文件时，realpath 无法与普通文件区分，edit 会照常修改；缓解是返回值里带 nlink，审计可见，需要更强保证时由 M8 的 E2 回滚机制覆盖。

### 3.3 匹配语义（判断点 1）

- 匹配对象是解码后的完整文本，按 edits 数组顺序依次替换，每次替换后在内存文本上重新扫描，后续指令看到的是前面指令的结果。
- 每条 oldString 必须在当前文本里恰好出现 1 次。0 次：整批失败，回 not-found 与最多 3 条候选（文件 + 行号 + 上下文行 + 近似度）。2 次以上：整批失败，回 match-ambiguous 与最多 10 条命中（文件 + 行号 + 该行内容）。
- 不做任何模糊匹配、不自动补上下文、不自动扩行、不做大小写不敏感匹配、不做空白归一化匹配。近似度只用于给候选排序，绝不用于直接落盘。
- 两条指令的匹配区间重叠、或第 n 条的 oldString 只在第 n-1 条应用后才出现，都按 invalid-argument 拒（data.reason='overlapping-edits'），不猜用户意图、不调整顺序。
- oldString 为空串、oldString 与 newString 完全相同，都按 invalid-argument 拒（空串会命中任意位置，空替换是无操作）。
- 不做回退：任何一条不满足唯一匹配，都不会退化成整文件重写。

### 3.5 原子性与失败回滚（判断点 3）

落盘只有一次真正的替换动作，顺序固定：

1. resolveWithin 归一化并 stat，取 mode/size/nlink。
2. 读原文为 Buffer，算 sha256Before；严格 UTF-8 解码（fatal 解码失败即 unsupported-encoding）；探测 NUL、BOM、换行风格、大小上限。
3. 内存里按顺序逐条替换并逐条做唯一匹配校验，任何一条失败 → 立刻返回，未做任何写操作。
4. 校验 expectedSha256。
5. 生成新文本并重新编码（BOM 原样拼回），写同目录临时文件 `<dirname>/.<basename>.<pid>.<rand>.tmp`，沿用原文件 mode。
6. rename 覆盖目标，这是唯一的替换点。
7. 失败路径：unlink 临时文件（best-effort），原目标文件零字节改动，返回 io-error 且 data.state='unchanged'。
8. 成功路径：返回 sha256Before / sha256After / bytesBefore / bytesAfter / applied / replacements。

三条与"把不修当成改了"直接相关的约束：

- unchanged 字段是显式的：dryRun 与任何失败路径都为 true，模型据此知道"这次什么都没动"，可以安全重发。
- sha256 前后都在结果里，宿主审计与模型都能核对改的到底是哪一份内容。
- 全程不写 .bak、不改动其它文件、不递归任何目录。

Windows 语义说明：fs.rename 覆盖已存在目标走 MoveFileEx 语义，天然是原子替换；代价是目标文件的替代数据流与显式 ACL 会丢（继承权限保留），这条记为已知风险。杀软或编辑器占用句柄时会拿到 EPERM/EBUSY，重试三次后如实报 io-error，不静默失败。

### 3.6 编码与换行保真（判断点 4）

- 读盘只走 Buffer，不经 fs.readFile(path,'utf8')，避免 Node 默认解码把非法字节替换成 U+FFFD 后悄悄改写文件。
- BOM：检测到 EF BB BF 就剥掉再匹配，写回时原样拼回。
- 换行：不做任何归一化。CRLF 文件里的 \r\n 原样在文本中参与匹配，写回时原样保留；LF 文件同理。检测到"oldString 用 LF 但文件是 CRLF，且换行统一后能唯一命中"时，只回一条 hint，不自动修。
- 非 UTF-8：fatal 解码失败即 unsupported-encoding，宁可拒绝也不"顺手转码"。GBK/UTF-16 文件在 M5 一律不可编辑。
- 末行换行、行尾空格、制表符：全部原样保留，因为只做定点替换。

### 3.7 同意档位对齐（判断点 5）

档位事实先摆清楚，再谈粒度：

- 工作区内的文件操作在 policy 里是 allow（policy.ts:203），因此任何档位下区内的 file.write / file.edit 都不过同意闸门；今天如此，M5 不改。
- 工作区外的文件操作：workspace 档 deny（policy.ts:214）、ask/auto 档 require-consent（policy.ts:216）、full 档 allow（policy.ts:215）。所以"越界必须显式同意"在 workspace 与 ask/auto 三档已经成立，只有 full 档是用户显式放弃询问。
- 因此需求稿问的"同一会话内多次 edit 是否需要重复授权"，答案是：区内编辑根本不弹同意框，不存在重复授权；重复授权只发生在越界编辑与 shell.exec 上。

要改的是越界那一路的放行粒度。今天会话放行表用整参数指纹（bot/registry.ts:42-59、75-91），file.write 的参数包含全文，等于"每换一份内容就要重新点一次同意"，与需求要求的"路径 + 操作"不一致。方案：

1. 新增纯函数模块 src/shared/consent-scope.ts，导出 `consentScope(tool, params): unknown`。文件族（file.read / file.write / file.edit / file.list / file.stat）返回 `{ op, path }`，path 用归一化后的工作区相对 posix 路径；其它工具原样返回 params。
2. desktop-host.ts 的 ensureConsent 两处同时改用它：1164 的 allowlist.has(tool, scope) 与 1179 的 allowlist.addTemporary(tool, scope, TTL)。两处必须同源，否则新键永远匹配不上，退化成每次都弹框（方向安全但体验退化）。
3. shell.exec 与 chat-* 的 scope 保持原样，换一条命令就重新弹框，这是必须保留的行为。

结果：用户对"某个路径上的编辑"授权一次，10 分钟 TTL 内该路径的后续编辑不再弹框；换路径或换操作立刻重新弹框。不引入"整目录授权"，不引入"永久放行"。

### 4.2 命令构造（判断点 6）

不引入 shell 字符串拼接，也不允许自由命令串。本次实测本机可用路径：

- E:\NAS\deepseek-studio\node_modules\vitest\vitest.mjs 存在 → 默认可以直调 JS 入口。
- C:\Program Files\nodejs\node_modules\npm\bin\npm-cli.js 存在，node 为 C:\Program Files\nodejs\node.exe。
- node_modules\.bin\vitest.cmd 也存在，但 Node 24 下 .cmd/.bat 不能用 shell:false 直接 spawn，所以不走这个。

解析顺序：

1. 有 cmd：校验字符集（只允许 [A-Za-z0-9:_-]）、校验它是 package.json scripts 的既有键名（否则 invalid-argument 并回可用键名 ≤20），argv = [process.execPath, <nodejs 安装目录>/node_modules/npm/bin/npm-cli.js, 'run', cmd]；npm-cli.js 不存在则回 not-found 并提示改用 scope 或不传 cmd。
2. 无 cmd 有 scope：要求本工作区存在 node_modules/vitest/vitest.mjs（否则 not-found），argv = [process.execPath, <ws>/node_modules/vitest/vitest.mjs, 'run', scope, '--reporter=json', '--outputFile=<日志路径>.json']。
3. 无 cmd 无 scope：同 2 但不带位置参数，跑全量。

两条附加约束：

- cmd 只用来选脚本，脚本体本身永不进入字符串命令面。代价是用户同意时看到的是"跑哪个脚本"，而不是展开后的完整命令行；缓解是脚本体就在工作区内的 package.json 里，用户可查，且下面的 policy 一节说明为什么不能把 test.run 当普通进程类工具自动放行。
- scope 必须是工作区内的相对路径或 glob，经 resolveWithin 校验（越界即 outside-workspace），作为独立 argv 元素传入，不拼接。

### 4.3 红绿判定与失败回灌

- 权威判据是退出码：exitCode === 0 且未超时 → passed=true；命令跑完但测试红 → ok=true、data.passed=false。这一点必须与工具层错误分开，否则测试红会被当成工具失败（shell.ts:294-297 会把非零退出码报成 ok:false 'nonzero-exit'），循环层的重试策略就会反复重跑一个本来就红的套件。
- 只有三类情况算工具失败：超时（timeout）、进程起不来（spawn-failed）、输出解析与日志都无法产出（io-error）。
- 计数优先取 vitest 的 json 报告（--reporter=json --outputFile），拿不到再退回文本解析（N passed / N failed / N skipped / Errors N 这类行）。kernel 原型里 total = passed + failed 的算法（kernel/test-runner.ts:44-48）会吞掉 skipped 与收集期错误，必须改成四项分开。
- 失败回灌预算：stdout 与 stderr 各保留首 2KiB 加尾 6KiB，总上限 16KiB；结构化失败最多 20 条，每条 name + file:line + 首行断言消息，单条截到 300 字符。日志整体落在工作区内 .deepseek/run-logs/<时间戳>-<随机>.<log|json>，结果里只给相对路径 + 字节数 + sha256 前缀。
- 因为 shell.exec 拒绝重定向且输出只留头部（shell.ts:133-139、264-273），test.run 不依赖它的截断：调用时把 maxOutputBytes 抬到 1MiB，自己按首尾保留裁剪，再用 --outputFile 把完整细节落到文件。

### 4.4 并发与超时（判断点 7）

- 每个工作区同时只允许一次运行。第二次调用立即返回 limit-exceeded（data.limit='concurrent-test-runs'），不排队。理由：TaskLoop 单轮超时 120s 且超时是 Promise.race 直接判停、不取消在飞的那一轮（task-loop.ts:161、190-199），排队会把等待藏进不透明的延迟里，先撞上回合超时，模型拿到的是 timeout 而不是"前面还有一次运行"，这是典型的幽灵失败。
- 默认 timeoutMs = 300000，上限 900000，cwd 固定为工作区根。既有 shell 能力的 120s 硬上限（shell.ts:18）不能直接沿用：完整套件在这个仓库上是分钟级。落地方式是把 clampTimeout 的上限从模块常量改为按实例构造传入（shell.ts:105-111 附近一处），shell.exec 继续用 120s，test.run 的实例用 900s。
- 超时必须走进程树终止，因此只能经既有 shell 能力执行（Windows 上是 taskkill /T /F，shell.ts:239-262）；test-runner 自己 spawn 会留下孤儿 vitest 进程，直接排除这种实现。

## 5. debug：不做独立工具（判断点 8）

### 5.1 结论与理由

debug 不登记成工具，因为没有工具能调试它自己看不懂的错误：模型拿到的只是 `[tool] failed: <错误码>`（task-loop.ts:111-114、212-221），它需要的是"错在哪、还能不能重试、现在文件是什么状态"，而不是再调用一次工具。把它做成工具还会多开一个 privileged 权限面，且页端解析器只认登记过的 invocationName（tool-contract.ts:141-160），多一个名字就多一条被注入利用的路径。

方案分两层：所有工具失败都返回统一错误信封（宿主侧），由循环层按信封决定是否重试（有限次）。

### 5.2 错误信封

新增 src/shared/tool-error-envelope.ts（纯函数），测试 tests/desktop/tool-error-envelope.test.ts。

```ts
export interface ToolErrorEnvelope {
```

### 5.3 重试策略

| 错误码 | 可重试 | 副作用状态要求 | 说明 |
|---|---|---|---|
| timeout | 是（1 次） | unchanged / unknown | 读类与 grep 类可安全重发 |
| io-error | 是（1 次） | 必须是 unchanged | EBUSY/EPERM 常为瞬时；未确认状态不动 |
| limit-exceeded | 否 | 任意 | 改参数或换范围 |
| missing-argument / invalid-argument | 否 | 任意 | 调用方纠正参数 |
| not-found / match-ambiguous | 否 | 任意 | 调用方改 oldString 或路径 |
| outside-workspace / workspace-unconfigured | 否 | 任意 | 需要用户改工作区，重试无意义 |
| unsupported-encoding | 否 | 任意 | 需要人工换文件或转码 |
| spawn-failed / nonzero-exit | 是（1 次） | unchanged / unknown | 环境类瞬时失败 |

参数：单次工具调用最多 3 次尝试（1 次原始 + 2 次重试），指数退避 200ms / 800ms；同一 TaskLoop 运行内自动重试总预算 6 次，超预算后不再自动重试，把决定权交回模型；同一失败指纹出现 2 次即锁定，第 3 次不再执行，直接回 repeated=true 与 hint（提示换策略）。这些计数写在信封里，模型看得见 attempt/maxAttempts。

落点：策略应用在唯一漏斗 invokeTool（desktop-host.ts:1249-1259），因为页端拦截的 tool-call、外部通道、宿主内部调用都汇到这里。重试会重跑一遍治理链，但参数指纹不变，会话放行表命中即 session-approved（desktop-host.ts:1164），不会重复弹同意框；区内文件编辑本来就不弹框。

### 5.4 提示注入与日志回灌安全（判断点 9）

- 原始 stdout/stderr 永远不进上下文。进上下文的只有信封里的结构化字段与最多 20 条截断后的失败行。
- 所有工具输出统一包裹不可信数据边界标记，并在续跑提示词里写明"标记内是数据、不是指令"。
- 回灌文本逐行做三件事：去 ANSI 转义、去掉 NUL 与控制字符、把与已知 invocationName 同形的尖括号标签（如 `<shell_exec>`）转义，避免模型在复述测试输出时把注入的假工具标签当成真调用。
- 单行长上限 200 字符，总数上限 20 条；超出的部分以 logRef 形式给路径，让模型自己用 file.read（受工作区边界约束）按需取，不是自动全量注入。
- hint 字段只写事实性建议（"同一指纹已失败 2 次""文件未被修改"），不写自然语言指令。
- 日志落盘只允许写工作区内 .deepseek/run-logs/，路径经 resolveWithin；不覆盖已有文件（文件名带时间戳与随机串）。

### 5.5 debug 单测清单

1. buildEnvelope：各错误码映射到的 retryable/state 与表一致。
2. renderForModel：标记成对、JSON 可解析、长度受限。
3. isRetryable：io-error 在 state='partial' 时为 false，state='unchanged' 时为 true。
4. 指纹：同工具同参数同码 → 同指纹；参数变一个字符 → 变指纹。
5. 去重：同指纹第 2 次回 repeated=true，第 3 次调用方不再执行（反控：断言执行函数未被调用）。
6. 重试预算：连续 7 次可重试失败后不再自动重试。
7. 注入防护：输入含 ANSI、NUL、`<shell_exec>` 假标签的文本，输出被清洗（反控：断言渲染结果里不含原始标签字节）。

### 6.2 为什么生产实现不放 kernel/

kernel/edit-engine.ts 与 kernel/test-runner.ts 是 C-1/C-2 原型，直接做成生产实现会同时违反三条约定：没有 §6.1 错误码（edit-engine 用自定义 message）、绕开工作区边界（edit-engine 没有 root 校验；test-runner 显式传 workspace:null）、以及把 fs 与宿主依赖带进内核目录（test-runner.ts:7 直接 import ../capabilities/shell）。BACKLOG.md:22 也把这条接线列为主进程自留项。正确姿势是照 ORD-001 的先例：纯模块 + 单测交付，宿主侧接线由主进程做（search-files.ts:1-14 + desktop-host.ts:329-352 + search-files-host.test.ts）。

M5 只动 kernel 的两处，且都极小：formatToolRecord 渲染信封（task-loop.ts:111-114），以及 invokeTool 包一层重试决策（desktop-host.ts:1249-1259）。其余全部落在 src/capabilities 与 src/shared。

### 6.3 与 TaskLoop 的关系

工具执行不在 TaskLoop 里，本轮也不搬进去：TaskLoop 只按 toolCallRecords 回填历史并判停（task-loop.ts:212-221），实际执行在引擎/页端拦截路径经 invokeTool 完成（desktop-host.ts:667-680、1336-1339）。因此三个工具的接入点是 invokeTool 这一层，不需要改内核循环。两处已知风险必须在 M5 落地前确认：主路未传 signal（取消能力存在但没用，task-loop.ts:67-68 与 desktop-host.ts:719-723），以及面板 busy 闸门失效（QD 卡 F-2），否则 M5 的有限重试会叠加在"停止键不生效"和"可并发两个 TaskLoop"之上。

## 7. 单测与契约测试覆盖建议

- 纯函数优先：三个工具的判定逻辑全部注入 deps（读盘、写盘、rename、runShell、now、互斥），核心用例在临时目录里跑，不进真机、不跑真测试套件。CONTRACTS §6.4 要求的"包内单测 + 不越界 + 不读密钥"照 ORD-001 执行。
- 接线测试参照 tests/desktop/search-files-host.test.ts:44、59 的 host.invokeTool 写法；privileged 工具在接线层要用 options.hostTools 注入替换表（desktop-host.ts:326 支持），避免依赖页端同意交互。
- 覆盖尺的已知口径：tools/coverage/check.ts 只统计 tests/desktop/*.test.ts 里的直接 import 字面量（QD 卡 F-4），所以每个新模块至少要有一个测试文件直接 import 它，否则覆盖门会把它记成未覆盖，即使行为其实被测到了。
- 每节列出的用例之外，统一补三类反控用例：约束真生效（失败路径零写入、越界必拒）、上限真生效（条数/字节/超时/重试预算）、以及错误码与 §6.1 词表一致（含新增两码的登记存在性检查）。
- 真机验收（不进自动测试）：面板发一次多文件编辑任务，人工从中途打断，确认停止键生效与否；跑一次 test.run 看失败摘要是否够模型定位；确认同意框在越界编辑与 test.run 上确实出现。

## 8. 风险点清单（按用户感知影响排序）

1. 改错文件或改错位置。缓解：唯一匹配硬约束、edit 不创建文件、路径必须经 resolveWithin、越界在 workspace 档直接拒。
2. 编辑把文件写坏。缓解：BOM 保留、换行不归一化、非 UTF-8 直接拒、临时文件 + 单点 rename、失败原文件零字节改动、返回值带前后 sha256。
3. 同意疲劳导致越界写入被放行。缓解：会话放行键从"整参数"改为"路径 + 操作"，换路径必须重新确认；不提供整目录或永久放行；TTL 维持现有常量。
4. 测试结论误导模型。缓解：退出码为红绿唯一权威，ok 与 passed 分离，计数四项分开，失败摘要结构化并限量。
5. 命令注入等价物。test.run 的脚本体在 package.json 里，policy 看不到；缓解是让它恒过同意闸门（不进 PROCESS_TOOLS 正是为了不被 auto 档静默放行），且 argv 永不进 shell。
6. 提示注入。测试输出与文件内容都可能被植入指令；缓解见 5.4，核心是原始输出不进上下文 + 不可信边界标记 + 假标签转义。
7. 幽灵失败。TaskLoop 单轮超时 120s 且不取消在飞轮（task-loop.ts:190-199），test.run 排队就会触发；缓解是拒而不排队，并把 test.run 的超时上限提到 900s。
8. 主路未接的腿放大一切问题。停止旗标不复位、busy 闸门失效、回合事件无生产者（QD 卡 F-1..F-3）会与 M5 的重试叠乘；缓解是 M5 落地前先确认这三条的处置，或至少不让编辑类工具依赖停止信号。
9. 既有 fail-open 被复制。search_files 的 root 直接取自模型参数（desktop-host.ts:334），policy 不治理该工具（policy.ts:94 名单里没有它），risk 为 read 不过同意闸门（tool-definitions.ts:108、tool-registry.ts:49-51），因此 `root: 'C:\\'` 这类调用不受工作区边界约束。M5 的两个新工具一律走 resolveWithin，不复制这个形态；是否顺带收紧 search_files 属于另一个决定，本文不擅自扩大范围。
10. Windows 文件替换语义。rename 覆盖会丢替代数据流与显式 ACL；被杀软或编辑器占用时 EBUSY/EPERM；缓解是重试三次 + 如实报错 + state='unchanged'。
11. 日志膨胀。.deepseek/run-logs 无上限；缓解是每次写入记相对路径与字节数，并在 M5 落地时加一条按目录大小裁剪的策略（保留最近 N 次）。

## 9. 不做什么

1. 不做多文件事务型批量编辑。Windows 上多次 rename 无法构成事务，"部分文件已改"正是用户最难接受的状态。多文件改动交给 file.write 或多次 file.edit；kernel/edit-engine.ts 的多文件批量 + 反向回滚只作为原型保留，不作为生产方案。
2. 不做模糊匹配、不做自动修 CRLF、不做空白归一化、不做大小写不敏感匹配，也不在匹配失败时回退整文件重写。
3. 不引入任何 shell 字符串面：不用 shell:true，不用重定向与管道，不对 cmd 做字符串拼接。
4. 不做独立的 debug 工具，也不给模型一个"再跑一次刚才那条命令"的工具。
5. 不做 test.run 的排队与串行化队列。
6. 不写文件级备份仓或自动回滚（E2 git shadow 是 M8 的事）。
7. 不自动去只读属性，不改 ACL，不尝试修改非 UTF-8 文件。
8. 不在 M5 里修 TaskLoop 主路剩下的四条腿（signal / stop / running / 事件总线）；那是 M4 遗留账，但 M5 的验收必须显式确认它们的状态。

## 10. 待确认问题（3 条）

1. test.run 是否保留"任意 package.json 脚本键名"这一入口？保留就要依赖 <nodejs 安装目录>/node_modules/npm/bin/npm-cli.js（本机实测存在），而 fnm/volta/自编译 node 会让该路径失效。若确认只支持"缺省直调本地 vitest + scope"，实现可以少一个失败面，代价是跑不了 typecheck 这类脚本。
2. 越界编辑的会话放行粒度改成"路径 + 操作"后，TTL 维持现有的 10 分钟（复用 DEFAULT_SESSION_GRANT_TTL_MS），还是越界编辑一律不给会话级放行、每次都必须显式点一次？这决定"用户体验"与"越界写入最小化"的取舍方向。
