## 1. 头号冲突裁定：(A) 删 —— 证据链

### 1.1 事实一：最终 body 的 prompt 长什么样（源码 + 真机双向确认）

```
最终 body.prompt = buildCapabilityPrompt(taskText) + memoriesBlock + "\n\n" + cleanPrompt
                   └── head：S1 能力块（含「## 可用工具」10 行）+ S2 MCP 目录（62 名）
                                                                ↑ 由 :1340 拼，:1340 之前是 :1339 的 strip
                   └── tail：cleanPrompt
                       ├ 首轮 = 页面原文本
                       └ 续跑轮 = 续跑 prompt（规则三行 + <original_task> + [FAILURE_RECOVERY]
                                  + <tool_results> + [S3 目录]）
```

- 源码：`main-world-interceptor.ts:1340`（拼 head）、`:2718`（续跑轮写 `parsed.prompt`）、`:2699-2701`（构造续跑 prompt）
- 真机：Verify 14 轮测得「相邻轮首差字节 = 稳定前缀边界（预算态 7,071 B → P1 修复后 ≈13,078 B）」→ **续跑 prompt 整体位于 head 之后**，与本图一致

### 1.2 事实二：S3 与 S1 的 10 行**逐字节相同**（实测）

对真实导出（`capabilityPromptText()` / `catalogText()`）抽「## 可用工具」段比对：

| 段 | 段字节 | 工具行数 | 工具行字节 | 多出的行 |
|----|--------|---------|-----------|----------|
| S1（`TOOL_CAPABILITY_PROMPT` 内，`interceptor:976`） | 1,037 | 10 | **1,021** | 无 |
| S3（`TOOL_CATALOG_TEXT`，`interceptor:994`） | 1,155 | 10 | **1,021** | `调用方式：直接输出 XML 标签，标签体内为合法 JSON，如 <shell_exec>{...}</shell_exec>`（134 B） |

**10 行工具声明逐字节相同**（`identicalToolLines = true`）。S3 多出的 134 B「调用方式」行，其信息已被 S1 的「## 工具调用」段覆盖（同一段里已有"输出直接 XML 标签、标签体内必须是合法 JSON"及 6 个示例）。

⇒ **S3 是纯重复，删掉零信息损失。**

### 1.3 事实三：删目录实参省多少（实测，四个口径一致）

| 口径 | 带目录 | 不带目录 | 省 |
|------|--------|---------|-----|
| 续跑轮（空结果） | 1,806 B | 629 B | **1,177 B** |
| 续跑轮（1 条结果） | 1,924 B | 747 B | **1,177 B** |
| 协议修复轮 | 1,728 B | 551 B | **1,177 B** |

省的是 **1,155 B 目录原文 + 22 B 分隔行（`\n\n### Available Tools\n`）= 1,177 B/轮**，与轮次、结果条数无关（恒定）。

### 1.4 事实四：为什么 MiMo 的「目录漂移」对我们不成立

MiMo 的论证链是「目录排在 `<tool_results>` 之后 → 结果 JSON 每轮长度变 → 目录漂移 → head 对不齐」。核源码 + 核真机后：

1. **续跑 prompt 里那份目录不是 MCP 目录**。MiMo 写它「即 `formatMcpToolsBlock` 的产物（`interceptor:1050`）」——**不对**。生产调用点传的是**静态** `TOOL_CATALOG_TEXT`（`interceptor:994`，1,155 B，10 个 studio 工具）：`interceptor:2700-2701`。`formatMcpToolsBlock`（:1050）产出的 MCP 目录在**另一条路**上（`buildCapabilityPrompt` :1171 → 拼进 :1340 的 head）。所以 MiMo 说的"MCP 目录漂移"在**内容上**就不存在（静态目录内容不随轮变）。
2. **即使目录会漂移，也影响不到被判据测量的前缀**。续跑 prompt 整体位于 head 之后（§1.1），它内部的任何顺序调整都不改变最终 body 的 prompt 前缀。Verify 的读数直接证明：首差字节**恰好落在稳定前缀边界**（13,078 B），而不是落在续跑 prompt 内部。
3. **`FAILURE_RECOVERY` 条件插入（`:313`）同理**在 tail 内 → 不影响前缀。

⇒ MiMo 的 I1/I4 若照字面实施，**对三条判据的贡献是 0**。这正是 PM 点名的那个坑：**MiMo 的 head = 续跑 prompt 的前缀；我们要守的 head = 最终 body 的 prompt 前缀**。两者不是同一个对象（§2 专门辨析）。

### 1.5 为什么不选 (B) 留

(B) 的唯一论据是「recency 效应：让 studio 工具名离工具结果更近」。三点回应：

1. 该论据是**假设**，本卡没有任何证据（无 A/B 读数）；
2. 同一批 studio 工具名在 head 里（13,078 B 之前）**已经出现**，对 13–25 KB 的 prompt 而言 13 KB 之前仍在注意力范围内；
3. 保留 (B) = 每轮让同一份 1,021 B 的工具声明出现两遍 → 与 PM 自己立的规矩（"别为了保住立项目标硬编收益"）相悖。

**裁定：(A) 删。** 配 §8 回滚开关 + §5 真机 A/B（工具调用成功率/可发现性），若真机观察到退化，按开关回滚。

## 2. 两个 head 的辨析（PM 点名的核心，写给实现者）

| | **我们守的 head（head-A）** | **MiMo 的 head（head-B）** |
|---|---|---|
| 定义 | **最终 body 的 `body.prompt` 的前缀** = 能力块（S1+S2）+ 记忆段 | **续跑 prompt 自身的头** = 规则三行 + `<original_task>` + 目录 |
| 由谁产生 | `prepareOutgoingBody` 的 prompt 分支（`interceptor:1340`） | `buildContinuationPrompt` 的拼装数组（`continuation-prompt.ts:305-319`） |
| 落在 body 的哪 | 开头（N ≈ 13,078 B） | head-A **之后**（tail 内） |
| 谁在测 | Verify（14 轮 + P1 复验 8 次）、dsh 的 chained 缓存 | MiMo 自定义（自测） |
| 稳不稳 | 同轮内稳（P1：8,192 B 内全等，首差 13,078–13,122 B）；跨轮会变（记忆段/MCP 段变化，**预期**） | 链内稳（需把 `FAILURE_RECOVERY` 挪走） |
| 与判据的关系 | **判据 2 直接对应它** | **与判据无关**（改它不会让判据 2 变好） |

⇒ **I1 必须写成 head-A。** 若把 I1 写成 head-B，就会出现"续跑 prompt 内部重排做完了，判据 2 的读数一点没变"的空转。

## 11. 诚实结论：M1.5 值不值得做

**结论：值得做，但规模是"小卡"，不是"改造"。**

| 维度 | 事实 |
|------|------|
| 判据压力 | **零**——三条判据今天全部达标（Verify 14 轮 + P1 复验 8 次）。M1.5 不推进任何判据 |
| 字节收益 | **-1,177 B/轮**（实测恒定）。相对 Verify 的 prompt 体量（13,524–23,291 B）约 **5–9%**；相对 body（10,119–25,637 B）约 **4–11%** |
| 改动成本 | 生产代码 **2 行**（去实参）+ 2 处 trace + 1 个测试钩子；`continuation-prompt.ts` 零改动；不动 `src/host/**`、不动 `src-tauri/**` |
| 风险 | 低：不动 head → 不涉及断链；回滚即刻生效（§8） |
| 真正的大头不在本卡 | 记忆段 5,551–6,082 B **落在稳定前缀内**（P1 复验 §4.3：跨轮首差 7,234 B 落记忆段内）→ 跨轮 head 会变；这属于 P1/P2 线，且要动 head（付断链代价）→ **本卡不做** |

**建议排期**：
- 若 PM 认为 -1.2 KB/轮 值得单独立项 → 按本契约做，**一张小卡**（实现 + 4 个测试文件 + 1 次真机 A/B）。
- 若认为不值得单独立项 → **并入 P1 的后续卡或"注入瘦身第 3 条"**，因为它与 P1 同属"注入体量"这条线，且 P1 复验已经把基线（13,078 B、首差字节、字节分段）准备好了，顺手做的边际成本最低。
- 无论哪种排法，**先做那 4 条回归护栏**（I1′/I2′/I5′/字节账）：它们是"别让今天的达标被后来人悄悄改坏"的保险，**不依赖删 S3 也能先落**。
