# M5 编程工具链方案 · edit-engine / test-runner / debug

> 2026-10-18 | 对应需求稿：docs/mimo-需求稿-M5-编程工具链.md
> 前置：TaskLoop 已接管主路径；file.read / file.write 已有整写能力；shell.exec 已有
> 现状核对：src/host/kernel/edit-engine.ts、src/host/kernel/test-runner.ts 已存在；debug 缺失

---

## 0. 结论摘要

| 工具 | 现状 | 本方案要补的 |
|---|---|---|
| edit-engine | 已有 applyEdits(workspace, instructions[])，oldText→newText，预检查 + 原子回滚 | 错误码对齐 CONTRACTS §6.1、多处匹配消歧、新增文件语义、consent 对齐、返回值加 details |
| test-runner | 已有 runTests(workspace, filter?)，硬编码 npx vitest run，正则解析 | 改为 {cmd?, scope?} 入参、命令白名单、exit code 为准、失败结构化摘录、超时分级 |
| debug | 无 | 新增纯函数包：错误信封 ToolErrorEnvelope + 重试决策 decideRetry，不改 TaskLoop 主路径 |

三条总原则：

1. 工具层只做纯函数 / 注入式实现，不反向依赖 TaskLoop 等主路径控制器。
2. 所有错误走 { ok: false, error } 而非抛异常（对齐 src/capabilities/types.ts 的 ExecuteResult）。
3. consent 闸在 registry 层统一裁决，工具内部不自行放行、不降档。

## 1. edit-engine（局部改文件）

### 1.1 接口签名

```ts
export interface EditParams {
  path: string;
  oldString: string;
  newString: string;
  line?: number;
  createIfMissing?: boolean;
  replaceAll?: boolean;
}

export interface EditData {
  path: string;
  change: 'modified' | 'created';
  replacements: number;
  linesAfter: number;
  diffPreview: string;
}

export type EditResult =
  | { ok: true; data: EditData; content: Array<{ type: 'text'; text: string }>; details: Record<string, unknown> }
  | { ok: false; error: string; details: Record<string, unknown>; content: Array<{ type: 'text'; text: string }>; isError: true };
```

多文件批量版保留现有 applyEdits（原子回滚），工具层单条调用即 applyEdits(ws, [one])。

### 1.2 错误码与边界情况

| 情况 | 处理 | error 码 | details |
|---|---|---|---|
| path / oldString / newString 缺失 | 拒绝 | missing-argument | field |
| 绝对路径 / 含 .. / 解析后不在 root 内 | fail-closed，不做 IO | outside-workspace | path, resolved |
| root 未注入 | 拒绝 | workspace-unconfigured | 空 |
| 文件不存在且未开 createIfMissing | 拒绝 | not-found | path |
| 文件不存在但 createIfMissing=true 且 oldString 非空 | 拒绝 | invalid-argument | reason: create-requires-empty-oldString |
| oldString 找不到 | 不返回原文，只返回最近似片段 + 行号 | not-found | nearest{line,text}, hint |
| 多处匹配且无 line、未开 replaceAll | 拒绝，不猜 | invalid-argument | matchCount, lineNumbers[] |
| 给了 line 但窗口内无匹配 | 拒绝 | invalid-argument | line, window |
| oldString 与 newString 相同 | 拒绝（空操作，防死循环） | invalid-argument | reason: noop-edit |
| 文件超 2MB 或 oldString 超 64KB | 拒绝 | limit-exceeded | limit, actual |
| 读 / 写 / rename 失败 | 捕获转码 | io-error | syscall, code（不透传堆栈） |

为什么找不到时返回 nearest 而不是原文：file.read 已有分页能力，把原文塞进 error 会浪费 token 且诱导模型整写。nearest 用行级近似匹配，成本 O(n) 可控。

### 1.3 新增文件 vs 修改已有文件

- 不新增独立 file.create 工具：createIfMissing: true + oldString: 空串 即为创建，语义清晰且复用同一套 consent。
- file.write 原样保留，作为整写 / 大改通道；edit 只负责点改。二者不互相替代。
- 工具 description 里写死优先级：小改用 edit；新建或整体重写用 file.write；改之前先 file.read 确认原文。

### 1.4 consent 闸对齐

- 在 src/host/tool-definitions.ts 注册 edit：risk: 'privileged'、execution: 'host'，与 file.write 同档。
- 理由：edit 能改任意工作区文件，破坏力与 write 等价，而且更隐蔽（模型看不到全貌）。
- 不新增档位、不降档；越界由能力层返回 outside-workspace，最终仍以宿主 CapabilityContext.allowOutsideWorkspace 为准（纵深防御）。
- 每次 edit 单独过闸，不做「本批次已授权」的隐式复用。

## 2. test-runner（跑测试）

### 2.1 接口签名

```ts
export interface TestRunParams {
  cmd?: string;
  scope?: 'changed' | 'all' | string;
  timeoutMs?: number;
  tailLines?: number;
}

export interface TestData {
  status: 'pass' | 'fail' | 'error';
  runner: 'vitest' | 'jest' | 'npm-script' | 'custom';
  cmd: string;
  exitCode: number | null;
  timedOut: boolean;
  durationMs: number;
  total: number | null;
  passed: number | null;
  failed: number | null;
  skipped: number | null;
  failures: Array<{ name: string; file?: string; message: string }>;
  outputTail: string;
  truncated: boolean;
}
```

结果包装成 ExecuteResult：{ ok, data: TestData, content: [{type:'text', text: renderForModel(data)}], details }。

### 2.2 默认跑什么 & 命令白名单

不硬编码 npx vitest run（现状问题：换 runner 就废）。按 workspace/package.json 的 scripts.test 决定：

1. 含 vitest → npx vitest run（scope 追加路径）
2. 含 jest → npx jest --ci
3. 其它非空 → npm test --silent
4. 无 scripts.test → not-found（details 给出尝试过的字段），不瞎跑

cmd 显式给定时必须过白名单：以 npm test / npx vitest / npx jest / node --test 开头，且不含 shell 元字符（分号、与号、竖线、重定向、反引号、美元符）。一律以 argv 数组交给 src/capabilities/shell.ts，不新增 spawn。

### 2.3 红绿判定

exit code 是唯一权威，正则只做补充统计：

- exitCode === 0 且未超时 → pass
- exitCode !== 0 且解析到 failed > 0 → fail
- exitCode !== 0 但解析不到任何用例、或超时、或 spawn 失败 → error（这类不该去改代码，该查环境）

补充解析尽力而为：vitest 的 Tests N passed 与 × 行；jest 的 Tests 汇总块。解析不到就把 total/passed/failed 置 null，绝不用 0 冒充。

> 现状坑：现有实现用 passed + failed 推 total，解析失败时会得到 0/0 假绿，必须修。

### 2.4 失败怎么给模型

分两层，避免一次塞爆上下文：

- content[0].text：结构化摘要（status / cmd / exitCode / durationMs），最多 10 条 failure（file:line + 首行错误），再附输出尾部 tailLines 行。
- details：完整 TestData，UI 可展开；原文超 200KB 截断并置 truncated: true。

只摘错误行，不贴全量 stdout：优先抓 FAIL / AssertionError / Error: / expected 匹配行上下各 2 行，去重后拼接。

### 2.5 超时

- 默认 120s（与现有实现一致），可调，上限 600s。
- 超时后 status: 'error'、timedOut: true，必须杀掉子进程树。
- 超时文案明确写「这不是断言失败，不要改测试代码」。

## 3. debug（错误恢复）

拆成两个纯函数，都不碰 TaskLoop 主路径；TaskLoop 只需拿到工具结果后调一次 decideRetry。

### 3.1 统一错误信封

```ts
export interface ToolErrorEnvelope {
  tool: string;
  error: string;
  stage: 'validate' | 'resolve' | 'read' | 'write' | 'execute' | 'parse';
  message: string;
  retryable: boolean;
  hint: string;
  stderrTail?: string;
  fingerprint: string;
}
```

给模型的文本模板：

```
[edit] not-found @ read
内容不匹配：oldString 在 src/a.ts 未找到。最近似第 42 行：const foo = bar();
建议：先 file.read src/a.ts 确认缩进后再 edit。
retryable=true
```

retryable 判定表（纯函数，可单测）：

| 错误码 | retryable | 理由 |
|---|---|---|
| missing-argument | true | 补参数可解 |
| invalid-argument | true | 改参数可解 |
| not-found | true | 文件 / 文本已变，重读后可解 |
| outside-workspace | false | 需人改策略，模型无权自愈 |
| workspace-unconfigured | false | 同上 |
| limit-exceeded | false | 应换策略（改用 file.write 或分段） |
| io-error | 仅 EBUSY / EPERM 为 true | 其余为 false |

### 3.2 重试策略 decideRetry

```ts
export interface RetryState {
  attempts: number;
  totalFailures: number;
  recent: string[];
}

export interface RetryDecision {
  action: 'retry-same' | 'retry-modified' | 'give-up' | 'escalate';
  reason: string;
  autoContinue: boolean;
}

export function decideRetry(
  env: ToolErrorEnvelope,
  state: RetryState,
  limits?: { maxSameFingerprint?: number; maxTotalFailures?: number; windowSize?: number }
): RetryDecision;
```

规则（按优先级）：

1. env.retryable === false → give-up，autoContinue=false，reason 给用户可读的一句话。
2. 同 fingerprint 已失败 ≥ 2 次 → give-up（相同参数绝不重试第三次，这是防死循环的主闸）。
3. recent 窗口内出现 ≥ 3 个不同 fingerprint 且都失败 → escalate（方向错了，交回模型重规划或问用户）。
4. totalFailures ≥ 6 → give-up。
5. 否则 retry-modified（autoContinue=true），并把 hint 带进下一轮。

默认 limits：maxSameFingerprint=2、maxTotalFailures=6、windowSize=5。上限硬编码在纯函数里，TaskLoop 不新增状态机字段。

### 3.3 与 TaskLoop 的边界

- 不改 TaskLoopStopReason 枚举（CONTRACTS §2 一个字都不动，避免同步白名单）。
- 工具失败仍是正常工具结果（ok:false），TaskLoop 照常喂回模型；decideRetry 只影响是否置 terminate 提前结束，不新增停止原因。

## 4. 单测覆盖建议

每个工具按「正常路径 + 每类错误路径 + 边界」覆盖，用临时目录 + 注入 fs，不依赖真实仓库树（对齐 CONTRACTS §6.3）。

### edit-engine（约 18 例）

- 正常：唯一匹配替换 / 创建新文件 / newString 空串删除 / replaceAll 多替换
- 错误：缺参、路径 .. 越界、绝对路径、root 未配置、文件不存在、create 但 oldString 非空、oldString 未命中、多处匹配无 line、line 窗口无命中、oldString 与 newString 相同
- 边界：空文件、文件末尾无换行、CRLF 文件、oldString 跨 3 行、超大文件 limit-exceeded
- 原子性：两条指令第二条失败 → 第一条已回滚（沿用现测，补 rolledBack 断言）
- 符号链接：workspace 内 symlink 指向外部 → outside-workspace

### test-runner（约 14 例）

- 正常：全绿（exit 0）、有失败（exit 1 且解析到 failed）、无 scripts.test 时按顺序回退
- 解析：vitest 文本样本、jest 样本、解析不到时 total 为 null 而不是 0、失败用例截断到 10 条
- 安全：cmd 白名单外（rm -rf、含 &&、含分号）→ invalid-argument；断言 argv 数组不含 shell
- 超时：timedOut 为 true → status 为 error，并断言子进程被杀
- 边界：空测试集（0 tests）、输出 1MB 截断、scope 指向工作区外 → outside-workspace

### debug（约 12 例）

- retryable 判定表：7 个错误码逐一断言（表驱动）
- decideRetry：同 fingerprint 第 3 次 → give-up；3 个不同 fp 全败 → escalate；总数 6 → give-up；不可恢复码 → give-up
- 信封序列化：文本模板包含 code / stage / hint；断言文本里不含堆栈
- 幂等：同输入同输出（纯函数）

CI 门槛：npm run typecheck && npx vitest run tests/desktop/kernel-*.test.ts 全绿，且新增文件不触碰 src/host/kernel/task-loop.ts。

## 5. 风险点

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | 多处匹配误改 | oldString 太短（如单个右花括号）极易命中多处，默认第一处会静默改错 | 默认宁失败；error 回 lineNumbers[]，模型带 line 重试；replaceAll 显式开关 |
| R2 | error 泄露大段原文 | 把原文回给模型既费 token 又诱导整写 | 只回 nearest 单行 + hint；全文走 file.read 分页 |
| R3 | 超时不杀子进程树 | Windows 上 npx → node → worker 三层，只 kill 顶层留孤儿吃 CPU | 单测断言进程树被杀；shell 层用 taskkill /T；超时立即置 status error |
| R4 | test 命令注入 | cmd 若走 shell 解释器，模型可拼 rm -rf | argv 数组 + 白名单 + 禁 shell 解释器；白名单外一律 invalid-argument |
| R5 | 假绿 | 解析失败时 failed=0 被判 ok:true | status 只认 exit code；解析不到置 null；parse 阶段 error 单独标记 |
| R6 | edit 绕过 consent | 若把 edit 定义为 read 档，模型可自动改文件 | risk 设为 privileged 与 write 同档；越界走 outside-workspace 且以宿主裁决为准 |
| R7 | 重试死循环 | 模型原样重试同一失败调用 | 同 fingerprint 上限 2 次；总失败 6 次；escalate 交回用户；上限在纯函数里可测 |
| R8 | 工具层与 kernel 耦合 | 顺手 import TaskLoop 导致主路径被动 | 只允许 node:fs / node:path / capabilities 类型；加 lint 规则禁止反向 import task-loop |
| R9 | Windows 换行 / 编码 | CRLF 文件用 LF 写 oldString 必然不匹配 | 比对原始内容；不匹配时 hint 提示可能是 CRLF；单测覆盖 CRLF |
| R10 | 工具描述诱导 | 模型不知道 edit 与 file.write 分工，仍爱整写 | description 写死优先级：小改 edit、新建 / 重写 write、先 read 再 edit |

## 6. 落地顺序

1. P0：debug 纯函数包（tool-error.ts + retry-policy.ts）+ 单测。无依赖，先立错误码规范，后面两个工具直接复用。
2. P1：edit-engine 补错误码 / details / line 消歧；在 tool-definitions.ts 注册 edit（privileged）；补单测。
3. P2：test-runner 改入参为 {cmd?, scope?}、加白名单、status 只认 exit code；补单测。
4. P3：TaskLoop 侧只加一行「读 details.retry.autoContinue 决定是否 terminate」，不改停止原因枚举。

## 7. 明确不做

- 不替代 file.write（保留整写能力）
- 不做 IDE 集成（语法高亮、跳转定义）
- 不做 git 集成（commit / diff）
- 不新增 TaskLoopStopReason 值
- 不新增 spawn、不绕 consent 闸
