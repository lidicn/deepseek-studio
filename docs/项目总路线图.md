## 4. 工具执行稳定性

### 4.1 D-1：Windows `.cmd/.bat` 路由

**状态：DONE（`f6393a2`）**。PATH/PATHEXT 解析、无扩展名影子文件续查、仅批处理走 `cmd /c` 已落地；真实 `npx` 已跑通。

**问题**：`shell_exec` 只识别硬编码 cmd 内建命令；`npx`、`pnpm`、`yarn` 等 `.cmd/.bat` 直接 spawn 会 ENOENT。

**修复原则**：

- 可执行解析必须基于 PATH + PATHEXT，不得继续堆命令名单。

- 管道/重定向继续拒绝。

**问题**：PowerShell cmdlet 直接 spawn 失败时，只返回 `spawn-failed`，没有可操作指引。

**修复原则**：

- Windows ENOENT 时返回 hint，提示 PowerShell cmdlet 应写成 `powershell -Command ...`。

## 4A. 审批授权 v2（P0，v0.8 新增）

### 4A.1 核心拆分

| 轴 | 回答的问题 | 取值 |
|---|---|---|
| `policyMode` | Agent 可以访问多宽的执行范围 | `workspace / auto / full`（`ask` 兼容旧值） |
| `approvalClass` | 这类工具是否需要人工确认 | `none / mode / always / hard-deny` |
| `grant` | 用户批准后，放行到什么对象、多久 | `once / turn / session / project / global / temporary` |

**`full` 最终定义**：执行范围完全放开，安全阀仍然保留。它只影响 `mode` 类文件/命令工具，不允许绕过 `always`、`hard-deny`、未知来源、writable-root 缺失与敏感路径规则。

### 4A.2 工具分级

- `mode`：`file.*`、普通 `shell.exec`、`mcp.test`。
- `always`：`policy.set`、`workspace.set`、`memory.delete`、`memory.purge`、`memory.unarchive`、`chat-send`、`python.exec`、`mcp.call`、`mcp.save`、`mcp.remove`。
- `none`：其余现有只读/低风险工具；`memory.save` 本批保持现状，不静默重分级。
- `hard-deny`：磁盘格式化、关机/重启、盘根递归删除、敏感凭据路径、未知工具/来源等动态规则。

### 4A.3 授权时间

- `once`：单次调用。
- `session`：`sessionId/botId + workspaceHash + toolId + actionClass + canonicalTarget`；会话结束、Bot 断开、工作区/策略变化、用户撤销、进程重启即失效，不以 10 分钟 TTL 为主。
- `project`：只能由用户在设置页显式创建、预览、撤销，不能由审批弹窗创建。
- `temporary`：仅高危精确目标的 10 分钟临时放行，必须有倒计时与撤销入口。
- `always` 工具不得发放普通 `session/project` grant；`hard-deny` 永远优先。
- `internal-bot` 的 `chat-insert/chat-send` 预授权必须标源，不能冒充用户授权。

### 4A.4 执行顺序

`工具登记/来源 → hard-deny → workspace/resource deny → deny 规则 → always 新鲜确认 → mode 有效 grant → policyMode → fail-closed`。

完整任务卡见 `docs/交接班/交接班_20261026.md` §18.5 + §19（§3-§8 保留为设计依据）。

**核心结论：两者都是「等错了信号」与「页面主线程争用」，不是「算得慢」。**

- **C1-F1**：`web-engine.ts:232-312` 的完成判定是 `lastText !== baselineText` 且连续 2 次稳定，但**基线在 `send()` 之后才读**（`:253`）。短答在页面侧渲染收尾快，基线读到的已是最终答案 → 条件恒假、`stableHits=0`、无其它出口，只能耗满 `stepTimeoutMs=120s` → `requireTaskLoopReply` 判 timeout 抛错 → 500。时长对得上：128.8s ≈ 120s + 一次 chat-read 往返；208.1s = 第 1 轮带工具未判停 + 第 2 轮再吃满 120s。另一个洞：`readLastMessage()` 返回了 `count` 但**从未使用**，只剩文本比对 → 同文重复（答两次"好的"）也会被判没变化。

- **交叉结论**：F1 和 F2 共享同一分母——页面主线程在流式回答时不受宿主控制。修法都指向「用事件/消息身份当权威信号 + 预取挪到页面不忙时」，不是调大超时。

**修复排期**：属 Core，T-1（Tauri 多窗挂死）解决后优先。C1-F1 已有纯单测可钉死的复现思路（R1–R3），建议先补测试再改判定。

### 18.7 附件实验结果与定性（2026-11-02 完成）

报告：`docs/验收/20261102-附件通道可行性实验.md`（阶段 2 实测 12:58–13:26）。

| 轮次 | 条件 | 结果 |
|---|---|---|
| 探活 | 1 条 93 B 消息 | **200**、模型回「就绪」、11,876ms、无限流文案 |
| E2 对照 | 新会话、不传附件、发 256,036 B 纯文本 | **200**，模型有完整回答 |
| E1 实验 | 新会话、只传 456,775 B 附件 + 同一条 256 KB 文本 | **200**；`ref_file_ids` 长度 1（附件确实随消息送出） |
| E3 纯文本加码 | 262 KB → 524 KB → 1 MB → **2,097,152 B** | **全部 200**，耗时 1.6s→4.4s 单调上升 |
| E3 带附件加码 | 512 KB / 1 MB / 1.5 MB + 附件（约 2 MB 请求体） | **全部 200** |

**判定：卡面假设的「450KB 墙」在本轮未复现**（命中预设的「E2 接受 且 E1 接受」档）。**未混入限流因素**：9 次请求全 200、`realErrs` 全空、无任何「频繁/too long/rate limit/429」文案。

**结论：附件通道不立项。** 理由：附件通道确实存在且可用（`upload_file` 200 → `ref_file_ids` 进 body → 服务端接受），但它**并不比纯文本路径更强**——纯文本一路加到 2 MB 也没被拒，所以「附件能绕开大小墙」这个立项理由**没有被证明**。§18.6 的 E1/E2/E3 到此收口，不再追加轮次。

**必须同时记下的判别边界（不能过度解读）**：HTTP **200 只证明"请求被接受"，不等于"全文进了上下文"**。要判定超长 prompt 是否被服务端截断/摘要，还需一次「尾部唯一标记召回」测试（在超长文本末尾放随机串，问它原样引用）。本轮没做，因此**不宣称"对话长度无上限"**，只宣称"256KB–2MB 区间未被拒"。

**下一步的开放问题**：当初撞到的 450KB 限制到底是什么（限流冷却 / 特定内容 / 当时账号状态）——若要追查，先**复现原始失败**（同一账号状态、同样的连续发送节奏），再谈其他，不基于假设投入。

**注入瘦身继续做**：它省的是每轮固定开销（token 与体积），与本实验无关，不受本条结论影响。

### 19.2 三处调整（用户 2026-11-02 批准）

**① M3 升级：把「频率」列为一等指标。**
原 M3 只测终态分布 + 假成功计数。但 2026-11-02 已确认真正的硬约束是**频率墙**，所以 M3 必须同时产出：
- 每个任务（一次用户消息）的**请求数分布**（P50 / P90 / max，以及超过 10 次的任务占比）；
- 同一任务内**相邻请求间隔**（毫秒）；
- **重试占比**（retryable 重试 / 截断重发占该任务请求数的比例）。
缺这三项，M3 跑满 7 天也回答不了"为什么聊不下去"。

**② 新增 M1.5「注入体量与请求表面积」，排在 M3 之前。**
理由（外部实测，见 §19.4）：单次输入涨到 293k token 曾导致四个账号两天内被限；每轮重发全量历史会让模型看到「历史 + 又一份历史」→ **有效上下文对折**；只发增量可把 5 轮上传量压到五分之一。

**M1.5 三条判据（缺一不算完成）：**
1. **工具目录段实测字节（口径 B，body 里真实呈现）≤ 3,000 B**。当前 2,631 B 已达标，改前基线 12,568 B（压缩 79%）；口径 A（选择器口径 2,390 B）只作设计参考，不进验收。
2. **续跑轮的 head 不变**（稳定块/变化块拆分）。这是 chained 成立的前提——dsh 实测"改 head（协议指令 / 工具目录 / system）会让链断一次"，head 每轮都变则收益归零。
3. **工具名集合瘦身前后相等**（差集为空）。只压「完整参数块」，一个工具名都不能丢。

**M1.5 必须先出设计稿再改码**：它动的是续跑 prompt 的结构，是当前风险最高的一处改动。

> **2026-11-02 真机校正（Verify 14 轮实测 + PM 源码复核，覆盖上面两条判据的原始表述）**
>
