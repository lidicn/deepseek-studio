## 0. 评审结论

方向判断正确，落地层的契约描述不足。

最值得肯定的，是四个「不做」判断——不搬运 cuckoo-code（GPL）、不 fork Harness（复杂度超载）、不继续堆手写 DOM、不先做全功能多 Agent。前三项直接避开了历史审计中「复杂度过载」这条主线风险；「先建渲染层 + 宿主适配层 + 设计系统，再给 overlay 加 CSS」的排序也是对的。

但作为方向决策稿，它有一个结构性问题：它用自然语言描述架构，却试图裁决需要机器验证的契约。全文出现 6 次「token」，0 处给出 token 命名；定义了 7 种工具卡片、5 种运行状态，0 处给出常量；提出「统一 z-index token」，但没有 z-index 层级表。这恰好复刻了前几轮审计总结出的首要元模式——跨模块契约靠约定而非单一真相源。设计稿正是定义 single source of truth 的最佳位置，这一版却把它留空。

结论：可进入实现，但必须先补 P0-1～P0-4 四项，否则 P1 之后的所有排期都建立在未验证假设上。

## 1. 必须修的四项（P0）

### P0-1 渲染层选型缺「宿主约束」论证（文档级漏洞）

第 6 章按「独立应用」选栈（React 18 + Vite + Monaco + xterm + Shiki + KaTeX），但产品形态是注入到 deepseek.com 的第三方页面。至少四个约束在文中零提及：

| 约束 | 风险 | 必须先回答 |
|---|---|---|
| 包体积 | 上述栈 + React runtime 打包后是 MB 级，每次页面加载解析一次 | 注入包体积预算（建议 ≤300KB gzip 首屏，重型能力懒加载） |
| CSP | 宿主若禁用 unsafe-eval / blob: / inline style，Vite dev 与 CSS 注入直接失败 | 实测宿主 CSP，确认 adoptedStyleSheets 可用 |
| React 实例共存 | 若 deepseek.com 本身是 React，两套 React 共享 __REACT_DEVTOOLS_GLOBAL_HOOK__ 会互相覆盖 | 开页面查该全局对象 + DOM 是否有 data-reactroot |
| 全局污染 | React event 委托、__REACT_* 全局键、CSS 变量 | 明确「零全局写入」清单 |

这不是实现细节，而是选型前提。若宿主 CSP 不允许，整份 P1–P6 都要换方案。建议在第 6 章前加「6.0 宿主约束与实测结论」，把上表填成实测数据。

### P0-2 Focus 模式与「真正的 Shadow DOM」互相排斥（内部矛盾）

- 2.2 要求 Focus 模式提供「composer 上方的轻量动作条」，且「原生页面优先」。
- P1 要求「真正的 Shadow DOM 根容器」。

两者不能同时成立：动作条必须贴在宿主原生 composer 上方，而 Shadow DOM 内节点无法插入宿主 DOM 树的指定位置（slot 只能由宿主侧提供，这里没有）。实现者必然二选一：要么在宿主 DOM 里裸挂节点（样式泄漏，回到审计老路），要么把动作条飘成浮层（遮挡/错位，正是 2.1 说要避免的）。

需要显式定义第三条路径：

> Focus 层的「宿主内嵌件」（composer 动作条、工具临时卡片）通过 HostComposerAdapter.getMountPoint() 返回的宿主 DOM 锚点挂载，样式用 scoped class + 高 specificity 前缀（ds-studio-focus-*），不使用 shadow；Workbench 层（自持画布）才使用 Shadow DOM 根。两套边界各自有样式隔离规则。

建议补一张「三种挂载模式 × 隔离手段」表。

### P0-3 状态色与主按钮全部不达 WCAG AA（已实测）

按 WCAG 2.1 相对亮度公式逐对计算：

| 前景 / 背景 | 对比度 | 阈值 4.5 | 结论 |
|---|---|---|---|
| 主文字 #16181D / #FFFFFF | 17.76 | 通过 | 良好 |
| 次文字 #5B6170 / #FFFFFF | 6.20 | 通过 | 良好 |
| 弱文字 #8A8F9B / #FFFFFF | 3.24 | 不通过 | 标签、占位不达 AA |
| 弱文字 #8A8F9B / #F7F8FA | 3.05 | 不通过 | 同上，更差 |
| 主色按钮白字 / #4D6BFE | 4.33 | 不通过 | 最高频元素不达 AA |
| 警告 #B7791F / #FFFFFF | 3.64 | 不通过 | 状态文字不可读 |
| 错误 #D64545 / #FFFFFF | 4.38 | 不通过 | 差一点但不过 |
| 成功 #2E9E6B / #FFFFFF | 3.38 | 不通过 | 状态文字不可读 |

这不是配色偏好：5.1 把「可扫读」「可信」写成视觉关键词，1.3 又把「我是否允许」「它正在做什么」交给状态色承载信息。状态色对比度不足，等于把关键信息对色弱用户直接抹掉。

已验证替换值（同色相、可达标）：

| 角色 | 现值 | 建议值 | 新对比度 |
|---|---|---|---|
| 主色（按钮底/白字） | #4D6BFE 4.33 | #3B5BDB | 5.67 |
| 主色（更稳） | — | #2F4FD8 | 6.50 |
| 弱文字 | #8A8F9B 3.24 | #6B7280 | 4.83（白）/ 4.55（#F7F8FA） |
| 警告 | #B7791F 3.64 | #8A5A00 | 5.93 |
| 成功 | #2E9E6B 3.38 | #1F7A52 | 5.30 |
| 错误 | #D64545 4.38 | #C43A3A | 5.23 |

建议采用双 token 制而非直接改色：--color-primary（底色，保留 #4D6BFE 用于填充/描边/图表）+ --color-primary-text（文字/图标，#2F4FD8）；状态色同理拆 -fill / -text。既保住品牌色感，又能过 AA。

### P0-4 「跟随系统深浅色」在注入场景下是错误判断

5.6 写「建议跟随系统」。但 Studio 注入在宿主页面里：若宿主自己切了浅色主题而系统是深色，prefers-color-scheme 在 Shadow DOM 内仍返回 dark，于是出现宿主白底 + Studio 黑底的割裂。第 8 章已列出 HostThemeAdapter，5.6 的结论与它冲突。

正确原则：主题判定源优先级 = 宿主显式主题 > 系统偏好 > 默认浅色；HostThemeAdapter 监听宿主 html[data-theme] / class / 计算后 background-color 作为首选项，暴露 theme$ 单一流，所有面板只订阅它。

同时 5.2 只给了深色 #111318 一个值，深色前景/边框/主色全缺，需补全同结构两套表。

## 2. 分章意见

§0 架构判断：5 条现状问题里，第 1 条（手写 DOM 无统一状态）与第 2 条（样式全局 style）实质是同一件事。更重要的是漏掉了 UI 侧最致命的两条历史根因：pointer-events 白名单导致新组件整块不可点、EventBus 订阅零退订导致重建后幽灵响应。现状清单不完整，就无法推导对策。

§2.4 模式切换：缺三件事——①模式状态存在哪（内存/持久化/跨会话恢复）；②「出现工具调用 → Workbench」是强制切换，用户正在 Focus 看原生聊天时会被后台任务弹出画布，体验不可接受，建议改为「非侵入徽标提示 + 用户点击进入」；③缺少「模式当前值」的视觉锚点规格（切换控件形态、宽度、位置、当前态标识）。

§3 信息架构：结构清晰，左中右职责划分是全文最好的部分。但缺状态归属：Status Bar 的「运行状态/连接状态/token-cost」没定义唯一数据源。历史审计中「UI 说在跑、实际 AgentLoop 已停」的类问题，根因就是多面板各自推断状态。建议明确「全局 execution state machine 是唯一数据源，任何面板不得自算运行态」。

§4.1 组件分层：Host Adapters 只列 4 个，缺 HostLifecycleAdapter（挂载/卸载/dispose）与 HostCapabilityAdapter（能力探测 → 降级等级）。

§4.2 工具卡片：只列 7 类，而工具契约已到 28 键，必然有大量工具无对应卡片。必须定义「未注册工具的默认卡片」并把卡片注册表做成 open registry，禁止 switch 硬编码 7 分支（否则每新增工具就要改 UI，正是契约失同步的源头）。

§4.3 Plan/Approval：只说「显示什么」，没说「从哪来」。Plan 是模型输出的结构化 JSON，还是文本正则解析？若是后者，会重演 RAW_TOOL_TAG_RE 那类脆弱解析。请在此处锁定 Plan 的 schema 与校验失败降级路径。

§5.4 尺寸：右侧 320–420 + 左面板 260–280 + rail 56 + 中栏最小 400 = 1036px。1280 屏可容纳（含滚动条约 1053），但 1024 宽分屏直接溢出，全文没有响应式断点。建议补：≥1440 三栏全展开；1200–1440 右栏收窄至 320、左栏可折叠；<1200 右栏变抽屉 overlay、左栏折叠为 rail；<900 强制 Focus。另「内容宽度 760–860」与「中栏最小 400」术语冲突，前者应是 max-width。

§5.4 / P1 z-index：P1 提「统一 z-index token」，视觉系统却没有层级表。宿主页面通常有极高层级（999999 级对话框），硬编码会输。建议：运行时探测宿主最大 z-index 作基线 --ds-z-base，在其上分层 rail +10 / panel +20 / overlay +30 / dialog +40 / toast +50 / tooltip +60。

§7 cuckoo-code GPL-3.0：许可证风险识别到位。但「借鉴设计 token 原则（4px 滚动条、12px 圆角、14–16px 内边距）」若照抄具体数值组合，存在衍生作品争议。建议文末加来源追溯表（provenance）：逐项标注「参考来源 / 原创 / 改写」，MIT 项目保留声明，GPL 项目只记原则性思路不记具体值。

§10 路线：P0 说「修复或登记现有红灯测试」，方向对但与仓库现状脱节——已知 grant-store.get() 一行回归导致 2 个用例失败，P0 应点名这一条并给出验收门禁（vitest run 全绿才允许进入 P1），否则「登记」会变成永久豁免。

§11 验收：UI 验收 7 条 + 工程验收 6 条，全部是人工可判断项，没有一条可自动化。缺最关键的三条（见 §5）。

## 3. 与十轮审计的追溯矩阵（文档缺失，建议整节补入）

| 历史缺陷 | 本稿是否回应 | 落地缺口 |
|---|---|---|
| F4-H1 假 Shadow DOM（shadow: container） | 部分回应，P1 要求「真正的 Shadow DOM」 | 缺 attachShadow 模式、adoptedStyleSheets 用法、:host 上定义 token（:root 在 shadow 内无效）、宿主 CSS 变量穿透策略、验收断言方式 |
| F4-H2 pointer-events 白名单 | 完全未提 | 「按钮按不了」的复发点。仅去白名单不够——需反转默认值：容器 pointer-events:none，:host > * 默认 auto，新组件无需登记即可点 |
| F6-C1 监听器泄漏 | 未提 | React 不会自动退订自定义 EventBus。需「生命周期契约」章节：每个 adapter 实现幂等 dispose()，destroy() 统一收集 disposer |

| C4 断线不清 pending | 未提 | Status Bar 无 pending 计数契约，断线后 UI 仍在「运行中」 |
| C6 无页回退退化看门狗 | 未提 | 验收只说「降级不白屏」，无降级等级定义（L0/L1/L2） |

```ts

export const UI_MODE = { focus: 'focus', workbench: 'workbench' } as const;

export const toolCardRegistry: Record<string, ToolCardComponent> = { /* ... */ };

```

启动期断言：Object.keys(toolCardRegistry) 与 FallbackToolCard 合计必须能覆盖 tool-contract 全部键；缺失仅告警、不得抛错（防新工具导致 UI 崩溃）。

### 4.3 生命周期契约（补入 §4，回应 F6-C1）

```ts
export interface StudioDisposable { dispose(): void }

export interface HostAdapter extends StudioDisposable {
  readonly kind: 'layout' | 'composer' | 'theme' | 'navigation' | 'lifecycle';
  readonly degradeLevel: 0 | 1 | 2;   // 0=正常 1=降级可用 2=仅只读/隐藏
}

// 规则：
// 1) 任何 globalEvents.on / addEventListener / MutationObserver / ResizeObserver / RAF
//    必须返回 disposer 并被同一个 dispose() 收集；
// 2) installStudioUI().destroy() 必须幂等，且执行后 handler 数回到基线；
// 3) 禁止模块级副作用订阅（import 即订阅）。
```

对应测试（进 CI）：mount → destroy → mount 后 globalEvents.handlerCount() === baseline；连续 3 次重建不增长。

## 5. 可自动化的验收补充（追加到 §11 工程验收）

1. npx vitest run 全绿，无「已登记红灯」（P0 门禁）。
2. 任意新增组件默认可点击：断言根容器 pointer-events: none、直接子节点默认 auto，无需白名单登记。
3. destroy() 后订阅归零、DOM 清零、requestAnimationFrame 无残留。
4. Markdown 输入 img onerror、javascript: 链接均被拦截。
5. 注入包体积 gzip ≤ 300KB（首屏），重型依赖不在首屏 chunk。
6. 宿主主题切换后 100ms 内 Studio 主题跟随（订阅 theme$，不读 prefers-color-scheme）。
7. 视口 1024 / 1280 / 1440 三档下三栏不溢出、中间区域 ≥400px。

## 6. 方法论层面的三点反思

1. 「方向决策稿」最容易漏掉的不是方向，是可裁决性。本稿在「要不要自研、要不要 fork」上判断精准，但在「两套隔离边界如何共存」「状态色是否可读」这类可测量问题上留白。评审设计稿时固定三问：这条决策能否被一个测试或一次测量否决？不能否决的，就还是口号。

2. 历史缺陷必须进入设计稿的输入集，而不是留在审计报告里。十轮审计沉淀的根因（pointer-events 白名单、订阅零退订、契约无单一真相源）在本稿三项全缺席。设计稿不引用它们，等于让下一版实现再犯一次；而追溯矩阵成本极低，收益是「新设计天然带回归保护」。

3. 注入式 UI 的一切技术选型，第一约束是宿主，不是生态。React/Vite/Monaco 的成熟度论证再充分，也抵不过一次 CSP 实测。建议把「宿主约束实测」作为 P0 前置项，先出一页实测结论，再冻结技术选型。

## 8. 结论

| 维度 | 评价 |
|---|---|
| 产品定位与形态（§0–§2） | 优秀。两种模式切分解决了「遮挡原生页面」与「完整工作台」的根本冲突 |
| 信息架构（§3–§4） | 良好。三栏职责清晰；缺状态归属与契约常量 |
| 视觉系统（§5） | 有基础问题。全部状态色不达 AA；深色缺项；跟随系统判断错误 |
| 技术选型（§6） | 方向对，缺宿主约束论证（阻塞性） |
| 参考取舍（§7–§9） | 优秀。GPL 风险识别到位，分工借鉴思路清晰 |
| 迁移路线（§10） | 良好。缺与现状红灯测试的对接 |
| 验收标准（§11） | 不足。13 条全为人工项，零自动化 |

总体：这是一份「产品判断成熟、工程契约待补」的设计稿。它成功回答了「做什么形态」，但尚未回答「凭什么不会重犯历史错误」。补完 P0 四项后可直接进入 P1 实现。
