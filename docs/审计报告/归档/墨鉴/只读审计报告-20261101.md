## 二、缺陷详情

### BUG-01 🔴 重试策略与错误信封整体未接线（死代码）

**位置**：`src/shared/retry-policy.ts`（全文）、`src/shared/tool-error-envelope.ts`（全文）

**证据**：全仓 `src/**/*.ts` 正则检索，四个核心符号**仅出现在自身定义行**，无任何 import / 调用：

```
--- shouldRetry (1) ---
    shared/retry-policy.ts:33: export function shouldRetry(...)
--- nextDelay (1) ---
    shared/retry-policy.ts:25: export function nextDelay(...)
--- DEFAULT_RETRY_POLICY (1) ---
    shared/retry-policy.ts:16: export const DEFAULT_RETRY_POLICY: RetryPolicy = {
--- isRetryable (1) ---
    shared/tool-error-envelope.ts:61: export function isRetryable(...)
--- buildErrorEnvelope (1) ---
    shared/tool-error-envelope.ts:43: export function buildErrorEnvelope(
```

**影响**：
1. 设计稿 M5 第 7.2 节承诺的「可重试错误（网络抖动/临时锁）自动指数退避重试」**从未生效**。`io-error`、`limit-exceeded` 这类瞬时失败对模型直接暴露为最终失败。
2. 所有工具错误实际走的是 `tool-loop.ts` 里硬编码的 `buildErrorExtras({ code: 'call-error' | 'call-skip' })`，与 `ERROR_MAP` 的 7 个语义码（`not-found` / `outside-workspace` / `io-error` …）**完全脱节**。模型看到的错误码永远只有 `call-error` / `call-skip` 两种，无法区分「永久失败」和「可重试」。
3. `ERROR_MAP` 里那 7 条精心写的 `suggestion` 文案，用户一次也看不到。

**建议**：二选一——要么在 `tool-loop.ts` 的 execute 分支接入 `buildErrorEnvelope` + `shouldRetry`/`nextDelay` 重试环；要么删掉这两个文件，把 `buildErrorExtras` 里的 code 体系与 `ERROR_MAP` 合并，避免「有实现但没人用」的假安全感。

### BUG-02 🔴 输出上限按字符数而非字节数计算，实际可超限 3 倍

**位置**：`src/capabilities/shell.ts:100-105`

```ts
function appendCapped(existing: string, chunk: string, limit: number): AppendResult {
  if (existing.length >= limit) return { text: existing, keep: false };
  const remaining = limit - existing.length;          // ← 按 UTF-16 码元计
  const next = chunk.length <= remaining ? chunk : chunk.slice(0, remaining);
  return { text: existing + next, keep: chunk.length <= remaining };
}
```

对照常量：`DEFAULT_MAX_OUTPUT_BYTES = 64 * 1024`（第 21 行）—— 命名是 **BYTES**，实现是 **length（码元）**。

**影响**：
1. 中文/emoji 输出时，1 个 UTF-16 码元 = 2~3 字节（UTF-8）。上限 65536 字符的中文输出 ≈ **192 KB**，是标称 64 KB 的 3 倍。该值会经 `content: [{type:'text', text: stdout}]` 直塞进模型上下文，直接放大 token 消耗与上下文溢出风险。
2. `chunk.slice(0, remaining)` 可能切在代理对（surrogate pair）中间，产出孤立代理项，下游 `JSON.stringify` 或渲染时会出现 `` 乱码。
3. 变量名 `maxOutputBytes` 与实际语义不符，后续维护者极易误判。

**建议**：改用 `Buffer.byteLength` 累计字节数，截断时按码点（`Array.from`）而非码元切分；或明确把常量改名为 `MAX_OUTPUT_CHARS` 并接受字符语义。

### BUG-03 🟠 被信号杀死的进程可能被判为「成功」

**位置**：`src/capabilities/shell.ts:399`

```ts
const exitCode = code ?? (signal ? -1 : 0);
const isError = exitCode !== 0;
```

**问题**：Node 的 `close` 事件里，进程被信号终止时 `code === null` 且 `signal` 非空 → 走 `-1`，正确。但若**平台未上报 signal**（Windows 上 `child.kill()` / `taskkill` 后常见 `code === null && signal === null`），则 `exitCode = 0` → `isError = false` → **返回 `ok: true`，且 `error: undefined`**。

**影响**：崩溃（段错误、OOM killer、taskkill）的命令被当成执行成功，模型会基于空/半截 stdout 继续推理，产生静默错误结果。这类 bug 最难排查——日志显示成功。

**建议**：`code === null` 一律视为异常（`exitCode = -1`，`isError = true`，`error = 'killed-no-exit-code'`），不要用 `signal` 是否存在做兜底。

### BUG-04 🟠 超时兜底路径下子进程可能残留 + 状态字段不一致

**位置**：`src/capabilities/shell.ts:413-427`（timer）与 `325-342`（`finish` / `common`）

```ts
const timer = setTimeout(() => {
  timedOut = true;
  killTree();                       // 失败时仅 console 级别兜底，无重试
  fallback = setTimeout(() => {
    finish({ ... data: { ...common(), exitCode: null, timedOut: true, timeoutMs } ... });
  }, TIMEOUT_GRACE_MS);
}, timeoutMs);
```

**问题**：
1. `killTree()` 内部 `spawn('taskkill', ...)` 若因权限/路径问题失败，只挂了 `killer.on('error')` 回落 `child.kill()`；**若 `child.kill()` 也抛错则被 `catch {}` 静默吞掉**（第 362-366 行）。此后兜底 timer 触发 `finish()`，Promise 已 resolve，但**子进程树仍在运行**，成为孤儿进程持续占用 CPU/句柄。
2. 兜底 `finish` 里 `data: { ...common(), exitCode: null }` —— `common()` 展开在前，`exitCode: null` 覆盖在后，看似正确；但 `details` 字段里是 `Date.now() - startedAt` **重新计算**，与 `common().durationMs` 可能差出 1500ms 以上，同一条结果里两个耗时字段不一致。
3. `finish()` 里 `clearTimeout(timer)` —— `timer` 是 `const` 声明于第 413 行，但 `finish` 定义于第 325 行。JS 的 TDZ 使得**若 `finish` 在 `timer` 初始化前被调用**（如 `child.on('error')` 极早触发），会抛 `ReferenceError: Cannot access 'timer' before initialization`。`spawn` 失败时 `error` 事件是异步的，实践中通常晚于同步代码，故实际触发概率低，但这是真实存在的时序脆弱点。

**建议**：`finish` 内改用 `if (typeof timer !== 'undefined') clearTimeout(timer)` 或将 `timer` 声明提前到 `let` + 初始化为 `null`；`killTree` 失败时记录到结果的 `details.killFailed = true`，让上层可感知孤儿风险。

### BUG-05 🟡 异常路径不发 `after-call`

**位置**：`src/shared/tool-loop.ts:112-121`

```ts
const final = await hooks.runAfter(options.toolName, params, errorResult, callId);
await events.emitAsync('call-error', { ... });   // 只有 call-error
return final;                                     // 没有 emitAsync('after-call', ...)
```

**影响**：
- `harness-metrics.ts:108-113` 已分别监听 `after-call`（success）与 `call-error`（failure），**统计口径未受影响**（已核实）。
- 但任何「以 `after-call` 作为一次调用终态」的订阅方（UI 卡片收尾、trace 落盘、耗时统计）会漏掉所有抛错调用，表现为「卡片一直 loading」或「trace 缺一条」。
- 与 BUG-01 叠加后影响放大：既然没有重试，抛错调用就是终态，却没有任何「终态统一事件」。

**建议**：抛错分支也 emit `after-call`（带 `isError: true`），或明确定义 `call-error` 为终态事件并在所有订阅方补齐。

### BUG-06 🟡 去重签名序列化碰撞

**位置**：`src/shared/tool-call-dedupe.ts:47-50`

```ts
function stableSerialize(value: unknown): string {
  if (value === null || typeof value !== 'object') {
    return JSON.stringify(value) ?? String(value);
  }
  ...
}
```

`JSON.stringify(NaN)` → `"null"`；`JSON.stringify(Infinity)` → `"null"`；`JSON.stringify(undefined)` → `undefined` → 回落 `"undefined"`。

故 `{a: NaN}`、`{a: Infinity}`、`{a: null}` 三者生成**同一签名**，`claimSignature` 会把后两次真实调用判为重复而静默丢弃。

**影响**：需模型在同一轮内针对同一工具输出 `NaN` 和 `null` 两种参数，实际概率极低；但一旦发生，表现为「工具调用无故消失」，且无任何日志。

**建议**：对非有限数显式编码（`"#NaN"` / `"#Infinity"` / `"#-Infinity"`），`undefined` 用 `"#undefined"`，与 `null` 区分。

## 六、第二轮补充：MCP 控制器（`src/host/mcp-controller.ts`，863 行）

### BUG-07 🔴 连接测试超时路径不杀子进程 → 孤儿进程泄漏

**位置**：`src/host/mcp-controller.ts:739-772`（`testStdioConnection`）

```ts
const initResult = await new Promise<any>((resolve, reject) => {
  const id = ++conn.requestId;
  conn.pendingRequests.set(id, { resolve, reject });
  proc.stdin?.write(...initialize...);
  setTimeout(() => reject(new Error('initialize timeout')), 5000);   // ← 第 748 行
});

if (!initResult.result) { proc.kill(); return { ok: false, ... }; }   // ← 只有这条分支 kill

const toolsResult = await new Promise<any>((resolve, reject) => {
  ...
  setTimeout(() => reject(new Error('tools/list timeout')), 5000);   // ← 第 764 行
});

proc.kill();   // ← 第 767 行，只有成功路径走到这里
```

**问题**：`initialize` 或 `tools/list` 超时 → Promise `reject` → 异常冒到外层 `catch (e)`（第 770 行）→ 直接 `return { ok: false, error }`，**`proc` 从未被 kill**。

**影响**：每次「测试 MCP 服务器连接」失败（服务器启动慢、初始化卡住、tools/list 无响应），都会在宿主机上留下一个**永不退出的 MCP 子进程**。用户反复点「测试连接」= 线性累积孤儿进程，最终耗尽句柄/内存。这是本轮最严重的一处。

**建议**：把 `proc.kill()` 放进 `finally` 块，或在外层 `catch` 里补 kill；更稳妥用 `try { ... } finally { try { proc.kill(); } catch {} }`。

### BUG-08 🟠 连接测试的超时定时器从不清理

**位置**：同文件第 748、764 行

`setTimeout(() => reject(...), 5000)` 的返回值未被保存，成功路径 resolve 后也没有 `clearTimeout`。

**影响**：虽然 Promise 已 settled 后 `reject` 是 no-op（不会抛 unhandled rejection），但两个 timer 仍会存活满 5 秒并持有 `reject` 与闭包引用。连接测试频繁时是可测量的 timer 堆积。属资源卫生问题，不改变业务结果。

**建议**：`const t = setTimeout(...); promise.finally(() => clearTimeout(t))`。

### BUG-09 🟡 JSON-RPC `id: 0` 会被误判为无 id

**位置**：同文件第 724 行（`testStdioConnection` 的 stdout 解析）

```ts
if (msg.id && conn.pendingRequests.has(msg.id)) {
```

主连接路径（第 372 行）用的是正确写法 `if (msg.id != null)`，此处却用了 truthy 判断。JSON-RPC 2.0 允许 `id: 0`；当前 `conn.requestId` 从 1 起递增，故实际不会命中 0 —— **当前不触发，但两处写法不一致，属于埋雷**。一旦未来改成 0 起编号，响应会被静默丢弃、请求等到 5s 超时。

**建议**：统一为 `msg.id != null`。

### 本轮已核实「无缺陷」的点（供后续排除）

- **stdout 分帧**（第 362-383 行）：`buffer += chunk; split('\n'); buffer = lines.pop()` 是标准做法，正确处理了跨 chunk 半行；`JSON.parse` 包在 try/catch 内（第 370-381 行），非法行静默跳过，不会中断流。
- **统一清理 `cleanup`**（第 339-354 行）：`cleanedUp` 幂等标志 + reject 所有 pending + `removeAllListeners` + 从 `connections` 表删除，`error` 与 `exit` 两条腿都接了。质量较高。
- **EPIPE 兜底**（第 395 行）：`proc.stdin.on('error', () => {})` 已挂空处理，避免向死进程写入触发 unhandled error。
- **stdio 请求超时**（第 453-458 行）：30s timer 在响应到达（第 376 行）和写入抛错（第 464 行）两处都 `clearTimeout`，无泄漏。
