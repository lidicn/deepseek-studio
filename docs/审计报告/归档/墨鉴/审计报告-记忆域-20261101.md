## 二、重点问题详述

### BUG-017（P2，数据破坏）密钥损坏 → 历史快照永久失效 → 回滚误删行

**位置**：`src/host/audit-crypto.ts` `readOrCreateKey()`

```ts
if (fs.existsSync(keyPath)) {
  const hex = fs.readFileSync(keyPath, 'utf8').trim();
  if (/^[0-9a-f]{64}$/i.test(hex)) return Buffer.from(hex, 'hex');
  console.warn('[memory] audit key file malformed, regenerating:', keyPath);
}
const key = crypto.randomBytes(32);
fs.writeFileSync(keyPath, key.toString('hex'), { mode: 0o600 });   // ← 覆盖原文件
```

**问题链**（三步放大）：

1. 密钥文件只要出现任何非 64 位 hex 内容（磁盘半写、编辑器保存、同步冲突、误触），**直接生成新钥并覆盖**，旧钥不留备份。
2. 此后所有历史 `enc1:` 密文都解不开，`open()` catch 后 `return null`（只 warn）。
3. `audit.ts rollback()` 拿到 `entry.before === null` 后走：
   ```ts
   if (entry.before) { ctx.writeSnapshotRow(entry.before); }
   else if (entry.memoryId) { ctx.deleteMemoryRow(entry.memoryId); }   // ← 删行
   ```
   → **本该“恢复”的操作变成“删除”**，且返回 `{ ok: true }`。

**影响**：用户点一次回滚，记忆被静默删掉，且没有任何错误提示。这是记忆域唯一能造成**不可逆数据丢失**的路径。

**修法方向**
- 密钥损坏时**不覆盖**：改为 `keyPath + '.bak'` 轮换，或直接 `throw` / 置 `available=false` 并**拒绝写入**（现在 `available=false` 只降级明文，反而把明文写进 db）。
- `open()` 解密失败应返回**哨兵值**（如 `Symbol('undecryptable')`）而不是 `null`，让 `rollback` 能区分「原本就没有 before」与「有但解不开」，后者必须 `{ ok:false, error:'snapshot undecryptable' }`，**绝不能走删行分支**。
- `rollback` 增加前置断言：`entry.op !== 'save-new' && entry.before === null` 时拒绝执行。

### BUG-018（P2）回滚窗口被硬编码 10 万条截断

**位置**：`src/host/memory/audit.ts` `rollback()`

```ts
const all = await listLog(ctx, { limit: 100000 });
const entry = all.find((e) => e.id === logId);
if (!entry) return { ok: false, error: 'log entry not found' };
```

- 日志超 10 万条后，早期条目 `find` 不到，返回的 `log entry not found` 与「条目真的不存在」**无法区分**。
- 每次都把 10 万条全量取出并对每条做 AES-256-GCM 解密，只为找 1 条 —— O(N) 解密，UI 上表现为回滚按钮卡死。
- `listLog` 本身有 `memoryId` 参数可用，但 `rollback` 是按 `logId`（自增主键）找，绕不过全表。

**修法方向**：`listLog` 增加 `byId` 精确查询（`SELECT * FROM memory_log WHERE id = ?`），`rollback` 改用它；`limit` 只留给列表展示。

### BUG-012 / BUG-013（P2）写入与删除都缺事务

`storage.ts save()` 的 SQL 分支顺序：

```
INSERT/UPDATE memories  →  recordLog()  →  syncFts()  →  applyEviction()
```

- `recordLog` 内部自带 try/catch 只 warn → 主记录已落库、审计缺失，且**没有任何补偿**。
- `applyEviction` 逐行 try/catch，部分失败只 push warning → 出现「主记录在、容量已超 MAX_MEMORIES」的持续超限态，下次写入继续淘汰，雪球。
- `remove()` 先 `DELETE FROM memories` 再 `recordLog('purge', before)` —— 审计写失败则 before 快照永久丢失，`rollback` 无法恢复该行。注释里已写明「必须取整行」，但**取到了也保不住**。

**修法方向**：`ctx.db.exec('BEGIN IMMEDIATE')` 包住「主表 + FTS + 审计」三步，`applyEviction` 移出事务（它是软归档、可重试）；或至少把 `recordLog` 失败升级为 `partial:true` 之外的显式告警字段，让上层能感知审计缺口。

### BUG-011（P2）FTS 命中即短路，且丢失排序

**位置**：`memory/retrieval.ts` `search()`

```ts
if (rows.length === 0) { /* LIKE 兜底 */ }   // ← 只要 FTS 有 1 条命中就不兜底
```

- 查询「AI 助手」：token `AI`(2 字符) 在 trigram 下失配，`助手` 命中；只要 `助手` 有结果，就**不再走 LIKE**，纯靠 `AI` 匹配的记录被漏召回。
- FTS 分支用 `ORDER BY bm25(...)`，LIKE 分支用 `ORDER BY pinned DESC, updated_at DESC` —— **两条分支排序语义不同**，同一查询命中不同分支时结果顺序会跳变；且 FTS 分支不经过 `sortRows`，`pinned` / `user 优先` 策略失效。

**修法方向**：FTS 与 LIKE 结果做并集去重（或 FTS 结果不足 `limit` 时补 LIKE）；两条分支统一过 `sortRows`。

### BUG-014（P3）循环依赖

`memory/storage.ts` → `import { mergeUpdateGovernance } from '../memory-store'`；`memory-store.ts` → `import * as storage from './memory/storage'`。

目前可跑，纯粹因为 `mergeUpdateGovernance` 是**函数声明**（有提升），且门面在模块求值时不立即调用。一旦有人把它改成 `const fn = () => {}` 或挪进 class，立刻 `ReferenceError: Cannot access before initialization`。

**修法方向**：把 `mergeUpdateGovernance` 下沉到 `memory/core.ts`（它本来就是个纯函数，`core.ts` 里 `sameStringArray` 等同级纯函数已经在）。

### BUG-015（P3）每次写入全表扫

```ts
export function prepareEviction(ctx, deltaValid) {
  if (deltaValid === 0) return { ok: true, evict: [] };
  const valid = ctx.validRows();          // SELECT * FROM memories 全表
  const projected = valid.length + deltaValid;
  ...
  pickEviction(valid, need)               // 再全量排序
}
```

`validRows()` = `allRows()` + 全量 `rowToMemory()` 对象构造（含 3 次 JSON.parse）。每次 `save()` 都跑一遍。MAX=500 时是常数成本，但这是**唯一随记忆量线性劣化的写路径**。

**修法方向**：改用 `SELECT COUNT(*) FROM memories WHERE invalid_at IS NULL AND pinned = 0` 做预算判断；仅在确实超限时才取候选行。

---

### BUG-016（P3）淘汰排序依赖墙钟

`pickEviction` 用 `a.updatedAt - b.updatedAt` 排「最旧」。系统时钟回拨（NTP 校正、休眠唤醒、双系统切换）会让新写入的行带更小时间戳 → 被优先淘汰。与 `shared/studio-execution.ts` 的 BUG-003 同源。

**修法方向**：加单调递增序号列（`seq INTEGER`，写入时取 `max(seq)+1`），排序用 seq 而非时间戳；时间戳仅作展示。

---

### BUG-019 / BUG-020（P3）候选池

- **019**：`promoteCandidate` = `save()` → `deleteCandidateRow()` → `recordLog('candidate-promote', ...)`。前两步任一成功、第三步失败，状态就不一致；`deleteCandidateRow` 失败时记忆已建但候选仍在 → **再次提升会创建重复记忆**（`save` 是同名更新所以幂等，但 `recordLog` 会重复留痕）。
- **020**：`memory_candidates` 表没有任何容量上限（`MAX_MEMORIES` 只管 `memories`）。候选只增不减（`addCandidate` 无去重、无淘汰），长期运行无界膨胀，`listCandidates` 全表返回无分页。

## 三、本轮排除的疑点（已核实不是 bug）

1. **FTS JOIN 写法**：`JOIN memories_fts f ON f.rowid = m.rowid WHERE memories_fts MATCH ?` —— 用 SQLite + trigram 实测**合法且能命中**；把 MATCH 换成别名 `f MATCH` 才报 `no such column: f`。当前写法正确。
2. `likePattern` 转义 `\ % _` + `ESCAPE '\'`，实测正确。
3. `toFtsQuery` 去 token 内双引号 → 防 FTS5 语法注入有效（只是查询词会变形，见观察项）。
4. `contentHash` / `dedupeHash` 压缩空白 + trim，SHA-1 仅作指纹。
5. `sameStringArray` 长度 + 排序后逐项比，顺序无关语义正确。
6. `mergeUpdateGovernance` 用 `??` 实现「未传保留、显式传值（含 false/[]）覆盖」，SQL 与 fallback 共用同一函数，无分叉 —— 设计良好。
7. `syncFts` / `applyEviction` 附属失败只收集 warning、不阻断主保存，均有独立 try/catch —— 降级策略明确（问题在缺事务，不在降级本身）。
8. `remove()` 用 `SELECT *, rowid AS rid` 取整行做 before 快照 —— 注释即修复记录，正确。
9. `deleteMemoryRow` 先删 FTS 再删主表，顺序正确。
10. `candidates.insertCandidateRow` / `deleteCandidateRow` 的 fallback 分支用 `findIndex` + 不可变替换，正确。
11. `forgetAudit` 只处理 db 分支是对的 —— fallback 分支的清理由 `storage.remove()` 内部 map 完成。

## 四、观察项（不计入 bug）

1. `toFtsQuery` 对 token 内双引号是**删除**而非转义 —— 不注入，但 `he"llo` 实际按 `hello` 搜。
2. `search()` 用 `[...q].length >= 3` 判 FTS，口径是整串长度而非每 token —— 多短词查询白跑一次 FTS。
3. `applyEviction` 只软归档主表，不动 FTS 行 —— 正确（查询侧有 `invalid_at IS NULL`），但 FTS 索引随归档行持续膨胀，长期无回收。
4. `recordLog` 把 `note` 也 seal 了，但 `forgetAudit` 写 `note='forgotten sha256:...'` 是明文 —— 不一致但无害（`open` 对非 enc1: 走 JSON.parse 失败兜底成字符串）。
5. `rejectCandidate` 把**候选 id** 写进 `memory_id` 列，与「记忆 id」语义混用；按 `memoryId` 过滤日志时会混出候选拒绝记录。
6. `audit-crypto` 密钥与 db 同目录、明文 hex，同机任意进程可读 —— 目标是「防 .db 文件泄露」，不是「防本机」，定位合理但需在文档写明。
7. `memory-store.ts` 门面导出面「9 值 + 8 类型」刻意收窄，分域 helper 用 export 但不进门面 —— 边界清晰。
8. `storage.ts` 内部保留 `this` 时代的 4 空格缩进残留（`export function save` 内层多缩进 4 格），纯风格。
9. `MAX_MEMORIES` 限制行数不限制单条 content 长度，超大 content 会直接进 db 与 FTS。
