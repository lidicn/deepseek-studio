# 墨鉴 · 审计补充报告：MCP 控制器

- 对象：`src/host/mcp-controller.ts`（863 行 / 33.5KB）

- 范围：stdio / HTTP 双传输、子进程生命周期、配置热重载、工具调用、连接测试

## BUG-016【P1】`initializeConnection` 失败后 stdio 子进程泄漏

位置：`src/host/mcp-controller.ts:397-398` + `275-295`

```ts
// connectStdio 尾部
this.connections.set(serverId, conn);
await this.initializeConnection(conn);   // ← 这里抛错则 proc 无人回收
return conn;
```

```ts
// connect() 的 catch
try {
  return this.connectStdio(serverId, config);
} catch (e) {
  console.error(...);
  this.connections.delete(serverId);   // ← 只删 Map，没有 proc.kill()
  return null;
}
```

**现象**：`initializeConnection` 内部依次 `await initialize` → `sendNotification` → `await tools/list`，任一步抛错（服务器 hang 到 30s 超时、server 返回 error、stdio 写失败），异常冒泡到 `connect()` 的 catch。catch 只做了 `connections.delete(serverId)`，**从未调用 `proc.kill()`**。

**为什么 `cleanup` 兜不住**：`cleanup` 只挂在 `proc.on('error')` 和 `proc.on('exit')` 上。服务器 hang 住时进程不退出、也不报 error，两个事件都不触发，cleanup 永远不跑。

**后果**：每失败一次就留下一个存活的 MCP 子进程。用户反复点「测试连接」/反复刷新工具列表，会积累 N 个 node/python 子进程，直到宿主重启才释放。Windows 上表现为 taskmgr 里多个孤儿 node.exe。

**修法方向**：
- `connectStdio` 里把 `await this.initializeConnection(conn)` 包进 try/catch，catch 中 `cleanup('init failed', e)` 后再 rethrow；
- 或在 `connect()` 的 catch 里补 `this.disconnectServer(serverId)`（它已经会 `proc.kill()` + reject pending），一行搞定。

## BUG-017【P2】`connect` 重入：未初始化连接被覆盖，旧子进程泄漏

位置：`src/host/mcp-controller.ts:275-295`

```ts
const existing = this.connections.get(serverId);
if (existing && existing.initialized) return existing;   // ← 只看 initialized
// ...
return this.connectStdio(serverId, config);              // ← 无条件再 spawn 一个
```

**现象**：`existing` 存在但 `initialized === false` 时（初始化的 30s 窗口内，或 `getAllTools` 的 10s race 超时后初始化仍在进行），代码会继续走到 `connectStdio`，`spawn` 出**第二个**子进程，然后 `this.connections.set(serverId, conn)` 直接把旧 conn 覆盖掉。旧 conn 的 `process` 没有任何人 kill。

**触发路径**（很常见）：
1. 用户打开工具列表 → `getAllTools` → `connect()` 开始 spawn + initialize；
2. 服务器启动慢，10s 后 `Promise.race` 超时返回 null，UI 显示「连接超时」；
3. 用户再点一次刷新 → 10s 内 connect 内部的 initialize 还没结束（30s 定时器）→ `existing.initialized === false` → 再 spawn 一个。

**后果**：子进程数量随刷新次数线性增长；旧的 `pendingRequests` 里的 30s 定时器也还在（虽然最终会自然超时 reject，但期间占内存）。

**修法方向**：
- `connect` 里对 `existing && !existing.initialized` 的 conn 先 `this.disconnectServer(serverId)` 再重新连；
- 或者用 `inflight: Map<string, Promise<conn>>` 合并并发 connect，避免同一 serverId 重复 spawn。

## BUG-018【P2】HTTP SSE 路径不检查 `parsed.error`，错误被当作成功结果返回

位置：`src/host/mcp-controller.ts:488-507`

```ts
if (contentType.includes('text/event-stream')) {
  const text = await res.text();
  for (const line of text.split('\n')) {
    if (line.startsWith('data:')) {
      const data = line.slice(5).trim();
      if (data) {
        try {
          const parsed = JSON.parse(data);
          if (parsed.id != null) return parsed.result ?? parsed;   // ← 漏了 error 检查
        } catch { /* ignore */ }
      }
    }
  }
  throw new Error('No JSON-RPC response in SSE stream');
}
// 非 SSE 路径（正确）
const data = await res.json() as { result?: unknown; error?: { message?: string } };
if (data.error) throw new Error(data.error.message ?? 'MCP error');   // ← 这里有
return data.result ?? data;
```

**现象**：SSE 响应里如果 JSON-RPC 报文是 `{jsonrpc, id:1, error:{code:-32601, message:'Method not found'}}`，`parsed.result` 为 `undefined` → 走 `?? parsed` → **把整个含 error 的对象当成功结果返回**。对比同一函数下半段的非 SSE 路径，那里有显式的 `if (data.error) throw`。

**后果**：`callTool` 收到这个「成功结果」后，`result.content` 为空 → `text = ''` → 返回 `{ ok: true, data: '' }`。上层（AI 模型）看到 `ok: true` 以为工具执行成功，实际什么都没执行。**静默失败**，比直接报错更难排查。

**影响面**：只影响 `transport: 'sse'` 或 `transport: 'http'` 且服务端返回 `text/event-stream` 的场景。Autoforge / TVPilot 等基于 SSE 的 MCP 服务器都会命中。

**修法方向**：SSE 分支里补一条
```ts
if (parsed.error) throw new Error(parsed.error.message ?? 'MCP error');
if (parsed.id != null) return parsed.result ?? parsed;
```

## BUG-019【P2】`saveServer` 读-改-写无锁，并发保存会丢失更新

位置：`src/host/mcp-controller.ts:818-851`

```ts
saveServer(serverId, config) {
  let file = { servers: {} };
  try { file = JSON.parse(fs.readFileSync(configPath,'utf8')); } catch {}   // 读
  file.servers[serverId] = config;                                          // 改
  fs.writeFileSync(configPath, JSON.stringify(file, null, 2), 'utf8');      // 写
  this.servers = file.servers;   // ← 用磁盘结果整体替换内存
}
```

**现象**：整个 read-modify-write 是同步的，但 `saveServer` 是同步函数、调用方若在 `await` 之间交错（例如设置面板同时保存两台服务器），后写者会用**自己读到的那份旧快照**覆盖前者的新增。此外 `this.servers = file.servers` 是**整体替换**内存 Map，会抹掉 `refreshConfigIfChanged` 期间可能已加载的更细粒度状态。

**后果**：并发保存 MCP 配置时，先保存的那台服务器会凭空消失。用户感知为「配好了但刷新就没了」。

**触发场景**：设置面板「添加服务器」按钮被连点两次、或自动配对流程与手动添加同时进行。概率不高但用户侧不可恢复（需要重新配）。

**修法方向**：
- `saveServer` 只更新 `file.servers[serverId]` 一个键，不动其余；当前实现其实已经做到了（`file.servers[serverId] = config`），问题在于「读」和「写」之间如果有另一次完整 save，前一次的写入被后一次的 `fs.writeFileSync` 覆盖。
- 真正要做的：写文件前重新读一次、合并、写，或者改用 `writeFileSync` 的临时文件 + rename 原子替换，并对 `saveServer` 串行化（一个简单的 Promise 队列即可）。

## 已核实无问题（不再重复投入）

| 检查点 | 结论 |
|---|---|
| stdio 的 `cleanup` 统一收敛 | ✅ `error` 和 `exit` 两条腿都走 cleanup，`cleanedUp` 标志防重入，`pendingRequests` 全部 reject，`connections.delete` 到位 |
| `proc.stdin?.on('error')` EPIPE 兜底 | ✅ 空回调但已吞掉 unhandled error，pending 由 cleanup 统一 reject |
| env 白名单 | ✅ `ALLOWED_ENV_KEYS` 大小写归一 + `config.env` 显式覆盖，不漏宿主 token |
| Windows `.cmd/.bat` 的 shell 处理 | ✅ `isCmdBatch` 只对 cmd/bat 开 shell，其余命令直接 spawn，避免命令注入 |
| `sendRequest` 的超时与 `closed` 快检 | ✅ 30s 定时器 + `conn.closed \|\| !conn.process \|\| !conn.process.stdin` 快速失败，不会干等 |
| `sendHttpRequest` 的 30s `AbortSignal.timeout` | ✅ 正确 |
| `sendNotification` HTTP fire-and-forget | ✅ `.catch()` 兜底 + 10s 超时，不阻塞主流程 |
| `callTool` 的 image base64 上限 | ✅ 5MB 上限（`MAX_IMAGE_BASE64_LEN` 从原始 5MB 反推），超出转文本占位 |
| `callTool` 的 `inline_bytes` 处理 | ✅ 兼容 TVPilot 风格，同样 5MB 上限，`format` 映射 mime |
| `disconnectServer` | ✅ `proc.kill()` + pending 全 reject + `connections.delete`，HTTP 连接（process:null）也能正确 reject |
| `refreshConfigIfChanged` 容错 | ✅ 文件删除 → 按空配置；解析失败 → 保留旧配置与旧连接（只更新 mtime 防刷屏） |
| `testConnection` 的 spawn error 监听 | ✅ 有 error 监听，不会 uncaughtException 杀宿主 |
| `testHttpConnection` | ✅ 三步（initialize / initialized / tools/list）齐全，超时 15s |
| `parseMcpServers` 兼容历史平铺式 | ✅ 先认 `.servers`，否则把顶层键当服务器，向后兼容 |
| `getMcpController` 单例 | ✅ 懒加载 + 全局缓存 |

**仅记录不列缺陷**：
- `testConnection` 里的 `setTimeout(reject, 5000)` 未清理定时器 → resolve 后定时器仍会跑 5s 才触发，但 `proc.kill()` 在 return 前执行，进程已死，影响可忽略。
- `getAllTools` 的 `Promise.race` 里的 10s `setTimeout` 无法清理 → race 结束后空转 10s 才释放，开销可忽略。
- `callTool` 只取 `result.content` 中第一个 `type === 'text'` 的项，多 text 会被丢弃 → 设计取舍，不改。
- `sendRequest` 超时后不 kill 进程 → 上层有重试，且服务器可能在超时后正常返回（只是慢），保留进程有复用价值；由 BUG-016 的初始化失败路径兜底。
