## 零、为什么先啃这个文件

前四轮（R1–R3 + R4 前置）已确认 15.7% 覆盖率，而 `inject/` 是 395.1 KB / 41 文件、零覆盖的最大一块。其中 `main-world-interceptor.ts` 单文件 152.5 KB，是**唯一同时接触模型流、工具调用解析、续跑调度、UI 收尾的层**。用户主诉的「对话断流」「工具卡住」「服务器暂时不可用」三类症状，机制上最可能长在这里。

本轮读法：先取模块级状态与定时器全景，再沿 `autoContinueWithPow` 主线逐段读，最后核 `stop()` 收尾。

## 一、High

### R4-H1｜`loopDepth` 在续跑入口被递增两次，工具轮次预算被砍半

位置：`main-world-interceptor.ts:2355-2359`

```
2355  // 重试不应消耗 loopDepth：它是「工具续跑」的步数预算，
2356  // 一次 429 就吃掉一步会让真正的工具轮次被提前耗尽。
2357  if (!continuationRetryPending && !isProtocolRepair) loopDepth += 1;
2358  continuationRetryPending = false;
2359  if (!resendVerbatim && !isProtocolRepair) loopDepth += 1;
```

四次场景推演：

| 场景 | continuationRetryPending | resendVerbatim | isProtocolRepair | 2357 | 2359 | 实际 | 应为 |
|---|---|---|---|---|---|---|---|
| 正常工具续跑 | false | false | false | +1 | +1 | **+2** | +1 |
| 429/5xx 重试 | true | false | false | 0 | +1 | **+1** | 0 |
| 首轮原样重发 | true | true | false | 0 | 0 | 0 | 0 |
| 协议修复 | false | false | true | 0 | 0 | 0 | 0 |

根因是 **2358 的 `continuationRetryPending = false` 插在两次判断中间**：2357 读到的是「本次是不是重试」，2358 立刻把标志清掉，于是 2359 无法再知道同一件事，只能退化成「不是重发就加一」。

后果两条，都与用户主诉直接对应：

1. **正常续跑每轮吃 2 步**。`MAX_LOOP` 的实际可用轮次约为名义值的一半。表现是「工具链跑到一半突然停了，日志说 reached MAX_LOOP」——用户感知为对话断流。
2. **2356 的注释承诺没有兑现**。注释明写「一次 429 就吃掉一步会让真正的工具轮次被提前耗尽」，但 429 重试路径（continuationRetryPending=true, resendVerbatim=false）仍走了 2359，照样 +1。修复意图存在，实现被 2358 破坏。

修法：把 2358 移到两次判断之后，或合并成一次判断：

```ts
const isRetryEntry = continuationRetryPending || isProtocolRepair || resendVerbatim;
if (!isRetryEntry) loopDepth += 1;
continuationRetryPending = false;
```

### R4-H2｜`stop()` 不清续跑定时器，卸载后仍会发出幽灵请求

位置：`main-world-interceptor.ts:2805-2831`

`stop()` 当前清理了 6 项：`stopFetch`、`stopXhr`、`hydrateTimer`、`codeObserver`、`stopSkillsPrewarm`、`skillsRefreshSender`。

**唯独漏了 `autoContinueTimer`**（1811 声明，2127 / 2146 / 2541 / 2553 / 2606 五处置位）。

后果链：

1. 用户在退避窗口内（`errorBackoffMs` 起始 2s，逐次翻倍）禁用扩展或页面卸载 → `stop()` 执行 → hook 已恢复。
2. 已排队的定时器在 1s/2s/4s 后照常触发 `void autoContinueWithPow()`。
3. `autoContinueWithPow` 里 2350 的守卫读 `loopState.abortedByUser` —— 但该标志只在用户点停止按钮时置位，`stop()` **不置位**，守卫放行。
4. 于是 `xhr.send(bodyStr)` 用**已被恢复成原始原型**的 send 发出真实请求。

这次请求不经过任何拦截器处理，宿主侧收不到、UI 不更新、`collectedExecutions` 不记录。用户看到的是「扩展已经关了，但网络面板里还有一条发给 DeepSeek 的 completion 请求」。

更值得注意的是 `stop()` 里其他 6 项都有 `try/catch` 包裹（典型的「宁可静默也不抛」），说明作者对卸载期的健壮性是有意识的——这个遗漏更像是没列全，而不是有意为之。

修法：`stop()` 内补 `if (autoContinueTimer) { clearTimeout(autoContinueTimer); autoContinueTimer = null; }`，并置 `loopState.abortedByUser = true`（复用 2350 已有的守卫，避免在五处定时器回调里各加一次检查）。

### R4-H3｜`continuationRetryPending` 仍是模块级单例，QD-R7 的并发修复没覆盖到它

位置：`main-world-interceptor.ts:479`（声明）、`2341`（守卫）、`2358/2540/2552`（写）

文件里 526-537 行有一段很长的注释，标题是「QD-R7-01（断流定案报告 F4）：完成哨兵必须归属到「某一条流」」。它承认：

> 这套架构里并发是常态——页面自己的 completion、Studio 的首轮重发、上一轮没跑完的流、页面 auto_resume 可以同时存在。

并据此把 `streamSawDone` 改成了按 `activeStreamId` 归属，把首轮重试预算改成了 `Map<turnId, FirstAttemptBudget>`（502 行）。

**但 `continuationRetryPending` 被跳过了**——它仍是 479 行的一个 `let` 布尔。

后果：并发两条轮次时，B 轮走到 2358 的 `continuationRetryPending = false`，会把 A 轮刚在 2540 置的 `true` 清掉。A 轮的定时器随后触发，2341 的守卫 `pending.length === 0 && !continuationRetryPending && !protocolRepairPending` 全部成立 → **直接 return，重试一次都发不出去**。

这与 QD-R4-01 注释里描述的原始 bug（474-475 行：「MAX_ERROR_RETRIES=3 的预算一次都花不出去，表现为『工具卡片转完，回复停了』且状态栏永停在『执行中…』」）是**同一个失效模式**，只是触发条件从「单轮 pending 已清空」变成了「并发轮次互相清标志」。

同样受影响的还有 `idleContinueCount`（587 行）、`errorRetryCount`（1823 行，闭包内，同实例内并发共享）。三者是同一族：**按轮次存在的状态被放在了按实例存在的作用域里**。

修法：把三者一并改成 `Map<turnId, ...>`，与 502 行的 `firstAttemptBudgets` 同一模式；或收进一个 `TurnState` 对象，按 `traceTurnId` 索引。

### R4-H4｜`trace` 记 `finished: true / completed`，但用户可能一个字都没看到

位置：`main-world-interceptor.ts:2631-2646`

```
2631  interceptorTrace.record({
2632    t: 'continuation.decision',
...
2637  interceptorTrace.record({ t: 'turn.end', turnId: traceTurnId, finished: true, stopReason: 'completed' });
2638  const cleanReply = stripRawToolTags(reply).trim();
2639  if (cleanReply) {
2640    try { chatUI?.finishAssistantMessage({ fallbackText: cleanReply, recordFinal: true }); } ...
2641    try { onAssistantReply?.(cleanReply, loopDepth); } ...
2642  } else if (reply) {
2643    d('auto-continue reply all-tool-text (stripped to empty), skipping push');
2644  }
```

`turn.end` 在 2637 无条件记为 `finished: true, stopReason: 'completed'`，然后 2638 才判断 `cleanReply` 是否为空。当 `reply` 全是被剥离的工具标签时（2642 分支），走的是「跳过推送」——**用户什么都没收到，但 trace 说这一轮圆满完成**。

这不是理论情况。`d()` 日志 2643 明确写了这个分支存在，而 C1-F5（73-76 行注释）记录的现场正是「模型吐了工具调用但没被执行」。两个条件叠加——工具调用没解析成功 + 正文全是工具标签——就会落进这个分支。

对本轮审计的直接影响：`__studioTraceReport()`（120-124 行）是团队唯一的断流取证入口。当用户报「回复没了」，取证报告会显示 `finished: true / completed`，**把排查方向引向「用户没看到」而不是「内容被丢弃」**。取证工具本身在误导取证。

修法：把 `turn.end` 的 record 移到 2638 之后，`cleanReply` 为空时记 `finished: false, stopReason: 'reply-stripped-empty'`。

## 二、Medium

### R4-M1｜`toolError` 语义在 trace 里也丢失
位置 2627-2630：`endScan.blocks > 0` 时只 `d()` 一行日志，没有 `interceptorTrace.record`。正文里残留未执行工具调用这件事，只在 diag 里留痕，不进 trace 快照。与 H4 同族（取证不完整）。

### R4-M2｜`scheduleFirstAttemptResend` 不检查 abort
位置 2140-2150：置 `autoContinueTimer` 前没有 `if (loopState.abortedByUser) return;`。用户在退避期点停止，1s 后仍会重发一次。2350 的守卫能拦住，但请求已经排上队，白白占一个 timer 槽。

### R4-M3｜`budget.sent` 的递增点在 hook 内，异常路径不计数
位置 1215 / 1495：`if (loopState?.inFirstAttemptResend) firstAttemptBudget(traceTurnId).sent += 1;` 在 XHR open/send 的 hook 里。若 `xhr.send` 同步抛异常（如同源策略、非法 URL），`sent` 不递增，而 2656 的 catch 会走 `finishStepFlow('auto-continue-failed')`。UI 最终显示「已自动重试 0 次仍失败」，与 2182 的模板拼出来是自相矛盾的句子。

### R4-M4｜`MAX_AUTO_CONTINUE` 的空转计数跨轮不重置
位置 587 声明、2290 只在**新用户消息**时清零。同一轮内多次「续跑但无工具」（2111 分支）会计入同一个 `idleContinueCount`，达到 3 次就 `stream-cut` 收尾。对「模型输出较长、中途断流两次」这种正常的长回答，3 次额度偏紧。

### R4-M5｜`firstAttemptBudgets` 的 32 轮截断不区分会话
位置 508-513：`while (size > 32) delete(keys().next().value)`。Map 迭代序是插入序，而 `traceTurnId` 是 `t${Date.now().toString(36)}`（1144），插入序≈时间序，所以 FIFO 基本正确。但 2296 在新用户消息时先 `delete(traceTurnId)` 再可能重新 set，会让该 turnId 排到队尾——影响可忽略，仅登记。

## 三、待验证（证据不足，不下结论）

### R4-V1｜`firstAttemptBudgets.delete(traceTurnId)` 的时序
2296 在 `onNewUserMessage` 回调里执行，而 `traceTurnId` 在 1144（`captureChatRequest`）赋值。两者谁先执行，取决于 `captureChatRequest` 内部调用 `onNewUserMessage` 的位置。若 `onNewUserMessage` 先于 1144 触发，2296 删的是**上一轮**的 budget，本轮 budget 漏删。需要读 1098-1160 的 `captureChatRequest` 全函数体才能定论。

### R4-V2｜续跑 XHR 用的是被 hook 的 send 还是原始 send
2653 `xhr.send(bodyStr)` 里的 `xhr` 若由 `new XMLHttpRequest()` 创建，其 `send` 是原型上的——即已被 `installXhrHooks` 改写过。这意味着**续跑请求自己也会被拦截一次**，可能触发重复的 `prepareOutgoingBody`。代码在 2399-2401 用 `pending.length = 0` 做了防御，但 `collectedExecutions` 不清，是否会在续跑 prompt 里出现重复的工具结果，需读 2420-2460 才能定论。

## 四、复核掉 3 条候选误报

1. **「`streamSawDone` 写入未检查 activeStreamId」** —— 1704 与 1725 两处写入都在 `isActiveStream(loopState, streamId) &&` 的短路保护下，不成立。
2. **「`toolCallDedupe.resetSignatures()` 会允许重复投递」** —— 1820 只在 `onStreamBegin` 重置 signature，`callId` 集合由 2292 的 `reset()` 独立管理，两层职责分离，设计正确。
3. **「`pending.length = 0` 会丢工具结果」** —— 2399-2401 的注释与 `collectedExecutions`（1817）的分工明确：pending 是本轮回填缓冲，collectedExecutions 跨轮累积。2401 清 pending 是有意的，不丢历史。

## 七、本轮对方法论的一个观察

H1 和 H3 有一个共同点：**代码里已经写下了正确的意图，但实现被后续一行破坏或绕过**。

- H1：2355-2356 的注释精确描述了「重试不吃 loopDepth」，2357 也确实按这个意图写了，但 2358 的清除插在中间，让 2359 无法复用同一判断。
- H3：526-537 的注释精确描述了「并发是常态、状态必须归属到流」，并按此改了 2 个状态，漏了第 3 个。

这类缺陷用「有没有注释解释设计」是查不出来的——注释是完整的。只有把同一函数体的**连续若干行**放在一起读，才能看出前后两行的语义不再衔接。这提示后续轮次：**读大文件时，注释密集区反而要加倍警惕**，因为注释会让人产生「这里想清楚了」的错觉。
