## 二、重点问题详述

### BUG-021 + BUG-022（P2）限流桶泄漏 + 限流键选错

```ts
function createRateLimiter(opts: RateLimitOptions = {}) {
  const buckets = new Map<string, { tokens: number; last: number }>();
  return {
    take(key: string) {
      const b = buckets.get(key) ?? { tokens: capacity, last: now };  // 新键即新建满额桶
      ...
      buckets.set(key, { tokens: tokens - 1, last: now });            // 永不移除
    },
  };
}
```

两处叠加放大：

1. **键选错**：调用方传的是请求头 Bearer 值原文。每次换一个 `Authorization: Bearer xxx` 就是一个全新满额桶 → 攻击者/误配置客户端可无限绕过限流。
2. **桶不回收**：Map 只 `set` 不 `delete`，无 TTL、无容量上限。桌面单机场景影响有限，但项目已支持 `agentLanAccess.lanEnabled` 局域网访问，此时这是**远程可驱动的无界内存增长**（OOM 风险）。

**修法方向**
- 键改为**鉴权后的身份**（`subject`）或 `sha256(token)`；鉴权失败的请求走独立 IP 桶或直接 401 且不计桶。
- 惰性回收：`take()` 内若 `buckets.size > 1024`，扫一遍删除 `now - last > 10min` 的桶；或直接用固定大小 LRU。
- 不把明文 token 常驻内存（哈希后存键）。

### BUG-023（P1）`/v1/tools/execute` 的 params 不做形状校验

```ts
if (typeof body.tool !== 'string' || body.tool.length === 0) { 400 }
if (body.botId !== undefined && typeof body.botId !== 'string') { 400 }
if (body.conversationId !== undefined && typeof body.conversationId !== 'string') { 400 }
const result = await options.toolExecutor(body.tool, body.params ?? {}, ctx);  // ← params 零校验
```

`body.params` 可以是 `string` / `number` / `array` / 任意标量。`?? {}` 只兜 `null`/`undefined`，`"abc"`、`123`、`[1,2]` 会**原样**进入 toolExecutor。同文件对 botId/conversationId 都做了严格 `typeof` 校验，**唯独最关键的工具入参没有** —— 属明显校验缺口，不是设计取舍。工具执行器内部若按对象解构取值，会拿到 undefined 或抛 TypeError（进而 500，掩盖真实错误）。

**修法方向**
```ts
if (body.params !== undefined &&
    (typeof body.params !== 'object' || body.params === null || Array.isArray(body.params))) {
  sendJson(400, { error: { code: 'bad_request', message: 'params must be an object' } });
  return;
}
```

### BUG-024（P2）`readBody` 超限/超时后不排空请求流

```ts
const timer = setTimeout(() => { if (settled) return; settled = true; reject(new Error('read body timeout')); }, 30_000);
req.on('data', (c) => {
  if (settled) return;
  size += c.length;
  if (size > MAX_BODY_BYTES) { settled = true; clearTimeout(timer); reject(new Error('request body too large')); return; }
  chunks.push(c);
});
```

`settled = true` 后 handler 立即 return，但 **socket 仍在接收数据**，Node 会持续触发 `data` 事件（只是被丢弃），直到客户端发完或对端关闭。后果：
- 超限：客户端可持续流式发送，本端一直读到 `end` 才释放，连接被白占；
- 超时：客户端「连上不发完」即可占住连接 30 秒，是标准慢速攻击面（本地服务风险低，但局域网模式下成立）。

**修法方向**：两个 reject 分支后加 `req.destroy()`（超时分支必须）；或在 reject 后 `req.resume()` 显式排空。

## 三、本轮确认**正确**的点（避免重复投入）

1. **鉴权 fail-closed**：所有 `/v1` 端点统一先 `auth.authenticate` 再分发；`/healthz`、`/agent*` 静态资源显式豁免且各有独立闸门（`/agent` 走 `decideAgentAccess` 配对码，非回环 fail-closed）。
2. **CORS fail-closed**：`applyCors` 只对 `isLocalOrigin` 写 `Allow-Origin`，非本地 origin 一个头都不写；PNA 预检白名单限死 `/studio`、`/agent-ws` 两路径并校验 origin。
3. **`/agent` 令牌注入**：`JSON.stringify(token)` 替换带引号字面量占位符，特殊字符安全，不产生非法 JS 字面量。
4. **`/v1/tools/audit` limit 钳制**：`Number.isFinite` + `Math.max(1, Math.min(500, floor))`，非有限数回落 50（仅空串语义偏差，见 BUG-025）。
5. **`readBody` 的 settled 双保险**：`data`/`end`/`error`/`timeout` 四路径均有 `if (settled) return`，不会重复 resolve/reject（问题只在缺 destroy）。
6. **`/v1/tools/execute` 的 tool 名、botId、conversationId 校验**：类型 + 空串都覆盖。
7. **`/v1/automation/tasks/*` 的 id 提取**：`slice(prefix.length)` 后交给 manager，空 id → `get('')` → 404，不会 500。
8. **并发拒绝计数**：`rejectedByConcurrency` 独立统计，`queued/depth/avgWaitMs` 恒 0 并在注释说明「超限即 429 不排队」，监控不会误读。
9. **`readBody` 编码安全**：先 `Buffer.concat` 再整体 `toString('utf-8')`，多字节字符跨 chunk 不会乱码（与 BUG-002 的截断问题不同，此处安全）。

## 四、观察项（不计入 bug）

1. `RECENT_LIMIT = 20` 用 `shift()` 淘汰；注释已写明「返回对象引用而非索引」以避免 shift 后索引错位 —— 正确处理。
2. 令牌桶 `need = (1 - tokens) / refillPerMinute` 单位分钟再乘 60_000 得毫秒，量纲正确；`Math.max(50, ...)` 避免忙等。
3. `isLocalOrigin` 中 `[::1]` 在 `URL.hostname` 里返回带方括号形式，集合两种都写了，覆盖到位。
4. `if (options.agentLanAccess)` 未配置时整段跳过 —— 当前 `/agent` 仅在有 agentPage 时可达且默认绑回环，风险受控；但若将来暴露到非回环而忘配，即为敞开。建议改显式 `if (!options.agentLanAccess) → 403`（fail-closed 更彻底）。
5. `/v1/agent/send` 的 `agentSender` 无超时包装 —— 长任务会一直挂住请求（并发上限 1 时后续请求全 429）。是否算缺陷取决于上层 sender 自带超时，本轮未深入。
