## 二、缺陷清单

### B-01【高危】审批白名单循环内提前 return，导致后续条目永不命中

- 文件：`src/host/consent-router.ts`
- 函数：`matchWhitelist`
- 现象：遍历 `entries` 时，一旦遇到同 `workspaceHash` + 同 `toolId` 但 `action` 不同的条目，直接 `return { hit: false, reason: 'action-mismatch' }`，**终止整个匹配过程**。
- 影响：用户同时授权过「读 A 目录」和「写 A 目录」后，若「读」条目先入表，则「写」操作每次都被判为 action-mismatch，白名单形同虚设，用户被反复弹窗要求授权。属于可稳定复现的功能缺陷，不是偶发。
- 修复：该分支应改为 `continue`，把 action 不匹配当作「本条不适用」而非「整体不适用」。同时 `whitelist-expired` 分支也有同样问题（过期条目应 `continue`，不该直接返回）。

### B-02【高危】硬拒绝地板的敏感路径规则对 `~/.ssh`、`~/.aws` 永不命中

- 文件：`src/host/consent-router.ts`
- 函数：`checkHardDeny`
- 现象：敏感路径用字面量 `~/.ssh/`、`~/.aws/` 做前缀匹配，但入参 `realPath` 是 `realpath()` 解析后的绝对路径。Windows 下实际值形如 `C:/Users/x/.ssh/config`，`POSIX` 下形如 `/home/x/.ssh/config`，两者都不以 `~` 开头，正则永不命中。
- 影响：硬拒绝地板明文承诺「任何档位都拦，用户同意也不能覆盖」，但私钥、云凭据目录实际处于**无地板保护**状态。任何写入类工具（file.write / file.edit / shell.exec）都可直达。
- 修复：改为对解析后路径做「路径段包含 `.ssh` 或 `.aws`」的判定，例如按分隔符切段后判断段名，而不是依赖 `~` 前缀字面量。
- 关联：`checkHardDeny` 中 `Remove-Item -Path C:/ -Recurse -Force` 这类带参数的形式不命中 `recursive-root-delete` 规则（该正则只匹配命令以盘符结尾），同样属地板缺口。

### B-03【中危】未知 policy 值走 fail-open，与全局 fail-closed 约定相反

- 文件：`src/host/consent-router.ts`
- 函数：`routeConsent`
- 现象：函数末尾第 5 步「非治理工具」直接 `return { verdict: 'safe', reason: 'not-governed' }`。当 `input.policy` 是 deny / allow / require-consent 之外的任意脏值（配置被手改、版本错配、上游字段名变更）时，会落到这一步，被当作 safe 放行。
- 影响：`tool-registry` 的 `approvalClassOf` 明确采用「非法值 fail-closed 到 always」的策略，此处却是 fail-open，两套治理语义互相矛盾。配置一旦脏化，审批闸门静默失效且无日志。
- 修复：在函数入口对 `policy` 做穷举校验，非法值返回 `deny`（reason 可用 `policy-deny` 或新增 `policy-invalid`）。

### B-04【中危】写操作 `memory.save` 被登记为只读且免审批

- 文件：`src/host/tool-definitions.ts`
- 条目：`memory.save`
- 现象：`risk: 'read'`、`approvalClass: 'none'`，但该工具会向宿主磁盘持久化记忆条目（跨会话写入）。
- 影响：在 full 档下完全免审写入；且 `risk: 'read'` 会让 `needsConsent()`（阈值口径）判定为不需要同意，两道闸同时失效。同文件内 `file.write` / `file.edit` 均为 `privileged`，分级不一致。
- 修复：`memory.save` 至少应为 `insert` 级别，`approvalClass` 与 file.write 对齐（`mode`）。

### B-05【中危】去重签名对 NaN / BigInt 处理不当，可致签名碰撞或直接抛错

- 文件：`src/shared/tool-call-dedupe.ts`
- 函数：`stableSerialize`（被 `claimSignature` 调用）
- 现象一（碰撞）：`JSON.stringify(NaN)` 返回字符串 `null`，与真实的 `null` 产生完全相同的签名；`undefined` 也走 `String(value)` 兜底为字面量 `undefined`，与字符串 `undefined` 无法区分。两组不同参数被折叠为同一签名。
- 现象二（抛错）：`JSON.stringify` 遇到 `BigInt` 会抛 `TypeError`，此处无 try/catch。一旦工具参数含 BigInt（例如某个 MCP 工具回传或用户脚本构造），`claimSignature` 直接抛异常，整次工具调用失败。
- 影响：误判为重复 → 合法的重复调用被静默丢弃（如用户要求读两次同一文件的不同时刻状态）；抛错 → 工具调用中断。
- 修复：序列化前对数值做类型标注（如 `NaN` → `NaN#`），BigInt 显式 `String(v) + 'n'`，并对整个序列化过程加 try/catch 降级为不参与签名去重。

### B-06【低危】before 钩子改写参数时未校验形状，可把 params 置为 null

- 文件：`src/shared/tool-hooks.ts`
- 函数：`runBefore`
- 现象：判定 `typeof returned === 'object' && returned !== null && 'params' in returned` 后直接 `current = (returned as { params }).params`，未校验 `params` 本身是非 null 对象。
- 影响：钩子返回 `{ params: null }` 或 `{ params: 'x' }` 时，`current` 变成非对象，后续钩子收到非法参数，最终 `execute(params)` 以非法入参执行，异常点远离根因，排查成本高。
- 修复：校验 `typeof returned.params === 'object' && returned.params !== null && !Array.isArray(returned.params)`，不合规则走 `failClosed('hook-invalid-return')`。

### B-07【低危】重试次数语义未定义，`nextDelay` 与 `shouldRetry` 存在 off-by-one 风险

- 文件：`src/shared/retry-policy.ts`
- 现象：`maxRetries: 2`、`shouldRetry` 用 `attempt < policy.maxRetries`、`nextDelay` 用 `base * 2^attempt`。若调用方以「已完成的重试次数」传入，`attempt=0` 得到 500ms 首次退避（合理），`attempt=1` 得 1000ms；但若以「当前是第几次尝试」传入（从 1 开始），则总重试次数退化为 1 次，与 `maxRetries: 2` 的命名承诺不符。
- 影响：无单测锁定语义时，任何调用方改动都会静默改变重试次数；对可重试的瞬时错误（409 / 429 / 网络抖动）表现为重试不足。
- 修复：在接口注释中明确 attempt 是「已完成重试次数，从 0 开始」，并在 `shouldRetry` 内断言 `attempt >= 0`。

### B-08【低危】旧格式回退对缺省 `ok` 字段多做一次 exit-code 输出

- 文件：`src/shared/tool-result-format.ts`
- 函数：`legacyResultText`
- 现象：判定条件 `if (!result.ok && exitCode !== undefined && exitCode !== 0)`。当旧卡片结果未携带 `ok` 字段（`LegacyToolCardResult.ok` 在部分历史路径上是可缺省的），`!undefined === true`，即使命令成功但 exitCode 为 0 之外的值，会追加一行 `[exit-code]`。
- 影响：UI 文案层面误报失败信号，用户看到多余的 exit-code 行。属于显示层缺陷，不影响执行。
- 修复：改为 `result.ok === false` 严格判定。

### B-09【低危】`file_edit` 参数适配把非法 edits 静默降级为空数组

- 文件：`src/shared/tool-contract.ts`
- 条目：`file_edit.adapt`
- 现象：`edits: Array.isArray(p.edits) ? p.edits : []`。模型若把 edits 传成字符串或对象，会被静默替换为 `[]` 传给宿主。
- 影响：宿主收到空 edits 后行为取决于实现（可能报「无匹配」或空操作成功），模型拿到的是模糊结果，无法自我纠正。属于「静默容错掩盖真实错误」类缺陷。
- 修复：非数组时不要塞 `[]`，应返回带明确错误的适配结果，让上层以参数校验失败回执。

### B-10【低危】`runToolCall` 丢弃 `runBefore` 收集的 `hookErrors`

- 文件：`src/shared/tool-loop.ts`
- 现象：`runBefore` 返回的 `RunBeforeOutcome` 含 `hookErrors`（含 before 阶段被 fail-open 忽略的异常），但 `runToolCall` 只读 `gate.proceed` 与 `gate.params`，`hookErrors` 无任何消费者。
- 影响：before 阶段除首个致命错误外的钩子异常只走了一次 console.error，没有进入 trace / 遥测，事后无法从工具调用记录里复盘。属可观测性缺口，会显著拉长此类问题的定位时间。
- 修复：把 `gate.hookErrors` 并入 `call-skip` / `before-call` 事件 payload，或写入 `details.hookErrors`。

## 三、修复优先级建议

1. **立即修**：B-01、B-02（治理白名单与硬拒绝地板失效，属于「看起来有保护、实际没有」的最危险形态）
2. **本迭代修**：B-03、B-04、B-05（fail-open 与分级错误、去重误判）
3. **排期修**：B-06 ~ B-10（健壮性与可观测性）

- 本报告全部结论基于源码静态阅读，未运行测试、未启动宿主进程。B-01 / B-02 建议补一条单测直接锁定（白名单双条目场景、`realpath` 后的 .ssh 路径场景）。
