## 一、逐条说明

### T-01（P1）续跑轮丢掉全部 user 消息

`buildPrompt` 第 148-166 行：

```ts
// 注释写的是「跳过最后一条 user 消息」
const msgs = round > 1 ? all.filter((m) => m.role !== 'user') : all;
```

注释意图是「避免重复 chat-insert 同一条用户文本」，实现却是 `!== user` 的**全量过滤**，把整段对话里每一条 user 消息都剔掉。

后果（maxRounds > 1 的多轮工具链）：

- round 1：prompt 含 `[user] 帮我重构 X`，模型看得到任务。
- round 2 起：prompt 只剩 `[assistant] …` 与 `[tool] …`，**任务本体消失**。模型只能从自己上一轮的措辞反推目标；上一轮 assistant 若只说「我来看看这个文件」，后续轮次就彻底失去方向 —— 反复读同一文件、乱跑工具、或凭空编造需求。

叠加 T-03（超长从头部截断）更糟：续跑轮最早的消息本就是 assistant/tool，截断后连「上一轮说了什么」也保不住。

正确做法是只剔除**最后一条** user：

```ts
const last = all[all.length - 1];
const msgs = round > 1 && last && last.role === 'user' ? all.slice(0, -1) : all;
```

### T-02（P1）超时路径的 unhandled rejection

第 275-296 行：

```ts
result = await Promise.race([
  withAbort(call, signal),          // A
  new Promise((_, reject) => {      // B
    roundTimer = setTimeout(() => reject(new RoundTimeoutError()), roundTimeoutMs);
  }),
]);
```

`Promise.race` 只接管第一个 settle 的 promise，另一个成为 loser：

| 谁先 settle | loser | loser 后续 | 后果 |
|---|---|---|---|
| A（正常返回 / abort） | B（timer） | finally 里 clearTimeout，永不 reject | 安全 |
| B（超时） | A（withAbort） | `call()` 即 `engine.send()` 仍在跑，超时后大概率 reject | **A 已无人 await → unhandled rejection** |

`withAbort` 内部是 `call().then(v => resolve(v), e => reject(e))` —— 它 reject 的是外层 promise A，而 A 在 race 输了之后没有任何 `.catch()`。Node 15+ 默认 `--unhandled-rejections=throw`，Electron 主进程 / CLI 直接以未捕获异常终止。

而这正是**超时场景**：本来就说明引擎或页面卡住，随后 send 报错是常态而非偶发 —— 一旦超时基本必崩。

修法：

```ts
const sendPromise = withAbort(call, signal);
sendPromise.catch(() => {});   // race 输了也有归属
result = await Promise.race([sendPromise, timeoutPromise]);
```

更彻底的做法是超时时主动 abort，让 `call` 真正停下，而不是继续裸跑。

### T-03（P2）按 UTF-16 码元从头部截断

第 160-165 行：

```ts
let out = lines.join(NL);
if (out.length > PROMPT_MAX_CHARS) {
  out = out.slice(out.length - PROMPT_MAX_CHARS);
}
```

两个问题：

1. **码元 vs 码点**：JS 的 `length` / `slice` 都以 UTF-16 码元计。截断点落在代理对（emoji、部分扩展汉字）中间会切出孤立代理项，序列化成 JSON 或 `Buffer.from(s, utf8)` 时变成 U+FFFD。这与已报的 BUG-001/002（studio-execution 字符/字节混用、多字节截断）是同一类缺陷。
2. **从头部切掉的正是任务**：prompt 顺序是 `[user] 任务` → `[tool]` → `[assistant]`，保留尾部意味着最早、最关键的指令最先被丢。叠加 T-01 后，续跑轮可能只剩 tool 记录。

修法：按码点截断（`Array.from(out)` 取尾部再 join），并优先保留最早一条 user + 最近 N 条，而不是简单尾部窗口。

### T-04（P2）maxRounds<=0 时返回 undefined 强转

第 336-341 行：

```ts
// maxRounds>=1 时 last 必被赋值；这里兜底类型
return last as TaskLoopRoundResult;
```

注释自己承认了这个前提。但 `maxRounds` 来自 `TaskLoopOptions.maxRounds?: number`，调用方传 0 或负数完全合法，代码里也没有钳制。此时 `for (let round = 1; round <= 0; ...)` 一次都不进，`last` 保持 undefined，`as` 强转运行期不报错，但**调用方**下一句 `requireTaskLoopReply(result)` 里的 `result.content.trim()` 立刻 TypeError。

修法：`const maxRounds = Math.max(1, opts.maxRounds ?? 1);`

### T-05（P3）两处小问题

1. **限流等待不可取消**（259-261）：`await new Promise(r => setTimeout(r, 2000))` 不监听 signal。用户中止后若恰在轮间等待，最坏再等 2 秒才走到下一次 `signal?.aborted` 检查。
2. **plan 模式并未真正禁止工具调用**（304）：`if (result.toolCallRecords && !isPlan)` 只是不把 tool 记录写进 history，`result.toolCalls` 仍参与 `computeStop` 与 `previousToolCalls`。模型若在 plan 模式发起工具调用，会产生「工具已执行、历史无记录」的不一致；且 `effectiveMaxRounds = 1` 让本轮以 `max-rounds` 收尾，用户看到的是「跑满轮数」而非「plan 模式禁止工具」。

## 二、已核实**不是**缺陷的点

1. `computeStop` 优先级链（timeout → completed → read-no-data/empty-response → no-tool-calls → undefined）与文件头注释、函数注释三处一致，无矛盾。
2. `TASK_COMPLETE_RE` 用非贪婪 `([\s\S]*?)` + 允许内部空白，`<task_complete>...</task_complete>` 能正确命中；无 `/g` 所以 `lastIndex` 不会跨调用污染。
3. `requireTaskLoopReply` 的五种失败原因与 `TaskLoopStopReason` 定义对齐，`content === 空` 与 `failedReason` 用 `||` 组合，不会把失败伪装成成功。
4. `withAbort` 在 `signal.aborted` 已为 true 时直接 reject，不会漏事件；`addEventListener(..., { once: true })` 保证不重复触发；成功/失败两条分支都 `removeEventListener`，不泄漏 listener。
5. `roundTimer` 在 `finally` 里 `clearTimeout`，成功轮次不留悬空 timer 让进程多活 120s —— 注释与实现一致。
6. abort 分支「user 消息已落库不回滚」是**显式设计取舍**（注释写明），不算 bug。
7. `previousToolCalls` 只在成功轮更新；abort / timeout 分支立刻 break，不存在「用旧值误判 useWait」的路径。
8. `useWait` 需同时满足 `round > 1`、`previousToolCalls > 0`、`typeof waitForNextReply === function` 三个条件，降级到 `engine.send(buildPrompt)` 的分支逻辑正确。
9. checkpoint 在 stopReason 判定之后、break 之前保存，`round` 与 `history.snapshot()` 同批落盘，恢复时状态自洽。
10. `store.load()` 未包 try —— `HistoryStore` 是注入接口，属调用方契约，不在本文件职责内。

1. **T-01 + T-02 一起修**：前者直接决定多轮任务能否跑通（当前实现下 maxRounds > 1 基本不可用），后者是崩溃级。改动都只有几行。
