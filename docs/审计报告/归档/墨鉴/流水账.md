**产出**：`审计报告-R4-拦截器层-20261102.md`（14,090 字节），4 High / 5 Medium / 2 待验证，复核掉 3 条候选误报。

**四条 High**：
- **R4-H1** `loopDepth` 在续跑入口被递增两次（2357 + 2359），`MAX_LOOP` 实际可用轮次约减半。根因是 2358 的 `continuationRetryPending = false` 插在两次判断中间，2359 拿不到同一信息。注释（2355-2356）明写「重试不该吃 loopDepth」，但 429 路径照样走 2359 —— 修复意图被后一行破坏。
- **R4-H2** `stop()` 清了 6 项却漏 `autoContinueTimer`，退避窗口内卸载会触发幽灵请求（`abortedByUser` 只在点停止时置位，`stop()` 不置位）。其余 6 项都有 try/catch，说明卸载健壮性是有意识的，这个更像没列全。
- **R4-H3** `continuationRetryPending` 仍是模块级单例，而 526-537 的 QD-R7 注释明确承认「并发是常态」并已把 `streamSawDone` / 首轮预算改成按流/按轮次归属 —— 漏了这一个。并发时 B 轮会清掉 A 轮的标志，A 的重试被 2341 守卫挡死，与 QD-R4-01 记录的原始 bug 同一失效模式。同族还有 `idleContinueCount`、`errorRetryCount`。
- **R4-H4** trace 在 2637 无条件记 `finished: true / completed`，2638 才判断正文是否被剥空。正文全是工具标签时（2642 分支，用户一个字没收到）trace 仍报圆满完成。而 `__studioTraceReport()` 是团队唯一的断流取证入口 —— 取证工具本身在误导排查方向。

**方法论收获**：H1 和 H3 的共同点是「注释写对了设计，实现被后续一行破坏或绕过」。这类缺陷靠「有没有注释解释设计」查不出来，必须把同一函数体的连续若干行放在一起读。提示后续：**注释密集区反而要加倍警惕**，注释会让人产生「这里想清楚了」的错觉。

**没做**：7 个直接依赖（`streaming-tool-parser` / `sse-text-extractor` / `deepseek-sse-frame-decoder` / `raw-tool-text` / `response-classifier` / `continuation-prompt` / `tool-call-dedupe`，合计约 60 KB）未读，留 R4.5 把「工具标签解析 → 流过滤 → 续跑 prompt 构造」这条链闭合。`inject/` 其余 40 文件（约 240 KB）未读。无运行时验证 —— H1 的 +1/+2 差异可以用 mock 调用序列在单测里直接验证，成本很低。
