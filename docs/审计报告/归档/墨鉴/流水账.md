### 三条 High

- **R5-N1**：`continuationRetryPending` 的 Map key 退化为「当前会话」单值。`currentSessionKey()` 返回 `currentChatSessionKey || 'unknown-session'`，同一时刻只有一个值，Map 上限就是 1。会话 A 置位后切到 B，B 清零删的是 B 的 key，A 的标志成孤儿；而 A 的定时器触发时读的又是 B 的 key → 守卫判 false 把 A 的重试挡死。反向也成立：key 撞上时 A 的陈旧 true 会让 B 通过守卫、发出本该被拦的续跑。**R4-H3 的失效模式没被消除，只是换了容器。**
- **R5-N2**：`inAutoContinue` 的复位（2949）发生在被 hook 的那个 XHR 自己的回调里，而 hook 回调先于它执行。注释（2194-2196）说「续跑轮失败由 autoContinueWithPow 分类，这里不插手」，用的是这个布尔做闸门；但闸门在需要它的时刻恰好还开着。首轮重发路径（`inFirstAttemptResend=true` 但 `inAutoContinue=false`）上，hook 的 2203 分支走 `escalateFirstAttemptFailure` 后 `return`（不是 `resolve`）→ `autoContinueWithPow` 的 `await new Promise` 永远等不到 resolve → Promise 悬挂；同时 3146 的 catch 也会对同一次失败再收一次尾。**双计预算 + Promise 悬挂 + trace 自相矛盾。** 依赖「hook 用覆盖+转发而非 addEventListener」这一读法（2231 有 `prev.apply`），建议 R7 运行时坐实。
- **R5-N3**：`firstAttemptResendActive`（850）是死变量——只在 2599 置 true、2635 置 false，**全文件零读取点**。所有判定走的都是 `firstAttemptResendPending` 或 `loopState.inFirstAttemptResend`。无害但有害：注释（847-849）说它「让 autoContinueWithPow 知道要重发」，维护者照注释读会读到永远 false 的值。

**读了什么**（约 2,000 行 / 110 KB）：loader.ts(155)、navigation.ts(90)、lifecycle.ts(60)、origin-guard.ts(19)、bridge-install.ts(41)、direct-target.ts(62)、direct-port.ts(57)、direct-bridge.ts(69)、ds-stop-control.ts(157)、step-control.ts(63)、step-flow-ui.ts(413)、catalog-selection.ts(238)、untrusted-memory.ts(240)、tool-card-ui.ts(378)、index.ts(10)。

**产出**：审计报告-R6-inject层补审-20261102.md（10,850 字符），3 Medium-High/Medium + 5 Medium + 4 Low + 3 待验证。

### 三条主要发现

- **R6-H1**（Medium-High）同域直连桥两端共用同一个 sessionId，port 层只校验 session 不校验发送方 → 任一端的 post 会被自己也收到（回声）。安全论证（页面脚本拿不到 session）成立，但方向性没考虑。若上游 handler 收到即回，则成回路。修法：两端 session 加角色后缀，或消息体带 __from 让 listener 跳过自己。
- **R6-H2**（Medium）navigation.stop() 注释写明「只在仍指向本观察者包装函数时恢复」，实现里完全没有这段代码 —— 只摘了 popstate/hashchange 监听，history.pushState 上的包装永久保留。危害被每实例的 stopped 标志兜住（不会误触发旧回调），但包装链会随 install/dispose 累积。**这是本项目第 6 例「注释写对了设计、实现没跟上」**。
- **R6-H3**（Medium）step-control.ts 文件头承诺「请求节流 2.5-6.5s」，REQUEST_DELAY_MIN/MAX_MS 两个常量定义后全文件零引用 —— 死代码。若上游真依赖这个模块节流，则请求间隔不受控；对 DeepSeek 这类有风控的站点，请求过快是「服务器暂时不可用」的常见诱因。需确认节流是否已上移到 interceptor 退避逻辑。

### 五条 Medium

R6-M1 loader.ts 两个安装失败分支口径不一致（origin 失败刻意不固化、install-order 失败直接固化且无理由）；R6-M2 catalog-selection 的 isPinned 在 62 次循环里每次重建 RegExp + 重算 toLowerCase（热路径）；R6-M3 selectCatalogTools 的 full 累加未扣 reserveBytes，与注释口径不符；R6-M4 untrusted-memory named 保留位注释说「停止保留」实现是 continue（实现更优，属文档缺陷）；R6-M5 step-control 的 clear() 只清定时器不 abort，接口语义模糊。

### 做得好

ds-stop-control.ts 是全仓注释质量最高的文件（判据全部标注真机 dump 来源，明确写了「不能用 aria-label」「生成中发送键不会消失」两条反直觉事实，并列时宁可不动作）；loader 的 origin 失败不固化是有真机依据的修复；untrusted-memory 的信封中和是真正的 prompt 注入防线；catalog-selection 的确定性排序注释写明「确定性是硬要求」。
