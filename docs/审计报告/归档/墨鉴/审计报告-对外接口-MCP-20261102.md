## 二、两个 P1 详述

### BUG-036（P1）initialize 失败 → 子进程泄漏

```ts
// connect() line 285-294
try {
  if (transport === 'http' || transport === 'sse') return this.connectHttp(serverId, config);
  return this.connectStdio(serverId, config);
} catch (e) {
  console.error(`[mcp ${serverId}] connect failed:`, ...);
  this.connections.delete(serverId);   // ← 只删引用
  return null;
}
```

`connectStdio` 内部：`spawn()` → 注册 error/exit/stdout/stderr 监听 → `connections.set` → `await this.initializeConnection(conn)`。

`initializeConnection` 里 `sendRequest(conn, 'initialize', ...)` 有 30s 超时；MCP server 若启动慢（npx 首次下载包很常见，几秒到几十秒）、或根本不实现 initialize，**30s 后 reject** → 冒泡到 `connect` 的 catch。

此时：
- `proc` 仍活着（没 kill，cleanup 没被调用，因为 exit/error 事件都还没触发）；
- `conn.closed` 仍是 false；
- `conn.pendingRequests` 里 initialize 那条已被 timer 自己删掉，但 connections 已 delete，无人再引用 conn —— **子进程成孤儿，stdout 监听器继续挂着**。

重复点几次「重连」，就漏几个 npx 进程（Windows 上是 node.exe）。

**修法方向**：`connect` 的 catch 里改为 `this.disconnectServer(serverId)`（它会 `process.kill()` + reject pending + delete）。更彻底的做法是把 `initializeConnection` 包进 `connectStdio` 内部的 try/finally，失败时 `cleanup('initialize failed', e)`。

### BUG-037（P1）SSE 传输实现不可用

```ts
// sendHttpRequest line 488-503
if (contentType.includes('text/event-stream')) {
  const text = await res.text();          // ← 等整个流结束
  for (const line of text.split(String.fromCharCode(10))) {
    if (line.startsWith('data:')) { ... return parsed.result ?? parsed; }
  }
  throw new Error('No JSON-RPC response in SSE stream');
}
```

SSE（Server-Sent Events）的语义是**长连接持续推送**，服务端不会在发完一条响应后关闭流。`res.text()` 要读到 EOF 才 resolve —— 于是：

- 要么等满 `AbortSignal.timeout(30000)` 抛 TimeoutError，被 catch 成 `{ ok: false, error: 'The operation was aborted due to timeout' }`；
- 要么服务端恰好关了连接（非标准实现），才能拿到内容。

也就是说：**配置 `transport: 'sse'` 的 MCP server 永远调不通**，报错还是「超时」，排查方向会被误导到网络问题。而 stdio 与 http（非 SSE 响应）两条路都正常，说明这不是设计取舍，是实现缺陷。

**修法方向**：用 `res.body` 的 `ReadableStream` reader 增量读取，逐行解析，**拿到第一个含 `id` 的 JSON-RPC 响应就 `reader.cancel()` 返回**，不要等 EOF。

## 三、其余问题要点

### BUG-027（P2）并发 connect 重复 spawn

`connect()` 的复用条件是 `existing && existing.initialized`。而 `connections.set(serverId, conn)` 发生在 await initialize **之前**，此时 `initialized === false`。两个并发调用（例如 `getAllTools` 被 UI 连续触发两次）都会判定「无可用连接」，各 spawn 一个进程，第二次 `connections.set` 覆盖第一次的引用；第一次进程的 exit/error 触发 `cleanup` 时执行 `connections.delete(serverId)`，把**第二个**的引用删掉 → 第二个连接永远拿不到，且它的 initialize 已经成功了但没人引用。

修法：在 connections 里存一个 `connecting: Promise<conn>`（或在 conn 上加 `initializing` 标志 + pending promise），第二次调用直接 await 同一个 promise。

### BUG-031（P2）testConnection 失败不杀进程

`testConnection` 的 try 块里 spawn 了 proc，成功路径末尾 `proc.kill()`，但 **catch 分支只有 `return { ok:false, error }`，没有 kill**。initialize 超时（5s）、或 proc 在 500ms 内没退出但后续 reject，都会走到 catch → 子进程遗留。

修法：try 外提 `let proc`，finally 里 `try { proc?.kill() } catch {}`。

### BUG-032（P2）配置文件非原子写

`saveServer` / `removeMcpServer` / `ensureMcpConfig` 三处都是 `fs.writeFileSync(path, JSON, 'utf8')`。

- 写一半断电/崩溃 → 文件是半截 JSON；
- 下次启动 `loadMcpServers` → `parseMcpServers` 抛 → catch 后 **`return {}`** → 内存 servers 为空 → 界面上**所有 MCP 服务器消失**，文件里却是坏数据，用户无从恢复；
- 运行期 `refreshConfigIfChanged` 的 catch 分支反而正确（保留旧配置），只有「重启后首次加载」这一步会静默清空。

修法：写 tmp 文件 + `fs.renameSync` 原子替换；`loadMcpServers` 失败时备份坏文件（`mcp-servers.json.bad`）并 warn，让用户还能手工救。

### BUG-033（P3）parseMcpServers 不校验形状

```ts
if (parsed.servers && typeof parsed.servers === 'object') {
  return parsed.servers as Record<string, McpServerConfig>;   // 数组也通过
}
```

`servers: []` 或 `servers: { a: "字符串" }` 都会原样返回。后者走到 `connectStdio` 时 `config.command` 为 undefined → `spawn(undefined, ...)` 抛 `TypeError: The "file" argument must be of type string`，被 `connect` 的 catch 兜住返回 null，用户看到「connect failed: The file argument...」，与「配置写错了」的真实原因对不上。

### BUG-034（P3）getAllTools 串行

N 台服务器，每台 `Promise.race([connect, 10s])`，串行累加。3 台最坏 30s。且 race 的 `setTimeout` 定时器不 clear —— 连接快速成功时，10s 后仍会触发一次空 resolve（不报错，但定时器占用）。

修法：`Promise.all` 并发；用 `AbortController` 或保存 timer 句柄 clearTimeout。

## 四、本轮确认**正确**的点（避免重复投入）

1. **env 白名单**：`connectStdio` 只透传 PATH/HOME/TEMP 等系统变量，`filteredEnv` 用 `ALLOWED_ENV_KEYS.has(key.toUpperCase())` 匹配，且用户配置的 `config.env` 在其后覆盖 —— 宿主 token 不会泄漏给 MCP server。设计到位。
2. **shell:false 红线**：仅 Windows 下 `.cmd`/`.bat` 才 `shell: true`，其他一律直接 spawn，避免命令注入。与 P2 阶段的 shell.ts 红线一致。
3. **spawn error 监听**：`connectStdio` 与 `testConnection` 都注册了 `proc.on('error')`，ENOENT 不会变成 uncaughtException 杀宿主（注释标注 P0-3 修复）。
4. **cleanup 幂等**：`cleanedUp` 标志 + error/exit 双路径共用，避免重复 reject/delete。
5. **stdin EPIPE 兜底**：`proc.stdin?.on('error', ...)` 有监听，向已死进程写入不会抛 unhandled error。
6. **R1-05 快速失败**：`sendRequest` 开头检查 `conn.closed || !conn.process || !conn.process.stdin`，进程已死立即 reject，不再干等 30s。
7. **热重载保留旧配置**：`refreshConfigIfChanged` 解析失败时记录 mtime 并 return（保留旧 servers 与旧连接），不会因编辑器半写入把工具全摘掉 —— 这个降级策略是对的。
8. **配置变更时断开旧连接**：`reload` / `refreshConfigIfChanged` / `saveServer` 都用 `JSON.stringify(next) !== JSON.stringify(old)` 比对，变了就 disconnect，避免复用旧 URL/旧 token。
9. **图片上限**：`MAX_IMAGE_BASE64_LEN` 按 5MB 原始大小换算成 base64 长度，超限降级为文本占位，不会把巨大 base64 塞进上下文。
10. **`defaultConfigPath` 口径统一**：`STUDIO_MCP_CONFIG` → `STUDIO_CONFIG_DIR` → `~/.config`，与 `saveServer` 同源（注释即修复记录）。

## 五、观察项（不计入 bug）

1. `parseMcpServers` 的 `parsed.servers` 分支直接 `return parsed.servers`，历史平铺式分支才逐项过滤 `command`/`url` —— 两条路径校验强度不一致。
2. `sendHttpRequest` 非 SSE 分支 `return data.result ?? data`：若服务端返回 `{result: null}`，会返回整个 `data` 而非 null。边缘语义。
3. `callTool` 把首个 text content 尝试 `JSON.parse`，失败则原样返回字符串 —— 行为合理，但 `details` 只在 data 是对象时给，纯文本结果拿不到 details。
4. `testConnection` 的 500ms「等待进程启动」是经验值；慢启动环境下即使进程正常也会误判 `proc.exitCode !== null`（该检查其实是 `!== null` 才失败，逻辑正确）。
5. `disconnectAll` 遍历 `[...connections.keys()]` 复制后再删，避免迭代中修改 Map —— 正确。
