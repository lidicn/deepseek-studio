## 一、新增缺陷

### BUG-010 | P2 | 置信度 高
**位置**：`src/host/memory/retrieval.ts` → `search()`

**现象**：多关键词查询在「每个词都很短」的场景下必然返回空。

**代码路径**：
1. `if ([...q].length >= 3)` 用**整串字符数**判断是否走 FTS，而不是逐 token 判断。
2. 查询 `AI 模型` 总长 5 ≥ 3 → 进入 FTS 分支，`toFtsQuery` 拆成 `"AI" OR "模型"`。
3. FTS5 的 `tokenize='trigram'` 按 **3 字符**成组建索引（`SCHEMA_SQL` 第 41-46 行注释自陈）。长度 2 的短语 `"AI"`、`"模型"` 在 trigram 索引里**不可能命中任何行**。
4. FTS 返回 0 行 → 落到 LIKE 兜底，但兜底用的 `pat = likePattern(q)` 是**整串** `%AI 模型%`。
5. 净效果：本该「命中 AI 或 模型 任一」的检索，退化成「必须连续出现 `AI 模型`」，实际几乎恒为空。

**影响**：记忆检索（Bot 上下文注入的上游）在多关键词/短词/中英混排查询下**静默失忆**——无报错、无日志，用户看到的是「明明记过却搜不到」。

**修法方向**（择一）：
- 最小改：LIKE 兜底改为按 token 分别匹配，多组 `OR (name LIKE ? OR content LIKE ? OR tags_json LIKE ?)` 拼接；
- 或：FTS 分支逐 token 判断，`[...tok].length >= 3` 的走 FTS、不足的单走 LIKE，结果合并去重；
- 或：分词从 `trigram` 换成 `unicode61` + 中文预分词（工作量大，不建议短期做）。

### BUG-011 | P2 | 置信度 中高
**位置**：`src/host/memory/storage.ts:391` → `writeSnapshotRow()`

**现象**：`INSERT OR REPLACE INTO memories` 在主键已存在时，SQLite 语义是「先 DELETE 旧行再 INSERT 新行」，新行会拿到**不同的隐式 rowid**。`memories_fts` 是独立虚表、靠 `rowid` 与主表对齐，旧 rowid 对应的 FTS 记录不会被数据库自动清理。

随后代码 `DELETE FROM memories_fts WHERE rowid = rid`（`rid` 是**新** rowid）只清了新条目，**旧 rowid 的 FTS 行成为孤儿**。

**影响**：
- FTS 表随 rollback / 快照回写次数单调膨胀；
- 孤儿行在 `search()` 的 `JOIN ... ON f.rowid = m.rowid` 中会被自然过滤，**不产生错误结果**，但拖慢 bm25 排序并持续占空间；
- 属「慢性泄漏」，长期运行后检索性能缓慢退化。

**修法方向**：`writeSnapshotRow` 改为先查旧 rowid 并 `DELETE FROM memories_fts WHERE rowid = 旧rid`，再 `INSERT OR REPLACE`，最后按新 rid 重建 FTS；或改为 `UPDATE ... WHERE id=?` + `INSERT ... WHERE NOT EXISTS` 两段式，避免 rowid 变化。

## 二、性能隐患（不计入缺陷）

### PERF-001 | P3 | `memory/storage.ts:423` `prepareEviction()`
每次 `save()` 前都调 `ctx.validRows()`，而 `validRows()` → `allRows()` 是 `SELECT * FROM memories` **全表拉取**，再逐行 `rowToMemory()` 做对象映射，最后在 JS 里 filter。

即：每写一条记忆 = 一次全表读 + O(n) 对象构造。记忆量上去后写入延迟线性增长，且与 `MAX_MEMORIES` 实际值无关（未超限也要先全量算一遍）。

**建议**：容量判断改 `SELECT COUNT(*) FROM memories WHERE invalid_at IS NULL`（走 `idx_memories_invalid_at`），仅在**确实超限**时才拉候选行做 `pickEviction`。

## 三、本轮已核实、判定为「无问题」的点

1. **哈希口径一致**：`contentHash`（type + 小写 name + 压缩空白 content）与 `dedupeHash`（type + 小写 + 压缩空白 content）在 SQL 路径与 fallback 路径共用同一函数，无双实现漂移。
2. **save 三分支语义对齐**：同名命中 / 跨名 dedupe 命中 / 新建 三条路径，SQL 与内存 fallback 两侧的治理字段合并（`mergeUpdateGovernance`：未传即保留、显式传值含 `false`/`[]` 即覆盖）与 no-op 判定条件**逐项对应**，未发现分叉。
3. **容量淘汰确定性**：`pickEviction` 排序键 `type(project 先) → updatedAt ASC → createdAt ASC → id ASC`，全序无歧义；`pinned` 行与已归档行被 filter 排除，不会误淘汰。
4. **附属操作失败降级**：`syncFts` / `applyEviction` 各自 try/catch，失败转 `warnings` 并通过 `partial: true` 上报，主记录完整性不受影响——设计正确。
5. **forget 语义**：`remove(id, {forget:true})` 先取整行快照再删，`forgetAudit` 抹掉历史审计，仅保留 sha256 指纹；普通 `remove` 保留 before 快照可回滚。两条路径均正确（第 280-281 行注释所述「只 SELECT rowid 会让快照变空行」的坑已被规避）。
6. **软归档与检索隔离**：`invalidate()` 只置 `invalid_at` 不删 FTS 条目，但 `search()` 的 FTS 与 LIKE 两条 SQL 都带 `invalid_at IS NULL` 过滤，归档行不会泄漏到检索结果。
7. **FTS 注入面**：`toFtsQuery` 先剥离双引号再包成短语，`likePattern` 转义 `\ % _` 并配 `ESCAPE ''`。FTS5 运算符（`OR`/`NOT`/`NEAR`/`*`）被包进短语后失去语法含义，未发现可利用的查询注入。
