## 三、新增发现

### R5-N1（High）`continuationRetryPending` 的 Map key 退化为「当前会话」单值

位置：795-807（定义）＋ 1586 附近（赋值）＋ 2826（清除）

```ts
let currentChatSessionKey = '';
function currentSessionKey(): string {
  return currentChatSessionKey || 'unknown-session';
}
function isContinuationRetryPending(): boolean {
  return continuationRetryPending.get(currentSessionKey()) === true;
}
function setContinuationRetryPending(value: boolean): void {
  const key = currentSessionKey();
  if (value) continuationRetryPending.set(key, true);
  else continuationRetryPending.delete(key);
}
```

`continuationRetryPending` 这个 Map 的语义是「按会话隔离重试标志」，但 key 来自一个**模块级单值** `currentChatSessionKey`。同一时刻只可能存在一个 key 值，Map 的容量上限就是 1。

于是 R4-H3 描述的失效模式**没有被消除**，只是换了个容器：

1. 会话 A 的首轮失败 → 2826 前后 `setContinuationRetryPending(true)`。
2. 用户切到会话 B，`currentChatSessionKey` 变成 B 的 key。
3. 会话 B 走到 2826 的 `setContinuationRetryPending(false)` → 删的是 **B 的 key**，A 的标志还留在 Map 里。
4. A 的退避定时器触发时，`isContinuationRetryPending()` 读的却是 **B 的 key**（因为 `currentChatSessionKey` 已被改成 B）→ 返回 false → 2799 的守卫把 A 的重试挡死。

更糟的是反向：B 的 key 恰好等于 A 曾经用过的 key 时，A 的陈旧 `true` 会被 B 读到，让 B 在 `pending.length === 0` 的情况下也通过 2799 守卫，发出一条本该被拦的续跑。

**为什么仍然值得报 High**：这是「注释写对了设计、实现绕过了设计」的又一例。795-807 的注释明写「用于按会话维度隔离重试标志」，实现却用一个必然唯一的 key 去索引 Map。**换容器不等于换语义。**

**修法**：key 改从每次请求的 `chat_session_id` 取（`extractChatSessionIdFromBody` 已有，2847 正在用），或把标志收进 `loopState`（每实例一份），彻底不依赖模块级 key。

### R5-N2（High）`inAutoContinue` 的复位时机晚于 hook 回调，续跑轮失败被计两次预算

位置：2192-2196（hook 侧判定）＋ 2946-2949（续跑 XHR 侧复位）

hook 里的设计意图写在 2194-2196：

```ts
// QD-R5-01：首轮重发链（含续跑轮）的失败由 autoContinueWithPow 的执行器
// 分类并升级，这里不再插手——否则一次失败会被计两次预算。
if (!loopState.inAutoContinue) {
  ...classifyResponse / escalateFirstAttemptFailure...
}
```

也就是说，`inAutoContinue === true` 时 hook 必须完全跳过失败分类，把这件事交给 `autoContinueWithPow` 的 try/catch（3146-3164）。

但续跑请求本身是通过被 hook 的 `XMLHttpRequest` 发出的（2930 `new XMLHttpRequest()` → 2931 `xhr.open` → 3143 `xhr.send`）。`proto.send` 的包装（1888-2236）在 `origSend` 之前就把 `readystatechange` 监听挂上了（`installResponseHookAndSend`），而续跑侧自己的 `xhr.onreadystatechange`（2946）是**赋值**，在 `xhr.send` 之后才生效——但 hook 用的是 `addEventListener` 还是覆盖 `onreadystatechange` 需要看 2200-2232 的实际写法；从 2231 `if (typeof prev === 'function') prev.apply(xhr, args)` 看，hook 是把 `prev` 当回调链的下一环调用的，说明 hook 用的是**覆盖 + 转发**，那么执行顺序是：**hook 自己的逻辑先跑完，再调 `prev`（即续跑侧 2946 的那个函数）**。

于是时序是：

1. `readyState === 4` → hook 回调进入，此时 `loopState.inAutoContinue` **仍为 true**（2949 的复位还没执行）。
2. hook 走到 2192 `settleStreamEnd(...)`。续跑轮的 `streamId` 是 hook 自己在 `prepareChatSend` 里 `beginStream` 认领的，所以不会被 2322 的 stale 判断拦掉。
3. `settleStreamEnd` 在 2377 `if (loopState.inAutoContinue) return false` 返回 false → `settled === false`。
4. 回到 hook，2196 `if (!loopState.inAutoContinue)` 读到 **true** → 整段跳过。
5. `prev` 执行 → 2949 `loopState.inAutoContinue = false`。

看起来防护生效了？**不**。问题在 3 与 4 之间：`settleStreamEnd` 在 2382-2389 有一个 `if (!loopState.inAutoContinue)` 的**内层**分支，它在 2377 之后——但 2377 已经 `return false` 了，所以内层不可达。**`settleStreamEnd` 对续跑轮完全不结算，直接交回外层**。

真正的问题在 `autoContinueWithPow` 的 catch（3146）：它无条件 `finishStepFlow({ code: 'auto-continue-failed' })` 并 `loopDepth = 0`，**不检查这次失败是否已经由 hook 的 2203 分支处理过**。而 hook 的 2203 分支（`firstVerdict.verdict === 'retryable'`）在 `!inAutoContinue` 时是**会**执行的——

而 `inAutoContinue` 在**首轮重发**（`resendVerbatim === true`，2806 `loopState.inFirstAttemptResend = true`）时**不会**被置 true（只有 2926 置）。所以：

- **首轮重发**（`inFirstAttemptResend = true`，`inAutoContinue = false`）：hook 2196 的条件成立 → 2203 走 `escalateFirstAttemptFailure` → 计一次 `scheduled`。同时 `autoContinueWithPow` 的 try/catch 也在等这个 XHR，失败时 3146 再 `finishStepFlow` + `loopDepth = 0`。**两条路径都处理同一次失败**。
- 2203 分支里 2209 是 `return`（不是 `resolve`），`autoContinueWithPow` 的 `await new Promise` 永远等不到 resolve → 只能等 `xhr.send` 同步抛错或超时。**Promise 悬挂**。

**后果**：(a) 首轮重发失败时预算被计两次、UI 弹两次错误；(b) `autoContinueWithPow` 的 Promise 可能永久挂起，`loopState.inAutoContinue` 停在中间态；(c) 3149 记的 `auto-continue-failed` 与 2203 记的 `first-attempt-retry` 语义冲突，trace 自相矛盾。

**修法**：hook 的 2203 分支补 `resolve()`（需要把 `resolve` 透传进来），或让续跑侧改用不受 hook 干扰的原生 send（`origSend`）；同时 3146 的 catch 加一道「本次已由 hook 处理」的幂等标志。

> 置信度说明：本条依赖「hook 用覆盖 + 转发而非 addEventListener」这一读法。R5 已读到 2231 的 `prev.apply`，但未读到 `installResponseHookAndSend` 内部（约 2198-2230 之间）对 `onreadystatechange` 的具体赋值。**建议 R7 用运行时验证坐实**。

### R5-N4（Medium）XHR 路径的 `sse.flush()` 只在 `part` 非空时执行，尾部残留可能丢

位置：2107-2109

```ts
let visible = sse.feed(part);
if (xhr.readyState === 4) visible += sse.flush();
```

这段在 `if (part) { ... }` 块内部（2082 开始）。而 `readyState === 4` 的那次回调**通常没有新增字节**——`__dsScanned` 已在上一轮 readyState===3 时把 `responseText` 消费完，此时 `part` 为空串 → 整个 `if (part)` 块不进入 → **`sse.flush()` 不执行**。

**修法**：把 `sse.flush()` 提到 `if (part)` 之外，与 fetch 路径对齐（2174 的 `tailParser.flush()` 已经是这么写的，说明作者知道要放外面，只是 `sse.flush` 漏了）。

### R5-N5（Medium）`traceTurnId` 跨轮复用，首轮重发预算可能记到上一轮头上

位置：913（声明）＋ 1586（赋值）＋ 1662 / 1945（`firstAttemptBudget(traceTurnId).sent += 1`）

`traceTurnId` 在 `captureChatRequest`（1536）里赋值，也就是**只有新用户消息**才刷新。而 `firstAttemptBudget(traceTurnId).sent += 1` 在 hook 的发送路径上（fetch 1662、XHR 1945）——如果这次发送是**上一轮失败后的重发**，`captureChatRequest` 不会重跑，`traceTurnId` 仍是上一轮的值。

看起来是对的（重发本来就该记在上一轮）。**但** 2754 有一行 `firstAttemptBudgets.delete(traceTurnId)`（在 `onNewUserMessage` 回调里），若它先于 1662/1945 执行，预算表已被删，`firstAttemptBudget(traceTurnId)` 会**新建一个 sent=0 的条目**，重发次数从 0 重新计——即「重试预算永远用不完」。

这与 R4-V1（`firstAttemptBudgets.delete` 的时序）是同一处，R5 读到了 2754 但没读到 2740-2760 的完整上下文。**维持待验证，但置信度从 R4 的「需读 1098-1160」上升到「需读 2740-2760」**——范围缩小了。

### R5-N6（Medium）`collectedExecutions` 只增不减，长会话内存与 filter 成本线性增长

### R5-N7（Low）`stop()` 里 `skillsRefreshSender` 的清理只在 `=== sender` 时生效，多实例场景下会泄漏引用

位置：3410

```ts
if (skillsRefreshSender === sender) skillsRefreshSender = null;
```

`skillsRefreshSender` 是模块级变量（2255 `skillsRefreshSender = sender`）。若同一页面挂载了两个拦截器实例（测试或热重载），后挂载的把变量覆盖成自己的 sender，先卸载的那个执行 `stop()` 时 `=== sender` 为 false → 不清理 → 模块级变量继续指向一个已 `stop()` 的实例的 sender。

**后果**：`refreshSkillsOnce` 会用已卸载实例的 sender 发请求，而该 sender 的宿主连接可能已断。不崩，但会持续失败并刷 `skillsLastError`。

**修法**：模块级变量改由引用计数管理，或 `stop()` 无条件置 null（代价是多实例时后卸载的会清掉前者的——但那本来就该是单实例语义）。

## 四、本轮确认「做得对」的地方（非客套）

1. **`settleStreamEnd` 的 stale stream 守卫**（2322-2325）：`activeStreamId !== streamId` 时整条跳过，注释里带实测数据（「243ms 内三次结算」）。这是全仓少见的、**用现场证据反推修法**的代码。
2. **三态判定**（2357-2362）：`streamBytes === 0` 时判 `no-stream` 而非 `truncated`，避免空 XHR 烧预算。注释写明「就是满屏执行未完成」的成因，问题—修法—验证三段齐全。

4. **`firstAttemptResendPending` 在 `autoContinueWithPow` 入口立即清零**（2804-2805）：先取值再清，后续所有分支都基于局部 `resendVerbatim`，不会出现「读到一半被别处清掉」。与 R5-N3 的死变量形成对比——说明作者知道该怎么写，只是漏了一个。

6. **`augmentInit` 与 `prepareOutgoingBody` 的幂等保护**（1917-1919 `if (prepared) return`）：注释写明「否则延迟路径会二次注入能力提示」。

## 六、方法论收获

本轮读到的最有信息量的一处，是 2194-2196 的注释与 2949 的实现之间的**时序假设落差**：

> 注释说「续跑轮的失败由 autoContinueWithPow 分类，这里不再插手」，用的是 `inAutoContinue` 这个布尔做闸门。
> 但 `inAutoContinue` 的复位（2949）发生在**被 hook 的那个 XHR 自己的回调里**，而 hook 的回调先于它执行。
> 结果：闸门在需要它的时刻恰好还开着，而唯一受益的分支（2377 的 `return false`）又把结算整个甩回外层，让 hook 的 2196 成了唯一处理点。

这一类缺陷（**用一个会被自身调用链修改的状态做防护**）与 R4 的 H1（用插在两次判断中间的清零破坏判断）同族，但更隐蔽：H1 是同一函数内相邻两行，本轮这个是跨了两个回调、隔了 700 行。

**提示后续轮次**：审「防护性分支」时，不要只确认「条件写对了」，还要确认「条件里的状态在到达该行之前不会被同一次调用链改写」。具体到本仓，`inAutoContinue` / `inFirstAttemptResend` / `streamActive` 这三个布尔都同时被 hook 侧与业务侧写入，是重点怀疑对象。
