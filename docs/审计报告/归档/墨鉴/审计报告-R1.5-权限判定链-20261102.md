## 2. 缺陷详述

### R15-001（P1，已实测）git-destructive 正则漏检 `git clean -xfd`

**位置**：`policy.ts:177-183`

```js
{ id: 'git-destructive', label: 'Git 破坏性操作', pattern: /git\s+(push[\s\S]*(--force|-f\b)|reset\s+--hard|clean\s+-fd|checkout\s+--\s+\.)/i },
```

**问题**：`clean\s+-fd` 只认字母序 `-fd`。git 的组合短选项**顺序无关**，`-fdx`、`-dfx`、`-xfd`、`-df` 全都能达到「强制删除未跟踪文件（含 ignored）」的效果，但正则全不匹配。

**实测**（Python `re` 复刻同一正则）：

| 命令 | 结果 |
|---|---|
| `git clean -fd` | HIT |
| `git clean -fdx` | HIT（`-fd` 前缀命中） |
| `git clean -xfd` | **MISS** |
| `git clean -dfx` | MISS |
| `git clean -df` | MISS |

**为什么是 P1**：RISK_PATTERNS 是 auto 档（默认档）对 shell 命令的**唯一防线**。`auto` 档下无风险命令直接放行、有风险命令才弹审批。`git clean -xfd` 会不可逆删除所有未跟踪文件**包括 .env / .gitignore 里忽略的本地配置**，漏检等于静默执行。

**修法**：
```js
pattern: /git\s+(push[\s\S]*(--force|-f\b)|reset\s+--hard|clean\s+-[a-z]*[fdx][a-z]*|checkout\s+--\s+\.)/i
```
更稳的写法是拆成选项检测函数：解析 `clean` 后的短选项簇，若含 `f` 且含 `d` 或 `x` 即判风险。

**同类问题**（顺带记录，未单列）：`destructive-delete` 正则对 `find . -delete`、`find / -name "*" -exec rm {} ;` 也 MISS。这两条属于「非 rm 系的删除」，是否需要覆盖取决于产品口径，建议至少在注释里写明不覆盖范围。

### R15-002（P1，待验证）`python.exec` 在 auto 档绕过风险检测

**位置**：`policy.ts:131-140` + `evaluatePolicy` 末尾 `not-governed` 分支

```js
export const PROCESS_TOOLS: readonly string[] = ['shell.exec', 'mcp.test'];
export const EXECUTION_TOOLS: readonly string[] = ['python.exec', 'mcp.call', 'mcp.save'];
```

判定流程：
1. `isFileTool` 否 → 跳过
2. `isProcessTool` 否 → **跳过整个风险检测块**
3. `EXECUTION_TOOLS.includes(tool) && mode === 'workspace'` → 仅 workspace 档 deny
4. 落到末尾 `return { decision: 'allow', reason: 'not-governed' }`

**结果**：`python.exec` 在 `ask` / `auto` / `full` 三档全部返回 `allow`，**RISK_PATTERNS 从未被调用**。

**风险面**：`python.exec` 能执行 `os.system('rm -rf /')`、`subprocess.run(['git','clean','-xfd'])`、`open(os.path.expanduser('~/.ssh/id_rsa'))`——上述所有命令都不会经过 `detectRisks`。

**为什么标「待验证」而非直接 P0**：注释写「其它档位：tool-definitions 已标 risk:privileged，由同意闸门兜底」。若 `python.exec` 的 `approvalClass` 是 `always`，authorization.ts 第 6 步会强制 ask，则实际不会静默执行；若是 `mode`，auto 档下 policyVerdict=allow 就直接放行。**定论取决于 `tool-definitions.ts` 的实际标注**，本轮未读该文件。

**修法（两选一）**：
- 把 `python.exec` 加入 `PROCESS_TOOLS`，让它的 code 字段经过风险检测（需扩展 `commandText` 支持读 `code` 字段）
- 或把 `EXECUTION_TOOLS` 的 deny 范围从「仅 workspace 档」扩展到「workspace + auto 档」

### R15-003（P2）可信目录大小写口径不一致

**位置**：`policy.ts:150-152` vs `authorization.ts:199-207`

```js
// policy.ts —— 用 path.resolve 原始结果
const resolved = pathResolve(target);
for (const dir of input.trustedDirs) {
  if (resolved.startsWith(pathResolve(dir) + pathSep) || resolved === pathResolve(dir)) {
```

```js
// authorization.ts —— 用 normalizePath（盘符转小写）
export function normalizePath(p: string): string {
  let out = p.replace(/\\\\/g, '/');
  out = out.replace(/^([a-zA-Z]:\\/)/, (_, d: string) => (d as string).toLowerCase());
```

**问题**：Windows 文件系统大小写不敏感，但字符串比较大小写敏感。

场景：可信目录配 `E:/Work`，用户请求 `e:/work/a.txt`：
- policy 层：`path.resolve('e:/work/a.txt')` = `e:\work\a.txt`，`startsWith('E:\Work\')` = false → 判越界
- authorization 层：两边都 normalizePath → `e:/work/a.txt` vs `e:/work` → 前缀匹配成立 → grant key 一致

同一路径在两层得到不同结论。后果：用户在 auto 档下点「本次对话始终允许」批准了 `E:/Work/a.txt`，下次访问 `e:/work/a.txt` 时 grant key 相同（authorization 侧），但 policy 层仍判越界 → 又弹一次审批。用户体验上是「批了还要再批」，且原因不可见。

**修法**：policy.ts 的可信目录比较改用 authorization.ts 导出的 `normalizePath`，两层共用同一口径。

### R15-004（P2）argv 边界在 grant key 中丢失

**位置**：`authorization.ts:157-160`

```js
function joinArgv(params: Readonly<Record<string, unknown>>): string {
  const argv = params.argv;
  if (Array.isArray(argv) && argv.every((a) => typeof a === 'string')) {
    return (argv as string[]).join(' ');
  }
  return '';
}
```

**问题**：空格拼接后作为 `canonicalTarget` 参与 grant key 计算。argv 的边界信息（哪个空格是参数分隔、哪个是参数内部空格）丢失。

**碰撞示例**：
- `argv = ['rm', '-rf', 'a b']` → join = `rm -rf a b`
- `argv = ['rm', '-rf a', 'b']` → join = `rm -rf a b`

两者 grant key 完全相同。用户在场景 A 批准后，场景 B 免审。虽然实际执行侧用 argv 数组不会混淆，但**授权作用域与执行语义脱节**——用户批的是「删 a b 文件」，实际允许的是「删 a 和 b」。

**修法**：`joinArgv` 改为带边界的序列化，例如 `JSON.stringify(argv)` 或 `argv.map(a => JSON.stringify(a)).join(' ')`。

## 3. 观察项（不计入缺陷）

1. **`mcp.remove` 的档位归属**：不在 `PROCESS_TOOLS` 也不在 `EXECUTION_TOOLS`，workspace 档下落 `not-governed → allow`。头部注释把 `mcp.remove` 列入 always 类（full 档仍 ask），若 approvalClass 确实是 always 则实际会 ask，不算静默放行。但「删除 MCP 配置」在「仅工作区」档下不被策略拒绝，语义上值得再确认。

2. **`outsideCwd` 的 null 短路**：
   ```js
   const outsideCwd = cwd && workspace && !workspace.contains(cwd);
   ```
   `workspace` 为 null 时整个表达式 falsy，auto 档下无风险 shell 命令仍放行。与头部「未配置工作区时所有文件类工具 deny（fail-closed）」一致（shell 不是文件类），但「未配置工作区」这一状态下 shell 是否应 fail-closed 是个产品决策，建议显式写进注释。

3. **类型强转**：
   ```js
   const allowed = allowedGrantScopesFor(def ?? ({ approvalClass: cls } as ToolDefinition));
   ```
   构造只含单字段的对象强转成 `ToolDefinition` 传给需要完整类型的函数，靠 `def.grantScopes ?? ['once']` 兜住。可运行但类型不安全，`strict` 模式下若 `ToolDefinition` 加了必填字段会静默出错。

## 4. 复核结论（对既有 35 条的影响）

### BUG-009（cmd /c 元字符检查被跳过）—— 维持原结论

本轮想闭合这条链，结论是**无法在 policy/authorization 层闭合**：
- 元字符转义逻辑在 `capabilities/shell.ts:258`，不在 policy.ts
- policy 只做「命令文本 → 风险模式匹配」，不做转义
- 两层是**串联而非替代**：shell.ts 跳过检查时，policy 的风险检测仍会跑（但 R15-001 说明这个检测本身有漏）

BUG-009 的修法仍是回到 shell.ts 补检查，与本轮无交叉。

### RISK_PATTERNS 其余 9 条 —— 无 lastIndex 污染

`detectRisks` 用 `r.pattern.test(command)` 逐条检测，正则字面量无 `g` 标志，不存在 `lastIndex` 残留导致隔次漏检的问题。实测 `rm -rf` / `rm -r -f` / `rm --recursive --force` / `push --force` / `push -f` / `clean -fd` / `clean -fdx` 均命中。

### authorization 10 步顺序 —— 与注释一致

实测代码路径：unknown → hard-deny → policy deny → conversationApproved → always → mode → none → fail-closed。`internal-bot` 预授权严格限定 `target.kind === 'chat-action'`，泛化后门已堵住（注释里写明「一旦被泛化，就等于让 bot 给自己开了删记忆/改档位的后门」）。设计意图落地准确，这是本轮最值得肯定的部分。
