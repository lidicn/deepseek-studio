## 二、High / Medium-High

### R6-H1（Medium-High）直连桥两端共用同一 sessionId，port 层不区分方向 → 自发自收

位置：bridge-install.ts:26-29 + direct-port.ts:27-38

```ts
// bridge-install.ts
const content  = createDirectBridge({ target, sessionId: options.sessionId, ... });
const injected = createDirectBridge({ target, sessionId: options.sessionId, ... });  // 同一个 sessionId
```

```ts
// direct-port.ts —— 只校验 session，不校验发送方
const listener = (event) => {
  const data = event.data as { __session?: string; __payload?: ... };
  if (!data || data.__session !== sessionId) return;
  if (data.__payload) {
    for (const h of [...handlers]) { try { h(data.__payload); } catch ... }
  }
};
```

两端挂同一个 DirectTarget 总线（按 origin 分桶）、同一个 sessionId。任一端的 post() 都会 dispatch 到总线，两端各自的 listener 都会通过 __session === sessionId 校验并投递给自己注册的 handler —— 包括发送方自己。

后果：content.post(...) 后，content 端自己的 onMessage 也会收到同一条消息。若上层 handler 会再 post（请求-响应、或转发），就形成回路；即使不回路，也会多一次无意义处理，且难以判断「这条消息是对方发的还是我自己发的」。direct-port 文件头注释写「不依赖 window.postMessage 的全局可见通道，页面脚本即使能 dispatch 总线也无法通过 session 校验」——安全性论证成立，但方向性没考虑。

为什么是 Medium-High 而非 High：现有调用方是否会在 onMessage 里再 post，本轮未读（bridge 的上游 RuntimeBridge 不在 inject/ 内）。若上游按 type 字段严格分发且响应型消息不被自己处理，则只是冗余；若存在「收到即回」的模式，则是死循环。

修法（改动很小）：bridge-install 给两端分配不同的 sessionId 后缀（如 sid + ':content' / sid + ':injected'），或在消息体加 __from 字段，listener 里拒绝 data.__from === selfRole；或在 port 层加 excludeSelf 选项，post 时打标、listener 跳过。

### R6-H2（Medium）navigation.stop() 从不恢复 history.pushState/replaceState 包装，注释承诺未兑现

位置：navigation.ts:57-90

```ts
if (shouldPatchHistory && history && patchedPush && patchedReplace) {
  history.pushState = (...args) => { patchedPush(...args); trigger(); };
  history.replaceState = (...args) => { patchedReplace(...args); trigger(); };
}
// ...
stop() {
  stopped = true;
  if (shouldPatchHistory) {
    // 保留其它观察者包装后的 pushState/replaceState 可能依赖的原函数引用，
    // 这里只在仍指向本观察者包装函数时恢复，避免误覆盖后续观察者。   ← 注释承诺
    globalThis.removeEventListener('popstate', onPop);
    globalThis.removeEventListener('hashchange', onPop);
    // ← 没有任何恢复 pushState/replaceState 的代码
  }
}
```

注释明确描述了「只在仍指向本观察者包装函数时恢复」的策略，实现里完全没有这段逻辑 —— 只摘了两个事件监听，history.pushState 上挂着的那层包装永久保留。

后果：
1. 包装链累积：stop() → 重新 createNavigationObserver + start() 会再包一层，旧的包装函数仍在链上。多次 install/dispose（热重载、路由重注入）后 pushState 调用链变长。
2. stopped 是每实例的：旧实例的包装函数仍在，触发时读的是旧实例的 stopped（已被 stop 置 true）→ 直接 return，不回调。所以不会误触发旧回调 —— 危害被 stopped 兜住，这也是定 Medium 而不是 High 的原因。
3. 但 start() 会把 stopped 复位为 false。若同一实例 stop 后再 start，旧包装（若存在多层）会重复触发同一个 trigger()。

性质：与 R4-H1、R4.5-N1 完全同族 —— 注释写对了设计，实现漏了对应代码。这已经是本项目第 4 例。

修法：stop() 里判断 history.pushState === ourPushWrapper 再还原为 patchedPush（保留原引用即可实现，变量已在作用域内），与注释描述一致。

### R6-H3（Medium）step-control.ts 文件头承诺「请求节流 2.5-6.5s」，常量定义后从未使用

位置：step-control.ts:1-12（文件头 + 常量）vs 全文 63 行

```ts
/**
 * 功能：
 * - 步骤超时（120s）+ AbortSignal
 * - 请求节流（2.5-6.5s 随机延迟）      ← 承诺
 */
const STEP_TIMEOUT_MS = 120_000;
const REQUEST_DELAY_MIN_MS = 2500;      // 定义后全文件无引用
const REQUEST_DELAY_MAX_MS = 6500;      // 定义后全文件无引用
```

createStepSignal 只实现了超时 + AbortSignal，没有任何节流逻辑。两个节流常量是死代码。

后果：若上游依赖这个模块做请求节流（文件头这么写，读代码的人会信），则实际请求间隔不受控。对 DeepSeek 页面这类有风控的站点，请求过快是「服务器暂时不可用」症状的常见诱因之一 —— 而用户主诉里正好有这一条。

判定：静态证据确定（常量零引用），但是否该在这里做节流取决于架构（也可能节流已上移到 interceptor 的退避逻辑里，本文件的注释是移植残留）。因此定 Medium + 需确认：若节流已在别处实现，本条降为「删除死常量 + 改注释」的文档清理。

修法：二选一 —— 补一个 delayBeforeStep(): Promise<void> 并在调用方 await；或删常量、改文件头注释。

## 三、Medium

### R6-M1｜loader.ts 对「安装失败是否固化」两处判断不一致

位置：loader.ts:107-117

```ts
if (!isAllowedOrigin(locationOrigin(), whitelist)) {
  // 不写 installed：origin 在文档早期可能取不到……一次误判不该固化成「永远不注入」
  status = 'skipped';
  return { installed: false, status: 'skipped', ... };       // installed 保持 false
}
if (!verifyInstallOrder()) {
  installed = true;                                          // ← 这里固化了
  return { installed: false, status: 'failed', reason: 'install-order' };
}
```

同一函数里两个失败分支，一个刻意不固化（有注释说明理由）、一个直接固化，没有给出任何理由。install-order 失败在语义上是「装载时机不对」，与 origin 取不到同属「环境还没准备好」类，同样可能是一次性误判。

后果：readyState !== 'loading' 且开了 strictInstallOrder 时，本轮永久放弃注入，后续 bootstrapInjection 重复调用只返回 already-installed，页面刷新前无法恢复。

修法：与 origin 分支对齐，不写 installed；或反过来给 origin 分支写 installed = true 并说明理由。二者择一，不能无声分叉。

### R6-M2｜catalog-selection.ts isPinned 在循环内每次重建 RegExp + 重算 lowercase

位置：catalog-selection.ts:157-165，调用点 181

```ts
const isPinned = (tool: T): boolean => {
  if (pinned.has(tool.name)) return true;
  const text = input.userText.toLowerCase();          // 每次调用重算
  const name = tool.name.toLowerCase();
  const re = new RegExp(`(^|[^a-z0-9_])${name.replace(...)}([^a-z0-9_]|$)`, 'i');  // 每次编译
  return re.test(text);
};
// 循环体
for (const entry of ranked) {
  if (isPinned(entry.tool) || fullBytes + cost <= input.budgetBytes) { ... }
}
```

62 个 MCP 工具 → 每轮选择编译 62 个正则、做 62 次 toLowerCase()。该函数在每次构建 prompt 时调用（每轮对话至少一次）。

后果：不是崩溃级，但属于「每轮对话都在做的无效开销」，且 userText.toLowerCase() 本可在函数外算一次。与 R2-8（realpathSync 在热路径）同属「热路径上的可省成本」。

修法：text 提到函数外；正则不能简单缓存（每个 tool 一个），但可改成不用正则的独立词边界判断：text.includes(name) 且前后字符非 [a-z0-9_] 的线性扫描，避免 62 次编译。

### R6-M3｜selectCatalogTools 的 full 累加未扣 reserveBytes，与注释口径不符

位置：catalog-selection.ts:64-67（注释）vs 181（实现）

```ts
/** 预算里要预留给目录固定开销的字节数。 */
reserveBytes?: number;
// ...
if (isPinned(entry.tool) || fullBytes + cost <= input.budgetBytes) {   // ← 用完整预算，未减 reserve
```

注释声明 reserveBytes 是「预算里要预留的固定开销」，但 full 的累加判断直接对 budgetBytes 比较，reserve 只在后面的「索引回填」段（189 行之后）出现。

修法：fullBytes + cost <= input.budgetBytes - reserve，与注释一致；或在注释里改成「reserve 仅用于索引段回填」并说明。

### R6-M4｜untrusted-memory.ts named 保留位的 continue 与注释「停止保留」不一致

位置：untrusted-memory.ts:131-140 + 注释 99-101

```ts
// 注释：named 块受 CAP 约束，超过即停止保留 → 降级
for (const row of rows) {
  if (chosen.size >= rowLimit) break;
  if (!namedIds.has(row.id)) continue;
  const tokens = estimateTokens(formatMemoryLine(row));
  if (namedUsed + tokens > MEMORY_INJECT_NAMED_RESERVE_TOKEN_CAP) continue;   // continue，不是 break
  chosen.add(row); namedUsed += tokens;
}
```

注释说「超过即停止保留」，实现是「跳过这一条、继续试下一条」。

判定：实现更优（不会因一条超大 named 挡住后面能放下的 named），符合 R3-04 的既有取舍。但注释与实现分叉，属文档缺陷 —— 且这是本项目高频模式（R6-H2、R6-H3、R4-H1、R4.5-N1 同族）。建议改注释为「跳过超额条目、继续尝试后续 named」。

### R6-M5｜step-control.ts 的 clear() 只清定时器，不 abort

位置：step-control.ts:36-40

```ts
const clear = () => {
  clearTimeout(timeout);
  parentSignal.removeEventListener('abort', onParentAbort);
};
```

clear() 后 controller 从未 abort，调用方手里的 signal 永远处于「未 abort」状态。

后果：语义模糊 —— clear() 到底是「取消这个步骤」还是「正常结束、停止监控」？若调用方在 clear() 后仍用该 signal 包 fetch，超时保护已解除但 signal 也不会中止请求。两种语义都能自圆其说，但接口没写清楚。

修法：注释明确 clear() = 「正常结束，撤销监控」；或提供 cancel() 单独做 abort。

## 四、Low

### R6-L1｜direct-port.close() 后 post() 仍会发出
close() 只 removeEventListener + handlers.clear()，没有 closed 标记；之后 post() 仍会 target.postMessage(...)，消息进入总线但无人接收（除非对端还活着 —— 那对端会收到，语义上还算「发出去」）。低危，但 DirectBridge.post() 在 port === undefined 时会 throw，而 port 存在但已 close 时不 throw，两处不一致。

### R6-L2｜origin-guard.normalizeOrigin 不归一化尾斜杠
https://chat.deepseek.com/ 与 https://chat.deepseek.com 不等。location.origin 永远不带尾斜杠，故实际不触发；但若白名单配置里写了带斜杠的项就会失效。R1 已记录，本轮不重复计入总数，仅确认仍在。

### R6-L3｜tool-card-ui 图片白名单放行 data:image/svg+xml
isSafeImageUrl 只判 startsWith('data:image/')，data:image/svg+xml;base64,... 也通过。若该 URL 被塞进 <img src>，SVG 内脚本不执行（img 上下文安全）；若被塞进 <iframe> 或 innerHTML，则可能执行。需确认渲染处（见待验证）。

### R6-L4｜direct-target 的 buses 只增不删
模块级 Map<string, EventTarget> 按 origin 分桶，无回收。实际 origin 只有 chat.deepseek.com 一个，无实质泄漏；但若将来多 origin 会累积。仅登记。

## 六、做得好的地方（本轮确认）

1. ds-stop-control.ts 是全仓注释质量最高的文件：判据全部标注真机 dump 来源，明确写了「不能用 aria-label（DeepSeek 停止键是纯图标）」「生成中发送键不会消失」两条反直觉事实，且分数并列时返回 no-stop-control（宁可不动作也不误点）。识别与点击分离的职责切分也对。
2. loader.ts 的 origin 失败不固化（107-112）：注释写清了「srcdoc iframe / about:blank 早期取不到 origin」的真实场景，是一个做过真机验证的修复。
3. direct-port 的 handler 逐个 try/catch + reportError：一个 handler 抛错不影响其它 handler，且有上报通道。
4. untrusted-memory 的信封中和：neutralizeUntrustedMemoryMarkers 把正文里的 OPEN/CLOSE 标记都替换成 REDACTED，防止记忆正文提前关闭数据块 —— 这是真正的 prompt 注入防线。
5. catalog-selection 的确定性排序：(b.score - a.score) || (a.index - b.index)，同分保持原始顺序，注释写明「确定性是硬要求」。可复现，不随 Map 迭代序漂移。
6. bridge-install 的 sessionId 由装载器写入：页面脚本拿不到，消除了 postMessage 的伪造面 —— 方向正确（只是 R6-H1 的发送方区分没做）。

## 九、方法论备注（累积观察）

到 R6 为止，「注释写对了设计、实现没跟上」这一类已经出现 6 次（R4-H1、R4-H3、R4.5-N1、R6-H2、R6-H3、R6-M4），占本轮 Medium 以上发现的 5/6。

这不是偶然的编码疏忽，而是这个项目的注释承担了「设计规格」的职能 —— 设计只存在于注释里，没有单测锁定，于是实现与注释在同一次提交里就分叉了。

对后续审计的提示：读注释时把每一句都当成一条待验证的断言。「禁止」「必须」「不应该」这类词附近，实现往往有偏差。反过来，对这个项目的修复建议也应该包含「把注释里的一句话变成一条单测」，否则修完还会再分叉。
