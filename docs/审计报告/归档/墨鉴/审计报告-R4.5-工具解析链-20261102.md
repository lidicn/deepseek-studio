## 二、R4 三问的回答

### Q1：工具标签跨 chunk 被截断，会当正文吐给用户吗

不会静默泄漏，但流结束时会把半截标签当 clean 文本返回一次。

链路三层：
1. StreamingToolCallParser 有 tail 保留机制，跨 chunk 的尖括号和半截标签名都留到下次拼接，tailHasUnclosedKnownToolTag 提供未闭合信号。
2. 流真在标签中途断开时，flush 把 tail 当 clean 返回 —— 这是唯一泄漏点。
3. 渲染前过 raw-tool-text 的 scanRawToolText，未闭合开标签会被从该标签起到文本末尾一并剥掉并标 unclosed，所以不进用户气泡。

结论：单层有泄漏，双层兜底后不漏。但 flush 的语义值得改：它把解析失败和没有标签都返回成 clean 字符串，调用方只能靠 hasUnclosedToolTag 这个布尔区分。

### Q2：SSE 帧解码器丢帧时有可观测信号吗

完全没有。这是本轮最干净的一条缺陷。

三处静默：
- deepseek-sse-frame-decoder 的 createFrame：JSON 解析失败直接 catch 忽略。
- 同文件 extractFromParsed：非对象早退返回空串。
- sse-text-extractor 的 extractLine：catch 返回空串。

没有计数、日志、回调、遥测。response-classifier 建了 50 条环形缓冲的 ErrorTrace，但只覆盖 HTTP 层和 SSE error 帧，帧解析失败不在其中。

后果：真机上内容少几个字、工具标签首字符丢了这类症状，取证时看不到任何帧级信号。与 R4-H4（trace 报 finished 为 true）同族 —— 取证工具本身在丢证据。

### Q3：续跑 prompt 构造依赖模块级单例状态吗

continuation-prompt.ts 不依赖，它是纯函数模块，零模块级可变状态，MAX_LOOP、MAX_ERROR_RETRIES、MAX_AUTO_CONTINUE 三个预算都是常量。这是全仓设计最干净的模块。

tool-call-dedupe 本身是工厂函数返回实例，Set 封装在闭包内，不是单例。但若拦截器在模块顶层创建一次（大概率，因为要跨轮复用 callId 认领），就退化成单例，见 N8。

## 三、新发现

### R4.5-N1（High）extractFromParsed 声明提取工具调用，实现从不赋值

deepseek-sse-frame-decoder.ts 的 extractFromParsed 返回 visibleText、reasoningText、hasToolCall 三项。hasToolCall 初始化为 false 后，全函数体没有任何一处赋 true，函数注释却写着从 frame.parsed 里提取可见文本和工具调用。

影响取决于调用方：若拦截器用 hasToolCall 参与本轮有无工具调用的判定，则永远 false，误判无工具，触发 nudge、续跑、trace 记 no-tools。这与 R4-H4 和 raw-tool-text 注释里记录的 C1-F5 是同一失效模式的三个面。

待确认：需 grep extractFromParsed 的调用点。若调用方另有路径（用 parser 的 calls 长度），此字段是死代码，降 P3 清理。

### R4.5-N2（High）SSE 错误帧对 code 为 0 判 fatal，与 HTTP 分类器语义冲突

response-classifier 里两个函数对 code 为 0 的处理相反：
- parseBodyError（HTTP 200 加 JSON body）：注释明写正常成功包也带 code 为 0，只有 0 与明确 error 同时出现才算内嵌错误，无 error 就放过。
- classifySseFrame（流内帧）：只要 code 为 0、429、500 且带 error 或 message 就判定，code 为 0 时 verdict 是 fatal。

两处差异：一是 HTTP 版要求 error 字段存在，SSE 版 error 或 message 都算；二是 HTTP 版对 code 为 0 无 error 时放行，SSE 版对 code 为 0 带 message 直接 fatal。

风险：DeepSeek 的 SSE 正常帧若携带 message 字段（例如 code 为 0、message 为 ok 之类的包装），会被判 fatal，正常流被中断并上报鉴权计费类错误。fatal 的语义是立即停手，不重试。

证据强度：代码逻辑确定，但未见真实帧样本。logs/cdp-chat-capture 有 20 份抓包（R4 引用），需确认正常帧是否带 message。带则 High，不带则降 Medium。

### R4.5-N3（Medium-High）tryFixEscapedQuotes 只修反斜杠丢失，不修换行丢失

streaming-tool-parser 的 make 里，JSON 解析失败时调 tryFixEscapedQuotes，该函数遍历 body，在字符串内遇到裸引号时补反斜杠。它处理的是引号。

但同一句注释承认的根因是 SSE 提取链路退化，同一链路也会把转义换行退化成字符 n 或真实换行：
- 退化成字符 n：JSON 仍合法，内容错误，少一个换行。
- 退化成真实换行：JSON 非法，走 __invalid_json 分支，模型能看到错误。

第一种是静默数据损坏：解析成功，参数看起来正常，但写进文件的内容少换行。工具调用显示成功，结果不对。local_file_write 写多行文件最容易触发。

修法：在 tryFixEscapedQuotes 里同时处理字符串内的裸换行，按 JSON 规范补转义。这是确定性修复，不会误伤，因为合法 JSON 字符串里不可能有裸换行。

### R4.5-N4（Medium）两套流解析器并存，哪条现役注释自相矛盾

deepseek-sse-frame-decoder 的文件头自己写了与 SseTextStreamExtractor 的区别，说后者按单换行切分、同时负责显示文本提取和工具解析、转义易损，说前者 parsed 独立于显示文本。

但 sse-text-extractor 的注释说它同时负责显示文本提取和工具解析。两处自相矛盾，读代码的人无法判断工具解析走的是显示文本到 parser，还是 frame.parsed 到 parser。

若走前者，N3 的转义退化就发生在这条链上，frame decoder 的优势用不上。若走后者，两条链独立，更健康。

这是文档缺陷，但会直接误导后续修复者。修法：在拦截器里注明现役路径。

### R4.5-N5（Medium）tailHasUnclosedKnownToolTag 前缀匹配过宽

tailHasUnclosedKnownToolTag 用 startsWith 判断。于是 tail 为半截标签名时 prefix 可能只有一个字母，shell_exec 以 s 开头就判 true。

而半截标签名完全可能是正文里的 span 标签、summary 标签这类 HTML 或 markdown 示例。

后果：流正常结束但尾部恰好是这类文本时，hasUnclosedToolTag 报 true。若上层据此判流被截断、不算完成，会触发续跑、重复请求。与 R4-H4 同族。

修法：prefix 长度达阈值（如 3）才做前缀匹配，或要求 tail 之后还有更多字符的迹象。

### R4.5-N6（Medium）PENDING_ACTION_RE 不含「我来」，加个句号就逃过 nudge

continuation-prompt 的 shouldNudge 决策链依次是：含 task_complete 返回 false、空文本返回 true、末尾含代码围栏返回 false、hasPendingActionAtTail 返回 true、完成标记命中返回 false、句末标点命中返回 false、默认 true。

PENDING_ACTION_RE 的中文动作词列表是：将 会 想 要 先 让 再 直接 现在 继续 尝试 开始 需要 还需要 仍需 打算 计划 马上 随后 稍后 先去 先来 接下来。没有单独的「来」。

所以「我来创建这个文件。」这句：我来不匹配 PENDING_ACTION，完成标记也不匹配，以句号结尾命中句末标点，返回 false，不 nudge。模型说了要做但没做，对话停住。

同样漏的还有我这就、我马上帮你、我现在给你（现在在列表里但后面必须跟动作词，帮你中的帮不在动作列表）。

这是正则启发式的固有局限，但我来是极高频表述。修法：列表加 来 和 这就，并放宽为你或帮加你加动词的分支。

证据强度：正则匹配确定，可单测。真机上模型是否常用这种句式未见统计，按对话停住症状反推是合理怀疑对象。

### R4.5-N7（Medium）SSE 丢帧零可观测性

见 Q2。三处 catch 全部静默。

修法：给 DeepSeekSseFrameDecoder 加 onParseFailure 回调，或类内累计 parseFailureCount，由拦截器写进 trace。成本极低，收益是断流取证第一次有帧级信号。

### R4.5-N8（Medium）tool-call-dedupe 的签名无 session 维度

claimSignature 的签名只有工具名加参数，没有 sessionId。若拦截器持有一个全局实例跨会话复用，则会话 A 调 shell_exec 后，会话 B 同一回合调同一调用会被判重复，B 的调用被跳过永不执行。

continuation-prompt 的 PendingResult 有 sessionId 字段，注释写明该结果产生时归属的 chat_session_id，说明系统承认并发会话，但 dedupe 没跟上。

这与 R4-H3（continuationRetryPending 是模块级单例，而 QD-R7 注释已把 streamSawDone 改成按流归属）是完全同一失效模式：承认并发、改造了一部分状态、漏了另一个。

## 四、复核掉的候选误报（2 条）

1. scanFrom 等于 buffer 长度减 3 回退不足？不成立。分隔符最长 4 字符，回退 3 足以覆盖尾部残留半个分隔符的所有情况，逐一推演三种残留后 scanFrom 都落在前缀起点或其之前，不漏匹配。R2 对 dpp 同名实现的判断一致。

2. createFrame 只按换行切，CRLF 行尾会污染 data？不成立。key 用 trim，value 用 trimStart，即使 value 尾部带回车，JSON 解析也容忍尾部空白。

## 六、方法论收获

注释写对了设计、实现没跟上，是本项目的高频缺陷类型。

本轮 N1 是典型：签名声明 hasToolCall，注释写提取工具调用，实现里该变量初始化后从未赋值。R4-H1（loopDepth 递增两次，注释说重试不该吃预算但实现照样吃）、R4-H3（QD-R7 注释承认并发、改了 3 个状态漏 1 个）是同一类型。

共同点：注释描述意图，代码执行现实，两者在同一次提交里就分叉了。

检测方法：对每个导出的类型、字段、返回值，逐个确认声明的东西是否真被产生。这比读逻辑更快命中，因为声明与实现是否一致是二元判断，不需要理解业务语义。
