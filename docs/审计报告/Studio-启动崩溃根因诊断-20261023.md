## 2. sidecar 是什么、怎么起的

在 `src-tauri/src/sidecar.rs:177-191` 的 `spawn_child()`：

```rust
let mut cmd = if cfg!(windows) {
    let mut c = Command::new("cmd");
    c.args(["/c", "npx", "tsx", "src/api/main.ts"]);   // 相对路径
    c
} else { ... Command::new("npx").args(["tsx", "src/api/main.ts"]) };
cmd.current_dir(&self.project_root)                     // 工作目录 = 项目根
   .stdout(Stdio::inherit())                            // 直接继承父进程的 stdout
   .stderr(Stdio::inherit());                           // 所以你才在同一个控制台看到子进程日志
```

- 命令行：`cmd /c npx tsx src/api/main.ts`（**相对路径**，因此必须靠 `current_dir` 指向项目根）。
- 工作目录：`project_root`，来自 `main.rs:475-480` = `exe_dir/../../..`，对 debug 产物即 `E:\NAS\deepseek-studio`；解析失败时硬编码回退到 `"E:/NAS/deepseek-studio"`。
- 环境变量：不改，全量继承父进程。
- stdout/stderr：`inherit`，不落文件、不解析。**这就是崩溃原文在仓库/应用日志里找不到的原因**——子进程的输出只在启动它的那个控制台里。
- 健康判据：`probe_health()`（`sidecar.rs:76-104`）裸 TCP 连 `127.0.0.1:8760` 并发 `GET /healthz`，要求响应以 `HTTP/1.1 200` 开头；端点定义在 `src/api/server.ts:282`。契约常量在 `sidecar.rs:20-22`（host 127.0.0.1、port 8760、path `/healthz`）。
- 重启预算：`sidecar.rs:25-30`：`STARTUP_HEALTH_TIMEOUT = 10s`、`RESTART_DELAY = 2s`、`MAX_RESTARTS = 5`。
- 打包：`tauri.conf.json` 没有 `externalBin`/`resources`，sidecar 不随包分发，运行期完全依赖项目根下的 `src/` 与 `node_modules/`。**这意味着当前设计只在「从仓库工作树跑」时成立，打出来的安装包必然起不了宿主。**
- 另有一处重复：`tauri.conf.json` 的 `beforeDevCommand = "npm run build:inject && npm run start"`，即 `npm run tauri dev` 会先自己起一个 `tsx src/api/main.ts`（`package.json` 的 `start`），supervisor 再起第二个 —— 端口只有一个，第二个必撞 EADDRINUSE。这是历史 66 次 `ExitStatus(2)` 的**候选**解释（未验证，见 §7）。

## 3. 崩溃根因：宿主「起得来，但 10 秒内来不及监听」

### 3.1 关键结论

宿主进程本身**没有崩溃**，它只是在 10 秒窗口内还没监听 8760；supervisor 按超时把它整棵杀掉，再重试，每次都从冷启动重来，于是永远追不上。

复现命令与 supervisor 完全一致：`cmd /c npx tsx src/api/main.ts`，cwd=`E:\NAS\deepseek-studio`，输出重定向到 `%TEMP%\studio-diag\*`。

### 3.3 时间花在哪：npx 包装层，不是应用自身

同一 cwd（仓库根）下的分项计时：

| 项 | 耗时 |
| --- | --- |
| `node -e 0` | 734 ms |
| `node node_modules\tsx\dist\cli.mjs --version` | 2 796 ms |
| `cmd /c npx --version` | 4 900 ms |
| `npx tsx --version`（一次冷启动极值） | **61 914 ms** |
| `npx tsx <临时 hello.ts>` | **16 549 ms** |
| `node node_modules\tsx\dist\cli.mjs <临时 hello.ts>` | 1 753 ms |
| 动态 import 整条 `src/host/desktop-host.ts` 模块图 | 1 524 ms |

进程链实测是三层 node：

```
node.exe ...\npm\bin\npx-cli.js tsx src/api/main.ts
node.exe "E:\NAS\deepseek-studio\node_modules\.bin\..\tsx\dist\cli.mjs" src/api/main.ts
node.exe --require ...\tsx\dist\preflight.cjs --import file:///.../tsx/dist/loader.mjs src/api/main.ts
```

也就是说：`npx`（要启动完整 npm CLI）→ `tsx` CLI → 真正跑应用的 node。光「hello world」级别，npx 这层就吃掉 14.8 秒；而应用自己的模块图加载只要 1.5 秒。**去掉 npx 后总就绪时间是 4.6 秒**，落在 10 秒预算内。

### 3.4 因果链（结论）

1. supervisor 用 `cmd /c npx tsx` 拉起宿主（`sidecar.rs:178-186`）；
2. npx 包装层使冷启动就绪时间在 12.7–41.2 秒之间（本轮 3 次实测）；
3. supervisor 只等 10 秒（`sidecar.rs:25`），超时即 `force_kill_process_tree` 并记 `health timeout after 10s`（`sidecar.rs:296-317`）；
4. 被杀掉的正是那个已经正确启动、只差几秒的宿主；下一轮从冷启动重来，冷缓存 + Defender 扫描使每轮都不可能在 10 秒内完成；
5. 5 次重试耗尽 → `GaveUp`（`sidecar.rs:376-385`）→ `[sidecar] gave up after 6 crashes`，应用继续跑但**宿主永久缺席**。

### 3.5 两个衍生缺陷（本轮直接观测到，会放大故障）

1. **杀树不干净**。`force_kill_process_tree`（`sidecar.rs:106-136`）对 `cmd` 的 PID 执行 `taskkill /PID <cmd> /T /F`。我在复现后用同样的方式清理，`REMAINING=1`、复查时仍有 3 个 node.exe 存活（`npx-cli.js` / `cli.mjs` / `loader` 各一）。残留进程会继续占着 8760。
2. **残留 → 下一轮变成确定性失败**。我第二次复现时，新宿主在 23.1 秒打出：

   ```
   [deepseek-studio] 端口冲突（EADDRINUSE）：无法绑定本地 API。
     当前配置：host=127.0.0.1 port=8760
   ```

   对应 `src/api/main.ts:245-250` 的 `process.exit(2)`，而 supervisor 把它映射成 `StartupFailed`（`sidecar.rs:349-358`）——不是崩溃而是「确定性失败」，不再重试。这解释了 crash.jsonl 里 66 条 `ExitStatus(2)`。

## 4. bot-windows.json 解析失败根因

**与 sidecar 崩溃无关，是独立故障。**

代码：`main.rs:222-227` 把路径定成 `dirs::config_dir()/deepseek-studio/bot-windows.json`；`main.rs:229-239` 读成功但 `serde_json::from_str` 失败就打 `WARN ... using empty` 并回退到空配置。

现场两个同名文件，代码读的那一个恰好是坏的：

| 位置 | 大小 | 字节 | 判定 |
| --- | --- | --- | --- |
| `C:\Users\lidicn\AppData\Roaming\deepseek-studio\bot-windows.json`（**代码实际读的**） | 16 B | `ef bb bf 7b 22 62 6f 74 73 22 3a 5b 5d 7d 0d 0a` | UTF-8 **BOM** + `{"bots":[]}` + CRLF；mtime 2026-10-17 13:30:16 |
| `C:\Users\lidicn\.config\deepseek-studio\bot-windows.json`（注释里写的位置） | 201 B | 无 BOM，含 `frontend-expert`、`backend-expert` 两条 | 合法 JSON；mtime 2026-10-14 20:20:57 |

两个独立缺陷叠加：

1. **目录错位**。`main.rs:90` 的注释写的是 `~/.config/deepseek-studio/bot-windows.json`，`:124-125` 甚至明确承认「config.json 在 home_dir/.config 下，与 bot-windows.json 在 config_dir/AppData\Roaming 下不是同一目录」。而真正有内容的配置躺在 `~/.config` 里，代码不看那里。
2. **BOM**。AppData 那份内容除 BOM 外是合法 JSON，但 serde_json 的 `from_str` 不接受前导 U+FEFF（`read_to_string` 会把 BOM 保留成字符）。所以即便不提目录问题，这个文件也永远解析失败。

消费方与后果：`main.rs:559` 用它的 `bots` 生成 bot 窗口计划（`plan_bot_windows`，`main.rs:313+`）。解析失败 → `bots` 为空 → **一个 bot 窗口都不建**，两个隔离 profile（`frontend-expert`/`backend-expert`）失效；`%APPDATA%\deepseek-studio\profiles\` 下那两个 EBWebView 目录还留在磁盘上（10-17 13:26），是它曾经生效过的痕迹。主窗口不受影响，所以这个故障只表现为「静默少了两个窗口」。BOM 是谁写进去的未确认（PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会加 BOM，仅为可能）。

## 5. inject 加载两次

**正常行为，不是重复加载，也不与崩溃同源。**

`load_init_script()` 每次调用都会打印一行 `[studio] inject loaded from: ...`（`main.rs:37-41`）。启动过程中它被调用两次：

1. `main.rs:523`：给主窗口拼注入脚本；
2. `main.rs:549-553`：给 bot 窗口准备 `base_script`——这段在 `for` 循环之外**无条件求值**，即使 bot 列表为空（本次正是空）也会执行。

时间线也对得上：第二行 `inject loaded` 紧跟 `WARN: bot-windows.json parse failed` 之前，正是 `main.rs:549` → `main.rs:559`（读配置）的顺序。中间夹着的 crash #1–#4 是 supervisor 线程的异步输出，与窗口创建无因果关系。

结论：两行日志只说明注入脚本被读了两次、拼了两遍字符串，注入本身只有一次（主窗口一次）。若要消除误导，只需把 `main.rs:549` 改为惰性求值（例如在循环内首次使用时加载）。

## 6. stream-incomplete 与崩溃的关系

**这是另一条独立故障，不要和 sidecar 崩溃合并成一个结论。**

页面那行「模型回复未完整接收（连接中断），已自动重试 2 次仍失败。请检查网络后手动重试。／stream-incomplete」出自注入层：

- 触发条件：`main-world-interceptor.ts:1133` `if (!loopState.streamSawDone)`——整轮 SSE 结束时**没看到完成哨兵**。
- 哨兵定义：`deepseek-sse-frame-decoder.ts:134-145`，即 `{"p":"response/status","o":"SET","v":"FINISHED"}` 或 `quasi_status=FINISHED`；该文件 `:123-124` 明确记录 **DeepSeek 从不下发 `data: [DONE]`**，所以旧式 DONE 判定会误判。
- 重发预算：`main-world-interceptor.ts:170` `FIRST_ATTEMPT_MAX_RETRIES = 2`；耗尽后由 `escalateFirstAttemptFailure`（`:1365-1397`）打印 `:1381` 那句「已自动重试 N 次仍失败」，与你截图完全一致（N=2）。
- 它是否读宿主的存活状态：**否**。这条判定链只依赖 SSE 帧解析与 HTTP 状态（`:1137` 对 401/403 等 fatal 另有分流），不查询 8760。宿主缺席走的是另一条路——`forward()`（`:1169-1245`）把工具调用投给 `sender`，失败会体现在工具卡片/工具错误上，不会显示成 stream-incomplete。

可直接区分的判据（建议按顺序做）：

1. **看是否只发生在带工具调用的轮次**。若纯问答（如「百度搭子模型与活动解答」这类无工具轮次）也复现同一句，就是页面↔DeepSeek 的流被截断，与宿主无关。
2. **修好 supervisor 后再看**。宿主就绪后如果 stream-incomplete 照旧，第二条故障成立；如果消失，说明我当时对注入层的读法有遗漏。
3. **读现场 trace**。注入层把每轮结果写进 `localStorage` 的 `ds-studio-traces`（`src/inject/trace-store.ts`，key `ds-studio-traces`，最多 50 条）。在 Studio 窗口里看 `stopReason`：`first-attempt-retry-out` 表示三连截断，`truncated-tool-tag` 表示工具标签被截断，两者指向的修复面不同。
4. **换宿主环境对照**。用普通浏览器打开 chat.deepseek.com 跑同一句：浏览器正常、Studio WebView 不正常 → 指向 WebView2 的网络栈/注入层；两边都不正常 → 指向链路层。

本轮能提供的环境侧证据（用于排除猜测）：`api.deepseek.com` DNS 解析正常（14.29.51.120 / 14.116.174.67），TCP 443 握手 28 ms，`GET /models` 242 ms 返回 401（用的是空 key，符合预期）；无 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 环境变量；系统 `ProxyEnable=0`（`ProxyServer` 里残留 `127.0.0.1:9000` 但未启用）；7890/1080/10809 等常见代理端口无监听。**因此「本机 MITM 代理截断 SSE」这一解释目前不成立**，剩下的候选是 WebView2 网络栈与链路层抖动，需要上面第 1–4 条实测来分。

## 7. 修复方案

### P0-1 去掉 npx 包装层（本条即可修掉你看到的崩溃）

改动面：`src-tauri/src/sidecar.rs:177-191` `spawn_child()`。

```rust
// Windows：直接调本地 tsx CLI，绕过 npx/npm CLI
let mut c = Command::new("node");
c.args(["./node_modules/tsx/dist/cli.mjs", "src/api/main.ts"]);
```

验证判据：启动应用后 (a) 控制台**不再出现** `[sidecar] crash #N`；(b) `curl http://127.0.0.1:8760/healthz` 在 5 秒内返回 200（本轮实测 4.6 s）；(c) `crash.jsonl` 行数不再增长。
回退：恢复 `cmd /c npx tsx ...` 两行即可，不影响其它逻辑。

### P0-2 把启动健康预算从 10 s 提到 60 s（纵深防御）

改动面：`src-tauri/src/sidecar.rs:25`。理由：本轮实测冷启动方差 12.7–41.2 秒（NAS 盘 + 杀软扫描 + npx 冷缓存），10 秒对这台机器过紧。若单独用这一条，启动仍要 20–40 秒才可用，所以要和 P0-1 一起做（P0-1 后正常路径 ~5 s，预算只作兜底）。
验证判据：人为用旧命令（含 npx）跑一次，观察不再出现 health timeout；确认 `RESTART_DELAY`/`MAX_RESTARTS` 未被顺带改掉。
