## 一、诊断部分：全部确证，且更严重

设计第 0 节的 5 条判断，我逐条实测：

### 1.1 ✅ "所有 UI 是注入脚本手写 DOM，无统一渲染边界"

确证。`src/ui/` 15 个文件 + `src/inject/` 26 个文件 + `src/desktop/` 3 个，共 **44 个前端文件**，全部手写 DOM。无框架、无状态管理、无组件基类。

### 1.2 ✅ "样式是全局 `<style>`，不是真正的 Shadow DOM" —— **比描述更严重**

```
attachShadow  命中: 0
shadowRoot    命中: 0
createElement('style') 命中: 8
```

**更严重的地方**：项目里有一个函数叫 `createShadowContainer`，它**根本不创建 Shadow DOM**：

```ts
// src/ui/studio-ui-core.ts:90
export function createShadowContainer(id: string): { container: HTMLElement; shadow: HTMLElement } {
  const container = document.createElement('div');
  container.id = id;
  container.className = 'studio-ui-root';
  container.style.cssText = 'display:block;pointer-events:none;';
  return { container, shadow: container };   // ← shadow 就是 container 自身
}
```

另有 `injectStyles(_shadow: HTMLElement, css: string)` —— **`_shadow` 参数完全未使用**（下划线前缀即未使用标记），样式全部追加到 `document.head`。

**这意味着**：Shadow DOM 曾经被规划过、函数名都起好了，但从未实现。后续任何按名字以为"已经有 Shadow DOM"的开发都会踩空。**评审建议把这条从"样式问题"升级为"命名与实际不符的陷阱"。**

### 1.3 ✅ "聊天 overlay 默认用不透明白底覆盖原生消息区"

确证：`studio-chat-room.ts` 有 `background: #ffffff`（:647）、`#fff`（:700）、`#f8f9fc`（:670）。
另有 `position: fixed; inset: 0; z-index: 2147483647` 出现在 `account-block.ts` 与 `consent.ts`。

⚠️ **但其中一个是刻意设计，见 §三.3。**

### 1.4 ✅ "输入栏和侧栏依赖几何扫描、混淆 class 和 MutationObserver"

确证：`MutationObserver` **14 处**、`getBoundingClientRect` **9 处**。

### 1.5 ✅ "Markdown 直接 innerHTML，没有 sanitizer"

确证，且源码注释写得很直白：

```
src/inject/markdown.ts:9-11
 * marked 的 sanitize 默认关闭——输入文本来自模型输出，已在 chat UI 内
 * 不引入 DOMPurify 以减依赖；如需严格 XSS 防护后续再加。
```

`innerHTML` 全项目 **27 处**。

## 二、🔴 与代码实况不符的关键假设（必须修订）

### 2.1 【P0】"React 18 + Vite" —— 当前构建体系里两者都不存在

```
package.json dependencies:  marked, node-cron          ← 只有 2 个运行时依赖
package.json devDependencies: esbuild, tsx, typescript, vitest, jsdom, ws ...
scripts.build: node esbuild.inject.mjs                  ← 无 Vite
```

精确匹配 `"react"` / `"react-dom"` / `"vite"`：**0 处**。
（`vitest` 含 "vite" 子串，容易误判，我做了精确匹配确认。）

当前构建是 **esbuild 单文件 IIFE 打包**，两个入口：

| 入口 | 产物 | 格式 |
|---|---|---|
| `src/desktop/entry.ts` | `src-tauri/inject/entry.js`（392 KB） | iife / es2020 / browser |
| `src/ui/agent-panel.ts` | `dist/agent-panel.js`（24 KB） | iife / es2020 / browser |

**这不是"加个依赖"就能改的事**，涉及：
- 引入 Vite 与现有 `esbuild.inject.mjs` 的关系（替换还是并存）
- Tauri `beforeDevCommand` / `beforeBuildCommand` 调用链改造
- 注入脚本从"单文件 IIFE"变成"Vite 产物"后的加载方式
- 现有 115 个测试文件与 `vitest` 的配置兼容

**设计第 6 节直接写"推荐栈：React 18 + Vite"，没有一句提到这些迁移成本。** 这是本评审认为最需要修订的地方。

### 2.2 【P0】设计遗漏了已存在的独立工作台底座

**项目里已经有一个非注入的独立页面**：

```
src/ui/agent.html      (2.4 KB，独立 HTML 页面)
src/ui/agent.css
src/ui/agent-panel.ts  → dist/agent-panel.js（经 /agent.js 服务）
```

`agent.html` 的实际结构：

```html
<header class="topbar">
  <div class="brand">DS · Studio 智能体</div>
  <div class="workspace" title="打开的目录即智能体的权限边界">
    <span class="ws-path">未选择工作区</span>
    <button id="btn-open-folder">打开文件夹</button>
  </div>
```

**它已经有顶栏、工作区选择器、权限边界表达** —— 这正是设计第 2.3 节 Workbench Top Bar 的核心内容。

而设计全文把 UI 描述为"注入脚本"，**完全没有提到这个已经存在的独立面**。

**这是本评审最重要的落地建议**：

> **Workbench 模式应当基于 `agent.html` 这个独立页面演进，而不是在注入层里长出来。**

理由：
1. 注入层受宿主页面约束（DOM 冲突、样式污染、宿主改版即退化）——设计自己第 0 节第 4 条就是这个抱怨
2. 独立页面不受这些约束，可以安全引入 React / Monaco / xterm.js
3. 底座已经存在，不用从零搭

### 2.3 【P0】Monaco Editor + xterm.js 放进注入脚本不可行

设计第 6.1 节推荐 Monaco Editor（代码/diff）与 xterm.js（终端）。

- Monaco 体积量级 **MB 级**，且依赖 web worker 与 `import.meta.url`
- 当前注入产物是 **392 KB 单文件 IIFE**，`platform: 'browser'`, `target: 'es2020'`
- 注入脚本运行在 **chat.deepseek.com 的页面主世界**，塞进 MB 级运行时会显著拖慢宿主页面

**这些重组件只适合放在独立页面（`agent.html`），不适合注入层。**

### 2.4 【P1】"统一 CSS 注入，避免重复追加" —— 已部分完成，非从零开始

设计 P1 把这条列为待做。实测 7 处 `<style>` 注入点：

| 文件 | 去重守卫 |
|---|---|
| `inject/step-flow-ui.ts` | ✅ `getElementById(STEP_FLOW_STYLE_ID)` |
| `inject/tool-card-dom.ts` | ✅ |
| `ui/account-block.ts` | ✅ |
| `ui/consent.ts` | ✅ |
| `inject/tool-card-ui.ts:209` | ❌ 无 |
| `ui/studio-chat-ui.ts:41` | ❌ 无 |
| `ui/studio-ui-core.ts:103` | ❌ 无 |

**7 处中已有 4 处正确去重**，剩下 3 处需要补。这条应该从"建立"改成"补齐 3 处 + 抽公共函数"。

### 2.5 【P2】主色 `#4D6BFE` 已在用，但现有实现用了渐变

```
src/ui/studio-chat-room.ts:608
background: linear-gradient(135deg, #4D6BFE, #3a55d8);
```

设计第 5.2 节定主色 `#4D6BFE`（与现有一致 ✅），但第 5.2 节同时写"禁止：到处渐变"。

**现有代码就在用渐变**，这条禁止项需要一个过渡说明，否则会与存量代码直接冲突。

### 2.6 【P2】`entry.js` 是运行时读取，不是 `include_str!` 编译时嵌入

```
src-tauri/src/main.rs:15
/// 运行时读取注入脚本（而非 include_str! 编译时嵌入）。
main.rs:24-34  候选路径 inject/entry.js、src-tauri/inject/entry.js、exe_dir/inject/entry.js
```

设计 P0 写"确认 `src-tauri/inject/entry.js` … 不被覆盖"，措辞建议改为"确认运行时注入脚本路径解析正确"，避免后来者按 `include_str!` 理解。

## 三、🟡 会误伤安全机制的验收条款

### 3.1 【必须修订】"登录页和二维码不被 Studio 遮挡" 与防封号铁律冲突

`src/ui/account-block.ts` 的注释：

```
/**
 * 账号身份锁阻塞覆盖层（v0.31，页侧）
 * 宿主检测到同账号双窗口 … 令本页 fail-closed：渲染全屏不可关闭的红底覆盖层，
 * 挡住一切 DeepSeek 交互，直到用户关闭本窗口或切换账号。
 *
 * 这是防封号铁律「1 槽位 : 1 账号 : 1 窗口」的执行手段 … 
 * 覆盖层刻意**无 Esc/点外关闭**（fail-closed，只能换号或关窗）。
 */
```

```css
position: fixed; inset: 0; z-index: 2147483647;
background: rgba(180, 24, 24, 0.97);
```

**这是一个刻意的全屏、不透明、不可关闭覆盖层**，是安全机制而非设计缺陷。

设计 P0 验收标准"登录页和二维码不被 Studio 遮挡"、以及第 6.2 节"不推荐：大量全屏纯白 overlay"——**如果机械执行，会把这个 fail-closed 机制改成可绕过，直接违反防封号铁律。**

**修订建议**：验收条款加例外：

> 除 `account-block`（账号身份锁，fail-closed 强制覆盖）外，登录页与二维码不得被遮挡。

同理第 6.2 节的"不推荐全屏 overlay"应限定为"不推荐**用于常规 UI 呈现**的全屏 overlay"。

### 3.2 【提醒】`agent.html` 里的 token 注入

```html
<script>window.__STUDIO_TOKEN__ = "__STUDIO_API_TOKEN__";</script>
```

这是独立页面（经 localhost 服务），与注入到 chat.deepseek.com 主世界不同，风险低一个量级。但既然要重构，建议顺手改为运行时从宿主接口获取，而不是 HTML 模板替换。

### 3.3 【提醒】残留的陈旧构建产物

```
src/ui/agent-panel.ts        修改于 2026-10-18 23:33
dist/agent-panel.js          构建于 2026-10-17 23:45   ← 落后约 24 小时
```

`dist/` 已被 `.gitignore` 忽略 ✅（这点比 pp 做得好），但**陈旧产物会导致"改了代码没生效"的假象**。这正是我在 pp 第十三轮踩过的坑（E2E 测的是仓库里的旧产物）。

**建议**：`gate` 或 `build` 步骤加"源码比产物新则强制重建"。

## 六、正面评价（这些判断很准，建议保留）

1. **第 0 节的 5 条诊断全部成立** —— 不是"配色不好看"而是架构边界缺失，这个定性是对的。
2. **Focus / Workbench 双模式** —— 精准命中"普通聊天要看原生页 vs 项目开发要完整工作台"的真实矛盾，比继续堆 overlay 高一个维度。
3. **第 7/8 节对 cuckoo-code 与 Harness 的取舍** —— 区分"借鉴原则"与"搬运代码"，并点出 GPL-3.0 许可耦合风险，判断专业。
4. **第 4.4 节"不要用彩色气泡区分 Agent"** —— 与我在审计中记录的多 Bot 可辨识性问题一致。
5. **第 11 节"宿主 DOM 改版时，UI 降级而不是白屏"** —— 这是对当前 MutationObserver 脆弱性的正确反制目标。
6. **§6.3 "自研的边界"** —— 明确"自研 ≠ 所有控件从零手写"，避免了另一个极端。

## 七、给落地顺序的建议（基于实测）

设计第 12 节说"先做 Focus，再做 Workbench；先做基础层，再做任务组件"。**方向对，但结合代码实况建议调整**：

| 序 | 动作 | 理由 |
|---|---|---|
| **0** | **先与上游对齐**：确认第八/十轮改造是否要恢复 | 12 条安全红线当前失效，重构叠加在这个状态上会互相掩盖 |
| **0.5** | **冻结基线 + 记录 20 条红灯处置** | 设计 P0 已有，但需明确"哪些修、哪些登记" |
| **1** | 设计 token（CSS 变量）+ 补齐 3 处 CSS 去重 + z-index token | 成本最低、收益最直接，且**不引入框架即可做** |
| **2** | **真 Shadow DOM**（修 `createShadowContainer`） | 与其他项解耦，可独立验收 |
| **3** | Markdown sanitizer | 独立、高收益、体积可控（DOMPurify ~20KB） |
| **4** | **Workbench 在 `agent.html` 上演进**，此时再评估引入 React | 独立页面引入框架的约束远小于注入层 |
| **5** | Focus 模式在注入层做轻量增强 | 注入层保持轻量，避免宿主性能退化 |
| **6** | 重组件（Monaco/xterm）只放独立页 | — |

**核心原则：注入层保持轻量，重的东西放独立页。** 这是设计文档目前没有明确区分的。
