## 0. 补充结论

已有两份评审已经指出 React/Vite 与单文件 IIFE 不匹配、权限词表冲突、Approval 映射、Plan gate 无调用方、diff 后端粒度不足、sanitizer 缺失等问题。本补充评审不重复这些结论，只裁决它们尚未回答或判断需要修正的部分。

本轮的五个新增结论：

1. **`agent.html` 不是“现成 Workbench 底座”，只是可达的 MVP 骨架。** 页面、`/agent-ws` 和共享宿主状态都存在，但 Tauri 当前没有创建任何加载 `/agent` 的窗口；页面本身也只有顶栏、消息流和 composer，没有项目树、会话、Inspector、diff、审批、产物和恢复能力。
2. **Workbench 应该走独立页面，Focus 应该留在注入层。** 这是对“注入层保持轻量、重组件放独立页”的正确落地方式，但不能把 `agent.html` 现状描述成“已经完成一半”。
3. **`/agent-ws` 与 `/studio` 共享 bot/AgentLoop/策略/工作区，但不共享完整 UI 事件模型。** `AgentLoopEvent` 只有 `user / assistant / tool / status / error / done` 六类，工具卡片拿不到工具名、参数、结果、退出码和 callId；直接照设计稿做 ToolCallCard 会造出没有数据源的假组件。
4. **当前红灯基线是 3 条，不是 20 条。** 本轮实测 1197 个测试中 3 个失败：`desktop-entry.test.ts` 的 `location.pathname` stub 缺失，以及 `tool-authority.test.ts` / `smoke.test.ts` 对已消费 grant 期望 `consumed`、实际得到 `not-found`。这三条必须登记为开工基线，不能写成“20 条红灯”。
5. **本期不应把 PWA 或手机远程控制塞进前端重构。** 当前 `/agent` 使用 HTML 内嵌 API token，且 WS 通道没有面向移动端的配对、撤销、设备管理和 TLS 方案。把它塞进本期会把 UI 重构变成远程控制安全项目。

## 1. 对“独立 Workbench 底座”的复核

### 1.1 成立的部分

`src/ui/agent.html`、`src/ui/agent.css`、`src/ui/agent-panel.ts` 确实存在，`/agent`、`/agent.js`、`/agent.css` 也确实由 `src/api/server.ts` 提供。`/agent-ws` 由 `src/host/agent-channel.ts` 创建，并接到 `desktop-host` 的 `bots`、`onAgentEvent`、`policyMode`、`workspaceRoot` 上。

因此，独立页面不是另起一套智能体。它和主窗口共享同一个宿主进程、同一个 bot 注册表和同一套策略状态。这一点支持“Workbench 放独立页”的方向。

### 1.2 需要修正的部分

**第一，Tauri 当前没有打开 `/agent` 的窗口。** `src-tauri/src/main.rs` 只创建两类窗口：

- 主窗口：`WebviewUrl::External(chat.deepseek.com)`；
- bot 窗口：同样加载 `chat.deepseek.com`，只用于独立登录态和工具执行。

全文件没有 `http://127.0.0.1:8760/agent` 或 `WebviewUrl::External(.../agent)`。所以现状是“后端路由存在、页面可被浏览器访问、Tauri 没有入口”，不是“已经有一个现成工作台窗口”。

**第二，`agent.html` 只是 MVP 骨架。** 它当前只有：

- 顶栏：品牌、工作区、三档权限、连接状态；
- 中间：线性消息流；
- 底部：textarea、发送、停止。

它没有左栏、右栏 Inspector、任务列表、会话恢复、文件树、diff、审批卡、产物卡、审计、终端和预览。把它称为“Workbench 底座”会误导排期。

**第三，`/agent` 的 token 传递方式不适合直接扩展为远程入口。** `server.ts` 在返回 HTML 时把 `__STUDIO_API_TOKEN__` 替换成真实 API token，页面再用 query 参数连 `/agent-ws`。这在“本机回环 + 本机进程本就能读配置”的威胁模型下可接受，但不能直接搬到手机或公网。

### 1.3 裁决

采用以下分工：

| 层 | 职责 | 技术边界 |
|---|---|---|
| 注入层 | Focus 模式、宿主页面内轻量增强、审批浮层、状态 chip | 继续走单文件 IIFE，不引入 React、Monaco、xterm |
| 独立页 | Workbench、三栏布局、diff、产物、任务历史、设置 | 可独立演进；是否引入 React 由单独 ADR 决定 |
| 宿主 | bot、AgentLoop、策略、工作区、授权、审计 | 两种 UI 共用，不复制业务状态 |

**禁止**把 Workbench 的全部组件塞回注入层，也**禁止**把独立页描述成“已经存在的工作台”而不计入新建工作量。

## 2. 事件模型缺口：工具卡片没有数据源

### 2.1 事实

`src/shared/agent-loop-event.ts` 的 `AgentEventType` 只有：

```ts
'user' | 'assistant' | 'tool' | 'status' | 'error' | 'done'
```

`tool` 事件只带：

```ts
{ type: 'tool'; text?: string; step?: number; toolCalls?: number; botId?: string; roomId?: string }
```

`src/host/agent-loop.ts` 在工具执行后只发“工具执行完成（N 次调用）”，不带工具名、参数、结果、错误码、退出码、耗时或 callId。

### 2.2 影响

设计稿要求 ToolCallCard 区分文件读取、文件修改、Shell、搜索、Web、MCP、测试，并显示状态、参数、结果和 diff 入口。当前事件流不足以支撑其中任何一项的真实数据，只能显示“发生了 N 次工具调用”。

如果施工时直接在 UI 侧按工具名 `switch`，会出现两种坏结果：

- 写死七类工具，未知工具直接空白或崩溃；
- UI 自己猜工具类型，和宿主审计记录不一致。

### 2.3 裁决

本期必须先做一个**最小结构化工具事件**，再谈 ToolCallCard。建议新增独立事件，不破坏旧事件：

```ts
export interface ToolRunEvent {
  type: 'tool-run';
  runId: string;
  tool: string;
  phase: 'started' | 'succeeded' | 'failed' | 'denied' | 'cancelled';
  step?: number;
  summary?: string;
  durationMs?: number;
  exitCode?: number | null;
  errorCode?: string;
  artifactPaths?: string[];
  botId?: string;
  roomId?: string;
}
```

约束：

- 不把完整参数、完整 stdout/stderr 塞进 WS 广播；只发摘要和可展开引用。
- `runId` 必须能关联审计记录；没有 `runId` 的卡片不允许显示“可回滚”。
- 未知 `tool` 必须落到通用卡片，显示原始 `tool` 字符串、phase、摘要和错误码。
- 在结构化事件落地前，ToolCallCard 只做“计数 + 通用摘要”，不假装能分类。

这是本期 UI 施工的**前置契约**。没有它，P5 的工具卡片验收无法成立。

## 3. 权限与审批的补充裁决

### 3.1 三套词表必须收敛

当前至少存在：

- 引擎：`workspace | ask | auto | full`（`src/host/policy.ts`）；
- 面板暴露：`workspace | auto | full`（`PANEL_POLICY_MODES`）；
- UI 状态：`full | auto | ask`（`src/ui/studio-ui-core.ts`）。

补充裁决：

- 唯一真源使用引擎的 `PolicyMode`。
- UI 类型必须能表示 `workspace`，即使 `ask` 不在面板出现。
- `ask` 只作为兼容值保留，不在新 Workbench/Focus 的正常选项里出现。
- 新增测试必须断言：面板永远不下发 `ask`，但收到 `ask` 的旧配置时不会崩溃。

### 3.2 Approval Card 不能出现“始终允许”

协议只有 `allow-once | deny | allow-session`。`allow-session` 的宿主实现是“工具 + 参数指纹 + 默认 10 分钟 TTL”，不是永久白名单。

补充裁决：

- 按钮文案固定为“允许一次 / 拒绝 / 本次会话允许（10 分钟）”。
- 如果将来做持久白名单，必须是独立入口，显示四要素，并明确“越界访问永不因白名单免问”。
- Plan 批准不等于工具授权；批准计划后，每一步工具仍走 grant + consent。

### 3.3 账号身份锁是安全例外

`account-block.ts` 的全屏红底覆盖层是刻意 fail-closed，不属于“遮挡登录页”的缺陷。验收条款必须写成：

> 除账号身份锁覆盖层外，登录页、二维码和原生消息区不得被 Studio 遮挡。

禁止为了“页面好看”给该覆盖层加 Esc、点外关闭或降低 z-index。

## 4. 技术路线裁决

### 4.1 本期不引入 React/Vite 到注入层

理由不是“React 不好”，而是当前注入产物是单个 IIFE，运行时读取后作为 `initialization_script` 注入真实站点。把 React、Vite 开发服务器、Monaco、xterm 一起塞进去，会同时改变构建链、加载方式和宿主页面性能，超出“前端重构”的可验收边界。

### 4.2 本期施工顺序

建议把设计稿的 P1–P5 重新排成可独立验收的四段：

| 阶段 | 交付 | 是否动注入层 | 是否动独立页 |
|---|---|---|---|
| A. 契约层 | design tokens、`PolicyMode` 收敛、`mountShadowRoot`、disposer、结构化工具事件类型 | 是 | 否 |
| B. Focus | 窄 rail、composer 动作条、权限/工作区/连接状态、审批浮层接入 | 是 | 否 |
| C. Workbench 壳 | 新增 `/workbench` 或升级 `/agent`，三栏骨架、任务流、Inspector 空态 | 否 | 是 |
| D. 任务组件 | ToolCallCard、PlanCard、ApprovalCard、DiffReview、ArtifactCard、ErrorCard | 否 | 是 |

`C` 开始前必须先决定独立页是否引入 React。这个决定不应阻塞 `A/B`。

### 4.3 独立页入口必须先补

如果采用独立页 Workbench，本期必须增加一个真实入口，三选一：

1. Tauri 菜单/托盘“打开工作台”，创建加载 `http://127.0.0.1:8760/agent` 的窗口；
2. 主窗口 Focus 模式里的“打开工作台”按钮，经 Tauri command 打开窗口；
3. 单窗口内切换到本地页面（改动最大，不推荐本期做）。

在该入口落地前，任何“Workbench 已可用”的说法都不成立。

## 6. 设计与素材补充

### 6.1 视觉方向

保留设计稿的关键词：“精密、克制、可信，像工作台，不像营销页”。补充三条硬约束：

- 主色只用于操作、选中和关键状态，不用于大面积背景；
- 禁止子 Agent 紫色 `#8b5cf6`、玻璃拟态、营销式渐变和无意义悬浮缩放；
- 所有文本/背景组合按 WCAG AA 校验，状态色必须成对提供 `fill` 与 `text` token。

### 6.2 Logo

唯一设计源是 `docs/设计稿/app-icon-v1.png`：

- 2048×2048；
- 24bpp RGB；
- 白底圆角方块 + 蓝色鲸鱼 + 对话气泡。

施工要求：

- 保留原图，不覆盖、不手工逐个缩放；
- 用 `npm run tauri -- icon docs/设计稿/app-icon-v1.png` 生成 `src-tauri/icons`；
- 生成后检查 `src-tauri/tauri.conf.json` 的 `bundle.icon`，当前只列了 `icons/icon.png`，应确认是否需要补 `.ico` 和多尺寸；
- 验收安装包图标、任务栏图标、窗口图标三处一致。

### 6.3 深色模式

设计稿说“首版可只做浅色，但 token 预留深色”。补充裁决：

- token 必须一开始就分 `light` / `dark` 两组；
- 主题来源优先级为宿主显式主题 > 系统偏好 > 浅色默认；
- 不允许只靠 `prefers-color-scheme` 写死；
- 首版可以只交付浅色视觉，但组件不得硬编码颜色。

## 7. 本期范围裁决

### 7.1 应纳入

- Focus 模式的宿主适配、窄 rail、composer 动作条、状态 chip；
- 真 Shadow DOM 根容器和样式去重；
- 设计 token 与契约常量；
- 权限词表收敛；
- Approval Card 三按钮映射；
- markdown sanitizer；
- Workbench 三栏骨架和入口；
- 通用工具卡片 + 未知工具兜底；

- PWA / 手机远程控制；
- Monaco / xterm / Shiki / KaTeX；
- hunk 级逐块 diff 应用；
- 持久白名单管理 UI；

- 搬运 cuckoo-code 代码；
- fork DeepSeek Harness；
- 给账号身份锁加可关闭入口；
- 在注入层引入重型框架；
- 用彩色气泡区分 Agent。

## 8. 对施工计划的硬要求

后续施工计划必须满足以下条件，否则不具备开工资格：

1. 每个 checkpoint 只允许一个主执行者，并写清允许修改的文件。
2. 每个 checkpoint 结束必须运行：

   ```powershell
   git status --short
   npm run typecheck
   npx vitest run
   npm run build:inject
   npm run gate
   ```

3. 每个 checkpoint 必须记录：
   - 修改文件；
   - 测试结果；
   - 新增失败（必须为 0）；
   - 已知基线失败（保持 3 条，除非单独修复）；
   - 回滚点；
   - 下一个 checkpoint 的入口条件。
4. 任何 UI 组件不得直接散落调用 `document.querySelector` 定位宿主元素；必须经 host adapter。
5. 所有订阅、定时器、MutationObserver、事件监听必须返回 disposer，并在 `destroy()` 中幂等释放。
6. 所有未知工具、未知错误码、缺失字段必须有兜底 UI，不允许白屏或静默吞错。
7. Markdown 必须经过 sanitizer，或本期明确关闭原始 HTML 渲染。
8. 不允许覆盖 `src-tauri/inject/entry.js` 的现有未提交修改。

## 9. 最终裁决

**方向：保留。**

**原文状态：不可直接开工。**

**修订后的基线：**

> 注入层做轻量 Focus，独立页做 Workbench，宿主共享任务与授权状态；先补契约和事件模型，再做视觉组件。

**下一步不是继续讨论风格，而是：**

1. 决定独立页是否引入 React（只影响 C/D 段）；
2. 补结构化工具事件契约；
3. 按 A → B → C → D 写文件级施工单；
4. 用本轮 3 条基线红灯作为验收起点，不允许新增失败。
