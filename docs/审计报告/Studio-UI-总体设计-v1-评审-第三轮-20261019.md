## 2. 两份评审报告之间的冲突裁决

### F1（高）权限词表：评审A 的补丁是第四套词表，必须废止

评审A §4.2 给出的可插入补丁是：

```ts
export const PERMISSION_TIER = ['readonly','ask','auto','danger-full'] as const;
```

这与其余四方全部冲突：

| 来源 | 词表 |
|---|---|
| 代码真相源 `policy.ts:32-47` | `workspace / ask / auto / full`（面板只暴露 `workspace / auto / full`） |
| 评审B C2 的修法 | 写死 `workspace \| auto \| full` |
| 执行接力 §7.2 阻断项 | 「固定 `workspace \| auto \| full`」 |
| 智能体面板需求定稿（2026-10-10）§1 | 三档：仅工作区 / 风险审批（默认）/ 完全放开 |

评审A 的 `readonly` 与 `workspace` 语义相近但取值不同，`danger-full` 则把「full 档需要风险标识」这个**展示层**关切错误地升格成了**取值**。而执行接力 §2.1 明确要求豆包产出 `ui-contract`，§7 又只机械引用了评审B 的阻断清单——如果实现者手里同时拿着两份评审，按评审A 抄进 `ui-contract.ts`，恰好复刻 C2 要消灭的「多套词表」元模式。

**裁决**：

1. 权限档位唯一取值 = `policy.ts:36-37` 的 `workspace | auto | full`，展示名唯一来源 = `policy.ts:42-47`。
2. 评审A 补丁中的 `readonly` 并入 `workspace` 的展示名，`danger-full` 并入「`full` 档在 chip 上必须有显著风险标识」——这是 §6 D5 token/组件层的一条设计要求，不是枚举值。
3. 执行接力 §7.2 后追加一句：「不得实现评审A §4.2 的 `readonly/ask/auto/danger-full` 四值枚举」，并点名三处 UI 收敛位置（`studio-ui-core.ts:25`、`studio-input-bar.ts:96`、`studio-settings-panel.ts:143-145`，本轮现读仍全部过期）。

### F5′（实测加重）「全绿」前置为假，且 HEAD 提交自己打破了 2 个红灯

`前端开发计划-v1.md` 前置写「M9 内核已稳（tsc=0 / vitest 1091 全绿 / gate 六步阻塞全过）」；路线图 M0 写「1096 测试绿」。本轮实跑（HEAD `4afea0f`）：

- `npx tsc --noEmit`：**0 错，exit 0**——这部分为真。
- `npx vitest run`：**118 个测试文件，1197 个测试，3 失败 / 1194 通过**，exit 1。

三个红灯及根因（逐个溯源到引入提交）：

| 红灯 | 现象 | 引入 |
|---|---|---|
| `tests/desktop/desktop-entry.test.ts` | `installStudio` 在 `src/desktop/entry.ts:128` 抛 `Cannot read properties of undefined (reading 'includes')`——测试只桩了 `location.origin`（`desktop-entry.test.ts:13`），没有 `pathname` | `d4bb933`（登录页隐藏 chatUI）在 entry.ts 加了 `location.pathname.includes` |
| `tests/desktop/tool-authority.test.ts:22` | grant 重放期望 `reason==='consumed'`，实得 `'not-found'` | **HEAD `4afea0f` 本身** |
| `tests/e2e/smoke.test.ts:49` | 同上，同一断言 | **HEAD `4afea0f` 本身** |

第二类值得单独说：HEAD 提交把 `grant-store.ts:82` 的 `return g && !g.consumed ? g : g ?? null` 清理成 `return g && !g.consumed ? g : null`，commit message 称「dead branch」。但那个 `: g ?? null` **不是死分支**——它是调用方区分「grant 已被消费（重放攻击面）」与「grant 不存在」的唯一依据。删掉后，重放检测的错误理由从 `consumed` 退化成 `not-found`，恰好把「这是一次被拦截的重放」这个安全可观测性信息抹掉了。这与 UI 直接相关：错误码中文化（M12 表）和 ErrorCard 若按 `not-found` 文案渲染，用户看到的是「找不到授权」而不是「该授权已被消费、重放被拒」——安全语义被 UI 文案进一步稀释。

**裁决建议**：设计稿 §10 P0 的「修复或登记」按本表执行——
1. `desktop-entry` 红灯：改测试补 `pathname` 桩（或 entry.ts 对 `location` 判空），属测试债，进 P0 当天修；
2. 两个 `consumed` 红灯：**回滚或修正 `4afea0f` 的那行**——恢复 `get()` 对已消费 grant 的可见性（或给 `consume()` 返回带 reason 的结果对象），不能以「登记」豁免，因为它是安全语义回归；
3. 在这两条修掉之前，执行接力 §2.1 的豆包停点条件「vitest 通过或失败项有明确记录」必须把这 3 条点名，防止「明确记录」变成永久豁免（评审A §2 对 grant-store 的同一警告，本轮升级为实证）。

## 4. 两份评审都缺的两块（本轮新增）

### N1（高）设计稿缺「状态与数据流」整章

§4.1 给了组件树，但全文没有回答：会话/任务/工具调用的状态存哪、归谁管、React 组件从哪拿流式 delta、断线后 pending 怎么表示。评审A 在 §2.3 意见里点了一句「全局 execution state machine 是唯一数据源」，评审B 在 C4/第 6 节点了 bridge 消息集——但都停留在批注，没有升为设计章节。这一章缺席的后果与「契约无单一真相源」元模式完全同构：每个面板自己推断状态，正是历史审计里「UI 说在跑、实际 loop 已停」的复发路径。

建议插入 §4.0「状态与数据流」，骨架如下：

```ts
// 4.0.1 唯一真相源
// StudioStore 是 UI 侧唯一可变状态容器；任何组件不得自建第二份
// 运行态推断（不读时间戳、不数心跳、不扫 DOM）。
interface StudioStore {
  execution: ExecutionState;        // 'idle'|'planning'|'running'|'awaiting-consent'|'error'|'offline'
  session: SessionState;            // 消息、工具调用、Plan、Approval 引用
  workspace: WorkspaceState;        // 项目、分支、权限档（词表见 D2）
  connection: 'online'|'degraded'|'offline';  // 断线时 execution 冻结为最后已知态 + pending 计数
}
// 4.0.2 IO 边界
// bridge（收编 src/inject/direct-bridge.ts 现有实现）是 Store 与宿主之间的
// 唯一通道；组件不直接 callHostTool，只 dispatch action。
// 4.0.3 生命周期
// Store 订阅 bridge、bridge 订阅宿主；destroy() 沿同一链路反向释放
//（与评审A §4.3 StudioDisposable 契约合并实现）。
```

配套验收：任何面板显示的「运行中」必须可指认为 `store.execution` 的直接投影；断线后 100ms 内 Status Bar 出现 pending 计数（回应评审B 对 C4 的断线不清 pending 指责）。

### N2（中）Workbench 的「独立窗口」选项从未被评估

§2.1 的论证只在「注入 overlay 内部」二选一（Focus vs Workbench），从未比较第三条路：**用 Tauri 第二 WebviewWindow 承载 Workbench，复用已存在的 `/agent` 路由与令牌下发**。对照：

| 维度 | 注入式 Workbench（设计稿现案） | 独立窗口（复用 /agent） |
|---|---|---|
| 宿主改版风险 | 高——三栏压在 deepseek.com DOM 上，几何扫描退化是历史主病灶 | 零——自持文档 |
| z-index 战争 | 需要运行时探测基线（评审A 已提） | 不存在 |
| 登录态 | 免登录（复用宿主会话） | 已解决——`server.ts` 令牌内嵌，本地进程威胁模型已声明 |
| CSP / 包体积 | 受宿主约束（评审A P0-1 实测项） | 自有 CSP，React/Monaco 无宿主限制 |
| 与 10-10 需求定稿 | 相悖（见 F4） | 一致（「专用面板为主」本来就拍过板） |
| 代价 | — | 窗口管理、两窗口状态同步（会话在 Focus 发起、Workbench 续跑需要 Store 经宿主中转） |

设计稿若仍选注入式，**需要写明放弃独立窗口的理由**——否则后续每一次宿主适配返工（P2 整个阶段的存在理由）都没有对照基准。这一条不阻断开工，但必须在 P2 开始前有结论，因为 P2 的工作量估计完全取决于它。
