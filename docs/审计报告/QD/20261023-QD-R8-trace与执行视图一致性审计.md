## 1. 发现

### QD-R8-01 [P2] 远端工作台丢弃 `final-answer.truncationMarker`：被截断的回答在手机/远程端看起来是完整的

**证据**（`src/ui/workbench/workbench-execution-view.ts:161-164`）：

```ts
case 'final-answer':
  appendAssistantMarkdown(canvas, event.text);   // ← 只取 text
  break;
```

对照主视图的两处消费（`src/ui/studio-chat-ui.ts:789-794` 实时、`:967` 回放）：

```ts
recordEvent({ type:'final-answer', ..., text: limited.text, truncationMarker: limited.truncationMarker });
markdown.innerHTML = renderMarkdown(event.text + (event.truncationMarker ?? ''));  // 回放拼接
```

`StudioFinalAnswerEvent.truncationMarker` 是 `limitFinalAnswer` 超过 64KB 时写入的显式截断标记
（`src/shared/studio-execution.ts:224-231`）。主视图两条路径都显示；远程执行视图完全忽略。

**后果**：
- 回答超过 64KB 时，电脑端 Studio 显示「回答过长，已截断（原始 N 字节…）」，手机/远程工作台
  却把同一份记录渲染成完整回答。**用户在最容易漏看截断的窄屏端，得到的是“回答已经完整”的错误印象**。
- 这是「断流不可见」在第二条展示链上的复现：同一条记录，两处 UI 结论不同。

**复现**：`REPRO-A` 实测失败：工作台正文 `"查看目录完成\n"`，不含 `回答过长`；正控把标记写进 `text` 后能正常显示，证明渲染器本身没问题，是取字段时丢了。

**建议**：`final-answer` 分支拼接 `event.truncationMarker ?? ''`（与主视图回放同形）；或在正文下方单独渲染一条
`msg-error`/提示条，避免把「已截断」混进 Markdown 正文。补一条与 `workbench-execution-view.test.ts` 同风格的用例。

**状态**：Verified-实证（盘面复制树）。

### QD-R8-02 [P3] 执行视图按事件全量重建：会话列表按钮与正文节点每次都被销毁重建

**证据**（`src/ui/agent-panel.ts:96-121` + `src/ui/workbench/workbench-execution-view.ts:47、142-144` + `src/host/desktop-host.ts:1178-1186`）：

```ts
// host：每次 kvSet 都广播
if (key === STUDIO_EXECUTION_INDEX_KEY && ...) emitExecutionIndex(value);
else if (key.startsWith(...SESSION_PREFIX) && ...) emitExecutionSession(value);

// panel：任何一次广播都重绘列表；本会话广播再重绘正文
function applyExecutionIndex(index) { ...; renderSessionList(); ... }
function applyExecutionSession(session) { ...; renderSessionList(); renderActiveSession(); }

// view：clear() 之后全量重建
renderExecutionIndex(...) { clear(container); ... }
renderExecutionSession(...) { clear(center); for (inspector of inspectors) clear(...); ... }
```

会话存储每写一个事件都会同时写会话与索引（`studio-execution-store.ts:107-127`）⇒ 一次工具回合内
「user-message / 每个 tool-start / 每个 tool-result / final-answer」每个事件触发 **1 次正文全重建 + 2 次列表全重建**。

**后果**：
- 窄屏会话列表（`select`/按钮）在每次事件时重建，键盘焦点与选择态丢失；用户正在列表里操作会被打断。
- 正文每次清空重建，滚动位置由 `appendMessage` 强制拉到底（`workbench-center.ts:28`）；用户向上翻看历史时
  会被新事件拽回底部。
- 工具面板（inspector/drawer）同样每次清空重建，`appendToolRun` 的「已完成不被进行中覆盖」保护在
  全量重绘面前没有意义（每次都从事件流重新推导）。

**复现**：`REPRO-B` 实测失败：同一索引重渲染后 `list node reused = false`；同一会话重渲染后
`message node reused = false`。结合上面的广播链，可确认节点销毁频率=事件频率。

**建议**：把渲染改成增量：`renderExecutionSession` 按 `session.key + events.length` 做 diff（或复用现有节点、
只 append 新事件）；`applyExecutionIndex` 在 `(key, updatedAt, title)` 三元组未变时跳过重绘。
宿主广播可合并（例如 50–100ms 节流），避免一个回合内几十次全量帧。

**状态**：Verified-实证（节点身份）+ Verified-代码事实（广播频率）。

### QD-R8-03 [P3] trace 的 `turnId` 是全局当前值：异步回调落账时可能已切到下一个用户回合

**证据**（`src/inject/main-world-interceptor.ts:600-606`、`:1158`、`:1229-1233`）：

```ts
// captureChatRequest：只有识别到“新用户消息”时才换 turn id
traceTurnId = `t${Date.now().toString(36)}`;
interceptorTrace.record({ t: 'turn.start', turnId: traceTurnId });

// forward 的异步回调：完成时才读取全局 traceTurnId
.then((r) => { ...; interceptorTrace.record({ t:'tool.exec', turnId: traceTurnId, ... }); })
```

`forward` 的 `sender` 可能跨秒返回；期间用户再发一条消息，`captureChatRequest` 会把 `traceTurnId` 换成新值。
旧工具完成、旧流收尾（`onStreamEnd` → `turn.end`）时读到的都是**新**回合 id ⇒ 报告里旧回合的工具/终态被记到新回合，
新回合可能提前出现 `turn.end`。

另外注释与实现不符：

```ts
// 新用户消息 = 新一轮 trace。id 与 execution turnId 同源同值。
traceTurnId = `t${Date.now().toString(36)}`;   // execution 侧是 crypto.randomUUID()
```

两者并不同值，`t<base36>` 与执行记录/回放里的 turnId 无法对撞——用户贴 `__studioTraceReport()` 时，
无法定位到执行记录里的同一回合。

**后果**：并发回合（用户在上一轮未结束时继续发言）下 trace 报告的归属会串；断流取证时「哪一轮断的」可能判错。
属诊断工具缺陷，不影响运行时行为。

**建议**：把 turn id 在请求入口捕获后随 `forward` 闭包传递（或让 trace 事件直接带 `sessionKey+turnId` 快照），
`onStreamEnd` 使用该流创建时捕获的值；同时把注释改成事实，并让 trace 与执行记录共享同一 turn id（可在
`captureChatRequest` 里从 `loopState` 取执行侧 turnId）。

**状态**：Verified-代码事实（异步回调读取可变全局）。

### QD-R8-04 [P3] trace 环形缓冲按事件丢最旧：长回合首先丢 `turn.start` / `request.sent` / PoW

**证据**（`src/shared/studio-trace.ts:138-157`）：

```ts
record(event) {
  buf.push(stamped);
  if (buf.length > cap) buf = buf.slice(buf.length - cap);   // 丢最旧
}
```

而 `sse.frame` 是**每个网络分片一条**（`main-world-interceptor.ts:677-678、904-905`）。上限 2000 条时，
一个几千分片的正常长回答就能把本回合开头的 `turn.start`、`request.sent`（含 bytes/powMs）全部挤掉。

**后果**：正是「长回合/断流」最需要取证的时候，报告开头缺失请求体积与 PoW 耗时，`groupTurns` 的
`firstTs` 也只剩尾部 ⇒ 时长被低估。与 R4-GAP-2（4 条断流路径不产生 trace 决策）叠加后，trace 在
最关键的场景里可用性进一步下降。

**复现**：`REPRO-C` 实测失败：cap=20、写入 `turn.start`+`request.sent`+40 条 `sse.frame` 后，
快照前 5 条全是 `sse.frame`，`turn.start`/`request.sent` 已不存在。

**建议**：按回合保留「首尾」而不是纯 FIFO（每轮固定保留第一条 `turn.start` 与 `request.sent`）；
或把 `sse.frame` 聚合成每回合一条增量计数（如每 100ms 或每 N 字符一条），把 2000 条预算留给因果事件。

**状态**：Verified-实证（盘面复制树）。

## 4. 小结

- 优先级：R8-01（远端静默截断，P2）→ R8-02（全量重绘，P3，但影响每回合体验）→ R8-03（trace 归属）→ R8-04（trace 缓冲）。
- 两条链的差距值得作为一个专项：主视图（studio-chat-ui）与远程执行视图（workbench-execution-view）消费同一份
  `StudioExecutionSession`，但字段消费不一致（截断标记、工具参数/结果、错误详情）。建议抽一个共享的
  「事件→视图模型」投影层，两处只做样式差异。
