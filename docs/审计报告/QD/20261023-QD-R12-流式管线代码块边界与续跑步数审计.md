## 1. 发现

### QD-R12-01 [P2] Markdown 围栏 / 行内代码里的工具标签被真执行，且从可见文本里被整个剥掉

**证据**：

解析器只认 `<name>` 形状，完全不感知代码围栏与行内反引号；`forward()` 对受支持工具无条件执行：

```ts
// src/inject/streaming-tool-parser.ts:38-64
while (i < input.length) {
  const lt = input.indexOf('<', i);
  ...
  const open = after.match(/^<([a-zA-Z_][\w.:-]*)>/);
  if (open && this.names.includes(open[1])) {
    ...
    calls.push(this.make(name, body, rawBlock));
    i = closeIdx + closeTag.length;
  }
  ...
}
return { calls, clean };   // 标签块从 clean 里整段消失
```

```ts
// src/inject/main-world-interceptor.ts:1090-1096
const forward = (call: ParsedToolCall): void => {
  console.log('[interceptor] forward:', call.invocationName, ...);
  if (!isSupportedUpstreamTool(call.invocationName)) { ... return; }
  // 之后直接开始建工具卡、执行
```

唯一的缓解是提示词规则，没有任何代码侧兜底：

```ts
// src/inject/main-world-interceptor.ts:320
- 工具调用放在最终回答正文里，不要放在思考/推理区域，不要放在 Markdown 代码块里
```

XHR 路径共用同一个解析器与 `forward()`（`main-world-interceptor.ts:917`），不因传输层不同而豁免。

**后果**：

1. 用户问「给我一个调用示例」，模型在 ```bash 围栏里写一个示例 → 示例被**真实执行**，同时围栏内容被从可见文本剥掉，聊天里只剩一个空代码块（日志原文：`'…```bash\n\n```…'`）。行内反引号同理，正文变成 `` `` ``。
2. 读级工具**不经同意闸门**：`search_files` 是 `risk: 'read'`（`src/host/tool-definitions.ts:113-118`），`CONSENT_MIN_RISK = 'insert'`（`src/host/tool-registry.ts:46`）⇒ 围栏里的 `<search_files>{"operation":"grep","query":"…"}</search_files>` 会在用户只要示例的场景下静默检索本地文件，把命中内容喂回模型上下文。
3. 特权工具（`shell_exec` / `file.read` / `file.stat` 均为 `privileged`）仍会弹同意框，不构成绕过；但同意框出现在「我只是要个示例」的回合里，属于把示例变成真实动作的语义错误，用户很容易顺手批准。
4. 模型输出被外部内容影响时（例如它刚读过的网页/文件里有示例标签），同样会触发；提示词规则无法约束这种情况。

**建议**：

1. 把围栏状态放进 `StreamingToolCallParser` 的 feed 状态机：跟踪 ``` 围栏（含语言行）与成对反引号；处于代码上下文时不得开工具标签、不得剥文本。跨 chunk 的半截围栏也要保留在 tail，与现有 `<` 前缀缓冲同一套机制。
2. 解析器升级后，`forward()` 不必改；但要加一条回归腿固定「围栏内 0 次执行 + 可见文本保留原文」。
3. 若短期不改解析器，至少在 `forward()` 执行前用原始流窗口判定该标签是否位于未闭合围栏内，命中则按普通文本处理。

**复现**：

- `复现用例/qd-r12-stream-pipeline.test.ts` 第 3、4 腿。
- 实测：`shell_exec` 与 `local_file_read` 各被 forward 1 次；可见文本分别丢失围栏内容与行内代码内容。
- 状态：**Verified-实证**（执行侧）；「读级工具静默执行」为 Verified-代码事实（风险表 + 同意阈值）。

### QD-R12-02 [P2] auto-continue 的 `loopDepth` 双重自增：每次续跑吃 2 步，25 步预算实际只剩约 12 轮；重试仍吃 1 步

**证据**：

```ts
// src/inject/main-world-interceptor.ts:1353-1359
// 重试不应消耗 loopDepth：它是「工具续跑」的步数预算，
// 一次 429 就吃掉一步会让真正的工具轮次被提前耗尽。
if (!continuationRetryPending) loopDepth += 1;
continuationRetryPending = false;
loopDepth += 1;          // ← 无条件再来一次
// v0.18：步骤编号随续跑递增，工具归到对应步骤
stepFlowStep = loopDepth;
```

`MAX_LOOP = 25`（`src/shared/continuation-prompt.ts:46`）。守卫是 `loopDepth < MAX_LOOP`（1158/1191/1213/1259）。
`loopDepth` 初值 0（`:1008`）⇒ 每次正常续跑 +2，序列 2/4/…/24，第 13 次进入时 24<25 仍放行，之后 26 停 ⇒ **有效约 13 次续跑，而不是 25 次**。
`continuationRetryPending` 为真时首行跳过，但第二行照样执行 ⇒ **重试仍消耗 1 步**，与紧邻注释和 QD-R4-01 建议第 2 条直接相反。

**后果**：

- 长工具任务（例如逐文件处理 20+ 个文件）在约第 12–13 轮被 `max-loop` 提前截停，用户看到的表现就是「工具调用断流 / 任务没做完就结束」。
- 429/5xx 重试每次吃掉一步工具预算，错误天气下可用轮次进一步缩水。
- `stepFlowStep = loopDepth` 后步号只走偶数，步骤栏编号跳号（2,4,6…），与「步骤 N」的语义不一致。

**建议**：

1. 删除 1357 的无条件自增，保留 `if (!continuationRetryPending) loopDepth += 1;` 一行；或反向重构为 `if (continuationRetryPending) { /* 不加 */ } else { loopDepth += 1; }`，让重试真正不占预算。
2. 若步号需要连续，步号与预算分离：`stepFlowStep += 1` 独立于 `loopDepth`。
3. 回归腿：首次续跑断言 `loop=1`；一次 429 后断言 `loop` 不变且请求数 +1。

**复现**：

- `复现用例/qd-r12-stream-pipeline.test.ts` 第 5 腿：一次工具执行后等待续跑，断言首次 `auto-continue loop=1`。
- 实测：`expected 2 to be 1`（首次续跑已是 2）。
- 状态：**Verified-实证**。

> 去重说明：QD-R4-01 只提出「重试不应消耗 loopDepth」的建议，未登记双重自增；本轮是该预算问题的第二根轴，编号独立，修复时两条一起改。

### QD-R12-03 [P3] fetch 路径的推理尾段只进步骤笔记，不进聊天 think 块（XHR 路径会进）

**证据**：

```ts
// fetch：src/inject/main-world-interceptor.ts:701-707
const sseTail = sse.flush();
const rsnTail = sse.consumeReasoning();
if (rsnTail) {
  stepReasoningAccum += rsnTail;
  stepFlow?.addReasoningNote(stepFlowStep, stepReasoningAccum);
  // ← 缺 chatUI.appendReasoning
}
```

```ts
// XHR：src/inject/main-world-interceptor.ts:892-904
let visible = sse.feed(part);
if (xhr.readyState === 4) visible += sse.flush();
...
const rsnX = sse.consumeReasoning();
if (rsnX) {
  stepReasoningAccum += rsnX;
  stepFlow?.addReasoningNote(stepFlowStep, stepReasoningAccum);
  if (loopState?.chatUI) loopState.chatUI.appendReasoning(stepReasoningAccum);   // ← 有
}
```

**后果**：

- 流最后一个 THINK 事件若没有结尾换行（只能由 `flush()` 解析），fetch 路径下这段推理只进步骤栏笔记，聊天消息里的「已思考」块看不到；用户在 fetch 通道下看到的思考内容比实际少一截。
- 两条传输路径对同一状态的处理不一致，后续修 think 块时容易只修一条腿。

**建议**：在 fetch 的 `rsnTail` 分支补一行 `if (loopState?.chatUI) loopState.chatUI.appendReasoning(stepReasoningAccum);`，与 XHR 对齐；回归腿用「完成哨兵之后再来一个无换行 THINK 快照」固定。

**复现**：

- `复现用例/qd-r12-stream-pipeline.test.ts` 第 6 腿。
- 实测：`appendReasoning` 收到空串，`expected '' to contain '尾推理'`。
- 状态：**Verified-实证**。
