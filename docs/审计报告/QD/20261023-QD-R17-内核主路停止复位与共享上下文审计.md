## 1. 发现

### QD-R17-01 [P1] 面板按一次「停止」后，TaskLoop 两条入口永不自复位：之后每条自动化/HTTP 任务 0ms 空回，并把空 assistant 永久写进共享历史

**证据**：`src/host/agent-loop.ts:82-84`（盘面 = HEAD 同形）——`stop()` 的全部实现就是置位：

```ts
    stop() {
      options.stopFlag.stopped = true;
    },
```

复位点**唯一**在 `agent-loop.ts:89`，且只在 `AgentLoop.send()` 起点：

```ts
    async send(text: string, opts?: { roomId?: string }): Promise<void> {
      if (active) throw new Error('agent-busy');
      active = true;
      currentRoomId = opts?.roomId;
      options.stopFlag.stopped = false;   // ← 全仓唯一复位点
```

`src/host/bot/registry.ts:139` 初始化 `{ stopped: false }`、`:197` `destroy()` 也置 true 而不复位。宿主侧两条 TaskLoop 装配（`desktop-host.ts:866-870` / `:901-905`，HEAD `:831` / `:866`）**只建循环、不碰 stopFlag**；`web-engine.ts:257` 的轮询首检因此第一拍就退出：

```ts
        if (options.isStopped?.()) { stopped = true; break; }
```

R2-06 的设计前提写在 `agent-loop.ts:175-177`（原文）：「停止信号由下一次 `send()` 开始时自行复位」——该前提默认**所有入口都走 `AgentLoop.send()`**。`b70d5d8` 把 HTTP/automation 主路切成 TaskLoop 后，这条前提不再覆盖全部入口。

**后果**（可触发，已实证）：用户在面板点一次「停止」（`agent-channel.ts:284-288` `case 'stop'` → `desktop-host.ts:1487` `bot.loop.stop()`），此后：
- automation 的 prompt 任务（`desktop-host.ts:1127-1129` → `agentSender` → `createTaskLoop`）**立即**返回空——REPRO-A 实测用时 `0ms`、`content=""`、`stopReason=empty-response`（不是 timeout：`task-loop.ts:151-154` 的空判定排在超时之后、工具判定之前）；
- HTTP `POST /v1/agent/send`（`src/api/server.ts:449-470`）拿到 `answer=""` 并回 200；automation 侧 `catch` 只 `console.warn`，任务照样记 success——与 **R10-02** 同后果家族（不同触发：R10-02 是页面离线，本条是「按过停止」）；
- 每次空回都往**进程级共享** `kernelHistory` 落一条 `assistant:""`（REPRO-A 历史读数四条），后续任务的 prompt 里带着这些空行（见 QD-R17-02）。
- **恢复条件必须写清**（⛔ 夸大为「永久直到重启」）：任何走 AgentLoop 的入口——面板直发（`desktop-host.ts:1485`，HEAD `:1442` `bot.loop.send`）或聊天室成员回复——一跑就 `:89` 复位解毒。所以真实形状是：**只要没人再发面板消息，自动化就一直是死的**；纯 automation 驱动的部署（无人对着面板打字）里，一次误触停止＝任务面整片哑掉且没有任何报错横幅。

**建议**：别把复位契约留在 AgentLoop 内部。两处一起改：① 宿主在每次 TaskLoop 装配前显式 `botRegistry.getState(botId)!.stopFlag.stopped = false`（把「一次 send 一个停止作用域」提到宿主层）；② 更正确的修法是给 `createTaskLoop` 接 `signal`（`TaskLoopOptions.signal` 字段已实现、生产⛔ 传，见 QD-R17-04），让 stop 成为 per-run 的 AbortController 而不是 per-bot 的全局粘滞位。

**复现**：`复现用例/qd-r17-taskloop.test.ts` → REPRO-A 四断言全红（`expected '' not to be ''` ×2、`expected true to be false` ×2），原始读数见 §0。

**状态**：Verified-实证（复位缺失、空回、空 assistant 落共享历史）+ 代码事实（生产两条装配点⛔ 复位）。

### QD-R17-02 [P1] `kernelHistory` 全生命周期⛔ 清空点、`buildPrompt` 全量序列化 ⇒ 串行任务必然携带上一任务全文（跨任务上下文泄漏 + 提示词单调增长）

**证据**：`desktop-host.ts:832`（HEAD `:797`）是 `kernelHistory` 的唯一创建点，且是**进程级一次**：

```ts
  const kernelHistory = createMessageHistory();
  const kernelExecutor = createHostToolsAdapter(hostTools);
  void kernelHistory; void kernelExecutor; // 里程碑2 接开关时启用
```

现跑 `grep -rn "kernelHistory" src/` → 5 命中：`:832` 创建、`:834` void、`:868` / `:903` 注入两条 TaskLoop、`:872` 注释；**没有任何一处 clear/reset/按任务重建**。现跑 `grep -rn "\.clear()" src/host/` 的 16 枚命中全是 `Set/Map/sessionAllowlist/pendingRequests`，⛔ 一枚落在 `MessageHistory` 上——`message-history.ts:52` 契约里那条 `clear(): void` 生产无调用者。`message-history.ts:61-65` 的 `MessageHistoryOptions` 只有 `idFactory` / `now`，**没有长度上限字段**；`task-loop.ts:105-109` 拼提示词用的是全量：

```ts
function buildPrompt(history: MessageHistory): string {
  const all = history.all();
  if (all.length === 0) return '';
  return JSON.stringify(all.map((m) => ({ role: m.role, content: m.content })));
}
```

**后果**（已实证，⛔ 需要并发）：同一条入口连续跑两个任务，第二个任务的出站文本就含第一个任务的**提问原文 + 回复原文**——REPRO-B 实测第二次 `chat-insert` 的正文＝`[{"role":"user","content":"会话一的机密提问"},{"role":"assistant","content":"回复1"},{"role":"user","content":"会话二的第一个问题"}]`。这条把 R10 在 `:106` 顺带记下的「并发才串台」观察**降了门槛**：串行即可，任何两次任务都串。三个后果面：
1. **跨任务数据泄漏**：任务甲（可能是内部数据、凭据相关提问）的全文被塞进任务乙的出站请求，发给模型并落到聊天页 DOM（页面对用户可见，也会进页端的会话历史）。
2. **提示词单调增长 ⇒ 断流**：`buildPrompt` 无窗口，`chat-insert` 有页面输入框上限；跑到第 N 轮时提示词超限，页面对超长输入的截断/拒收会让 `chat-read` 永远看不到与基线不同的稳定文本 ⇒ `stepTimeoutMs`（生产 120s，`web-engine.ts` 缺省）到点、`timedOut=true` ⇒ `task-loop.ts:152` 判 `'timeout'` 收尾。用户侧＝任务静默结束、无回复。
3. **与 QD-R17-01 复合**：空 assistant 行永久留在同一份历史里，污染是单调累积的（⛔ 自愈）。

**建议**：装配点按任务建历史（`createTaskLoop({ history: createMessageHistory() })`）；若内核确实要长驻记忆，则 ①给 `MessageHistoryOptions` 补 `maxMessages` 并让 `buildPrompt` 走 `lastN()`，②宿主在任务终态（`stopReason` 为 `timeout`/`empty-response`）时把那条空 assistant 从历史里剔掉，⛔ 让它过夜。

**复现**：同上件 → REPRO-B 两断言红（`expected '[{"role":"user","content":"会话一的机密提问"}…' not to contain '会话一的机密提问'` / `not to contain '回复1'`），同腿正控断言 `r2.content === '回复2'` 绿 ⇒ 排除「整条链跑不通」。

**状态**：Verified-实证（串行携带 + 无清空点）；后果 2 的「页面截断」环节是**代码事实外推**（本轮假页面对长度不敏感，未实证），修复前需在真页面上量一次超长 `chat-insert` 的行为。

### QD-R17-03 [P1] 引擎级共享可变状态（`toolCallCounter` / `currentRecords` / `roundNum`）无回合隔离 ⇒ 并发两条 TaskLoop 互继承工具计数，各多跑一轮、双双 timeout 并把基线文本当回复落库

**证据**：工具计数挂在 **per-bot state** 上，全局单增：`desktop-host.ts:1561`（HEAD `:1496`）

```ts
        onToolCall: ({ callId, tool, botId }) => {
          const state = botRegistry.getState(botId ?? 'main');
          if (state) state.toolCallCounter.current += 1;
```

引擎读它靠「起点差值」（`web-engine.ts:227` / `:294`，HEAD-EQUAL）：

```ts
      const counterStart = options.toolCallCounter.current;
      ...
      const toolCalls = options.toolCallCounter.current - counterStart;
```

⇒ 只要有两个 send 同时在飞，任一条看到的 `toolCalls` 就**包含另一条的工具执行**。同理 `web-engine.ts:127/:229/:314` 的 `currentRecords`、`:165` 的 `roundNum`、`:163` 的 `reconnectAttempts` 都是引擎闭包级单例，无 per-run 句柄。闸门拦不住：`agent-channel.ts:276` 与 `:165` 都读 `running`，而 `running` 的源是 `desktop-host.ts:1488`（HEAD `:1445`）`get running() { return bot.loop.running; }` ＝ AgentLoop 的 `active`（`agent-loop.ts:67/:79`），TaskLoop 路径⛔ 置位——**REPRO-D 实测：TaskLoop 已 `chat-insert` 1 条、在飞轮询中，`main.loop.running === false`**。这条读数是对 **R10-01** 的实证补强（R10 当时给的是四入口清单 + 代码事实），⛔ 新开编号。

**后果**（已实证）：面板上连发两条（或面板 + automation 同时），两条各跑一轮后：
- `state.toolCallCounter.current += 3`（模拟 hub 在这一刻执行了 3 次工具）落在**两条共用的**计数器上 ⇒ 两条的 `toolCalls` 都＝3 ⇒ `task-loop.ts:151-156` 的 `computeStop` 都不判停 ⇒ **各多跑一轮**；
- 实测读数：2 条用户消息 → **`insert 数=4` / `发出次数=4`**（断言 `≤2` 红），即每条用户消息被写进页面输入框两遍；
- 第二轮的 `chat-send` 把页面文本复位（真页面上＝上一条回复成为新基线），两条都读不到变化 ⇒ `stopReason=timeout`、`content="（页面初始内容）"`（= 本轮基线）⇒ `task-loop.ts:220` 把这段**基线文本当 assistant 回复**落进 `kernelHistory`。真页面上基线就是「上一条回复」，所以用户看到的是旧回复出现在新回合里、且工具明明执行过却判 timeout（＝**工具断流**）。两条都 `round=2`、`toolCalls=0`（多跑的那轮没有新工具，计数已被第一条吃掉）。

**建议**：① 工具计数从 state 级降到 run 级——`send()` 由 hub 直接把本轮 `ToolCallRecord[]` 交付（`onToolCall` 回调链已有，缺的是别再用共享差值判回合）；② 在宿主层给 main bot 加**单写者闸门**（TaskLoop 在飞时拒第二条 send，并回明确错误码而不是 `agent-busy`）；③ `web-engine` 的 `currentRecords`/`roundNum` 改成 `send` 局部变量。

**复现**：同上件 → REPRO-C（红断言：`用户发两条，页面被写入的次数: expected 4 to be less than or equal to 2`）。
**状态**：Verified-实证（共享计数 → 多跑一轮 → 4 次 insert → 双双 timeout → 基线文本落库）；「乙读到甲的那一条回复」这一子主张**未成立**，见 §2 第 1 行。
