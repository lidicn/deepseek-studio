### QD-R2-02 [P1] `59220b8` 的 P0-4「写链不再毒化」把「一次失败」换成了「下一批静默丢弃 + 调用方看到成功」

**证据**：`src/host/file-storage-backend.ts:42-53`
```ts
writeChain = writeChain.then(async () => { …readAll… writeFile(tmp)… rename(tmp, filePath); },
  (err) => { console.warn(`[storage] previous write failed, chain recovered: ${…}`); });
await writeChain;
```
`Promise.prototype.then(onFulfilled, onRejected)` 的第二个参数**替代**而非叠加第一个：只要上一批的 work 抛错，本次调用的 `work` 就不会执行，链头只打一行 warn，然后 `await writeChain` **正常 resolve** ⇒ 调用方以为写成功了。

**后果**：任何一次真实写失败（磁盘满、`rename` 被占用、`filePath` 父目录被换掉、进程崩溃留下的半截 tmp 占用），会让**紧随其后的那一批 KV 写整批消失且无错误码**；若失败原因持续存在，则此后每一次写都是「resolved + 没落盘」。local storage 的调用面（`src/bridge/storage.ts` 的 `StorageKvBackend`）拿不到 `KV_PERSIST_FAILED`，扩展侧 `chrome.storage.local` 语义与真实盘上内容从此分叉 —— 属于**静默错误结果**，不是崩溃类，因此比崩溃更难被发现。

**复现**：`复现用例/qd-r2-repro.test.ts` 组 QD-R2-02，红，实测原文：
```
{"outcomes":["k1: threw EPERM: operation not permitted, rename '…\storage.json.tmp' -> '…\storage.json'",
             "k2: resolved"],
 "readBack":{}}
```
（构造法：把 `filePath` 指向一个**同名目录**，使 `rename` 恒失败。`stderr` 同时打印了 `[storage] previous write failed, chain recovered:` —— 即失败被降级成一行日志。）

**状态**：Verified-实证。

**建议**：`writeChain = writeChain.then(work)`，失败处理放在**链外**：
```ts
const prev = writeChain;
writeChain = prev.then(work, () => undefined);   // 仅保证链不断
await prev.then(() => work())…                   // 或直接：把本批的失败原样抛给调用方
```
最小改动版本：`writeChain = writeChain.catch(() => undefined).then(work); await writeChain;` —— 恢复位仍不毒化后续，但**当批失败必须抛给调用方**（KV 层已有 `StorageBridgeError('KV_PERSIST_FAILED')` 可用）。补一条回归腿：连续两次 `writeBatch`，中间用不可写目标，断言「第二次要么在盘上要么抛错」，禁止 `resolved && readBack 为空` 组合。

### QD-R2-03 [P1] 页端消息结算不看连接身份状态：被判「篡改」的页的伪造 `result` 仍被采信，未做 Origin 自证的连接可代用户回 `allow-session`

**证据**：`src/host/page-runtime.ts:276-282`（`msg.type === 'result'` → 直接 `p.resolve({ok: msg.ok, data: msg.data,…})`）、`:347-353`（`consent-decision` → 直接 `p.resolve(msg.decision)`）。两处都 ⛔ 不读 `rec.ready` / `rec.untrusted`，而同文件 `:206-210` 的 `pickClient` 明确写了「被自检判定为篡改的页必须被跳过，否则工具就派发给了敌意页面」—— 即**出站**有闸门，**入站结算**没有。`integrity-alert` 处理在 `:283-286`（只置 `rec.untrusted = true`），置位后同一条连接的后续消息照旧全部可结算。Origin 交叉校验 `:237` 的条件是 `if (rec.reqOrigin && msg.origin …)`，`:243` `rec.origin = msg.origin ?? null` → **不上报 origin 的 hello 直接 `ready = true`**（`:249`）。

**复现**：`复现用例/qd-r2-repro.test.ts` 组 QD-R2-03，两腿皆红。
- A：连接（带 token）→ 握手成功 → 宿主 `dispatch('file.read', …, 'call-1')` → 该页自报 `integrity-alert`（宿主判其不可信）→ 再回 `{type:'result', callId:'call-1', ok:true, data:'FORGED'}` → 实测宿主把伪造值交给上层：`{"ok":true,"data":"FORGED"}`。
- B：连接（带 token、hello 不带 origin）→ 成为 ready 且收到 `consent-required` → 自回 `allow-session` → 实测宿主返回 `allow-session`（对照断言 `expect(c.ack).not.toBeNull()` 绿，排除「根本没握手成功所以假绿」）。

**后果**：同意闸门（唯一的人类介入点）可被**任何持有 token 的本机进程**用一条报文代答；被判定篡改的页面仍可伪造工具结果，写入链路的 `ok:true` 完全由页端自证。注：token 边界仍成立（本机进程要连 `/studio` 需要 token），所以这 ⛔ 是「远程可利用」，而是「**宿主把人类闸门当成了装饰**」；但结合 QD-R2-01（页面带不上 token）实际在线的 ready 客户端就只剩测试/脚本进程，闸门失效面反而更大。

**建议**：① 在 `ws.on('message')` 顶部统一 `if (msg.type !== 'hello' && (!rec.ready || rec.untrusted)) { options.onError?.('rejected-from-untrusted-page'); return; }`；② consent/dispatch 的结算只接受**当初收到该 payload 的同一条连接**（`pendingConsent`/`pendingDispatch` 记 `clientId`，比对后再 resolve）；③ hello 若既无 upgrade Origin 又无自报 origin，则标 `attested=false`，`requestConsent` 不得选它作为同意对象（工具派发可以，同意不行）。

**状态**：Verified-实证。
