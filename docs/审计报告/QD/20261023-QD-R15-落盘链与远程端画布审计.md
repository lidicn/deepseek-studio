## 1. 发现

### QD-R15-01 [P1] 断线窗口的首次读取会被当成「这个会话不存在」⇒ store 造出 1 事件空会话投毒 cache，重连后 cache 从不失效 ⇒ 下一次落盘把磁盘上的真历史整段覆盖

**证据**（三段链，缺一不成）：

`src/desktop/host-client.ts:385-408` —— 未连接时 KV **不报错、不排队，直接按「查无此值 / 写成功」返回**：

```ts
kvGet(key) { return new Promise((resolve, reject) => {
  if (!ws || ws.readyState !== OPEN) { resolve(undefined); return; }   // :387 断线读 = undefined
  ...
}); },
kvSet(key, value) { return new Promise((resolve, reject) => {
  if (!ws || ws.readyState !== OPEN) { resolve(); return; }             // :399 断线写 = 成功但一个字节都没发
  ...
}); },
```

`src/desktop/entry.ts:162-171` —— 覆盖层的 store 把 KV 直接接到这条桥上，没有「连接才允许读写」的准入：

```ts
const executionStore = createStudioExecutionStore({
  kv: { kvGet: (key) => host.kvGet(key), kvSet: (key, value) => host.kvSet(key, value), ... },
  onConnected: (callback) => host.onConnected(callback),
  isConnected: () => host.connected,       // ⛔ 传了，但 store 内部⛔ 用它挡读写
});
```

`src/ui/studio-execution-store.ts:85-99 / 141-149` —— 读不到就当没有，写之前先覆盖 cache：

```ts
async function readSession(key) {
  const cached = cache.get(key);
  if (cached) return cached;                        // ① 命中即返回，⛔ 与磁盘对账
  const raw = await options.kv.kvGet(studioExecutionStorageKey(key));
  if (!isStudioExecutionSession(raw)) return null;  // ② 断线时的 undefined 落在这里 = 「会话不存在」
  ...
}
async saveEvent(key, event) { return enqueue(async () => {
  const session = (await readSession(key)) ?? createEmptyStudioExecutionSession(key);  // ③ 造空会话
  appendExecutionEvent(session, event);
  cache.set(key, session);                          // ④ 投毒点：此后本会话内所有读都走这份 1 事件副本
  await writeSession(session);                      // ⑤ 断线时 kvSet 假成功；在线时把 1 事件覆盖到磁盘
  return session;
}); },
```

重连路径也不救：`entry.ts:182-184` 的 `executionStore.onConnected(() => chatUI?.activateSession(chatUI.sessionKey))` 最终仍调 `store.loadSession(key)` → ① 命中被投毒的 cache ⇒ **重连后读回来的还是那份 1 事件**。全文件没有任何 `cache.delete` / 重连失效 / dirty 集合。

**后果**（实测 REPRO-B）：桌面端刚启动、宿主权 socket 还没 open（或宿主重启、WS 抖动、8760 端口被占后重连退避中）时，用户在 DeepSeek 页面上做任何一次会被记录的动作（发一条消息 / 一次工具调用），该会话在内存里就被替换成「只有这一条事件」的会话，并且：

1. 断线期间的落盘**假成功**（`reportError=0`，宿主侧一个字节都没收到）；
2. socket 打开后 store 仍是 1 条而磁盘是 2 条（`[REPRO-B] socket 打开后 store=1 条 / 磁盘=2 条`）；
3. 重连后的下一次写入把这份截断会话**整块落盘**，磁盘内容从 `["旧页面上的第一轮","旧页面上的第二轮"]` 变成 `["新写的一轮","再写一轮"]` —— **原有轮次永久消失**，且全程没有任何错误提示。

这是本轮唯一的**数据丢失**级缺陷：受害者是用户已经写下的执行记录（也是远程端/工作台唯一的数据源，见 `workbench-execution-view.ts` 顶部注释「数据源只有宿主镜像的 StudioExecutionSession」）。丢完之后，远程端「新对话」里既没有旧内容、电脑端也找不回来。

**建议**（按优先级，①②必须同做才闭合）：

① store 把「连接」当作读写准入，而不是只收不用：`readSession`/`writeSession` 前判 `options.isConnected()`；未连接时**不得**把 `null` 当成「会话不存在」新建，改为保留事件进一个 `dirty: Map<key, StudioExecutionEvent[]>` 并 `report('studio execution deferred: host offline')`。
② `onConnected` 回调里 `cache.clear()`（或只清那些没有 dirty 积压的键），再把积压按 turnId 顺序重放。这条改动同时修掉 R15-02。
③ `host-client.kvSet/kvRemove` 在未连接时应 **reject**（与 `sendToolCall` 的 `no-host` 同形），⛔ 静默 `resolve()`——「什么都没做」不能对外宣称「做完了」。

**复现**：`复现用例/qd-r15-execution-offline.test.ts` → REPRO-B **实测失败 = 复现**；CONTROL（全程在线）通过 ⇒ 不是夹具恒红
**状态**：Verified-实证（真 host-client + 真 store + 真 shared 校验器，假物只有 WebSocket 与宿主 KV 存储）

### QD-R15-02 [P2] 断线期间的落盘失败既不报错也不重试：事件只活在内存，页面/宿主先关一步就永久丢

**证据**：同 `studio-execution-store.ts:141-149` 的 `saveEvent` 与 `:117-127` 的 `enqueue`：

```ts
function enqueue<T>(operation: () => Promise<T>, message = '…'): Promise<T> {
  const result = writeChain.then(operation);
  writeChain = result.then(() => undefined, (error) => { report(message, error); });  // 失败只 report，⛔ 重试、⛔ 回滚 cache
  return result;
}
```

配合 `host-client.ts:399` 的假成功，这条链上**连 report 都不会发生**（`kvSet` 没抛错）——比「report 了但没人看」更糟：观测面也是 0。
实测（REPRO-A）：断线时 `saveEvent` 返回 `事件数=4`（cache 完整，界面看起来一切正常），`磁盘事件数=3`、`reportError 次数=0`。

**后果**：这条与 R15-01 的区别在严重度而非形状——R15-01 里 cache 被截断（读也没了）；这里 cache 仍是全的，事件会在**下一次同会话写入**时顺带补上（读数 `[REPRO-A] 覆盖后磁盘内容=[...含"断线期间的第四轮"...]` 证明了补齐路径）。
真正丢的场景是「断线期间产生事件 → 之后这一轮没有再触发任何写入 → 用户关页面 / 桌面端退出」。此时那条事件（工具调用记录、最终答复）永久不落盘，重启后该轮在电脑端与远程端同时消失——表现为**工具记录断流**且无任何解释。
`STUDIO_EXECUTION_MAX_EVENTS=500` 的 `slice` 截断也在同一条 `writeSession` 路径上，一旦断线叠加长会话，丢弃是双向的。

**建议**：① `writeSession` 落盘失败或 `!isConnected()` 时把该 session 的关键差异（自 `updatedAt` 起的事件）记入 `dirty`，重连后重放（即 R15-01 建议 ②）；② `host-client.kvSet` 未连接改为 reject，让「假成功」至少变成一次可观测的失败；③ 短期止血可以在 `enqueue` 的 report 文案里带上 `key` 与事件类型，方便从日志判断丢了哪一轮。

**复现**：`qd-r15-execution-offline.test.ts` → REPRO-A 前两条断言（`reportError>0`、断线事件当刻落盘）**实测失败 = 复现**
**状态**：Verified-实证

### QD-R15-03 [P2] 远程端的宿主拒绝提示是「带外节点」，会被下一次执行会话整块重绘无声吃掉 ⇒ 用户点发送后什么都没发生
