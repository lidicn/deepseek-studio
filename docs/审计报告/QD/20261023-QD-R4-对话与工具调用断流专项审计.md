## 1. 发现

### QD-R4-01 [P1] 自动续跑遇 429 / 5xx / 断网：退避重试回调被自己的 `pending` 守卫挡死，循环静默停摆且 UI 永不复位

**证据**（HEAD 面，行号以 `git show HEAD:` 为准）：

```ts
// HEAD src/inject/main-world-interceptor.ts:937-938
async function autoContinueWithPow(): Promise<void> {
  if (!loopState.lastChatBody || pending.length === 0 || loopDepth >= MAX_LOOP) return;

// HEAD :955-957  发送续跑前清空 pending（F8 修复，防 XHR hook 重复注入）
pending.length = 0;

// HEAD :1043-1050  可重试错误：挂一个退避定时器，回调重新进入 autoContinueWithPow
} else if (verdict.verdict === 'retryable') {
  errorRetryCount += 1;
  loopState.streamActive = false;
  if (autoContinueTimer) clearTimeout(autoContinueTimer);
  const delay = verdict.retryAfterMs ?? errorBackoffMs(errorRetryCount - 1);
  autoContinueTimer = setTimeout(() => { autoContinueTimer = null; autoContinueWithPow(); }, delay);
}
```

盘面同构：`:1141`（守卫）、`:1159`（清空）、`:1227-1235`（重试分支）。

**根因链**：续跑请求发出前 `pending.length = 0` → 请求失败（429/5xx/status 0/200 错误体）→ 定时器 2s/4s/8s 后调用
`autoContinueWithPow()` → 第一行守卫看到 `pending.length === 0` → **直接 return**。`MAX_ERROR_RETRIES=3` 的预算一次都花不出去。

**后果**（两面实测）：

- 工具续跑中途遇到一次 429 / 5xx / 断网，**不会重试、不会补发、不会给最终回答**。用户在页面上看到的就是「工具卡片转完，回复停了」。
- HEAD 面：重试分支不调用 `finishStepFlow`，`setBusy(false)` 永不执行 → 步骤流定在「running」；用例实测 `setBusy` 调用序列只有 `[[true]]`，`finishAssistantMessage`/`appendError` 均为 0 次。
- 盘面：重试分支补了一次 `chatUI.finishAssistantMessage({recordFinal:false})`，但 `finishAssistantMessage` 本身不碰 busy（`src/ui/studio-chat-ui.ts:767-804`，`setBusy` 在 `:806-809`）→ 状态栏永远停在「执行中…」。用例实测 `{"setBusy":[[true]],"finishAssistantMessage":[[{"recordFinal":false}]],"appendError":[]}`。
- 宿主侧同样被拖住：页端不发续跑 → `waitForNextReply` 空转到 `stepTimeoutMs = 120_000`（`src/host/engine/web-engine.ts:121`）才返回；盘面 00:06 的在飞修改会补一条「等待模型续跑超时」错误（`agent-loop.ts:146-154`），HEAD 则把它当成空最终回答收起。两种都要等满 **2 分钟**，根因仍是页端 0 次重试。
- 直接推翻验收文档的承诺：`docs/前端开发计划/Studio自验收-20261022.md:313` 写「指数退避重试 3 次，耗尽即停」——实测 **0 次**。

**建议**：

1. 重试不要走 `pending` 守卫。给 `autoContinueWithPow` 加显式 `retry?: boolean`（守卫改为 `pending.length === 0 && !retry`），或把「发送续跑 body」抽成不依赖 `pending` 的 `sendContinuation(body)`，重试只重发上一份 body。
2. 重试不应消耗 `loopDepth`（当前入口 `loopDepth += 1`，重试会吃工具步数）；成功轮要重置 `errorRetryCount`（盘面已加，HEAD 未加）。
3. 错误预算耗尽 / fatal 时统一走 `finishStepFlow({code,message})`，保证 `setBusy(false)` 与错误可见。
4. 回归用例：把 `复现用例/qd-r4-repro.test.ts` 第 2 腿转正进 `tests/desktop/`。

**复现**：`复现用例/qd-r4-repro.test.ts` 第 2 腿（429）。两面实测均失败：

```
HEAD: R4 request count after retry window: 2          （期望 3 = 页面 + 续跑#1 + 重试）
      R4 retry after-window UI: {"setBusy":[[true]],"finishAssistantMessage":[],"appendError":[]}
盘面: R4 request count after retry window: 2
      R4 retry after-window UI: {"setBusy":[[true]],"finishAssistantMessage":[[{"recordFinal":false}]],"appendError":[]}
```

正控（同一 harness 能看见真实续跑）：第 1 腿在续跑回复里再投一个工具调用 → 请求数 3，用例通过。
日志里确实进入了重试分支：`auto-continue retryable: status=429 reason=rate-limited, retry 1/3 in 2144ms`，此后 30s 无第二次请求。

**状态**：**Verified-实证（HEAD + 盘面双面复现，含正控）**。

### QD-R4-02 [P1] 工具标签被流截断：XHR 路径从不 `parser.flush()`，fetch 路径 flush 后只取 `calls`（恒空），半截标签静默消失

**证据**：

```ts
// HEAD :683-707  XHR readyState>=3 与 =4 共用：只 flush SSE 提取器，不 flush 工具解析器
let visible = sse.feed(part);
if (xhr.readyState === 4) visible += sse.flush();
...
const { calls } = parser.feed(rawDataText || visible);
for (const c of calls) forward(c);
// —— 全文没有 parser.flush()

// HEAD :482-484  fetch 路径 flush 了，但只取 calls；flush 的残留 tail 被丢弃
const fin = parser.flush();
for (const c of fin.calls) forward(c);
// 尾部 flush 不发内容（原始 chunk 已转发）
```

`src/inject/streaming-tool-parser.ts` 的 `feed()` 把未闭合标签留在 `tail`；`flush()` 按设计返回 `{ calls: [], clean: tail }`
（`streaming-tool-parser.ts:91-95`，未闭合标签**永远不会**变成 call）。因此两条路径对「流在标签中间断掉」的处理都是：不执行、不报错、不续跑。

**同族的第三处尾部丢弃**：`DeepSeekSseFrameDecoder` 提供了 `finish()`（`deepseek-sse-frame-decoder.ts:31-39`），
但 interceptor 只调 `push()`（HEAD `:629` / 盘面 `:791`）。末尾没有空行终结的 frame 不会进入 `rawDataText`；
而喂给工具解析器的是 `rawDataText || visible`，只要前面有过完整 frame，含 `sse.flush()` 尾文本的 `visible` 就不会被使用。
⇒ 最后一个事件即使内容完整、只是缺 `\n\n`，其文本也只显示不解析，恰好落在这个事件里的工具标签会丢。

盘面同样：fetch `:659-661` 只取 `fin.calls`；XHR `:823-831` 只 `feed()`，无 `flush()`。

**后果**：模型输出 `<shell_exec>{"command":"echo one"` 时网络断/被截断：
- 工具**不会执行**（用例实测 `tool calls = 0`）；
- 不会出现错误提示（`appendError = 0`）；
- 不会触发续跑（`chat requests = 1`）；
- 盘面还会把这段含半截标签的文本当作**完整最终回答**收尾（`finishAssistantMessage = 1`），HEAD 则把气泡留在流式态。

这正是「工具调用断流」最典型的失效模式：模型以为要干活，宿主什么都没收到，用户只看到半句话。

**建议**：

1. 在 XHR `readyState === 4` 时调用 `parser.flush()`，不要只看 `calls`——`clean`/`tail` 非空即表示有未闭合标签。
2. 检测到未闭合标签时按可重试错误处理（复用 `classifyResponse` 的 retryable 语义），或者在 UI 明确提示「工具调用被截断，已停止本轮」并复位 busy。
3. fetch 路径同样处理 `fin.flush` 的 tail。
4. 转正第 3 腿为回归用例。

**复现**：第 3 腿喂 `我先执行。` + `<shell_exec>{"command":"echo one"`（无闭合标签）后结束流：

```
HEAD: R4 truncated: tool calls = 0 chat requests = 1 appendError calls = 0 finishAssistantMessage calls = 0
盘面: R4 truncated: tool calls = 0 chat requests = 1 appendError calls = 0 finishAssistantMessage calls = 1
```

**状态**：**Verified-实证（HEAD + 盘面双面复现）**。

### QD-R4-03 [P2] 没有「流是否完整」判据：正常断流被当作完成；盘面新增的「空转续跑 3 次封顶」整段不可达

**证据**：

- 全仓 `src/inject/**` 无 `finish_reason` / 流完成哨兵判断（`grep` 仅命中 `sse-text-extractor.ts:27/131` 对 `[DONE]` 的「忽略」）。`onStreamEnd` 只看 `pending` 与 `stepFlow`：
  ```ts
  // HEAD :901-917
  if (pending.length > 0 && loopState.lastChatBody && loopDepth < MAX_LOOP) {
    scheduleAutoContinue();
  } else if (stepFlow && loopDepth === 0) { stepFlow.finish(...); }
  ```
  没有「本轮是否真的收到了完成信号」这一维。模型吐到一半网络断掉（没有任何工具）→ 走 else → 被当成正常完成。
- 盘面的空转封顶（`:1054-1069`）：
  ```ts
  if (pending.length === 0) {
    idleContinueCount += 1;
    if (idleContinueCount > MAX_AUTO_CONTINUE) { ...停止... }
  }
  ...
  autoContinueTimer = setTimeout(() => { autoContinueTimer = null; autoContinueWithPow(); }, 1000);
  ```
  但 `autoContinueWithPow` 的守卫（`:1141`）要求 `pending.length > 0`。而 `scheduleAutoContinue()` 的**全部**调用点都保证 pending>0：
  `:985/:1018/:1040` 紧跟在 `pending.push(...)` 之后；`:1080` 外层 `if (pending.length > 0)`；`:1261` 外层 `if (pending.length > 0)`。
  ⇒ `pending.length === 0` 分支**永远不执行**；即便执行，1s 后 `autoContinueWithPow` 也会在守卫处 return。**空转续跑一次都发不出去。**
- HEAD 面连 `MAX_AUTO_CONTINUE` 都没有 import（只在盘面 `:24`）。

**后果**：无工具的回复被截断时，没有任何恢复动作，也不会提示；用户只能自己发现「回答没说完」再手动追问。
盘面文档所宣称的「连续 3 次输出不完整才停」并未生效——实际上第 1 次就直接停（且不提示）。

**与既有验收结论对撞**：`docs/前端开发计划/Studio晚轮验收-20261022.md` 的 B1-5 复核段写
「实际放行 3 次空转、第 4 次停」「已复核 finishStepFlow 在空转封顶路径上的兜底是完备的」。
本轮实测：**0 次放行**，该段结论不成立（只核了计数器比较，没有核「定时器回调能否穿过守卫」）。

**建议**：

1. 先加完成哨兵：记录本轮是否见到 `[DONE]` / `finish_reason`；未见即视为截断，走 retryable 重发（沿用 QD-R4-01 修好后的重试通道）。
2. 空转封顶要么接到一条不依赖 `pending` 的发送通道（与 QD-R4-01 同修），要么删除该死代码并同步修正验收文档。
3. 补一条「无工具、流在中途结束」的用例，断言要么重发、要么出现可见错误。

**复现**：第 3 腿已证明「截断流无恢复」；无工具截断走同一 `onStreamEnd` else 分支，属同一条代码事实。
**状态**：**Verified-代码事实 + 实证（截断流无恢复）**。死代码判定为静态可证（全部调用点逐一核过）。

### QD-R4-04 [P1·条件] 用户点「停止」后循环继续：abort 的 status 0 被当成可重试网络错误，pending 工具结果触发新的续跑请求

**证据**：

```ts
// HEAD :901-903  流结束补查 pending → 直接续跑
loopState.onStreamEnd = () => {
  if (pending.length > 0 && loopState.lastChatBody && loopDepth < MAX_LOOP) {
    scheduleAutoContinue();
```

- 用户点停止 → `xhr.abort()` → `readyState=4, status=0`，与「网络断开」**不可区分**；
- `classifyResponse(0)` → `retryable / network-error`；
- 此时若本轮工具结果已经回来（`pending.length > 0`），`onStreamEnd` 照常调度 → 1s 后发出新的续跑请求。
- 盘面额外显示错误气泡（`:838-849`），文案是「服务器暂时无法访问。本轮消息不会自动重发，请检查网络后手动重试。」——但它是用户主动停的，而且**紧接着又自动发了一次**，文案与行为互相矛盾。

**后果**：停止按钮不是停止。用户按下停止后，宿主仍会发出续跑请求，模型可能继续输出并**继续触发工具调用**（shell/file/mcp）——
这是一条用户控制面被绕过的路径，不只是多发一次请求。

**建议**：

1. 在 XHR hook 里包 `XMLHttpRequest.prototype.abort`，给该 xhr 打 `__dsAborted = true`；
2. `readyState === 4` 分类前先看 `__dsAborted`：命中则**不分类、不重试、不续跑**，清 `pending`、取消 `autoContinueTimer`、`finishStepFlow()`/`setBusy(false)`；
3. 盘面的错误气泡在 abort 场景不要出（或改成「已停止」而不是网络错误）。

**复现**：第 4 腿：readyState 3 时收到工具标签 → 工具结果落库 → `xhr.abort()` → 推进 5s：

```
HEAD: R4 abort: appendError = []
      R4 abort: chat requests after stop = 2        （期望 1）
盘面: R4 abort: appendError = [["network-error","服务器暂时无法访问。本轮消息不会自动重发，请检查网络后手动重试。"]]
      R4 abort: chat requests after stop = 2
```

**状态**：**Verified-实证（HEAD + 盘面双面复现）**。条件：工具结果在用户按下停止前已经回到 `pending`（长任务中很常见）。

### QD-R4-05 [P2] 新用户消息继承上一回合的 pending 工具结果：prompt 被注入 `[tool-result:...]`；定时器与 idle 计数也不清

**证据**：

```ts
// HEAD :921-935  新用户消息只重置这三样
loopState.onNewUserMessage = () => {
  collectedExecutions.length = 0;
  loopDepth = 0;
  errorRetryCount = 0;
  loopState.sseErrorSeen = null;
  loopState.autoReplyHadTools = false;
  ...
};
// 没有 pending.length = 0，也没有 clearTimeout(autoContinueTimer)

// HEAD :377-403  prepareOutgoingBody：任何 chat 请求只要 pending>0 就注入并清空
const hasResults = pending.length > 0;
...
if (hasResults) prompt = reinjectIntoPrompt(prompt, pending.slice());
...
pending.length = 0;
```

盘面 `onNewUserMessage`（`:1113-1138`）同构，仍不清 `pending`/`autoContinueTimer`/`idleContinueCount`。

**后果**（实测）：任务 A 的工具结果刚落库，用户马上发任务 B → B 的 prompt 末尾被追加：

```
task B

【工具执行结果】
[tool-result:shell_exec]
ok
```

模型会把 A 的工具结果当成 B 的上下文，轻则回答被污染，重则基于错误前提继续调工具。
另有代码事实风险：若 1s 续跑定时器在 B 发出后仍存活，且 A 的**另一个**迟到工具结果在定时器触发前落库（pending 重新 >0），
定时器会用 B 的 `lastChatBody` + 已清空的 `collectedExecutions` 发出一轮「续跑 B」的请求；`autoContinueWithPow` 不检查
`loopState.streamActive`，因此这轮请求可能在 B 仍在流式输出时并发发出（未构造「双工具 + 慢宿主 + 1s 内发新消息」用例，标代码事实）。

**建议**：`onNewUserMessage` 里一并执行 `pending.length = 0; if (autoContinueTimer) { clearTimeout(autoContinueTimer); autoContinueTimer = null; } idleContinueCount = 0;`；
更稳的做法是给每个回合一个 `turnSeq`，定时器回调校验 `turnSeq` 未变才发送。

**复现**：第 5 腿：A 发工具调用 → 结果落库 → 立即发 B，检查 B 的请求 body：

```
HEAD/盘面: R4 cross-turn: second prompt tail = "...（技能目录说明）...\n\ntask B\n\n【工具执行结果】\n[tool-result:shell_exec]\nok"
           R4 cross-turn: tool calls before B = 1
```

**状态**：**Verified-实证（prompt 污染，HEAD + 盘面双面）；定时器竞态为 Verified-代码事实**。

### QD-R4-06 [P2·条件] fetch 流中途抛错：`controller.error(err); return;` 既不落 `streamActive=false` 也不触发 `onStreamEnd` → 工具循环卡死

**证据**：

```ts
// HEAD :485-488（盘面 :662-665 同构）
} catch (err) {
  controller.error(err);
  return;
}
controller.close();
if (loopState) {
  loopState.streamActive = false;
  if (typeof loopState.onStreamEnd === 'function') { ... }
}
```

**后果**：若页面用 `fetch` 拉流，读流中途抛错（网络重置、解码异常）会从 catch 直接 return：
`streamActive` 永远保持 `true`，`onStreamEnd` 不执行。此后工具结果回来时，
`forward` 的 `.then` 里 `if (!loopState.streamActive && ...) scheduleAutoContinue()` 永远不成立 → 循环停在中途，
UI 也没有收尾（`finishStepFlow` 不会调用）。

**建议**：把 `streamActive=false` + `onStreamEnd()` 移到 `finally`（或在 catch 里执行），并给 `controller.error` 路径补错误提示/复位。

**复现**：未构造（需要让 fake fetch 的 reader 在流中途抛错；可以先确认页面实际走 fetch 还是 XHR 再决定是否升级）。
**状态**：**Not Verified（条件触发）**——代码事实成立，但未确认当前 DeepSeek 页面走 fetch 拉流。
