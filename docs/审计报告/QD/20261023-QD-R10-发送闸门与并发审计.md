## 1. 发现

### QD-R10-01 [P1] 四条发送入口只有面板一条受 busy 闸门约束：TaskLoop 在飞时面板仍可发送，两条 send 并发写同一页面输入框

**证据**：

```ts

const bot = options.host.bots.get(botId);
if (bot.running) {

await bot.sendMessage(text);
```


另外三条入口走 `TaskLoop`，**完全不进这道闸门、也不在任何地方登记 running**：

```ts

async function agentSender(text: string): Promise<string> {

```


```ts

  onTaskTrigger: async (task) => { ... await agentSender(task.payload.prompt); ... },

// automation.ts：cron 回调直接 void executeTask，没有队列
```

第四条入口 `agent.sendMessage`（`desktop-host.ts:855-875`）同样每次 `new` 一个 TaskLoop；`agent.running`（`:877-879`）也仍返回 `mainBot.loop.running`。而 `WebEngine.send` 没有 in-flight 锁（`web-engine.ts:225-305`），页面只有**一个输入框**。

**复现读数**：

- CONTROL-A：`AgentLoop` 在飞时 `loop.running=true`，第二次 `send` 得到 `agent-busy` ⇒ 面板路径的闸门本身好使。
- REPRO-A：TaskLoop 在飞时 `loop.running=false`，面板 `send` **没有被拒绝**（`panelErr=""`），引擎并发度 `maxConcurrent=2`。
- REPRO-C：两个并发 `engine.send` 共用页面输入框，`sent=["会乙"]`——**"会甲"从未送出**；A 读到的是 `答复:会乙`（B 的答复），B 也读到同一句。

**后果**：

- **用户消息被覆盖丢失**：先插入的文本在它自己的 `chat-send` 之前就被后一条 `chat-insert` 覆盖，页面只发出后一条；先发方的 `chat-send` 因输入框已空而空转（`chat-send.ts` 的 circle-button 路径正是"点到即 ok"）。
- **答复串线**：两个 `waitForNextReply` 轮询同一个"最后一条消息"，谁先稳定谁先拿走，另一条通常拿到同一句。REPRO-C 里 `ra` 与 `rb` 同为 `答复:会乙`。
- **触发面是正常功能组合**：automation prompt 任务按 cron 触发（`void executeTask`，无串行化）、HTTP 外部调用、面板聊天三者任意两条同时发生即可。`kernelHistory` 也只有一份（`desktop-host.ts:832`），并发 TaskLoop 的提示词会互相混入（REPRO-B：第二个任务的 prompt 含"任务甲"）。
- 面板在 ack 前就清空输入（`agent-panel.ts:221-226`）；一旦宿主以 `agent-busy` 拒绝，用户输入已丢，只剩一行 `操作失败：agent-busy` 写进画布（`agent-panel.ts:206-211`），下一次执行会话重绘即消失。
- `TaskLoop` 没有接 `stopFlag` / `AbortSignal`（`agentSender` 未传 `signal`），所以 R9 的停止链也够不到这些运行中的任务。

**建议**：在**页面/引擎边界**加单一 lease（按 botId 的单飞队列），由面板、HTTP、automation、facade 四条入口共同遵守；automation 宜排队（并在 ack 里带队列位置），面板宜在入队前把输入保留到 ack。`running` 状态应同时覆盖 AgentLoop 与 TaskLoop。补一条宿主级双入口回归用例。

**状态**：Verified-实证（并发机制）+ 代码事实（生产接线）

### QD-R10-03 [P3] `agentSender` 的空答复回退会取任意 bot 的 assistant 事件，不校验 botId / 是否本轮

**证据**：

```ts
// src/host/desktop-host.ts:791-799 —— 所有 bot 的事件都进同一个监听集合
const botRegistry = createBotRegistry({
  onEvent: (event) => {
    for (const cb of agentListeners) { ... cb(event); ... }
  },
});
// src/host/agent-loop.ts:72-75 —— 事件带 botId
const stamped = botId ? { ...event, botId } : { ...event };
```

```ts
// src/host/desktop-host.ts:891-895 —— 不筛 botId、不筛本轮
const listener = (event: AgentLoopEvent) => {
  if (event.type === 'assistant' && event.text) {
    finalAnswer = event.text;
  }
};
```

TaskLoop 自身不产生 AgentLoopEvent，因此 `finalAnswer` 只可能来自**别的** loop（面板的 `AgentLoop` 或聊天室成员 bot）。当本轮 `result.content` 为空时，`:907` 的回退就会把那次别的会话的答复返回给 API 调用方。

**后果**：`/v1/agent/send` 在自身超时/空结果时，可能返回另一个 bot（或另一个用户动作）的答复；调用方无法分辨。聊天室成员 bot 活动 + 并发 API 调用即是触发面。

**建议**：按 `event.botId === 'main'` 且 `event` 产生于本次请求开始之后过滤；更稳妥的是删除回退，直接返回 `{ content, stopReason }` 结构，由调用方决定如何报错。

**状态**：Verified-代码事实（未构造：`agentSender` 是 `createDesktopHost` 闭包，整套宿主夹具成本高；最小修法已给出）

## 4. 结论与修复顺序

1. **R10-01（P1）**：在页面/引擎边界建立单一 lease，覆盖面板、HTTP、automation、facade 四条入口；TaskLoop 接入同一个 stop 信号；面板 ack 前不清输入。
2. **R10-02（P2）**：`agentSender` 检查 `stopReason` / `completion`，空结果不得回 200 成功；automation 记失败。
3. **R10-03（P3）**：`finalAnswer` 回退按 botId 与本轮时间过滤，或整体删除。
