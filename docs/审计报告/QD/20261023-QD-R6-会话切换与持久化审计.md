## 1. 发现

### QD-R6-01 [P2] `renameSession` 不删旧索引项：每次「新对话→拿到 chat id」都留一条幽灵条目

**证据**（`src/ui/studio-execution-store.ts:171-190` + `:107-127`）：

```ts
// renameSession
await writeSession(renamed);                       // 里面只过滤 e.key !== renamed.key
await options.kv.kvRemove(studioExecutionStorageKey(fromKey));

// writeSession
const sessions = index.sessions.filter((entry) => entry.key !== session.key);
sessions.unshift(nextEntry);
const evicted = sessions.splice(STUDIO_EXECUTION_MAX_SESSIONS);
...
for (const entry of evicted) await options.kv.kvRemove(studioExecutionStorageKey(entry.key));
```

`writeSession` 只替换**目标键**的条目，`fromKey` 条目原样保留；随后存储被 `kvRemove`，索引里于是留下
「键在、会话不在」的幽灵条目。

**后果**：
- 会话索引被幽灵条目占位。`STUDIO_EXECUTION_MAX_SESSIONS = 50`，而 `writeSession` 淘汰时会 `kvRemove`
  被淘汰键的**存储**——幽灵条目本身不需要存储，却参与排序与计数 ⇒ 幽灵足够多时，**真实会话会被挤出去并删除存储**。
- 每次新对话迁移 `route:… → chat:<id>` 都会产生一条；`route:` 键按路径归一化，路径种类越多积累越快。
- 索引是将来会话列表/恢复的取材面，幽灵条目会让条目数与真实可恢复数不一致。

**复现**：`REPRO-A` 实测失败：`expected [ 'chat:x', 'route:/' ] to deeply equal [ 'chat:x' ]`。

**建议**：`renameSession` 在 `writeSession` 前把 `fromKey` 从索引移除（或给 `writeSession` 传 `replaces?: string[]`）；
更稳的做法是 `writeSession` 以存储是否存在为准做一次惰性清理。

**状态**：Verified-实证（盘面复制树）。

### QD-R6-02 [P2｜条件] `clearAll` 只按索引清，孤儿会话键永远清不掉

**证据**（`:191-208`）：

```ts
const index = await loadIndex();
for (const entry of index.sessions) await options.kv.kvRemove(studioExecutionStorageKey(entry.key));
for (const key of cache.keys()) await options.kv.kvRemove(studioExecutionStorageKey(key));
cache.clear();
await options.kv.kvRemove(STUDIO_EXECUTION_INDEX_KEY);
```

清理集合 = 索引条目 ∪ 内存缓存，**不是** KV 里实际存在的会话键。`saveEvent` 先写会话（`:108`）后写索引（`:120`），
中间失败/进程退出、索引损坏、或旧版本遗留都会留下「有会话、无索引项」的孤儿键；`clearAll` 永远看不到它们。

**后果**：「清空本机记录」后，宿主 KV 里仍保留对话正文（可能是整段工具输出），刷新/新版本恢复逻辑若改按前缀扫描即可重新读出。
属删除不彻底（隐私面），不是当前 UI 可见故障。

**复现**：`REPRO-B` 实测失败：写入一个索引外的 `chat:orphan` → `clearAll()` → 键仍在。

**建议**：`clearAll` 改为按 `STUDIO_EXECUTION_SESSION_PREFIX` 前缀枚举 KV 键删除（宿主需提供 `kvList`/前缀删除），
索引只用于排序与展示；至少在 `host-client` 侧提供 `kvClearPrefix`。

**状态**：Verified-实证（盘面复制树，条件=存在孤儿键）。

### QD-R6-03 [P2] 每个事件重写整份会话：20 个 8KB 事件实测写放大 **10.52×**，500 事件量级约 250×

**证据**（`:149-156` + `:107-127`）：

```ts
async saveEvent(key, event) {
  return enqueue(async () => {
    const session = (await readSession(key)) ?? createEmptyStudioExecutionSession(key);
    appendExecutionEvent(session, event);
    cache.set(key, session);
    await writeSession(session);          // 整份 session（最多 500 事件）经 kvSet 走 WS
    return session;
  });
}
```

`writeSession` 每次都 `kvSet` 整份会话 + 读改写索引。`recordEvent` 对每个事件 `void persistence.saveEvent(...)`
（`studio-chat-ui.ts:540`），事件按流式节奏产生 ⇒ 写链长度为事件数的二次方量级。

**实测**（REPRO-D）：20 个 `tool-result`、每个 8KB ⇒ 终态会话 166,583 字节，累计写入 **1,751,755 字节**，
放大 **10.52×**。若跑满 500 事件、单事件按上限 16KB 估，终态约 8MB，累计写量在 GB 级。

**后果**：
- 宿主 WS 与磁盘被重复写；`kvSet` 有 30s 超时（`host-client.ts:400-407`），慢宿主上写链越排越长；
- `loadSession` 开头 `await writeChain`（`:103`）⇒ **切换会话/刷新恢复要排在整条写链后面**，表现就是「切会话转圈、像断流」；
- 写链中任一写失败只报 `reportError` 不停止后续（`:129-138`），失败会静默累积。

**复现**：`REPRO-D` 实测失败：`expected 10.5158… to be less than 2`，`R6 write amplification: { finalBytes: 166583, totalWritten: 1751755 }`。

**建议**：改成增量落盘——会话按事件追加写（宿主 KV 支持 append 或按 `turnId` 分块），或至少对 `saveEvent` 做
200–500ms 合并写；索引只在「标题/updatedAt 变化」时写。

**状态**：Verified-实证（盘面复制树）。

### QD-R6-04 [P3] `limitToolPayload` 按字符数判限、按字节截断：中文载荷可超预算近 3 倍

**证据**（`src/shared/studio-execution.ts:203-220`）：

```ts
if (serialized.length <= limit) { ... return value; }      // UTF-16 code units
return { truncated: true, originalBytes: byteLength(serialized), preview: truncateUtf8(serialized, limit) };
```

判定用 `length`（UTF-16 码元），截断与 `originalBytes` 用 UTF-8 字节。10,000 个汉字 = 10,013 码元 < 16,384，
**直接原样返回**，实际 UTF-8 约 30KB；英文则被严格限制在 16KB。

**后果**：中文工具结果/参数的实际落盘量可达预算 3 倍，放大 R6-03 的写放大；同一上限对不同语言不等效。

**复现**：`REPRO-C` 实测失败：`expected false to be true`（`'truncated' in limited` 为 false）。

**建议**：判定也改用 `byteLength(serialized)`；`truncateUtf8` 已有按字节切的能力。

**状态**：Verified-实证（盘面复制树）。

### QD-R6-05 [P3] 事件上限按条截断会把首个 `user-message` 裁掉 → 会话标题漂移

**证据**：`appendExecutionEvent`（`studio-execution.ts:234-244`）只做 `splice(0, len - 500)`；
`sessionTitle`（`:246-252`）取**第一条** `user-message`，没有则回退 `routeKey ?? key`；
`writeSession` 每次重算标题写进索引（`studio-execution-store.ts:110-115`）。

**后果**：会话事件超过 500 条后，原始标题来源被裁掉，索引里的标题变成 `route:…`/`chat:…` 键本身；
同时 `replayExecutionSession` 从第 501 条开始重放，工具卡可能没有对应的 user-message 上下文。
（内容截断是设计上限，问题在**标题依赖被截断的数据**且无持久化标题字段。）

**复现**：`REPRO-E` 实测失败：`expected +0 to be 1`（500 条后续事件后 user-message 计数为 0）。

**建议**：`StudioExecutionSession` 增加 `title` 字段，创建时定格；重放时若首个事件不是 user-message，补一个“更早记录已截断”的说明。

**状态**：Verified-实证（盘面复制树）。

## 3. 跨轮去重

- R6-03 是 R5 系列「切会话/刷新」体验劣化的底层放大器；R5-03 的持久化污染也经此写链落盘，两者叠加时更难复现。
- R6-01 的幽灵条目会让 R6-02 的 `clearAll` 多删一次（无害），但不会补清孤儿键，二者不是同一根因。
- R6-04 与 R6-03 同属「载荷预算」，修 R6-04 可让 R6-03 的实测放大在高载荷下更接近名义值。
