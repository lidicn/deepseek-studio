## 1. 发现

### QD-R14-01 [P1] `failAllPending` 不分连接清扫：关掉任一标签页会把别的页正在等的工具判成失败、把别个 bot 的待决同意判成 deny

**证据**：`src/host/page-runtime.ts`

```ts
// :186-187  pending 表按 callId 存，每条都记了归属连接
const pendingDispatch = new Map<string, { ownerId: string; resolve: (r: ExecuteResult) => void; timer: ... }>();
const pendingConsent = new Map<string, { ownerId: string; resolve: (d: ConsentDecision) => void; timer: ... }>();

// :194-207  清扫时无条件结算全部，⛔ 按 ownerId 过滤
function failAllPending(reason: string): void {
  for (const [id, p] of pendingDispatch) {
    clearTimeout(p.timer); pendingDispatch.delete(id);
    p.resolve({ ok: false, error: reason });
  }
  for (const [id, p] of pendingConsent) {
    clearTimeout(p.timer); pendingConsent.delete(id);
    p.resolve('deny');
  }
}

// :442-443  任一连接关闭/出错都触发整表清扫
ws.on('close', () => { clients.delete(id); failAllPending('page-disconnected'); options.onDisconnect?.({ id, botId: rec.botId }); });
ws.on('error', () => { clients.delete(id); failAllPending('page-disconnected'); options.onDisconnect?.({ id, botId: rec.botId }); });
```

而回执路由是**认连接**的（`:303` `if (p && p.ownerId === id)`、`:380` 同样）——`ownerId` 在 :185 的注释里被写成设计意图（「跨连接的回执一律忽略」），`dispatch`/`requestConsent` 也在 `:472` / `:488` 老老实实绑了 `ownerId: picked.id`。
⇒ **结算侧认连接，清扫侧不认**。这套防护只做了一半：QD-R2-03 加的 `ownerId` 挡住的是「B 连接冒充回答 A 的调用」，没挡住「B 连接关闭时替 A 做了决定」。

**后果**（三条，按危害排序）：

1. **工具断流（假失败）**：同一 botId 开两个 DeepSeek 标签页时，`pickClient` 返回**第一个** ready 的可信页。宿主把工具发给页 1，用户关掉页 2（甚至页 2 是 duplicate-account 的 untrusted 连接，它压根没收到 dispatch），`failAllPending` 立刻把那次待决工具判成 `{ok:false, error:'page-disconnected'}`。
   这条假失败会**原样回填给模型**——模型据此认为工具失败，常见后续是重发同一条 `chat-send`（重复插卡/重复发送）或直接放弃任务。实测读数：`{"ok":false,"reason":"page-disconnected"}`，同一时刻 owner 连接的 `readyState=1`（OPEN）且已经收到 `dispatch`。
2. **真结果被丢弃**：条目已在清扫时 `delete`，页 1 随后送达的真实 `result` 走到 `:302-303` 时 `pendingDispatch.get(callId)` 为空，被静默忽略。用户侧表现为「工具明明跑完了，宿主这边却没有结果」——这是一条无声的断流，没有任何错误横幅。
3. **同意被代答 deny**（REPRO-B，跨 bot 同样中招）：botB 的工具正在等用户在 botB 页面上点同意弹窗，此刻关闭**无关的 botA 页面**，`pendingConsent` 被整表 `resolve('deny')`。用户后来真点了「允许」也没有效果（`:380` 的 `ownerId` 匹配到已删除的条目）。实测读数：`{"ok":false,"reason":"consent-denied"}`，botB 连接 `readyState=1` 且其 `consent-required` 弹窗仍未应答。
   ⇒ 危害不止「这一次工具没跑」：**用户看到的授权 UI 与宿主实际记录的决定不一致**，属于授权闸门面的完整性问题。

**建议**（二选一，推荐 ①）：

① 让清扫按归属过滤，与回执路由同一套标准：
```ts
function failAllPending(reason: string, ownerId: string): void {
  for (const [id, p] of pendingDispatch) {
    if (p.ownerId !== ownerId) continue;
    clearTimeout(p.timer); pendingDispatch.delete(id);
    p.resolve({ ok: false, error: reason });
  }
  for (const [id, p] of pendingConsent) {
    if (p.ownerId !== ownerId) continue;
    clearTimeout(p.timer); pendingConsent.delete(id);
    p.resolve('deny');
  }
}
```
`:442-443` 两处传 `id`。C4 的原意（「持有者断开 ⇒ 不要让调用方永久挂起」）完全保留——CONTROL-A 那种形状仍然绿。
② 若要保持「任一断开全清」的粗粒度语义，则在 `dispatch` 前用 `clients` 里连接的数量做准入：多于一条连接时改走「按 ownerId 单独挂 close 钩子」而不是共用清扫。①改动小、语义更正确，建议 ①。

**复现**：`复现用例/qd-r14-page-runtime-crossclose.test.ts` → REPRO-A / REPRO-B **实测失败 = 复现**（含 CONTROL-A/CONTROL-B 两条正控通过）
**状态**：Verified-实证（盘面 `06a53338`；⛔ 外推至 HEAD，HEAD 无此特性的相关面）

### QD-R14-02 [P3] `/agent-ws` 的执行索引「连接快照」与「实时广播」之间没有版本序：慢快照会把新索引覆盖成旧索引

**证据**：`src/host/agent-channel.ts`

```ts
// :198-204  连接建立时异步取一份快照下发，没有 seq / version / updatedAt 比较
function sendExecutionIndex(ws: WebSocket): void {
  void (async () => {
    const index = await options.getExecutionIndex?.();
    if (index) safeSend(ws, { type: 'execution-index', index });
  })();
}
// :233  connection 里调用；:191  broadcastExecutionIndex 里 for (const ws of sockets) safeSend(...)
```

两条腿写同一个客户端状态（面板的 `executionIndex`），但**没有任何顺序保护**：快照是 `await` 一个可能慢的宿主读取（`desktop-host.ts:1460-1545` 把它接到 kv/exec 读取上），广播是同步触发。

**后果**：面板刚连上、恰好有一次会话写入（或 `renameSession` 触发的 index 更新）时，客户端先收到**新**索引广播，随后收到**连接时刻之前**的旧快照并覆盖它。实测读数：下发顺序 `['chat:fresh', 'chat:old']`，最后生效的是 `chat:old`。
影响面是「工作台执行列表少一条 / 停留在旧内容」，需要用户重连或等下一次广播才自愈——属于**残留类**症状（旧视图赖着不走），不是断流。同时它也放大了 QD-R6-01 的幽灵条目效应：旧快照里可能含已经无效的键。

**建议**：给 `execution-index` 负载加一个单调比较锚并让客户端**只接受不回退**的快照——最省事的取法是用 `index.sessions` 里最大 `updatedAt` 或宿主侧一个自增 `rev`；`sendExecutionIndex` 与 `broadcastExecutionIndex` 共用同一条比较规则。若不想动协议，退一步：连接后 200ms 内补发一次广播（覆盖竞态窗），但这只是收窄窗口，⛔ 消除。

**复现**：`复现用例/qd-r14-execution-channel.test.ts` → REPRO-C **实测失败 = 复现**（CONTROL「没有并发广播时，连接快照正常下发」通过）
**状态**：Verified-实证。⚠ 定级 P3 而非 P2：自愈路径存在（任何后续广播即恢复），且只影响列表快照的**一次**覆盖，不丢数据。

### QD-R14-03 [P3] 工作台切会话时正文不重渲染 + `applyExecutionSession(null)` 早退 ⇒ 高亮已经换到 B，屏幕上仍是 A 的内容

**证据**：`src/ui/agent-panel.ts`

```ts
// :79-86  selectSession 清掉 activeSession，但只重绘列表，⛔ 调 renderActiveSession()
function selectSession(key: string): void {
  selectedSessionKey = key;
  activeSession = null;                       // :82
  renderExecutionIndex(sessionList, executionIndex, selectedSessionKey, selectSession);  // :88
}

// :114-120  null 直接早退，正文节点保持上一次渲染结果
function applyExecutionSession(session: StudioExecutionSession | null): void {
  if (!session) return;                       // 早退
  activeSession = session;
  renderActiveSession();
}
// :214  ack 路径把 null 送进来，正好落进上面的早退
if (data?.session !== undefined) applyExecutionSession(data.session ?? null);
```

对照组：`:102 / :108 / :126` 三处都会 `activeSession = null` 之后**紧跟** `renderActiveSession()`。⇒ 不是设计选择，是 `selectSession` 漏了那一行、`applyExecutionSession` 的 `!session` 早退把「清空」当成了「什么都不做」。

**后果**：直接对应本轮主题的第三条症状——**新对话里看得见旧对话**。两种触发形状：
1. 用户点选另一条会话（或点 R6-01 的幽灵条目，宿主回 `session:null`，见 EVIDENCE-D）：列表选中项变了，正文区仍是上一条会话的完整转录。用户会以为「新会话里残留了旧对话」，实际是 UI 没清屏。
2. 在该状态下发送：`canSend/canStop` 来自 `workbench-state`，与正文渲染无关，用户仍能发出去；写回的却是另一条会话——**看起来**串台了。

**建议**：① `selectSession` 在 `:82` 之后补一次 `renderActiveSession()`（与 :108/:126 同形）；② `applyExecutionSession` 把早退条件改成「只在 `session` 非空时赋值，其余一律 `activeSession = null; renderActiveSession()`」，让 `null` 明确表示「清屏」而不是「忽略」。两处都是 2-3 行的形状修正。

**复现**：⛔ DOM 用例。原因：`agent-panel.ts` 是带副作用的 DOM 模块，`import` 即执行 `startSocket()`（`:237` 起就是顶层 `addEventListener` / 顶层 `renderActiveSession()`），在 node/jsdom 下跑它需要 mock 整条 WS + 存储初始化链，成本超过这条 P3 的价值。宿主侧的**输入形状已实证**：`复现用例/qd-r14-execution-channel.test.ts` EVIDENCE-D 腿（通过）证明「索引里存在的键，宿主按契约回 `ack.ok===true, data.session===null`」，即 :214 那条 `null` 路径是真实可达的，不是假想。
**状态**：Verified-代码事实（`:82→:88` 与 `:114-120` 的缺失可直接静态证；缺 DOM 级终证）
