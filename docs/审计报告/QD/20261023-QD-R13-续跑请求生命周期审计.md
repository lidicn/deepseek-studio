## 1. 发现

### QD-R13-01 [P2] fetch 路径完全不捕获请求头：页面一旦走 fetch，续跑 PoW 的凭证集为空

**证据**：

请求头只有一个捕获入口——XHR 的 `setRequestHeader`：

```ts
// src/inject/main-world-interceptor.ts:802-808
proto.setRequestHeader = function (name, value) {
  const url = String(this.__dsUrl ?? '');
  if (url.includes('/api/v0/chat/') && capturedHeaders) {
    capturedHeaders[name] = value;
  }
  return origSetRequestHeader.apply(this, [name, value]);
};
```

fetch 路径只捕获 body，`init.headers` / `Request.headers` 从不进 `capturedHeaders`：

```ts
// src/inject/main-world-interceptor.ts:630-632
if (isDeepSeekChatEndpoint(url, method) && loopState && typeof init?.body === 'string') {
  captureChatRequest(init.body, loopState, diag);   // 只解析 body
}
```

而续跑把它当作唯一凭证来源：

```ts
// src/inject/main-world-interceptor.ts:1017（设计意图，逐字）
// v0.9 POW：捕获页面正常请求的 headers（Authorization / X-App-Version 等）
// src/inject/main-world-interceptor.ts:1391-1394
const filteredHeaders = filterReplayableHeaders(capturedHeaders);
const powHeaders = await createPowHeaders(filteredHeaders);
```

**后果**：

- 页面若用 fetch 发对话请求（或某次 A/B 分支/站点改版切到 fetch），`capturedHeaders` 为空；
  续跑先拿空头去 `POST /api/v0/chat/create_pow_challenge`，再拿空头发 completion。
  若服务端要求 `Authorization` 而非仅 Cookie，**第一次续跑就失败**，表现是「工具执行完，回复停了」。
- 该缺陷是条件性的：`docs/Audit/20261017-对话开始服务器暂时不可用-根因审计.md:106` 的真机日志显示，
  10-17 的页面走 XHR 且捕获到了完整头集；因此**今天未必触发**，但一旦传输层变化即全量失效。
- 同样的空头还会被当作「重放头」传给 challenge 与 completion，服务端风控可能记为匿名请求。

**建议**：

1. 在 fetch hook 的 chat 分支里补捕获：`init?.headers` 为 `Headers` 时用 `forEach`，为数组时按
   `[k, v]` 展开，为普通对象时 `Object.entries`；`input` 是 `Request` 时读 `input.headers`。
2. 只捕获 `/api/v0/chat/` 前缀（与 XHR 同口径），避免把其它 API 的头混进来。
3. 回归腿：同一用例分别以 XHR / fetch 发页面请求，断言两条路径下 `createPowHeaders` 入参都含 `authorization`。

**复现**：

- `复现用例/qd-r13-continuation-http.test.ts` 第 2 腿（页面 fetch + `init.headers`），与第 1 腿（XHR 正控）成对。
- 实测：正控 `authorization=Bearer captured`；fetch 腿入参 key 列表为 `[]`。
- 状态：**Verified-实证**（捕获缺口）；**影响为条件性**（服务端是否只认 Bearer 无法离线验证）。

### QD-R13-02 [P2] 续跑 XHR 无超时、无 `ontimeout`：连接挂起时整轮永久停在 running，且污染后续轮次

**证据**：

续跑请求只依赖 `readyState === 4` 的回调来推进，未设置任何超时：

```ts
// src/inject/main-world-interceptor.ts:1399-1417（节选）
loopState.inAutoContinue = true;
...
const xhr = new XMLHttpRequest();
xhr.open('POST', '/api/v0/chat/completion', true);
...
xhr.onreadystatechange = () => {
  if (xhr.readyState === 4) {
    ...
    loopState.inAutoContinue = false;
    ...
    resolve();
  }
};
xhr.send(bodyStr);
```

全文检索 `xhr.timeout` / `ontimeout`：0 处。`inAutoContinue` 只在 readyState 4 复位（1417），
而它同时是**全局**开关：

```ts
// :909-911  任意聊天 XHR 在 inAutoContinue 期间都把文本累积进上一轮的 autoReplyText
if (loopState && loopState.inAutoContinue) {
  loopState.autoReplyText += visible;
}
// :957  且跳过正常轮次的错误分类
if (!loopState.inAutoContinue) {
  const firstVerdict = ...;
}
```

**后果**：

- 传输挂起（TCP 黑洞、代理断在半路、休眠唤醒后的僵死连接）时，`onreadystatechange` 可以长时间不回调；
  没有超时就没有任何兜底：`autoContinueWithPow` 的 Promise 永不 settle，`loopDepth` 不前进，
  `streamActive` 停在 true，UI 一直「执行中…」。用户唯一的出路是刷新页面。
- 挂起期间 `inAutoContinue` 恒为 true：若用户不等而直接发新消息，那条新流的文本会被同时累加进
  **上一轮**的 `autoReplyText`，且它的错误帧分类被 `:957` 跳过。僵死请求一旦后来完成，就会把
  新对话的内容当作上一轮的续跑回复推给宿主，形成跨轮/跨对话污染——正是本轮要查的「新对话残留」。
- 宿主侧 `waitForNextReply` 会在 120s 超时，但宿主 stop 到不了页端（R9-02 已登记），页端状态不会因此复位。

**建议**：

1. 给续跑 XHR 设显式超时（建议与宿主 `stepTimeoutMs` 对齐的 120s），`ontimeout` 里按
   `retryable/network-error` 走既有退避预算，而不是静默挂死。
2. 超时/错误/中止三条路径统一在 `finally` 语义里复位 `inAutoContinue`、`streamActive`，并 `finishStepFlow` 收尾。
3. 回归腿：假 XHR 永不回调，推进到超时时间后断言出现可见错误、busy 复位、`inAutoContinue === false`。

**复现**：

- `复现用例/qd-r13-continuation-http.test.ts` 第 3 腿：续跑 XHR 发出后不回调，等 1.2s。
- 实测：`timeout=0`、`ontimeout=null`、busy 仍为 true、`appendError` 0 次。
- 状态：**Verified-实证**（无超时配置 + 无兜底 + 无可见错误）；「永久」由结构与 XHR 默认 `timeout=0` 推得，
  真机挂起窗口未构造。
