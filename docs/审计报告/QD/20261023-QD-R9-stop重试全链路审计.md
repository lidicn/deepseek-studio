### QD-R9-01 [P2] 远程端任务进行中 `running` 永不置真：停止键常隐、发送闸门常开

**证据**：

```ts

  const botsList = options.host.bots.list();
```

```ts
// src/host/agent-channel.ts:172-174 —— 轮次事件只广播 event，不广播 state
function broadcast(event: AgentLoopEvent): void {
  for (const ws of sockets) safeSend(ws, { type: 'event', event });
```

`state` 只在四处发出：WS 接入（:232）、`get-state`（:258）、`set-policy`/`set-workspace`（:297/:304），以及
`desktop-host.ts:1598/:1602` 的 `onConnect` / `onDisconnect`。**send 开始、send 结束、stop 都没有 `broadcastState()`**。

```ts

  else if (event.type === 'error') { next.running = false; next.lastError = ...; }

// :119-126

```

```ts

btnStop.addEventListener('click', () => call({ type: 'stop' }));
// :206-211 —— 闸门失守后的 busy 错误被直接写进对话画布

el.textContent = `操作失败：${error}`;
```

**后果**：
- 手机/远程端发起任务后，宿主只推 `event`，客户端的 `running` 永远保持 `false` ⇒ `#btn-stop` **整轮都不出现**。唯一的例外是「连接建立时任务已在跑」——此时初始 state 才能带出 `running=true`。
- 同一原因使 `canSend` 保持 `true`：用户在任务进行中仍可点发送。宿主用 `agent-busy` 拒绝（`agent-channel.ts:276-278`），客户端把 `操作失败：agent-busy` 追加进正文（`agent-panel.ts:206-211`），而正文由执行会话驱动、下一次广播整块重绘 ⇒ 这行错误要么闪一下消失，要么夹在工具卡之间。
- 与 R9-02/03 叠加后形成完整闭环：**停止键不可达 → 旧轮继续跑 → 旧答复污染下一轮**。

**复现**：`REPRO-A` 实测失败。真 `createAgentChannel` + 真 `ws` 客户端，`send` 成功后 250ms 内没有任何 `state` 消息（`strayState = timeout`），客户端状态为 `{running:false, canStop:false, canSend:true}`；第二次 send 得到 `agent-busy`。`CONTROL` 腿调用 `channel.broadcastState()` 后同一客户端变为 `running=true / canStop=true`，证明缺的是调用点，不是广播机制。

**建议**：在 `AgentLoop` 的 `user`/`done` 边界以及 `stop` 处理里调用 `agentChannel?.broadcastState()`（或在 event 信封里增加 `running` 字段，由 reducer 在 `user`/`status` 置真、`done`/`error` 置假）。客户端点击发送后应先本地置 `running=true` 并禁用按钮，等 ack 失败再回滚。

**状态**：Verified-实证（盘面复制树）。

### QD-R9-02 [P2] 宿主 stop 只停「等待」，不停页面：旧轮继续出流并继续执行工具

**证据**：


该旗标唯一的消费点是 WebEngine 的轮询：

```ts
// src/host/engine/web-engine.ts:257 / :323 / :345
```

```ts

  (this as Record<string, unknown>)[DS_ABORTED_FLAG] = true;
  if (loopState) loopState.abortedByUser = true;
  ...

  d('auto-continue suppressed: user aborted this turn');
```

宿主→页面的能力面没有停止动作：`src/capabilities/` 15 个文件里只有 `chat-insert` / `chat-read` / `chat-send`，全仓 `chat-stop` 0 命中；`stop` 也不会经 `page-runtime` 下发。工具执行入口同样不看停止旗标：

**后果**：
- 用户按下停止后，宿主只是不再等待；**页面的上游 XHR/SSE 没有被 abort**，页端 auto-continue 仍按自己的 `MAX_LOOP`/工具结果继续发请求。
- 旧轮随后产生的工具调用仍会经 hub 进入 `executor` 执行（含 shell/file 等高风险能力，仍走同意闸门与审计），工具卡与执行会话继续增长。用户看到的「已停止」只发生在宿主侧。

**复现**：未构造。页端的在飞 XHR 与 auto-continue 都在 `chat.deepseek.com` 主世界内，仓库里没有能替代真实页面流的夹具；本轮按代码事实登记，人工验证步骤：远程端发起含工具的任务 → 点宿主 stop → 观察页面是否继续输出、工具卡是否继续新增、`audit` 是否继续记录调用。

**建议**：新增宿主→页面的 `chat-abort` 通道（页端收到后对在飞 XHR 调 `abort()`，`abortedByUser` 已有现成语义）；stop 时同时通知页面并清掉 `pending`/续跑定时器。作为兜底，`executor` 入口在 `stopFlag.stopped` 为真时拒执行并回填一条 `[tool-result] error: user-stopped`，避免旧轮继续跑高风险工具。

**状态**：Verified-代码事实（未构造，缺真实页面流）。

### QD-R9-03 [P1] 停止后旧轮的最终答复不会被作废，下一轮续跑等待把它当成本轮结果

**证据**：

```ts
// src/host/desktop-host.ts:1606-1613 —— 页端推送一律置 fresh
onAssistantReply: (text, loop, botId) => {
  const state = botRegistry.getState(botId ?? 'main');
  if (!state) return;
  state.lastAutoReply.text = text;
  state.lastAutoReply.loop = loop;
  state.lastAutoReply.updatedAt = Date.now();
  state.lastAutoReply.fresh = true;
},
// :821-824
consumeAutoReply: () => { const r = { ...state.lastAutoReply }; state.lastAutoReply.fresh = false; return r; },
```

`WebEngine.send()` 开始时**不清空**该缓冲（`web-engine.ts:225-247` 只重置本轮工具记录），而续跑等待是「来者不拒」：

```ts
// src/host/engine/web-engine.ts:321-327
if (options.consumeAutoReply) {
  while (Date.now() - startedAt < stepTimeoutMs) {
    if (options.isStopped?.()) { stopped = true; break; }
    const reply = options.consumeAutoReply();
    if (reply.fresh && reply.text.length > 0) {          // ← 不看 reply.loop / updatedAt
      return { content: reply.text, toolCalls, ... };
    }
```

```ts
// src/host/agent-loop.ts:134-138 / :159
result = await options.engine.waitForNextReply();
...
emit({ type: 'assistant', text: result.content, step });
```

**后果**：停止（R9-02）后页面继续跑完，`onAssistantReply` 把「旧轮最终答复」置为 fresh；用户随后发的新任务只要本轮有工具调用，`waitForNextReply()` 会**立即**把旧答复返回，AgentLoop 再把它当本轮 assistant 输出。用户问的是新问题，看到的是上一轮（甚至已被停止那轮）的结论——静默错误结果，且执行会话里新轮没有对应的 `final-answer`，回放/远程端同样错。`reply.loop` 字段写了但从未被校验，是现成的关联信息。

**复现**：`REPRO-B` 实测失败：预置 `{text:'旧轮结论', fresh:true}`，调用 `engine.send('新任务')` 后 `waitForNextReply()` 立即返回 `"旧轮结论"`（`timedOut=undefined`、`toolCalls=0`），且 `buffer.fresh` 仍为 `true`。`CONTROL` 同形但 `fresh=false`，同一调用返回 `"新轮基线"`（超时后读 DOM），不返回旧文本。

**建议**：每轮 `send()` 开始时显式失效旧缓冲（`fresh=false`、`text=''`，或记录 turn 起点时间戳）；`waitForNextReply` 只接受 `updatedAt >= 本轮 send 开始时刻` 且 `loop` 与本轮匹配的回复。更彻底的做法是把 `turnId` 带进 `auto-continue` 推送，由宿主按 turn 过滤。

**状态**：Verified-实证（盘面复制树）。

### QD-R9-04 [P3] 停止无法打断步间节流等待，`AbortController` 是一次性的死信号

**证据**：

```ts
// src/host/agent-loop.ts:131-133
if (options.throttleBetweenSteps !== false) {
  await waitBetweenRequests(new AbortController().signal);   // ← 从未 abort
}
```

`waitBetweenRequests` 的随机 2.5-6.5s 睡眠（`src/inject/step-control.ts`）只对传入信号生效；这里每次新建一个永不 abort 的控制器。停止旗标要到睡眠结束、进入下一圈或 `waitForNextReply` 轮询时才被读到。

**后果**：用户在步间节流窗口按停止，界面最多再显示 6.5s「执行中」；若后面紧跟 `waitForNextReply`，还要等它下一次轮询。不是数据错误，但让停止看起来「没反应」。

**建议**：`AgentLoop` 持有自己的 `AbortController`，`stop()` 里除了置位 `stopFlag` 再 `abort()` 它，`waitBetweenRequests` 与后续等待都接同一个信号。

**状态**：Verified-代码事实。

### QD-R9-05 [P3] 停止不写执行会话终态，回放停在 running（并入 R7-03 的触发面）

**证据**：

```ts
// src/shared/studio-execution.ts:68-73
export type StudioExecutionEvent =
  | StudioUserMessageEvent
  | StudioToolStartEvent
  | StudioToolResultEvent
  | StudioFinalAnswerEvent
  | StudioSystemErrorEvent;
```

事件联合里没有 `turn-end` / `stopped`。宿主 stop 只发 AgentLoop 的 `status`/`done`（`agent-loop.ts:113-115、167`），`agent-panel.ts:185` 明确忽略 loop 事件，执行会话也不落任何终止事件。若停止发生在 `tool-start` 之后、`tool-result` 之前，会话最后一条就是 `tool-start`。

**建议**：增加 `turn-end`（带 `stopReason: 'user-stopped' | 'failed' | 'completed'`）或复用一个明确的 `system-error(code:'user-stopped')`，由宿主 stop 路径写入；渲染侧再把没有终态的 `tool-start` 归一化为 `cancelled`（R7-03 方案）。

**状态**：Verified-代码事实（与 R7-03 合并编号，不重复计缺陷）。

## 4. 小结与优先级

本轮把 stop 链路拆成三段，三段各自都有断点：

1. **点不到**（R9-01）：远程端 `running` 永不广播，停止键整轮隐藏、发送闸门常开；
2. **停不住**（R9-02）：即便 stop 送达，只停宿主等待，页面流与工具执行继续；
3. **留不住干净上下文**（R9-03）：旧轮最终答复保留 `fresh`，下一轮续跑直接吞掉，形成跨轮静默错答。

建议修复顺序：R9-01（一处广播 + 客户端闸门，改动小、可立刻恢复控制面）→ R9-02（新增页端 abort 通道 + 执行器兜底）→ R9-03（每轮清缓冲 + turn 关联）→ R9-05/R9-04（终态与可中断等待）。

R10 将接发送闸门与 busy 状态机：同一批证据会复用本轮的面板 WS 夹具，重点看「重复发送 / 断线重连后的 running 复位 / ack 丢失」。
