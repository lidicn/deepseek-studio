## 2. 发现

### QD-R20-01 [P1] 面板 reducer 不辨事件来源：别 bot／别房的 `done` 把自己家的 `running` 抹平 ⇒ 停止键消失、发送闸门被提前打开

**证据**：

```ts
// src/ui/workbench/workbench-state.ts:85-94（实时盘面；HEAD blob 面 :82-93 同形，两面都不读归属）
export function applyLoopEvent(state: WorkbenchState, event: AgentLoopEvent): WorkbenchState {
  const next: WorkbenchState = { ...state, events: [...state.events, event] };
  if (event.type === 'done') {
    next.running = false;                       // ← 任何来源的 done 都算"我这轮结束了"
  } else if (event.type === 'error') {
    next.running = false;
    next.lastError = event.text ?? '执行出错';   // ← 任何来源的 error 都写进我这轮的错误位
  }
  return next;                                  // ← 全程⛔ 读 event.botId / event.roomId
}
```

```ts
// src/ui/workbench/workbench-state.ts:119-126（盘面）
export function canSend(s) { return s.connection === 'connected' && s.desktopPageConnected && !s.running; }
export function canStop(s) { return s.running; }
// src/ui/agent-panel.ts:140-142
btnStop.classList.toggle('hidden', !canStop(state));   // running 被别房抹平 ⇒ 停止键整轮隐藏
```

**后果**（可触发，已实证）：远程面板上用户发起一轮任务、任务仍在跑时，只要**另一个 bot / 另一个聊天室**（sub-bot 发言、摘要器、strategy、定时任务经 `agentSender`）在这一轮内产出终态事件，`{type:'event'}` 就会经 `broadcast` 原样到达面板 socket，于是：

1. 自己家的 `running` 置假 → `#btn-stop` 消失，**用户失去唯一的停止入口**（这正是 R9-02 的"停止键不可达"闭环，但根因不同：R9-01 记的是宿主⛔ 调 `broadcastState()`，本条记的是 reducer 读了**别人的**事件）。
2. `canSend` 变 `true` → 闸门在自己回合未结束时打开，用户能再点发送；宿主用 `agent-busy` 拒（`agent-channel.ts:276-278`），错误被 `agent-panel.ts` 的 `handleAck` 追加进画布正文，下一次广播整块重绘 ⇒ 表现为"发出去的提示闪一下没了 / 夹在工具卡之间"。
3. 别房 error 的 `event.text` 写进 `lastError`（如 `analyst：本轮未取得模型回复`），面板把**别人家的故障**当成本轮故障展示。注意可见性分面：`workbench-statusbar.ts:29` 在 `connection==='connected'` 时会隐藏 `lastError`，所以状态栏那一格⛔ 出红字；可见路径是 HEAD 面 `agent-panel.renderEvent` 的 `case 'error' → appendMessage(canvas,'error',…)`。本条不夸大为"状态栏错报"。

**复现**：`复现用例/qd-r20-eventbus.test.ts`
- `REPRO-A`（**红**）：喂 `botId='analyst'` 的 `done` + `error` 进真 `applyLoopEvent`，断言"本方回合未结束 ⇒ running ⛔ 应由别房 done 抹平 / 发送闸门⛔ 应被别房终态打开 / lastError ⛔ 不应写别房副 bot 的错误"。断言原文（run-2/run-3 一致）：
  ```
  → 本方回合未结束，running 不应由别房 done 抹平: expected false to be true
  → 发送闸门不应被别房终态打开: expected true to be false
  → lastError 不应写别房副 bot 的错误: expected 'analyst：本轮未取得模型回复' not to contain 'analyst'
  ```
- `REPRO-B`（**红**）：真 `createAgentChannel` + 真 `ws` 客户端 + 真 reducer 全链，聊天室副 bot 的一整轮（4 条事件）原样送达远程面板：`面板收到事件数=4 botId集合=analyst`，且 `面板收到 user 文本="【Studio Agent】甲房内部提示词（含其他成员发言）"`。
- `C1` / `C2` / `REFUTED-E`（**绿**，正控）：证明①戳记规则本身工作（带 `{roomId}` 的 send 4 条事件全带 `roomId=room-A`；不带则 `roomId=undefined`），②宿主侧并发闸门**没有**失效——第二次 `send` 立刻得 `agent-busy`、耗时 `0ms`。

**建议**（具体形状）：
1. `WorkbenchState` 增加 `currentRun: { botId: string; roomId?: string } | null`，由面板在**自己发出 send 的 ack 成功时**写入（不是靠事件推断）；`applyLoopEvent` 只在 `event.botId === state.currentRun.botId && (event.roomId ?? undefined) === (state.currentRun.roomId ?? undefined)` 时才动 `running` / `lastError`，其余事件丢弃或只入 `events` 不参与状态机。
2. ⛔ 采"在 reducer 里看到 `user`/`status` 就置 `running = true`"作为 R9-01 的修法：REPRO-A2 形状探针显示，全量 fan-out 下会有一条**别房的 `user` 事件**（内容正是内部 persona 提示词）到达面板，若按该建议实现，面板会把别人的回合当自己的开始 ⇒ `running` 恒真、按钮**永久锁死**。R9-01 的修复必须与本条同批落，否则修 R9-01 会引入一枚比"停止键不出现"更重的死锁。

**状态**：Verified-实证（REPRO-A / REPRO-B 红，run-2、run-3 两跑一致）。
