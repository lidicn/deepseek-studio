## 1. 发现

### QD-R7-01 [P2] 切会话后迟到的工具结果被整体丢弃：旧会话记录缺 `tool-result`，回放永远停在「执行中」

**证据**（`src/ui/studio-chat-ui.ts:837-881`）：

```ts
const cardRoot = toolCardRoots.get(callId) ?? currentAssistant;
if (!cardRoot || !result) return false;
if (!cardRoot.isConnected) {
  // 会话已切换/清空时不要把旧结果写进新会话。
  toolCardRoots.delete(callId);
  toolCardTurns.delete(callId);
  return false;                 // ← 连后面的 recordEvent(tool-result) 一起跳过
}
updateRedesignedToolCardByCallId(callId, data, result, cardRoot, durationMs);
...
recordEvent({ type: 'tool-result', ... });   // :862，只有守卫通过才执行
```

守卫的**意图**是防止旧结果写进新会话的 DOM，这个目的达到了；但 `tool-result` 事件与 DOM 更新绑在同一个分支里，
守卫变成「一整条腿都不落」。会话 A 的执行记录于是永远停在「只有 tool-start、没有 tool-result」。

**后果**：
- 用户切回会话 A（或刷新后恢复）时，重放会对这条只有开始的记录建一张 `running` 卡，摘要显示
  `已调用工具 · 1 次 · 1 执行中`，秒表从**回放时刻**重新起跳（`renderItem` 的 `startedAt = Date.now()`），
  永远不会结算。用户看到的是「工具一直在跑」——正是本 campaign 要抓的「工具断流」的持久化形态。
- 工具结果本身没有丢（interceptor 的 `pending` 仍在，续跑照常），丢的是**历史记录**：回放/导出与真实执行不一致。

**复现**：`REPRO-A` 实测失败：`accepted=false`、`chat:a events=["user-message","tool-start"]`、回放 `data-status="running"`。
（对照 `CONTROL`：同形状的实时卡为 `succeeded`。）

**建议**：把「DOM 回填」与「执行记录入账」拆成两条腿。守卫触发时仍按 `toolCardTurns.get(callId)` 的 turnId
调用一次 `recordEvent({type:'tool-result', ...})`（可加 `delivered:false` 或 `detached:true` 字段），仅跳过
`updateRedesignedToolCardByCallId`。若无 DOM 可写，至少要落一条 `system-error`/`tool-result(cancelled)`，
让回放侧有终态可依。

**状态**：Verified-实证（盘面复制树）。

### QD-R7-02 [P2] 回放把持久化信封当作 `data`：恢复后的工具卡输出退化成原始 JSON，与实时卡不一致

**证据**（`src/ui/studio-chat-ui.ts:862-878` 与 `:951-959`）：

```ts
// 实时入账：content/details 在信封顶层
result: limitToolPayload({
  data: result.data, content: result.content, details: result.details,
  isError: result.isError, terminate: result.terminate,
}),

// 回放：整个信封塞进 data，content/details 没有展平
updateRedesignedToolCardByCallId(event.callId, { toolName, params }, {
  ok: event.ok,
  data: event.result,        // ← { data, content, details, ... } 整体
  error: event.error,
  isError: !event.ok,
}, target, event.durationMs);
```

`tool-card-ui.redesign.ts:570-573` 调 `formatToolResultText(result)`：顶层 `content` 缺失 → `joinContent` 返回
`null` → 回退 `legacyResultText` → `data` 既不是 `stdout` 结构也不是字符串 → `JSON.stringify(整个信封)`。

**后果**：
- 实时卡显示 `HELLO-R7`；切走再切回后同一张卡显示
  `{"data":{"stdout":"HELLO-R7",...},"content":[{"type":"text","text":"HELLO-R7"}],...}`。
- 结果是**同一会话在刷新前后呈现不同的历史**，用户会以为工具输出变了；也把 `content` 与 `details` 重复展示一遍。
- 失败结果同理：实时卡的 `[错误] 文本` 在回放里变成信封 JSON，错误可读性丢失。

**复现**：`REPRO-B` 实测失败：实时输出含 `HELLO-R7` 且不含 `"content"`；回放文本原文见日志（含 `"data"`/`"content"`/`"details"` 键）。

**建议**：回放时解包并展平：`const p = event.result as {data?:unknown;content?:...;details?:...;isError?:boolean;terminate?:boolean} | undefined`，
然后传 `data: p?.data, content: p?.content, details: p?.details, isError: p?.isError ?? !event.ok, terminate: p?.terminate`。
若信封是 `{truncated:true,...}`（>16KB），应显式渲染「已截断」提示，而不是把预览字符串当 JSON 再包一层。

**状态**：Verified-实证（盘面复制树）。

### QD-R7-03 [P3] 回放不归一化「无结果」的 tool-start：崩溃/刷新后卡片永久显示「执行中」并重新计时

**证据**（`src/ui/studio-chat-ui.ts:926-939` + `tool-card-ui.redesign.ts:788-810`、`:713`）：

```ts
} else if (event.type === 'tool-start') {
  ...
  createRedesignedToolCard({ toolName: event.toolName, params }, event.callId, lastToolAssistant);
}
// create 路径：renderItem(item, data, status='running', data.durationMs=undefined, Date.now(), false)
// running → startTicker(row, startedAt)，每秒把 Date.now()-startedAt 写进 .ds-flow-time
```

重放只按事件流重建，没有任何「这条 tool-start 没有终态」的收敛逻辑：卡片状态 `running`，摘要计入 `1 执行中`，
秒表从现在开始计。崩溃、页签关闭、宿主断开等任何「tool-start 已落盘、tool-result 尚未落盘」的会话都会这样恢复。

**后果**：恢复后的会话看起来有一个正在运行的工具，用户等待一个永远不会来的结果；摘要永远不收敛。
与 R7-01 是同一症状的两条来源——R7-01 是**结果被丢弃**，本条是**结果本来就来不及产生**。数据侧无法凭空补出结果，
但展示侧应明确「已中断」，而不是假装还在跑。

**复现**：`REPRO-C` 实测失败：手工写入只含 `tool-start` 的会话 → 回放 `data-status="running"`、摘要 `1 执行中`。

**建议**：`replayExecutionSession` 对没有匹配 `tool-result` 的 `tool-start` 使用终止态渲染
（新增 `interrupted` 状态，或复用 `cancelled` 并在展开区注明「会话中断，未收到执行结果」），且不启动 ticker；
同时不要让这类条目计入「执行中」计数。

**状态**：Verified-实证（盘面复制树）。

### QD-R7-04 [P1] 切到新会话后旧回合迟到的 `tool-start` 会在新会话建卡并落账——`finishToolCard` 的守卫被绕过

**证据**（`src/ui/studio-chat-ui.ts:818-824`）：

```ts
function startToolCard(callId: string, data: ToolCardData): boolean {
  if (!currentAssistant) startAssistantMessage();   // ← 会话切换后 currentAssistant=null，直接在新会话新建气泡
  if (!currentAssistant) return false;
  renderInspectorEntry(callId, data.toolName, 'started');
  createRedesignedToolCard(data, callId, currentAssistant);
  toolCardRoots.set(callId, currentAssistant);
  toolCardTurns.set(callId, currentTurnId);
  recordEvent({ type: 'tool-start', ... });          // ← sessionKey 已是新会话
```

`clearMessagesForSession` 把 `currentAssistant` 置空，但 `startToolCard` 没有任何「本回合是否仍属于当前会话」的判定；
它自动补开气泡、建卡、并把 `tool-start` 记进**新会话**。随后 `finishToolCard` 的 `isConnected` 守卫看到的是
**新建且已连接**的气泡，因此照常回填并记 `tool-result`。interceptor 侧 `forward` 不感知 UI 会话，旧流的工具标签
在切换之后解析出来仍会走到这里（fetch/XHR 两条路径都经 `forward`，`main-world-interceptor.ts:1080`）。

**后果**：
- 旧对话的工具调用（参数可能含命令、文件路径、查询内容）被**持久化进新对话的执行记录**，且 `turnId` 取的是新会话
  当前回合 id，回放时看起来就是新会话自己调用的工具。
- 与 R5-03（迟到正文增量写进新会话并落 `final-answer`）同族，但这是**第二个入口**：修 R5-03 时若只守卫
  `appendToAssistantMessage`，本条仍可复现（正是本仓反复出现的「只落一条腿」）。
- 触发条件是常规动作：流未结束就切会话/点新对话。

**复现**：`REPRO-D` 实测失败：切换后 `startToolCard`+`finishToolCard` →
`chat:b card present = true`、`chat:b events = ["tool-start","tool-result"]`。

**建议**：给流式回调建立「回合归属」。最小修法：`startToolCard/finishToolCard` 接收或读取**流开始时捕获的
sessionKey/turnId**（interceptor 在 `captureChatRequest` 时把当前会话键带进 loopState），与当前 `sessionKey`
不一致时拒绝建卡，只记入原会话记录（若原会话仍在做持久化）或直接丢弃并留一条 trace。
不要依赖 `currentAssistant` 是否存在来判断归属——它只表示「UI 现在有没有开着的泡泡」。

**状态**：Verified-实证（盘面复制树）。
