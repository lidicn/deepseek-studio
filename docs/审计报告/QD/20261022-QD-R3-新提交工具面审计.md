## 1. 发现

### QD-R3-01 [P1] `search_files` 对模型可达，但整条治理链不认它 ⇒ 任意绝对目录可列/可 grep，**零同意**（含 `workspace` 档）

> **承接登记（阶段 0 去重命中）**：本条的**根因**已由 `docs/审计报告/Studio-UI-总体设计-v1-评审报告.md`（2026-10-19）§6.5 登记——「`search_files` 不在 FILE_TOOLS / PROCESS_TOOLS / EXECUTION_TOOLS 任一集合 → `not-governed` → `allow`；`risk:'read'`；`root` 允许从 params 传入」。该报告给的是 UI 语义建议（「把检索根目录显式展示」），**未改代码**。
> 本轮新增的是**可达性升级**：在 `dcedede` 之前，`search_files` 不在 `SUPPORTED_INVOCATION_NAMES`（`git show dcedede^:src/shared/tool-contract.ts | grep search_files` → 0 命中），模型发不进来，缺口是 latent；`dcedede` 把它接进模型表后，缺口变成**模型可直接触发的 live 通道**。本轮同时补上了端到端实证与派发层细节（策略段整体被跳过、同意阈值为 `insert`）。**⛔ 把本条记作「新根因」**；它是同一根因的可达性升级。

**证据（HEAD 面，逐行）**

1. `dcedede` 把它接进了模型面：
   - `src/shared/tool-contract.ts:83-96`：`search_files: { id: 'search_files', adapt: … }`，且 `search_files` 出现在 `MODEL_INVOCATION_TOOLS` 里；
   - `src/shared/tool-contract.ts:197`：`SUPPORTED_INVOCATION_NAMES = Object.keys(MODEL_INVOCATION_TOOLS)` ⇒ 含 `search_files`；
   - `src/inject/streaming-tool-parser.ts:50,66`：标签字符类已放宽为 `[a-zA-Z_][\w.:-]*`，`<search_files>` 可解析；
   - `src/inject/main-world-interceptor.ts:784-785`：`forward()` 只以 `isSupportedUpstreamTool(call.invocationName)` 为闸，`search_files` 通过。

2. 宿主派发的**策略闸门是「按工具名进白名单」的**，`search_files` 不在名单里：

   ```ts
   // src/host/desktop-host.ts:1218
   if (isFileTool(name) || isProcessTool(name)) {
     // evaluatePolicy(...) + routeConsent(...) 全在这一段里
   }
   ```

   ```ts
   // src/host/policy.ts:86
   export const FILE_TOOLS: readonly string[] = ['file.read', 'file.write', 'file.edit', 'file.list', 'file.stat'];
   // PROCESS_TOOLS = ['shell.exec', 'mcp.test']
   ```

   ⇒ `isFileTool('search_files') === false`、`isProcessTool('search_files') === false`，**整段策略闸门与越界同意路由被跳过**。

3. 同意闸门也不拦：

   ```ts
   // src/host/tool-definitions.ts:112-120
   { id: 'search_files', title: '搜索本地文件', …, risk: 'read', execution: 'host', … }
   // src/host/tool-registry.ts:46-50
   export const CONSENT_MIN_RISK: ToolRisk = 'insert';
   export function needsConsent(def) { return riskRank(def.risk) >= riskRank(CONSENT_MIN_RISK); }
   ```

   ⇒ `needsConsent({ risk: 'read' }) === false`，**不会弹同意**。

4. 执行侧对 `root` 不做任何工作区校验：

   ```ts
   // src/host/desktop-host.ts:390
   const root = typeof params.root === 'string' ? params.root : mutableWorkspace.root;
   // 之后直接 listFiles({ root, … }) / grepFiles({ root, … })
   ```

   `src/capabilities/search-files.ts:8` 的模块契约是「root 由调用方注入；模块只在注入 root 之内遍历」——它保证的只是**不越出被注入的 root**，而注入值来自 `params.root` 原样。

5. 即使有人在将来把 `search_files` 补进 `FILE_TOOLS` 并让派发调用策略，**策略函数本身**也会放行：`src/host/policy.ts:285` 的兜底是
   `return { decision: 'allow', reason: 'not-governed' };`（文件分支只读 `params.path`，`search_files` 用的是 `params.root`）。

**后果（可触发场景）**

模型在任意一档（`workspace` / `ask` / `auto` / `full`）输出：

```xml
<search_files>{"operation":"grep","root":"E:/","query":"<任意串>"}</search_files>
```

宿主即以进程权限在该绝对路径下递归检索，把**命中的文件名与内容行**回传给模型；`operation:"list"` 则可枚举目录树。没有工作区边界、没有同意弹窗、没有越界标记；`workspace` 档「不越界」的承诺在这个工具上不成立。可读范围＝宿主进程可读范围（用户主目录、其它仓、配置目录等），仅受 `limit` 与文件系统权限约束。

**建议（两条腿必须同批，只补一条会变成「良性地拒绝」或「继续放行」）**

1. **策略面**：把 `search_files` 纳入文件类治理，并让文件分支识别 `root`——
   `firstString(params, ['path', 'filePath', 'target', 'root'])`，或为 `search_files` 单独先解析 root 再 `workspace.contains()`；派发段的 `resolvedPath` / `relPath` / `outside` 也须从 `root` 取值（现在只读 `paramsBag.path`，位于 `desktop-host.ts:1247`）。
2. **同意面**：把 `search_files` 的 `risk` 提到 `privileged`（与 `file.read/file.write/file.edit` 同级），使 `ask/auto/full` 走同意闸门、`workspace` 档越界硬拒。
3. **回归**：补策略矩阵（workspace 越界 deny / ask、auto 越界 require-consent / full allow）＋派发端到端（`root` 指向工作区外时无同意不可执行）。
4. **落地顺序**：先修本条，再落盘面那枚「把 `search_files` 写进提示词目录」的改动（见 QD-R3-02）——否则等于把一条已存在的越界通道**主动广告**给模型。

**复现（HEAD 副本树，7 腿：5 红 2 绿，原始输出）**

- 通过的 2 腿：**A**（解析器＋`isSupportedUpstreamTool`＋映射确实让 `search_files` 到达宿主）、**C**（`listFiles` 对一个工作区外的临时目录返回 `secret.txt`——能力层确实不认工作区）。
- B/D1/D2/D3 分别实证：策略判 allow、派发谓词 false、def risk 为 `read`、同意阈值为 `insert`。
- 复现件：`docs/审计报告/QD/复现用例/qd-r3-repro.test.ts`（原始件在 HEAD 副本树 `tests/desktop/` 下跑，未写入被审仓 `src/`）。
