## 1. 发现

### QD-R5-01 [P1] 点「新对话」时若助手气泡未收尾，清屏被守卫挡死，旧会话原地不动

**证据**（盘面 `src/ui/studio-chat-ui.ts:1040-1049`）：

```ts
if (normalized.startsWith('route:')) {
  if (currentAssistant !== null) return; // 回合在飞，不清屏
  sessionKey = normalized;
  clearMessagesForSession();
  executionSession = createEmptyStudioExecutionSession(normalized);
  ...
}
```

`currentAssistant` 不只代表「有请求在飞」：自 v1.6 的合并回合改造后，工具循环期间它**始终打开**（`onStreamEnd` 的
`pending.length > 0 || streamHadTools` 分支只记 trace，不收尾）。更关键的是 R4-01 的 429 死端：
`autoContinueWithPow` 的 retryable 分支既不 `finishStepFlow` 也不 `finishAssistantMessage` ⇒ `currentAssistant` **永久非 null**。
此时用户点新对话 → 路由从 `/a/chat/s/<id>` 变到 `/` → `entry.ts:188` → `activateSession('route:/')` → 守卫 return：
- `sessionKey` 仍是旧会话（`:1041` 在赋值之前返回）；
- 消息列表原样保留，连空态都不出现；
- 没有任何 toast / 提示解释为什么点不动。

**后果**：断流（429/5xx）后「新对话」按钮看起来失效；用户只能刷新页面。这正是「新对话仍有旧对话残留」最直接的形态。

**复现**：`REPRO-A` 实测 4 红之一，失败原文：
`expected 'STALLED-QUESTION复制助手助手▶思考中…复制执行 Inspe…' not to contain 'STALLED-QUESTION'`。

**建议**：守卫改为「有在飞请求才挡」而不是「气泡非空就挡」——例如用 `loopState.streamActive` / 请求序号传入
`activateSession`；或在 `autoContinueWithPow` 的所有终态分支统一 `finishStepFlow`（R4-01 的修法）后再判。
无论如何，挡下时必须给可见反馈（`appendError('busy', '当前回合仍在执行，已取消并新建会话？')` 或禁用按钮 + tooltip）。

**状态**：Verified-实证（盘面复制树）；HEAD 无此逻辑（面差见 §0）。

### QD-R5-02 [P2｜条件] `route:` 桶同键激活走早退，「新回合先切干净 route 会话」的注释失效

**证据**：interceptor 在每条新用户消息上调用（`src/inject/main-world-interceptor.ts:1120-1124`）：

```ts
// 上一回合的临时桶可能还带着历史事件。新回合开始前显式把 UI 切到干净的
// route: 会话，否则新对话时上一段结果会残留在消息列表里。
if (chatUI && chatUI.sessionKey.startsWith('route:')) {
  void chatUI.activateSession(chatUI.sessionKey);
}
```

但 `activateSession` 的同键早退在前（`studio-chat-ui.ts:1021-1033`）：

```ts
sessionKey = normalized;
if (normalized === previousKey && executionSession.events.length > 0) {
  // 同一会话键重复激活只做落盘，不清屏。
  ... return;
}
```

⇒ 只要 `route:` 桶里已有事件，这条「显式切干净」的调用就**一定**走到早退，什么也不清。

**触发条件**：会话键停在 `route:/` 且桶里有事件——首包在拿到 `chat_session_id` 前失败/被 abort（R4-01 的 429、R4-04 的
用户停止都能留下 `user-message`/`system-error`）；此时页面 URL 往往仍是 `/`。用户再点「新对话」时路径没变，
`navigation.ts` 的 pushState/replaceState 不发事件 → 唯一可能清屏的就是上面这条同键调用 → 被早退挡掉。
随后发的第一条消息把旧消息保留，并把新回合追加在同一列表里；`executionSession` 仍是同一个 `route:/`，旧事件继续落盘。

> 为什么不是必然：仓库抓到的真实请求体里每条 chat 请求都带 `chat_session_id`（`docs/前端开发计划/接力状态.md:366`），
> 正常首包会立刻迁移到 `chat:<id>`，route 桶只存在一个同步窗口。本条的射程是「首包未拿到 id 就失败」的条件面。

**复现**：`REPRO-B` 实测失败：
`expected 'STALE-ROUTE-MSG复制执行 Inspector关闭暂无工具执行…' not to contain 'STALE-ROUTE-MSG'`。

**建议**：`onNewUserMessage` 的这次调用改走显式的「开新会话」通道（例如 `activateSession(key, { reset: true })`，
或新增 `beginNewTurn()`），不要复用「激活会话」语义去表达「清空临时桶」；同键早退只应服务真正的重连场景。

**状态**：Verified-实证（盘面复制树，条件面已在用例中显式构造）。

### QD-R5-03 [P1] 切换会话后，旧会话的迟到流增量被渲染并持久化进新会话

**证据**：文本增量在 `currentAssistant` 为空时会**自动新建气泡**（`studio-chat-ui.ts:739-741`、`:750-751`）：

```ts
function appendToAssistantMessage(text: string): void {
  if (!currentAssistant) startAssistantMessage();
  currentRawText += text;
  ...
}
```

而工具卡有「会话已切换」保护（`finishToolCard :845-850`）：

```ts
if (!cardRoot.isConnected) {
  // 会话已切换/清空时不要把旧结果写进新会话。
  toolCardRoots.delete(callId);
  toolCardTurns.delete(callId);
  return false;
}
```

**文本路径没有这层保护**。`activateSession` 的非 route 分支也没有任何「回合在飞」守卫（对比 route 分支 `:1041`）：
流式过程中点击侧栏另一个会话（或新会话）→ `replayExecutionSession()` / 空分支把 `currentAssistant` 置空、`currentRawText` 清零
→ 旧请求的下一片 SSE delta 到达 → `appendToAssistantMessage` 新建气泡 → `currentTurnId` 已是新会话的 turn →
`finishAssistantMessage` 把这段旧会话的文本作为**新会话的 final-answer** 写入 `sessionKey`（新会话键）。

**后果**：新会话里凭空出现上一段对话的尾部文本；持久化记录被污染（刷新后仍在）；旧会话的正文前半段则永久丢失
（`currentRawText` 被清零，只剩切换后的尾巴）。工具卡不会跟着泄漏，造成「正文有、工具卡没有」的半截记录。

**复现**：`REPRO-C` 实测失败（DOM 与持久化两处）：
`expected '助手助手▶思考中…LATE-A-DELTA…' not to contain 'LATE-A-DELTA'`；
持久化断言 `chat:b` 的 `final-answer` 含 `LATE-A-DELTA`。

**建议**：给 stream 事件加「会话代次」：`startAssistantMessage` / `appendToAssistantMessage` / `finishAssistantMessage`
都带 `sessionGeneration`（`activateSession` 已维护该计数器），代次不匹配的增量直接丢弃并记 trace；
或在 `activateSession` 非 route 分支遇到在飞流时先 abort 页端请求。

**状态**：Verified-实证（盘面复制树）。

### QD-R5-04 [P2] 无工具成功回合结束后 busy 不复位；新建空会话继续显示「执行中…」

**证据**：
- `onStreamEnd` 的无工具分支只收尾气泡（`main-world-interceptor.ts:1103-1105`）：`chatUI.finishAssistantMessage()`，**没有 `setBusy(false)`**；
- `setBusy(false)` 只出现在 `finishStepFlow`（`:909`，工具/错误路径）和 XHR 错误分支（`:848`）；
- `activateSession` 的 route 分支（`:1040-1049`）与空会话分支（`:1060-1065`）都不复位 busy；
  只有 `replayExecutionSession`（`:997`）复位。

**后果**：普通一问一答（无工具）结束后，状态栏一直停在「执行中…」，直到下一次工具/错误路径；
用户在此时点新对话，新会话的空态里仍写着「执行中…」——又一条「旧对话残留」。
另外 `finishAssistantMessage` 本身也不复位 busy，所以任何「只收尾气泡」的调用方都会继承这个洞。

**复现**：`REPRO-D` 实测失败：`expected '执行中…' to be '完成'`（先锁收尾后状态，再锁新会话状态）。

**建议**：`finishAssistantMessage()` 成功收尾时按「本回合无待办」复位 busy，或把 `setBusy(false)` 收进
`onStreamEnd` 三个分支的共同尾部；`activateSession` 的 route/空分支显式 `setBusy(false)`。

**状态**：Verified-实证（UI 调用序列）+ 代码事实（interceptor 分支无 setBusy）。

## 3. 跨轮去重

- R4-05「新消息继承上一回合 pending」在**宿主/interceptor 层**；R5-02 在**UI 会话层**（route 桶早退），两层都中时症状叠加，修法分别处理。
- R4-01「429 死端」是 R5-01 的**触发器**：R4-01 不修，`currentAssistant` 永久非空，R5-01 就变成常态化。
- R5-03 与本轮 R5-01 同属「activateSession 缺在飞守卫」，但一个是挡清屏、一个是漏清理，方向相反；修法可一并（在飞流→abort 而非静默）。
