## 1. 修复 1 · sidecar 区分「启动失败」与「运行中崩溃」

**根因**（用户现场：`[sidecar] crash #1, restarting in 2s...` 循环刷屏）：

- `src/api/main.ts:241-253` 撞 `EADDRINUSE` 时 `process.exit(2)`
- `src-tauri/src/sidecar.rs` 的 supervisor 把**任何非 0 退出**当 crash → 退避重启 5 次
- 这是**可预期故障被当成崩溃**：端口占用方不退出，重启多少次都同样撞端口

**实现**（`src-tauri/src/sidecar.rs`，+152/-60）：

- 新增 `SidecarState::StartupFailed(String)` + `SidecarEvent::FatalStartup`
- 新增常量 `SIDECAR_EXIT_PORT_CONFLICT: i32 = 2`（与 `main.ts` 的退出码硬对齐，两侧注释互指）
- `do_monitor`：`status.code() == Some(2)` → `StartupFailed`，不进重启预算
- `do_spawn` 健康超时分支：`restarts==0 && probe_health()`（杀完子进程端口仍被占）→ `StartupFailed`
- spawn 失败（npx 不存在 / 权限拒绝）→ 同样 `StartupFailed`
- 附带修复：`Child::kill()` 在 Windows 只结束 `cmd.exe` 包装进程，`npx` 拉起的 `node.exe` 继续占 8760。
  新增 `force_kill_process_tree()` 按 PID `taskkill /T /F` 结束整棵树；`shutdown()` 改为轮询 `child_pid`
  直到监管线程确认停止，避免「应用退了、Node 还占着端口」

**未写 Rust 测试**：`sidecar.rs` 原本 0 测试，仓库无 Rust 测试基建。`cargo check` 通过。

**旁证**（实测）：本机 `Get-NetTCPConnection -LocalPort 8760` 曾显示 PID 20212 持听，
命令行是 `node ... tsx/dist/preflight.cjs ... src/api/main.ts`——正是残留 sidecar 占用端口的现场形态。

## 2. 修复 2 · 首轮断流自动重试（主体 + 4 条自查 bug）

### 2.1 要解决什么

QD-R4 之前：首轮请求失败只 `appendError` + `setBusy(false)` 就结束。一次网络抖动，用户每轮都要手动重发。
这正是用户报告的「满屏 服务器暂时无法访问 / stream-incomplete」的成因之一。

### 2.2 实现要点

统一升级点 `escalateFirstAttemptFailure(code, why)`：

- 预算内（`FIRST_ATTEMPT_MAX_RETRIES = 2`）→ 指数退避后**原样重发**上一份 chat 请求体
- 预算耗尽 → 收尾并明确告知「已自动重试 N 次仍失败」（不再假装没试过）
- 三条入口共用：XHR `readyState=4` 的 retryable 分支、fetch `!response.ok` 分支、无哨兵结算分支

**原样重发**（`resendVerbatim`）而不是套续跑 prompt：首轮失败时还没有任何工具结果，
套上 `<original_task>/<tool_results>` 等于把「重发同一个问题」变成「拿着空工具结果的续跑」。

### 2.3 本席引入并修掉的 4 条真 bug（自查记录）

这 4 条都是**改完之后才暴露的**，每条都有实测证据，不是推测。

**Bug A · 401 被当成断流重试**（交接摘要已定位，本轮修）

`settleStreamEnd` 的无哨兵分支在 XHR 路径的调用点（`main-world-interceptor.ts:990`）位于 `classifyResponse`
分类**之前**。401 时 `streamSawDone` 仍为 false → 先撞上「无哨兵」→ fatal 也被重试。

修复：`settleStreamEnd` 签名加可选 `httpStatus`，分支开头 `classifyResponse(httpStatus)` 判 fatal 则
`return false` 交回外层分类器。测试用例 3（401 不重试）由红转绿。

**Bug B · 续跑轮被无哨兵分支抢走，QD-R4-01 被修坏**

`settleStreamEnd` 的 `!streamSawDone` 分支原本只管首轮，但续跑轮（`inAutoContinue=true`）的
429 响应里同样没有哨兵 → 分支照走 → `escalateFirstAttemptFailure` + `appendError` + `return true`
→ `autoContinueWithPow` 里挂在 XHR 上的业务 `onreadystatechange` **永不执行**
→ 续跑的 `errorRetryCount` / 退避 / `auto-continue retryable` diag 全部失效。

实测证据：`429 后按退避重发，且重试不消耗工具续跑步数` 转红，断言 `auto-continue retryable ... retry 1/3` 为 false。

修复：分支开头加 `if (loopState.inAutoContinue) return false;`。该用例转绿。

**Bug C · 一次失败被计两次预算，2 次上限发出 4 个请求**

重发轮（`inAutoContinue=true`）走到 XHR hook 的 retryable 分支时，`settleStreamEnd` 已按 Bug B 的修法放行，
于是 hook 自己 `escalateFirstAttemptFailure` 一次；而 `autoContinueWithPow` 的执行器**也** escalate 一次。
一次失败 = 两次计预算。

实测证据：网络错误场景 `REQS: 4`（期望 3），diag 里只有一条 `retry 1/2`。

修复：hook 的 retryable 分支加注释明确「首轮重发链的失败只由执行器升级」，
执行器里的分支改为「进链即清标志，fatal 走 `finishStepFlow`、retryable 才 escalate」，保证一次且仅一次。

**Bug D · 重发被 `captureChatRequest` 当成新用户消息，预算永远烧不完**

重发体会被 `prepareOutgoingBody` 注入 `[studio-tool-capability]` 前缀；`captureChatRequest` 的
「是否新任务」判据只看「不含 `<original_task>`/`<tool_results>`」→ 把首轮重发判成新一轮
→ `onNewUserMessage` 里 `firstAttemptRetryCount = 0` → 2 次上限永远烧不完，且 prompt 漂成续跑版。

实测证据（diag 逐行）：

```
first-attempt retryable: reason=network-error retry 1/2 in 2193ms
first-attempt retry: resend lastChatBody verbatim (attempt 1/2)
originalTask captured len=2412          ← 重发被当成新任务
new user message: reset collectedExecutions/loopDepth/errorRetryCount
auto-continue loop=0 status=0 autoReplyLen=0 inAuto=true
auto-continue retryable: ... retry 1/3  ← 掉进了续跑的 errorRetryCount 分支
```

修复：`LoopState` 加 `inFirstAttemptResend`，`autoContinueWithPow` 发出前置位、`await` 返回后清除；
`captureChatRequest` 判据加 `&& !loopState.inFirstAttemptResend`。

### 2.4 附带修正

- `proto.send` 的 chat 分支与 fetch hook 对称，重置 `streamSawDone` / `streamTruncatedTag`
  （此前 XHR 路径不重置，上一轮的 FINISHED 会让本轮被误判为「流已完成」）
- `autoContinueWithPow` 里同样兜底重置这两个标志
- 首轮重发不消耗 `loopDepth`：它是「重发同一轮」不是「新的一步」；且 `loopDepth` 递增会让
  `onStreamEnd` 的 `loopDepth===0` 判失败，普通回合的收尾路径整段被跳过
- `onNewUserMessage` 重置新增的两个标志

## 3. 修复 3 · 重放错误折叠

**根因**：QD-R4 让「无 FINISHED 哨兵」的轮次显形之后，`replayExecutionSession` 把 `storage.json` 里
**累积多日**的历史错误逐张渲染成卡片。用户每次切换会话都被历史错误埋掉——「满屏执行未完成」。

**实现**：

- `src/ui/studio-chat-ui.ts`：`replayExecutionSession` 内 `system-error` 改为按 code 折叠计数；
  新增 `appendReplayErrorSummary()` 在收尾处输出一条汇总
- `src/ui/studio-chat-css.ts`：新增 `.ds-sc-replay-error-summary` / `-text` 两个类
- 实时路径 `appendError` 照旧即时出卡（那一张是「本轮」的反馈），语义不混

**自查修掉 1 条**：汇总条原稿用了 `var(--ds-fill-1, ...)` 与带兜底的 `var(--ds-line-2, ...)`。
`--ds-fill-1` 在两套主题里都**没有定义**，兜底值把漏定义掩盖了，
`studio-chat-css.test.ts` 的令牌审计直接抓到（`浅色缺少 --ds-fill-1`）。换成真实存在的 `--ds-think-bg`。
