## 1. 发现

### QD-R18-01 [P1] auto-continue 未推送时，`waitForNextReply` 的 DOM 降级轮询一次都不会执行：路径 A 烧光整个 `stepTimeoutMs`，路径 B 的第一拍就 break

**证据**：`src/host/engine/web-engine.ts:311-350`（HEAD-EQUAL）——`startedAt` 在函数顶部取**一次**，路径 A 的 while 用同一个预算，超时后**落进**路径 B，而路径 B 的循环第一行就是同一个时刻判断：

```ts
    async waitForNextReply(): Promise<EngineSendResult> {
      const counterStart = options.toolCallCounter.current;
      const startedAt = Date.now();                      // ← 只取一次
      ...
      if (options.consumeAutoReply) {                    // 路径 A
        while (Date.now() - startedAt < stepTimeoutMs) { ... await sleep(pollIntervalMs); }
        ...
        timedOut = true;                                  // ← 没有 return，继续往下
      }

      // 路径 B：DOM 轮询
      const baseline = await readLastMessage();           // 唯一一次真实读取（读数＝1）
      ...
      for (;;) {
        if (options.isStopped?.()) { stopped = true; break; }
        if (Date.now() - startedAt > stepTimeoutMs) {      // ← 此刻必然为真
          timedOut = true;
          break;                                          // ← 一次页面内容都没读就退出
        }
```

生产**永远**有 `consumeAutoReply`（`desktop-host.ts:821-825`，HEAD 同形），所以路径 A 恒被选中 ⇒ **路径 B 的降级轮询是死代码**。文件头注释（`web-engine.ts:1-13`）与 `:306-310` 的方法注释都写着「降级为 DOM 轮询（兼容 auto-continue 未推送的情况）」——注释描述的能力实际不可达。

**后果**（已实证，直接对应目标症状「工具断流」）：页端拦截器把工具结果回填后，模型若在页面里正常答完了但**没走 auto-continue 推送**（页端 WS 断/推送丢失/拦截器分支未命中），宿主的行为是：
1. 空等满 `stepTimeoutMs`＝**120 秒**（R4 §:86 已量过这条等待）；
2. 期间**从不读页面**——REPRO-A 实测 `chat-read 总次数=1`，那一次还是路径 B 开头取基线，取完就 break；
3. 返回 `content=''`、`completion='truncated'` ⇒ 页面上那条已经存在的回复**永久丢失**；
4. 分叉出两种用户可见面：面板/房间走 AgentLoop ⇒ `agent-loop.ts:146-154` 命中 `result.timedOut && !content` ⇒ 播一条「等待模型续跑超时」错误并 `continuationFailed` 终止（有横幅，但结论丢了）；automation/HTTP 走 TaskLoop ⇒ 该返回值 `toolCalls=0` 且内容为空 ⇒ `task-loop.ts:154` 判 `'empty-response'` ⇒ **连错误都没有**（与 QD-R17-01 的收尾形状同形）。

**建议**：路径 A 的 while 只该管"等推送"，不该吃掉整个 `stepTimeoutMs`——① 给 auto-continue 单独一个更短的窗口（如 `stepTimeoutMs/3`），到点**带着剩余预算**进路径 B；② 或直接改写：`while (未超总预算) { 先看 fresh；再看 DOM }`，两条信号在同一循环里轮询（这才是注释里写的"降级"）；③ 顺手修 `timedOut=true` 后不 `return` 的落空结构——它是"看着有兜底、其实不可达"的典型。

**复现**：`复现用例/qd-r18-continuation.test.ts` REPRO-A：页面 20ms 起就有 `'页面上明明有的回复'`，auto-continue 恒 `fresh:false` ⇒ `expected '' to contain '页面上明明有的回复'`，且 `chat-read 总次数=1`。

**状态**：Verified-实证。

### QD-R18-02 [P2] `completion` 四值有生产者⛔ 消费者：断线轮 `timedOut` ⛔ 置位 ⇒ TaskLoop 把断线判成 `empty-response` 正常收尾（R10-02 的机制命名 + 第二条 producer 腿）

**证据**：引擎侧两条断线返回都**只填 `completion`、不填 `timedOut`**（`web-engine.ts:266-276` 重连耗尽、`:241-243` 发送失败；HEAD-EQUAL）：

```ts
            return {
              content: lastText,
              toolCalls: tc,
              toolCallRecords: currentRecords ?? undefined,
              completion: 'disconnected',      // ← 无 timedOut 字段 ⇒ undefined
            };
```

`decideCompletion` 本来会把 dispatchFailed 映射成 `'disconnected'`（`web-engine.ts:25-35`），但两处断线返回**绕过它硬编**（`:295` / `:382` 传的都是 `dispatchFailed: false`）。消费侧 `task-loop.ts:151-156` 的 `computeStop(content, toolCalls, timedOut)` **⛔ 接收 completion**，`:203-212` 的 catch 也只认 `RoundTimeoutError`／`signal.aborted` ⇒ 断线只能落到 `'empty-response'`。现跑 `grep -rn "\.completion" src/host/kernel/` → 0 命中 ⇒ completion 通道**有生产者、无消费者**。

**后果**（已实证）：断线发生在**读侧**（`chat-read` 失败，`chat-insert/send` 都成功）时——这是 R10-02 没覆盖的那条 producer 腿（R10-02 的复现是让 `chat-insert` 失败）——
- `engine.send` 返回 `completion='disconnected'`、`getReconnectAttempts()=1`（引擎明明知道"曾经断过线、重连没救回来"），REPRO-C 读数两点皆有；
- TaskLoop `stopReason='empty-response'` 正常 resolve、并把空 assistant 写进共享 `kernelHistory`（REPRO-C 第二条断言：`expected true to be false`）；
- 上游按 R10-02 已登记的形状继续静默：`/v1/agent/send` 回 `200 {ok:true, answer:""}`、automation 记 `success`。

**与 R10-02 的关系（⛔ 重复立案）**：R10-02 登记的是**后果**（空内容正常收尾、出站 200），复现走的是写侧；本条登记的是**机制**（`completion` 通道未被任何消费者读取）+ **读侧这条新 producer**（重连耗尽后同样静默）。修法在同一个位置：`computeStop` 之前先看 `result.completion !== 'complete'` 就判停并带原因，R10-02 的建议（`agentSender` 看 `stopReason/completion`）才真正有可读的值可看。

**建议**：① `TaskLoopRoundResult` 带出 `completion`，`computeStop` 优先级里在 `timeout` 之前插一条 `disconnected`；② 两处硬编 `'disconnected'` 的返回改为走 `decideCompletion({timedOut, dispatchFailed:true, stopped})`，让分类只有一个出口；③ 顺手把 `timedOut` 在断线返回里也置上，这样即便上层不改，旧代码至少判成 `'timeout'`。

**复现**：同上件 REPRO-C（`readFails: () => true`，两条断言：`expected 'empty-response' to be 'timeout'`、`断线轮不应把空 assistant 写进历史: expected true to be false`）。

**状态**：Verified-实证（读侧静默 + 空 assistant 入库）+ 代码事实（`grep .completion src/host/kernel/` 0 命中）。

### QD-R18-03 [P2] auto-continue 成功那一轮不产结构化日志、不触发 `onRoundComplete`、不关闭指标回合；且生产装配点根本没有注入 logger/metrics ⇒ 整条 S3/S5/S21 观测链在面板主路上恒空

**证据**：`web-engine.ts:321-334` 路径 A 的两条返回：

```ts
          if (reply.fresh && reply.text.length > 0) {
            const toolCalls = options.toolCallCounter.current - counterStart;
            return { content: reply.text, toolCalls, toolCallRecords: currentRecords ?? undefined, completion: 'complete' };
          }
          ...
        if (stopped) {
          return { content: '', toolCalls: 0, ..., completion: 'unknown' };

```

两条都**直接 return**，⛔ `closeRoundForMetrics(...)`、⛔ `logRound(...)`、⛔ `options.onRoundComplete?.(...)`——而同文件 `send()`（`:295-303`）与路径 B 收尾（`:382-390`）三件都做。S21 的 `onRoundComplete` 是宿主侧唯一的"每轮一条结构化事件"出口（`web-engine.ts:92-93` 声明），v0.9 之后页端 auto-continue 恰是**生产主路**，所以这条出口在最常走的路径上恒不触发。
另一半：现跑 `grep -rn "createWebEngine(" src/` → **仅 1 处**（`desktop-host.ts:814`），它传的是 `dispatch / toolCallCounter / isStopped / getAutoReply / consumeAutoReply` 五项，⛔ `metrics`、⛔ `toolEventBus`、⛔ `logger`、⛔ `onRoundComplete`；再 `grep -rn "createHarnessMetrics\|getMetrics()" src/` → 命中全在 `web-engine.ts` 自身与 `src/shared/harness-metrics.ts` 定义处，**0 个生产消费者** ⇒ 引擎里 `let metrics`（`:130-133`）恒 `undefined`，`closeRoundForMetrics` 恒 no-op。

**后果**：① 排障面——一轮走 auto-continue 成功的对话，宿主日志/事件里**一条记录都没有**，`[web-engine] waitForNextReply start` 那行裸 `console.log`（`:315`）是仅存痕迹（本轮 `r18-run-2.log` 里出现 3 次）；② 指标面——`toolRounds`/`nudgeRate`/`noNudgeCompletionRate` 这套对齐 §1.3「≥95% 无需 nudge 完成率」阈值的量具在生产恒 0/未定义，任何"按指标判断质量提升"的结论都拿不到数（与记忆里那条「`npm run metrics:report` 对真实转录 52/52 parseError」是同族：**量具在，链不在**）；③ 即便将来注入 metrics，路径 A 仍会让 `openRound` 跨轮不关闭（`harness-metrics.ts:130-146` 的关闭权全在 `assistant/error/done/user` 事件上），下一轮的「纠偏」status 会记进上一回合 ⇒ nudgeRate 失真。**该子项是条件性的**：当前生产未注入 metrics ⇒ 暂不产生实际失真读数。
另注：`harness-metrics.ts:21-23` 的注释「path A 超时降级走 console.log、不经 onEvent」只说对了后半，前半与 QD-R18-01 冲突（降级根本不走 console.log，而是走一次基线读取后 break）。

**复现**：同上件 REPRO-B：`logger 条数=1 rounds 条数=1`，且**唯一那条**日志来自 send 腿（读数见 §0），auto-continue 那一轮 0 条——断言 `expected 1 to be 2` ×2 红。

**状态**：Verified-实证（路径 A 三条收尾动作缺失）+ 代码事实（生产装配点未注入，两处 grep 均可现跑）。
