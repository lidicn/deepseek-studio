## 1. 发现

### QD-01 [P1] `runTests()` 声称按工作区跑测试，`workspace` 参数整条链上⛔ 被使用 ⇒ 恒在**本进程 cwd** 跑，并把结果当目标工程的结论返回

**证据**：`src/host/kernel/test-runner.ts:25`（签名收 `workspace`）、`:30`（`createShellCapability({ workspace: null, timeoutMs: 120_000 })`——把边界校验对象传成 `null`）、`:35`（`shell.execute({ argv })`——**⛔ 传 `cwd`**）。
落点侧：`src/capabilities/shell.ts` `execute()` 内 `const cwd = requestedCwd ?? wsActive?.root ?? process.cwd();`，且越界检查写作 `if (wsActive && !wsActive.contains(cwd) && …)` ⇒ `wsActive=null` 时**该检查整体短路**。
机读的独立证据：`tsc` 本次实报 `test-runner.ts(25,32): error TS6133: 'workspace' is declared but its value is never read`。

**后果**：① 调用方拿 `runTests('E:/some-other-project', …)` 得到的是**本仓**的 vitest 输出，却被结构化成"目标工程测试通过／失败"——静默错目标，属"静默错误结果"类；② 越界 cwd 检查与 consent 同族闸门一并失效（本模块⛔ 经 `desktop-host.ts` 的 `requestConsent` 链，实测 `grep -rn "runTests" --include=*.ts src tools`＝**0 调用点**，即它一旦接线就是**免同意、免边界**的子进程出口）。

**建议**（二选一，⛔ 两条都留）：甲＝把参数用起来：`createShellCapability({ workspace: { root: workspace, contains } , …})` ＋ `execute({ argv, cwd: workspace })`；乙＝删参数、签名改成 `runTests(filter?)` 并在头注写明"恒在宿主 cwd"。同时**补 consent 腿**（与跨域第 28 条"handlers ⛔ 直连 tauri shell"同一刀）。

**复现**：⛔ 跑嵌套 vitest（本仓全量此刻在飞，再 spawn 一次会污染他人工作树），故停在代码事实。
**状态**：`Verified-代码事实`（静态链＝参数未用＋`cwd` 三重兜底＋tsc 的 TS6133 三条同向）。

### QD-02 [P1] `applyEdits()` 的替换串未转义 `$` 特殊模式 ⇒ **原文被静默改写并回报成功**

**证据**：`src/host/kernel/edit-engine.ts:108` `content.replace(instr.oldText, instr.newText)`（同一形状还在 `:53` 的死代码 `applySingleEdit` 里）。ECMAScript 规定：当替换参数是**字符串**时，`$&`／`` $` ``／`$'`／`$1`… 会被展开。

**复现**：`docs/审计报告/QD/复现用例/qd-02-edit-engine-dollar.test.ts` → 实测（18:12，`npx vitest run tests/desktop/qd-02-edit-engine-dollar.test.ts`）：
- `QD-02a` 原文件 `Hello world`，`oldText='world'`、`newText='X$`Y'` ⇒ 盘上成 **`Hello XHello Y`**，而 `res.ok=true`、`replacements=1`；
- `QD-02b` `newText='$&!'` ⇒ 盘上成 **`Hello world!`**（本应字面 `$&!`），同样回报成功。
**REPRO_RC=1**（三条断言全红＝缺陷成立）。

**后果**：AI 生成的 diff 里出现美元符号是常规场景（模板串、正则替换串、Shell 片段、价格文案）。这条链**一旦接线**就是"用户代码被改坏且没有任何信号"——数据损坏类，不可逆（回滚只在**抛异常**时触发，见 `:113` 的 `catch`，而 `$` 展开⛔ 抛异常）。

**建议**：改用函数式替换——`content.replace(instr.oldText, () => instr.newText)`；或上线前置断言 `newText.includes('$')` 时明示拒绝。两者都请在 `tests/desktop/kernel-edit-engine.test.ts` 里补**真临时目录腿**（⛔ 合成字符串）。

**状态**：`Verified-实证`（用例复现）。

### QD-03 [P1] 结构化计数用两条正则扫全文，**超时／部分输出面解析结果恒为 0/0/0**，调用方⛔ 能区分"零用例"与"没跑完"

**证据**：`test-runner.ts:43-47`（`/(\d+)\s+passed/`、`/(\d+)\s+failed/`，`total = passed + failed`）、`:58`（`ok: result.ok && failed === 0`）、`:50-55`（失败名靠 `/×\s+(.+)/g` 再 `slice(0, 10)`）。
**实测（本轮真实数据两次对撞）**：
1. 单文件失败样本（`/tmp/qd02.txt`，1 文件／3 用例全红）→ 解析得 `passed=0 failed=3 total=3`，**与真值相符**；首枚匹配原文＝`"3 failed"`（来自 `⎯⎯⎯ Failed Tests 3 ⎯⎯⎯` 横幅，它**早于** `Test Files` 汇总行）⇒ 见 §2 的 REFUTED。
2. **全量收口面**（终态：`Test Files 106 passed (106)`、`Tests 1072 passed (1072)`）→ 同一段解析代码得 **`passed=106 failed=0 total=106`** ⇒ 报的是**测试文件数**，真值是**用例数 1072**，**低报 10 倍**；`ok` 又由 `failed===0` 参与 ⇒ 上层读到"106 个用例全过"。**本条把 §2 R-1 从"证伪"翻回"证实"**：抢占与否取决于输出面——失败样本里 `⎯⎯⎯ Failed Tests 3 ⎯⎯⎯` 横幅先到（那次读数恰好对），全绿面⛔ 横幅 ⇒ `Test Files` 行先到。
3. **全量跑到一半的面**（18:25 快照 40 KB、⛔ 汇总行）→ 解析得 **`passed=0 failed=0 total=0`、`failures[]` 空** ⇒ 与 QD-04 合看才是**默认路径**（120 s 先到 ⇒ 永远拿⛔ 到汇总行）。

**后果**：`TestRunResult` 的四个数字是上层（未来的"编辑→自测"闭环）唯一的判据面。0/0/0 与"这个工程没有测试"同形，`ok` 又由 `failed===0` 参与 ⇒ 任何把 `ok`／`total` 读成"绿"的写法都会在这里吃假绿。另 `total` 定义漏 `skipped`（真值应 `passed+failed+skipped==collected`）。

**建议**：⛔ 用文本正则。跑 vitest 加 `--reporter=json --outputFile=<tmp>` 读结构化面；或 `--reporter=json` 走 stdout 再 `JSON.parse`。过渡期最低要求：解析失败（`total===0`）时**强制** `ok=false` 并回 `error:'unparsed-output'`，⛔ 让"没数"冒充"没挂"。

**状态**：`Verified-实证`（两个真实全量面：收口面 106 vs 真值 1072＝低报 10 倍；中途面 0/0/0）。

### QD-04 [P1] C-2 自带 **120 s 硬超时**，而本仓全量 vitest 实测 ≫ 120 s ⇒ 全量自测**恒判 timedOut**，闭环⛔ 可能建立

**证据**：`test-runner.ts:30` `timeoutMs: 120_000`；`src/capabilities/shell.ts:18` `export const MAX_TIMEOUT_MS = 120_000;`（`clampTimeout` 把任何请求夹到该上限 ⇒ **⛔ 有配置能让它等更久**）。
**实测（终数）**：全量 `npx vitest run` **`Duration 470.65s`**（18:13 起跑 → 18:21 收口），＝ `MAX_TIMEOUT_MS` 的 **3.9 倍**；`fileParallelism:false` 串行＋1072 例是主因。超时分支（`shell.ts` 的 `timedOut:true`）回 `ok:false` ＋**只带头 64 KB 的 partial 输出**（本次全量输出面 43841 B，单流尚未触顶；stderr 另计）⇒ 恰好落进 QD-03 的 0/0/0 面。

**后果**：设计意图（内核改完自己跑测试验收）在这台机器上**结构性可达**；表现是"每次都超时、每次 0 失败、每次看不出为什么"。这是稳定性问题而⛔ 是性能问题——上层会把它当"测试通过／失败"来消费。

**建议**：三件同做——① 默认改**定向跑**（`filter` 必填，按改动文件映射到测试文件）；② 上限参数化并允许宿主提高 `MAX_TIMEOUT_MS`（或改 `spawn` 长驻 watcher）；③ 超时返回体里带 `timedOut` 字段透传到 `TestRunResult`，⛔ 混进"失败计数 0"。

**状态**：`Verified-实证`（同一命令实测耗时／上限常量两处对撞）。

### QD-06 [P2] 遥测落盘的日切按 **UTC**、坏行**静默丢弃**、且⛔ 保留／轮转策略
