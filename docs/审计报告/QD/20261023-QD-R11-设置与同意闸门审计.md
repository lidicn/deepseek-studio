## 1. 发现

### QD-R11-01 [P1] 硬拒绝地板在生产链路上三层失效：full 档不调用、调用点不传 realPath、返回的 deny 被丢弃

**证据**：

`consent-router.ts` 把硬拒绝定义为跨档位的最后一道闸门，且在 `policy === 'allow'` 之前执行：

```ts
// src/host/consent-router.ts:81-110（定义）
/** 硬拒绝地板：任何档位都拦，用户同意也不能覆盖。 */
function checkHardDeny(toolId, params, realPath) {
  if (toolId === 'shell.exec') {
    if (/^(format|mkfs|diskpart)\b/i.test(cmd)) return 'dangerous-disk';
    if (/^shutdown\b|^reboot\b|.../i.test(cmd)) return 'power-control';
    ...
  }
  if (realPath) {
    const lower = realPath.toLowerCase();
    if (/^c:\\windows\\/.test(lower)
      || /^c:\\program files\\/.test(lower)
      || /^\/etc\//.test(lower)
      ...
      || /~\/\.ssh\//.test(lower)
    ) return 'sensitive-path';
  }
}

// src/host/consent-router.ts:158-160（先于 policy==='allow' 判定）
const hard = checkHardDeny(input.toolId, input.params, input.realPath);
if (hard) return { verdict: 'deny', reason: 'hard-deny', action, hardRule: hard };
if (input.policy === 'allow') return { verdict: 'safe', reason: 'policy-allow', action };
```

但生产的唯一调用点同时踩中三处：

```ts
// src/host/desktop-host.ts:1271-1276 —— full 档的 allow 直接把 requiresHumanConsent 置 false
requiresHumanConsent = verdict.decision === 'require-consent';
...
if (verdict.decision === 'deny') return finish('policy-denied', verdict.reason);

// src/host/desktop-host.ts:1286 —— 只有「需要同意」时才调用 routeConsent
if (requiresHumanConsent && !outsideApproved) {
  ...
  const wlResult = routeConsent({
    toolId: name,
    params: paramsBag,
    ...
    // ⛔ 没有 realPath
  });
  // :1307-1309 —— 只消费 whitelist-hit；deny 被静默丢弃
  if (wlResult.verdict === 'safe' && wlResult.reason === 'whitelist-hit') {
    requiresHumanConsent = false;
  }
}
```

**复现读数**：

- CONTROL-A / A1 / B：地板本身可判（`/etc/passwd`、`C:\Windows\...`、`format C:` 均 `deny`）。
- REPRO-B1：`shell.exec` + `shutdown /s /t 0` 在 `full` 档下 `evaluatePolicy` 返回 `allow/risk-detected`，`requiresHumanConsent=false` ⇒ `routeConsent` 根本不会被调用。
- REPRO-B2：生产调用对象里 `realPath` 不存在（源码断言 `callHasRealPath=false`）。
- REPRO-B3：调用点之后 500 字符内没有 `wlResult.verdict === 'deny'` 分支（`consumesDeny=false`）。
- REPRO-A3：即便补上 `realPath`，`C:\Users\dev\.ssh\id_rsa` 也只到 `ask`（`~` 模式永不出现于绝对路径）。

**后果**：

- **full 档**：`shutdown /s /t 0`、`format C:`、`diskpart`、写 `C:\Windows\System32\...` 直接执行——地板注释写的「任何档位都拦」不成立。`full` 档用户确实选择了「不询问」，但地板的存在意义正是排除这一类不可逆操作。
- **auto 档**：同一批命令会弹出审批；**用户点同意后照常执行**——`routeConsent` 已经判了 `deny`，但调用点把它丢掉。这违反「用户同意也不能覆盖」的硬拒绝契约。
- **敏感路径写入**：即使 auto 档用户拒绝，也只是普通审批；而一旦同意，`C:\Windows` 写入不受任何额外阻挡。生产环境连 `realPath` 都没传，等于整段 `realPath` 分支从未运行过。
- **修复 01 时若只补 `realPath`**，REPRO-A2（正斜杠 `C:/Windows/...`）与 A3（家目录 `.ssh`）仍会漏——必须一起处理（见 R11-03）。

**建议**：把硬拒绝抽成独立纯函数，在 `executeTool` 进入策略分支**之前**无条件调用（与档位、consent、白名单无关），命中即 `finish('policy-denied', hardRule)`；`realPath` 用 `fs.realpathSync.native`（不存在时回落 `path.resolve`）解析；删除或改写 `routeConsent` 内重复的地板判定，避免两处口径分叉。补回归：`full` 档 `shutdown` 必须拒绝；`auto` 档 routeConsent 判 deny 时不得进入 `ensureConsent`。

**状态**：Verified-实证（A2/A3/B1 纯函数 + B2/B3 源码断言）+ 代码事实（执行接线）

### QD-R11-02 [P2] MCP 连接生命周期不跟随配置：编辑不重连、删除不断连，旧进程继续可调用

**证据**：

```ts
// src/host/mcp-controller.ts:202-205 —— 已初始化的连接优先于配置
async connect(serverId: string) {
  const existing = this.connections.get(serverId);
  if (existing && existing.initialized) return existing;
  const config = this.servers[serverId];
  if (!config) return null;
  ...
}

// src/host/mcp-controller.ts:188-190 —— reload 只重读配置，不清理连接
reload(configPath?: string): void {
  this.servers = loadMcpServers(configPath);
}

// src/host/mcp-controller.ts:729-755 —— saveServer 直接覆盖 this.servers，不碰连接
saveServer(serverId, config) { ...; file.servers[serverId] = config; ...; this.servers = file.servers; }

// src/host/mcp-controller.ts:130-145 —— removeMcpServer 只改文件
export function removeMcpServer(serverId, configPath) { ...; delete bag[serverId]; fs.writeFileSync(...); }

// src/host/desktop-host.ts:636-646 —— 删除后只 reload()
const result = removeMcpServer(serverId, configPath);
if (result.ok) getMcpController().reload();
```

**复现读数**：

```
[R11-C/edit]   tools1=["old_tool"]  tools2=["old_tool"]  （配置已改成 new_tool）
[R11-C/remove] rmOk=true  listed=[]  callOk=true  data={"tool":"old_tool",...}
```

**后果**：

- **编辑不生效**：把服务器命令从 A 改成 B 并保存后，`mcp.list` 仍返回旧进程的旧工具表；新命令要等宿主重启才生效。界面已提示保存成功。
- **删除不撤权**：`mcp.list` 已不列出该服务器（`listed=[]`），但 `mcp.call` 仍能按旧 id 调用旧进程（`callOk=true`）。这是一个「UI 看不见、执行面仍在」的幽灵能力；模型在当前会话里早就见过该 `serverId`，删除后仍可继续调用，直到宿主进程退出。
- 对 HTTP/SSE 传输同样成立：`connectHttp` 的 `httpUrl` 缓存在旧连接上，改 URL 后仍打旧地址。

**建议**：`saveServer` / `remove` 后对 `serverId` 执行 `disconnect(serverId)`（kill 子进程、清 `connections`、置 `closed`）；`reload` 比较新旧配置摘要，丢弃摘要变化的连接；`connect` 命中缓存前校验配置摘要。补回归：编辑后 `tools2` 必须切到新工具；删除后 `callTool` 必须返回 `not available`。

**状态**：Verified-实证（C1/C2，真 stdio MCP server）

### QD-R11-03 [P2] 敏感路径地板对正斜杠 Windows 路径与用户家目录凭据路径无效

**证据**：

```ts
// src/host/consent-router.ts:100-110
if (realPath) {
  const lower = realPath.toLowerCase();
  if (/^c:\\windows\\/.test(lower)
    || /^c:\\program files\\/.test(lower)
    || /^\/etc\//.test(lower)
    ...
    || /~\/\.ssh\//.test(lower)
    || /~\/\.aws\//.test(lower)
  ) return 'sensitive-path';
}
```

**复现读数**：

- REPRO-A2：`C:/Windows/System32/drivers/etc/hosts` → `safe/policy-allow`（正斜杠形态未被识别）。
- REPRO-A3：`C:\Users\dev\.ssh\id_rsa` → `ask/outside-workspace`（`~` 只存在于 shell 习惯写法，绝对路径里永远没有）。
- CONTROL-A1：`C:\Windows\...`（反斜杠）→ `deny/sensitive-path`，证明反斜杠形态没问题。

**后果**：即使 R11-01 修好、开始传 `realPath`，用户家目录下的 `.ssh` / `.aws` / `.git-credentials` / `.npmrc` 仍只是普通审批对象，用户点同意即可写；正斜杠写法（来自模型或调用方参数）也绕开 Windows 系统目录判定。这与 `policy.ts` 的 `credential-path` 风险模式（只用于 shell 命令文本）不是同一层，文件写入侧没有等价保护。

**建议**：路径判定前统一 `path.resolve` + `toLowerCase` 并同时接受 `/`、`\`；用 `os.homedir()` 展开并匹配 `\.ssh\`、`\.aws\`、`\.gnupg\`、`\.npmrc`、`\.netrc`、`\.git-credentials`；保留 POSIX 规则。补回归：A2/A3 两条必须 `deny/sensitive-path`。

**状态**：Verified-实证（A2/A3）

### QD-R11-04 [P3] 白名单匹配在首条同工具异 action 记录处提前返回，后续命中被跳过

**证据**：

```ts
// src/host/consent-router.ts:136-144
for (const e of entries) {
  if (e.workspaceHash !== q.workspaceHash) continue;
  if (e.toolId !== q.toolId) continue;
  if (e.action !== q.action) return { hit: false, reason: 'action-mismatch' };  // ⛔ 应 continue
  if (e.ttlMs && q.now - e.createdAt > e.ttlMs) return { hit: false, reason: 'whitelist-expired' };
  if (globMatch(e.pathPattern, q.relPath)) return { hit: true, entry: e };
}
```

**复现读数**：白名单同时有 `file.write/write` 与 `file.write/append` 两条，调用 `{ append: true }` 时实际返回 `ask/action-mismatch`，期望命中第二条返回 `safe/whitelist-hit`。

**后果**：白名单是「少打扰」机制，不是安全边界；该缺陷只造成**多余审批**（用户可能以为白名单失效）。`file.write` 的 `append` 与 `write` 是唯一会产生同工具多 action 的场景，影响面有限。

**建议**：`return` 改 `continue`，循环结束后再按「是否见过同工具记录」给出 `action-mismatch` / `whitelist-absent` / `whitelist-expired` 中最准确的原因。

**状态**：Verified-实证（REPRO-D）
