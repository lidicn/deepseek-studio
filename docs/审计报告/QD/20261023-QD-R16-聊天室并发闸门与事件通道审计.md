## 1. 发现

### QD-R16-01 [P1] 房间分流⛔ 查 busy 却把 `agent-busy` 吞成空回复，空白 bot 消息永久落盘并推进气泡

**证据**：三段拼起来是一条完整的「有闸门、无出口」链。

`src/host/agent-channel.ts:269-282`——同一 `case 'send'` 里，直发路径有预检、房间路径没有：

```ts
if (msg.roomId && options.host.chatRoomRuntime) {
  ack(true, { roomId: msg.roomId });                       // ← 先 ack 成功
  await options.host.chatRoomRuntime.handleUserMessage(msg.roomId, text);
  return;                                                  // ← 没有任何 bot.running 预检
}
const botId = msg.botId ?? MAIN_BOT_ID;
const bot = options.host.bots.get(botId);
if (bot.running) {
  ack(false, undefined, 'agent-busy');                     // ← 直发路径会明确告诉调用方
  return;
}
```

`src/host/bot/round-orchestrator.ts:101-110`——generateReply 抛出后，原因被裸 catch 丢弃：

```ts
try {
  reply = await this.generateReply(persona, ctx);
} catch {
  contents[persona] = '';          // ← 'agent-busy' 的 message 不落任何地方
  spoken.add(persona);
  order.push(persona);
  continue;                        // ← 该 persona 仍进 members
}
```

`src/host/bot/chat-room-runtime.ts:431-455`——空串照旧落盘 + 照旧推 UI，⛔ 空值过滤：

```ts
const content = round.contents[persona] ?? '';
const stored = messageStore.append({ roomId, senderId: botId, senderType, content, … });
onBotReply?.({ kind: 'chat-bot-reply', …, content, messageId: stored.id, … });
```

**后果**（REPRO-A 实证）：第一条还在跑（引擎 500ms）时发第二条，第二轮 **1ms** 就"完成"——它没排队也没告知，而是：① `contents={"analyst":""}`；② 往房间历史写了一条 `sub-bot:""`（读数里明列，且顺序上排在第一条正常回复**之前**，用户看到的是「先空白、后有」）；③ 推了一个空气泡。用户的第二个问题**永久无人应答**，且房间历史里留下一条空白 bot 消息——刷新后从 store 重新拉历史，气泡还在（`getMessages` 原样返回），这正是「新对话仍有旧对话残留」在聊天室侧的形态。同一条消息还挤占了 `getRoomParticipants`/上下文注入的输入集（`buildContext` 的历史包含这条空消息）。

**建议**（两处都要动，缺一半不算修）：
1. 房间分流补 busy 预检——但语义⛔ 是直发路径的 `ack(false,'agent-busy')`（房间是多 bot，一个忙不代表整房忙）。可行形：在 `handleUserMessage` 入口对 `participants` 逐个查 `registry.get(botId).loop.running`，**忙的那位从本轮 targets 剔除并显式回一条 `chat-bot-reply{content:'（analyst 正在处理上一条，本条未排队）'}`**，或引入每房间 FIFO 队列（排队才是用户期待）。
2. orchestrator 的 fail-soft 保留原因：`catch (err) { contents[persona] = ''; … }` 之外新增 `errors?: Record<string,string>` 到 `ConversationRound`（或让 runtime 在 step 8 判空跳过落盘）。⛔ 让 `''` 变成一条持久消息。

**复现**：`复现用例/qd-r16-chatroom.test.ts` → `REPRO-A` 实测**失败=复现**（三条 soft 断言全红，读数见 §0）。CONTROL 腿同批绿。

**状态**：Verified-实证（宿主侧空回复落盘 + 空气泡 + 1ms 返回全部实测）。UI 侧「空气泡可见」是 `studio-chat-room.ts:310-317` `appendBotMessage(botId, ev.content ?? '')` 的代码事实，本轮未跑真 UI。

### QD-R16-02 [P1] 摘要器超时只放弃「读」，⛔ 中断 loop ⇒ 该 bot 此后一段时间整房静默

**证据**：`src/host/bot/chat-room-runtime.ts:284-311`——`Promise.race` 到点 reject，`finally` 只 `unsub()` + `clearTimeout()`，被 race 掉的 `bot.loop.send` 仍在跑：

```ts

  bot.loop.send(`${AGENT_SENTINEL}${prompt}`),   // ← 超时后这条 await 仍占着 AgentLoop 的 active
  timeout,
]);
…
} finally {
  unsub();
  if (timer) clearTimeout(timer);
}
```

`src/host/agent-loop.ts:85-87`——`active` 在第一个 `await` 之前同步置位，释放权唯一归 `finally`（`:171-178`），全局看门狗默认 15min 且只置 stopFlag。聊天室侧⛔ 任何 `bot.loop.stop()` 调用点（`grep -n 'loop.stop\|\.stop()' src/host/bot/chat-room-runtime.ts` 现跑 0 命中）。

**后果**（REPRO-B 实证）：摘要 150ms 超时抛出 `[summary: timeout]`，同一刻 `loop.running=true`；紧接着发进房间的新问题拿到 `contents={"analyst":""}`——即 QD-R16-01 的空回复，但触发者不是用户连发，而是**一次内部摘要**。引擎侧真实延迟由 DeepSeek 页面决定（可到分钟级），所以「一段时间」的实际长度就是那一次 send 的自然结束时刻，最坏由 15min 看门狗兜底。用户视角：散会/手动总结之后，房间对该 bot 静默若干分钟，每条提问都变成一条空白气泡（残留 + 断流复合）。摘要有租约/CAS 保护（`:302-307` 注释），所以脏摘要不会落盘——但 loop 占用这一条腿没管。

**建议**：摘要器超时后**必须释放占用**——两条合法修法，选一：① `timeout` 分支里 `bot.loop.stop()`（`agent-loop.ts:82-84` 已有该出口，置 stopFlag 后 loop 在下一回合边界自行 `finally` 释放）；② 给摘要单独走一个不与房间成员共用的 bot（`summarizerBotId` 已有该能力，缺的是装配处保证不撞成员）。修法①更省，且同时治好 R16-01 在摘要路径上的暴露面。

**复现**：`qd-r16-chatroom.test.ts` → `REPRO-B` 实测**失败=复现**（`running=true` 与空回复两条断言红）。

**状态**：Verified-实证。

### QD-R16-03 [P1] 回复落盘/后续步骤抛错 ⇒ `round-complete` 不推，聊天室输入框永久锁死


`src/ui/studio-chat-room.ts:241-246`——ack 分支⛔ 碰 `roundInProgress`：

### QD-R16-04 [P2] 房间轮次把 `chat-send` / `chat-insert` 升成永久免检，且作用域是整个 bot⛔ 只是这一轮

**证据**：`src/host/bot/registry.ts:46-48`（永久类无参数、无 TTL）+ `chat-room-runtime.ts:230-232`（每轮房间回复前加，⛔ 轮次结束后撤销）+ `:292-293`（摘要器同样加）：

```ts
addPermanent(tool: string): void { this.entries.set(`${tool}#`, null); }
…
state?.sessionAllowlist.addPermanent('chat-insert');
state?.sessionAllowlist.addPermanent('chat-send');
```

撤销点只有 `setPolicyMode`（`desktop-host.ts:1091-1092`）、`setWorkspaceRoot`（`:1102-1103 / 1112-1113`）与 bot 断开三处——都是**用户手动动作或生命周期事件**，⛔「本轮结束」。

**后果**（REPRO-C 实证）：走过一次房间回复后，`has('chat-send', {text:'与房间无关的正文'})` = `true`，`chat-insert` 同。也就是说：某 bot 一旦进过一次聊天室，之后任何路径（面板直发、`POST /v1/agent/send`、automation 任务、离线审计 runner）用同一 bot 触发 `chat-send`/`chat-insert` 都**不再过同意闸门**，且不绑参数。`chat-send` 是把文本按回车送进 DeepSeek 页面的工具，`chat-insert` 是往输入框写文本——两者合起来足以用当前登录账号发出任意正文，而用户只在很久以前的某次进房时被问过（实际⛔ 问过：`addPermanent` 是代码写的预授权，不是用户点允）。
另一半不一致：`setPolicyMode` 的 `clear()` 连**预授权**一起抹（注释只说「旧 allow-session 授权一律作废」），于是「永久」既不真永久、也⛔ 按语义边界撤销——档位切换这种事与「这个 bot 是聊天室成员」无关。

**建议**：房间用途的放行降到 `addTemporary(tool, params, ttl)` 或加轮次作用域（轮次结束 `revoke`）；保留 `addPermanent` 给 bot **创建时**一次性预授权（`desktop-host.ts:860-861/888-889/1483-1484` 就是这个形状），而不是每轮重复打。若决定维持永久，至少把它绑到「本轮 roomId」并在 `setPolicyMode` 之外提供撤销口，并把 `clear()` 拆成 `clearTemporary()` / 保留预授权，别再让档位切换误伤。
