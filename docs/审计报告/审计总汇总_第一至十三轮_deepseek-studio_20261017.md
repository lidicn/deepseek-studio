## 一、执行摘要

十三轮审计从「用户报的三个症状」出发，最终覆盖全部代码区域（TS + Rust + 配置 + 构建产物），并建立了防复发机制。

**三个原始症状的最终结论**：

| 症状 | 表象 | 真实根因 | 状态 |
|---|---|---|---|
| MCP 存不上 | 保存后列表不刷新 | ① `ui:mcp-saved` 死事件 ② 存储写链一次失败永久毒化 | ✅ 双根因均修，真机闭环 |
| 新建项目不刷新 | 侧边栏列表不变 | ① `ui:projects-updated` 全代码库无人 emit ② 同上写链毒化 | ✅ 双根因均修，真机闭环 |
| 按钮点不动 | 点击无反应 | ① 核心源文件 0 字节 ② 全域静默层（emit 吞异常 + 静默 catch） | ✅ 不复现 |

**一句话总结**：这个项目的主要缺陷模式不是"写得差"，而是**同一职责存在两套标准**——每一处"曾经做对"的代码，后来都成了修复"做错"那处的模板。但更根本的问题是可观测性缺失：**失败路径上没有任何信号**，导致上述症状长期无法定位。

**一个必须诚实说明的事实**：十三轮里我发现的产品缺陷逐步趋零（第十三轮为 0），但发现并修正了**6 处测试/审计自身的缺陷**（详见 §六）。虚假绿灯比没有绿灯更危险。

## 四、第一轮三条原始症状的最终闭环

这是本次审计的主线。三条症状分别在第 11、12、13 轮在**真实浏览器 + 真实 WebSocket**上完成闭环验证。

| 症状 | 根因分解 | 修复轮次 | 真机验证轮次 | 最终验证结果 |
|---|---|---|---|---|
| **① MCP 存不上** | a. `ui:mcp-saved` 发了没人听（UI 不重绘）<br>b. 写链毒化（根本没存上） | 六 / 六 | 十三 | `mcp.save {serverId:"e2e-test-server"}` → 列表出现该服务器 ✅ |
| **② 新建项目不刷新** | a. `ui:projects-updated` 无人 emit<br>b. 写链毒化 | 六 / 六 | 十二 | `folder.pick → project.create → project.list` 全链，持久表可读回 ✅ |
| **③ 按钮点不动** | a. 源文件 0 字节<br>b. 全域静默层（emit 吞异常 + 静默 catch） | 上游 / 六 | 十一 | 真实点击 FAB → 面板展开（x=0, w=260）✅ |

**值得注意**：症状 ①②各有**两个独立根因**，分别对应"UI 反馈断裂"和"数据根本没落盘"。只修任意一个都不足以闭环——第十三轮之前的验证之所以反复，正是因为两条根因交织。

## 五、五大共性模式（比单个 bug 更重要）

### 模式一：同一职责两套标准（本项目最主要缺陷模式）

| 职责 | 做对的那处 | 做错的那处 |
|---|---|---|
| 网络入口鉴权 | `/v1/*` bearer、`/agent-ws` query token | `/studio` 零鉴权（P0-2） |
| 命令执行红线 | `capabilities/shell.ts`（`shell:false` + 语法拒绝 + 工作区约束） | `automation.ts` `exec`（P2-2） |
| XSS 转义 | 模型数据主链路 `escapeHtml` | `src/ui/*` 零转义（P1-5~8） |
| 定时器管理 | 正式请求路径（`:313`） | 测试路径 / race 路径（P1-9~10） |
| Promise 链失败恢复 | `bridge/storage.ts:359`（注释明写"前次失败不得阻断后续"） | `file-storage-backend` 无 `.catch`（P0-4） |
| `ok` 检查 | `workspace.set` 检查了 | `policy.set` / `memory.delete` / `mcp.remove` 未检查（P1-12~16） |
| 进程终止 | Node 侧 `capabilities/shell.ts` 做进程树处理 | Rust 侧裸 `child.kill()`（P1-20） |
| UI 生命周期 | 新代码 `destroy()` 完整 | 旧代码 18 处订阅 0 退订（P1-2） |

**关键规律**：**每一处"曾经做对"的代码，后来都成了修复"做错"那处的模板**（P0-4 照抄 `enqueueMutation`、P2-2 照抄 shell capability、P1-2 照抄新 UI 的 `destroy()`）。说明团队有能力写出正确实现，**缺的是横向一致性的强制机制**——这正是第七轮新增的 `conventions-audit` 在补的位置。

### 模式二：清理逻辑写在 `await` 之后

异常路径一律跳过清理：

- `testConnection` 的 `proc.kill()` 在 `await` 之后 → 超时泄漏子进程（P1-9）
- 多处 `try/await/catch` 中资源释放在成功分支而非 `finally`

**统一解法**：改 `try/finally`。

### 模式三：可观测性缺失放大了所有缺陷（最根本的一条）

`EventBus.emit` 原为无条件 `catch {}`，加上 7 处静默 catch，构成**全域静默层**：UI 逻辑出错时界面「没反应」、控制台也「没反应」。这是三条原始症状长期无法定位的直接原因。

**如果只提一条最高优先级改进建议，就是这条：所有异步调用失败时必须留下日志，让"静默失败"变成"可见的失败"。**

### 模式四：静默降级

| 场景 | 表现 |
|---|---|
| `node:sqlite` 不可用 | 持久化退化为内存，仅一行 `console.warn`，UI 无感知（P2-5） |
| `better-sqlite3` 未编译 | 降级内存后端 |
| 配置持久化失败 | 返回 `ok: true`（P1-16） |

共同点：**降级是合理的容错，但没有告知用户**。项目其实已有 `stats.backend` 这类可观测字段，只是没接到 UI。

### 模式五：验证对象与真实契约脱节

| 实例 | 表现 |
|---|---|
| 团队自建安全扫描器能报错但没接 gate | 防护形同不存在（P2-6） |
| `tsc` 报错不阻断构建 | 硬错误被忽略 |
| 12 条红线测试在 CI 上永远红 | 长期红 = 无覆盖（P1-22） |
| **mock 宿主消息类型写错** | 只看发送方向的断言全绿，依赖返回值的链路静默中断 |

## 六、审计方法论的六次自我纠错

这部分比缺陷台账更值得读——**审计者的工具本身也需要被审计**。

| # | 错误 | 后果 | 修正 |
|---|---|---|---|
| **1** | 十轮里把 18 条失败笼统称为"环境噪音"，从未逐条归因 | 其中 **12 条是安全红线**，因平台依赖在 CI 上从未生效 | 第十轮逐条归因 + 平台依赖可注入化 |
| **2** | 第五轮写下"4 条待查，尤其命令注入红线"，此后九轮未查 | 最危险的防护恰恰是验证不到的那条 | 第十轮补上 |
| **3** | 面板展开用 `computed display` 判断 | 实际靠 `transform: translateX(-100%)`，display 恒 `block` → **断言恒真** | 改用 class + `rect.x` 视口位置 |
| **4** | 用 `children[1]` 取侧边栏面板 | 取到的是 overlay（x=0），真面板已在视口外（x=-260）→ 假绿灯 | 改用 `.studio-sidebar` class |
| **5** | 泄漏基线取在对话框打开态 | 循环后计数自然下降，负增长也判"通过" | 宁可删除该断言，也不留假绿灯 |
| **6** | **E2E 一直用仓库提交的旧构建产物** | 测的不是当前 `src/` → 出现 3 条"假失败"（档位旧标签、policy.set 未下发、MCP 列表不刷新） | 运行前强制 `esbuild.inject.mjs` |

**共同点：验证前没有确认被测对象是不是你以为的那个。**

**最深的教训**：如果只统计"发现了几个 bug"，第十三轮是 0；但如果统计"修正了多少条会误导人的结论"，是 3。**一个虚假的绿灯，会让后续所有人都在错误的基础上做判断。**

| **MCP 对话框校验** | `studio-mcp-dialog.ts` | 缺命令时显示「请输入启动命令」且**不调用宿主**——校验拦在调用前，有可见反馈 |
| **`EventScope`** | `studio-ui-core.ts` | 集中登记 disposer、销毁时一次性退订（第八轮引入，是解决订阅泄漏的正确抽象） |
| **重复代码率** | 全项目 | 0.81%（jscpd）——相当干净 |
