## 一、新发现 P1+ —— 权限模式下拉是装饰控件（安全默认值静默降级）

| | |
|---|---|
| **严重度** | P1+ / 功能失效 + 安全默认值降级 |
| **位置** | `src/ui/studio-input-bar.ts:109-117`（修复前） |
| **证据** | 静态追踪 + 全项目调用点枚举 |

### 证据链

**① 全项目 `policy.set` 只有一处调用**

```
grep -rn "'policy.set'" --include="*.ts" src
  src/host/desktop-host.ts:504        ← 宿主注册
  src/host/tool-definitions.ts:186    ← 工具定义
  src/shared/tool-contract.ts:125     ← 契约
  src/ui/studio-settings-panel.ts:154 ← 唯一调用点
```

**② 输入框栏的切换只写内存**

```ts
option.addEventListener('click', () => {
  globalState.policyMode = mode as 'full'|'auto'|'ask';   // ← 只改内存
  modeBtn.querySelector('.studio-bar-label')!.textContent = label;
  globalEvents.emit('ui:policy-changed', mode);            // ← 零订阅者
});
```

**③ `globalState.policyMode` 的所有读取点都在 UI 内部**（渲染用），无一处同步宿主：

```
src/ui/agent-panel.ts:217       渲染选中态
src/ui/studio-input-bar.ts:99/105/106/110  渲染
src/ui/studio-settings-panel.ts:148/153    渲染
src/ui/studio-ui-core.ts:25/57             类型与默认值
```

**④ 唯一的"同步企图"是 `ui:policy-changed`，而它在修复前是 emit-only 死事件**（零订阅者）。

### 为什么比第四轮的"假成功"更严重

| 层级 | 轮次 | 行为 | 后果 |
|---|---|---|---|
| 第一层 | 第一轮 P2 | UI 缺 `workspace` 档、默认 `full` | 用户选不到最严档 |
| 第二层 | 第四轮 P1① | 设置面板调了 `policy.set` 但**不检查 ok** | 失败时显示严格档、实际宽松档 |
| **第三层** | **本轮** | 输入框栏**根本没调用** | 无论成功失败，宿主档位**从未改变** |

用户在输入框栏切到「每次询问」，界面显示已切换，**宿主仍在原档执行所有工具**。

### 修复

`src/ui/studio-input-bar.ts`：
1. 真正 `await callHostTool('policy.set', { mode })`；
2. 检查 `result.ok`，**失败回滚 UI**（含下拉选中态），并 `console.warn` 报错；
3. 设置面板订阅 `ui:policy-changed` 同步选中态（补 `data-mode` 标识）；
4. 保留 emit 供其他组件同步。

## 二、P0 修复落地（3 个，① 由上游完成）

### ① 空文件致输入框栏缺失 — ✅ 上游已修

### ② `/studio` WS 零鉴权 — ✅ 本轮修复

上游已补了一半（带伪造 Origin 的网页会被 upgrade 校验拦住）。本轮补齐剩余缺口。

**修复前实测**（无 Origin 的本机脚本）：

```
已登记页: [{"origin":"https://chat.deepseek.com","untrusted":false}]
executor 调用次数: 1
实际参数: [{"tool":"shell.exec","params":{"command":"id"}}]
⚠ 未授权执行成功
```

代码里升级阶段的注释写着"无 Origin 的非浏览器客户端放行，由 hello-ready 闸门兜底"——
但 `tool-call` 分支**完全不查 `rec.untrusted` / `rec.ready`**，兜底并不存在。

**修复**（两道防线）：
- **闸门一**：无 Origin 的连接必须出示本机凭据 `?token=`，与既有 `/agent-ws` 通道口径一致；
  未配置 token 时一律拒绝（fail-closed）。
- **闸门二**：`tool-call` 分支执行前校验 `rec.untrusted || !rec.ready`，拒绝并返回 `untrusted-connection`。

**修复后实测**（5 个场景）：

```
✅ 已拦截 恶意 Origin 网页 (https://evil.com)        | 连接=被拒 | executor调用=0
✅ 已拦截 无 Origin + 无 token（第二轮 P0 原始场景）  | 连接=被拒 | executor调用=0
✅ 已拦截 无 Origin + 错误 token                      | 连接=被拒 | executor调用=0
⚠ 可执行 无 Origin + 正确 token（本机合法客户端）     | 连接=成功 | executor调用=1
✅ 已拦截 未配置 token 时无 Origin 连接               | 连接=被拒 | executor调用=0
```

第四个场景是**设计意图**——本机 CLI/脚本确实需要接入，凭凭据接入后即可执行。

### ③ MCP `spawn` 致宿主崩溃 — ✅ 本轮修复

**修复前**：`spawn` 无 `error` 监听器 → ENOENT → `uncaughtException` → 宿主进程退出。

**修复**：
- 正式连接（`:206` 附近）与测试连接各加 `proc.on('error')`，转成普通连接失败；
- 测试连接用 `try/finally` 无条件 `proc.kill()`（原 `kill()` 写在 `await` 之后，超时路径跳过）；
- 超时定时器保存句柄，成功路径也 `clearTimeout`。

**实测**：

```
--- 场景1: spawn 不存在的命令 ---
  结果: {"ok":false,"error":"进程启动失败: spawn __no_such_cmd_xyz__ ENOENT"}
  是否触发未捕获异常: 否 ✅（宿主存活）
--- 场景2: 超时路径子进程回收 ---
  调用前 ChildProcess: 0
  耗时 5509ms 结果: {"ok":false,"error":"initialize timeout"}
  1.5秒后 ChildProcess: 0 ✅ 已回收
```

### ④ 存储写链永久毒化 — ✅ 本轮修复

照抄同项目 `bridge/storage.ts` 的 `enqueueMutation` 双 `then` 模式：本次调用方照常收到 reject，
链条本身续命。

**实测**（循环引用注入）：

```
第1次(正常): {"a":1}
第2次: 按预期失败 -> Converting circular structure to JSON
第3次(正常数据): 成功 ✅
最终: {"a":1,"c":3}
```

## 四、治理闸门（4 项全部落地）

| 项 | 内容 | 作用 |
|---|---|---|
| **Node 版本声明** | `package.json` 增加 `engines.node >= 22.5.0` | 此前未声明，`node:sqlite` 不可用时静默退化为内存，重启丢数据 |
| **安全扫描接 gate** | `tools/gate/run.ts` 增加 `security-audit` 步骤 | 该工具此前存在且能正确报错（exit 1），但从未被调用 |
| **扫描器降噪** | `tools/audit/security.ts` 分级 error/warn | 42 条噪→0 error；识别已转义/已净化写法，避免习惯性忽略 |
| **typecheck 固定本地编译器** | `node node_modules/typescript/bin/tsc` | 原用 npx，会解析到全局 TS 7.x 致 `baseUrl` 报错误失败 |

### 扫描器降噪的细节

改造前只查 `.innerHTML =`，42 条命中里大半是 `= ''` 清空与纯字面量。改造后：

- `= ''` 清空 → **不报**
- 纯字面量（含跨行模板）→ **warn**
- 插值被 `escapeHtml` / `sanitizeHtml` / `renderMarkdown` / `buildCardHtml` 包裹 → **warn**
- 纯数值表达式（如 `${Math.round(a/b)}`）→ **warn**
- 其余含插值的动态赋值 → **error**（阻断）
- 带 `// security-ok: 理由` 注释 → 人工确认，降为 warn（用于 `el()` 的 `html` 通用逃生口等）

### 一个值得团队注意的观察

第六轮新发现的 P1+（权限模式不下发）与第四轮的 P1①（policy.set 假成功）、
第一轮 P2（档位定义不一致）构成**同一条链上的三层缺陷**。

而不是继续在各组件里各自修修补补。
