## 1. M1-C 造样：步骤与断言口径

### 1.1 先说一个必须纠正的前提（**Gate 的 M0 样本不是 SSE**）

Gate 的 M0 离线分布里那 1 组 `long-stream-no-sentinel`（`logs/cdp-chat-capture/34740.130-response-body.txt`，23,611 B）**不是 SSE 流**：

| 证据 | 读数 |
|---|---|
| response meta 的 `content-type` | **`application/json`**（对照真 SSE 样本 `34740.129` 是 `text/event-stream; charset=utf-8`） |
| request URL | `GET /api/v0/chat/history_messages?chat_session_id=…`（**历史消息快照**，非 `/chat/completion`） |
| body 开头 | `{"code":0,"msg":"","data":{"biz_code":0,…,"chat_session":{"id":…}}` |
| 可否 JSON 解析 | **可以**（整块是一个 JSON 对象） |
| `quasi_status` 出现次数 | **0** |
| `event: close` / `[DONE]` / `<task_complete>` | 0 / 0 / 0 |
| 那 4 处 `FINISHED` 的上下文 | 全是 `…,"status":"FINISHED","incomplete_message"…` —— 是**消息对象的状态字段**，不是 SSE 帧里的完成信号 |

→ 它之所以被 M0 判成「长流无哨兵」，是因为**它根本不是流**，不是「流到了尾却缺哨兵」。拿它当 M1 的哨兵缺失样本会造出假结论。**这条报给 PM 与 Gate**，口径要改（分类前先看 `content-type`/URL 是否 SSE）。

### 1.2 正确的造样步骤（我改从真实 SSE 裁）

源：`logs/cdp-chat-capture/34740.129-response-body.txt`（2,065 B，`content-type: text/event-stream`，含真哨兵）。

| 步 | 操作 | 结果 |
|---|---|---|
| ① | 确认源是真 SSE（`content-type` 含 `text/event-stream`） | ✓ |
| ② | 按**顺序**裁掉尾部哨兵帧：`event: close` → `data: {…"p":"response/status"…}` → `{"p":"quasi_status","v":"FINISHED"}` | 实测移除 3 帧，共 107 字符 |
| ③ | 保留头部（`event: ready` / `update_session`）与 `response/fragments` 段；把 **fragments 段**按字节重复 23 次，使总长 ≥ 2×M0 长流门槛（4096 B） | 产出 **8,216 B**（`repeatFactor=23`） |
| ④ | 生成**同源对照**：同一份源**不砍尾** | 2,065 B，带全部哨兵 |

### 1.4 断言口径（M1-C 回放要卡的四条）

1. **区分度**：同一脚本喂两份 fixture → 输出**必须不同**。`long-no-sentinel` 应判 `interrupted`（新终态），`long-with-sentinel` 应判 `complete`；若两者同判 → 判停逻辑没真正用上哨兵，**FAIL**。
2. **不误伤**：喂 `long-with-sentinel`（含 FINISHED）时**不得**出现 `interrupted`。
3. **证据留痕**：每轮回放必须留下「页侧哨兵结论 + 宿主终态」的成对记录（页侧 `sawFinishSentinel` 与宿主 `completion` 要能对齐到同一轮）。
4. **不崩**：未知取值（如将来新增的终态）必须单列而不是抛异常——沿用 M0 脚本的既有约定。

## 2. M1-D 登记表模板

`docs/验收/20261102-M1-D-真机登记表-同提示词5次.md`（照 `docs/C1-真机人工清单-20261028.md:72-80` 的「登记无法执行项」格式）：

- **阶段 0 前置**：进程/端口、**当轮产物双处同哈希 + stderr `inject loaded from:` 原文**、产物指纹表、**限流探活**（报「消息发送过于频繁」即停，本轮作废）。
- **阶段 1**：固定一条长输出提示词（讲解 SSE 三种完成信号，≥800 字）→ **新会话 ×5**、间隔 8–15 秒；每轮登记发送时刻、状态码、响应字节、宿主终态、耗时、**页侧哨兵四选一**（FINISHED / [DONE] / task_complete / 无）。
- **阶段 2 判读表**：5 轮全哨兵 → 未观测≠不存在；出现无哨兵且宿主非 complete → 哨兵缺失可复现，M1 的 `interrupted` 有实证；出现无哨兵但宿主仍 complete → 走了旁路，需回看页侧日志；任一轮限流 → 作废不下结论。
- **必须写的两句话**：是否观测到长流无哨兵；该结论是否混入限流因素。

## 5. 追加：造样被**现成分类器**认账（不需改 `tools/**`）

Core 在改 M1 宿主侧、Gate 在改 M0 口径，我这轮不占窗口，做了一件能替双方兜底的事——**用 Gate 现成的 `tools/metrics/term-state.ts` 直接分类我造的 fixture**，证明造样在工具链里真的立得住。

### 5.1 踩到的两个工具侧事实（Gate 改口径时需要知道）

| # | 事实 | 位置 | 影响 |
|---|---|---|---|
| A | capture 分组扫描**只在输入路径以 `cdp-chat-capture` 结尾时**才启用 | `tools/metrics/term-state.ts:423`（`/cdp-chat-capture$/.test(p)`） | 我的 fixture 目录最初叫 `capture/` → 分类器扫不到、报告显示「（无抓包）」。改名为 `cdp-chat-capture/` 后才被识别。**Gate 若改口径，建议把「目录名硬依赖」也收敛成显式参数**，否则换目录名就静默失效。 |
| B | 分类器**只看 body 字节数与哨兵正则**，不看 `content-type`/URL | `term-state.ts:172-181` | 这正是 `34740.130`（`application/json` 的 history 快照）被误判成「长流无哨兵」的机制：**分类器没有任何「这是不是流」的前置判断**。PM 已定的口径（先看 content-type/URL 再看哨兵）正好补这里。 |

### 5.2 造样被认账的实测读数

命令（只读，不改 `tools/**`）：

```
npx tsx tools/metrics/term-state.ts logs/verify-f1f2/m1c-fixtures/cdp-chat-capture \
     --out logs/verify-f1f2/m1c-fixtures/term-state-fixture-run.md
```

退出码 **0**（有终态证据被分桶），报告 C 段：

| 分类 | 请求数 |
|---|---|
| `finished-signal` | 1 |
| `long-stream-no-sentinel` | 1 |

明细：
- `m1c.long-no-sentinel`：status=200 **body=8216B** agent=N task_complete=N FINISHED=N [DONE]=N → **long-stream-no-sentinel**
- `m1c.long-with-sentinel`：status=200 **body=2065B** agent=N task_complete=N **FINISHED=Y** [DONE]=N → **finished-signal**

→ **区分度成立**：同一份造样流程产出的两份 fixture，被现成分类器分到**不同桶**；且无哨兵版确实越过 4,096 B 长流门槛（8,216 B），不会被误落「短体」。

### 5.3 给 M1-C 回放的可直接复用形态

造样脚本 `logs/verify-f1f2/m1c-make-fixture.mjs` 现在同时产出两套形态：

- `m1c-fixtures/long-no-sentinel.sse.txt` / `long-with-sentinel.sse.txt`：**裸 SSE**，给「M1-C 回放」直接喂引擎/判停逻辑；
- `m1c-fixtures/cdp-chat-capture/m1c.long-*.{request.json,response-meta.json,response-body.txt}`：**M0 分类器可消费的三元组**，meta 里带真实 SSE 的 `content-type: text/event-stream; charset=utf-8` 与 `/api/v0/chat/completion` URL。

→ M1-C 回放建议用**裸 SSE 那套**（判停逻辑吃的是流文本）；M0 复跑用**三元组那套**。两者同源、只差哨兵尾帧。
