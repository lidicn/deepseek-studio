## 6. 缺陷与观察（新增）

### F1（中）打字预热实际只用「第 6 个字符」那一小段做 select

- **机制**：`scheduleMemorySelectWarmup` 在**第一个草稿长度 ≥ 6 的 input 事件**上排定时器，并把**当时的草稿快照**存进 `warmupDraft`；之后 600 ms 到点就用这份快照去 `kickMemorySelect`。连续打字时，命中的是第 6 个字符那一刻的草稿。
- **实测**：运行 A / C 的预热 select 草稿长度**均为 6 字**（`taskTextLen: 6`，原文「请帮人在 d」「核对一下 d」）；页内 select 调用记录里**从未出现**以最终 148/160 字全文发起的 select。
- **后果**：① 选中的 12 条与任务语义脱钩（运行 A 的任务问「记忆注入瘦身」，选进来的是「媒体搜索技能诉求」「用户角色」等）；② 发送点因「草稿是最终文本前缀」**复用同一个 pending**，最终文本自己那份 select **从未发出**。
- **建议**：预热取「当前草稿」而不是首次快照；或在发送点对**最终文本**另发一次 select（并让迟到结果按 seq 排队覆盖旧结果，P1 的 seq 机制已具备该能力）。

### F2（中）「草稿前缀复用」判据过宽，导致跨轮沿用旧记忆

- **机制**：`kickMemorySelect` 的复用条件是 `trimmed.startsWith(existing.task) && existing.task.length >= 6`。
- **实测**：运行 B 的任务（查 lever-hub 产线 / dcd 决策）与运行 A 的任务语义完全不同，却因为都以「请帮我在 d」开头 6 字而**复用了运行 A 的 pending** —— 页内 select 调用数**没有增加**，两轮记忆块**逐字节相同**（6,082 B，`equal=True`）。
- **后果**：一次 select 的结果可以跨任意多条用户消息沿用，只要开头 6 字相同；记忆选择与当前任务脱钩。
- **建议**：复用判据至少要求前缀长度达到某个比例（如 ≥ 任务长度的 30%）或直接重发 select（seq 机制可保证新结果不被旧结果覆盖）。

### F3（订正我自己上一轮的结论）上一轮 F1「页面通道固定 ~150 ms 开销」不成立

- 上一轮（2026-11-02 M1.5）我写：页面通道 select 往返 149/166/170 ms，**稳定超过** 120 ms 预算 ⇒ 每轮必超时。
- **今天的数据推翻其中的「固定开销」部分**：页面通道同一路径实测 **10 / 11 / 12 / 96 ms**（文本 6–1,741 字），**只有** 1,533 字重复词文本才 236 ms。
- **真正的变量是 FTS 查询文本本身**（长度 × 内容重复度）：上一轮那段 149–170 ms 的样本恰好是 1,916 字的**累积串**（ chat-insert 不清空输入框造成），是最贵的一类文本。
- **仍然成立的部分**：超过预算时确实会 0 B，且 P1 的「迟到结果落地」正好补上这一段。

### F4（低）`memory.bytes` 与 body 内测量差 2 B（口径说明，非缺陷）

`memory.bytes` 含前导 `\n\n`，body 内呈现不含。两者逐次吻合，可作为以后回归的判据（差值恒为 2）。
