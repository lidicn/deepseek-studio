### 1.3 脚本

| 脚本 | 作用 |
|---|---|
| `logs/verify-f1f2/gen-attach-samples.mjs` | 生成上述两个合成样本并打指纹 |
| `logs/verify-f1f2/attach-e2e.mjs` | CDP 驱动：`--phase e2|e1|e3`；`DOM.setFileInputFiles` 上传 + 发消息 + 采集读数 |

`attach-e2e.mjs` 的能力与纪律：

- **上传**：优先复用页面现成 `input[type=file]`，没有就造一个隐藏 input，再用 `DOM.setFileInputFiles` 塞文件；随后回读 `input.files[0].name/size` 与页面上的文件 chip，确认**文件确实挂上了**。
- **发消息**：填 textarea → 先试 Enter、再回退点 `div.ds-button--circle`（UI 踩过的坑：发送控件是 div 不是 button，Enter 在某些页面态不触发）。
- **读数**（全部结构化，不含会话正文）：`Network.responseReceived` 里 `/api/v0/chat/*` 的状态码与耗时；页面错误/提示元素**原文**（`[class*=error]` / `[class*=toast]` / `[role=alert]` 等，截 300 字符内）；模型回答节点数与长度。
- **E3 加码**：倍率阶梯 ×1/×2/×3，每级记录累计字节 + 错误原文；一旦报错即停。
- 退出用 `ws.terminate()` + 120ms 收尾（P12 修法，避免 libuv 断言污染读数）。

## 2. 阶段 2 执行计划（**待 PM 放窗**）

严格按卡面顺序，**E2 先**：

1. **探活**：先发 1KB 小消息；若返回「消息发送过于频繁」/限流文案 → **立即停**，不再撞（避免延长冷却），报告只记「限流中，本轮无效」。
2. **E2（对照）**：新会话、**不传附件**，发那条 256,036 字符消息 → 记录是否接受、耗时、状态码。
3. **E1（实验）**：新会话、**只上传 456,775 B 附件**（先确认 `input.files[0].size` 对得上），再发**同一条**消息 → 记录同上。
4. **E3（加码）**：倍率阶梯递增，记录累计字节 + 错误文案原文。
5. 每条之间 **5–10 秒**间隔；每级都开**新会话**（避免历史预算污染）。

**判定**

| 结果组合 | 判定 |
|---|---|
| E2 接受 且 E1 拒绝 | 450KB 墙存在且附件不计入预算 → **附件通道值得立项**（PM 卡面即此判据） |
| E2 拒绝 且 E1 拒绝 | 墙存在且**附件计入**预算 → 附件通道价值大幅下降 |
| E2 接受 且 E1 接受 | **450KB 墙不存在或远高** → 之前撞的是限流，附件通道不成立为独立议题 |
| 任一轮出现限流文案 | 该轮**作废**，记「混入限流因素」，不判结论 |

## 5. 阶段 2 实测（2026-11-02 12:58–13:26，窗口由 PM 放行）

### 5.1 探活（前置）

`logs/verify-f1f2/attach-probe-alive.mjs`：1 条 **93 B** 小消息 → **200**、`{"ok":true,"answer":"就绪"}`、耗时 **11,876 ms**、**无「消息发送过于频繁」类文案** → 账号不在限流冷却，允许进入 E2。

### 5.2 E2 对照（**不传附件**，发 256,036 B 纯文本）

| 项 | 读数 |
|---|---|
| HTTP | `POST /api/v0/chat/completion` **200** |
| 发送方式 | Enter（`via=enter`） |
| 发出耗时 | 1,246 ms |
| 宿主日志 | `xhr chat body len=258362` → `chat body injected len=268309` → SSE 逐片 `extracted` → `response/status SET FINISHED` → `event: close` |
| 模型回答 | **有**（宿主日志出现完整回答文本与收尾句） |
| 结论 | **纯文本 256KB 被接受** |

### 5.3 E1 实验（**只传 456,775 B 附件** + 同一条 256,036 B 文本）

| 项 | 读数 |
|---|---|
| 上传 | `POST /api/v0/file/upload_file` **200**（`create_pow_challenge` 先走 PoW） |
| **附件是否随消息送出** | **是** —— 页内抓到的完整 chat body：`ref_file_ids` = **数组长度 1**，`items=["file-8ad3729c-ed11-4c4b-9351-8ba9d49a6dd2"]`；body 258,397 B、`prompt` 256,035 字符 |
| HTTP | **200** |
| 发出耗时 | 1,465 ms |
| 结论 | **附件 + 256KB 文本被接受** |

### 5.4 E3 加码（纯文本逐级，**不带附件**）——找「墙」

| 文本字节 | HTTP | 耗时 | 真实错误文案 |
|---|---|---|---|
| 262,144 | **200** | 1,585 ms | 无 |
| 524,288 | **200** | 2,024 ms | 无 |
| 1,048,576 | **200** | 2,218 ms | 无 |
| **2,097,152** | **200** | 4,440 ms | 无 |

→ **纯文本路径上到 2 MB 全接受**，卡面假设的「450KB 墙」在纯文本下**不存在或远高于 2 MB**。

### 5.5 E3 加码（**带附件** + 逐级加码）

| 文本字节 | `ref_file_ids` 长度 | HTTP | 真实错误文案 |
|---|---|---|---|
| 512,072 | **1** | 200 | 无 |
| 1,024,144 | **1** | 200 | 无 |
| 1,536,216 | **1** | 200 | 无 |

→ 附件**确实计入请求**（`ref_file_ids` 非空），但**同样不被拒**；带附件 + 1.5 MB 文本 = 约 2 MB 请求体，仍 200。

### 5.6 判定（PM 卡面三种组合对照）

| 结果组合 | 判定 | 实际读数 |
|---|---|---|
| E2 接受 且 E1 接受 | **450KB 墙不存在或远高** → 之前撞的更可能是限流/其它约束 | ✅ **本轮命中这一档** |
| E2 接受 且 E1 拒绝 | 附件不计入预算、值得立项 | 未命中 |
| E2 拒绝 且 E1 拒绝 | 附件计入预算 | 未命中 |

**明确判定：本轮结论 = 「纯文本与带附件两条路径在 256KB～2MB 区间均未被服务端拒绝；卡面假设的 450KB 墙未复现」。**

**是否混入限流因素：否。** 依据：① 探活 200 且模型正常回「就绪」；② 全部 9 次请求 HTTP **均 200**、**无一条**出现「频繁/too many/rate limit/429/过长/超出/限制/拒绝」类文案；③ `realErrs` 数组在每一级都是**空**；④ 响应耗时随体量单调上升（1.2s→4.4s）而非被拒。

### 5.7 结论对「附件通道是否值得立项」的意义

- 卡片原假设是「附件走独立通道、不计入 450KB 预算 ⇒ 值得立项」。
- 本轮实测：**这条通道确实存在且可用**（`upload_file` 200 → `ref_file_ids` 带进 chat body → 服务端接受），但**它当前并不比纯文本路径更强**——纯文本一路加到 2 MB 也没被拒，所以「附件能绕过大小墙」这个立项理由**没有被证明**。
- 真正该问的是：**当初撞到的 450KB 限制是什么？** 本轮没能复现它（可能是限流冷却、可能是特定长度/特定内容、可能是当时账号状态）。建议下一步**先复现原始失败**，再决定是否立项，而不是基于「附件绕墙」假设投入。
