## 3. 判据 ②：续跑轮 head 稳定性

### 3.1 口径

- **prompt 头**：对 `body.prompt` 的 UTF-8 字节取前 N 字节做 SHA256（N = 256 / 1,024 / 4,096 / 8,192 / 16,384）。
- **body 头**：对整个上线 body 的 UTF-8 字节取前 N 字节做 SHA256（对照用）。
- **首差字节**：相邻两轮 prompt 的 UTF-8 字节序列第一个不同的下标。

### 3.2 结果

| 运行 | 轮数 | prompt 前 256 B | 前 1,024 B | 前 4,096 B | 前 8,192 B | 前 16,384 B | **body 前 256 B** | 相邻轮首差字节 |
|---|---|---|---|---|---|---|---|---|
| A（预算态） | 5 | 全等 | 全等 | **全等** | 不全等 | 不全等 | **每轮都变** | 7,071 / 8,938 / 13,200 / 7,072 |
| B（+技能段） | 4 | 全等 | 全等 | **全等** | 不全等 | 不全等 | **每轮都变** | 7,652 / 21,139 / 7,653 |
| C（+记忆关键词） | 3 | 全等 | 全等 | **全等** | 不全等 | 不全等 | **每轮都变** | 7,652 / 12,329 |
| D（回滚态） | 2 | 全等 | 全等 | **全等** | **全等** | 不全等 | **每轮都变** | 18,060 |

### 3.3 判读

1. **head 是稳定的**：续跑轮之间，**prompt 前 4,096 B 逐轮逐字节相同**（14 轮无一例外）。首差字节恰好落在「能力前缀」末尾（= 固定能力段 + MCP 块 + 名字索引 + 调用方式行 + 技能段 + 分隔符），即**前缀之后才是每轮变化的内容**（用户文本 / 工具结果 / 续跑 prompt）。
2. **稳定前缀长度**：预算态 **7,071 B**（A）/ **7,652 B**（B、C，含技能段）/ 回滚态 **18,060 B**。⇒ **瘦身把稳定前缀从 18,060 B 砍到 7,071 B（-61%）**，这正是「只发增量」能省下的部分。
3. **必须按 prompt 口径测 head，不能按 body 口径**：整包 body 的前 256 B **每一轮都不同**（JSON 前缀字段 `chat_session_id` / `parent_message_id` 等随轮变化）。若拿 body 头做增量判断，会得出「head 每轮都变 → 增量收益为零」的错误结论。
4. **对 PM 的外部实测的对应**：外部说「改 head 会让服务端父链断一次」。本次实测 head **并不改**（续跑轮逐字节一致），所以现状不触发断链；但任何「只发增量」方案只要**不再重发这 7,071 B 前缀**，head 就会变 → 会触发那次断链。**结论：增量方案必须连同前缀一起保持字节一致（或让服务端缓存前缀），否则要付一次断链代价。**

## 7. 缺陷与观察

### F1（高）记忆段真机实测 0 B —— `memory.select` 预取稳定超预算

- **现象**：14 个上线 body（4 次运行、含明确点名技能、含明确命中既有记忆的任务）**全部没有 `## 已有记忆` 块**，记忆段恒 0 B。
- **证据**：宿主审计 `memory.select` 三次页面通道调用 `durationMs` = **149 / 166 / 170 ms**，均 > 页端预算 120 ms（`src/inject/main-world-interceptor.ts:1088`）→ 本轮取不到结果；**迟到结果也没有进入后续轮**（续跑轮同样 0 B），即「回落上一帧」也没兜住。
- **对照**：同一进程内直连 `POST /v1/tools/execute`（同一文本）耗时 **14 ms**（短文本）/ 375 ms（1,916 字长文本）→ 慢在**页面通道**（WS 往返 + 工具派发），不在 `memory.select` 本身。
- **对照历史**：2026-10-31 C1 报告实测 554 ms / 1,203 ms —— **同一现象在瘦身构建上复现，且今天是「必现」而非偶发**。
- **影响**：`memory.select` 在真机当前状态下**功能不生效**（预取结果既不进本轮，也不进下一轮）。建议实现者定位页面通道的 150 ms 固定开销；或把「迟到结果」也写进 `currentMemories`（回落上一帧的语义应覆盖这种情况）。

### F2（中）连发多轮时，上线 body 的用户文本是**累积串**（取证方法副作用 + 产品行为）

- **现象**：三次 `/v1/agent/send` 的首轮 body 里，用户文本是 A+B+C 三条任务 + 前两次 `[assistant]` 回答的**拼接**（运行 C 首轮用户文本 1,916 字符），页面输入框没被清空。
- **影响**：① 注入用的 taskText（技能点名、记忆选型）也是累积串 → 运行 C 的技能段命中 `visual-report` 并非本轮任务点名；② 每轮都在重发历史文本（与「只发增量」议题直接相关）；③ 我前 3 次运行的目录段差异（5/57 vs 24/38 类）部分由此产生。
- **定性**：这是 `chat-insert` 不清空输入框的**真实产品行为**，不是实现 bug；但**是我的取证方法造成的污染**，必须在报告里写明（§8 P31）。

### F3（中）「head 稳定」必须按 prompt 口径测

- **现象**：整包 body 的前 256 B 每轮都变（JSON 头部字段随轮变化），而 prompt 的前 4,096 B 逐轮完全相同。
- **影响**：任何按 body 头做增量/缓存判断的验收或优化都会得到「head 每轮都变 → 增量收益为零」的错误结论（这正是 PM 外部实测担心的那种误判）。

### F4（低）sidecar 的 `injected len` 是 JS **字符**数，比真实 UTF-8 字节少 23%–41%

- **证据**：sidecar 日志 `xhr chat body injected len=5103 / 7020 / 12599 / 14542 / 14529 / 13395 / 15329`，与本次逐轮 `bodyChars` **逐条吻合**；而真实上线字节为 8,060 / 10,779 / 16,578 / 18,889 / 18,818 / 22,861 / 25,637（字符/字节 = 63.3% / 65.1% / 76.0% / 77.0% / 77.2% / 58.6% / 59.8%）。
- **结论**：任何基于 `injected len` 的体积结论都要按字节重算（PM 今天的教训②，已量化）。

### F5（低）`mcp.callHint` 段在「无名字索引」时会被并入 `mcp.full`

- **现象**：回滚态无 `### 其他工具（仅名称）` 段，脚本的 `mcp.full` 边界因此把「调用方式」行（97 B）算了进去 → MCP 全量块读数 12,780 B，扣除后为 12,683 B。
- **影响**：不影响分辨结论（§5），但跨报告比对时需注明（自纠记录，见 §8 P32）。
