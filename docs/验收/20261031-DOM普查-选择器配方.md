## 1. 结论先说

1. **`ds-sc-*` 不是页面的类名**（Studio 注入层自建，见前一份报告 §3.1.1）。**页面自己的**会话 DOM 全部是**混淆类名** + **虚拟列表**。
2. **页面 DOM 里没有任何可用的 user/assistant 角色类名**（普查结果：角色类名集合为**空**）→ `chat-read.ts:26-35` 的 `inferRole()` 启发式在现网**永远返回 'unknown'**，不能作为拆分依据。
3. **虚拟列表只挂载可见项**：本会话实际 6 条消息，DOM 里只有 **3 个** item 挂载 → 视口外消息**读不到**（J7）。
4. 每条消息的文本节点**约 10k 字符**——因为 Studio 的记忆注入块被写进了**用户消息本体**（请求体被改写），用户气泡里含「已有记忆」全文。**任何「取最后一条消息」的读法都会取到用户气泡 + 注入块，而不是 assistant 答案。**

## 3. 给 F1 卡的实现建议（按可靠性排序）

1. **首选：以 SSE `final-answer` 通道为准，DOM 只做交叉校验。**
   宿主本来就能拿到本轮答案：页端拦截器解析流 → `final-answer` 事件 → 注入层镜像（`studio-chat-ui.ts:1025-1035`）+ 宿主 `state.lastAutoReply`。
   判停时用「本轮 SSE 内容」与「DOM 读到的文本」**比对一致**才算数——这同时把 PM 那条「answer 要对得上本轮」从验收判据落进实现层。
2. **若必须读 DOM**：
   - 根：`.ds-virtual-list:not(.ds-virtual-list--printable) .ds-virtual-list-visible-items > *`（排除打印副本、排除侧边栏）；
   - 正文：item 的 `._72b6158`（kids=0，纯文本节点，`textContent` 可直接取）；
   - **角色**：现网**没有角色类名**，需用 item 的子节点差异（`._942b85d` 只出现在部分 item）或结构特征判定；**不要用 `inferRole()` 的类名/文本启发式**；
   - **用户气泡里含 Studio 注入的记忆全文**（10k 级），取「最后一条」会取到用户气泡——必须先定位 assistant 侧内容。
3. **虚拟列表（视口外消息）**：`.ds-virtual-list-visible-items` 只含可见项（本会话 6 条只挂 3 条）→ 需要**滚动加载**或**取数据层**；两者都不可行时，结论是「DOM 读不全，必须走 SSE 通道」。
4. **选择器不要硬编码混淆类名**（`_72b6158` / `_81e7b5e` 会随 DeepSeek 发版失效）：用 `.ds-virtual-list*` 这种**语义类名**做锚点，混淆类名只作为兜底/校验。
5. **`chat-read` 返回必须带 session/消息标识**（PM 硬要求）：现返回体只有 `{count, messages:[{role,text}]}`，宿主无法对账轮次。
