### 3.1.1 订正：`ds-sc-*` **不是** DeepSeek 的 DOM（这条差点让修复走偏）

我第一版把上面 DOM 里看到的 `.ds-sc-markdown` / `.ds-sc-msg-assistant ds-sc-msg-main-bot` / `.ds-sc-message-list` 认定为「DeepSeek 新的消息类名」——**这是错的**：

- `src/ui/studio-chat-ui.ts:357/687/804/1027/1029` 显示，这些类名是 **Studio 自己的注入层在创建**（`messageList.className = 'ds-sc-message-list'`、`msg.className = 'ds-sc-msg-assistant ds-sc-msg-${senderType}'`、`markdown.className = 'ds-sc-markdown'`），内容来自**拦截器从 SSE 流解析出的 `final-answer` 事件**（`:1025-1035`），**不是**从页面 DOM 读出来的；
- 全 `src` 里 `ds-sc-markdown` 只有这两处**创建**，没有任何一处把它当**页面选择器**去读（`vis-card.ts:5` 的注释只是提到它属于 DeepSeek React 管理的 DOM）；
- 所以我真机 DOM 里看到的「`F1-V2-OK` 落在 `.ds-sc-markdown` 里」——那是 **Studio 自己的对话镜像**，**不是 DeepSeek 的消息节点**。

**DeepSeek 真实 DOM 现在的形态**（证据来自 `src` 里 Studio 已真机验证过的选择器链，`src/ui/studio-ui-install.ts:287`，注释「完整路径（用户提供）」）：

```
#root > div > div.c3ecdb44 > div._7780f2e > div > div.ds-virtual-list > div._871cbca > div.aaff8b8f > div > div > div.ec4f5d61 > div._58b31c9
```

即 DeepSeek 用的是**混淆/哈希类名**（`c3ecdb44`、`_7780f2e`、`_871cbca`、`aaff8b8f`、`ec4f5d61`、`_58b31c9`）+ `ds-virtual-list`；真机 DOM 里也确实出现了 `ds-virtual-list-items` / `ds-virtual-list-visible-items`（`src` 里没有这两个名字 → 属 DeepSeek 侧）。

**给 F1 卡的结论**：
- ⛔ **不要**照「`ds-sc-*` 已有 44 处、直接用」办——那些是 **Studio 自己的命名空间**（样式 + 注入层渲染），拿它当页面选择器，读到的是 Studio 镜像而非页面消息，且与注入层强耦合（overlay 一关就没了）。
- ✅ 方向是**结构化定位**（`#root` → 虚拟列表容器 → 消息项 → 文本节点）+ **处理虚拟列表只挂载可见项**；硬编码混淆类名会随 DeepSeek 发版再次失效，必须有兜底。
- ✅ 另一条现成可靠通道：宿主本来就通过**拦截器 SSE → `final-answer` → `state.lastAutoReply`** 拿到模型答案（`studio-chat-ui.ts:1025` 的数据源）。判停可用该通道做主依据或交叉校验，而不是只靠 DOM 轮询。

> 已备好只读普查探针 `docs/验收/_probe/deepseek-dom-census.mjs`：枚举 DeepSeek 侧（排除 `ds-studio-/studio-/ds-sc-/ds-flow-` 命名空间）的类名频次、虚拟列表结构、答案正文节点的祖先链，产出选择器配方。需一次窗口（Core 修完 F1 后复验，或 PM 另排）。

**但①暴露了一个更深的结构性缺口**：既然 `chat-read` 的返回没有任何轮次/会话标识，宿主**在协议层就无法判断自己读到的是哪一轮的文本**。这正是「读不到新回复 → 把上一轮答案当本轮答案返回（200）」能发生的根因；也说明 PM 加的判据「状态码 + 内容对得上本轮」**今天在协议层无法被保证**，必须由 F1 卡同时给 `chat-read` 的返回补上会话/消息标识（或等价的时间戳/轮次标记），否则「对得上」只能靠内容猜。

### 3.5 新发现（高危）：对外 API 会返回**上一轮的旧答案**

第二轮复现（v2）返回 **HTTP 200 / 6734ms**，但 `answer` 的内容是**上一轮七轮工具链任务的总结**（含 `CHAIN-DONE`），而页面 DOM 里最新的一条回答是我这一轮的 `F1-V2-OK`：

```
apiBody: {"ok":true,"answer":"1) 根目录前 5 项：… 6) 作用：它是注入到页面 main world 的拦截控制器… CHAIN-DONE"}
```

→ **对外 API 返回 200 ≠ 这一轮的问题被回答了**。答案来自页端 auto-continue 通道（宿主 `state.lastAutoReply`）的**陈旧内容**。验收判据必须加一条：**200 的 `answer` 要与本轮请求对得上**，不能只看状态码。

## 7. 我自己的失误与订正（如实记账）

1. **把强杀后的孤儿态当成 F1 线索**。宿主已被杀、8760 由孤儿 sidecar 占着时测到 `no-page-for-dom-capability` + `ws upgrade rejected`，一度当作根因方向；PM 用「宿主已死、sidecar 还在」纠正后撤回，只保留为 P0 前置体检项。

4. **探针假设了不存在的 `GET /v1/trace` 端点**，实际 trace 是落盘 JSONL（`page-runtime.ts:336`）。已改。

9. **第一版启动器 `Now-Ms` 用 Int32 存 epoch 毫秒溢出**（宿主启动即退的表象之一），已改 Int64。

11. **把 Studio 注入层的类名误当成 DeepSeek 的 DOM**（本轮最严重的一次误判）。我在真机 DOM 里看到 `.ds-sc-markdown` 里装着答案文本，就推断「DeepSeek 换了 `ds-sc-*` 类名体系」，并据此给 PM 写了「`ds-sc-*` 直接用」的方向。核 `src` 后发现 `ds-sc-*` 是 **Studio 自己的注入层在创建**（`studio-chat-ui.ts:357/687/804/1027/1029`），内容来自 SSE 拦截的 `final-answer` 事件——**不是页面消息节点**。DeepSeek 真实侧是混淆类名 + `ds-virtual-list`（`studio-ui-install.ts:287` 有真机验证过的完整链）。**差点让 F1 修复照着错的类名写**；已订正报告 §3.1.1 / §6，并把普查探针备好。教训：看到页面里某个类名，先确认**谁创建的它**（Studio 自建 vs 页面自带），再下结论。
