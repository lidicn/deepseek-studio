## 2. ③ 的 404 根因（P1-2 缺陷单）

**证据链（双通道交叉验证）**：

- live 端点（`releases/latest/download/latest.json`，当前 = v0.14.4 的）：`url = https://github.com/lidicn/deepseek-studio/releases/download/v0.14.4/DeepSeek++ Studio_0.14.4_x64-setup.exe`（**空格名**）。
- 实测：该 url 的 wire 形态（reqwest 会 %20 编码空格）→ **HTTP 404**；真实资产名（**点号** `DeepSeek++.Studio_0.14.4_x64-setup.exe`）→ **302**（我 0.14.4 参照包就是走点号 URL 下成的，27,746,117 B 与 API 字节一致）。
- **v0.14.3 与 v0.14.4 两个 Release 各自的 `latest.json` 资产 url 全是空格名**（各 release 资产原文存 `logs/verify-v0142/release-latest-v0.14.3.json` / `release-latest-v0.14.4.json`）→ 两个发布版的 updater 下载全 404。
- **v0.14.0 的 GitHub 资产名也是点号**（API 实测）→ **latest.json 空格 url 自 0.14.0 起就是坏的**；latent 原因：0.14.0 无调用点（第一缺陷）、0.14.1/0.14.2 轮被指针卡死与 ACL 挡住，从未走到下载步。**本卡是第一次真走到下载，才把这条炸出来。**

**机制（假设，需 Core/Gate 实证）**：`productName = "DeepSeek++ Studio"`（各 tag 均带空格，`git show v0.14.x:src-tauri/tauri.conf.json` 核过）→ Tauri 本地 NSIS 产物名带空格 → `release.yml` compose 步 `$nsis.Name`（本地名，空格）写入 latest.json → 但 GitHub 上传的资产名实际是点号（上传链路/服务端把空格规范化为点，或 Tauri 产物命名规则本身带点而 compose 取到的不是最终名）→ **url 与资产名错位 = 死链**。

**修法（Core/Gate）**：
1. `release.yml` compose：url 必须用**上传后 GitHub 实际注册的资产名**——最稳做法：draft 建好后从 API 读回资产名再回填 url，**重新生成 latest.json 并重新签名**（.sig 是 latest.json 内容的 Tauri 签名，url 一变旧签名作废，**手动 web 换资产是修不掉的**，只能走管线重签）；或在 compose 侧显式 ` -replace ' ','.'` 并实测确认 GitHub 规范化规则。
2. 发版流加**前置闸**：compose 后对 url 发 HEAD（期望 302/200）+ `tauri signer verify` latest.json → 不过直接 fail，不让坏资产上 Release。
3. 重发：v0.14.4 的 latest.json 资产已坏且是 Latest 指向 → 重发 v0.14.5（修好的 compose + 最新代码）并把 Latest 指过去（或删 v0.14.4 重发，PM 裁）。
4. 顺带（可选，产品决定）：`productName` 改成无空格（如 `DeepSeek++Studio`），本地/远端名一次对齐，杜绝此类错位。
