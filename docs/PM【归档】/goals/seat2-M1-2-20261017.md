## 5. 任务分解

### A-1 · 接口一致性核对（先做这个，可能要停手）

逐方法核对 `WebEngine` 是否精确实现 `ModelEngine`。

- 若**已经完全匹配** → 在交付卡贴出核对表，进 A-2。
- 若**有缺失或签名不符** → 补齐（这是你的文件，可以改）。
- 若发现**必须改 model-engine.ts 才能匹配** → **立刻停手交卡**（它是冻结区，这说明 M1-1 边界核对有误）。

### A-2 · 把 onToolCall 接到 harness-metrics

在 `web-engine.ts` 内：

1. 在 web-engine.ts 顶部：import { createHarnessMetrics } from 相对路径 ../../shared/harness-metrics（路径自行核对，src/host/engine 到 src/shared 需上溯两级）
2. `WebEngineOptions` 加可选 `metrics?: HarnessMetrics`（**允许外部注入**，方便测试）
3. 若未注入，内部创建一个（懒创建即可）
4. 在 `recordToolCall()` 里同时把事件喂给 metrics
5. 暴露 `getMetrics(): HarnessMetrics` 供外部读快照

**关键约束**：
- **不要改 harness-metrics.ts**。它现在的事件模型如果喂不进去，就在交付卡写清楚「需要它暴露什么」，PM 下一轮处理。
- **不传 metrics 时行为必须与现在完全一致**（向后兼容，`agent-loop.test.ts` 必须仍绿）。

### A-3 · 测试（≥ 8 用例）

`tests/desktop/web-engine-transport.test.ts` 必须覆盖：

1. `WebEngine` 类型赋值给 `ModelEngine` 变量能编译通过（接口一致性，编译期断言）
2. 不传 metrics → `recordToolCall` 不崩，老行为不变
3. 传 metrics → `recordToolCall` 后 `metrics.snapshot()` 的数字变了（贴出前后值）
4. 连续两轮 send → 每轮缓冲独立（轮间不串）
5. `onToolCall` 回调仍被调用（M2-2 行为未退化）
6. `toolCallRecords` 仍正确填充（M2-2 行为未退化）
7. 注入 metrics 与内部自建 metrics 两种路径都能取到快照
8. `dispose()` 后不泄漏（若接口有 dispose）
