# Goal 模式 · 使用说明

> 建：2026-10-17 | 维护：PM
> 一份 goal 卡 = 一个席位一个里程碑 = 一次 goal 模式会话。

---

## 一、你的工作方式（席位视角）

1. PM 给你一个 goal 卡路径 → 你读它
2. 你开 goal 模式，按卡里的「任务」逐条做完
3. 做完（或触发停手条件）→ 落盘一份**交付卡**到 `docs/PM/handoff/`
4. 你只回一句话 + 交付卡路径给 PM
5. PM 读你的卡、跑验收命令、更新 STATE

**你不需要向 PM 解释过程。** 过程写在卡里，PM 只核数字。

---

## 二、交付卡命名（必须严格）

```
seat<N>-<里程碑编号>-<yyyymmdd-HHmm>.md
例：seat1-M2-1-20261017-1530.md
```

模板：`docs/PM/handoff/_TEMPLATE.md`

---

## 三、五条硬规矩

| # | 规矩 | 为什么 |
|---|---|---|
| G-1 | **只写你的独占文件域**，禁止区一个字节都不碰 | 三席并行，碰了就是互相污染 |
| G-2 | 交付卡第 2 节必须**粘贴原始输出**，不许写「已通过」「全绿」 | 描述无法验证，数字可以 |
| G-3 | **不做卡外的活**。看到别的问题，写进第 4 节「遗留与风险」，不要顺手改 | 顺手改 = 越界 = 别人白干 |
| G-4 | 触发停手条件 → **立刻停手并交付**，不要硬撑 | 停手不是失败，是止损 |
| G-5 | 不切分支、不 commit、不 push | 提交权归 PM |

---

## 四、停手条件（任一触发即交付）

1. 验收命令跑不过，且 30 分钟内定位不到原因
2. 发现必须改禁止区才能完成
3. 发现卡里的技术前提是错的（例：卡说某文件有 X，实际没有）
4. 任务超出卡里估时 2 倍

---

## 五、PM 收到交付卡后的动作（供你理解全流程）

1. 从第 2 节核原始输出（不看第 1 节的自述）
2. 跑一遍同样的命令复现
3. 核第 3 节边界自证
4. 全过 → 更新 STATE.md 与 DECISIONS.md → 发下一张卡
5. 不过 → 卡退回，写清哪条数字对不上
