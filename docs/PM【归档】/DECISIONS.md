## D-011 · 2026-10-17 · D2 裁决：不接 pi-agent-core，回退自建薄 loop

**决策**：M1-3 的结论是 **不接入 pi-agent-core**，只借鉴其事件流形状（start / text_delta / done）重构 EngineSendResult。

**依据（席2 探针实测，PM 已核报告）**：

| 项 | 实测 |
|---|---|
| 接入成本估算 | **5–6 天**（StreamFn 桥接 1.5d + 消息转换 1d + 工具执行权桥接 2.5–3d + 事件适配 0.5d） |
| 是否破坏 agent-loop 契约 | 否，但会**整体替换**它（197 行 → 薄适配层），不是小改 |
| pi 工具模型 | AgentTool.execute() **由 loop 自己执行** |
| 我们的工具执行权 | 在**页端拦截器 + 同意闸门 + policy**，不在 loop |

**判定过程**：D2 原定阈值是「≤3d 且不破坏契约 → 继续接；>5d 或契约冲突 → 回退」。实测 **5–6d > 5d**，且「整体替换」等价于契约重写 → 两个条件都命中回退分支。

**核心理由**：pi 的 inline execute 与我们的页端授权链根本冲突。要么把 host 能力包成 AgentTool（绕过已验证的 policy/consent 链路），要么 stub 掉 pi 的工具执行（等于和 pi 的 loop 设计对着干）。两条路都是拿已上生产的安全链路去换一个通用 loop，**风险 > 收益**。

**落点**：docs/架构文档/M1-3-pi接入探针报告-20261017.md §5。探针代码 src/host/kernel/pi-transport-probe.ts（142 行）保留作为技术记录，**不进生产路径**。package.json 里 pi-agent-core 0.83.0 保留还是移除，待 M2-3 完成后一次性决定（现在移除会让探针测试红）。

**状态**：有效，已裁决，不再取数。

## D-015 · 2026-10-17 · 路线图模式替代 goal 卡片

**决策**：废弃 goal 卡片模式（每轮发卡 → 交付 → 等 PM 审 → 下一轮发卡）。改为**每席一份常驻路线图**（`docs/PM/roadmaps/seat{1,2,3}.md`），开发者从路线图「当前阶段」直接开工，做完落盘交付文件，PM 审核后更新路线图推下一阶段。

**理由**（用户 11:27 原话：没发挥人多优势，三个开发者交付内容你再审核，效率极低）：
- 卡片模式下三席在交付后空转等 PM 审完、发新卡，串行等待 > 并行产出
- 路线图是活文档：PM 改路线图 = 派新活，不需要等三席举手
- 开发者读完路线图就知道下一步，不需要等 PM 发卡
- 每席路线图的文件域是预定义的，不会互相踩

**模式变化**：
| 旧模式 | 新模式 |
|---|---|
| goal 卡（每轮新建） | 路线图（常驻，PM 持续更新） |
| 做完等 PM 发卡 | 做完落盘交付，PM 更新路线图即推下一阶段 |
| PM 每轮写卡 | PM 只审核 + 更新路线图「当前阶段」 |
| handoff/ 存交付卡 | handoff/ 仍存交付文件（阶段交付） |

**文件域分配（本轮起）**：
- 席1：agent-loop.ts、kernel/**、model-engine.ts（只读）
- 席2：web-engine.ts、harness-metrics.ts、main-world-interceptor.ts
- 席3：tools/metrics/**、continuation-prompt.ts、宿主装配层、package.json（仅 script）
