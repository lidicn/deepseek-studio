## 0. 我的定位与分工边界

Bot 平台 v2 是双人协作。我（Claude）负责的是**引擎 + 宿主 + 运行时接线 + UI 树**——把 CB 写好的纯算法/数据层「接到」真实的窗口、WebEngine、SQLite、面板上。CB 写「存什么 / 怎么路由 / 怎么接力」，我写「谁去执行 / 在哪个窗口执行 / 结果怎么回面板」。

| 层 | 谁负责 | 性质 |
|---|---|---|
| 引擎（AgentLoop / BotRegistry / WebEngine / 多窗口寻址） | **Claude** | 有状态、碰运行时 |
| 宿主接线（desktop-host / page-runtime / protocol / Tauri main.rs） | **Claude** | 有副作用、碰窗口 |
| 人设注入 + 工具白名单（SlotRuntime） | **Claude** | 有状态、碰 BotInstance |
| 聊天室 UI + 接线 | **Claude**（UI+接线）/ CB（算法） | 我做 UI 和把算法接上 |
| 数据层（记忆 / Persona / Slot / ChatStore / 上下文引擎） | CB | 纯数据 |
| 算法层（路由 / 接力 / 轮次编排 / 人设指令模板） | CB | 纯函数（`instructions.ts` 已由我交付） |
| 稳定性 / 成本 / API / 多平台 | **Claude** | 运行时硬化 |

**铁律**：我碰运行时（窗口、进程、Tauri、WS），CB 碰纯数据/算法。衔接面只 `types.ts`。

### v0.25 — SlotRuntime + 人设白名单 + Scheduler 接入 ✅

| 项 | 内容 |
|---|---|
| 工期 | 3-4 天 → 同日 |
| 关键文件 | `src/host/bot/slot-runtime.ts`（新建）、`registry.ts`（state 加 executor）、`desktop-host.ts`（hub executor 接入） |
| 验证 | `bot-slot-runtime`(8) + `bot-slot-runtime-integration`(13) = 21/21；Phase 1 全量回归 123/123；`tsc` 0 |

**核心设计（三个刻意的「不对称」）**：

1. **两条工具路径不对称**。页面驱动工具（`chat-read`/`chat-insert`/`chat-send`）是 WebEngine↔页面通信唯一通道，结构上永不过白名单（过滤掉引擎就死）；模型发起工具（`shell.exec`/`file.read` 等）走 `hub.executor` → 人设白名单 → 仍回 `invokeTool` 走完整授权链。白名单只「拒绝」从不「免授权通过」——命中后仍委托 `invokeTool`。拒绝码固定 `tool-not-allowed-by-persona`，与 `consent-denied`/`unknown-tool` 区分，便于审计。

2. **WebEngine 没有系统提示词概念**。它把文本贴进 chat.deepseek.com 输入框。所以 `persona.prompt` 作为消息文本的一部分，紧跟 `AGENT_SENTINEL`（`【Studio Agent】`，语义「agent 驱动而非用户手输」）之后。人设块与任务块用 `\n---\n` 分隔，避免模型混淆「你是谁」与「现在做什么」。

3. **`loadPersona` 失败抛错 / `unloadPersona` 对不存在 bot 是真 no-op**——不对称是刻意的：前者静默跳过 = bot 无白名单执行（安全相关，必须抛）；后者清理不存在的 bot 无意义。

`run(handle)`：slotId→botId 对账 + persona.name 对账 + runId 与槽位对账 → 组合 `[personaBlock, taskText].filter(Boolean).join('\n\n---\n\n')` → 截断到 `MAX_TASK_TEXT_CHARS=4000` → 调 `instance.loop.send(`${AGENT_SENTINEL}${limited}`)`。

**关键设计（见 v0.27 接线层实现 `chat-room-runtime.ts`）**：

1. **generateReply 回调解 void 返回值**：`AgentLoop.send(text): Promise<void>` 返回 void，回复经 `emit({type:'assistant', text})` 发出。接线层用 agentSender 模式（`desktop-host.ts:613-632` 蓝本）的 per-bot 泛化——临时 listener 按 `event.botId === botId && event.type === 'assistant'` 过滤捕获 → `bot.loop.send(AGENT_SENTINEL + message)` → 返回捕获的原始文本。maxDepth:2 并行波时 botId 过滤防串味。

2. **契约张力：存储净内容 vs 路由需 @mentions**。`ChatMessage.content` 契约要求「已剥离 @路由标记的净内容」（供上下文注入 + UI 显示），但 `MentionRouter.route` 调 `resolveMentions(message.content)` 要 @mentions 在。解法：**两种表示分离**——`messageStore.append` 存净内容（契约合规），路由触发器 `trigger` 携带原始文本（含 @mentions，供 router 解析）。这是接线层职责，CB 的算法层不用改。

3. **真摘要器 agentSender 模式**：`createModelSummarizer` 拼摘要 prompt → `bot.loop.send(AGENT_SENTINEL + prompt)` → listener 按 botId 过滤捕获 → 返回摘要文本。替换 v0.26 的桩实现。摘要 bot 不可用时 fail-soft 返回占位串（不炸主流程）。

4. **向后兼容**：无 `chatRooms` 配置时 `chatRoomRuntime = null`，agent-channel send handler 走原 `bot.sendMessage` 直发路径，现有 583 测试零回归。`roomId` 参数可选——面板不带 roomId 时行为与 v0.26 完全一致。

**接线面（我的活，CB 不碰）**：
- `desktop-host` 收用户消息 → `MentionParser.resolveMentions` → `MentionRouter.route` → 逐个 `ContextEngine.buildContext(personaInjector: agentInstructionBuilder.build)` → 调对应 bot 的 WebEngine

## 9. 我的执行原则

1. **碰运行时的是我，碰纯数据/算法的是 CB**——衔接面只 `types.ts`。
2. **向后兼容是硬约束**：每个 botId 参数都可选，缺省 = `main`，现有单 Bot 路径零回归（v0.23/v0.24 已验证此模式）。
3. **WebEngine 没有系统提示词**：人设 prompt 是消息文本的一部分，紧跟 `AGENT_SENTINEL`。这是 v0.25 定的，v0.27 接线时沿用。
4. **白名单只拒绝不免授权通过**：命中白名单仍走 `invokeTool` 完整授权链（v0.25 定的，v0.37 安全审计沿用）。
5. **v0.28 是硬决策门**：PoC 不达标停止整个计划，不沉没成本。算法层（v0.27a）是互动质量成败关键。
6. **分支 `feat/bot-core`**：我的引擎改造一条线，CB 的 `feat/bot-data` 不混提交，各自 PR 进 master。未 commit 工作等用户确认再动 git。
