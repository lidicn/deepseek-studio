## 二、本轮改了什么

`release.yml`（Gate）：
1. **step 17 / step 18 的草稿查找改为 by-id 优先**：`env: RELEASE_ID: ${{ steps.create_release.outputs.id }}` 走数据通道（**runBody 零插值锁不破**，见 compose L61），先 `GET /releases/$draftId`，取不到才退回 `/releases?per_page=100` 过滤 `draft`，首查 3 次带退避；**列表端点按 compose L92/L117 的既有锁保留为回退，不删**。
2. **现场三件进注解**：`list diagnostic: returned=$listCount drafts=$listDraftCount first=$listFirst`（step 17，L500/L506）。
3. **无条件探针降级**：step 16 的 `::error::[patch-body] draftId=…` 改成 `::notice::`（L376）——它在成功路径上也会留一条红色错误行，误导 triage。
4. **注释里的未证实因果改为候选口径**（L373）。

`release-compose.test.ts`（Gate）：新增 `gateByIdFirst()` 顺序锁＋两枚 it（正向锁 by-id 优先、负控「摘掉 by-id 必红」）。**旧正向锁一条未删**（`per_page=100` 三处、`preflight equality check`、PATCH 等值 throw 全在）。

`tests/desktop/_host-port-guard.ts` 及 9 枚同族测试（Core，上一批已入库）：端口交 OS 分配＋校验 undici 禁用表＋`MAX_LISTEN_ATTEMPTS=16`＋自锁断言。**实证已获得：CI(master) run `42950470758` `completed/success`（11:15:23）＝守卫件在全新 `windows-latest` runner 首跑绿。**

## 四、打 tag 前后的动作

1. 三向一致自查：`git tag` 待打的名字 ＝ `package.json.version` ＝ `tauri.conf.json.version`，不一致 workflow 第一关就挡下。
2. 全量 `npm run gate` 由私聊 PM 统一跑；绿后逐枚 `git add`（禁 `-A`/`.`），墨鉴流水账与 R5/R6 恒不 add。
3. annotated tag → push master → push tag。
4. CI 一次性取数（匿名 API 额度 60/小时，用完等复位；能拿到只读令牌就别等）：run 结论、**step 级读数**、`releases` 是否残留草稿。
5. 草稿五件核对：资产名与 `latest.json` 引用一致／正文与 `docs/release-notes-v0.14.17.md` 逐字等值／`draft=true`／`tag=v0.14.17`／三向版本一致。**资产枚数以本次 run 的 Release assets API 实测为准，不许沿用 v0.14.12 的 5 枚当预期。**
6. **叫出资人点 Publish，并必须勾「Set as the latest release」**——用 API 建的草稿发布时默认不带 Latest，`releases/latest` 指针不推进（已踩两次）。
