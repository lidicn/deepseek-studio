## 三、开发者发言的误判与遗漏

### 3.1 误判（4 处）

**误判一：说"无软失效"，实际是"软失效已实现但悬空"。**
`invalidate` / `restore` / `listInvalidated` 三件套齐全（`memory-store.ts:458-485`、`:519-523`），`MemoryStoreV2` 契约里也写死了（`bot/types.ts:95-96`），测试覆盖了幂等、`list` 不返回但数据保留、失效不参与 search、可 restore。真正缺的是"没人调"。这个区别决定方向不同：不需要"设计并实现软失效"，只需要"把已有的接上并调整语义"——工作量差一个量级。

**误判二：说 `chain-anchor` 因架构不同不可移植。**
studio 自己就在用 `parent_message_id`（`:1381`、`:234`）。不可搬的真实理由是重复建设，不是协议不兼容。这条误判的代价是：如果将来 studio 真的需要"跨重启保留会话链锚点"（现在 `loopState` 是内存态），dpp 那份 136 行的实现是可以直接参考的，不该因为"架构不同"被判死。

**误判三：说"无自动抽取"。**
代码层没错，但漏掉了 `:340-346` 那段「你必须调用 memory_save 工具」的硬规则。这在效果上是一种抽取机制——只是抽取决策交给了模型自由判断，且没有去重、没有来源标注、没有置信度、没有候选池。对风险判断来说这是反向的：**不是"没有抽取所以安全"，而是"有抽取但没有护栏"**。另外这也解释了 23 条里为什么 `source` 全 NULL：写入路径压根没有赋值。

**误判四（隐性）：把 `memory_delete` 算作"已治理"。**
`src/inject/execution-policy.ts:12-18` 确实把 `memory_delete` 列进 `HIGH_RISK_TOOLS`，`requiresConsent()` (`:43-45`) 会对它返回 true。但**这个文件零 importer**——全仓（src + tests，391 个文件）grep `execution-policy` 只命中它自己的文件头注释。它是一份从 dpp 移植过来、从未接线的死代码。真实生效的是 `tool-registry.ts:46` 的阈值闸门，而记忆工具登记的是 `risk: 'read'`。如果开发者读的是 `execution-policy.ts`，会得到一个完全相反的结论。这也正好是 dpp 那三份死代码的同类问题：死代码会骗人。

### 3.2 遗漏（6 处，按严重度）

**遗漏一：`memory_delete` 免同意 + 硬删 + 页端一键可达。**
- `tool-definitions.ts:210-218`：`id: 'memory.delete'`，描述写着「删除一条长期记忆（**自动放行**）」，`risk: 'read'`。
- `tool-registry.ts:21` 档位定义 `read < insert < send < privileged`；`:46` `CONSENT_MIN_RISK = 'insert'`；`:49-51` `needsConsent(def) = riskRank(def.risk) >= riskRank('insert')`。
- `desktop-host.ts:1255` `let requiresHumanConsent = needsConsent(def)` → `read` ⇒ **false**；`:1259` 策略闸门只对 `isFileTool(name) || isProcessTool(name)` 生效，记忆工具两者都不是 → 落到 `policy.ts:285` `{ decision: 'allow', reason: 'not-governed' }`。
- 删除动作本身：`desktop-host.ts:650-659` → `store.remove(id)` → `memory-store.ts:371-386` 直接 `DELETE FROM memories_fts` + `DELETE FROM memories`，无回收站、无版本。
- 页端入口：`studio-settings-panel.ts:355` `await callHostTool('memory.delete', { id: mem.id })`，记忆列表每行一个删除按钮。

对照同仓已经修过的同类问题，这条更刺眼：`tool-definitions.ts:219-221` 注释「QD-R2-04 修复：原 risk:'read' 会被自动放行，模型自调即可把文件根指向任意目录」→ `workspace.set` 提到了 `privileged`；`:229-231` 同样把 `policy.set` 提到 `privileged`；`mcp.test` 因 R4-P0-1 提到 `privileged`。**同一个仓库、同一套论证，`memory.delete` 被漏掉了。** R4 审计（`docs/Audit/20261017-R4-记忆自动化授权审计.md`，范围明确列了 `memory-store`）也只点了 `mcp.test`，没点记忆工具。

**遗漏二：`memory.delete` 不广播，被删的记忆继续注入。**
`desktop-host.ts:487-512` 的 `memory.save` 在成功后 `:506-509` 调 `hub?.broadcastMemories(...)`；而 `:650-659` 的 `memory.delete` **没有任何广播**。页端 `currentMemories`（`main-world-interceptor.ts:124`）只在连接建立时（`:1002-1003`）和收到推送时（`:1529`）更新。后果：删掉一条记忆后，本轮会话的每一次请求仍会把这条记忆拼进 system 提示词，直到重连或重启。设置面板因为 `:356` 自己做了本地过滤而看不出问题——这正是"UI 掩盖数据层缺陷"的典型。

**遗漏三：注入没有不可信边界（prompt injection 回路的缺口）。**
现状是一个完整闭环：记忆内容 → 拼进 **system 消息**（`:520-526`）→ 模型读取 → 模型被 `:340-346` 要求继续写记忆。全链路没有任何边界标记、去指令化或内容中和。

dpp 为此专门写了一整个模块 `core/memory/untrusted-content.ts`（46 行），文件头把事故写得很清楚：「a `reference` memory literally stores an external resource link. Observed failure: the model saw a URL inside memory and called `browser_navigate` on its own, so every memory-bearing turn opened an extra tab.」实现是 `:37-46`：`UNTRUSTED_MEMORY_OPEN` + 本地化 notice + 中和 marker + `UNTRUSTED_MEMORY_CLOSE`，并且 `:21-24` 会把内容里已有的 marker 替换成 `[[redacted-memory-content-marker]]`，防止记忆自己提前闭合包裹。这对 studio 完全可以照搬，代价约 50 行。

需要说清楚的是当下的实测风险等级：**这 23 条里，含 URL 的 0 条、含命令词（curl/powershell/bash/npm/git）的 0 条、含换行的 0 条、含 XML 标签的 0 条。**所以这是"回路已闭合、尚未被利用的潜在面"，不是"已经发生的注入"。我不把它列成 P0 的紧急修复，而是列成 P0 里的边界补齐——原因见 §4：它同时是 P1 所有选择逻辑的前置条件。

另外有一个细节值得记：模型面**无法**伪造治理字段。`tool-contract.ts:97-105` 的 `memory_save` adapt 只透传 `type` / `name` / `content` / `tags`，不含 `source` / `confidence` / `personaTags`。但宿主 RPC 层 `desktop-host.ts:491-501` 是**照单全收**（`:498-500` 从 `params` 直取三个字段）。所以现在的口径是"模型穿不进去，但任何拿到宿主 RPC 的调用方可以自报来源"。一旦 UI 或 API 暴露这三个参数，`source: 'user'` 就是一句自证。

**遗漏四：无 workspace 隔离，也无容量上限、无跨名去重、无冲突版本。**
- 隔离：`memory-store.ts:581-586` 全局单例 + `:61-65` 固定路径 `~/.config/deepseek-studio/memories.db`；`memories` 表实测列清单里**没有** `workspace` / `project` 列。同仓里 `workspaceHash` 只服务授权与影子（`consent-router.ts:34`、`consent-whitelist-store.ts:20`、`shadow-store.ts:24`），记忆层完全不用。dpp 那边有 `core/memory/scope.ts`（11 行）+ `filterMemoriesByProjectScope`，测试 `memory-scope.test.ts` 2 条。
- 容量：没有总条数上限。唯一的界是注入时的 `slice(0, 50)`，那是**显示**上限，不是**存储**上限。
- 去重：`contentHash`（`:81-84`）只在"(type, name) 命中"这条路径上参与比较（`:307-319`），同名不同内容会覆盖、同内容不同名会重复入库。
- 冲突：`save()` 是整行替换（`:322-329`），旧内容无留痕；而且**未传值会被重置**——`:326` 的 `pinned` 用的是 `params.pinned ?? false`，`tags` 用 `params.tags ?? []`（`:305`）。也就是说：模型用同名重存一条置顶记忆、且没带 `pinned`，它会静默变成非置顶；没带 `tags`，原有标签被清空。现在 `pinned` 全 0 且这套逻辑尚未被踩到，属潜在缺陷。

顺带一个和软失效强耦合的坑：`save()` 的重名匹配条件是 `WHERE type = ? AND lower(name) = lower(?) AND invalid_at IS NULL`（`:311`）。**失效后的记忆不参与重名匹配**，所以"归档一条 → 下次同名再存"会新建第二行，旧行仍留在库里。软失效一旦启用，重复行会稳定增长。这是 §4 P1 必须先修的前提。

**遗漏五：注入预算完全缺失，且当前量级被高估也被低估。**
- 缺预算：上限是条数 50（`:495`），不是 token。单条内容不截断（当前最长 515 字）。
- 实测现状：23 条拼成注入块 = **4587 字符 ≈ 1843 token**（按 dpp `core/token/estimator.ts:3-9` 的口径：CJK 0.6 / ASCII 0.3）。单条约 80 token。
- 这意味着两件事同时成立：**（a）现在不是成本问题**——1843 token 相对 DeepSeek 的上下文窗口不值一提；**（b）已经超过 dpp 的自定预算**（`core/constants.ts:3` `MEMORY_TOKEN_BUDGET = 1500`）。也就是说"照搬 dpp 的 1500 预算"会立刻开始裁掉今天的记忆。
- 外推（明确是外推）：按 1.1 条/天的有机写入速率，约 2 周后触到 50 条上限，届时注入块约 4000 token 且停止增长（因为 `slice` 会截）。这个上限是"静默丢弃最新之外的记忆"还是"丢弃最旧"，取决于 `list()` 的排序——`sortRows`（`:565-570`）是置顶优先 + `updated_at` 倒序，即**丢弃的是最久没更新的**，而不是最不相关的。对"用户身份"这类长期记忆（创建早、少更新）恰好最容易被丢。这一点开发者没提，但它比"缺相关性排序"更早咬人。

**遗漏六：注入路径零测试。**
`tests/` 下 164 个文件、1596 个 `it(`。存储层 `memory-store-v2.test.ts` 有 18 条，覆盖了保存校验、同名更新、空操作、硬删、排序、五种检索路径、FTS 语法注入、personaTag、invalidate 幂等、迁移、降级、stats——**存储层被测试覆盖得比它唯一的生产消费点还多**。对 `formatMemoriesBlock` / `已有记忆` / `__studioMemories` / `memories-update` / `currentMemories` 在 `tests/` 下 grep：**0 命中**。也就是说 18 条测试保护的是一段没人调用的 API，而真正每轮请求都在跑的注入逻辑一条测试都没有。这也是"遗漏二"（删除不广播）能活到今天的原因。

### 3.3 发言里成立且值得肯定的部分

不全是错。这三条判断我核完认为是准的，而且是这次评审里最有价值的部分：

1. **"存储层和写入链路是实的，检索层是悬空的，治理层是空的"** —— 精确。存储层 18 条测试 + 23 行真数据 + FTS 无漂移；检索层零调用；治理层 23/23 全 NULL 且无任何读取点。
2. **"studio 的存储选型优于 dpp，不需要向 dpp 对齐存储"** —— 成立。studio 直接落 SQLite + FTS5 trigram，dpp 走 IndexedDB + 自建倒排再换 FTS5，中间那段路 studio 不用走。
3. **"dpp 走的是预留接口换 FTS5，studio 直接落在 FTS5"** —— 与 dpp 自己的文档一致（`docs/元宝/评审_废弃Phase2-3-4记忆索引_20261022.md` 已判定那三份倒排为死代码孤岛并同意删除）。

## 四、记忆系统开发方向

### 4.0 先给结论：现有优先级建议是错的

开发者把 `search()` 接线当成"接上就有收益"的第一优先。我核完认为**不是**，理由是三条实测数据：

1. **规模不匹配**：23 条 / 1843 token。全量注入已经在上下文预算内，相关性排序在这条曲线上产生的可见差异接近零。要产生差异，得等记忆量到"装不下"的程度。
2. **收益方向错了**：当前真正的失效模式不是"注入了不相关的记忆"，而是"注入了不该被信任的记忆"（无边界）、"删掉的记忆还在注入"（不广播）、"最久没更新的长期记忆会被静默丢弃"（排序偏置）。这三件都和相关性打分无关。
3. **前置条件没满足**：在注入内容还不可信的时候，把选择逻辑做精细，等于更精准地把不可信内容送进 system prompt。dpp 是先做 envelope（`untrusted-content.ts`）再做选择的，顺序不能倒。

所以路线是：**P0 补治理与边界 → P1 补一致性与写入语义 → P2 才做注入选择与抽取。**

#### P1-2　治理字段：先定语义，本期只落 `source`

- **理由（数据支撑）**：`confidence` 在 `src/` 下**没有任何读取点**（除 `rowToMemory` 回填与 `save` 校验），`personaTags` 的消费者 `listByPersona` 和 `search({personaTag})` 都是零调用方。也就是说现在写进去的 `confidence` 和 `personaTags`，没有任何代码会读。写一个没人读的字段，收益是零，成本是"以后有人以为它是权威值"。
- **建议定义（需拍板）**：

  | 字段 | 谁赋值 | 取值 | 谁读 |
  |---|---|---|---|
  | `source` | **宿主赋值，不接受调用方传入** | `user` / `agent` / `curator` / `import` | 页端记忆列表、审计 |
  | `confidence` | 暂不写（NULL） | — | 无 |
  | `personaTags` | 暂不写（`[]`） | — | 无（等 `listByPersona` 真接线） |

- **改动面**：`desktop-host.ts:491-501` 把 `:498-500` 的三行透传改成宿主侧赋值（`memory.save` 命令的调用来源决定 `source`）；`SaveMemoryParams`（`memory-store.ts:40-52`）的治理字段从公开参数降为内部参数。
- **验收判据**：
  - 单测：经模型工具 `memory_save` 写入 → `source === 'agent'`；经 UI 写入 → `'user'`；旧 JSON 导入 → `'import'`。
  - 单测：调用方传 `source: 'user'` 经宿主 RPC 也应被覆盖为真实来源（负向用例）。
  - DB 只读复核：新写入行的 `source` 非 NULL。
- **风险**：低代码风险，主要是语义决策。若决策错（比如按项目分库后才回头改 `source`），返工面在 DB 迁移。

#### P1-3　`save()` 的覆盖语义改成合并 + 容量上限 + 跨名去重

- **理由**：`:326` 的 `pinned` 与 `:305` 的 `tags` 会在未传值时被重置（静默丢数据）；无总条数上限；同内容不同名会重复。
- **改动面**：`memory-store.ts:293-369`（`save`）内三处：`pinned`/`tags` 未传则保留 existing；`contentHash` 命中已有行时返回既有 id 而非新建；新增 `MAX_MEMORIES` 常量并在新建前检查（超限按 `updated_at` 最旧 + 非 pinned 失效）。
- **验收判据**：
  - 单测：置顶记忆用同名 save 且不带 `pinned` → 仍为置顶。
  - 单测：带 tags 的记忆用同名 save 且不带 `tags` → 原 tags 不变。
  - 单测：同内容不同 name 的第二次 save → 返回第一次的 id，行数不变。
  - 单测：灌入 `MAX+1` 条 → 有效条数 ≤ `MAX`，且被失效的是"最旧且非置顶"。
- **风险**：中。改的是数据层核心写路径，`memory-store-v2.test.ts` 现有 18 条里至少 3 条（`:44` 同名更新、`:62` 硬删后不可见、`:72` 排序）会受影响，需要同步调整断言——**这是本路线里唯一会动既有测试预期的项**。

### P2：后续（按触发条件启动，不是按时间）

#### P2-1　注入选择（预算 + 排序），但分两步

**这一步才回答开发者原来的问题：`search()` 接不接、接在哪。**

- **第一步（零 RPC，先做）**：只加预算和确定性排序，不引入相关性。
  - 改动面：`main-world-interceptor.ts:493-500` 加 token 预算（用 dpp `estimator.ts:3-9` 的 0.6/0.3 口径，目标 1500–2000 token），超出时按 `pinned → updated_at` 倒序截断；把"最久没更新先丢"改成"置顶 + `type === 'user'` 优先"。
  - 验收：注入块 token 估算 ≤ 预算；23 条时全部装下（即当前行为不变），灌到 40 条时按上述优先级截断且置顶/user 类不被丢。
- **第二步（需要一次 RPC）**：接 `search()` 做相关性。
  - **接在哪**：SQLite 在宿主，页端拿不到——所以必然是"页端把本轮 user 文本发给宿主，宿主选片后回传"。形态是新增一个 host 命令（如 `memory.select { query, limit, budget }`），由 `main-world-interceptor` 在 `prepareOutgoingBody`（`:502`）里请求，失败则降级为全量注入（fail-open 到现状）。
  - **不建议**做成 `memory_search` 工具。理由：那是"给模型主动检索的能力"，属产品决策；而"注入哪几条"是每轮必发生的基础设施。两者混在一起会让模型多一次工具往返，且对 23 条的规模毫无意义。除非有"记忆很多、用户想主动查"的真实需求，否则不加。
  - **验收**：给定 60 条合成记忆 + 一个查询，注入块 ≤ 预算且命中 ≥ 3 条；宿主不可达时降级为全量、不阻塞请求（回归）。
  - **风险**：每轮多一次本地 WS 往返（延迟 + 新增失败路径）；必须先有 P0-4 的 envelope。

- **触发条件（写进待办，不是排期）**：有效记忆数 > 35 或注入块 > 2500 token。按当前 1.1 条/天，约 2 周后触发。

#### P2-2　记忆抽取：建议做"候选池"，不做自动写正式表

**这是风险最高的一条，我的明确建议是：不批准"从对话自动生成正式记忆"。**

- **理由（三条，都基于本轮实测）**：
  1. 抽取的决策权已经在模型手里（`:340-346`「你必须调用 memory_save」），只是没有护栏。再加"自动抽取"等于把这个权力放大，而不是加固。
  2. 记忆是**攻击面**，不是知识库。dpp 的事故记录（`untrusted-content.ts:5-13`）证明"记忆里存了个链接"就能让 agent 自己开 tab。studio 的记忆会进 system 消息，注入后果比开 tab 严重。
  3. 当前 23 条里 `source` 全 NULL ——**连"这条是谁写的"都答不出来**。在这个基础上做自动写入，等于往一个没有出处的库里批量灌没有出处的数据。
- **替代方案**：候选池。模型只能写 `memory_candidates` 表（不入注入、不参与 `list()`），用户在记忆 tab 里一键 approve 才落正式表并赋 `source`。
- **前提（缺一不可）**：P0-4 envelope + P1-2 的宿主赋值 `source` + P2-1 第一步的预算（否则候选转正后立刻撑爆注入）。
- **验收**：候选池写入不影响注入（注入块字节数不变）；approve 后 `source` 正确、注入块增长可测；reject 后候选行可查但永不注入。

#### P2-3　审计与回滚：`memory_log`

- **理由**：`audit.ts` 是 200 条内存环形缓冲（`:11`），不落盘，只记工具摘要（`:56-78`）；记忆行有 `created_at`/`updated_at` 但没有 actor。所以"某条记忆何时由谁写入/改过"现在不可答。
- **改动面**：`memories.db` 加 `memory_log(id, memory_id, action, actor, before_json, after_json, at)`，在 `save`/`remove`/`invalidate`/`restore` 四处写日志。
- **验收**：任取一条记忆，能列出完整变更链；`memory.delete` 可从 `before_json` 还原。
- **风险**：低（纯追加）。注意别把 `content` 全文写进日志造成库膨胀——`before_json` 可以只存 hash + 前 200 字。

#### P2-4　多 workspace 隔离：先定产品语义

- **理由**：`memories` 表无 `workspace` 列，全局单例单库。但"记忆该按人还是按项目"是产品问题，不是技术问题。
- **判断依据**：看记忆内容——23 条里 `type` 是 `user`(13) / `project`(10)，`project` 那 10 条是"项目决策"类，天然该跟项目走。所以建议：`user` 类全局共享，`project` 类加 `project_id`（可参考 dpp `scope.ts` 11 行 + `filterMemoriesByProjectScope`）。
- **验收**：切换 workspace 后 `list()` 只返回 `user` 类 + 当前项目的 `project` 类；跨项目不可见。

## 六、开源调研边界建议

开发者问："要不要开始调研 Mem0 / Zep-Graphiti / Letta / Claude Code、Cline？"

**建议：做，但只做一次窄口径的对照，不引库，时间盒 1 天，产出 ≤ 2 页。**

### 6.1 为什么做

因为 studio 现在缺的东西里，有一项是"没有先例可抄"的：**记忆写入的信任边界与冲突表示**。P0-4 的 envelope 可以抄 dpp，但"候选池 + 人工确认"这套流程形态没有现成参照。Mem0 的 pipeline 设计和 Letta 的 self-editing 权限面，恰好是这两个问题的前人答案。

### 6.2 边界（写死在调研任务书里）

1. **只借思路，不引库**。产出必须是"结论 + 我们的对应做法"，禁止出现"建议引入 X"。
2. **只回答 4 个问题**，其它一律不看：
   - 记忆写入的信任边界怎么划？（谁有权写、写在 system 消息里怎么防指令化、有没有"候选-确认"两态先例）
   - 冲突与失效怎么表示？（版本、软失效、覆盖留痕——studio 现在 `save` 是整行覆盖、`invalid_at` 是单字段）
   - 注入预算怎么算？（是否有动态预算，还是固定 token 上限；dpp 是固定 1500 + 按 prompt 长度衰减，`selector.ts:85-90`）
   - 单用户本地库 vs 多租户服务，裁剪代价在哪？（这是判断"能不能借"的唯一硬标准）
3. **只需看 2 个对象**：
   - **Mem0** —— 只看抽取/整合 pipeline 的**阶段划分**（不是实现）。
   - **Letta** —— 只看 self-editing 的**权限面**（模型能改自己什么、不能改什么）。
   - **Zep/Graphiti 可以不看**：时序知识图谱在单用户本地库上没有收益，studio 没有"随时间变化的事实"这种查询需求（23 条里没有一条是时态事实）。
   - **Claude Code / Cline**：约束最接近（本地 agent），但它们的记忆通常是 CLAUDE.md / 文件约定，不是 DB，形态差异大。**如果时间够就看一眼 Claude Code 的 CLAUDE.md 加载顺序**（哪一层优先、怎么截断），这跟 studio 的注入优先级直接相关；时间不够就跳过。
4. **不看代码，只看文档与设计说明**。看代码会滑进"移植"。

### 6.3 不该做的那部分

不要做"开源记忆系统横评"。studio 的选型已经定了（SQLite + FTS5），横评会得出"应该换向量库"这类与前提冲突的结论，浪费一轮。**调研的唯一目的是回答"信任边界与失效表示有没有更好的先例"，不是选型。**

## 七、需用户拍板事项

按影响面排序，每条给出我的建议（不建议的会说明为什么）：

1. **`memory.save` 要不要也从 `read` 提到 `insert`？**
   建议：**不提**。理由：`save` 是 upsert（同名覆盖），不是破坏性操作；提到 `insert` 会让"模型自动记忆"每一步都弹同意，等于把这条链路废掉（`:340-346` 明确要求模型主动写）。只把 `delete` 提到 `privileged`（P0-1）。

2. **`memory.delete` 是改软删，还是保留硬删 + 二次确认？**
   建议：**两步走**——P0-1 先加同意闸门（立刻降风险），P1-1 再改成 `invalidate`。不要一步到位，因为软删会引入"库只涨不降"，需要配套 purge 入口和 UI 两态，属于 P1 的量。

3. **注入选择的接线点：宿主预选 vs 新增 `memory_search` 工具？**
   建议：**宿主预选**（新增 `memory.select` host 命令），不加 `memory_search` 工具。理由见 P2-1。若你认为"模型应能主动查记忆"是产品需求，那是另一个决定，可以并行加，但不该拿它当注入的实现。

4. **记忆的产品语义：按人（全局）还是按项目（隔离）？**
   建议：**`user` 类全局 + `project` 类按项目**（P2-4）。这一条会决定 `memories` 表要不要加列，改晚了要迁移。

5. **是否接受一次 prompt 面变更（P0-4 的 envelope）？**
   需要你确认"可以改 prompt 措辞并做一轮真机抽检"。这是本路线里唯一会改变模型行为的动作，代码改动小，验证成本高（要真机跑几轮看有没有副作用）。

6. **`execution-policy.ts` 是删还是接？**
   建议：**删**（P0-2）。如果你记得它本来要接什么，先告诉我再接。
