二架构总览

项目实际上是四层、两个进程、三条 WebSocket/HTTP 通道的结构。把设计文档（docs/architecture.md）和真实代码放在一起看，最大的落差是：文档描述的是「Rust 主进程托管一切」（KV 存储、HTTP API、导航白名单、MCP 宿主都计划写在 Rust 侧），而实现把整个大脑搬到了一个独立的 Node 进程里，Rust 只剩 54 行建窗代码。这不是错误 —— 作者在 docs/版本路线图.md 里把 Rust 宿主化排到了 v0.7 —— 但两份文档同时留在仓库里且没有互相标注，是后面所有「找错文件」的来源。

2.1 进程与通道

  • Tauri 主进程（Rust）：src-tauri/src/main.rs。建两个窗口 —— main 加载远端 https://chat.deepseek.com（WebviewUrl::External）并挂 initialization_script(include_str!("../inject/entry.js"))；agent 加载 http://127.0.0.1:8756/agent。可选地用 STUDIO_SPAWN_HOST 环境变量触发 npm run start 拉起宿主。
  • Node 常驻宿主：src/api/main.ts → src/host/desktop-host.ts。一个 node:http 服务器监听 127.0.0.1:8756，同时承载 HTTP API、两个 WebSocket 端点（/studio 给注入页、/agent-ws 给面板）、以及给面板用的静态页面 /agent。
  • 通道一（页 ↔ 宿主）ws://127.0.0.1:8756/studio：双向工具派发（dispatch / result）、同意闸门（consent-required / consent-decision）、以及 v0.6 的反向投递（tool-call → tool-call-result）。
  • 通道二（面板 ↔ 宿主）/agent-ws?token=…：面板驱动 send / stop / set-policy / set-workspace / pick-folder，宿主回推 agent 事件流。
  • 通道三（外部 ↔ 宿主）http://127.0.0.1:8756/v1/…：OpenAI 兼容的 /v1/chat/completions（含 SSE）、/v1/models、/v1/tools/execute、/v1/tools/audit、/v1/queue/status，Bearer token 鉴权 + 令牌桶限流 + 串行并发上限。

2.2 数据流：一次「自然语言 → 改本机文件」的完整路径

  1. 用户在面板输入 → /agent-ws → agentChannel.handle('send') → agentLoop.send(text)（src/host/agent-channel.ts:127-139）。
  2. AgentLoop 把文本交给 ModelEngine；MVP 实现是 web-engine.ts：调 chat-insert 写进聊天页输入框 → chat-send 触发发送 → 之后每 1.5 秒调一次 chat-read，用「连续两次快照一致」判定回复结束，单步 120 秒看门狗兜底（src/host/engine/web-engine.ts:31-93）。
  3. 聊天页里的 MAIN-world 拦截器 hook 了 fetch/XHR，边流式边解析模型吐出的 <local_file_write>{…}</local_file_write> 标签，把标签从可见流里剥掉，并把调用经 /studio 以 tool-call 投给宿主。
  4. 宿主侧 tool-contract.ts 把上游 invocationName（local_file_write）映射成 Studio 工具 id（file.write）并适配参数。
  5. 执行入口统一收敛到 desktop-host.ts:493-502 invokeTool()：它自己签发一张一次性 grant，再立刻消费它，随后进入 executeTool → registry 白名单闸门 → policy 三档判定 → （必要时）向页端弹同意模态 → 派发到宿主侧 capability（shell/file）或页端 capability（chat-*）。
  6. 结果走 audit 留痕、经 tool-call-result 回到页端拦截器的 pending 队列，在下一次出站请求里回填给模型，形成「模型发起 → 宿主执行 → 结果回注」闭环。

交付与升级 有 build:inject（esbuild 双产物）、tauri:build、注入产物用 include_str! 编进二进制 没有宿主构建步骤（生产靠 tsx src/api/main.ts，而 tsx 是 devDependency）；无单文件产物/安装包验证、无签名、无自动更新、无回滚、无 CI（无 .github）；tauri.conf.json 的 frontendDist: "../dist" 指向一个只含 index.html 的目录，而两个窗口实际都走 External URL，该配置形同虚设 项目现在无法交付给任何不想装 Node + devDependencies 的用户 缺口
扩展点 两处扩展设计得很干净：ModelEngine 接口（web / api 双实现位，api 桩显式返回「未实现」而不是静默失败）+ tool-contract.ts 单表映射；capability 以 Map<id, ExecutableCapability> 注入，加工具只改两处 站点白名单是硬编码单源（DEEPSEEK_ORIGIN 同时是身份与白名单，见 P0-2）；端口/路径常量散落；执行侧（page/host）靠 execution 字段声明，缺省是危险的 'page'（已在 registry 里归一化，但默认值方向仍值得反过来）；没有插件/适配器的加载与隔离机制 换模型要动 desktop-host.ts 装配；换站点要改常量并重打包 可用但薄
文档与实现一致性 AGENTS.md（上游）与 docs/architecture-review.md 的架构不变量写得相当锋利，甚至预判了多处后来的风险 docs/architecture.md v0.1 描述的是 Rust 侧架构（kv_store.rs/http_api.rs/独立模式/8765 端口），与实现的 Node 架构、8756 端口、目录结构（文档里还有 src/content.js、vite.config.ts、README.md 这些不存在的文件）不符；三处版本号 0.4.0 与实际 v0.5/v0.6 能力错位 按文档找文件会找不到；交接给他人（或三个月后的自己）需要先做一次考古 缺口

3.1 分层与模块边界

现状。八层目录（api / host / capabilities / inject / bridge / desktop / ui / shared）职责清楚，依赖单向：desktop/entry.ts 装配 → inject/ 骨架 → capabilities/ 执行；宿主侧 desktop-host.ts 是唯一的组合根，把 registry、authority、policy、workspace、audit、hub、agent-loop 串起来；shared/tool-contract.ts 是纯函数共享模块，页端与宿主各取一份同一张表 —— 这是很难得的克制。

缺什么。① src/types/ 是空目录（类型散落在各模块的 types.ts），说明「类型集中层」这个抽象被放弃了但目录还留着；② src/inject/lifecycle.ts 提供的是全 noop 的 resource scope（addCleanup/listen/observe/ownPort 全是空实现，snapshot() 恒返回 0），于是「stop 后资源归零」这条不变量在桌面壳里根本没有被验证的载体；③ desktop-host.ts 单文件同时承担装配、治理判定、路由（routeExecution）、agent 编排、API 装配，已经 640 行量级，是全项目最可能先腐化的文件。

后果。资源不变量失守不会立刻报错，但一旦页面 SPA 路由切换或重复注入，泄漏的监听器/定时器将只体现为「越用越慢」；desktop-host.ts 继续长下去，任何人要加一个工具都得在一个文件里同时理解四层概念。

3.2 配置管理

现状。resolveWorkspaceRoot() 有明确的优先级与来源标注（env | config | none），并且刻意拒绝回落到进程 cwd（注释里写明「否则『工作区内自动放行』会变成『宿主所在目录全部自动放行』」）；setPolicyMode 先校验枚举再持久化；配置写入失败只告警不崩。

缺什么。没有配置 schema 与版本号；persistConfigPatch 是「读整包 → 改字段 → 整包覆盖」，没有临时文件 + rename 的原子性保护；resolveWorkspaceRoot 只做 path.resolve 而不校验目录是否存在（非法路径会把文件能力推进 deny 态而不是给出可读错误）；8756 这个端口在 Rust、注入脚本、tauri.conf、api/main.ts 里各写一份；配置项的生效时机（哪些热生效、哪些要重启）没有文档。

后果。手工编辑配置出错时会静默退化为「文件工具全不可用」，用户拿到的是 workspace-unconfigured 而不是「你的 workspaceRoot 指向了一个不存在的目录」；端口冲突时四处都要改。

3.3 错误处理与故障恢复

现状。失败一律表达为 { ok:false, error: '<code>' }，不靠异常穿过 ws 层；页端断线有指数退避重连（500 ms → 10 s 上界）；dispatch / requestConsent 分别有 30 s / 60 s 超时且失败方向是 no-page-runtime / deny（fail-closed）；shell 有能力超时（默认 30 s、上限 120 s）与 64 KB 输出截断；HTTP 层的并发计数曾经会在异常路径下扣成负数，代码里能看到为修这个问题而收敛出的单一 release() 出口。

缺什么。看门狗只在模型侧（web-engine.ts 的 120 s 单步超时）；/v1/* 没有请求级超时；错误类型不统一（HTTP 500 会把内部 err.message 原样回传）；重试决策散落在各处（页端重连有退避、工具执行没有、模型调用没有）；降级不可恢复：完整性告警一旦命中该页永久不可信（P1-1）。

后果。上游变慢时面板表现为「长时间无输出」，用户无法区分「模型在想」与「链路已断」；一次误告警会让 chat-* 能力在整个页面生命周期内静默失效。

3.4 并发与状态管理

现状。HTTP 层默认 maxConcurrent=1 串行（与「避免高频触发上游风控」的动机一致），超限返回 429 + Retry-After；令牌桶按 Authorization 值分桶；agent 事件通过监听器集合广播，且每个观察者的异常被单独吞掉以免打断循环。

缺什么。① agent 循环的控制流建立在一个全局计数器上：desktop-host.ts:536-538 的 onToolCall 每次页端投来工具调用就 agentToolCounter.current += 1，web-engine.ts:91 用「本轮计数差 > 0」决定「要不要继续推模型」。它既不知道工具成功还是失败，也不知道结果内容，更无法区分「这是面板这一步触发的」还是「用户手打对话触发的」——因为 /studio 是所有页共用的一条通道。② stop() 只置 stopped 标志，等待中的 send() 不会被打断（web-engine 在轮询循环里检查标志，但 chat-read 派发本身不可中止）。③ 工作区与权限档位是进程级单例，两个面板窗口共享同一份状态（agent-channel 用广播把所有事件发给所有连接）。④ 多页时 pickClient() 只取「第一个未标记不可信的连接」，没有按 origin/会话选择。

后果。面板与人工对话同时使用时会出现「凭空多出一步」的续跑；「停止」按钮的响应取决于当前卡在哪一步；将来开多会话/多窗口时状态会互相覆盖。

3.5 数据持久化

现状。只有三样东西真正落盘：~/.config/deepseek-studio/config.json（token / secret / workspaceRoot / policyMode）、WebView2 的 profile 目录（登录态 cookie）、以及 src-tauri/inject/entry.js 这类编译产物。

缺什么。chrome.storage 的桥（src/bridge/storage.ts）默认后端是内存实现（第 395 行 createMemoryStorageKvBackend()），接口 StorageKvBackend 已经为「Rust KV 原子写」预留好了形状但没人实现；grant 存储是内存 Map；审计环是内存环形缓冲（默认 200 条）；对话/任务/工具结果历史完全不落地；没有 schema 与迁移概念；没有备份/恢复/损坏处理路径（配置 JSON 被写坏就只能靠人手工修）。

后果。重启即失忆：审计无法用于事后追责（而这恰恰是引入 shell/file 能力时作者自己写下的理由）；模型多步任务中断后无法续跑；上游快照之外的「状态」全部是易失的。

3.6 接口契约

现状。HTTP 面刻意做成 OpenAI 兼容形状（chat.completion.chunk / reasoning_content 单独通道 / 以空 delta + finish_reason=stop 收尾 / data: [DONE]），/v1/queue/status 还额外给了 avgWaitMs 与最近执行记录 —— 这些细节说明作者真的在想「别人怎么消费我」。宿主↔页协议用 TS 联合类型把全部消息枚举清楚（protocol.ts），错误走 result.ok=false + error 而不走 ws 异常。

缺什么。没有版本策略：/v1 只是路径，没有弃用标注、没有兼容承诺、没有「未实现」与「不支持」的区分（/v1/embeddings 与 /v1/audio 返回 501 是靠 isUnimplementedPath() 白名单硬编码的）；ws 消息没有独立 schema 校验（页端是「不可信输入的一侧」，却只有 TS 类型）；/v1/tools/execute 的入参只校验 tool 是不是非空字符串，params 直接透传给能力层。最关键的是：契约的语义是假的 —— /v1/chat/completions 背后是 createFakeOfficialBackend()（P1-4）。

后果。任何按文档接入的外部 agent 会先拿到固定假回复；页端（真正不可信的那一侧）发来的消息结构没有任何运行时校验，全靠类型注释。

3.7 鉴权与信任边界

现状（这一维度做得最多的部分）。HTTP 面有常量时间比较的 Bearer 鉴权（src/api/auth.ts:26-31，避免时序侧信道）；令牌环支持轮换且宽限期内同时接受新旧令牌（host-token.ts:67-97，并解释了为什么——否则轮换瞬间正在跑的 agent 链路会静默断掉）；grant 是一次性消费并可绑定 document/session/requestId；registry 有 origin 白名单与 fail-closed 语义；能力层对工作区做二次校验并且用 realpath 拦软链逃逸；CORS 只放行 localhost / 127.0.0.1。

问题是这些边界里有三条没有真正合上：

  • /studio 是无身份通道，而它恰恰是特权工具的执行入口（P0-1）；
  • grant 由执行方自己签发、origin 写成常量，使「白名单」成为同义反复（P0-2）；
  • /agent 免鉴权却把 API 令牌内嵌进了 HTML，而 Windows 上配置文件权限位本来是无效的（P1-2）。

后果。把三件事串起来看：一个恶意网页 → 连上 /studio → 发一条 tool-call → 宿主自签 grant（origin 常量天然通过白名单）→ 默认 auto 档下写工作区文件或执行不含风险关键字的命令 → 全程无同意弹窗、无人工可见的提示。这就是 P0 组合风险的完整链路，也是本报告建议优先处理的原因。

3.8 可观测性

现状。有审计环（工具、参数摘要、决策与原因、风险标记、耗时、终态）并通过 /v1/tools/audit 暴露最近 N 条（上限 500）；/v1/queue/status 给了并发/排队/平均等待与近期执行；日志有模块前缀；面板有连接状态灯与档位显示。

缺什么。日志是纯文本、无 level 字段、无结构化输出、无轮转（写 stdout）；没有指标导出与 trace 贯通（审计里有 callId，但日志里没有它，无法把「一次工具执行」与「一条 ws 消息」串起来）；审计不落盘、不可查历史、容量固定 200 条且被覆盖式淘汰；关键状态变化（档位切换、工作区切换、令牌轮换）没有日志断言只有代码；没有「为什么这次被拒绝」的用户可见回执（拒绝原因进了审计与模型上下文，未必进了 UI）。

后果。出问题时的排查路径是「翻 stdout 回忆 + 复现」，而不是「按 callId 查一次执行」。对一个会执行本机命令的系统来说，这个能力等级偏低。

3.9 测试

现状。23 个文件 / 185 个用例 / 2,554 行，最近一次 vitest run 全绿（约 82 s）。测试挑的地方很准：策略判定矩阵、白名单 fail-closed、grant 一次性、限流与并发上限、注入加载器幂等与重装载、模块级单例竞态（为此显式关掉文件级并行）。vitest.config.ts 里那段「并行执行会争用 bootstrapInjection 的模块级 installState」的注释，说明作者知道自己在绕什么坑，也知道那个坑是设计带来的。

缺什么。没有真实 ws 的端到端冒烟（Windows WebView2 的手工验证被 jsdom 级装配测试替代，作者在 docs/开发计划.md 里如实标注了）；没有并发/压力用例；没有针对「/studio 无凭据连接」「/agent 泄令牌」这类边界失效的回归用例；没有覆盖率门禁，因此「边界被绕过」这种缺陷不会让测试变红。

后果。当前测试全绿与 P0 缺陷并存并不矛盾 —— 它们测的是模块内部行为，而 P0 问题出在模块之间的接线处。这个盲区应当被显式补上（把 P0-1 的复现写成测试，它就会立刻变红）。

3.10 交付与升级

现状。build:inject 用 esbuild 产出两个 IIFE（src-tauri/inject/entry.js 59 KB、dist/agent-panel.js 5.3 KB）；注入产物通过 include_str! 编进 Rust 二进制，因此「注入脚本」这一半是自带分发的；tauri:build 走 Tauri 标准打包。

缺什么。宿主没有构建步骤：npm start = tsx src/api/main.ts，直接执行 TypeScript 源码，而 tsx 与 typescript 都躺在 devDependencies 里；package.json 没有 dependencies 段（运行时依赖没有与开发依赖分离）；没有安装包/单文件产物的验证步骤、没有签名、没有自动更新与回滚、没有 CI 配置目录；tauri.conf.json 的 frontendDist: "../dist" 指向的目录里只有一个 index.html，而两个窗口都用 External URL 加载，这份配置实际上不生效；生产态拉起宿主靠 STUDIO_SPAWN_HOST 环境变量（默认关闭），也就是说双击安装后的应用默认没有宿主。

后果。「能不能交付」的答案是不能（对不想装 Node 的用户而言）。这属于产品定位层面的决策缺口，而不是代码问题 —— 但必须在写更多功能之前决定：是把宿主编译成单文件走到 sidecar/bundled 形态，还是坦然承认这是「开发者自用工具」。

3.11 扩展点

现状。两处设计值得表扬：① ModelEngine 接口只暴露 name / health() / send()，web 与 api 双实现位，api 侧给了显式抛「未实现」的桩，避免「静默失败假装能用」；② 工具映射集中在 shared/tool-contract.ts 一张表里（新增上游工具只改一处），配合 execution: 'page' | 'host' 声明让「在哪儿执行」成为数据而非分支。

缺什么。站点白名单是硬清单源（DEEPSEEK_ORIGIN），换站点要改常量并重新打包注入产物；端口与路径常量散落四处；execution 的缺省值是 'page'（虽然 registry 的 put() 会把缺省归一化，但默认方向仍是「更危险的一侧」，建议反过来）；没有插件/适配器加载与隔离机制（一个第三方 MCP 或 skill 目前无处安放）。

后果。「加一个新 provider」目前要动 desktop-host.ts 的装配 + 常量 + 可能重打注入产物，属于「一处逻辑、四处修改」。

3.12 文档与实现一致性

现状。docs/architecture-review.md 是项目自己在 2026-10-09 做的一轮设计缺口评审，质量相当高（双 world 内容脚本模型缺失、grant 签发者未定、chrome.storage.session 语义无对应 —— 这几条后来都被现实印证了）；docs/版本路线图.md 有明确的「方向修正记录」（外部 agent HTTP 接口降级为可选外围）；上游 AGENTS.md 列出了 prompt bytes、storage key、runtime message 名等不变量。

缺什么。docs/architecture.md（v0.1，2026-10-07）与实现已经系统性分离：它描述 Rust 主进程托管 KV（kv_store.rs）、HTTP API（http_api.rs）、导航白名单（nav.rs）、独立模式（PoW 求解 + 私有 API 客户端）、端口 8765、目录含 src/content.js / vite.config.ts / README.md —— 这些在当前仓库里都不存在或未实现。三份清单文件（package.json / Cargo.toml / tauri.conf.json）的 version 都是 0.4.0，而代码与计划文件已经在 v0.5 / v0.6。根目录没有 README，没有 LICENSE，也没有说明「这份 architecture.md 是目标态还是现状」的一句话。

后果。文档目前的作用是「反向误导」：新人（或三个月后的作者）按 architecture.md 找 src-tauri/src/kv_store.rs 会一无所获，且会误以为端口是 8765、会误以为存在独立模式。这一条比它看起来重要 —— 它决定了这次评审的结论能否被下一次评审复用。

一句话总结第三节：这套架构在「模块怎么切」上做得比大多数 v0.x 项目都干净（分层、单点装配、共享契约、可插拔引擎、测试挑了硬骨头），但三条边界（页↔宿通道身份、grant 的来源、档位与正则的因果关系）没有合上，加两条工程链路（宿主打包、持久化）没有修，以及一份会误导人的主设计文档。缺口数量可控，且都是能在有限时间内收敛的形态。

四设计缺陷清单

按严重程度排序。每条给出位置（文件与行号）、机理（为什么会成为问题）、触发条件（什么条件下爆发）、影响面、改法。末尾的「判定」区分确定有问题（事实层，代码就是这样）与有风险（设计取向，取决于后面的规模与场景）。同一根因合并为一条。

P0-1页↔宿工具通道 /studio 没有任何身份：无令牌、不校验 Origin，且采信客户端自报的 origin
位置
src/host/page-runtime.ts:60-99（new WebSocketServer({ server, path: '/studio' })，wss.on('connection') 里唯一的鉴权动作是把 hello 消息里客户端自报的 origin 记下来）；src/desktop/host-client.ts:117-126（页端连接时不带任何凭据）；src/desktop/entry.ts:28（地址常量 ws://127.0.0.1:8756/studio）；src/host/desktop-host.ts:530-539（该 hub 挂着 executor: invokeTool，即特权工具的直达入口）
机理
WebSocket 握手不受同源策略/CORS 约束：任何本机进程、以及用户浏览器里任何网页（原本的 Origin 头就在握手请求里）都能建立连接。而服务端既没有校验这个现成的 Origin 头，也没有要求任何共享秘密，还把「我是谁」完全交给对端自己声明。对比之下，同一进程里的 /agent-ws 是查了 query token 的（agent-channel.ts:87-97）——也就是说，保护「面板」的强度高于保护「能执行命令的通道」，方向正好反了。
触发条件
连上 ws://127.0.0.1:8756/studio → 发 {"type":"hello","origin":"https://chat.deepseek.com"} → 之后按 protocol.ts 的消息格式直接发 tool-call（例如 invocationName: "local_file_write"）。不需要令牌、不需要页面、不需要用户点击。
影响面
在默认档位（见 P0-3）下即等价于「本机用户级任意文件写入 + 不含风险关键字的任意命令执行」。这是本报告里唯一一条无需任何前置条件即可被外部输入触发的路径。
改法

P0-2授权链自签自销：执行方自己签发 grant，并把请求来源写死成常量
位置
src/host/desktop-host.ts:493-502（invokeTool()：documentId:'host-agent'、sessionId:'host-agent'、scope: tool、origin: DEEPSEEK_ORIGIN → 立刻 executeTool(tool, params, grant)）；同一函数被 :333（HTTP /v1/tools/execute）与 :534（页端 tool-call）两条完全不同的入口共用；src/host/authority.ts 的 verifyGrant()（仅比对 scope，不比对 documentId/sessionId/origin）；src/host/tool-definitions.ts:47-86（全部特权工具 allowedOrigins: [DEEPSEEK_ORIGIN]）
机理
「授权先于执行」要成立，前提是签发权与执行权分离：签发方校验「这次调用确实来自它声称的上下文」，执行方只认票据。这里却把两者合并在同一个函数里，还用一个常量填写「来源」。结果：registry.isOriginAllowed() 永远为真、白名单闸门不可能拒绝、grant 的 origin 字段恒等于被信任的那个源，验收测试里「非白名单 origin 被拒绝」的用例只能靠手工构造 grant 才跑得通 —— 真实调用路径上这个分支是死代码。
触发条件
无需任何特殊条件：只要能让宿主调用 invokeTool（即 P0-1 的任意连接，或持有 API token 的任意客户端），就会自动获得一张合法 grant。
影响面
① 白名单/授权/审计三处机制对真实调用者零区分度；② 审计里的 origin、documentId、sessionId 是虚构值，事后追责会把责任指到「某个 DeepSeek 页面」，而真正来源（某个本机进程 / 某个网页）不会被记录。这比第一条更隐蔽：它让「我们有授权链和审计」这件事失去证据价值。
改法
① 收敛签发入口：只允许在「已完成身份验证的会话」上签发，origin/documentId/sessionId 从该会话对象取，禁止调用方传入；② 宿主自发的调用（HTTP API、agent loop）走一条显式的「宿主内调用」路径，不伪造页面身份，而是在审计里如实标注 caller = api:<tokenId> | agent:<loopId> | page:<pageId>；③ verifyGrant 补齐与存储记录的交叉比对（documentId/sessionId/origin 全部要比）；④ 把 DEEPSEEK_ORIGIN 拆成两个不同概念：注入白名单 与 调用方身份，用一个常量同时充当两者是这条缺陷的根。
判定：确定有问题（属于「安全机制存在但语义不成立」，比缺失更难被发现）。

位置

机理
auto 档的判定是黑名单的否定：只有命令文本命中那 10 条正则才弹审批，其余全部静默执行。而黑名单天生列不完「有破坏力但写法平淡」的命令；更关键的是，正则匹配的是命令文本，而风险实际发生在副作用上。同时 cwd 在工作区内 并不等于「只在工作区内产生副作用」——npm install -g、写 %APPDATA%、git push、启动一个后台常驻进程，全都在「cwd 合法」名下通过。

影响面
它不是「命令注入漏洞」（作者已经用 shell:false + argv 把注入面关掉了，这一点做得对），而是默认安全姿态与产品承诺之间的落差：面板上显示「🟡 风险审批」，用户会理解成「有风险的事会问我」，实际语义是「我只拦我看得出来的十种写法」。叠加 P0-1/P0-2 后，这条决定了那条外部路径的最终后果等级。
改法
① 把默认档改成 workspace（仅工作区、shell 直接拒绝），让「放开」成为用户显式动作；② 或者把 auto 的判据从黑名单换成白名单：以 argv[0] 为主键维护「可自动执行」的命令表（npm/node/git status…），表外一律审批；③ 把已经在数据里的判定依据（reason + riskFlags）如实展示在面板与审计上，让「为什么放过」可解释；④ 给「工作区内」补上语义：至少要拦住绝对路径写外部位置与全局安装类操作。
判定：确定有问题（默认姿态）。其中「正则被当作安全边界」这一取向另标为有风险：在单人自用场景下可以接受，一旦面向他人分发就必须换掉。
P1-1完整性自检「一次命中即永久降级」，而且真机日志里已经触发过一次
位置
src/host/page-runtime.ts:107-110（收到 integrity-alert 即 rec.untrusted = true，此后没有任何复位路径）；:77-84（pickClient() 跳过所有 untrusted 连接）；src/desktop/integrity.ts:63-77（freezeStudioObject 把 window.__deepseekStudio 钉成不可写、不可配置，探测周期 5 s）；证据：tauri.log 末行 [page-runtime] integrity violation: page=07946e4d… reason=descriptor-downgraded undefined
机理
探针每 5 秒比对一次 window.__deepseekStudio 的引用/成员/属性描述符；一旦发现「描述符被改成可写可配置」即上报，宿主把整页标记为不可信。问题是：降级是单向且静默的。同域页面（以及任何扩展、注入器、调试工具、甚至 Tauri 自己在窗口重建时）都有可能触碰这个描述符；而误命中之后的后果是 chat-read/chat-insert/chat-send 全部派发不到页面 —— 面板会表现为「模型引擎不可用」，但用户看不到任何原因。
触发条件
任何一次描述符状态变化（真机日志已经出现过一次，且日志里 detail 是空的 undefined，说明连违规细节都没能给出）。
影响面
核心闭环（面板 → 聊天页 → 模型）会在一次误报后永久失效直到重建连接/重启；因为 pickClient() 只挑可信页，单页场景下等价于「整个工具派发链路关闭」。而且它同时关掉了合法降级路径的可见性。
改法
① 降级要可恢复：连续 N 次（例如 3 次）复查无异常即可重新信任，或在页面重新注入（generation 递增）时重置；② 把违规细节真正填进 detail（当前是 undefined），并在面板上以「引擎不可用 + 原因」显式提示，而不是让 upper layer 只看到 chat-read-failed；③ 区分「描述符被动过」与「对象被替换/删除」的严重度 —— 前者更可能是环境副作用，不必直接降等级；④ 这条链路需要一条真实 ws 的回归测试，把它从「只在上线后才发现的降级」变成「CI 可复现的状态机」。
判定：确定有问题（已有真机证据）。
P1-2本地凭据的保护只依赖文件权限，而这两条都不成立：面板页免鉴权下发令牌 + Windows 上 0600 无效
位置
src/api/server.ts（/agent 路由，约 190-215 行）（/agent 路由在 Bearer 校验之前返回 HTML，并把令牌替换进页面：.replace(/__STUDIO_API_TOKEN__/, JSON.stringify(token))；/agent.css、/agent.js 同样免鉴权）；src/ui/agent.html（window.__STUDIO_TOKEN__ = "__STUDIO_API_TOKEN__"）；src/api/main.ts（配置写盘用 mode: 0o600）；src/host/workspace.ts（配置路径 ~/.config/deepseek-studio/config.json，同一文件里还存着 HMAC secret）
机理
设计文档里的威胁模型是「本地进程本就能读 config.json，所以把令牌发给面板页不算额外泄漏」。这在单用户机器上基本成立，但有两个缺口：① 免鉴权的 /agent 把令牌变成了「一次 GET 就能拿到的东西」，任何以更低权限运行的本机进程（浏览器插件、别的用户、沙箱化应用）都能取到，而不再需要文件读取权限；② Node 的 mode 参数在 Windows 上不生效（Node 文档明确：Windows 不支持 POSIX 权限位），所以那行 0o600 给人以虚假的安全感，实际保护来自 %USERPROFILE% 的默认 ACL，而 ~/.config 这个目录在 Windows 上并非受保护路径。
触发条件
curl http://127.0.0.1:8756/agent | findstr STUDIO_TOKEN 即可从本机任意进程取到令牌；拿到令牌后 /v1/tools/execute 直接可用（见 P0-2），/agent-ws 也可连。
影响面
「本机其他程序」这一威胁面在产品叙事里被当作不可信源，但实际只需一次 HTTP GET。同一台机器上多用户共用时，config.json 里的 HMAC secret 泄漏意味着 grant 可被离线伪造。
改法
① 面板页不要内嵌长期令牌：改为宿主在窗口创建时通过 Tauri IPC / 一次性 nonce 交换短暂凭据；至少让 /agent* 也走鉴权（面板窗口可以用一次性的、与窗口生命周期绑定的短期 token）；② Windows 上用 DPAPI（或 Credential Manager）保存 secret，而不是靠文件模式位；③ 令牌与 secret 分开存放，secret 永不通过任何网络端点暴露；④ 令牌轮换已经在实现里（rotateApiToken），把它接到「每次启动/每次面板重连」这种自然端口上。
判定：确定有问题（弱化面），其中「本机同用户进程不可信」是否纳入威胁模型属有风险的设计取向。

判定：确定有问题（与自述能力不符）。

P1-7智能体循环的「这一步发生了什么」建立在一个全局计数器上：不知道成败、不知道内容、还会串扰
位置
src/host/desktop-host.ts:536-538（hub.onToolCall → agentToolCounter.current += 1，一个进程级共享对象）；src/host/engine/web-engine.ts:55 + :91（本轮起点记 counterStart，结束后用 current - counterStart 得出「本步工具调用数」）；src/host/agent-loop.ts:19-33（循环只依赖 toolCalls 与 RAW_TOOL_TAG_RE 决定是否续跑与是否纠偏）；src/host/page-runtime.ts:118-145（tool-call 分支在执行前就调 onToolCall）
机理
作者在 agent-loop.ts 抬头写下的设计取舍是对的：「本模块不解析工具标签，避免双重解析/双重执行」。但落地时把「有没有工具调用」这个结果降级成了「计数器有没有变」这个旁证：① 计数在执行前自增，所以失败/被拒绝的调用同样计入「已执行完毕」，循环随后会向模型发「工具已执行完毕，结果已回填」的 nudge（agent-loop.ts:21-23），而实际上可能什么都没做成；② 计数器属于进程而非某次会话，用户在同一个聊天页里手工提问触发的工具调用（v0.6 桥对页面**所有**工具调用都会投递）会被算进面板那一步的差额里；③ 结果内容不进入控制流，因此「纠偏」「重试」「失败上报」都缺少依据。
触发条件
① 工具执行失败或被策略拒绝时（面板仍会被告知「已执行完毕」）；② 面板对话与人工对话同时使用同一浏览器页时（串扰）。
影响面
恰恰是产品核心（多步自主执行）的可靠性边界：模型可能基于「其实失败了」的假设继续推理，用户看到的工具卡片与真实结果不一致；将来加多会话会让这个计数器彻底不成立。
改法
① 把「工具调用」从计数器改成事件对象：{callId, tool, ok, error, durationMs, stepId}，由 onToolResult（已经存在）驱动循环，而不是由 onToolCall 驱动；② 给 agent 每一步分配 stepId 并让页端投递带上它（callId 已经具备这个条件），从而把「面板触发的调用」与「人工触发的调用」分开；③ 把拒绝/失败原因结构化回填给模型（拒绝原因回填在 docs/设计稿_智能体面板.md 里已经写在设计里，实现没跟上）；④ 单步超时对 chat-insert/send/read 分别设阈值，而不是只有整体 120 s。
判定：确定有问题（控制流依据错位）。串扰部分另标为有风险：单人单页使用时不明显，一旦多页即必然发生。

P2-2HTTP 面若干健壮性缺口：无请求体上限、解析失败按 500 报、无请求超时
位置
src/api/server.ts:394-401（readBody() 无长度上限地收集全部 chunk）；:303（JSON.parse(raw) 未包 try/catch，畸形 JSON 会走外层 catch 变成 500 internal 而不是 400）；:361-364（外层 catch 把 err.message 原文回传客户端）；:294-300（并发超限直接 429，而 queued/depth 指标仍以「排队」语义对外暴露，两者口径不一致）；src/api/compat.ts:isUnimplementedPath（未实现路由靠硬编码名单）
机理
都是「本地服务所以先这样」的合理简化，但它们叠加起来使 8756 变成一个对本机任何进程开放的、可被轻易打满内存/日志的端点；同时「500 + 内部错误原文」会把文件路径等实现细节泄漏给客户端。

影响面

判定：确定有问题（健壮性细节，修起来很快）。

位置
src/ui/consent.ts:104-160（用 document.createElement 把遮罩与卡片注入聊天页 DOM，z-index 2147483646，超时/Esc/点遮罩一律 deny）；src/inject/direct-target.ts:18-27（直连桥的底层是一个模块级 EventTarget 总线，按 origin 分桶）；src/inject/direct-port.ts:27-41（用 __session 字段做消息过滤）
机理
direct-target/direct-port 用「页面脚本读不到的模块作用域 + 私有 sessionId」替代了 window.postMessage，这一步比上游的 postMessage 桥确实更安全，注释里的判断成立。但同一个 JS 世界意味着页面脚本可以 hook 全局原型：EventTarget.prototype.addEventListener/dispatchEvent、document.createElement、setTimeout 都还在页面脚本手里，因此页面对这条桥具备「观测与丢弃」能力（拿不到伪造能力）；同意弹窗既然是页内 DOM，也就可能被页面伪装或遮盖（用户点到的「允许」不一定是我们那张卡片）。作者在 integrity.ts 抬头已经写明「这是检测而非阻止」，态度是清醒的。

影响面
同意闸门是这套系统唯一的人工确认环节，它的可信度不该依赖页面的善意。当前实现的强度相当于「在没有隔离的世界里放一个自绘弹窗」。

判定：有风险（设计取向；当前强度在单用户自用下可接受，作为安全卖点则不足）。
P2-4「回复结束」靠轮询 DOM + 两次快照一致来猜
位置

  1. 产品定位：自用工具还是可分发应用？这一条决定后面所有取舍：签名/自动更新/权限模型/崩溃恢复/隐私声明要不要做。当前代码气质更像「作者本人的强力工具」，但三条最重的安全机制（授权链、审计、同意闸门）又明显在向"可交付"的形态对齐 —— 两者需要一个明确的结论，否则会持续同时做两件事。
  2. 上游复用的策略需要收敛。现在 deepseek-pp/src 是 1,133 个文件的只读快照，运行时实际只被一处动态 import 引用（且说明符是错的），而桥、生命周期、拦截器都在 src/inject 下重写了一份。要么真正接入 core/**（并接受随之而来的耦合与升级成本），要么把它明确降级为"参考源码"并从运行时依赖中彻底摘出去、在文档里写清。中间的模糊态最贵：它让人以为复用了，实际上维护了两份。

  4. 权限模型应当自 UI 反推而不是自正则正推。用户看到的是「仅工作区 / 风险审批 / 完全放开」这三句话，实现却是 10 条正则。更稳的路径是：先写下每一档对用户的承诺（例如「仅工作区 = 绝不触碰工作区外路径、不执行命令」），再要求实现满足它，最后才谈怎么用启发式做得更好。
