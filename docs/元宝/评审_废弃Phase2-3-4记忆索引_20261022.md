## 一、✅ 更强论据：这不是"质量差"，是**死代码孤岛**

你论证的是"算法弱于 selector、接进去净负收益"。这些都对，但它们是**预测性论据**（要接进去才知道）。

**我核实到一个决定性事实——三份代码零调用方：**

```
grep -rn "persistent-index|getMemoryIndex|tokenizeBigram|memory-search-tool
         |memorySearch|MEMORY_SEARCH_TOOL_DESCRIPTOR"
     core/ entrypoints/ tests/
     （排除三份文件自身）

→ 结果：空
```

**依赖结构是闭合的孤岛：**

```
index.ts  ←── memory-search-tool.ts（import 但从未使用）
   ↑      ←── persistent-index.ts（真实使用）
   └── 两者均零调用方
```

**这意味着删除零风险**，不需要评估"接进去会怎样"——它们从来就没接进去过。

**建议把主论据换成这个。** 理由：质量差的已接线代码，删除需要谨慎评估；未接线的死代码，删除是纯粹收益。**后者是硬证据，前者是判断。**

顺带：这也解释了为什么 `memory_index` 表是空的 —— 唯一写入方 `persistent-index.ts` 从未被调用。你的安全前提成立，且证据比我预期更硬。

## 三、⚠️ 孤儿表清理：方式要正确

你建议"后续 schema 升级时把这张表从 `MEMORY_TABLE_SCHEMAS` 里摘掉"。方向对，但有个坑：

```
store.ts:60  version: 50  stores 含 INDEX_TABLE_NAME
store.ts:66  version: 60  stores 含 INDEX_TABLE_NAME
```

**Dexie 按版本顺序升级已有数据库。如果直接改掉 version 50/60 的定义，已升级到该版本的库会走错迁移路径。**

**正确做法**：新增一个 version，`stores` 里不再包含 `memory_index`（Dexie 会自动删表），**历史 version 定义不动**。

另注：`INDEX_TABLE_NAME` 是从 `schema.ts` 导入的独立常量，不在 `MEMORY_TABLE_SCHEMAS` 数组里——清理时要改的是 `store.ts:64` 和 `store.ts:72` 两处注册。
