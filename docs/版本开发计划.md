## 3. M10-7.1 · 同名保存保留未传字段

> **状态：DONE（2026-10-24）**
> 提交：`4b2f760 fix(memory): 同名保存保留未传治理字段`
> 验收：M10-7.1 16 条 + `memory-store-v2` 18 条，共 34 passed；typecheck EXIT=0。
> 覆盖：五类治理字段保留、显式 false/[] 覆盖、归档复活保留、SQL/fallback true no-op、空白归一化同口径。
>
> **⚠ 2026-10-26 真机验收推翻本结论：状态回退为 OPEN（见 D-5）。**
> 16 条用例直连 `store.save()`，绕过了工具边界；真实调用路径上同名保存会把 `tags` 清成 `[]`，
> 且 `pinned` 全链路不可写入。`memory-store` 本身的合并逻辑没有错，是边界把"未传"变成了"显式覆盖"。

### 3.1 目标

同名 `save()` 更新内容时，任何未传可选字段都保留原值，不得被默认值覆盖。

覆盖字段：

| 字段 | 当前错误行为 |
|---|---|
| `pinned` | `?? false` 重置 |
| `tags` | `?? []` 重置 |
| `personaTags` | `?? []` 重置 |
| `source` | 未传时写 `null` |
| `confidence` | 未传时写 `null` |

### 3.2 改动文件

- `src/host/memory-store.ts`
- `tests/desktop/memory-governance.test.ts`
- 如需要新增独立测试文件，必须先向 PM 报备。

### 3.3 实现约束

1. 同名命中有效行时，先计算合并值：

```text
pinned      = params.pinned      ?? existing.pinned
tags        = params.tags        ?? existing.tags
personaTags = params.personaTags ?? existing.personaTags
source      = params.source      ?? existing.source
confidence  = params.confidence  ?? existing.confidence
```

2. SQL 更新绑定合并值，不要继续用 `params.x ?? 空值`。
3. fallback 路径使用同一语义；若两份逻辑较长，抽纯 helper，避免再次分叉。
4. 同名命中已归档行时同样保留未传字段，再执行复活。
5. 内容与所有可选字段均无变化时不搅动 `updatedAt`。
6. 不要在本卡改 `contentHash`、容量或去重逻辑。

### 3.4 必测

1. 置顶行更新 content，不传 pinned → `pinned=true`。
2. tags 行更新 content，不传 tags → 原 tags 深等。
3. personaTags 行更新 content，不传 → 原 personaTags 深等。
4. source/confidence 行更新 content，不传 → 原值保留。
5. 只传 pinned=false → 明确取消置顶；不能把“未传”和“显式 false”混为一谈。
6. fallback 路径至少覆盖 pinned + tags；如无法注入 fallback，则抽 helper 直接单测合并函数，并在测试中说明。
7. 归档行同名复活：未传 pinned/tags 时，复活后仍保留原字段。

## 4. M10-7.2 · 跨名称同内容去重

> **状态：DONE（2026-10-24）**
> 提交：`7eaca30 feat(memory): 增加跨名称内容去重与兼容迁移`
> 验收：M10-7.2 9 条 + `memory-store-v2` 18 条，共 27 passed；typecheck EXIT=0。
> 覆盖：新库、旧库有行、旧库空表缺列、旧 JSON 导入、大小写/空白归一、归档复活、fallback。

### 4.1 目标

同一 `type` 下，内容规范化后相同但 `name` 不同，第二次 `save()` 返回既有行 id，不新增行。

### 4.2 为什么不能复用 `content_hash`

现有：

```text
content_hash = sha1(type + lower(name) + normalized(content))
```

名称参与 hash，无法跨名命中。保留它作为旧兼容指纹，新增：

```text
dedupe_hash = sha1(type + normalized(content))
```

### 4.3 改动文件

- `src/host/memory-store.ts`
- 新增/修改 `tests/desktop/memory-governance.test.ts`
- 若涉及类型，可改 `src/host/bot/types.ts`，但不得改 `MemoryStoreV2` 既有签名。

### 4.4 兼容迁移要求

当前建库是 `CREATE TABLE IF NOT EXISTS`，不会给旧库自动加列。必须：

1. 用 `PRAGMA table_info(memories)` 检查 `dedupe_hash`。
2. 缺失时执行 `ALTER TABLE memories ADD COLUMN dedupe_hash TEXT`。
3. 为存量行回填 `dedupe_hash`。
4. 建立非唯一索引 `(type, dedupe_hash)`；不要用唯一约束把历史归档重复行卡死。
5. 迁移失败不得静默降级为“永远不去重”；至少 warning，并在测试里覆盖“旧库无列 → 启动后有列且有值”。

### 4.5 命中优先级

1. 先做同名匹配；同名更新仍是最高优先级。
2. 同名未命中时，按 `type + dedupe_hash` 查。
3. 多条命中：有效行优先；否则最近更新时间优先。
4. 命中有效行：更新内容到既有 id，不改 name（跨名去重时保留首个名称），并返回既有 id。
5. 命中归档行：复活原行，保留原 id。
6. 必须保留旧 `content_hash` 的更新语义。

### 4.6 必测

1. 同 type、同 content、不同 name → 第二次返回第一次 id，`stats().total` 不变。
2. 同 content、不同 type → 不去重，仍新增。
3. 大小写/连续空白经规范化后相同 → 去重。
4. 命中归档行 → 复活原行，not create new。
5. 旧库无 `dedupe_hash` 列 → 打开后迁移成功，存量行 hash 非空。
6. 同 dedupe 两条历史行 → 选择规则稳定，不随机。

### 4.7 命令

```powershell
npx vitest run tests/desktop/memory-store-v2.test.ts tests/desktop/memory-governance.test.ts
$env:NODE_OPTIONS="--max-old-space-size=8192"
npm run typecheck
```

### 4.8 完成判据

- 旧库迁移可重复执行，第二次无副作用。
- `dedupe_hash` 回填正确。
- HTML/大小写/空白规范化与旧 contentHash 使用同一 normalization helper。
- 归档复活与 M10-5 语义一致。

### 4.9 建议提交


## 5. M10-7.3 · 容量上限与确定性淘汰

> **状态：DONE（2026-10-25）**
> 提交：`af608ab fix(memory): 增加容量上限与确定性软归档`
> 验收：三文件 71/71、M10-7.3 专项 12/12、typecheck EXIT=0。
> 覆盖：新建与归档复活容量治理、project→user 淘汰、pinned 保护、全 pinned 拒绝、SQL/fallback 同口径、同数据集确定性。

### 5.1 目标

新增导出常量 `MAX_MEMORIES=500`。有效记忆超限时，软归档确定性选出的最旧行，确保 `stats().valid <= MAX_MEMORIES`。

### 5.2 改动文件

- `src/host/memory-store.ts`
- `tests/desktop/memory-governance.test.ts`

### 5.3 淘汰顺序

严格按以下优先级：

1. `pinned=true`：永不淘汰。
2. `type=project` 且非 pinned：先淘汰。
3. `type=user` 且非 pinned：仍超限时才淘汰。
4. 同级按 `updatedAt ASC`。
5. `updatedAt` 相同按 `createdAt ASC`。
6. 再相同按 `id ASC`，保证确定性。

### 5.4 行为约束

1. 使用 `invalid_at` 软归档，不 hard delete。
2. 同名更新不增加有效行数，不应触发无意义淘汰。
3. 新插入导致超限：先选出待淘汰行，再完成本次插入，最终 `valid <= MAX`。
4. 归档行复活导致超限：同样执行容量治理。
5. 若超限但所有候选都 pinned / 不可淘汰：返回结构化 `ok:false`，本次 save 不落地。
6. SQL 与 fallback 用同一排序规则。
7. 不修改 `MemoryStoreV2` 契约签名。

### 5.5 必测

1. `MAX_MEMORIES` 正确导出且为 500。
2. 灌入 `MAX+5` 后 `stats().valid === MAX`。
3. 被淘汰对象是最旧 project 非 pinned。
4. project 不足时淘汰最旧 user 非 pinned。
5. pinned 在任何顺序下都不被淘汰。
6. 全部 pinned、有效数已超限时，新增返回明确错误且行数不变。
7. 淘汰为归档，`invalidated` 增加而非 `total` 减少。
8. fallback 路径至少覆盖淘汰顺序 helper。

### 5.6 命令

```powershell
npx vitest run tests/desktop/memory-store-v2.test.ts tests/desktop/memory-governance.test.ts tests/desktop/memory-archive-lifecycle.test.ts
$env:NODE_OPTIONS="--max-old-space-size=8192"
npm run typecheck
```

### 5.7 完成判据

- 容量逻辑不依赖插入偶然顺序。
- 错误不抛未捕获异常。
- 不破坏 M10-5 的归档/恢复。
- 与 M10-7.2 去重叠加时，先去重再判容量。

**现象**：`tests/desktop/bot-chat-room-store.test.ts > 降级模式按 throughMessageId 范围正确`
断言 `expected ['2','1'] to deeply equal ['1']`。

**根因**（PM 复核）：未提交的 `clampTimestamp()` 把显式 `timestamp` 强拉到 `Math.max(requested, now, maxSeenTs)`，
测试里 `timestamp: 1 / 2` 双双被钳成同一毫秒值。`loadRoom()` 排序键是 `timestamp ASC, id ASC`，
而 `generateMessageId()` 的 6 位随机后缀使同毫秒内的 `id ASC` 等于抛硬币，
`throughMessageId = m1.id` 就有一半概率落在索引 1，`slice(0, idx+1)` 遂返回两条。

**实测量化**（vitest 2.1.9，node 24.14.0）：

- HEAD（`6090ce2`，不含该改动）：该文件 6/6 轮确定性通过。
- 含脏改动的工作树：同一文件 12 轮里 9 轮失败。
- 定向探针（200 轮）：`timestamp` 相同 200/200，`throughMessageId` 结果错误 **102/200（51%）**。
- 该注释自称「尊重显式传入（测试/回放需要）」，实际并未尊重——注释与实现相反，需一并更正。

**修复方向**（供归属方选择，不预设结论）：

1. 显式传入的 `timestamp` 原样保留，只对缺省值做钳制；或
2. 排序兜底不用随机 `id`，改用单调插入序（如自增 `seq`）；或
3. 两条都做——`throughMessageId` 语义依赖稳定顺序，随机后缀本就不该参与排序兜底。

**验收**：修后该文件连续 12 轮 0 失败；`bot-chat-room-store` 与 `bot-round-orchestrator` 专项全绿；typecheck EXIT=0。

### 13.2 D-5（P0）· 同名保存清空 `tags` / `pinned`

> **状态：DONE（2026-10-26）**
> 提交：`f985766 fix(memory): 记忆工具边界不再把未传当成显式清空`
> 验收：9 文件 159/159；typecheck EXIT=0；`entry.js` 已重建至 370,567 B（产物未随本次提交，见 §15）。
> 新增 `tests/desktop/memory-tool-boundary.test.ts` 7 条：完整链保字段、显式清空负控、目录文案两处。
> 另修正两条把旧缺陷契约写死的既有用例（`memory-governance` 的"只转发 4 字段"、`v09` 的"缺省 tags 必须为 []"）。

**真机读数**：

- 先存 `{tags:["a","b"], pinned:true}`，再同名只改 content、不传 tags/pinned → 落库变成 `pinned=0`、`tags_json=[]`。
- 首次创建就显式传 `pinned:true`，落库同样是 `pinned=0`（探针 C 证实）。

**三层根因**（缺任何一层都不会出事）：

| 层 | 位置 | 行为 |
|---|---|---|
| ① 目录 | `src/inject/main-world-interceptor.ts` 的 `TOOL_CATALOG_TEXT` | `memory_save` 参数只写 `type/name/content/tags(可选)`，**`pinned` 从未告诉模型** |
| ② 适配 | `src/shared/tool-contract.ts:97-105` | `adapt` 只转发 `type/name/content/tags`，**`pinned` 直接丢弃**；`tags` 缺省被填成 `[]` |
| ③ 宿主 | `src/host/desktop-host.ts` 的 `memory.save` | `pinned: Boolean(params.pinned)`、`tags: Array.isArray(...) ? ... : []`，把缺省固化成显式值 |

落到 `memory-store.mergeUpdateGovernance()` 时，`params.tags ?? existing.tags` 里的 `[]` 不是 nullish，
于是「未传」被当成「显式清空」。**16 条单测直连 `store.save()`，正好绕过 ①②③，所以全绿。**

**修复方向**（三层一起改，少一层都会复现）：

1. `TOOL_CATALOG_TEXT` 与 `TOOL_CAPABILITY_PROMPT` 的 `memory_save` 参数补齐 `pinned`（可选，布尔）。
2. `tool-contract.ts` 的 `memory_save.adapt`：`pinned` 仅在传入布尔值时转发；`tags` 仅在传入数组时转发，
   缺省时**不要生成该 key**（不要填 `[]`）。
3. `desktop-host.ts` 的 `memory.save`：同样采用「有则转、无则不传」，不把缺省固化成 `false` / `[]`。
4. 补一条**走完整工具链**的回归腿（`adapt` → handler → `store.save`），不能只测 store。

**验收判据**：真机复跑同一条探针序列，1.3 必须得到 `pinned=1`、`tags_json=["a","b"]`；
另加负控——显式传 `tags:[]` / `pinned:false` 仍然要能清空，证明没有把显式覆盖一起废掉。

### 13.3 D-6 · ~~记忆工具面缺失~~（**已撤回：设计如此，不是缺陷**）

上一版把 `memory.list / delete / listArchived / unarchive / purge` 不在模型侧判成缺陷，**判错了**。
复核 `src/shared/tool-contract.ts:132-164`：这五个键全部位于 `UI_ONLY_TOOLS`，
注释写明「收录原则：把宿主已登记的能力投影给模型；不含任何改变宿主配置/安全档位的 RPC」，
且 `SUPPORTED_INVOCATION_NAMES` 只喂 `MODEL_INVOCATION_TOOLS`，权限面在此处是**故意分开**的。

所以：

- 删除 / 彻底删除 / 恢复 / 列表属于**人工在面板操作**，模型不可达是安全设计，不得改。
- 2026-10-26 验收报告里「阶段 3 未验证」是**预期结果**，不是缺陷——
