### ★Q2 分支
路线图 §4 说「继续 feat/bot-data，或切 feat/bot-chat，你定」。我倾向**继续 feat/bot-data**（数据层统一在一支，review/合流更顺）。你认可吗？还是希望数据层拆成独立 `feat/bot-chat`？

### ★Q3 DB 连接复用方式（单 db 文件约束）
路线图 §2.6 注1：「复用记忆层 v2 的 SQLite 连接，不另开 db，新增表即可」——避免两个 DatabaseSync 连同一文件导致锁问题。
- 我的方案 A（推荐，改动最小）：在 `MemoryStore` 增加 `getDb(): DatabaseSync | null` + `isInMemoryFallback(): boolean`，ChatMessageStore 构造时传入 MemoryStore，复用**同一个**连接并在其上 `CREATE TABLE IF NOT EXISTS chat_messages / chat_snapshots / chat_summaries`。降级模式下双方各自内存数组。
- 方案 B：抽一个共享单例 `bot-db.ts`，MemoryStore 和聊天室存储都从它取连接（重构已交付的 MemoryStore，风险略高）。
- 请你选 A 还是 B；如果选 A，加 `getDb()` 这种非破坏性扩展你 OK 吗？

### ★Q4 ContextEngine 的「压缩摘要」怎么做（影响测试设计）
测试 #15 需要观察「第二次 buildContext 不重算已摘要部分」。摘要本身要调模型。
- 我的方案：ContextEngine 注入一个 `summarizer: (messages) => Promise<string>` 回调，v0.26 用**桩/计数器**（测试观察调用次数与传入消息范围），真实模型摘要由你 v0.27 接（agent-prompt.ts / buildAgentInstructions）。
- 是否认可「v0.26 只建结构+锁+CAS，摘要器留桩」？还是你希望 v0.26 就接现有 ModelEngine 做真摘要（会触碰引擎层，耦合面变大）？

### Q5 buildContext 返回的 systemPrompt 形态

### Q6 字段语义对齐 Ekko（避免返工）
我按 Ekko 报告拟的本地类型草稿，请确认或纠偏：
- `ChatMessage`: `{ id, roomId, senderId, senderType: 'user'|'main-bot'|'sub-bot', content, timestamp, mentions: StructuredMention[] }`
- `StructuredMention`: `{ type: 'all' | 'agent', participantId?: string }`（`@all` → type:'all'；`@前端专家` → type:'agent', participantId:'前端专家'）

- 这些字段名/枚举是否与你后续 types.ts 一致？尤其 `senderType` 三态枚举。
