## ★Q2 maxDepth 语义：波数 ✅（你的理解正确）

你要的是**波数**，不是跳数。逐条对齐：

- `maxDepth:1`（默认）→ 只跑第 0 波（路由 targets）。第 0 波回复里解析出的接力目标**不执行**，直接进 `pendingHandoff`。验收示例 `@前端专家 → pendingHandoff=['backend-expert']` 正是这个语义。✅
- `maxDepth:2` → 追加执行第 1 波（pendingHandoff 里的人真的回），第 1 波再解析出的接力进 `pendingHandoff`。
- 防环：A→B→A→B 在 `maxDepth:1` 下天然不发生（第 0 波的接力不执行）；`maxDepth:2` 时靠「本轮已出现过的人不再进 pendingHandoff」截断。

**验收对齐**：你的任务#7「构造互相 @ 的两人设，断言 pendingHandoff 不再增长」——在 `maxDepth:1` 下，pendingHandoff 永远只含第 0 波解析出的目标（不会再增长，因为不执行）；在 `maxDepth:2` 下，第 1 波执行后，A 解析出 B 但 B 已在本轮出现过 → 不加。两种都测更稳，但 `maxDepth:1` 的断言是底线。

## ★Q3 两轮编排怎么驱动？→ 连续调两次 planRound ✅，不加 planFollowUp

### ① 保持 planRound 为最小集 ✅

认可。`planRound` 契约不变，不加 `seed`/`pendingHandoff` 入参。两轮 = 调用方连续调两次 `planRound`，第 2 轮用一个能路由到 B 的 trigger。

### ② 不加 planFollowUp

不需要。原因：第 2 轮的 trigger 是什么、要不要跑、跑多深，这些都是**接线层的策略决策**（我 v0.27 做），不是编排器的算法职责。编排器只管「给我一个 trigger + 房间 + 参与者，我产出这一轮的编排」。把续轮策略塞进编排器会让它从纯算法变成有状态的调度器，破坏「无副作用」边界。

任务#6 的两轮单测：你连续调两次 `planRound`，第 2 轮的 trigger 是你构造的一条「@后端专家」消息（净内容），断言第 2 轮的 targets/members 含 backend-expert。这能验证「接力目标在第 2 轮被路由命中」，不需要编排器自己续轮。

## Q4 HandoffParser 净内容剥离范围 → 改：未注册 @名保留在净内容

你的默认是「剥离所有 @标记（含未注册名和 @all）」。我要求改：**未注册的 @名保留在净内容里，只剥离已注册的 @名和 @all。**

理由（我读了你的 `findMentions` 实现，L49-102）：

`findMentions` 只匹配 `participants` 里列出的名字——一个拼错的 `@typo-name` 不在 participants 列表里，`findMentions` 返回的 `RawMention[]` 根本不含它，`stripMentionTokens` 也就**不会剥离它**。所以你的 `DefaultMentionParser.stripMentionTokens` 现状就是「未注册 @名保留」的行为。

如果 HandoffParser 另起一套剥离逻辑把所有 @ 都吃掉，会跟 MentionParser 的行为不一致——同一个 @名 在两个地方得到不同处理，调试时极难追。所以：

- **净内容 = 用 `MentionParser.stripMentionTokens` 产出**（复用，不另写）。已注册 @名 + @all 被剥离；未注册 @名原样保留。
- **unresolved = HandoffParser 自己识别的未注册 @名**（它需要 `extractMentionRanges` 来定位「这个 @ 后面跟了什么字符」，但不在净内容里动它们）。

这样净内容里用户能看到 `@typo-name` 原文，知道拼错了；`unresolved` 里调用方能告警。两边职责清晰：MentionParser 管剥离，HandoffParser 管接力识别 + 未注册上报。

**你提的 mention-parser 附加导出 `extractMentionRanges`/`stripRanges`**：认可，非破坏附加。但注意——HandoffParser 如果用 `stripMentionTokens` 产净内容，可能不需要 `stripRanges`（MentionParser 已经会剥离已注册的）。`extractMentionRanges` 倒是真需要（用来识别未注册 @名进 unresolved）。你按实际需要加，能少加就少加。

## Q6 ParticipantResolver.has 语义 → 认可，但 all 的语义要收紧

你的默认：
- `has(name, room) = room.memberPersonas.includes(name)`（只看房间配置，不管注册）✅
- `resolve` 要求「在房 + 已注册」否则 undefined ✅
- `all` 按 memberPersonas 顺序返回**已注册**成员

前两条认可。第三条收紧：**`all` 返回已注册成员**——但如果一个房间配置了 5 个成员、只注册了 3 个，`all` 只返回 3 个。这会让 MentionRouter 的 @all 路由只唤醒 3 个而非 5 个。

这是对的（没注册的 bot 唤不醒，强行唤醒也只是空转），但要在代码注释里写明：**`all` 的返回是「当前可唤醒的成员子集」，不是「房间配置的完整成员表」**。房间配置完整成员表从 `room.memberPersonas` 取。MentionRouter 做 @all 路由时用 `participantResolver.all(room)`（已注册子集），而非 `room.memberPersonas`（配置全集）。
