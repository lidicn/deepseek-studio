## 二、契约一致性（重点：签名与返回语义 1:1 对齐）

`FileReportStore implements ReportStore`（`src/host/bot/types.ts` L536-549，TS 编译期强制一致）。与 `InMemoryReportStore` 逐方法对照：

| 方法 | 契约签名 | InMemory（桩）返回 | FileReportStore（FS）返回 | 是否一致 |
|---|---|---|---|---|
| `ensureBatchDir` | `(batchId: string) => string` | `memory://runs/<batchId>` | `<runsDir>/<batchId>`（绝对路径，mkdir -p） | 语义一致（都是"批次目录路径"） |
| `appendTranscript` | `(batchId, slotId, event: unknown) => void` | Map 数组 push | `appendFileSync` 追加**一行 jsonl** | 一致（均按序追加） |
| `writeSubReport` | `(batchId, slotId, report: SubBotReport) => void` | Map set（覆盖） | 写 `.tmp` + `renameSync`（原子覆盖） | 一致（均覆盖非追加） |
| `readSubReports` | `(batchId: string) => SubBotReport[]` | 插入顺序 | **按文件名排序**（见下方"有意差异"） | 数组形状一致 |
| `writeMergedReport` | `(batchId, content: string) => string` | `memory://runs/<batchId>/summary.md` | `<runsDir>/<batchId>/summary.md` | 一致 |
| `getMergedReportPath` | `(batchId: string) => string` | 有则路径 / 无则 `''` | 有则路径 / 无则 `''` | **完全一致** |

`SubBotReport` 全部字段（`slotId` / `dimension` / `summary` / `findings` / `evidenceRefs` / `transcriptPath`）经 JSON 往返后 `toEqual` 严格相等，已被单测锁死 → 你的 `report-merge.ts`（消费 `findings` / `evidenceRefs` / `transcriptPath`）无需任何改动。

### 一处有意差异（唯一）：`readSubReports` 的排序

- 桩版返回 **Map 插入顺序**；FS 版按**文件名（`<slotId>.report.json`）字典序**排序。
- 理由：`readdirSync` 顺序随文件系统变化，而 `mergeReports` 的去重是"首次出现者胜" + severity 稳定排序——不定序会导致同一批审计每次合并结果可能不同。定序是正确性需求，不是风格偏好。
- 影响面：`FileReportStore` 目前只在 `desktop-host.ts` 生产接线处替换；现有单测全部基于桩版，**无测试受影响**。若你后续把某条测试切到 FS 版，请把断言写成"按 slotId 升序"而非"按写入顺序"。

## 三、落盘布局

```
<runsDir>/                              # = <configDir>/runs
└── <batchId>/                          # 一批审计，batchId 当不透明字符串（不 parse）
    ├── <slotId>.jsonl                  # 逐事件转录：appendFileSync 每行一个 JSON（非单 JSON 数组）
    ├── <slotId>.report.json            # 结构化子报告：JSON.stringify(report, null, 2)，原子写
    └── summary.md                      # 综合报告：writeMergedReport 产物
```

依据设计稿 `设计稿-Bot编排-账号槽位人设三层解耦-20261014.md:161`——**纯 FS，不进 SQLite**（转录是高频追加流，SQLite 不合适）。

## 五、工程决策（供你 review）

1. **全同步 fs API**（`mkdirSync`/`appendFileSync`/`writeFileSync`/`renameSync`/`readdirSync`/`readFileSync`/`existsSync`）。
   原因：`ReportStore` 六个方法签名全是同步（返回 `string`/`void`，非 `Promise`），换 async 会破坏你已锁定的契约。单进程 Node 宿主下同步写安全。
2. **原子写**：`.tmp` + `renameSync`，对齐既有 `src/host/file-storage-backend.ts:46-48` 的成熟做法，防读到半截 JSON。
3. **路径穿越防护**：`assertSafeSegment` 拒绝空串 / `.` / `..` / 含 `/` `\` 的 `batchId` 与 `slotId`，六个入口全部校验。`batchId` 由你生成（`batch-<base36>-<rand>`）本不该出问题，但畸形输入写穿目录的代价太高，防御成本近乎为零。
4. **坏文件不抛**：`readSubReports` 遇到解析失败的 `.report.json` 会 `console.warn` 跳过并继续。单个槽报告损坏不该让整批 merge 崩掉——审计产物的可用性优先于严格性。
5. **兜底建目录**：`appendTranscript` / `writeSubReport` 内部都调 `ensureBatchDir`（`mkdirSync recursive` 幂等）。理论上你的 offline-runner 已建过目录，这是防御性兜底，成本可忽略。
6. **零新依赖**：只用 `node:fs` / `node:path` / `node:os`。
