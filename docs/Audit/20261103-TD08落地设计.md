## 一、接口设计

### 1.1 签名（`src/host/workspace.ts`）

```ts
// WorkspaceContext 接口（现 :52 附近）追加：
export interface WorkspaceContext {
  root: string;
  contains(target: string): boolean;
  resolveWithin(target: string): string | null;          // 现状语义：允许目标不存在（新建文件）
  /** TD-08（20261103 PM 裁决 4）：目标必须真实存在（含符号链接 realpath 后仍在区内）。 */
  resolveWithinExisting(target: string): string | null;
}
```

### 1.2 与现有 `resolveWithin` 的关系：**包一层，不加参数、不改默认**

```ts
// createWorkspace 返回对象（现 :190-198）：
return {
  root: rootAbs,
  contains: containsRaw,
  resolveWithin(target) {                                   // ← 语义一字不动
    const abs = resolveTarget(target);
    return containsRaw(abs) ? abs : null;
  },
  resolveWithinExisting(target) {                           // ← 新增：包一层
    const abs = this.resolveWithin(target);
    if (abs === null) return null;
    return existsSync(abs) ? abs : null;                    // existsSync 跟随 realpath（abs 已解符号链接）
  },
};
```

- **为什么是包一层而不是加参数**：`resolveWithin(target, {existing})` 会改接口形状，且 `MutableWorkspaceContext`（`:230`）与 `policy.test.ts:78`（显式断言"不存在但落在区内 → 允许"，即新建文件语义）都锁着现签名。包一层 = 默认语义零风险，`policy.test.ts:78` 原样保持绿。
- **为什么不用 statSyncSafe**：`existsSync` 已足够（abs 是 realpath 后的绝对路径）；与 `desktop-host.ts:1365` 的 `statSyncSafe` 是两种场景，不混用。
- **MutableWorkspaceContext 代理**（`:230-232`）加同名透传：`resolveWithinExisting(target) { return inner ? inner.resolveWithinExisting(target) : null; }`。

## 二、`file.ts:48` 共用解析按操作分流（伪代码）

`file.ts` 的 `target()`（`:40-51`）被 file.read / file.list / file.stat / file.write 四个操作共用。**按操作分流，不是全改**：

```ts
// createFileCapability(id, options) —— id 就是操作名，顺手可用
type FileOp = 'read' | 'list' | 'stat' | 'write';

const target = (
  params: Record<string, unknown>,
  ctx?: CapabilityContext,
  op: FileOp,                                   // ← execute 里把 id 尾段传进来
): string | null => {
  const raw = firstString(params, ['path', 'filePath', 'target']);
  if (!raw) return null;
  if (!workspace || !isWorkspaceConfigured(workspace)) return null;

  // TD-08 分流（20261103 设计）：
  //   list        → resolveWithinExisting：目录必须存在（不存在报 target-not-found，
  //                 而不是现在的 readdir ENOENT → 泛化 io-error）
  //   read/stat   → 保持 resolveWithin：缺文件已由后续 FS 操作捕获
  //                 （read: :116 fsp.open ENOENT → io-error，capabilities-shell.test.ts:357-359
  //                  断言该标签；stat: :93-95 自带 ENOENT → 'not-found'，标签已准确）
  //   write       → 保持 resolveWithin：新建文件是合法语义（绝不能走 Existing）
  const within = op === 'list'
    ? workspace.resolveWithinExisting(raw)
    : workspace.resolveWithin(raw);

  if (within) return within;
  return ctx?.allowOutsideWorkspace === true ? path.resolve(raw) : null;
};
```

**对 §六 调用点分类的一处修正**（比早前"read/list 整体 Existing"更细，以此为准）：

| 操作 | 走哪个 | 理由 |
|---|---|---|
| file.list | **Existing** | 目录不存在是必然失败，且现在只报泛化 `io-error`；改后报 `target-not-found` |
| file.read | **保持原语义** | 缺文件已被 `fsp.open` 的 ENOENT 捕获（`:116`→`:148` io-error），走 Existing 只会改错误标签并**破坏 `capabilities-shell.test.ts:357-359`**（断言 `io-error`），无安全增益。标签要不要改 `not-found` 是另一张小卡，不混入 |
| file.stat | **保持原语义** | `:93-95` 已按 ENOENT 报 `not-found`（若走 Existing 反而把"区内但不存在"误报成 `outside-workspace`） |
| file.write | **保持原语义** | 新建文件是核心语义 |

**判定原则（复述）**：目标"不存在即操作必然失败且当前无 FS 调用兜底"→ Existing；"缺文件已被后续 FS 操作以准确错误捕获"或"不存在是合法输入"→ 原语义。
