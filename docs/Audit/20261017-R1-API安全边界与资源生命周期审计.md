## 3. 逐条发现

### R1-01 [P1] /v1/debug/eval 完全跳过鉴权

**证据** src/api/server.ts:267-272

    if (pathname === '/v1/debug/eval') {
      // 跳过鉴权，直接处理
    } else if (!auth.authenticate(req.headers['authorization'])) {
      sendJson(401, { error: { code: 'unauthorized', message: 'missing or invalid bearer token' } });
      return;
    }

真正的处理器在 server.ts:341（if pathname === '/v1/debug/eval' && method === 'POST'），调用 options.debugEval(code)，该委托最终在 chat.deepseek.com 页面上下文执行任意 JS。鉴权声明在 165 行（const auth = ...），首个使用在 269 行——豁免分支位于两者之间，等价于全局后门。

**后果** 本机任意进程（其他用户态程序、恶意脚本、被入侵的本地服务）无需令牌即可 POST 到 127.0.0.1:port/v1/debug/eval，在已登录的 DeepSeek 页面执行任意 JS：读 localStorage / 会话凭证、以用户身份发起上游请求、篡改宿主行为、绕过工具授权。CORS 的 fail-closed 只约束浏览器读取响应，不约束本机进程发起请求，因此它不是本问题的防线。注释「调试端点免鉴权（本地回环）」把「回环」误当安全边界——回环只说明同机，不说明可信。

**建议** 删除该豁免，与其余 /v1 端点走统一鉴权；确需调试时用环境变量 STUDIO_DEBUG=1 显式开启，且开启后仍校验 Bearer。

**状态** Verified

### R1-02 [P2] 工作区相对路径以进程 cwd 为基准

**证据** src/host/workspace.ts

    const defaultDeps = { resolve: (p) => path.resolve(p), ... };
    function containsRaw(target) { const abs = d.resolve(target); ... }

path.resolve 对相对路径以 process.cwd() 为基准，而不是 workspace.root。src/capabilities/file.ts 的 target() 同样 return path.resolve(raw)。而 workspace.ts 接口注释承诺「resolveWithin 解析出绝对路径；仅当确实在工作区内才返回」。

**后果** 同一个工具调用的语义随宿主启动目录变化：cwd 落在工作区内时相对路径可用且指向 cwd 下文件；cwd 在工作区外时直接判 outside-workspace 失败。用户观察到的是「有时能读、有时越界」，且成功时实际打开的文件与用户以为的「工作区相对路径」不一致（写入可能落到非预期位置）。属于可用性与语义缺陷，不构成越界绕过（校验所用 abs 与实际使用的 abs 是同一值）。

**建议** 相对路径统一 path.resolve(workspace.root, target)；contains 前先归一化到 root 基准；补单测覆盖 cwd ≠ root 的场景。

**状态** Verified

### R1-03 [P1] shell 超时只 kill 直接子进程，且先 resolve 后等 close

**证据** src/capabilities/shell.ts:260-267

    const timer = setTimeout(() => {
      try { child.kill(); } catch { /* 已经退出：忽略 */ }
      finish({ ok: false, error: 'timeout', data: { ...common(), timeoutMs } });
    }, timeoutMs);

finish() 立即 resolve，不等 close 事件；Windows 下 child.kill() 默认只终止直接子进程，powershell -Command 派生的孙进程（git / node / python 等）不在终止范围内。

**后果** ①超时返回后子进程仍在运行，持续占用 CPU、句柄与文件锁，反复超时会累积孤儿进程，直到宿主卡顿或出现写文件冲突（慢性稳定性风险）；②resolve 早于 close，common() 读取的 child.exitCode / signalCode 仍为 null，调用方拿到「exitCode=null + signal=null」的超时结果，与非零退出无法用同一字段区分；③超时瞬间的 stdout 尾部可能丢失。

**建议** Windows 用 taskkill /PID <pid> /T /F 终止进程树；finish 改由 close 事件驱动（kill 后加兜底定时器防止 close 不来）；timeout 分支显式置 timedOut 标志而非复用 exitCode。

**状态** Verified（代码路径已确认）；孤儿进程累积规模需运行时复现量化

### R1-04 [P2] 流式 SSE 未处理客户端断开，上游生成不中止

**证据** src/api/server.ts 流式分支

    for await (const c of options.backend.chatCompletion(request)) {
      res.write(formatSSE(c));
    }
    ... catch (err) { ok = false; res.write(formatSSE(errorChunk(String(err)))); }
    finally { res.end(); release(ok); }

全程未监听 req.on('close')，也未把 AbortSignal 传入 backend.chatCompletion。

**后果** 客户端中途断开（关页面 / 断网）时，res.write 抛 ERR_STREAM_DESTROYED，catch 内再次 res.write 会二次抛错并冒泡到外层 catch，对已结束的响应 sendJson 触发 write after end；同时 for await 不被中断，上游继续生成到自然结束，白耗配额，并占住 maxConcurrent=1 的唯一并发位，后续请求全部 429（concurrency_limited）。

**建议** const ac = new AbortController(); req.on('close', () => ac.abort())；backend.chatCompletion 接收 signal；所有 res.write 前判 res.writableEnded。

**状态** Verified

### R1-05 [P2] MCP stdio 在进程缺失时空转 30s

**证据** src/host/mcp-controller.ts:318-320

    try { conn.process?.stdin?.write(JSON.stringify(msg) + '
'); }
    catch (e) { conn.pendingRequests.delete(id); clearTimeout(timer); reject(...); }

可选链使 process 为 undefined 时不抛错、不写入，promise 只能等 313 行的 30s 定时器超时。proc.on('exit') 会从 connections 删除该 server，但持有旧 conn 引用的调用方仍会走到这里。

**后果** 每次 MCP 工具调用固定挂起 30s；工具循环串行执行时表现为整轮对话「无响应」，用户侧只看到卡住，日志里只有一条 timed out。

**建议** 写入前显式判 if (!conn.process?.stdin) reject(new Error('MCP server not running'))；exit 时标记 conn.closed，后续请求快速失败。

**状态** Verified

### R1-06 [P3] queued 计数永不增长，排队指标恒为 0

**证据** src/api/server.ts 并发闸门

    if (active >= maxConcurrent) { res.setHeader('Retry-After', '1'); sendJson(429, ...); return; }
    ... queued += 1; active += 1;
    const entry = pushRecent({ startedAt: Date.now(), waitMs: 0 });
    entry.waitMs = Date.now() - enqueuedAt;

并发超限时直接 429 拒绝，不存在排队；queued 只在通过闸门后自增并立刻被 active 覆盖；waitMs 在同一 tick 内计算，恒约 0。

**后果** 注释声称要区分「卡在排队」与「跑得慢」，但实现既无排队也无等待时长，/v1/queue/status 的 depth 与 avgWaitMs 恒为 0，排障时无法区分限流拒绝与执行缓慢。

**建议** 要么实现真正的等待队列，要么把字段改名为 rejectedByConcurrency 并如实反映语义。

**状态** Verified

### R1-07 [P3] 文件头注释与实现矛盾

**证据** src/api/server.ts:10 注释「鉴权缺失/错误 → 401（fail-closed）」；实现中免鉴权端点除 /v1/debug/eval 外还有 /healthz（230 行）、/agent 与 /agent.js 与 /agent.css（239-258 行），注释均未提及。

**后果** 读者据注释建立错误的安全模型；后续维护者可能认为所有 /v1 均已受保护而继续添加免鉴权分支。

**建议** 注释列出全部免鉴权端点及理由，或改为引用一处集中常量清单。

**状态** Verified

### R1-08 [P3] finish() 与 close 竞态导致 exitCode 语义不稳

**证据** 同 R1-03 的 finish 提前 resolve；common() 读取 child.exitCode / child.signalCode；close 回调另行用 code ?? (signal ? -1 : 0) 计算 exitCode，两处语义不一致（close 分支覆盖 data.exitCode，timeout 分支不覆盖）。

**后果** 超时结果里 exitCode=null，「非零退出」与「超时」在日志中无法用同一字段区分。

**建议** 统一由 close 产出 exitCode；timeout 分支显式置 exitCode=null 并加 timedOut: true。

**状态** Verified

## 8. 结论

本轮在 api / capabilities / mcp 三处发现 2 项 P1、3 项 P2、3 项 P3。

最需要立即处理的是 **R1-01**：调试端点的鉴权豁免把「本地回环」当成信任边界，而本机任意进程都能访问回环，等价于把页面 JS 执行权开放给本机所有程序——这是本轮唯一的安全绕过项。

**R1-03** 的孤儿进程问题会随使用时长累积，属于慢性稳定性风险，单次不致命但长期会拖垮宿主。

**R1-04** 与 **R1-05** 都是「挂住」类缺陷：前者占住唯一并发位，后者让工具调用空等 30s，用户侧表现均为无响应，但根因分属两个子系统。

**R1-02** 是文档承诺与实现不一致导致的可用性问题，不影响边界安全（校验路径与实际使用路径一致，fail-closed 成立）。

三条收敛判据均未满足，本轮不宣称收敛。
