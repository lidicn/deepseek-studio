## 1 关键事实：这条文案不是 studio 写的

对 src / tools / public / scripts 全量扫描（含 .ts/.js/.mjs/.cjs/.json/.html/.css）：

```
Select-String -Pattern '服务器暂时不可用|暂时不可用|服务不可用|503|Service Unavailable'
→ stdout 为空（0 命中）
```

**推论**：这句中文提示来自 DeepSeek 网页端在收到服务端错误后的 UI 渲染，或由服务端错误体直接透出。studio 既没有定义它，**也没有任何代码去识别它**——这才是问题所在。

## 2 对话开始阶段的真实请求链

```
用户点「发送」
  └─ 页面 XHR  POST /api/v0/chat/create_pow_challenge   （取 PoW 挑战）
  └─ 页面 XHR  POST /api/v0/chat/create_pow_challenge   （target=/api/v0/file/upload_file，另一路）
  └─ 页面 XHR  POST /api/v0/chat/completion             ← studio 在此拦截并改写 body
        ├─ [注入] TOOL_CAPABILITY_PROMPT（约 2000 字符）
        ├─ [注入] ## 已有记忆（最多 50 条，全文无截断）
        ├─ [注入] 上一轮工具结果 block（若有）
        └─ 发往服务端
  └─ 服务端返回错误（HTTP 200 但错误体 / 或 5xx / 或 断连）
        └─ 页面渲染：「服务器暂时不可用」
        └─ studio 拦截器：解析不到 v 字段 → 认为本轮无内容 → 继续 nudge / auto-continue
```

对话**开始**阶段之所以高发，是因为它同时承担了三件事：建会话、算 PoW、发首个 prompt。其中任意一环失败都会表现为同一条文案，而 studio 对三者**都没有区分能力**。

## 3 逐条根因取证

### R2（主因）失败被当成空回复，触发 25×8 的重试正反馈环

**代码位置**：`src/shared/continuation-prompt.ts:45,47`

```ts
export const MAX_LOOP = 25;
export const MAX_NUDGES = 8;
```

**失败路径**（`src/inject/main-world-interceptor.ts`）：

| 环节 | 行号 | 行为 |
|---|---|---|
| 收到响应 | 560-575 | `xhr.readyState >= 3` 时按字节偏移切增量，喂给 `SseTextStreamExtractor` |
| 提取文本 | `sse-text-extractor.ts:132-200` | 只认 `v` 为 string / 数组 / `p=response/fragments` 三种形态；**错误帧不匹配任何分支，直接返回空串** |
| 判定本轮 | 900-910 | `autoReplyText` 为空 → `reply` 为空 → 不推送宿主，但**也不报错** |
| 进入重试 | 958-960 | 唯一分支：`if (xhr.status === 429)` 才退避；**其余任何异常状态都直接落到 else 分支** |
| else 分支 | 962-985 | `hadTools=false` 且 `shouldNudge()` 为真 → `autoContinueNudge()`；nudge 用尽后仍未结束 → 循环继续 |
| 结果 | — | 一次真实的服务端失败，被放大为最多 **25 轮 auto-continue**，每轮又可能叠加 nudge，**累计上限 33 次请求** |

**为什么这会让「不可用」变高发**：DeepSeek 对同一会话的连续请求有速率与并发约束。33 次连发几乎必然触发服务端限流或网关拒绝，而拒绝又返回同一条「服务器暂时不可用」文案，被拦截器再次判为空回复——**形成自我维持的故障环**。

> 这是「偶发」升级为「高发」的关键机制，也是本次审计的首要修复目标。

### R3 auto-continue 复用一次性校验头与旧 body

**代码位置**：`main-world-interceptor.ts:886-905`

```ts
// 过滤 capturedHeaders：移除会干扰请求的头
// - content-type / content-length / x-ds-pow-response
for (const [k, v] of Object.entries(capturedHeaders)) {
  const lower = k.toLowerCase();
  if (lower === 'content-type' || lower === 'content-length' || lower === 'x-ds-pow-response') continue;
  filteredHeaders[k] = v;
}
```

**问题**：过滤清单只排除了 3 个头。而从运行日志实测，被捕获并复用的头包含：

```
[interceptor] auto-continue loop=1 computing PoW... capturedHeaders=
["x-device-id","x-device-model","x-client-bundle-id","x-client-platform",
 "x-client-version","x-client-locale","x-client-timezone-offset","authorization",
 "content-type","accept","x-ds-pow-response","x-hif-leim","x-hif-dliq"]
```

| 头 | 是否应复用 | 说明 |
|---|---|---|
| `authorization` | ✅ 应复用 | 会话凭证 |
| `x-device-id` / `x-device-model` | ✅ 应复用 | 设备标识，稳定 |
| `x-client-version` / `platform` / `locale` | ✅ 应复用 | 客户端元信息 |
| `x-client-bundle-id` | ⚠️ 谨慎 | 随构建变化 |
| **`x-hif-leim` / `x-hif-dliq`** | ❌ **不应复用** | 服务端下发的一次性校验/风控令牌，跨请求复用会被判定为重放 |
| **`x-ds-pow-response`** | ❌ 已排除 | 正确，但仅此一项不够 |

**同时**：`bodyStr` 直接取自 `loopState.lastChatBody`（即上一次请求体），仅替换 `prompt` 与 `parent_message_id`。若上游对 `chat_session_id`、`message_id` 有会话级校验，复用旧 body 会再次踩雷。

**PoW 复用**：`pow.ts:createPowChallenge()` 每次重新取 challenge（这点正确），但 challenge 有 `expire_at` / `expire_after` 字段，`pow.ts` 解析了却**从未使用**——若排队等待导致超时，仍会带着过期 challenge 去解，服务端直接拒绝。

### R5 错误分类缺失：全链路只有 429 一条分支

对 `src` 全量搜索错误处理：

```
res.status / response.status / error_msg / errorMsg / code === 的命中：
  mcp-controller.ts:345,628   ← MCP 协议，与对话无关
  sandbox-executor.ts:82      ← ENOENT/ETIMEDOUT，本地沙箱
  main-world-interceptor.ts:958, 1077  ← 仅 xhr.status === 429
```

**缺失的错误分类**：

| 应识别 | 现状 | 后果 |
|---|---|---|
| `xhr.status === 0`（网络中断/CORS/被拦截） | 未处理 | 静默 |
| `xhr.status >= 500` | 未处理 | 静默 |
| HTTP 200 但响应体是错误 JSON（如 `{"code":...,"msg":"服务器暂时不可用"}`） | 未处理 | 静默 |

## 4 解决方案

### P0-1 新增错误分类器（阻断重试正反馈环）

**新建** `src/inject/response-classifier.ts`：

```ts
export type ResponseVerdict =
  | { kind: 'ok' }
  | { kind: 'retryable'; reason: string; retryAfterMs: number }
  | { kind: 'fatal'; reason: string };

const RETRYABLE_HINTS = ['服务器暂时不可用', '服务繁忙', '请稍后重试', 'rate limit', 'overloaded'];
const FATAL_HINTS = ['登录', 'unauthorized', 'forbidden', '违规', '内容不合规'];

export function classifyResponse(status: number, bodyText: string): ResponseVerdict {
  if (status === 0) return { kind: 'retryable', reason: 'network', retryAfterMs: 1500 };
  if (status === 429) return { kind: 'retryable', reason: '429', retryAfterMs: 8000 };
  if (status >= 500) return { kind: 'retryable', reason: `http-${status}`, retryAfterMs: 4000 };

  // HTTP 200 但 body 是错误体：这是本项目的核心盲区
  const probe = bodyText.slice(0, 2000);
  if (FATAL_HINTS.some((h) => probe.includes(h))) {
    return { kind: 'fatal', reason: 'auth-or-policy' };
  }
  if (RETRYABLE_HINTS.some((h) => probe.includes(h))) {
    return { kind: 'retryable', reason: 'body-unavailable', retryAfterMs: 5000 };
  }
  return { kind: 'ok' };
}
```

**接入点 1**：`autoContinueWithPow()` 的 `xhr.onreadystatechange`（约 940 行），把 `if (xhr.status === 429)` 替换为：

```ts
const verdict = classifyResponse(xhr.status, xhr.responseText || '');
if (verdict.kind === 'fatal') {
  d(`auto-continue abort: ${verdict.reason}`);
  onFatalError?.(verdict.reason);   // 上报宿主，UI 显示可读原因
  loopDepth = 0; nudgeCount = 0;
  resolve();
  return;
}
if (verdict.kind === 'retryable' && loopDepth < MAX_LOOP) {
  d(`auto-continue retryable (${verdict.reason}), backoff ${verdict.retryAfterMs}ms`);
  loopState.streamActive = false;
  if (autoContinueTimer) clearTimeout(autoContinueTimer);
  autoContinueTimer = setTimeout(() => { autoContinueTimer = null; autoContinueWithPow(); }, verdict.retryAfterMs);
  resolve();
  return;
}
// ok 才继续原有 hadTools / nudge 判定
```

**接入点 2**：正常用户消息的 `installXhrHooks` / `installFetchHook` 的 `readyState === 4` 分支，同样调用 `classifyResponse`，命中 retryable 时**向 UI 推送明确提示**而不是静默。

### P0-2 收紧重试预算与退避（削弱放大倍数）

`src/shared/continuation-prompt.ts`：

```ts
// 原：MAX_LOOP = 25; MAX_NUDGES = 8;
export const MAX_LOOP = 6;
export const MAX_NUDGES = 2;
```

**理由**：25×8 是为「长任务多轮工具调用」设计的，但它与「错误重试」共用了同一个计数器，导致一次失败能烧掉几十次请求。正确做法是**把「工具续跑轮数」与「错误重试次数」拆成两个独立预算**：

```ts
export const MAX_TOOL_TURNS = 25;   // 工具续跑，保持原值
export const MAX_ERROR_RETRIES = 3; // 错误重试，独立且严格
```

并在重试路径上使用**指数退避 + 抖动**：`1500 → 4000 → 9000` 毫秒，避免 33 次请求在数秒内倾泻。

### P0-3 头复用白名单化（替换黑名单）

把 `main-world-interceptor.ts:893-901` 的「排除 3 个」改为「只保留白名单」：

```ts
const HEADER_ALLOWLIST = new Set([
  'authorization',
  'x-device-id', 'x-device-model',
  'x-client-platform', 'x-client-version',
  'x-client-locale', 'x-client-timezone-offset',
  'accept',
]);
const filteredHeaders: Record<string, string> = {};
for (const [k, v] of Object.entries(capturedHeaders)) {
  if (HEADER_ALLOWLIST.has(k.toLowerCase())) filteredHeaders[k] = v;
}
```

**效果**：`x-hif-leim` / `x-hif-dliq` / `x-ds-pow-response` / `x-client-bundle-id` 自动被排除，不再出现重放判定。白名单比黑名单安全——上游新增一次性头时默认不被复用。

### P0-4 PoW challenge 过期保护

`src/inject/pow.ts` 中 `createPowHeaders()` 计算前增加校验：

```ts
const nowSec = Math.floor(Date.now() / 1000);
const expireAt = challenge.expire_at || (nowSec + (challenge.expire_after || 0));
if (expireAt > 0 && expireAt <= nowSec + 2) {   // 留 2 秒解算余量
  throw new Error(`PoW challenge expired (expire_at=${expireAt}, now=${nowSec})`);
}
```

**并在调用侧**（`autoContinueWithPow`）捕获该错误后**重新取 challenge**，而不是直接放弃本轮。

## 6 验收标准

| # | 验收项 | 判定方法 | 通过标准 |
|---|---|---|---|
| A1 | 错误分类生效 | 构造 500 / status=0 / body 含「服务器暂时不可用」三种响应 | 三者均被识别为 `retryable`，且**不进入 nudge 分支** |
| A2 | 重试次数受控 | 持续返回错误体 | 连续请求数 ≤ 3，间隔符合 1.5s/4s/9s |
| A3 | 一次性头不复用 | 打印 `filteredHeaders` 的 keys | 不含 `x-hif-leim` / `x-hif-dliq` / `x-ds-pow-response` |
| A4 | PoW 过期拦截 | 注入 `expire_at = now - 1` 的假 challenge | 抛出明确错误并重新取 challenge |
| A5 | 首包体积 | 记录 `xhr chat body injected len=` | 首跳增量 ≤ 2500 字符（不含用户原文） |
| A6 | 错误可见 | 触发 retryable | UI 出现重试提示；触发 fatal 时出现可读原因 |
| A7 | 不回归 | `npx vitest run` | 现有 72 个测试全部通过 |

## 8 结论

「服务器暂时不可用」在**对话开始**阶段高发，是**外部诱因**与**内部放大机制**叠加的结果：

1. **外部诱因**：DeepSeek 服务端在会话建立、PoW 校验、首个 token 生成这三处本就最容易失败，返回的文案统一为「服务器暂时不可用」。
2. **内部放大（主因）**：studio 只识别 `status === 429`，对 `status=0`、5xx、HTTP 200 错误体、SSE 错误帧全部失明；失明的后果是「本轮无回复」，于是自动续跑与 nudge 机制把 1 次失败放大成最多 33 次请求，反而把用户推入限流，使偶发故障变成高发故障。
3. **加剧因素**：auto-continue 复用一次性校验头与旧 body；PoW challenge 过期字段未校验；首跳注入约 2000 字符提示词与不设字符上限的记忆块。

**修复顺序建议**：先做 P0-1（错误分类）与 P0-2（预算拆分），这两项合计改动小、收益最大，可直接把故障放大倍数从 33 降到 3；再做 P0-3、P0-4 消除必然失败路径；最后做 P1/P2 提升体验与可观测性。
