# C1-F1 / C1-F2 根因假设（20261031）

- 席位：Core（只读分析，未改源码、未提交）
- 输入：C1-F1 `/v1/agent/send` 页面已收尾却 500 timeout（128.8s / 208.1s，3 次）；C1-F2 `memory.select` 554/1203ms vs 120ms 预算
- 结论：**两个都不是"算得慢"，而是"等错了信号"与"页面主线程争用"**。F1 是完成判定依赖「文本与基线不同」，基线在短答场景可能已经等于最终答案 → 永远等不到变化，只能耗到一轮 120s 上限；F2 的检索本身 <1ms，慢在页面↔宿主往返与页面侧排队。

## C1-F1 `/v1/agent/send` 短答 500 timeout

### 1. 调用链与关键参数

```
POST /v1/agent/send                       src/api/server.ts:474-497
  → options.agentSender(msg)              src/host/desktop-host.ts:1070
    → createTaskLoop({maxRounds:25, roundTimeoutMs:300_000})   src/host/desktop-host.ts:1078-1083
      → loop.run(`[AGENT_SENTINEL]${text}`)
        → engine.send(...)                src/host/engine/web-engine.ts:232
        → requireTaskLoopReply(result)    src/host/kernel/task-loop.ts:66  ← 这里抛错 → 500
```

| 参数 | 值 | 位置 |
|------|----|------|
| `pollIntervalMs` | **1500ms** | `web-engine.ts:120` |
| `stepTimeoutMs` | **120_000ms** | `web-engine.ts:121` |
| `roundTimeoutMs`（路由用） | **300_000ms** | `desktop-host.ts:74` |
| `maxRounds` | 25 | `desktop-host.ts:1052/1081` |
| 稳定判定 | 连续 **2** 次快照相同 | `web-engine.ts:292-294` |

### 2. 完成判定的实际逻辑（`web-engine.ts:232-312`）

```
发送成功
→ baseline = await readLastMessage()          :253   ← 注意：在 send 之后才读基线
→ 循环：sleep(1500) → snap = readLastMessage()
     若 (lastText !== baselineText && lastText.length>0 && lastText === prevSnapshot)
        stableHits++ ; >=2 → break             :289-297
     否则 stableHits = 0
→ 只能靠 stepTimeout(120s) 退出 → timedOut=true → completion='truncated'  :265, 302
→ task-loop: computeStop(timedOut) → stopReason='timeout'                  :197
→ requireTaskLoopReply：stopReason='timeout' → 抛 TaskLoopReplyError       :68-76
→ /v1/agent/send catch → 500 {ok:false,error:'task loop returned no successful reply (timeout)'}
```

**核心缺陷**：完成条件的第一项是 `lastText !== baselineText`。只要基线读到的文本已经等于最终答案，条件恒假，`stableHits` 永远是 0，**没有任何其它出口**，只能等满 `stepTimeoutMs=120s`。

### 3. 假设清单

| # | 假设 | 机制 | 可能性 | 现有证据 |
|---|------|------|--------|----------|
| H1 | **基线即最终答案** | `chat-insert`+`chat-send` 两次 dispatch 本身要走页面↔宿主往返（每次几十~几百 ms），短答（"好的"这类）在页面侧渲染+流式收尾可能早于 `readLastMessage()`（`:253`）返回；此时 `baselineText` = 最终答案 → 循环永不结束 | **高** | 3 次失败全是"短答/页面已收尾"；时长 128.8s ≈ 120s + 首次 chat-read 往返与调度开销 ≈ 8.8s |
| H2 | **同文重复陷阱** | 若最终答案与基线读到的那条助手消息**文本相同**（例如两次都答"好的"），`lastText === baselineText` 同样恒真；即使页面渲染了新消息也会被判为"没变化" | 中 | 逻辑上完全成立；`readLastMessage` 已返回 `count`（`:151-158`）但**从未被使用**，没有消息身份/序号参与判定 |
| H3 | 第二轮叠加导致的 208.1s | 第 1 轮用工具（`toolCalls>0`）不判停 → 进入第 2 轮 `waitForNextReply`（`:248`），其 DOM 降级路径同样有 120s `stepTimeoutMs`；86s + 2s 轮间隙 + 120s ≈ **208s** | 中高 | 208.1s 与"1.5 轮 120s 预算"高度吻合；`roundTimeoutMs=300s` 说明不是它触发 |
| H4 | 只认 DOM 稳定性、不消费"回复结束"信号 | 页面已有 `pushStreamDelta`/`consumeAutoReply` 两条推送通道（`:210-213`、`:318-337`），但 `send()` 只用 DOM 轮询；页面明确收尾后宿主无从得知 | 中 | 代码事实：`send()` 里没有 `consumeAutoReply` 分支（只有 `waitForNextReply` 有） |
| H5 | `lastText.length > 0` 门槛 | 若 chat-read 在流式开头返回空文本，条件不满足 → `stableHits` 反复清零，直到文本出现；短答下会额外吃掉数个 1.5s 周期 | 低-中 | 逻辑成立，但不足以单独解释 120s |
| H6 | 页面 chat-read 本身变慢 | 页面主线程被流式渲染占满时，每次 `dispatch('chat-read')` 可能就是几百 ms~秒级；会拉长轮询周期并解释 8.8s 溢出 | 中 | 与 C1-F2 指向同一分母（见文末交叉结论） |

### 4. 最小复现思路（不需要真机）

**R1（决定性，纯单测）**：构造 fake dispatch，使 `readLastMessage()` 第一次（基线）与之后每次轮询返回**同一段最终答案文本**。

```ts
// 伪代码：tests/host/web-engine.test.ts
const dispatch = async (cmd) => ({ ok: true, data: { count: 3, messages: [{ text: '好的' }, { text: '好的' }] } });
const engine = createWebEngine({ dispatch, pollIntervalMs: 20, stepTimeoutMs: 200 });
const t0 = Date.now();
const r = await engine.send('你好');
// 期望（缺陷成立时）：r.completion === 'truncated'、r.content === '好的'、耗时 ≈ 200ms（不是 60ms 内完成）
```

**R2（同文重复）**：基线返回 `count=1,text='好的'`，轮询返回 `count=2,text='好的'`（消息条数变了、文本相同）。
→ 若同样耗到 timeout，则证明「判定只看文本、不看 count/id」是第二个可独立触发的洞。

**R3（对照）**：基线 `text='你好'`，随后 `'好的','好的','好的'` → 应在 ~3 个 poll 内以 `complete` 返回（证明 H1/H2 之外的路径正常）。

### 5. 需要真机的一条确认

用 `/v1/agent/send` 发一条**极短**提示（如"只回复：好"），在宿主侧用 CDP 在发送后 100–300ms 读一次 `chat-read` 结果，看是否**已经包含这条回复**（即基线已等于答案）。这一步只需读，不改源码。

### 6. 修复方向（供 PM 排期参考，不在本卡实施）

1. 完成判定加**消息身份**：用 `readLastMessage()` 已有的 `count`（或消息 id）判断"是否出现了新消息"，文本只用于稳定检测，不再拿它当唯一变化信号。
2. 基线改为"发送前最后一条 assistant 消息的 id/count"，而不是文本快照。
3. `send()` 消费页面推送的收尾信号（`pushStreamDelta`/`consumeAutoReply` 已有通道），DOM 轮询退化为兜底。
4. 兜底超时从 120s 降到接近用户可感知阈值（如 20–30s），并在超时返回 `truncated` 时把"已收尾的页面内容"作为答案返回，而不是直接 500。

## C1-F2 `memory.select` 554/1203ms vs 120ms 预算

### 1. "120ms 预算"是什么

预算不在宿主，在**页面侧预取等待**：

```ts
// src/inject/main-world-interceptor.ts:157-167  预取发起（按 taskText 去重、复用 in-flight）
function kickMemorySelect(taskText: string): void
// src/inject/main-world-interceptor.ts:170-183  有界等待
async function awaitMemorySelectBudget(limitMs = 120)   ← 120ms 预算
```

即：页面在拼提示词时最多等 120ms 拿记忆候选，拿不到就沿用上一帧（`currentMemories` 不更新）。
所以 554/1203ms 的实测值意味着：**这份预取几乎总是超预算，记忆注入长期是"上一帧/空"**——这是功能正确性问题，不只是性能。

### 2. 宿主侧执行链（`desktop-host.ts:814-831`）

```
memory.select
  → store.list()                      全表 SELECT * → 全部记忆（含 content）
  → filter(pinned)
  → taskText ? store.search(text,{limit:12}) : []       FTS5 trigram bm25 → LIKE 兜底
  → 去重（pinned 优先）→ 返回 { memories:[{id,type,name,content,tags}], selection }
```

调用外层还有 `executeTool` 的治理链（`desktop-host.ts:1421+`）：`authority.consume(grant)` → registry/allowlist → `audit.record(...)`（每次调用落一条审计）。

### 3. 实测证据：检索与载荷都不是瓶颈

本机真实库只读探测（`node:sqlite` readOnly，不改文件）：

```json
{ "rows": 23, "valid": 23, "pinned": 0, "contentBytes": 3596,
  "avgLen": 156, "maxLen": 515,
  "selectAllMs": 0.6, "mapMs": 0.2, "jsonMs": 0.1, "jsonBytes": 4564 }
```

- 全表 `SELECT * FROM memories` **0.6ms**，映射 0.2ms，整个候选集 JSON 只有 **4.5KB**。
- 结论：`store.list()`、`search()`、序列化、WS 载荷（4.5KB）**都不可能**产生 554/1203ms。
- 即使放大到 5000 条 × 200B，也只是 ~1–5ms 级（线性），量级差两个数量级。

### 4. 假设清单

| # | 假设 | 机制 | 可能性 | 验证方式 |
|---|------|------|--------|----------|
| F2-H1 | **页面主线程被流式渲染占满** | WS `message` 事件 → `JSON.parse` → 结果回调 → `kickMemorySelect` 的 `.then` 全部排在页面主线程任务队列里；DeepSeek 回答流式更新 DOM 时，这些任务被推后几百 ms~1s | **高** | 真机：同一路径的**空载工具**（`settings.get` / `kv-get`）在页面空闲 vs 流式中各测 20 次，对比中位数 |
| F2-H2 | 宿主侧每次调用固定开销（治理链） | `executeTool` 每轮：grant 消费（本地校验）+ origin 白名单 + 审计落盘一条；若审计是同步写文件并 fsync，单次可达数十 ms | 中 | 纯单测：直接调 `hostTools.get('memory.select').execute()` 计时（绕过 WS）；再单独计时 `audit.record` |
| F2-H3 | 宿主事件循环被 chat-read 轮询挤压 | 代理运行期每 1.5s 一次 `chat-read`（页面 DOM 读，往返几百 ms），`memory.select` 的执行排在同一个消息处理循环里 | 中 | 真机：代理空闲 vs 代理跑轮次时各测一次 |
| F2-H4 | `getMemoryStore()` 首调用初始化 | 首次打开 SQLite（建表/迁移/FTS）10–90ms，可解释"直连 12–92ms"的上界，但**不可解释 554/1203ms** | 低（对 554/1203） | 纯单测：连续调用 2 次，比较第 1 次与第 N 次 |
| F2-H5 | 预取触发太晚 | `kickMemorySelect` 挂在发送流程里（`main-world-interceptor.ts:157+`），与 `chat-send` 竞争同一帧；等它发出请求时预算窗口已经开始倒计时 | 中高 | 真机：在 `interceptorTrace` 里比对 `memory.select` 发起时刻与 `chat-send` 时刻的差值（trace 已有 `tool.exec` 时长字段） |
| F2-H6 | 预算值本身太紧 | 即便一切正常，一次页面↔宿主工具往返在繁忙页面也常 >120ms | 中 | 用 H1 的数据反推：若空载往返中位数已 >120ms，则预算本身要改 |

### 5. 验证矩阵（哪些能纯单测、哪些必须真机）

| 结论 | 方法 | 是否需要真机 |
|------|------|--------------|
| 检索/列表/载荷不是瓶颈 | 已用只读 DB 探测证实；可再加单测：seed 23 / 500 / 5000 行，测 `memory.select.execute()` 耗时 | ❌ 纯单测即可 |
| 治理链开销（audit/consume） | 单测直接调 `execute()` 与 `authority.consume()` 分段计时 | ❌ 纯单测 |
| 页面侧排队（F2-H1） | 需要真机：同路径空载工具对照 + 空闲/流式两态对照 | ✅ 真机 |
| 预取时机（F2-H5） | 用已有 `interceptorTrace` 时间戳做离线比对（不改源码，读 trace） | ✅ 真机（读 trace） |
| 预算是否合理（F2-H6） | 真机空载往返中位数 vs 120ms | ✅ 真机 |

**关键判别实验（一次就能分流）**：在真机上用**同一个 WS 往返**打两个工具——`memory.select` 与 `settings.get`（后者几乎零计算、返回几十字节）。
- 若两者都 500–1200ms → 慢在传输/页面排队（F2-H1/H5），与记忆库无关；
- 若 `settings.get` ~20ms、`memory.select` 554ms → 慢在宿主侧该工具自身（F2-H2/H4），再去单测分段计时。

### 6. 修复方向（供排期参考）

1. 预取提前：在用户按下发送、`chat-insert` 之前就发 `memory.select`（现在与发送流程抢同一帧）。
2. 分层返回：先返回 `pinned` + 标签精确命中（几乎零计算），再异步补 `search` 结果；页面对第一段给足预算。
3. 结果缓存键从 `taskText` 改成"会话 + 最近 N 轮关键词"，避免每轮重算。
4. 预算与实现对齐：把 120ms 明确成 SLO，并在超预算时记一条 `interceptorTrace`（现在只能靠 `durationMs` 事后看，没有"超预算"事件）。

## 交叉结论

F1 与 F2 的失败形态不同（一个是判定条件错、一个是延迟），但共享同一个分母：**页面主线程在流式回答期间被占满，页面↔宿主的往返不受宿主控制**。
- F1：靠 DOM 稳定性判完成，且基线取文本；页面收尾早于基线 → 必然空等。
- F2：靠页面侧 120ms 预算拿预取结果，而往返延迟由页面忙闲决定 → 必然常超时。

因此两条修复里，"把权威信号改成事件/消息身份"（F1）与"把预取挪到页面不忙的时刻"（F2）都比"把超时调大"更接近根因。
