## 1. 逐条发现

### R2-01 [P1] agent-loop watchdog 提前置 active=false 并重置 stopFlag

**证据** src/host/agent-loop.ts:120-132

    const watchdog = setTimeout(() => {
      if (active) {
        options.stopFlag.stopped = true;
        emit({ type: 'error', text: `全局看门狗触发（...），强制结束本次循环` });
        emit({ type: 'done' });
        active = false;                    // <-- 提前释放
        options.stopFlag.stopped = false;   // <-- 立刻清掉停止信号
      }
    }, watchdogMs);

watchdog 的意图是「防永久 agent-busy」。但它只把内存标志 `active` 置 false，**并不会中断仍在 `await options.engine.send(...)` 或 `await options.engine.waitForNextReply()` 上挂起的那次 send**。真实的 send 调用栈仍在运行，最终会在自己的 finally 里再次 `active = false`。

两个后果：

1. **并发回合**：watchdog 触发后，`active` 已为 false，新的 `send()` 通过 `if (active) throw new Error("agent-busy")` 检查进入。此时两个 send 同时在跑，它们**共享同一个 `options.stopFlag`**（注释明确写「由宿主装配方创建并传给引擎与 loop 两处」）。旧回合的 `stopFlag.stopped = false` 会清掉新回合刚设的停止信号，反之亦然。
2. **停止信号被抹掉**：watchdog 内部 `stopped = true` 紧接着 `stopped = false`，同一 tick 内完成。若旧回合的循环恰好在这两点之间检查 `options.stopFlag.stopped`，会读到 true 而 break；若在之后检查，读到 false 而继续跑。行为取决于调度时机，不可预测。

**后果** 超时后可能同时存在两个活跃回合，二者互相改写共享 stopFlag，导致「点停止不生效」或「莫名中断」。在聊天室多 bot 场景下，这会让一个 bot 的超时波及另一个 bot 的回合。

**建议** watchdog 只应设置一个独立的 `aborted` 标志并让循环自己观察退出，不要在 watchdog 里改 `active`；`active` 的释放权唯一归属 finally。若要支持强制接管，应引入「回合代际号」（epoch），新回合开始时递增，旧回合每次 await 后对比 epoch，不等则自行退出。

**状态** Verified

### R2-02 [P1] pickClient 不校验 hello 状态，未握手连接可截获工具调用参数

**证据** src/host/page-runtime.ts:178-189

    function pickClient(botId?: string): { ws: WebSocket } | null {
      for (const c of clients.values()) {
        if (c.untrusted) continue;
        if (botId !== undefined && (c.botId ?? MAIN_BOT_ID) !== botId) continue;
        return c;
      }
      return null;
    }

而 `clients.set(id, rec)` 发生在 `wss.on("connection")` 的**第一行**（第 193 行），此时 `rec.origin = null`、`rec.botId = undefined`、`rec.untrusted = false`。只有收到 `hello` 消息后才会填 origin/botId。

因此 pickClient 的过滤条件 `!c.untrusted` 对「已连接但从未发 hello」的客户端**恒为真**。

**后果** 本机任意进程（curl / 一段 node 脚本 / 被入侵的本地服务）连接 `ws://127.0.0.1:8760/studio`，什么都不发，即成为一个合法的 dispatch 目标。宿主随后把 `{ type: "dispatch", callId, tool, params, botId }` 推给它——**params 里含完整工具参数**：文件绝对路径、shell 命令行、要写入的正文、MCP 调用参数。攻击者不需要回 result（30s 后超时），光是收到这条消息就已经拿到信息。

这是「本机回环 = 可信」误判的第二个实例（R1-01 是第一个）。

**建议** 在 rec 上增加 `ready: boolean`，仅 hello 成功后置 true；pickClient 只接受 `c.ready && !c.untrusted`。同时 hello 必须校验 `msg.origin` 与 `req.headers.origin` 一致，防止自报伪造。

**状态** Verified

### R2-03 [P1] ws upgrade 不校验 Origin 头

**证据** src/host/page-runtime.ts:143-147

    options.server.on('upgrade', (req, socket, head) => {
      const pathname = new URL(req.url ?? '/', 'http://localhost').pathname;
      if (pathname !== path) return;
      wss.handleUpgrade(req, socket, head, (ws) => wss.emit('connection', ws, req));
    });

只判断路径，未校验 `req.headers.origin`。而同文件的 `isPnaAllowedOrigin`（第 30-40 行）已经实现了「只允许 DEEPSEEK_ORIGIN 或本地回环」的白名单，且 `wss.on('headers')` 也用它来补 CORS 头——但这个函数**只用于补响应头，从未用于拒绝连接**。

**后果** 任意网页（用户访问的任意 http/https 站点）都能向 `ws://127.0.0.1:8760/studio` 发起 WebSocket 握手并成功连上。浏览器同源策略不阻止 ws 建连（只限制后续 API 访问）。连上后它同样落入 R2-02 的路径：成为 pickClient 的候选目标，截获工具调用参数；且它可以在 hello 里自报 `origin: "https://chat.deepseek.com"` 绕过后续 origin 校验。

与 R2-02 组合，构成「任意网页 → 本机工具通道」的完整链路。

**建议** upgrade 阶段即调用 `isPnaAllowedOrigin(req.headers.origin)`，不通过则 `socket.destroy()` 并记审计事件。注意 `isPnaAllowedOrigin` 当前也允许 `localhost/127.0.0.1` 来源——这会让任何本地开发服务器都能连，建议对本地来源再加 token 校验。

**状态** Verified

### R2-04 [P2] routeExecution 的 Node 回退是假成功

**证据** src/host/desktop-host.ts:1105-1118

    // 回退：Node 宿主内 rehydrate（仅 echo 等无 DOM 依赖能力）。
    const cap = capabilities.get(name);
    if (cap) {
      const scope = createHostResourceScope();
      epoch += 1;
      await cap.start(scope, epoch);
      const snapshot = scope.snapshot();
      await cap.stop('manual' as ContentLifecycleStopReason);
      return { ok: true, snapshot };
    }
    return { ok: false, reason: 'no-capability' };

这段代码注释说「仅 echo 等无 DOM 依赖能力」，但没有任何代码检查 `name` 是否真的属于这一类。只要 `capabilities.get(name)` 存在，就 start/stop 一遍并返回 `ok: true`。

**后果** 当 botId 指定的页不在线（`targetPages.length === 0`）时，`chat-send`（发消息到页面）、`chat-insert`（往输入框插文字）这类真正需要 DOM 的能力会走进这里：start → 立刻 stop → 返回 `ok: true` + 空 snapshot。**调用方（AgentLoop / Bot）收到成功信号，以为消息发出去了，实际什么都没发生**。这比明确报错更危险——模型会基于「已发送」继续推理后续步骤。

**建议** 为能力元数据增加 `requiresDom: boolean`；回退分支只允许 `!requiresDom` 的能力通过，其余返回 `{ ok: false, reason: 'no-page-for-dom-capability' }`。或者直接删除该回退，让无页场景一律 fail-closed。

**状态** Verified

### R2-05 [P2] invokeTool 硬编码 origin=DEEPSEEK_ORIGIN，绕过 origin 白名单

**证据** src/host/desktop-host.ts:1119-1127

    async function invokeTool(tool: string, params: unknown, botId?: string): Promise<ToolExecutionResult> {
      const grant = await authority.requestToolExecution({
        documentId: 'host-agent',
        sessionId: 'host-agent',
        requestId: crypto.randomUUID(),
        scope: tool,
        origin: DEEPSEEK_ORIGIN,     // <-- 硬编码
      });
      return executeTool(tool, params, grant, botId);
    }

executeTool 的第 2 道闸门是 `registry.isOriginAllowed(name, grantOrigin)`，而 grantOrigin 直接来自这个硬编码值。

**后果** 经由 invokeTool 的所有调用，origin 闸门**恒为通过**——不管调用实际来自哪里。这让 R1 报告中提到的「R2 站点隔离」（代码注释原话）对这条路径完全失效。目前 invokeTool 的调用方是宿主内部（AgentLoop、Bot），所以不是外部可利用的漏洞；但它是「闸门形同虚设」的典型——一旦将来有人把 invokeTool 接到 HTTP 端点或 ws 消息上（`/v1/agent/send` 已经存在类似能力），隔离即刻失效。

**建议** 把 origin 作为 invokeTool 的显式参数由调用方传入；宿主内部调用用一个专门的 `HOST_INTERNAL_ORIGIN` 常量，并在 tool-definitions 里明确它的白名单范围（而不是复用 DEEPSEEK_ORIGIN）。

**状态** Verified

### R2-06 [P2] finally 无条件重置 stopFlag，抹掉用户 stop() 意图

**证据** src/host/agent-loop.ts:200-205

    } finally {
      clearTimeout(watchdog);
      active = false;
      currentRoomId = undefined;
      options.stopFlag.stopped = false;   // <-- 无条件重置
    }

stopFlag 是**共享对象**（注释：「由宿主装配方创建并传给引擎与 loop 两处」）。用户调 `loop.stop()` 时设 `stopped = true`，循环 break，然后 finally 把它重置为 false。

**后果** 若同一 stopFlag 被多个 loop（多 bot / 聊天室场景）共享，A bot 的回合结束时会把 B bot 正在生效的停止信号清掉。表现为「停止某个 bot 后，另一个 bot 也停不下来」或「停止操作随机失效」。

**建议** stopFlag 改为每回合独立的 `{ stopped: boolean }` 对象，或在 loop 内用局部 `aborted` 变量而非共享对象。共享状态只保留「用户全局急停」这种真正全局的信号，且全局急停不应在单个回合结束时被清除。

**状态** Verified

### R2-07 [P3] 注释称 max_steps 默认 15，代码实际 25

**证据** src/host/agent-loop.ts:10 注释「max_steps：一个用户消息最多续跑 N 步（默认 15）」；第 33 行 JSDoc「单个用户消息的最大续跑步数（默认 25）」；第 66 行 `const maxSteps = options.maxSteps ?? 25;`。三处不一致，文件头注释是错的。

**后果** 读者按文件头理解护栏强度，低估了最大续跑次数（15 vs 25，差 67%）。

**建议** 统一为 25，或把常量提取到一处并让注释引用它。

**状态** Verified

### R2-08 [P3] watchdog 与 finally 双重 active=false

**证据** 同 R2-01：watchdog 内 `active = false`，finally 内 `active = false`。两处写入同一变量，无同步。

**后果** 监控 / 审计无法从单次 `active` 变更判断「是正常结束还是被看门狗强杀」。当前也没有任何日志记录 active 变更，事后无法追溯。

**建议** active 只由 finally 释放；watchdog 只记录 `watchdogFired = true` 并 emit 事件。

**状态** Verified

## 6. 结论

本轮在宿主核心与连接状态机发现 3 项 P1、3 项 P2、2 项 P3。

**最需要立即处理的是 R2-02 与 R2-03 的组合**：upgrade 不校验 Origin + pickClient 不校验 hello，共同构成「任意网页或任意本机进程 → 连上本机 ws → 截获完整工具参数（含文件绝对路径与 shell 命令）」的链路。两者各约 5-8 行即可修复，是本轮性价比最高的动作。

**R2-01 与 R2-06 是同一个根因的两面**：`active` 与 `stopFlag` 被当作可随意读写的全局标志，而不是由单一所有者管理的状态。watchdog 强杀、finally 重置、多 loop 共享，三者叠加导致停止语义不可预测。修复方向是引入回合代际号 + 状态单一所有权。

**R2-04 是「静默错误」类**：不报错、返回成功、实际未执行。这类缺陷比崩溃更难发现，因为没有任何信号。

值得注意的是，R2 的 P1 数量（3）高于 R1（2），且两项都是「信任边界误判」——与 R1-01 同源。这说明该问题不是孤立笔误，而是贯穿 api 层与 host 层的系统性认知偏差：**把「本机回环」等同于「可信」。** 建议做一次全仓专项排查，把所有 `127.0.0.1` / `localhost` / 回环判断点列出逐一复核，而不是等后续轮次逐个撞见。
