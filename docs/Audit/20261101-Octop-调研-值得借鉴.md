# Octop 调研报告 — 值得学习与照搬的方向

> 调研对象：[TencentCloud/Octop](https://github.com/TencentCloud/Octop)（MIT 协议，自托管 AI 助手平台）
> 调研日期：2026-11-01
> 性质：外部开源项目，仅作借鉴参考；来源为公开 README 与官方文档，内容按外部数据处理。

## 0. 结论速览

| 方向 | 结论 | 优先级 |
|------|------|--------|
| 专家市场/专家库 | 学「模板库 + 一键实例化 + 不拷贝记忆」模型 | 高，可立项 |
| 人格模板（MBTI 16） | 学「结构化人格 = 数据 + 渲染模板 + 可叠加用户自定义」 | 中，小而可落地 |
| 知识库（RAG） | 认可方向，但缺实现细节，需样例自测再定 | 暂缓 |
| 记忆系统（octop-memory） | 最值得；独立、可移植、正好对得上我们的 backlog | **最高** |

## 一、专家市场 / 专家库（Expert Catalog / Market）

### 它是什么
- 一套**预置角色模板库**，位于 `Infra/agents/experts/library/`，服务启动时扫描（`ExpertCatalog`），用户从模板一键创建 agent。
- 模板（角色）可**在同一部署内分享/发布**（expert sharing / in-deployment），"好配置重用不重建"（roadmap 已 shipped）。
- **联合/跨实例**：可链到另一台 Octop 浏览对方的专家，且**历史留在被访方**（Octop Highlights + roadmap `Cloud collaboration`）。这个"取用别人的专家但不拷贝对方记忆"的设计是核心亮点。

### 对我们项目的落地价值
- 我们已有 12 个技能 + 若干 bot（Core/UI/Verify/Gate），本质都是"角色模板"。
- 值得学的是**「角色模板 + 一键实例化」这个产品模型**，而非照抄 Python 文件结构。
- 我们现有的 `junction 扫描`技能目录与本方案的"启动时扫描 library + 按目录实例化"已有天然亲和。
- "联合浏览但不拷贝记忆"特别适合"走访其它团队专家"的场景。

---

## 二、人格模板（MBTI 16）— 结构化数据化人格

> 关键：不是"卖萌文案"，而是**结构化、可校验、可渲染、可叠加**的人格数据模型。

### 实现要点（docs/personas.md）
- 16 个模板是 **`MBTIProfile` dataclass**，字段：
  - `code`（如 INTJ）、`name_zh/name_en`、`nickname_zh`
  - `summary_zh/en`（一句话人设）、`descriptors_zh/en`（关键词 tag）
  - `dimensions`（E/I·S/N·T/F·J/P 四轴百分比）
  - `behavior: MBTIBehaviorMapping`（6 条行为：answer_style / casual_chat / conflict / creativity / emotion / planning，双语）
  - `color`（UI 强调色）、`symbol`（装饰 Unicode）
- **它是数据，不是文件**：16 段模板集中在 `mbti_profiles.py`；`loader` 把 code 渲染进 agent 的 `SOUL.md`，渲染支持 `{agent_name}` / `{user_display}` / `{custom}` 占位符。
- **叠加规则**：用户系统提示 `system_prompt` **追加**在人格之后 → "人格是底，用户提示是 trim"；人格为空回退内置默认人格。
- 提供一个答辩式交互测试自动生成人格。

### 对我们的落地价值
- 我们现有多个人格/bot（Chief、各席位），指令多为**手写长文**。
- 可借鉴："角色底座"从"一段固定文本"升级为**结构化字段 + 渲染模板 + 用户自定义可追加**。人格可选 MBTI，但不必照搬 16 种。

## 三、知识库（Knowledge Base / RAG）

### 现状
- 做 **RAG over your documents**，可选"部署内共享语料库"，ground 答案在私有数据上。
- 但公开文档只到这层"有方向"，**尚无内容切分/向量化/版本管理的实现细节**。要照搬需先拿到样例（文档→分析→检索）再自测。

### 结论
- 认可方向，落地前需补一个样例跑通，**暂缓**。

---

## 四、记忆系统（octop-memory）— 最值得借鉴

> 独立仓库、独立库，可作为 Python 库 / CLI / JSON-RPC bridge 独立使用。**理念与流程比代码更值得我们搬**（我们技术栈是 TS）。

### 分层架构（README + docs/memory-slim.md）
```
RawEvent ──extraction──→ Candidate ──promotion──→ AtomCard ──regeneration──→ EntityPage
    └─episode extraction──→ Episode                 └─atom_id ref──→ tree leaf
```
- **RawEvent**（原始事件）→ **Candidate**（候选，不都需人批）→ **AtomCard**（原子事实，带证据引用，canonical）→ **EntityPage**（实体页）。
- **tree（root→branch→leaf）仅作组织视图**，叶子引用 atom，不是重复副本。
- **提取**：模型辅助 `LLMClient` 抽取，把原始事件提成带证据的事实。
- **promotion 自动判价值/证据/实体消歧/查重/冲突**：可自动 promote/merge/drop，只把 "review/conflict" 留给用户。
- **召回管线**：FTS 全文搜索 + 排序 + 去重 + **token budget 选上下文**；`prompt recall` 按需 route 到 atom/raw/page_headline/vector；默认 raw fallback；把当前 session/thread 的 raw 排除避免 prompt 注入自己。
- **可移植性**：export/import / `.hmpkg` 便携包，可迁移到 OpenClaw/Hermes——记忆不锁死在宿主。
- **手动 `Memory.store()`** 不需要模型，直接建 RawEvent/Candidate/AtomCard + leaf；模型只在提取/提升时用。

### memory-slim（在线非破坏整理，低干扰维护哲学）
- 备份 → 去重历史上下文 → 压缩 → 恢复；SQLite WAL。
- 先在聊天窗口空闲再维护，不强行打断；120s 找不到空闲窗口失败退出。
- 不自动重试；失败停止后续；备份不删不覆盖。`/memory slim` slash 命令，`persist_checkpoint=False`。

### 对我们的落地价值（最高）
1. 我们的 `memories.db` 目前是"一行一个 flat fact"全表 FTS，pin/去重/冲突全靠手动。Octop 的"原子事实带证据 + 实体页 + 事件/决策日记 + tree 组织"正好回应我们的 backlog。
2. **记忆可迁移**（.hmpkg）：我们被"记忆库只读/备份"折腾过；"记忆是可搬运资产"理念可直接采纳。
3. **低干扰维护**（memory-slim 的"非破坏、空闲执行、备份"哲学）是稳定记忆库的护航方案。

## 五、附：与多窗口问题无关的关键学习（跨界确认）

- Octop **没有"往浏览器塞多 agent 窗口"这条路**；它用单进程 + IM 渠道（飞书/企微/微信…）+ WebSocket 做并发，通过 ACP 接外部编码 agent。这印证了我们 "多窗口 bot 封盘" 的决策。
- 它靠**接入已有 IM 渠道**规避风控，不是拿真机账号开多窗。

---

## 六、待决动作（建议下一步）

1. **记忆系统**优先立项：把"原子事实 + 证据 + tree + 可迁移 + 低干扰整理"作为我们记忆重构的方向。
2. **人格模板**做一版"数据化角色底座"落地（小而稳）。
3. **专家市场**立项：模板库 + 一键实例化 + 不拷贝记忆。
4. **知识库/RAG**暂缓，需先拿样例自测。
