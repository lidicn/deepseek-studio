# 发版操作 · v0.14.10（维护者说明，**不贴进 Release**）

> 本文件与 `release-notes-v0.14.10.md` 是**分开的两份**。拆分原因见下「口径」。

## 怎么用

1. GitHub → [Releases](https://github.com/lidicn/deepseek-studio/releases) → 找到 `v0.14.10 (Draft)`（草稿只有本人可见，属正常）→ 点 **Edit**。
2. 把 **`docs/release-notes-v0.14.10.md` 的全部内容**整段贴进 **Release description** 框。
3. 右侧勾选 **Set as the latest release**（**必须勾**，否则 `releases/latest` 指针不推进；已三次踩坑）。
4. 点 **Publish release**。

## 口径：为什么正文文件必须是纯正文

发版工作流 `release.yml` 的 `Compose latest.json` 步骤会读 `docs/release-notes-<tag>.md`，`Trim()` 后截 500 字符写入 `latest.json.notes`；而 `notes` 正是更新弹窗里显示的那行说明（`update-card.ts` 渲染 `info.notes`）。

⇒ **若把维护说明写进同一个文件，前 350 字符全是元说明**（标题、用途、背景、注意事项、分隔线、"从这里开始复制"），截 500 后推给用户弹窗的就是这些内部话。所以：

- `docs/release-notes-<tag>.md` → **只放用户可见正文**，一个字都不要多。
- `docs/发版操作-<tag>.md` → 维护者操作说明放这里（即本文件）。

## 生效范围（本次发布读不到新逻辑）

- tag `v0.14.10` 钉在 commit `1d0f41a`，而 `release.yml` 与 `docs/release-notes-v0.14.10.md` 都是**标签之后**的提交（`3f2810b` 起）——实测该文件在 tag 里 **ABSENT**，tag 里的 `release.yml` blob 仍是旧版 `1e270e7`（`notes` 硬编码）。
- 工作流在 **tag 那个 commit** 上解析，所以 **v0.14.10 的 `latest.json.notes` 仍是泛化串 `Release v0.14.10`**，与正文无关。上面「已知问题」第一条已如实写给用户。
- ⇒ **从下一版起**，`docs/release-notes-<tag>.md` 必须**先于 tag 入库**，新逻辑才可能生效；否则永远走回落。这条属发版编排要求，已记入 PM 台账。
