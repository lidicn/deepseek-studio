## §1 Transport 接口真相

### A1. transport 接口的确切形状

pi-agent-core 里**没有我们意义上的 "transport" 接口**。`Transport` 在 pi-ai 里只是一个 HTTP 传输枚举：

```ts
// node_modules/@earendil-works/pi-ai/dist/types.d.ts:37
export type Transport = "sse" | "websocket" | "websocket-cached" | "auto";
```

真正的 LLM 调用边界是 `StreamFn`：

```ts
// node_modules/@earendil-works/pi-agent-core/dist/types.d.ts:13
export type StreamFn = (
  model: Model<Api>,
  context: Context,
  options?: SimpleStreamOptions
) => AssistantMessageEventStream | Promise<AssistantMessageEventStream>;
```

**这不是一个 "transport 抽象层"，而是一个直接发 API 请求的函数。** 它接收 Model（含 baseUrl/apiKey）、Context（messages+tools）、options，返回一个事件流。

### A2. messages 类型 vs 我们的 ChatMessage

pi 的消息是严格的 tagged union：

```ts
// pi-ai types.d.ts:283-320
export type Message = UserMessage | AssistantMessage | ToolResultMessage;

interface UserMessage {
  role: "user";
  content: string | (TextContent | ImageContent)[];
  timestamp: number;
}
interface AssistantMessage {
  role: "assistant";
  content: (TextContent | ThinkingContent | ToolCall)[];
  api: Api; provider: ProviderId; model: string;
  usage: Usage; stopReason: StopReason; timestamp: number;
  // ...
}
interface ToolResultMessage<TDetails = any> {
  role: "toolResult";
  toolCallId: string; toolName: string;
  content: (TextContent | ImageContent)[];
  isError: boolean; timestamp: number;
}
```

**与我们的差距**：我们当前发给引擎的是纯文本 `send(text: string)`，拿回 `{ content: string, toolCalls: number }`。没有结构化消息、没有 timestamp、没有 usage、没有 toolCallId。要接 pi，需要写一层双向转换：我们的扁平 transcript ↔ pi 的 `Message[]`。

### A3. 流式 delta 回调签名

```ts
// pi-ai types.d.ts:375-428
type AssistantMessageEvent =
  | { type: "start"; partial: AssistantMessage }
  | { type: "text_start"; contentIndex: number; partial: AssistantMessage }
  | { type: "text_delta"; contentIndex: number; delta: string; partial: AssistantMessage }
  | { type: "text_end"; contentIndex: number; content: string; partial: AssistantMessage }
  | { type: "toolcall_start" | "toolcall_delta" | "toolcall_end"; ... }
  | { type: "done"; reason: "stop"|"length"|"toolUse"; message: AssistantMessage }
  | { type: "error"; reason: "aborted"|"error"; error: AssistantMessage };
```

事件流是一个 pushable stream（`AssistantMessageEventStream.push(event)` / `.end(result)`）。我们的页端 SSE delta 可以 pipe 进这个 push 接口，这一层是可行的。

## §2 工具调用类型

### A4. 工具调用类型 vs ToolCallRecord

pi 的工具是**自执行的**：

```ts
// pi-agent-core types.d.ts:333
interface AgentTool<TParameters extends TSchema = TSchema, TDetails = any> extends Tool<TParameters> {
  label: string;
  execute: (
    toolCallId: string,
    params: Static<TParameters>,
    signal?: AbortSignal,
    onUpdate?: AgentToolUpdateCallback<TDetails>
  ) => Promise<AgentToolResult<TDetails>>;
}
```

**关键差异**：pi 的 loop 收到 assistant 消息里的 `ToolCall` content block 后，**自己调用 `tool.execute()`**，把结果作为 `ToolResultMessage` 追加到 transcript，再发下一轮请求。

我们当前架构：工具由**浏览器页端拦截器**执行（带同意闸门、policy 判定、host 能力链），agent-loop 只数 `toolCalls` 个数然后等页端 nudge。**工具执行权在页端，不在 loop。**

## §5 D2 裁决

**接入成本估算：5–6 天**

依据：
- StreamFn 桥接到页端 SSE（把我们的页端 delta 灌进 pushable stream）：~1.5d
- 扁平 transcript ↔ pi Message[] 双向转换：~1d
- **工具执行权桥接（最大风险）**：pi 的 loop 要自己执行 tool.execute()，但我们的工具执行权在页端拦截器+同意闸门。要么 (a) 把 host 能力包成 AgentTool 绕开页端——这会绕过已验证的授权链；要么 (b) stub 掉 pi 的工具执行、让页端继续执行——这等于和 pi 的 loop 设计对着干。~2.5–3d
- pi 富事件 → 我们简单 UI 事件适配器：~0.5d

**是否破坏 177 行 agent-loop 契约：否（但会整体替换它）。**

证据：我们的 `AgentLoop` 接口是 `send(text) → Promise<void>` + `onEvent({type,text,step})`。pi 的 Agent 是类、own transcript、有 subscribe/steer/followUp。下游消费者（bot orchestrator、UI）只依赖我们的事件形状，写一层适配器即可。但 agent-loop.ts 本身（197 行，不是 177 行）会被整体替换为薄适配层，不是"小改"。

**结论：回退为「仅借鉴 transport 接口形状，自建薄 loop」。**

理由：探针证明 StreamFn 抽象本身干净可用，但 pi 的工具执行模型（inline execute）与我们的页端拦截器授权链根本冲突。强行对齐 pi 的工具执行意味着重做已经过安全验证的 policy/consent 链路，风险远大于收益。建议保留我们现有的 agent-loop（它已经在生产跑），只借鉴 pi 的事件流形状（start/text_delta/done）来重构我们的 EngineSendResult。
