## 一、项目概述

### 1.1 基本信息

| 维度 | 详情 |
|------|------|
| 作者 | Mario Zechner（libGDX 游戏引擎作者，游戏基础设施老兵） |
| 仓库 | earendil-works/pi（2026年5月从 badlogic/pi-mono 迁移） |
| 语言 | TypeScript monorepo |
| 协议 | MIT |
| Node 要求 | 22.19+ |
| 国内生态 | 小米"小龙虾"底层使用的 harness agent |
| 设计哲学 | 做减法（Anti-Framework），只提供 primitive，一切可替换 |

### 1.2 定位

Pi 是一个**极简、可扩展的 Agent Harness**。它不做框架，只提供最基础的模型交互能力（Agent Loop + 工具调用 + 状态管理），其他能力（记忆、多 Agent、交流通道等）都通过自定义扩展的方式开发。

> "Pi ships with powerful defaults but skips features like sub-agents and plan mode. Ask Pi to build what you want, or install a package that does it your way."

### 1.3 与同类产品的差异

Pi 走的是和 Claude Code 完全相反的路线：
- Claude Code：功能内置，黑盒，定制困难
- Pi：核心极简，一切可替换，扩展生态丰富

## 三、pi-agent-core 核心设计（重点）

### 3.1 整体架构

pi-agent-core 是 Pi 的心脏，提供**有状态 Agent + 工具执行 + 事件流**。核心循环仅约 949 行。

```
AgentMessage[] → transformContext() → AgentMessage[] → convertToLlm() → Message[] → LLM
                  (可选：裁剪/压缩)          (必需：过滤/转换)
```

### 3.2 Agent 类

```typescript
const agent = new Agent({
  initialState: {
    systemPrompt: "You are a helpful assistant.",
    model: model,
    thinkingLevel: "medium",  // off/minimal/low/medium/high/xhigh/max
    messages: [],
  },
  streamFn: models.streamSimple.bind(models),  // 必需
  convertToLlm: (messages) => messages.filter(...),  // 自定义消息类型时必需
  transformContext: async (messages, signal) => pruneOldMessages(messages),
  steeringMode: "one-at-a-time",  // 或 "all"
  followUpMode: "one-at-a-time",
  toolExecution: "parallel",  // 或 "sequential"
  beforeToolCall: async ({ toolCall, args, context }) => { ... },
  afterToolCall: async ({ toolCall, result, isError, context }) => { ... },
  prepareRequest: async ({ context }, signal) => { ... },
  finishTurn: async ({ message, toolResults }, signal) => { ... },
});
```

### 3.3 事件系统

Pi 的事件系统是其核心设计之一，所有 UI 更新都通过事件驱动：

| 事件 | 描述 |
|------|------|
| `agent_start` | Agent 开始处理 |
| `agent_end` | 运行结束（最后一个事件，订阅者仍会被等待） |
| `turn_start` | 新 turn 开始（一次 LLM 调用 + 工具执行） |
| `turn_end` | turn 完成（含 assistant 消息和工具结果） |
| `message_start` | 任意消息开始（user/assistant/toolResult） |
| `message_update` | **仅 assistant**，包含流式 delta |
| `message_end` | 消息完成 |
| `tool_execution_start` | 工具开始执行 |
| `tool_execution_update` | 工具流式进度（可选） |
| `tool_execution_end` | 工具执行完成 |

**事件序列（无工具调用）：**
```
prompt("Hello")
├─ agent_start
├─ turn_start
├─ message_start { userMessage }
├─ message_end { userMessage }
├─ message_start { assistantMessage }
├─ message_update... (流式 chunks)
├─ message_end { assistantMessage }
├─ turn_end
└─ agent_end
```

**事件序列（有工具调用）：**
```
prompt("Read config.json")
├─ agent_start
├─ turn_start
├─ message_start/end { userMessage }
├─ message_start { assistantMessage with toolCall }
├─ message_update...
├─ message_end { assistantMessage }
├─ tool_execution_start { toolCallId, toolName, args }
├─ tool_execution_update { partialResult }  (如果工具流式)
├─ tool_execution_end { toolCallId, result }
├─ message_start/end { toolResultMessage }
├─ turn_end { message, toolResults: [toolResult] }
│
├─ turn_start  (下一 turn，LLM 响应工具结果)
├─ message_start { assistantMessage }
├─ message_update...
├─ message_end
├─ turn_end
└─ agent_end
```

### 3.4 工具执行模式

- **parallel（默认）**：预检工具调用顺序执行，允许的工具并发执行，`tool_execution_end` 按完成顺序发出，但持久化的 toolResult 消息按 assistant 源码顺序
- **sequential**：逐个执行工具
- 可全局设置（`toolExecution`）或按工具设置（`executionMode`）
- 如果一批工具调用中有任何一个工具的 `executionMode: "sequential"`，整批都顺序执行

### 3.5 钩子系统

Pi 提供 4 个关键钩子，是其可扩展性的核心：

#### beforeToolCall
在 `tool_execution_start` 之后、参数验证通过之后运行。可以阻止执行并附加 `terminate: true`。

```typescript
agent.beforeToolCall = async ({ toolCall, args, context }) => {
  if (toolCall.name === "bash") {
    return { block: true, reason: "bash is disabled", terminate: true };
  }
};
```

#### afterToolCall
在工具执行完成之后、`tool_execution_end` 和最终 toolResult 消息事件发出之前运行。可以覆盖结果。

```typescript
agent.afterToolCall = async ({ toolCall, result, isError, context }) => {
  if (toolCall.name === "notify_done" && !isError) {
    return { terminate: true };
  }
  if (!isError) {
    return { details: { ...result.details, audited: true } };
  }
};
```

#### prepareRequest
在每次对话提供者请求之前立即运行（包括第一次）。用于安装规范的持久化上下文。

```typescript
agent.prepareRequest = async ({ context }) => ({
  context: { ...context, messages: await session.loadModelContext() },
});
```

#### finishTurn
在 assistant 和所有工具结果完成之后、`turn_end` 之前运行。决定是否继续或结束。

```typescript
agent.finishTurn = async ({ message }) => {
  if (message.stopReason === "error" || message.stopReason === "aborted") return;
  if (shouldEndRun(message)) return { action: "end" };
  return needsAnotherResponse(message) ? { action: "continue" } : undefined;
};
```

- 返回 `undefined`：保持正常调度
- `{ action: "end" }`：在 `turn_end` 后立即停止
- `{ action: "continue" }`：确保下一次请求（如果工具结果/steering/follow-up 已经导致请求，则不额外发起）

### 3.6 terminate 机制

工具、被阻止的 `beforeToolCall` 结果、`afterToolCall` 覆盖都可以返回 `terminate: true`，提示跳过自动续跑的 LLM 调用。

**关键规则**：只有当该批次中**每个**最终工具结果都设置了 `terminate: true` 时，循环才会提前停止。混合批次正常继续。

这是一个优雅的设计——避免单个工具的 terminate 误中断整个多工具批次。

### 3.7 状态管理

```typescript
interface AgentState {
  model: Model<any>;
  thinkingLevel: ThinkingLevel;
  tools: AgentTool<any>[];
  messages: AgentMessage[];
  readonly isStreaming: boolean;
  readonly streamingMessage?: AgentMessage;
  readonly pendingToolCalls: ReadonlySet<string>;
  readonly errorMessage?: string;
}
```

- 通过 `agent.state` 访问
- 赋值 `agent.state.tools = [...]` 或 `agent.state.messages = [...]` 会复制顶层数组
- 系统提示和工具声明由 transcript 管理（leading system message 是 prompt，后续 system message 是 patch）
- `agent.state.systemPrompt` 是只读的，重放 transcript
- 每次请求前，循环会 diff `agent.state.tools` 和 transcript 声明的工具，如果不同则在 system message 中公告变更

### 3.8 消息转换

Pi 区分 `AgentMessage`（灵活，可包含自定义类型）和 LLM Message（只有 user/assistant/toolResult）。

```
AgentMessage[] → transformContext() → AgentMessage[] → convertToLlm() → Message[] → LLM
```

- **transformContext**：裁剪旧消息、注入外部上下文（可选）
- **convertToLlm**：过滤 UI-only 消息、将自定义类型转换为 LLM 格式（必需）

支持通过 TypeScript declaration merging 扩展自定义消息类型：

```typescript
declare module "@earendil-works/pi-agent-core" {
  interface AgentMessage {
    role: "notification";
    text: string;
  }
}
```

### 3.9 Steering / Follow-up 队列

- **Steering**：在工具运行时中断 Agent，注入新消息
- **Follow-up**：在 Agent 完成当前工作后排队新任务
- 队列模式：`one-at-a-time`（默认）或 `all`
- 支持清空队列：`clearSteeringQueue()` / `clearFollowUpQueue()` / `clearAllQueues()`

### 3.10 工具定义

```typescript
const readFileTool: AgentTool = {
  name: "read_file",
  label: "Read File",  // UI 显示
  description: "Read a file's contents",
  parameters: Type.Object({
    path: Type.String({ description: "File path" }),
  }),
  executionMode: "sequential",  // 可选，覆盖全局设置
  execute: async (toolCallId, params, signal, onUpdate) => {
    const content = await fs.readFile(params.path, "utf-8");
    onUpdate?.({ content: [{ type: "text", text: "Reading..." }], details: {} });
    return {
      content: [{ type: "text", text: content }],
      details: { path: params.path, size: content.length },
    };
  },
};
```

**错误处理规范**：工具失败时 **throw error**，不要返回错误消息作为 content。抛出的错误会被 Agent 捕获并以 `isError: true` 的工具错误报告给 LLM。

### 3.11 低级 API

除了 `Agent` 类，Pi 还提供低级的 `agentLoop()` 和 `agentLoopContinue()`，返回 for-await-of 事件流：

```typescript
for await (const event of agentLoop([userMessage], context, config, undefined, streamFn)) {
  console.log(event.type);
}
```

低级 API 是观察性的，不等待异步事件处理完成。如果需要消息处理作为工具预检的屏障，使用 `Agent` 类。

### 4.3 技能系统（Skills）

Pi 实现了 **Agent Skills 规范**（与 Anthropic skills 兼容）。

#### 技能结构

```text
pdf-tools/
├── SKILL.md
├── scripts/
│   └── extract.sh
├── references/
│   └── formats.md
└── assets/
    └── template.json
```

#### SKILL.md 格式

```markdown
---
name: pdf-tools
description: Extract text and tables from PDF files. Use when reading, converting, or inspecting PDFs.
license: MIT
compatibility: requires pdftotext
metadata: { version: "1.0" }
allowed-tools: [bash, read]
disable-model-invocation: false
---

Read `references/formats.md` before converting a document.
Run scripts relative to this skill directory.
```

#### 技能加载机制

1. **启动时**：Pi 扫描配置的技能目录，将每个技能的 name + description + path 加入系统提示词（**不加载完整指令**）
2. **任务匹配时**：模型读取 `SKILL.md` 并遵循其指令
3. **强制加载**：`/skill:name` 命令，参数会追加为用户请求

这种设计的优势：详细指导只在需要时才进入上下文，节省 token。

#### 技能位置

- 用户目录：`~/.agents/skills/`
- 项目目录：`.agents/skills/`（从工作目录向上递归查找，到仓库根停止）
- Pi 包：package 中的 `skills/` 目录

## 五、pi-durable 持久化设计

pi-durable 是 Pi 的持久化层（实验性），核心思想：**所有内容在显示之前先提交到存储**。如果进程在 turn 中途崩溃，重新打开存储可以从断点继续。

### 5.1 核心概念

| 概念 | 描述 |
|------|------|
| **Harness** | 一个打开的存储 + 运行 Agent 的机器。所有变更通过原子提交，提交存储后才显示 |
| **Conversation** | 对话 transcript。`root()` 创建根对话；可创建更多并 fork |
| **Entry** | 不可变 transcript 记录：user message、model response、tool result、system prompt change、reset、自定义类型 |
| **Commit** | 原子写入。`conversation.commit((tx) => ...)` 可以同时追加 entries、编辑 documents、创建 tasks |
| **Document** | 类型化 JSON 状态，存储在 transcript 旁边，在 commit 中变更。内置：agent choices、provider session identity、running generation/tools、queued submissions、spend |
| **Task** | 持久化状态机，每步保存检查点，重启后从最后一个继续。每个 task 有 owner（conversation 或另一个 task） |
| **Submission** | 提交给 conversation 的内容（用户输入或 entry），可以等待 |
| **Turn / Run** | turn = 一次模型响应 + 其工具调用；run = 从输入到最终答案的 turns |

### 5.2 一次回答的 Entry/Task 序列

```
pi.generation → pi.system (仅当 prompt 或工具变更时), pi.assistant (tool calls)
pi.tool × n → pi.tool-result × n   (generation 拥有，等待它们)
pi.generation → pi.assistant (answer) → submission done
```

### 5.3 存储后端

| 后端 | 导入 | 说明 |
|------|------|------|
| Memory | `MemoryStorage` | 不持久化 |
| SQLite | `openNodeSqliteStorage(file)` | 单数据库文件，WAL 模式，commit  survives 进程崩溃 |
| JSONL | `openNodeJsonlStorage(directory)` | 追加-only 文件，可选 fsync |
| Cloudflare Durable Object | `openDurableObjectSqliteStorage(ctx.storage)` | Durable Object 的 SQLite 存储 |

### 5.4 崩溃恢复

```typescript
const harness = await Harness.open(await openNodeSqliteStorage("./session.sqlite"), { models, registry }, context);
const root = await harness.root(context);  // 上次的同一个 root
harness.resume();  // 继续上次进程未完成的运行
```

- 每个 conversation 有持久化的 UUIDv7（`pi.provider`），作为 provider 的 sessionId，支持 prompt cache 和 session affinity
- 相同 `requestId` 的重试提交返回已存在的 submission（幂等）
- `harness.submission(id)` 通过 ID 重新获取 submission

### 5.5 Reset / Handoff

```typescript
await root.reset(undefined, context);  // 从零开始
await root.reset("We were fixing the flaky login test. Continue.", context);  // 带交接笔记
```

Reset 启动新上下文，模型不再看到旧 entries，但旧记录保留在存储中。工具可以通过 `control: { handoff: "..." }` 请求同样的操作。

### 5.6 上下文压缩（Compaction）

```typescript
const id = await root.compact("Keep the failing test names", context);  // 手动
```

自动压缩配置：

```typescript
settings: {
  compaction: {
    enabled: true,
    reserveTokens: 16384,       // 超过 contextWindow - reserveTokens 时等待压缩
    keepRecentTokens: 20000,    // 大致保留多少最近上下文
    backgroundTokens: 32768,    // 低于此阈值时后台启动压缩；0 禁用
  },
}
```

- 压缩在后台进行，conversation 继续工作
- 摘要在 conversation 空闲时立即放置，否则在下一个 turn 边界放置
- provider 因上下文过长拒绝请求时，自动压缩并重试一次

### 5.7 Subagents / Child Tasks

- Subagent 工具创建子 conversation，ownership 归属 task
- 子任务可以 `waiting` 状态等待多个子任务完成，支持 `failFast` 策略
- 所有状态持久化，重启安全

## 七、设计哲学总结

### 7.1 核心原则

1. **做减法（Anti-Framework）**：不做框架，只提供 primitive。核心 Agent Loop 仅 949 行。
2. **一切可替换**：工具、上下文管理、技能、主题、UI 都是可替换组件。
3. **显式优于隐式**：不内置 sub-agents、plan mode 等功能，让用户自己构建或安装包。
4. **事件驱动**：所有 UI 更新通过事件系统，订阅者按注册顺序被等待。
5. **持久化优先**（pi-durable）：所有内容在显示之前先提交到存储。
6. **错误规范**：工具失败 throw error，不返回错误消息作为 content。

### 7.2 与 dsh 的对比

| 维度 | Pi Agent | dsh (DeepSeek Harness) |
|------|----------|------------------------|
| 定位 | 极简 Agent Harness | 企业级 Agent 框架 |
| 插件架构 | 无（扩展系统） | Cordis 插件内核，159 插件 |
| Agent Loop | 949 行，简单 | 复杂（turn/step 双层，10+ 事件瀑布） |
| Session | pi-durable（可选） | 自研 append-only SessionEvent log（必选） |
| 文档规范 | 常规 | 严格（字数预算、类型检查、md-wrap） |
| 学习成本 | 低（一下午读完核心） | 高（数周） |
| 团队 | 个人（Mario Zechner） | DeepSeek 官方团队 |

## 九、可移植到 studio 的设计（按优先级）

### 9.1 高优先级（核心改进）

#### 1. Agent Loop 事件驱动重构
**现状**：studio 的工具循环是简单的拦截→执行→回填，缺乏可观测性和可扩展性。
**Pi 的设计**：10 种事件（agent_start/end, turn_start/end, message_start/update/end, tool_execution_start/update/end），所有 UI 更新通过事件驱动。
**移植建议**：重构 studio 的工具循环为事件驱动，增加 `tool_execution_start/update/end` 事件，让 UI 可以实时显示工具执行进度（而不是等执行完才显示结果）。

#### 2. beforeToolCall / afterToolCall 钩子
**现状**：studio 的授权/策略是在执行前一次性判断，缺乏细粒度控制和结果后处理。
**Pi 的设计**：4 个钩子（beforeToolCall, afterToolCall, prepareRequest, finishTurn），可以在工具执行前后插入自定义逻辑。
**移植建议**：在 studio 的工具执行管线中增加 `beforeToolCall` 和 `afterToolCall` 钩子，用于：
- 更细粒度的授权控制（不仅是 allow/deny，还可以修改参数）
- 工具结果后处理（格式化、审计、日志）
- terminate 机制

#### 3. terminate 机制
**现状**：studio 没有跳过自动续跑的机制，工具执行完总是触发续跑。
**Pi 的设计**：工具可以返回 `terminate: true`，当批次中所有工具都 terminate 时跳过自动续跑。
**移植建议**：在工具结果中增加 `terminate` 字段，在 autoContinueWithPow 中检查——如果所有 pending 工具结果都 terminate，则不触发续跑。这对于"通知完成"类工具非常有用。

#### 4. 工具结果格式规范
**现状**：studio 的工具结果格式不统一（stdout/stderr/exitCode/argv/cwd 混在一起），UI 显示凌乱。
**Pi 的设计**：工具返回 `{ content: [{type:"text", text:...}], details: {...} }`，失败时 throw error（自动标记 isError）。
**移植建议**：统一 studio 的工具结果格式，区分 `content`（给模型看的）和 `details`（给 UI 看的元数据），失败时用 `isError: true` 标记。

### 9.2 中优先级（扩展生态）

#### 5. 技能系统（Agent Skills 规范）
**现状**：studio 的技能系统是自研的，格式不标准。
**Pi 的设计**：实现了 Agent Skills 规范（与 Anthropic skills 兼容），SKILL.md + frontmatter，启动时只加载 name+description，任务匹配时才加载完整指令。
**移植建议**：将 studio 的技能系统改为兼容 Agent Skills 规范，这样可以直接使用 Anthropic skills collection 和 Pi skills collection 中的技能。

#### 6. 包分发系统
**现状**：studio 没有扩展/技能的分发机制。
**Pi 的设计**：Pi packages（npm/git/local），将 extensions/skills/prompts/themes 打包分发。
**移植建议**：设计 studio 的包格式（可以简化，不需要 npm 分发，先支持本地目录和 git），让用户可以安装第三方扩展/技能。

#### 7. 上下文压缩（Compaction）
**现状**：studio 没有上下文压缩机制，长对话会超出 deepseek 的上下文窗口。
**Pi 的设计**：自动/手动 compaction，后台压缩，摘要在 turn 边界放置。
**移植建议**：在 studio 中增加上下文压缩机制——当对话接近上下文窗口时，自动总结早期消息并替换为摘要。这需要在页端拦截器中实现（因为对话由 deepseek 网页管理）。

### 9.3 低优先级（未来扩展）

#### 8. 多模型抽象（pi-ai）
**现状**：studio 仅支持 deepseek 网页。
**Pi 的设计**：pi-ai 统一 30+ 厂商 LLM API。
**移植建议**：如果 studio 未来扩展到其他模型（如直接调用 API 而不是注入网页），可以参考 pi-ai 的设计。但当前阶段不需要。

#### 9. 持久化设计（pi-durable）
**现状**：studio 的对话由 deepseek 网页管理，不需要自己持久化。
**Pi 的设计**：Entry + Commit + Document + Task，崩溃恢复。
**移植建议**：如果 studio 未来需要自己管理对话（脱离 deepseek 网页），可以参考 pi-durable 的设计。但当前阶段不需要。

#### 10. Steering / Follow-up 队列
**现状**：studio 没有中断/排队机制。
**Pi 的设计**：steering（工具运行时中断）+ follow-up（完成后排队）。
**移植建议**：可以在 studio 中增加 follow-up 队列——用户在 Agent 运行时输入的消息排队，等当前 turn 完成后自动发送。这对于长任务很有用。

## 十、不建议移植的设计

1. **pi-durable 全量**：studio 是注入式，对话由 deepseek 网页管理，不需要自己做持久化。
2. **pi-tui**：studio 是桌面应用，不需要终端 UI。
3. **chord**：太底层，studio 不需要应用组合运行时。
4. **多模型抽象**：studio 目前定位是 deepseek 网页增强，不需要多模型。
5. **Cordis 插件架构**：Pi 没有用 Cordis（dsh 才用），studio 也不需要。Pi 的扩展系统更简单，更适合 studio。
