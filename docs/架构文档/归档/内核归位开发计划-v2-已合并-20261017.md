### 0.3 v2 改了什么

v1 回答的是「怎么把真源从网页收回宿主」。v2 回答四个 v1 没问的问题：

1. **收回之后怎么知道它在正常工作？** → 日志（§5）+ 遥测（§6）
2. **出问题时怎么复盘？** → 诊断能力（§7）
3. **拿什么改代码、拿什么验证？** → 工具集（§8）+ harness（§9）
4. **谁保证这些不被悄悄改坏？** → 管道统一（§10）

**一句话判断：v1 是「可靠地调用工具」的计划，v2 要把它变成「可靠地改代码、并且知道自己改得对不对」的计划。**

## 5. 阶段 L · 日志系统（结论：不够完善，缺一整层）

### 5.1 现状诊断（三条硬证据）

| 事实 | 取法 | 结论 |
|---|---|---|
| **无 logger 抽象** | createLogger/class Logger/interface Logger/winston/pino/logLevel 全仓 **0 命中** | 没有任何一层能统一控制级别、格式、去向 |
| **104 处裸 console** | Select-String -Pattern "console\.(log|warn|error|debug|info)" | 日志散落各文件，无法按模块开关、无法结构化、无法落盘 |
| **5 个日志相关文件各管一摊** | audit.ts 安全审计 / bot/audit-meeting.ts 会议审计 / inject/trace-store.ts 页面侧追踪 / shared/harness-metrics.ts 指标 / ui/studio-mcp-dialog.ts UI | **无一是通用日志**；且 trace-store 在 src/inject/，**宿主侧没有对应物** |

**判断：日志系统不是「不够完善」，是「没有系统」。** 现在是 104 个孤立输出点，出问题只能靠肉眼翻终端。

### 5.2 三个具体后果

1. **生产环境无日志可查**：Tauri 打包后 console 去向不明，用户报「卡住了」时宿主侧零证据。
2. **无法按模块降噪**：mcp-controller.ts 里既有有用的 console.error，也有 5 处**零日志的静默 catch**。没有级别控制，只能全开或全关。
3. **跨进程断链**：页面侧有 trace-store（traceId 体系），宿主侧没有。一次工具调用从页面到宿主，**traceId 在边界处断裂**。

### 5.3 目标形态

```
src/shared/logger.ts          ← 单一日志入口（唯一允许调 console 的文件）
  ├── createLogger(module)    → { debug, info, warn, error, child(bindings) }
  ├── 结构化字段：ts / level / module / traceId / sessionId / tool / durationMs / err
  ├── 级别：trace < debug < info < warn < error（env STUDIO_LOG_LEVEL 控制，默认 info）
  ├── 输出：dev → 人读；prod → JSONL 单行
  └── 落盘：<appData>/logs/<yyyy-mm-dd>.jsonl，按天轮转，保留 14 天

src/host/logger-sink.ts       ← 宿主侧落盘 sink（Node fs）
src/inject/logger-sink.ts     ← 页面侧 sink（复用 trace-store 的存储）
```

**关键设计：traceId 是第一等字段，不是可选字段。** 页面侧 createTrace 生成的 id 通过 WS 首帧带给宿主，宿主所有日志自动带上它。这是 §7 诊断能力的地基。

### 5.5 裁决点

- 建议：**先自研**。需求窄（本地 JSONL + 级别 + traceId），引 pino 多一层依赖和 transport 配置；自研接口与 pino 兼容，将来换只换实现。

- 建议：**gate 加 vitest（ci:true）**。理由：不跑测试的「一键闸门」名不副实。代价是 gate 变慢（~150s），可接受。

**D13 · live 档归属**：
- 现状：`live-nudge-rate` 是 gate 的可选腿。
- 建议：**保持本地可选、CI 永不跑**（需要真机网页，CI 跑不了）。在 legs.ts 里标 `ci: false, local: true`。

### 11.3 执行顺序（四批）

| 批次 | 内容 | 理由 |
|---|---|---|
| **第 1 批** | L-1, L-2, C-3, T-1, T-2 | 全部是「别的任务都依赖它」的地基。日志与遥测 store、上下文预算，三者互不阻塞可并行 |

### 11.4 为什么第 1 批不含 C-1

C-1（edit-engine）看起来最该先做，但它依赖 `logger` 才能排查「改到一半失败」这类问题。**没有日志的编辑引擎，出问题是黑箱。** 所以 L-1 必须先行——这也是 v2 与「只做 edit-engine」那种直觉判断的差别。

## 12. 能力等级判断（v2 完成后）

### 12.1 三级对照

| 等级 | 现状（M0–M2） | 完成 v2 阶段 C | 完成 v2 全部 |

| L2 中型 feature（5–8 文件 + 跑测试） | 偶发能成，必须人盯 | 多数能成 | **多数能成且可自证** |
| L3 真实代码库维护 | 不行 | 勉强入门 | **勉强可做** |
| L4 独立完成项目 | 不行 | 不行 | 不行 |

### 12.2 「可自证」是什么意思

v2 与 v1 的关键差别不是「做得更多」，而是**做完之后能自己知道做对没做对**：

- v1 之后：TaskLoop 跑完，判停靠 `continuation-prompt` 的信号 → 它「以为」自己完成了
- v2 之后：TaskLoop 跑完，`test.run` 返回结构化结果 → 它**知道**测试是绿是红

这一条差异，把 L2 从「偶发能成、必须人盯」推到「多数能成、可自证」。

### 12.3 v2 仍然不解决的（诚实标注）

| 不解决 | 为什么 |
|---|---|
| L4 独立完成项目 | 基础模型能力 + 上下文窗口是硬约束，工程设施无法突破 |
| 跨仓库/跨服务重构 | 需要分布式上下文，单机应用不适用 |
| 真实并发编辑冲突 | 单用户桌面场景，暂不需要 |
| 恶意代码执行隔离 | 沙箱是 v1 就 CUT 的项，推给 studio 侧（见 §3.2） |
