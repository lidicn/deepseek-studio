## 2. Dry Run 配置（2 bot 最小验证）

### 2a. 窗口配置 `bot-windows.json`

**Windows 路径坑**：Rust `dirs::config_dir()` 在 Windows = `AppData\Roaming`，不是 `~/.config`。bot-windows.json 必须放在 `C:\Users\<user>\AppData\Roaming\deepseek-studio\bot-windows.json`（Rust 才能读到）。Node 侧的 config.json + personas 仍在 `~/.config/deepseek-studio/`。

```json
{
  "bots": [
    { "botId": "frontend-expert", "visible": true, "dataDir": "profiles/frontend-expert" },
    { "botId": "backend-expert", "visible": true, "dataDir": "profiles/backend-expert" }
  ]
}
```

- `botId` = persona 名（registry.create 时 botId=persona 名，窗口 label 也 = botId）
- `visible: true` — dry run 阶段需可见（手动扫码登录）；PoC 阶段可改 false
- `dataDir` — 独立 WebView2 user data folder，Cookie/localStorage 不串号
  - 每个 bot 需在该窗口里**单独扫码登录 DeepSeek**（首次手动登录，之后 Cookie 缓存）
- **serde camelCase**：JSON 用 `botId`/`dataDir`/`visible`（camelCase），Rust 字段是 `bot_id`/`data_dir`（snake_case），靠 `#[serde(rename_all="camelCase")]` 映射。不加 rename → empty botId → "bot window skipped"

### 2b. 聊天室配置 `~/.config/deepseek-studio/config.json` 加 `chatRooms` 字段：

```json
{
  "port": 8760,
  "host": "127.0.0.1",
  "secret": "<你的 secret>",
  "token": "<你的 token>",
  "workspaceRoot": "E:\\NAS",
  "policyMode": "auto",
  "chatRooms": [
    {
      "roomId": "dry-run-1",
      "roomName": "Dry Run 测试室",
      "hostPersona": "host",
      "memberPersonas": ["frontend-expert", "backend-expert"]
    }
  ],
  "chatRoomMaxDepth": 1
}
```

> **注意**：`memberPersonas` 里的 persona 名必须与 `~/.config/deepseek-studio/personas/<name>/prompt.md` 的目录名一致。当前 personas/ 下有 `frontend-expert` / `backend-expert` / `audit-expert`。dry run 用前两个。
>
> `hostPersona` = `"host"` 但 personas/ 下没有 host 目录——要么补一个 `personas/host/prompt.md`，要么 dry run 不设 hostPersona（无 @ 时不兜底，宁可不答也不乱答）。

### 建议 dry run 配置（无主持人兜底，更干净）

```json
{
  "chatRooms": [
    {
      "roomId": "dry-run-1",
      "roomName": "Dry Run 测试室",
      "memberPersonas": ["frontend-expert", "backend-expert"]
    }
  ],
  "chatRoomMaxDepth": 1
}
```

## 3. Dry Run 步骤

### Step 1：确认 personas 目录

```bash
ls ~/.config/deepseek-studio/personas/
# 应看到 frontend-expert / backend-expert（audit-expert 是 PoC 用，dry run 不需要）
# 每个目录下有 prompt.md
```

### Step 2：写入 chatRooms 配置

把上面的 JSON 配置合并进 `~/.config/deepseek-studio/config.json`（保留现有 token/secret 等字段）。

### Step 3：启动宿主

```bash
npm run tauri:dev   # 编译 Rust + 启动 Node sidecar + 开 3 窗口
```

启动日志应出现：
```
[deepseek-studio] 聊天室模式启用：Dry Run 测试室
[deepseek-studio] 本地 HTTP API on http://127.0.0.1:8760
[studio] bot windows config: 2 entries          ← 无 "empty botId" skip
[studio] bot window created: label="frontend-expert" visible=true
[studio] bot window created: label="backend-expert" visible=true
```

> **devUrl 坑**：`tauri.conf.json` 的 `devUrl` 不能是 `localhost:8756`（Tauri dev 会等前端 dev server 卡死）。改成 `"https://chat.deepseek.com"`。
>
> **exe 替换坑**：重新编译时如果旧 `deepseek-studio.exe` 还在跑，cargo 报 `failed to remove exe (os error 5)`。先 `taskkill //F //IM deepseek-studio.exe` 再重启。
>
> **EADDRINUSE 8760**：exe 内部 sidecar Node 与 Tauri beforeDevCommand 的 Node 都绑 8760，sidecar 会 crash-restart 循环。**不影响使用**——beforeDevCommand 的 Node 稳定服务着 WS。可忽略日志里的 crash 循环。

### Step 4：经 WS 发消息

**WS 路径坑**：agent-channel 在 **`/agent-ws`**（不是 `/studio`）。`/studio` 是 page-runtime（tool-call 通道），连上去发 `send` 消息无回复。

```bash
# 连 /agent-ws（不是 /studio！）
ws://127.0.0.1:8760/agent-ws?token=<token>
# 发
{ "type": "send", "roomId": "dry-run-1", "text": "@backend-expert 你怎么看当前后端架构？", "reqId": "1" }
```

连上立即收到 `state` 消息（含 `bots: [main, frontend-expert, backend-expert]`）。发消息后收到：
1. `ack`（`ok:true, data:{roomId}`）
2. `event: user`（含 persona prompt + 上下文，botId=被@的 bot）
3. `event: status`（"已发送，等待模型回复…"）
4. `event: assistant`（真实回复文本，~7s）
5. `event: done`（botId 标记）
6. `event: user`（摘要 prompt，botId=main）→ `status` → `assistant`（摘要，~10s）→ `done`

### Step 5：验证检查点

| # | 检查点 | 预期 | 失败排查 |
|---|---|---|---|
| 1 | frontend-expert bot 被唤醒 | 日志有 `[desktop-host] onAssistantReply ... botId=frontend-expert` | 检查 bot 预创建：log 有无「聊天室成员 bot frontend-expert 创建/加载人设失败」 |
| 2 | frontend-expert 回复进聊天室 | `getMessages('dry-run-1')` 有 bot 回复消息 | 检查 SSE 回复捕获：assistant 事件是否 emit |
| 3 | backend-expert 没被唤醒（@specific） | members 只有 frontend-expert | 检查路由：@解析是否正确 |
| 4 | 回复内容基于 persona prompt | 回复提及前端视角（组件/状态管理） | 检查人设加载：persona prompt 是否注入 |
| 5 | @all 全员参与 | `@all 大家评估下` → 两个 bot 都回 | 检查 buildParticipants：两个 bot 是否都在 registry |
| 6 | 接力标记识别 | frontend 回复含 `@backend-expert` → pendingHandoff 含 backend-expert | 检查 HandoffParser：原始回复是否保留 @标记 |

### Step 6：拉取消息历史验证

```javascript
// 经 agent-channel 或直接调 host
const msgs = host.chatRoomRuntime?.getMessages('dry-run-1');
// 应有：1 条 user 消息 + N 条 bot 回复消息
// user 消息 content 是净内容（@frontend-expert 被剥离）
// bot 消息 senderType = 'sub-bot'（botId !== 'main'）
```

## 5. 已知风险点（真机可能暴露的问题）

| 风险 | 症状 | 对策 |
|---|---|---|
| WebEngine 贴文速度 | deepseek.com 输入框粘贴/提交可能有延迟 | AgentLoop 有 watchdogMs，若超时调大 |
| SSE 回复捕获时序 | assistant 事件在 send resolve 后才 emit？ | 代码层已验证同步 emit，真机若异步则 listener 需等 |
| 多窗口 profile 隔离 | 两个 bot 的 deepseek 登录态冲突 | v0.24 data_directory 隔离，真机验 |
| 人设 prompt 太长 | personaBlock + contextText 超 4000 字截断 | SlotRuntime.run 有 MAX_TASK_TEXT_CHARS=4000 截断 |
| 摘要触发 | 长对话后 ContextEngine 应触发摘要 | CB 任务 B2/B3，等 CB 交付 |
