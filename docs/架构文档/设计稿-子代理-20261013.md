# 设计稿：studio 子代理（Subagent）

> 目标：在 deepseek-studio 中实现子代理能力，做到「上下文隔离 + 真并行 + 可审计 + 不封号」。
> 核心结论：**studio 走 Engine-first，不是 Window-first** —— 这是与 cuckoo-code 的根本分野。

---

## 0. 第一原则：按「引擎」隔离，不按「窗口」隔离

cuckoo-code 的教训（实测自 app.asar）：`createSubagentProfile(parent)` 把 `id / providerId / partition` 全部继承父窗口 → 子代理=同账号第二个窗口 → 同账号多开 → DeepSeek 风控封号。它的「并行提效」被风控锁死，只剩上下文隔离。

studio 已有的 `src/host/engine/model-engine.ts` 提供了 cuckoo 没有的东西：

```ts
export interface ModelEngine {
  readonly name: 'web' | 'api';
  health(): Promise<{ ok: boolean; reason?: string }>;
  send(text: string): Promise<EngineSendResult>;
  waitForNextReply?(): Promise<EngineSendResult>;
}
```

- `WebEngine`：驱动 chat.deepseek.com 页面（免费，XML 工具标签协议，有风控）
- `ApiEngine`：DeepSeek 官方 API（原生 function calling，无多开概念，有明确 rate limit）

**所以 studio 的子代理默认跑在 `ApiEngine` 上，与主对话的 `WebEngine` 完全解耦。** 主对话继续用免费网页版，子代理用 API —— 既拿到并行，又不碰风控。这是 cuckoo 做不到的。

---

## 1. 核心概念

| 概念 | 职责 | 落位 |
|---|---|---|
| `AgentDefinition` | 子代理定义（md + frontmatter） | `.studio/agents/*.md` |
| `SubAgentRegistry` | 扫描/校验/索引定义 | `src/host/subagent/registry.ts` |
| `SubAgentRuntime` | 一次子代理运行实例 | `src/host/subagent/runtime.ts` |
| `runAgent` 工具 | 主对话委派入口 | `src/host/tool-definitions.ts` 注册 |
| `EnginePool` | 引擎分配 + 并发锁 | `src/host/engine/pool.ts` |

**复用而非重造**：子代理的执行体就是一个独立的 `createAgentLoop()` 实例（`agent-loop.ts` 已经是自包含状态机），只是换了 engine、换了 systemPrompt、换了 tool 子集、换了 maxSteps。

---

## 2. AgentDefinition 规范

`.studio/agents/code-review.md`：

```markdown
---
name: code-review
description: 需要对项目做只读代码审计、定位潜在 bug 时委派给此子代理
engine: api            # ★ studio 核心增量：api | web | inherit
model: deepseek-chat   # engine=api 时指定
maxSteps: 30
timeoutMs: 600000
tokenBudget: 200000
riskCap: read          # 只能收紧，不能放宽父级
tools:                 # 工具白名单（缺省=继承父级全部只读工具）
  - local_file_read
  - local_file_stat
  - shell_exec
---

你是一名代码审计专家。执行方式：
1. 先用 glob/grep 搜索关键文件，不要逐行读整个项目
2. 定位可疑区域后再精读
3. 输出：问题定位 + 证据 + 修复建议，控制在 500 字内
```

**与 cuckoo 的关键差异**：cuckoo 的 md 只有 name/description/prompt；studio 额外有 `engine` / `model` / `tokenBudget` / `riskCap` —— 账号/平台是**可指定的**，不是硬编码继承。

## 3. 运行时架构

```
主循环 AgentLoop(engine=WebEngine, session=main)
  │
  └─ 工具调用 runAgent(code-review, task)
       │
       └─ SubAgentRuntime
            ├─ 1. 选引擎：EnginePool.acquire(agent.engine)
            │       api  → 直接开（真并行）
            │       web  → 进全局串行队列（防风控）
            ├─ 2. 建工具视图：ToolRegistry.filter(agent.tools, agent.riskCap)
            ├─ 3. 起 AgentLoop(engine=child, systemPrompt=agent.prompt, maxSteps)
            ├─ 4. 事件经 toolEventBus 打 subagentId 标签回流面板
            └─ 5. 只回结构化摘要给父
```

---

## 4. 并发模型（防封号的根本）

| 引擎 | 并发策略 | 依据 |
|---|---|---|
| **api** | 真并行，受 `maxConcurrentSubagents` + 速率限制 | API 无多开概念，有明确 rate limit |
| **web** | **全局单飞锁** `webEngineMutex`，一次只允许一个 web 会话发请求 | 网页版同账号多窗口=风控 |

**这条 `webEngineMutex` 是 studio 相对 cuckoo 的决定性差异**：cuckoo 允许子代理窗口和主窗口同时发请求；studio 强制「同一时刻只有一个 web 会话在跑」，从机制上消灭同账号并发。

---

## 5. 隔离三档

| 档位 | 主引擎 | 子引擎 | 上下文 | 并行 | 封号风险 |
|---|---|---|---|---|---|
| L1 上下文隔离 | web | web | ✅ 隔离 | ❌ 串行 | 无（串行锁保证） |
| L2 引擎隔离 | web | **api** | ✅ 隔离 | ✅ 并行 | 无 |
| L3 全隔离 | api | api | ✅ 隔离 | ✅ 并行 | 无 |

推荐默认 L2：主对话吃免费网页版额度，子代理吃 API 额度换并行。

## 6. 父子协议

```ts
// 工具签名
runAgent(name: string, task: string): Promise<SubAgentResult>

interface SubAgentResult {
  ok: boolean;
  summary: string;              // 只回摘要，不回全量 transcript
  artifacts?: { path: string; op: 'read'|'write' }[];
  toolCalls: number;
  steps: number;
  usage?: { promptTokens: number; completionTokens: number };
  error?: string;               // 结构化错误，不让父循环崩溃
}
```

- **只回摘要**：全量 transcript 落盘，父上下文只进 summary —— 这是「上下文隔离」的兑现方式。
- **失败隔离**：子代理异常被 runtime 捕获并转成 `{ok:false, error}`，绝不上抛压垮主循环。
- **深度限制**：`depth=1`，子代理不能再调 `runAgent`（对应 cuckoo 的 `isSubagentWindow` 防递归）。

## 7. 安全与治理

复用 `tool-registry.ts` 的风险分级，子代理侧**只能收紧不能放宽**：

```ts
subagentRiskCap <= parentRiskCap          // 子不能提权
subagentTools ⊆ parentTools               // 子不能拿到父没有的工具
subagentOrigins = parentOrigins           // origin 白名单继承
```

- `privileged` 工具（shell_exec / local_file_write）需 agent 定义**显式声明** + 用户**一次性授权**，且永远走 `execution: 'host'` 侧。
- 子代理**不得修改父级授权状态**（authority.ts 单向）。
- 审计：每次 run 落盘 `.studio/agents-runs/<runId>.jsonl`（tool-call 记录 + 摘要），供事后追溯。

---

## 8. 成本、取消、生命周期

- **预算**：每个子代理有 `tokenBudget` / `maxSteps` / `timeoutMs`，任一超支即中止并回报 `error: 'budget-exceeded'`。
- **全局预算**：一次主对话可派生的子代理总数上限（防失控）。
- **取消级联**：父 `stop()` → 遍历活跃子 runtime → `abort()`。
- **看门狗**：复用 `agent-loop.ts` 既有的 `watchdogMs`（默认 15 min）。
- **崩溃隔离**：子 runtime 崩溃不影响父；父可从 `{ok:false}` 决定重试或换策略。

## 9. UI

- 主面板把子代理渲染成**嵌套卡片**：`name / task / 状态 / 步数 / 摘要`。
- 事件流已带 `subagentId`，天然支持树形展示（`tool-event-bus.ts` 已有 emitAsync 管线）。
- 点开卡片 → 看该 run 的 transcript（读 `.studio/agents-runs/<runId>.jsonl`）。

## 10. 落地路线

| 阶段 | 内容 | 依赖 |
|---|---|---|
| P1 | `AgentDefinition` + `SubAgentRegistry`（纯定义层） | 无 |
| P2 | `ApiEngine` 实现（当前是 stub）+ `SubAgentRuntime` | model-engine |
| P3 | `EnginePool` + web 串行锁 | P2 |
| P4 | `runAgent` 工具注册 + 父子协议 | P3 |
| P5 | UI 树 + 审计落盘 | P4 |
| P6 | 预算/取消/深度硬化 | P5 |

**第一步最小可验证**：P1+P2 —— 定义一个 `code-review` agent，用 `ApiEngine` 跑通「委派 → 独立上下文 → 回摘要」，不碰 web 锁。

## 11. 与 cuckoo-code 的对比

| 维度 | cuckoo-code | studio（本设计） |
|---|---|---|
| 子代理账号 | 硬编码继承父窗口 | **engine/model 可指定** |
| 平台 | 跟随父窗口 | **可跨引擎（web↔api）** |
| 并行 | 同账号多开 → 封号 | API 真并行 / web 串行锁 |
| 上下文隔离 | ✅ | ✅ |
| 工具集控制 | agent.tools | agent.tools + **riskCap 收紧** |
| 防递归 | isSubagentWindow | depth=1 |
| 成本控制 | maxTurns | maxSteps + tokenBudget + timeout |
| 审计 | 无明确落盘 | transcript jsonl |
| UI | 嵌套窗口 | 嵌套卡片 + 事件标签 |

---

## 12. 一页决策

1. **Engine-first**：子代理按引擎隔离，不按窗口 —— 从根上绕开同账号多开。
2. **默认 api 引擎跑子代理**：主对话吃免费网页版，子代理吃 API 换并行。
3. **web 引擎必串行**：`webEngineMutex` 是防封号的生命线，不可绕过。
4. **只回摘要**：全量落盘，父上下文只进 summary —— 这才是子代理的核心价值。
5. **复用而非重造**：`createAgentLoop` + `ToolRegistry` + `toolEventBus` 已经够用，子代理只是换参数再实例化一次。
