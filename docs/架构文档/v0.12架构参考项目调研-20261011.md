## 一、核心发现：三个参考项目

### 1. Mainframe（qlan-ro/mainframe）—— 最值得参考

**项目定位**：AI 开发环境桌面应用，驱动 coding-agent CLI（Claude Code / Codex）

**架构模式**：Tauri 2 薄壳 + Rust daemon sidecar

```
┌─────────────────────────────────────────────────────────┐
│  Tauri 2 Shell（薄 supervisor）                          │
│  ┌──────────┐  ┌────────────────┐  ┌────────────────┐ │
│  │ WebView  │  │ sidecar.rs     │  │ 桌面原生功能    │ │
│  │ (React)  │  │ daemon 进程监管 │  │ terminal/pty   │ │
│  │          │  │                │  │ preview/截图    │ │
│  │          │  │                │  │ updater/自动更新│ │
│  └────┬─────┘  └───────┬────────┘  └────────────────┘ │
│       │                  │ spawn (sidecar)               │
│       │ HTTP/WS :31415  ▼                               │
│       │          ┌───────────────┐                       │
│       └─────────►│ Rust Daemon   │                       │
│                  │ (axum HTTP+WS)│                       │
│                  │ 21 crates      │                       │
│                  └───────────────┘                       │
└─────────────────────────────────────────────────────────┘
```

**关键设计决策**：

| 决策 | 说明 |
|------|------|
| **Tauri 壳不链接 daemon** | 两个独立 Cargo workspace，Tauri 只 spawn daemon 作为 sidecar 子进程 |
| **UI 直连 daemon** | WebView 里的 React 通过 HTTP/WS 直接和 daemon 通信，不经过 Tauri IPC（除了少量桌面原生功能） |
| **daemon 可独立运行** | headless 模式可用，mobile app 和 CLI 子命令依赖此能力 |
| **从 Node 逐行移植到 Rust** | 21 个 crates，大部分 crate 文档注释写着 "ported from packages/core/src/..." |

**崩溃恢复机制**（重点参考）：

1. **FileChildRegistry**：launch 进程和 tunnel 共享一个 on-disk 的 `managed-children.json`，崩溃后的下一次启动可以回收所有孤儿进程
2. **panic hook**：异常退出前做同样的 reaping
3. **启动后 stray-child sweep**：bind 端口后扫描并清理上次崩溃遗留的子进程
4. **background-task reconciliation**：启动后恢复后台任务状态
5. **liveness scheduler**：定期检查子进程存活性

**自动化引擎**：

- `mainframe-automations` crate
- when-trigger / do-step 模型，通过 trait "ports" 执行
- 支持 GitHub issue/webhook 集成触发

### 2. Racc（liu1700/racc）—— 三 crate 共享架构

**项目定位**：AI 终端桌面应用（Claude Code / Codex 的 PTY 封装）

**架构模式**：三 crate Rust workspace，同时支持 Tauri 桌面和 headless server

| Crate | 类型 | 用途 |
|-------|------|------|
| **racc-core** | Library | 共享业务逻辑：AppContext、EventBus、TransportManager、DB、SSH |
| **racc-server** | Binary | Headless HTTP/WebSocket server（Axum），服务 React 前端 + JSON-RPC |
| **racc** | Tauri app | 桌面应用，用 Tauri IPC 包装 racc-core |

**关键设计**：

- **AppContext 共享**：Tauri 和 server 都构造同一个 `AppContext` struct，确保行为一致
- **EventBus 抽象**：`BroadcastEventBus`（tokio::sync::broadcast），Tauri 桥接到 WebView `AppHandle.emit()`，server 桥接到 WebSocket
- **前端 Transport 抽象**：`TauriTransport`（invoke/listen）vs `WebSocketTransport`（JSON-RPC over WS），自动检测 `__TAURI_INTERNALS__`
- **单进程 Tauri 架构**：Rust 后端和 React 前端在一个进程，前端通过 invoke() 调用 Rust

**对我们的启示**：EventBus 抽象和前端 Transport 抽象的设计思路，可以用于未来如果要做 headless server 模式。

### 3. Picoframe（tomjn/picoframe）—— Sidecar 持久化服务模式

**项目定位**：插件化桌面应用框架

**架构模式**：Tauri Rust + Bun sidecar 持久化 localhost HTTP server

```
Tauri (Rust) ──spawn──► sidecar server (Bun)
      ▲                         │
      │──── GET /health ───────►│
      │──── POST /command ─────►│
      │◄═══ GET /events SSE ════│
```

**关键设计**：

| 方面 | 方案 |
|------|------|
| **传输** | 127.0.0.1 TCP + bearer token（不用 Unix socket，Windows 支持不一致） |
| **握手** | 子进程写 handshake file `{port, token, pid}`，父进程读取 |
| **认证** | 256-bit 共享密钥，每个请求带 `Authorization: Bearer <token>` |
| **孤儿防护（双向）** | ① Rust 侧 RunEvent::Exit + drop 时 kill 子进程 ② 子进程 watch `PARENT_PID`，父进程消失时 self-exit |
| **进度推送** | SSE (`GET /events`)，Tauri 侧桥接到前端 toast |

**对我们的启示**：双向孤儿防护机制非常值得参考——即使父进程被 SIGKILL，子进程也能自我了结。

## 二、架构选型建议

### 推荐方案：Mainframe 模式（Tauri 薄壳 + Node daemon sidecar）

**核心理念**：不把 Node 宿主重写为 Rust，而是让 Tauri 成为一个薄 supervisor，把现有的 Node 宿主作为 sidecar 子进程管理。

```
┌──────────────────────────────────────────────────────────┐
│  Tauri Shell（Rust，薄壳）                                │
│  ┌──────────┐  ┌─────────────────┐  ┌─────────────────┐ │
│  │ WebView  │  │ sidecar 监管     │  │ 桌面原生功能     │ │
│  │ (deepseek│  │ - spawn Node     │  │ - 自动更新       │ │
│  │  网页+注入)│  │ - 健康检查       │  │ - 系统托盘       │ │
│  │          │  │ - 崩溃自动重启    │  │ - 窗口管理       │ │
│  └────┬─────┘  │ - 优雅关闭       │  │ - 开机自启       │ │
│       │        └────────┬────────┘  └─────────────────┘ │
│       │                 │ spawn (sidecar)                  │
│       │ WS :8760        ▼                                 │
│       │          ┌───────────────┐                        │
│       └─────────►│ Node Daemon   │                        │
│                  │ (现有宿主)     │                        │
│                  │ src/api/main.ts│                        │
│                  │ src/host/*     │                        │
│                  └───────────────┘                        │
└──────────────────────────────────────────────────────────┘
```

### 为什么选这个方案而不是全 Rust 迁移？

| 维度 | 全 Rust 迁移 | Tauri 薄壳 + Node sidecar |
|------|-------------|---------------------------|
| **工作量** | 巨大（~6000 行 Node 宿主 → Rust，21+ crates） | 小（Tauri 侧新增 sidecar 监管 ~500 行 Rust） |
| **风险** | 高（授权链、工具执行、MCP、记忆等核心逻辑重写容易出 bug） | 低（Node 宿主已经稳定运行，只改进程管理方式） |
| **MCP stdio** | 需要 Rust 重写 MCP 客户端 | Node 侧已有成熟实现，不动 |
| **Python 沙箱** | 需要 Rust 重写或 sidecar | Node 侧已有实现，不动 |
| **打包分发** | 单二进制（但需要打包 Node runtime 或 sidecar） | Tauri 安装包 + Node sidecar 二进制（用 pkg 或 nexe 打包） |
| **崩溃恢复** | 同进程崩溃 = 全挂 | Tauri 壳存活，daemon 崩溃可自动重启 |
| **自动化调度** | 需要 Rust 实现 | Node 侧用 node-cron 即可，几行代码 |

**结论**：全 Rust 迁移的收益（单二进制、内存效率）不足以抵消风险和工作量。Mainframe 模式能在 1-2 周内获得 v0.12 的核心收益（崩溃恢复、自动化、打包分发准备），而不需要重写任何核心逻辑。

## 三、v0.12 具体落地计划（基于 Mainframe 模式）

### Phase 1：Tauri 侧 sidecar 监管（核心）

**新增 Rust 模块**：`src-tauri/src/sidecar.rs`

| 功能 | 实现要点 |
|------|----------|
| **spawn daemon** | 用 `std::process::Command` 或 `tauri-plugin-shell` 的 `Command::sidecar()` 启动 Node daemon |
| **健康检查** | 启动后轮询 `GET http://127.0.0.1:8760/health`，超时 30s |
| **崩溃自动重启** | 监控子进程 exit，退出后延迟 2s 重启，最多重试 5 次 |
| **优雅关闭** | `RunEvent::Exit` 时发 SIGTERM 给 daemon，等待 5s 后强制 kill |
| **孤儿防护** | daemon 侧加 `process.on('disconnect')` 和 parent PID 监控，父进程消失时 self-exit |

**daemon 打包**：
- 用 `pkg` 或 `nexe` 把 `src/api/main.ts` 打包成单二进制 `studio-daemon.exe`
- 配置 Tauri `externalBin` 把 daemon 打进安装包

### Phase 2：自动化调度（Node 侧）

**新增模块**：`src/host/automation.ts`

| 功能 | 实现 |
|------|------|
| **定时任务存储** | 复用现有 storage，`automations.json` 存任务定义（cron 表达式 + 动作） |
| **调度引擎** | `node-cron` 或 `node-schedule`，启动时加载所有任务 |
| **动作类型** | ① 发送消息到对话（chat-send）② 执行工具（shell/file/mcp）③ 调用 webhook |
| **任务管理 API** | `automation.list/create/delete/toggle`，通过 WebSocket 暴露给 UI |
| **执行日志** | 每次触发记录执行时间、结果、错误，持久化存储 |

### Phase 3：桌面原生功能增强

| 功能 | 优先级 | 说明 |
|------|--------|------|
| **系统托盘** | P1 | 最小化到托盘，托盘菜单（显示窗口/退出/打开日志） |
| **自动更新** | P1 | `tauri-plugin-updater`，配置更新源 |
| **开机自启** | P2 | `tauri-plugin-autostart`，设置里可开关 |
| **窗口状态记忆** | P2 | 记住窗口大小/位置，重启后恢复 |
| **日志查看器** | P3 | 设置面板里直接查看 daemon 日志 |

### Phase 4：崩溃恢复验证

| 测试场景 | 预期 |
|----------|------|
| daemon 进程被 kill | Tauri 检测到退出，2s 后自动重启，WebView 重连 WS |
| daemon 崩溃（uncaught exception） | 同上，且崩溃日志写入 tauri-real.log |
| Tauri 窗口关闭 | daemon 收到 SIGTERM，优雅关闭（5s 超时后强制 kill） |
| Tauri 被 SIGKILL | daemon 检测到父进程消失，self-exit（孤儿防护） |
| 重启应用 | 窗口位置/大小恢复，daemon 启动，WS 连接建立，自动化任务重新加载 |

## 五、风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| Node daemon 打包后体积大（~50MB） | 高 | 可接受，Tauri 安装包本来就 ~10MB，加 Node runtime 后 ~60MB |
| daemon 重启后 WS 连接丢失，工具调用中断 | 中 | 页端加重连逻辑，daemon 侧工具执行状态持久化（短期可接受中断） |
| sidecar 进程在 Windows 上权限问题 | 中 | 用 `tauri-plugin-shell` 的 sidecar 机制，已处理 Windows 权限 |
| 自动化任务执行时用户不在电脑前 | 低 | 任务执行结果写入日志，用户回来后可查看；需要用户交互的任务跳过 |
