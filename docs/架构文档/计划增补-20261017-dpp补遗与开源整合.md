## 2. 开源 agent 能整合什么？—— 三类整合，代价差一个数量级

先说结论：**能整合，但绝大多数应该通过 MCP 整合，而不是「把别人的 agent 嵌进来」。**
原因：studio 的核心资产是**授权链 + 同意闸 + 审计**（`policy` → `requestConsent` → `hostTools`）。任何「整包嵌入的 agent runtime」都会自带一套工具执行路径，**绕开这条链**——这是 QD 跨域第 28 条警告过的形状。

### 2.1 三类整合方式

| 类 | 形态 | 代价 | 风险 | 适配 studio 吗 |
|---|---|---|---|---|
| **A · MCP 工具** | 外部进程通过 stdio/HTTP 提供工具，studio 作为 MCP **客户端** | 低（已有 `mcp-controller.ts`） | 中（第三方 MCP 能执行任意代码 → 需信任分级） | ✅ **首选** |
| **B · ACP 客户端** | studio 作为 **ACP client**，把外部 coding agent 当子进程驱动 | 中（JSON-RPC + 会话协议） | 中高（agent 自带工具执行，需包 consent） | 🟡 **可选，做「外部引擎」** |
| **C · 嵌入式 runtime** | 把 OpenHands / SWE-agent 之类整套跑起来 | 高（Python 运行时 + 沙箱） | 高（完全另一套执行链） | 🔴 **不建议** |

### 2.2 A 类：MCP 服务器（最便宜的能力解锁）

| 项目 | 补 studio 什么 | 与现有任务的关系 | 建议 |
|---|---|---|---|
| **Serena**（`oraios/serena`，MIT，Python，`uvx` 起） | **LSP 级符号检索与精确编辑**：`find_symbol` / `find_referencing_symbols` / `rename_symbol` / `replace_symbol_body` / `insert_after_symbol`，30+ 语言 | **直接替代 `C-5`（code-index 自建 3d）与 `K-5`**，还顺带强于 `K-3/K-4`（纯 glob/grep） | ✅ **强烈建议先试点**：比自己写 LSP 索引便宜一个数量级 |
| **Playwright MCP**（微软） | 浏览器自动化（点击/填表/取快照） | 替代 `FS-18` 的「诊断」面，并给出「模型可驱动浏览器」的路径 | 🟡 先接「诊断」用，控制面留到 `D24` 决定 |
| **GitHub MCP** | 仓库/PR/issue 操作 | 补 `K-7`（repo.status）之外的远端操作 | 🟡 需要 token 管理 + 信任分级 |
| **filesystem / git MCP** | 通用文件与 git 操作 | 与 `K-3/K-4`、`K-7` 重叠 | ⚪ 已有自研能力时不必接 |

**A 类的三个硬约束**（必须写进任务，否则就是引狼入室）：

1. **第三方 MCP 必须过 `FS-6` 的能力租约**（并发上限 + 超时回收），否则 N 个 MCP 就是 N 条不受控执行链。
2. **第三方 MCP 的每个工具必须映射到 `risk` 档位**（`TA-2` 的 schema 尺要能读 MCP 的 tool 声明），否则「闸按标签走」会被 MCP 绕过。
3. **第三方 MCP 的启动必须过 consent**：现在 `mcp.test` 已被 `59220b8` 改成 `privileged`，但**首次连接一个新 MCP server 时用户看不见「它是什么、能干什么」**——需要一条「MCP 信任分级」的裁决（见 `D29`）。

### 2.3 B 类：ACP（把外部 coding agent 当引擎）

ACP（Agent Client Protocol）要点（据官方文档）：

- 标准化「编辑器 ↔ coding agent」；**本地 agent 作为子进程、JSON-RPC over stdio**；远程 agent 走 HTTP/WebSocket（远程支持仍在推进）。
- **复用 MCP 的 JSON 表示**，并补了「显示 diff」这类 agentic UX 类型。
- 目标是「像 LSP 那样解耦」——editor 支持 ACP 就自动支持整个 ACP agent 生态。

对 studio 的意义：**studio 已经是「编辑器 + 宿主」的混合体**，做 ACP client 能立刻拿到 claude-code / gemini-cli / codex / opencode 等 agent 作为**可选引擎**，用于 studio 自有 loop 不擅长的场景（大重构、长任务）。

**但有一个必须先解决的问题**：ACP agent **自己执行工具**（它有自己的 shell/edit 权限），这与 studio 的 consent 三层闸冲突——和当初 `M1-3` 裁决不接 pi 是**同一个理由**（见 `D-011`）。

⇒ 所以 B 类的正确定位是：**「沙箱化的外部引擎」**——ACP agent 只能在工作区的一个**受限子目录**里跑（DD-1 的授权目录 + `workspace.contains` 双闸），且它的**每一次文件写入都要落轨迹**（`TR-3`）。做不到这两条，就别做。

### 2.4 C 类：嵌入式 runtime（不建议）

| 项目 | 形态 | 为什么不建议嵌 |
|---|---|---|
| **OpenHands SDK**（4 包：`sdk` / `tools` / `workspace` / `agent_server`） | Python；本地模式直接跑，生产模式跑在沙箱；`agent_server` 暴露 REST + WebSocket | 它自带 workspace + security + tool 全链，等于在 studio 里再装一个 studio；且要 Python 运行时 |
| **SWE-agent** | Python + shell 沙箱 | 同上，且面向 benchmark 而非桌面产品 |
| **aider** | CLI + 库 | 可以**当命令用**（包成 skill / `shell.job`），但别当 runtime 嵌 |
| **Cline / Roo Code** | VS Code 扩展 | 形态不兼容（依赖 VS Code 宿主） |
| **goose**（Block，Rust） | MCP-native 的本地 agent | 形态较接近，但仍是「另一个 agent」——若要试，走 B 类（子进程）而非嵌库 |

## 7. 计划够不够完善？还该加什么？

### 7.1 已经不需要再加的（防止过度设计）

- **任务粒度**：165 → 现在 177 项，落点/验收/估时齐全，再细就是伪精度。
- **阶段覆盖**：M0–M3 / C / L / TL / DG / OP / K / H / P / TA / RT / TJ / DP / AB / TR / FS / DD / OS —— 十八个系列已经覆盖「内核、能力、观测、安全、设施、整合」六个面。
- **裁决点**：D1–D30，每个卡点都有二选一。

### 7.2 还缺的**两件**（我认为这是最后的真空白）

| # | 缺什么 | 为什么它是空白 | 建议 |
|---|---|---|---|
| **1** | **「用户可见的进度与状态」这一层** | 全计划里所有观测（日记/轨迹/诊断）都是**给开发者看的**。但 studio 是给**一个人日常用**的桌面应用——用户需要知道「现在在跑什么、卡在哪、要不要我点什么」。现在只有一个 busy 态和同意弹窗 | 加 **UX-1**：任务面板（当前回合/步骤/工具/耗时/可中断），数据直接用 `TR-3` 的轨迹 + `AB-9` 的闸状态，**不新增存储**。0.5~1d |
| **2** | **「首次使用」与「坏了怎么办」的恢复路径** | `OP-5` 有崩溃恢复，`OP-3` 有配置迁移，但**没有「用户视角的恢复入口」**：配置坏了→怎么重置？记忆库坏了→怎么导出/重建？MCP 连不上→怎么诊断？ | 加 **UX-2**：`/v1/recover` 一组最小恢复动作（重置配置/重建记忆索引/清理轨迹/导出诊断包）+ 设置面板入口。1~1.5d |

**除了这两件，我建议停止追加**——继续加任务只会拉长工期，而不是提高成功率。真正的瓶颈已经不是「计划不够细」，而是「已完成 19d、剩余 162d」这个比例。
