## 1. 先纠一个「照抄会踩」的结论：dpp 的方案在 Studio 上收益小一个量级

PM 给的 dpp 事实是：**42 个工具 → catalog 24,084B**（≈573 B/工具），目标 ≤8,000B。

我**直连真机配置的两个 MCP 服务器**（TVPilot / Autoforge）取真实 `tools/list` 实测：

| server | 工具数 | 全量行字节 | 均摊 |
|---|---|---|---|
| TVPilot | 26 | **1,947 B** | 75 B/工具（描述 10–17 字） |
| Autoforge | 36 | **10,620 B** | 295 B/工具（最长 **436 字**） |
| **合计** | **62** | **12,568 B** | 203 B/工具 |

**仅名字索引（62 个名字）= 950 B**。

→ **dpp 是 573 B/工具，Studio 是 203 B/工具**，且**长度极不均衡**（长描述集中在 Autoforge）。
dpp「目录占 prompt 97.6%」在 Studio 不成立 —— Studio 注入块的大头是
**固定能力说明 `TOOL_CAPABILITY_PROMPT` 4,557 B**，不是工具目录。

## 2. Studio 侧注入块的真实结构（落点）

入口：`src/inject/main-world-interceptor.ts` → `buildCapabilityPrompt(taskText)`（`:951`）

```ts
export function buildCapabilityPrompt(taskText = ''): string {
  const blocks = [TOOL_CAPABILITY_PROMPT];      // 4,557 B 固定
  const mcpBlock = formatMcpToolsBlock();        // ≈5,390 B（含 62 工具）
  if (mcpBlock) blocks.push(mcpBlock);
  const skillsBlock = formatSkillsBlock(taskText);
  if (skillsBlock) blocks.push(skillsBlock);      // 通常 0 B（只给点名的）
  blocks.push(TOOL_CAPABILITY_END_MARKER);
  return blocks.join('\n\n');
}
```

### 2.1 大头一：MCP 块（`formatMcpToolsBlock()` `:855`）—— 唯一真正值得瘦身的一块

当前形态（**全部 62 个工具无条件平铺**）：
```
## 已配置的 MCP 工具（可直接通过 mcp_call 调用）
### 服务器：<serverId>
- <name> — <description>
...
调用方式：<mcp_call>{"serverId":"服务器名","tool":"工具名","args":{...}}</mcp_call>
```

### 2.2 大头二：`TOOL_CAPABILITY_PROMPT`（4,557 B 固定）—— **不是目录，是能力说明**

**不适用 dpp 的 top-k 选择**：它是固定文本（62 行），与用户任务无关，
无论选不选都在。压缩它属于「精简提示词」，**不是「目录预算」**，
**本卡不做**（PM 说「本卡只做第 1 条：目录预算 + top-k + 名字索引 + 回滚开关」）。

### 2.3 skills 块 —— **已经是「只给点名的」，无需再瘦身**

`formatExplicitSkillsBlock()`（`:921`）只在用户**明确点名**（`/skill-id` 或独立词）
时才列；没点名返回空串。所以 12 个 skills 通常贡献 0 B。
→ **dpp 的「名字索引保发现性」对 skills 不适用**（发现性由显式点名的规则保证）。

### 2.4 `TOOL_CATALOG_TEXT`（1,167 B / 10 工具）—— **只进续跑 prompt，首轮不注入**

`buildContinuationPrompt(originalTask, execForThisTurn, TOOL_CATALOG_TEXT)`（`:2438`）。
真机日志：续跑请求体 `len=16325`（注入后 26272 B）。
它只有 10 个 Studio 固定工具，**预算机制对它无意义**。

## 4.1 实现期发现的两个真问题（已修，都有实测依据）

### 问题 1：名字索引带描述 → 光索引就超预算

dpp 的索引行是「`- name: 短描述`」（40 字截断），因为它只有 42 个工具、描述短。
Studio 实测：62 个工具的描述较长，索引带描述 → **索引自身 ≈4.7 KB，光索引就超了 3,000 B 预算**
（这是**用例跑出来的**，不是我估的：第一版按 dpp 原样带描述，A1 直接红 `expected 7712 to be ≤ 3000`）。

**修法**：索引**只留名字**（`- name`）。「保发现性」的**最小充分形式就是名字**——
模型只要知道「有这个工具」就能按名字调用，描述是锦上添花。
**代价**：仅名字索引从 4.7 KB 降到 **950 B**（62 个名字），预算立刻宽裕。

### 问题 2：描述长的工具系统性吃亏（top-k 的真副作用）

实测（62 工具、预算 3,000、任务点名 `af_action_07`）：
按「分数 + 预算累加」时，它前面已排了 28 个**短描述**工具（TVPilot 组），
预算在轮到它之前就耗尽 → **它只剩名字、模型看不到描述**。
而「用户点名了某个工具」正是最该给全描述的场景。

**修法**：新增 `pinnedTools` 语义 —— 任务文本里以**独立词**出现的工具
（名字或 serverId）**无条件**拿完整行，且**回填降级时永不降级它**。
独立词边界（`af_action_1` 不命中 `af_action_12`）有专门用例锁定。

**效果**：点名的 `af_action_07` 现在进 full 段。

## 7.1 ⚠️ 给 Verify 页内脚本的两处配合修正（放窗前必须改，否则表会误导人）

我逐行核对了 `logs/verify-f1f2/inject-segments-live.mjs` 与我实现的分段边界，

### ① 致命：`mcpToolLines` 会把「名字索引行」一起数进去 → 前后都是 62，看不出压缩效果

脚本 `:91`：
```js

```
`- ` 开头的行有**两种**：
- 完整行：`- <name> — <description>`（含 `—`）
- **名字索引行（新段）**：`- <name>`（**不含** `—`）

→ 改前 62 全是完整行 = **62**；改后 29 完整 + 33 索引 = **还是 62**。
**这张表会让人以为「完全没压缩」**，而实际字节从 12,568 B 降到 2,390 B。

**修法**（拆成两个读数）：
```js
const idxH = mcpPart.indexOf('### 其他工具（仅名称）');
const mcpFullPart = idxH >= 0 ? mcpPart.slice(0, idxH) : mcpPart;
const mcpIndexPart = idxH >= 0 ? mcpPart.slice(idxH) : '';
// 完整行：只数带 — 的；索引行：单独数
mcpFullToolLines: (mcpFullPart.match(/^- .+ — /gm) ?? []).length,
mcpIndexToolLines: (mcpIndexPart.match(/^- /gm) ?? []).length,
mcpIndexHeaderPresent: idxH >= 0,
```
（`mcpBlockBytes` 不用改 —— 它量的是整段，**本来就该包含索引**。）

### ② 记忆段恒为 0：标记匹配不上

```js

```
注入层实际输出是 **`## 已有记忆`**（`src/inject/untrusted-memory.ts:106`），

（`untrusted-memory.ts:10-11`）。
`## 已有记忆` **不含**子串 `## 记忆`（`## ` 后面是「已有记忆」）→ **正则匹配不上**。

→ `memPart` 恒为 `''`、`memoryBlockBytes` 恒为 **0**、`userPromptBytes` 把记忆+原文混在一起。

## 7.2 ⚠️ 一个**必须先对齐的口径**：`mcpBlockBytes` 有两个数，别混

我用注入层真实模块离线构造了 62 工具、预算 3,000 B 的 MCP 块，套 Verify 的分段逻辑实测，
发现**「MCP 块字节」有两个不同口径**，差 **234 B**：

| 口径 | 值 | 包含什么 |
|---|---|---|
| **A. 选择器口径**（`selection.bytes.total`） | **2,390 B** | 只有 **full 行 + 名字索引**（1,864 + 526） |
| **B. 实际块口径**（Verify 脚本量到的 `mcpBlockBytes`） | **≈2,631 B** | A + 固定开销：标题行 63 + 服务器分组标题 48 + 调用方式行 95 + 换行 ≈ 28 |

**差额来源（实测拆解）**：固定开销 = 标题行 63 B + `### 服务器：`×2 共 48 B +
调用方式行 95 B + 换行 ≈ 28 B = **234 B**。

> 我之前报的「2,390 B」是**口径 A**；Verify 脚本量到的是**口径 B**。
> **PM 的 A1 判据「MCP 块 ≤ 3,000 B」按哪个口径都达标**（B = 2,631 ≤ 3,000），

**为什么两个口径会差**：`selectCatalogTools` 的 `budgetBytes` 管的是
「**full 行 + 名字索引**」的额度；固定开销（标题/分组/调用方式）**不计入**预算，

且 dpp 的初始选择阶段同样直接用 `budgetBytes`、只在回填降级时用 `budget - reserve`）。
Studio 的固定开销实测仅 234 B，`reserveBytes = 600` 够用。

**改前对照**（口径 B，同一算法）：**12,568 B → 2,631 B，压掉 79%**。
