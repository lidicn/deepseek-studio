## 2. 改动

### 2.1 `src/capabilities/chat-read.ts`（页端能力）

1. **选择器换成真机普查配方**（命中优先），旧选择器保留兜底：
   `.ds-virtual-list-visible-items > *` → `.ds-virtual-list ._81e7b5e` → 旧 6 条。
2. **正文取「文本量最大的后代」**：DeepSeek 的气泡是消息项下的独立子节点，
   直接取 `textContent` 会把整条 turn 拼起来。
3. **带标识**：整体 `sessionId`（URL `/a/chat/s/<uuid>`）+ 每条 `id` / `index` → 协议层能对账
   「这段文本属于哪一轮」（PM 的 J4）。
4. **fail-closed**：没有一条非空文本 → `ok:false / no-messages-found`，不再返回「ok:true + 空」（R2）。
5. **`ensureLatest` 参数**：把虚拟列表滚到底部，强制挂载最新消息项（缓解 R4）。

### 2.2 `src/host/engine/web-engine.ts`（宿主引擎）

1. **`readConversation()` 取代 `readLastMessage()`**，返回三态：
   - `hard`（能力跑不通，如 `no-page-for-dom-capability`、传输失败）→ 走 S4 重连，重连耗尽 → `disconnected`；
   - `empty`（`no-messages-found`，能力跑通但这会儿没消息）→ **继续等**，不是错误；
   - `ok` → 有内容。
   > 这条区分是 R2 的正反面：`empty` 不再被当成「读到空」，`hard` 也不会被当成「还没到」而空转 120s。
2. **剔除自己的气泡**：本轮 prompt 原文已知，含 prompt 文本的消息一律不算答案（R3）。
3. **基线取在插入之后**：此时 DOM 里最后一条是用户气泡，剔除后拿到的就是「上一轮答案」；
   候选文本变了 = 本轮答案到了。
4. **SSE 优先**：若 `getAutoReply()` 有**本轮新**的回复（`seq` 比本轮开始时大）→ 以它为准直接收。
5. **超时不给旧答案**：本轮从未见到新文本 → 返回空内容 + `completion='truncated'`，
   **绝不**拿上一轮答案冒充本轮结果。
6. `waitForNextReply()` 的 DOM 路径同步改（同 1/5）。

## 3. 一个必须说清的架构事实（影响 J7 判读）

**普通回合恒为空**」；`onAssistantReply` 的两处推送（:2407 / :2469）都在 auto-continue 续跑分支里。

- 若真机复验 J7 判 FAIL（答案当时未挂载进 DOM），根因是「注入层没把普通轮的 final-answer
  推给宿主」，修复点在 `src/inject/**`（**UI 的域，我未动**）→ 需要 PM 开一张 inject 侧小卡。

## 7. 已知副作用与风险

1. `ensureLatest` 会把虚拟列表滚到底部——在 Studio 自己的窗口里属预期行为，
   但如果用户正看着这个窗口，滚动位置会被拉到底。
2. 剔除 prompt 用「文本包含 prompt」判定，prompt 短于 8 字符时不生效（探针 prompt 远长于此）。
3. 普查样本只有一个会话，混淆类名（`._81e7b5e` / `._72b6158`）可能随站点发版变化；
   主选择器用的是**语义类名**（`.ds-virtual-list-visible-items > *`），类名兜底只是第二道保险。
4. 用户会话原文一律不进仓库/报告（PM 规则）：本文件只写结构、类名与计数，不含原文。

### 8.2 新增：双源读取（答案源优先级）

`chat-read` 现在同时读两个来源并各自带基线：

1. **Studio 镜像（SSE 派生）** — `.ds-sc-message-list` 里的 `.ds-sc-msg-assistant` → `data.mirror.lastAssistantText`
   - 由我们自己的注入层按拦截器解析的 `final-answer` 渲染，**不受 DeepSeek 虚拟列表挂载影响**；
   - 这是「SSE 为准」在宿主侧唯一可达的实现（不需要改 `src/inject/**`）。
2. **DeepSeek 真实 DOM** — 虚拟列表项，剔除本轮 prompt 与能力前导注入后的最后一条。

宿主 `readConversation()` 返回 `{ text, mirrorText }`；循环里
`mirrorChanged` 优先于 `domChanged`，两者都与**各自基线**比较，变了才算本轮新内容。

## 9. 第三轮（按 Verify R4 复验的三处缺陷改，20261031 22:50）

R4 读数先记清楚：**不是读不到答案**了。模型 1–2s 就答（`extracted[8]: F1V3-MVW` + `quasi_status FINISHED`），
`chat-read` **64/64 次**采样都带 `mirrorCount=15 / mirrorLastLen=13 / mirrorHasUpper=true`
（答案确实在 `data.mirror` 里），但对外仍然 500 / **130 213ms**。三处缺陷全在引擎调度：

| Verify 指出的缺陷 | 本轮改动 |
|------------------|----------|
| ① `waitForNextReply` 的路径 A（`consumeAutoReply`）在普通轮**永远不 fresh**，把整个 `stepTimeoutMs`（120s）吃光，之后路径 B 一次都没跑 | 路径 A 从「独占预算的前置阶段」改成**每轮 poll 先看一眼的快路径**；A 与 B 共用一个 deadline、同一个循环（`web-engine.ts` `waitForNextReply`） |
| ② 路径 B 只读 `snap.text`，不读已经取到的 `snap.mirrorText` | 路径 B 改为「镜像优先、DOM 兜底」，与 `send()` 同一套候选逻辑 |
| ③ 基线取在发送之后（模型 1–2s 就答完 → 漏判） | **基线移到 `chat-send` 之前**，并且判「本轮」改用**身份信号**：镜像助手条数 `mirrorCount` 增长（或文本变化），不再只靠「文本 ≠ 基线」 |

对应新增用例（`tests/desktop/web-engine-f1.test.ts` 7、8 两条）：

- 7：`consumeAutoReply` 永不 fresh + 镜像 60ms 后 +1 → 必须在 ~2s 内拿到答案（旧实现会空转满预算）；
- 8：基线在发送前 + 答案 40ms 后到达 → 必须判到（R4 的 130s 回归）。

## 10. 第四轮（按 Verify R5 复验改，20261031 23:10）

R5 的硬事实：答案 **2s 内**就进了镜像（正控 15 条 → 发送后首次轮询 16 条并恒定、`mirrorHasUpper=true`），
页内命中链也对（`DIV.ds-sc-markdown` ← `DIV.ds-sc-msg-assistant` ← `DIV.ds-sc-message-list`），
但对外仍是 **129.8s / 500**。

### 10.1 决定性缺陷（Verify 指得对）

`waitForNextReply()` 在**自己开始时**重取基线；那时 `mirrorCount` 已经是 16（含答案），
于是「条数增长 / 文本变化」全为假 → `candidate=''` → 空转满 `stepTimeoutMs` → 500。
上一轮我只把 `send()` 的基线前置了，**续跑这条没落**。

**修法**：`send()` 在发送前取的本轮基线存入引擎级 `roundBaseline`
（`{mirrorCount, mirrorText, text, at}`，10 分钟 TTL），`waitForNextReply()` **优先复用它**，
只在没有或陈旧时才自己读一条；每轮结束时把「本轮结束状态」写回 `roundBaseline`，
多轮续跑逐轮推进、不会越比越旧。

### 10.2 自查：为什么会进续跑（Verify 第 2 点）

查了触发链，**不是工具计数被拉高**：

- `task-loop.ts:248`：`useWait = round > 1 && previousToolCalls > 0`；
- `previousToolCalls` 来自 `EngineSendResult.toolCalls`，只统计**模型发起的工具调用**
  （`page-runtime.ts:453` 的 `onToolCall` 只在收到页端 `tool-call` 报文时触发）；
- 引擎自己 dispatch 的 `chat-read/chat-insert/chat-send` 走的是宿主→页端方向，**不进这个计数**；
  `loaded 12 skills` / `loaded 62 MCP tools` 是页端日志，不是 tool-call 报文。

所以第 1 轮确实有模型工具调用 → 进续跑是**正确行为**，失败点只在基线（10.1 已修）。
