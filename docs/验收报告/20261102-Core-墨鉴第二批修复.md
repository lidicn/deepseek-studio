## 二、R15-001：Git 破坏性命令守卫

### 缺陷

`policy.ts` 的 `git-destructive` 正则写的是 `clean\s+-fd`，**只匹配 `-fd`**：

| 命令 | 修复前 | 修复后 |
|---|---|---|
| `git clean -fd` | 命中 | 命中 |
| `git clean -xfd` | **逃检** | 命中 |
| `git clean -fdx` | **逃检** | 命中 |
| `git clean -df` | **逃检** | 命中 |
| `git clean -d -f` | **逃检** | 命中 |
| `git clean --force` | **逃检** | 命中 |

（历史上就有 `git checkout -- .` 丢未提交改动的前科，破坏性命令守卫不能再漏。）

### 修法

```
git\s+(?:push[\s\S]*?(?:--force|-f\b)
      |reset\s+--hard
      |clean\s+(?:-\w+\s+)*-\w*f\w*        ← 选项可空格分隔、任意组合、必须含 f
      |clean\s+(?:-\w+\s+)*--force\b
      |checkout\s+(?:--\s+)?\.
      |restore\s+(?:--\s+)?\.)
```

### 测试（表驱动，`tests/desktop/policy-git-destructive.test.ts`）

- **16 条必命中**：`clean -fd` / `-xfd` / `-fdx` / `-df` / `-xffd` / `--force` / `-f -d` / `-d -f` / `checkout -- .` / `checkout .` / `restore .` / `restore -- .` / `reset --hard` / `reset --hard HEAD~1` / `push --force` / `push -f origin main`；
- **10 条不误伤**：`status` / `log` / `diff` / `add .` / `commit -m` / **`clean -n`（dry-run 不删东西）** / `checkout feature-branch` / `restore --source=HEAD file.ts` / `push origin main` / `reset --soft HEAD~1`。

## 三、R15-002：`python.exec` 在 auto 档的风险检测（核实**成立**）

### 核实过程

| 事实 | 证据 |
|---|---|
| `python.exec` 不在 `PROCESS_TOOLS` | `policy.ts`：`PROCESS_TOOLS = ['shell.exec', 'mcp.test']` |
| → 不进 `isProcessTool` 分支 | 该分支才调 `detectRisks` |
| → auto 档直接落到 `not-governed allow` | `EXECUTION_TOOLS` 只在 **workspace 档**硬拒 |
| 结论 | **auto 档下 `python.exec` 的代码文本从不经过任何风险检测** |

比审计原文更严重：不是「绕过了风险检测」，而是**整个检测分支都进不去**。

### 修法

1. `evaluatePolicy` 新增 `python.exec` 分支：auto / ask 档按 `params.code` 调 `detectRisks`，命中即 `require-consent` + `reason='risk-detected'`；full 档放行但如实记 `riskFlags`（可审计）。
2. **新增 Python 专属风险模式** `python-destructive`（原模式只认 shell 命令名 `rm`/`rmdir`/`del`/`erase`，`shutil.rmtree` / `os.remove` 等一个都不匹配）：

```
\b(?:shutil\s*\.\s*rmtree|os\s*\.\s*(?:remove|unlink|rmdir|removedirs)
  |pathlib\s*\.\s*Path\s*\([^)]*\)\s*\.\s*(?:unlink|rmdir)|send2trash)
```

### 测试（5 条）

auto 档破坏性代码 → `require-consent` + `riskFlags` 含 `python-destructive`；auto 档普通代码 → `allow`；ask 档 → `require-consent`；workspace 档 → 仍硬拒（行为不变）；full 档 → `allow` 但 `riskFlags` 如实记录。

## 四、R2-2 / R2-4：KV 数据丢失

### R2-2（退出前丢写入）

原实现只有 100ms 防抖定时器，`stop()` 不 flush → 退出前最后 100ms 窗口内的写入**静默丢失**。

修法（`desktop-host.ts`）：

1. 新增 `flushKvNow()`：清定时器 + 落盘待写批次（`pendingKvSet` / `pendingKvRemove`）；
2. `stop()` 里 **`await kvWaitIdle()` → `await flushKvNow()`**。

**实测发现还有第二个丢失窗口**：`kvSet` 的第一步是 `await kvGet(key)`（首载），stop 发生在它之前时，值还没进 `pendingKvSet` → 光 flush 落盘的是**空批次**。所以又加了**在途计数**（`kvBegin`/`kvEnd`/`kvWaitIdle`），`stop()` 先等在途操作全部结束。

### R2-4（首载竞态）

原实现首载 `Object.assign(kvCache, await kvBackend.readAll())` —— 若首载**等待期间**有人 `kvSet`，磁盘旧值会**覆盖**内存新值。

修法：新增 `kvWrittenDuringLoad` 集合，首载时**只填未被写过的键**。

### 测试（2 条）

- R2-2：页端 `kv-set` 拿到 `kv-result` 回执（即值已到宿主）后**立刻** `stop()` → 落盘文件含该键；
- R2-4：磁盘预置旧值 → 写入新值 → 读回必须是**新值**。

> 一条如实记录：R2-2 的用例**第一版是红的**。排查发现是**测试的时序问题**——我在 `kv-set` 发出后立刻 `stop()`，此时请求**还在网络上没到宿主**，宿主手里没有数据可落盘。用调试脚本确认（`kv-result ok:true` → stop → 文件内容正确）后，把用例改成「等回执到达再 stop」，这才是 R2-2 的真实场景（「值已进宿主、但防抖窗口未到」）。
>
> 顺带发现一个**本卡范围外**的边界：**stop 时仍在网络上的 WS 消息会丢**。这属于「退出时在途请求」问题，不是 R2-2 说的「退出前 100ms 窗口」，未在本卡处理。

## 五、R3-6 / R3-7 / R3-8 / R3-10：悬挂与未握手

### R3-6 / R3-7（超时必须回执页端）

**协议缺一条消息**：原来宿主超时只结算自己的 Promise，页端那边：
- 同意弹窗一直挂在屏幕上，用户**还能点**「同意」，但宿主已判超时拒绝 → **点了没反应**；
- dispatch 的对端 pending 永久悬挂。

修法：

1. **协议新增 `consent-abort`**（宿主 → 页端）：`{ type:'consent-abort'; callId; reason }`；
2. 宿主：consent 超时 → 发 `consent-abort`；dispatch 超时 → 回 `tool-call-result{ok:false, error:'page-timeout'}`（与页端→宿主的 `result` 对称）；
3. 页端 `host-client.ts`：登记同意弹窗句柄（`consentHandles`），收到 `consent-abort` → `dispose()` 关掉弹窗（不再回 decision）；已决策则从表里摘除。

### R3-8（`tool-call` 孤儿）

原来页端发来的 `tool-call` 在宿主侧**不登记、无超时、不受 `failAllPending` 管辖** → 执行卡住时页端 pending 永久悬挂；页端断开时宿主还在跑、结果发给死 socket。

修法：新增 `pendingToolCalls` 表 + `toolCallTimeoutMs`（默认 60s）+ 纳入 `failAllPending`；执行返回时用 `settleToolCall()` 判定是否已被超时/断连结算（避免重复回执）。

### R3-10（入站 `ready` 校验）

原来只有 `result` / `consent-decision` 校验 `!rec.ready || rec.untrusted`，而 `kv-*` / `tool-call` / `runtime-envelope` **没有校验** → 连上但从不发 hello 的本机进程可直接读写用户 KV 或投递工具调用。

修法：新增统一集合 `REQUIRES_READY`，作为**前置检查**放在分支链之前；未握手时对需要回执的消息回 `page-not-ready`（`kv-*` → `kv-result`，`tool-call` → `tool-call-result`）。

> **一个我自己踩的坑（已修）**：第一版把守卫写成 `else if (REQUIRES_READY.has(msg.type))` 分支 —— `else if` 链**只走一个分支**，这会把 `kv-*` / `tool-call` 的正常处理**整个吞掉**（工具调用永远收不到回执 → 超时）。这正是 UI 报的那 4 例失败的根因。改成**前置检查**（`else if (REQUIRES_READY.has(msg.type) && (!rec.ready || rec.untrusted))`）后，`tool-bridge` / `consent-whitelist-wire` 恢复 15/15。
>
> **安全门没有放宽**：未握手 → 仍然不执行（回 `page-not-ready`），并且我在 `host-r2r3-guards.test.ts` 里**锁住了这条**（两条用例：未握手 `kv-set` 不写盘、未握手 `tool-call` 回失败不执行）。

### 测试（`tests/desktop/host-r2r3-guards.test.ts`，6 条）

R2-2、R2-4、R3-6（同意请求已发出且未被作废）、R3-7（dispatch 请求已发出）、R3-10 两条（未握手 → `page-not-ready` + 不写盘/不执行）。
