## 0. 一句话结论

中文查询不再按空白切 token：CJK 连续段走 **bigram**、拉丁/路径仍整段、`「」『』《》""` 包裹的片段作为**点名短语**直接参与匹配；FTS / LIKE / 无库降级三条分支**同源**派生 token。红 → 绿已走完，记忆域 12 文件 154 条回归全绿，`tsc --noEmit` EXIT=0。

## 1. 根因复核（自己核过，不是照抄转述）

| 位置 | 现状 | 后果 |
|---|---|---|
| `src/host/memory/core.ts:76`（`toFtsQuery`） | `query.split(/\s+/)` → 每 token 包 `"…"` 用 OR 连 | 中文长句只有一个长 token → trigram **短语**要求整段出现 → 失配 |
| `src/host/memory/retrieval.ts:75`（LIKE 分支） | 同样 `q.split(/\s+/)`，模式 `%token%` | `%整句%` → 失配 |
| `src/host/memory/retrieval.ts:95`（降级路径） | 同样按空白切 | 内存降级下行为一致地错 |

137 字中文任务 → 约 5 个 token，且都是长串 → FTS 与 LIKE 双双落空 → 召回集为空或只剩含长路径 token 的无关记忆 → **两条完全不同的中文任务选出逐字节相同的记忆块**（真机读数 3,687 字符相同）。根因成立。

补充一条复核时发现、真机读数里没说全的**第二半原因**：即使命中了点名条目，`sortRows` 按 `pinned → user → updated_at` 排，而 `memory.select` 只取前 12 条（`desktop-host.ts:821`，`limit: 12`）→ 一条较老的点名记忆仍可能被挤出注入窗口。所以只改分词不够，还要让点名条目在**非置顶组内**提前。

## 3. 实现口径（默认取值 + 回退口径，已写进 `retrieval-tokens.ts` 文件头注释）

**默认（v2 口径）**
- CJK 连续段 → **双字切分 bigram**；拉丁串 / 路径 → **按空白整段切**（口径不变）
- `「…」「『…』《…》""''` 包裹的片段 → 作为**点名短语**直接当 token 参与匹配（用户显式点名必须召回）
- CJK bigram 沿整句**等距采样**（不是只取句首）→ 专名落在句尾也能覆盖
- 单字 CJK 段：长句里不收（避免 `%工%` 这类噪声 token）；但**整条查询就这一个字**时保留（旧口径能召回，不能平白丢能力）

**回退口径**
- 环境变量 `STUDIO_MEMORY_TOKENIZER=legacy` → 回到旧空白切分口径（与改前字节级一致）
- 每次查询现读 env → **回滚不需要重启宿主**

**上界（护栏，防 FTS 查询/ LIKE 扫描爆炸）**

| 常量 | 值 | 说明 |
|---|---|---|
| `MAX_CJK_BIGRAMS` | 40 | LIKE 侧召回主力 |
| `MAX_CJK_TRIGRAMS` | 6 | FTS 侧，走索引但短语贵 → 少而精 |
| `MAX_LATIN_TOKENS` | 6 | 两侧共用 |
| `MAX_QUOTED_PHRASES` | 4 | 点名片段条数 |
| `MAX_QUOTED_DECOMPOSED` | 6 | 每个点名片段的分解 token |

截断优先级：点名片段 → CJK bigram → 拉丁；触发时 `truncated = true` 供观测。

**为什么 FTS 与 LIKE 取不同子集仍是"同口径"**：`memories_fts` 是 `tokenize='trigram'`（`core.ts:45`），2 字符 token 在该索引下**必然失配**（既有注释 `retrieval.ts:34-40` 已记）。所以 FTS 侧只放 ≥3 字符 token，LIKE 侧放全部短 token —— 但两侧都从**同一份分词结果**派生，既有纪律「两分支必须同口径」不破。

## 4. 性能与实际上界（本机实测，304 行库）

脚本：`logs/verify-exit/f5-profile3.cjs`

```
FTS5 trigram ：≈ 12 ms 固定 + ≈ 4 ms/短语   （1→17.8ms、8→44.1ms、24→156ms）
LIKE         ：≈ 0.3 ms/token              （16→4.4ms、32→7.1ms、64→19.2ms、136→53.4ms）
全表无过滤   ：2.8 ms
```

结论：**LIKE 每个字符覆盖的性价比比 FTS 高约一个数量级** → 召回主力放 LIKE（bigram 40 个），FTS 只留 6 个短语承担 bm25 排序与保险。

按存储上限 `MAX_MEMORIES = 500`（`src/host/memory/types.ts:97`）折算最坏规模：FTS ≈ 12 + 6×4 = **36 ms**，LIKE ≈ 50 token × 0.3 ms × 500 行折算 ≈ **24 ms** → 合计 **≈ 60 ms**，留在页端 120 ms 预算内。

`MEM_SELECT_WAIT_BUDGET_MS = 120`（`src/inject/main-world-interceptor.ts:285`）**一个数没动**，且有一条跨域只读断言守着它。

## 9. 已知取舍（诚实写）

1. **长句里 2 字的中文专名**，若既没被等距采样覆盖、又不带引号点名，可能召不回。≥3 字专名由 trigram + bigram 覆盖。
2. **FTS 侧的 trigram 仍是"整段出现"语义**：中文长句在 FTS 上命中率低，但 LIKE 侧 bigram 已兜住，`FTS ∪ LIKE` 的并集语义不变。
3. **显式点名只影响"是否能进注入窗口"，不喧宾夺主**：置顶组（pinned）绝对不动，组内原有相对顺序也不动；没有引号片段时该段代码完全不执行 → 既有排序断言零影响（`memory-batch3-consistency` BUG-011 已验）。
4. **token 上界会丢信息**：超长查询触发截断时可能漏召回句中被截掉的片段；`truncated` 标志留给将来观测。
