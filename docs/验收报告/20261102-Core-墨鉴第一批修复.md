## 二、P0-1 / BUG-017：审计密钥与回滚的数据丢失边界

### 2.1 缺陷确认（PM 核实属实，我逐行复读确认）

| 位置 | 缺陷 |
|---|---|
| `audit-crypto.ts:39-43` | 密钥文件格式不对 → `writeFileSync` **覆盖写入新钥** → 旧钥一被覆盖，库里所有历史密文**永久解不开**（不可逆） |
| `audit-crypto.ts:112` | 解密失败 `return null` → 与「本来就没有内容」**不可区分** |
| `memory/audit.ts:107-113` | `before` 为 null → 走 `deleteMemoryRow` 分支 → **本该恢复的操作变成静默删除**，还返回 `{ok:true}` |

### 2.2 修法

**① 坏钥改名备份 `.bad`，绝不覆盖**（`audit-crypto.ts`）

- 原文件**改名**为 `<path>.bad`（保留原始字节供人工恢复），**不在本进程内生成新钥顶替** → 返回 `null` 降级为明文快照并告警；
- 历史密文保持原样，不被新的错误密钥污染。

> 口径说明：密钥这里用「改名」，配置那里（BUG-005）用「复制」——两者不同是**有意的**：密钥文件改名后原路径不再被使用（下次打开会走「不存在 → 生成新钥」，而此时库里没有历史密文需要保护）；配置文件必须**原位保留**，否则用户/其它工具再读 `config.json` 会得到 ENOENT 而不是「内容损坏」。

**② 解密失败返回哨兵**（`audit-crypto.ts`）

新增 `AUDIT_DECRYPT_FAILED`（`Symbol`）与 `isAuditDecryptFailed(v)`：

- `open()` 解密失败时返回**哨兵**而非 `null`；
- 哨兵是 `Symbol`，只能靠 `isAuditDecryptFailed` 判定 —— 这正是调用方区分「本来没有」与「解不开」的**唯一依据**（不能靠猜 `null`）。

**③ `MemoryLogEntry` 加两个可选标记**（`memory/types.ts`，additive）

`beforeUndecryptable?: boolean` / `afterUndecryptable?: boolean` —— 显式表达「快照存在但解不开」。

**④ `listLog` 标记 + `rollback` 拒绝**（`memory/audit.ts`）

- `listLog`：`ctx.audit.open()` 返回哨兵时，置 `before: null` **并**打 `beforeUndecryptable: true`；
- `rollback`：**先判 `entry.beforeUndecryptable` → 直接返回 `{ok:false, error: '...'}`**，绝不进入删除分支；数据原地不动。

### 2.3 回归测试（`tests/desktop/memory-audit-key-guard.test.ts`，4 例）

| # | 用例 | 断言要点 |
|---|---|---|
| 1 | 坏钥改名备份 `.bad`，绝不覆盖 | 原路径**不存在**（已改名）、`.bad` 存在且**字节与原始完全相同** |
| 2 | 坏钥场景历史密文不被新钥污染 | `memory_log.before_json` 仍是 `enc1:` 密文（**没被重写**） |
| 3 | **解密失败 → rollback 拒绝，行原地不动** | `rollback.ok === false`、error 含 `cannot be decrypted`、**`get(id)` 仍能取到行**且内容含原值 |
| 4 | 哨兵可被显式识别 | `isAuditDecryptFailed(null/undefined/'text'/{})` 全为 `false`（不靠猜） |

## 三、P0-2 / BUG-005 + BUG-004：配置文件安全边界

### 3.1 缺陷确认

| 位置 | 缺陷 |
|---|---|
| `api/main.ts:107` vs `:110/:147/:153` | 注释承诺「不覆盖磁盘上的损坏文件」，但代码把 `stored` 置空后**仍会走到写盘分支** → 注释与实现自相矛盾，用户损坏配置被**静默覆盖** |
| `api/main.ts:150-153` | 只写 6 个白名单字段 → `chatRooms` / `chatRoomMaxDepth` / `apiEngine` **静默丢弃**（用户配好的聊天室与真实 API key 没了） |

### 3.2 修法

**① 抽出 `src/api/config-loader.ts`（新增）**

原逻辑在 `main.ts` 里，而该模块**导入即执行 `main()`**（会起 8760 服务），无法被单测安全导入。新模块是**纯函数 + 无副作用**，且：

- `loadConfig(override?: { cfgDir?, cfgPath? })` —— 配置路径**可注入**，测试用临时目录，绝不碰用户真实 `~/.config/deepseek-studio/config.json`；
- `ResolvedConfig` 新增 `configFileBroken: boolean`（本次是否禁止写盘），供调用方/测试断言；
- `main.ts` 改为 `import { loadConfig } from './config-loader'`，旧实现整段删除（**行为等价**：随机 token 编码保持原来的 `base64url`，未改成 hex）。

**② 坏配置：复制备份 `.bad`，原文件原地不动 + 本次不写盘**

- 用 **`copyFileSync`**（不是 rename）→ 原路径仍有文件、**字节不变**，用户/其它工具再读不会 ENOENT；
- 置 `configFileBroken = true` → **跳过写盘分支**，改用内存随机 token 启动，并在日志明确说明「本次不写盘」。

**③ 写盘改「读-改-写合并」**

- 基底 = **磁盘原始配置**（读出来解析），只覆盖本次真正变更的键（`host`/`port`/`token`/`secret`/`workspaceRoot`/`policyMode`）；
- 其余（**已知与未知**）一律保留 —— `chatRooms`/`chatRoomMaxDepth`/`apiEngine`/未来新增字段都不再丢；
- 口径与 `src/host/workspace.ts` 的 `persistConfigPatch` 一致。

## 四、P1-1 / BUG-009 + BUG-008：shell 安全边界

### 4.1 缺陷确认

| 位置 | 缺陷 |
|---|---|
| `capabilities/shell.ts:230`（CMD_BUILTINS）/`:260`（.cmd/.bat） | 元字符检查只覆盖**两条自动加前缀**的路径；用户**显式**传 `argv: ['cmd','/c','echo','x&calc']` 时**一个都不查** → cmd 二次解释 → 命令注入 |
| `capabilities/shell.ts:285` | `argv = [...argv.slice(0, cmdIdx), '-EncodedCommand', encoded]` 把 `-Command` **之后**的参数全丢 |

### 4.2 修法

**① 显式 `cmd /c` 全量元字符检查**（`shell.ts`）

- 识别 `cmd` / `cmd.exe` + `/c`（大小写不敏感）前缀；
- 该前缀之后**所有**参数（含第一段）逐个查 `& | < > ^`，命中即返回 `shell-metachar-in-cmd-builtin` + 提示；
- 与既有两处检查**同口径**（同一个正则 `CMD_METACHARS`）。

**② `-Command` 之后参数不丢**（`shell.ts`）

修正时踩到 **PowerShell 自身的限制**（实测确认，写进代码注释）：

```
powershell -EncodedCommand <enc> -Tail
→ "a command is already specified with -Command or -EncodedCommand"（退出码 -196608）
```

即 **`-EncodedCommand` 不接受尾部参数**，而原生 `-Command` 接受（尾部参数成为脚本的 `$args`）。所以口径是：

- **没有**尾部参数 → 转 `-EncodedCommand`（中文编码修复的原始目标场景，行为不变）；
- **有**尾部参数 → **保持原生 `-Command`**，尾部参数一个不丢、顺序不变（宁可放弃中文编码修复，也不能丢参数）。

### 4.3 回归测试（`tests/desktop/security-shell-guard.test.ts`，9 例）

| # | 用例 | 断言要点 |
|---|---|---|
| 1 | 显式 `cmd /c` 参数含元字符 → 拒绝 | `ok===false`、`error==='shell-metachar-in-cmd-builtin'` |
| 2 | 各元字符都拦（`\| < > ^`） | 4 个元字符逐一被拒 |
| 3 | `cmd.exe` 变体同样被拦 | 被拒 |
| 4 | `/C` 大小写变体同样被拦 | 被拒 |
| 5 | 不含元字符的 `cmd /c` **不误伤** | `error !== 'shell-metachar-in-cmd-builtin'` |
| 6 | 非 cmd 命令不受影响 | 普通 node 命令正常执行、输出正确 |
| 7 | **`-Command` 尾部参数不丢** | 输出含 `tail=-TailMarker` |
| 8 | 多个尾部参数**顺序不变** | 输出含 `a=AAA,BBB` |
| 9 | 无尾部参数仍走 `-EncodedCommand` | 输出含 `enc-ok`（中文编码修复的原行为没被破坏） |

> 测试写法说明：PowerShell 把 `-Command` 的尾部参数传给 `$args` 的标准写法是 `& { script }` 包装（实测：不包装时尾部参数不会进 `$args`）。用例 7/8 按这个真实语义写。

## 七、一条如实记录

写 BUG-008 用例时，我第一版断言按「尾部参数直接跟在 `-Command` 后面」写，**失败**。排查发现是 **PowerShell 自身的调用约定**：`-Command 'script' AAA` 里 `AAA` 不会进 `$args`，必须用 `& { script }` 包装；而 `-EncodedCommand` 更是完全拒绝尾部参数（报错退出码 -196608）。所以最终修法是「有尾部参数就保持原生 `-Command`」——这是实测出来的，不是照搬审计结论。
