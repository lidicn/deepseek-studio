## 3. 根因

`main.rs` 主窗关闭 handler 把收尾闭包交给 `app_handle.run_on_main_thread(...)` 执行，
该闭包里才有 `terminate_app_webviews()` + `app.exit(0)` + `std::process::exit(0)`。

**`run_on_main_thread` 返回 `ok=false`（`EventLoopProxy` 已关闭 / 主事件循环不再接受排队）
→ teardown 闭包从未执行 → `process::exit(0)` 永不发生 → 进程不死。**

这解释了此前所有观测：窗口隐藏 / sidecar 关闭 / webview 回收 / 8760 释放全部由 Rust 侧
在别处完成（都成功了），唯独「最后一步终止进程」是闭包里做的，而闭包没被调度。

**被证据否掉的三个假设**（一并记录，避免后人重走）：
1. 40 处无超时外部调用拖住 exit —— `netstat` 84ms→64ms、`CIM` 1.2s 稳定，负载不退化；
2. 重启循环累加 —— crash.jsonl 那次零条目，`do_shutdown` 只跑了一遍；
3. Chromium/WebView2 退出清理挂起 —— teardown 闭包根本没执行，谈不上清理挂起。

### ok=false 的成因（结论：**已钉死**）

**触发条件 = 多窗 WM_CLOSE，且先关闭 WebView2 辅助窗 `com.deepseek.studio-sic`。**

实测证据（最终包，真实对话后关窗）：

| 关窗方式 | `queued ok` | 说明 |
|---|---|---|
| **只发主窗 WM_CLOSE** | `true` | 正常路径，1.94–2.1s 退出（多次复现） |
| **三可见窗都发（先 sic、Tao，后主窗）** | **`false`** | 复现：辅助窗一关，主窗 close-flow 里的排队即失败 |

机制推断：`com.deepseek.studio-sic` 是 WebView2 `CoreWebView2Controller` 的宿主窗口；
先关它 → 销毁 controller → 主线程的 WebView2 消息泵随之失效 →
之后 `run_on_main_thread`（依赖事件循环/消息泵投递任务的 `EventLoopProxy`）返回 Err。
这也解释了为什么 Core 的"起完就关（只关主窗）"测试永远测不到，而真实用户按多窗关闭 / 系统关窗
（会连带关闭辅助窗）时必踩。

之前对"长时运行/电源状态"的推断**不成立**，撤回；真正变量是**关没关 WebView2 辅助窗**。

## 4. 修法（`src-tauri/src/main.rs`，+40/−1）

两条互不依赖的硬出口，确保「用户点了关闭，进程一定死」：

1. **`run_on_main_thread` 返回失败 → 直接 force exit**（主修法，命中本次根因）
   ```rust
   let queued_ok = queued.is_ok();
   p0_log(format!("run_on_main_thread queued ok={}", queued_ok));
   if !queued_ok {
       p0_log("run_on_main_thread queue FAILED (main loop gone/rejected) → force exit(0)");
       let killed = terminate_app_webviews();
       p0_log(format!("force-exit: terminated app webviews = {}", killed));
       std::process::exit(0);
   }
   ```

2. **退出 watchdog**（兜住「排队成功但主线程永不执行」这一形态，与调度层无关）
   ```rust
   const EXIT_DEADLINE: std::time::Duration = std::time::Duration::from_secs(5);
   // 后台收尾线程最开头 spawn：从"用户点关闭这一刻"起算，超时即自走
   std::thread::spawn(|| {
       std::thread::sleep(EXIT_DEADLINE);
       p0_log(format!("WATCHDOG: still alive {:?} after close → force exit", EXIT_DEADLINE));
       let killed = terminate_app_webviews();
       p0_log(format!("WATCHDOG: terminated app webviews = {}", killed));
       std::process::exit(0);
   });
   ```

### 取舍（务必知悉）

- **优先级**：用户点关闭 → 进程必须死。清不干净的兜底可以放弃，**退出本身不许被堵死**。
- watchdog 触发时牺牲的是「WebView 优雅回收」，所以触发时会**再调一次 `terminate_app_webviews()`**
  尽量减少残留；代价是极端情况下仍可能有 WebView2 残留到下一次启动（8760 端口由 sidecar 退出路径
  与下次启动的 `terminate_listener_on_port`/`terminate_host_by_cmdline` 兜底）。
- `EXIT_DEADLINE=5s`：正常路径实测 1.9–3.7s 完成，5s 给 1.3~2.6 倍余量；正常路径下 watchdog
  不会触发（实测确认），只在真挂住时兜底。
- 分工：`run_on_main_thread` 失败走 exit(0) 立即退出；排队成功则由 watchdog 计时兜底。
