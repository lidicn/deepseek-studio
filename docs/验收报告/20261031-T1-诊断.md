# T-1 多窗关闭挂死 · 根因诊断（20261031）

- 席位：Core｜时间：2026-10-31 16:02–17:05
- 被测二进制：`src-tauri\target\debug\deepseek-studio.exe`（含 P0 锚点）20,016,640 B｜mtime 2026-10-31 16:06:11｜SHA256 `3B0A3A779E2B6E4EB999C134F86265D8840F19F9A83425FC03E0D39FF7674BF3`
- 原始日志：`logs/verify-exit/roundT1*.err.log`、`logs/verify-exit/probe-wb.err.log`、`logs/verify-exit/roundT1*.summary.json`
- 结论：**根因不是"销毁顺序"也不是"线程"，而是 `open_workbench` 的建窗调用本身卡住/失败，产出一个"Tauri 不认账、OS 层却活着"的野窗口；这个野窗口既无法被隐藏也无法被销毁，其 WebView2 又拖住事件循环退出，于是关窗永远退不掉。**

---

## 1. 一句话根因链

```
页面 IPC 触发 open_workbench
   └─ WebviewWindowBuilder::build()  【卡住 / 失败】
        ├─ OS 层：HWND 已创建、标题正确、可见  → 用户看到"多了一个窗"
        ├─ WebView2：停在 about:blank，从未导航到 /agent
        ├─ Tauri：从未把它登记进 webview_windows()  → 主线程里"看不见"这个窗
        │        └─ 于是 M4 的 hide(others) 与 M6 的 destroy(others) 全部跳过它
        │           （p0: `hide other: …` 一次都没出现，`teardown window set: ["main"]`）
        └─ 退出时：这个野窗口的 WebView2 仍在跑，事件循环收尾等它 → 进程不退
             └─ app.exit(0) 只是"请求"退出（tauri-2.12.2 app.rs:581-587），
                真正退出要等事件循环收尾 → 收尾被野窗口拖住 → 30s 不退
```

## 3. 决定性证据

### 3.1 建窗调用卡住（`probe-wb.err.log`）

```
[p0 1793435466243ms ThreadId(1)] workbench build begin
        ↑ 之后没有 workbench build ok= …（该锚点紧跟在 build() 之后）
```

`build()` 永不返回。同时 CDP 目标列表出现一个 **`about:blank`** target：

```json
[ { "id": "036167E7E9D1AA7F05F641E443C71986", "title": "about:blank", "url": "about:blank" },
  { "id": "9A5618F04C923AB1DABCF18AE50FFB96", "title": "DeepSeek", "url": "https://chat.deepseek.com/" } ]
```

→ WebView2 控制器建出来了，但**从未导航到 `http://127.0.0.1:8760/agent`**；窗口 HWND 已存在且可见（标题 `DeepSeek++ Studio · 工作台`）。

### 3.2 URL 本身没问题（已排除）

```
GET http://127.0.0.1:8760/agent  → 200, 468ms, 4337 bytes
GET http://127.0.0.1:8760/healthz → 200, 152ms
```

→ 不是宿主没起、不是路由挂死。

### 3.3 主线程被冻结（`probe-wb` 收尾）

```
CloseMainWindow=True exited=False elapsed=8035ms   ← 连"关闭窗口"事件都处理不了
```

`workbench build begin` 打在 **ThreadId(1)（主线程）**：`open_workbench` 是在主线程上同步执行 `build()` 的，而 `build()` 在等 WebView2 初始化完成 —— 初始化又需要主线程的消息泵 → **主线程自锁**。于是：

- 后续任何命令都排队（`roundT1c` 里工作台建窗后，bot 建窗命令根本没开始执行）；
- `WM_CLOSE` 也排不上（`CloseRequested` 回调永远不跑）；
- 这解释了 PM 下午的现场观察：**「CloseMainWindow 后等 7.5s 仍未退出，被迫 force kill」**——那次会话正好开过工作台窗。

### 3.4 退出阶段：野窗口既藏不掉也销毁不了

```
[p0 …] close-requested: main
[p0 …] close-flow begin (main)
[p0 …] hide main                      ← 只隐藏了主窗
        （没有 hide other: workbench）  ← 循环里没有"其它窗"可迭代
[p0 …] teardown window set: ["main"]  ← Tauri 只认这一个窗
[p0 …] destroy begin: main / destroy done: main
[p0 …] calling app.exit(0)
[p0 …] app.exit(0) returned           ← 只是"请求"退出
（进程仍在 → 30s 强杀）
```

对照单窗正常轮：同样的 `app.exit(0) returned` 之后进程**立刻退出**（exitCode=0）。
→ 差别只在于**是否存在那个野窗口**。

### 3.5 强杀后的残留佐证

多窗轮被强杀后，仍有 **6 个 `msedgewebview2.exe`** 存活（单窗轮为 0）——正是那个野窗口的 WebView2；它不在 Tauri 管理内，所以 Tauri 退出时不会回收它，进程表也清不掉。后续轮次 `healthz` 就绪从 7s 涨到 25–51s（残留进程 + profile 锁竞争）。

## 4. 已排除的解释

| 假设 | 排除依据 |
|------|----------|
| 销毁顺序错（先关主窗） | `destroy begin/done: main` 前后齐全，6ms 内完成；不是它卡住 |
| `destroy()` 跨线程不安全 | 销毁全程在主线程（ThreadId(1)）执行，`destroy done` 已打印 |
| `run_on_main_thread` 没调度 | `run_on_main_thread queued ok=true` + `main-thread teardown entered` 都出现了 |
| sidecar 收尾阻塞 | `sidecar shutdown begin`→`returned` 间隔 4.3–6.4s，之后一切正常推进 |
| 第二次 CloseRequested 重入 | `CloseRequested(main)` 计数恒为 1 |
| 端口/子进程兜底太慢 | 关闭期无 `powershell.exe`，taskkill 3 次；且卡死与 sidecar 无关（单窗同路径正常退出） |
| `/agent` 路由挂死 | 直接请求 200/468ms |
| 机器负载导致假阳性 | 挂死轮的 p0 时序完整自洽；且负载最重时反而出现"完全无响应"的更硬证据 |

## 6. 修复方案（**均超过 1–2 行，按纪律先报方案，未自行实施**）

### 方案 A · 治本：让工作台窗走一条能成功的建窗路径（推荐）

要点：`build()` 在 IPC 回调（主线程）里同步调用会自锁。改法二选一：

- A1：把建窗挪出 IPC 回调——由主线程在**消息泵空闲时**创建（例如托盘菜单事件 / `setup` 之后投递一次 `run_on_main_thread`），命令本身立即返回 `Ok(())`；
- A2：若确认"必须由命令创建"，则改为**异步**：命令只记下请求并 `run_on_main_thread` 投递，实际 `build()` 在主线程消息循环里执行且不等待其完成（`build()` 换用非阻塞路径或改为 `WebviewWindowBuilder::build()` + 立即返回的封装）。

改动量：约 5–12 行（需改 `open_workbench` 的调用契约 + `entry.ts` 侧 `__studioOpenWorkbench` 的返回语义）。
风险：命令语义从"同步建好"变"已受理"，前端需要改成"建好后回调/轮询"。
验证：重跑 `roundT1-workbench`（期望：`workbench build ok=true tracked=["main","workbench"]` → `teardown window set: ["main","workbench"]` → 30s 内退出、exitCode=0、残留 webview=0）。

### 方案 B · 治标（可与 A 叠加）：退出路径兜底野窗口

在 teardown 闭包里，除了销毁 Tauri 登记的窗，再**杀掉本 app 归属的 `msedgewebview2.exe`**（按 `--webview-exe-name=deepseek-studio.exe` / user-data-dir 特征，复用 sidecar 那套 cmdline 兜底思路），然后 `std::process::exit(0)` 收尾。

改动量：约 10–15 行（新增一个 cmdline 兜底 helper）。
收益：即使将来又出现野窗口，也**保证退得掉**且**不留残留进程/profile 锁**。
风险：杀错进程的特征匹配必须收紧（只匹配本 app 的 webview）。

### 方案 C · 最小止血（**不推荐单独上**）

把 `app_for_windows.exit(0)` 换成 `std::process::exit(0)`（1 行）→ 一定退得掉。
副作用：每次正常关闭都会跳过 Tauri 清理，**每次都留下 WebView2 孤儿**（实测强杀后确实残留 6 个），EBWebView profile 锁会影响下一次启动 → 只是把"退不掉"换成"下次起不来"。

### 建议

先 A（治本）+ B（兜底）一起上，A 解决"多窗可用"，B 保证"任何异常都能退干净"。C 只作为 B 内部的收尾手段使用。

### 9.1 A（治本）· 建窗移出 IPC 回调

源码级根因（本轮从 tauri 源码确认）：

- wry runtime 建 webview =「`send_user_message` 投递 + `rx.recv()` **阻塞**等事件循环建窗」
  （`tauri-runtime-wry-2.12.1/src/lib.rs:365-405`）；
- 而 `send_user_message` 在**主线程上会内联执行**（同文件 `lib.rs:263-280`：主线程走 `handle_user_message`，非主线程才 `proxy.send_event`）；
- IPC 命令回调本身就跑在主线程（p0 日志 `ThreadId(1)`）→ WebView2 控制器创建被**嵌在 WebView2 的 IPC 消息派发里** → UI 线程无法泵消息 → 死锁。

改动（两处对称）：

| 位置 | 改动 |
|------|------|
| `open_workbench` | 建窗移到 `std::thread::spawn` 的工作线程；命令立即 `Ok(())`（前端 `__studioOpenWorkbench` 本就 fire-and-forget） |
| `open_bot_window` | 同上：`create_bot_window` 移出 IPC 回调，`BotWindowContext` 按值拷进线程 |

效果：主线程不再被建窗占住 → 即使建窗仍有问题，**app 依然可响应、可关闭**（旧行为是主线程冻结，8s 内 WM_CLOSE 都处理不了）。

### 9.2 B（兜底）· 退出前回收本 app 的 WebView2

新增 `terminate_app_webviews() -> usize`（main.rs:75，Windows；非 Windows 空实现）：

- 用 PowerShell CIM 找 `msedgewebview2.exe` 中命令行含 `--webview-exe-name=deepseek-studio*` 的进程
  （= 本 app 的 WebView2 browser 进程，每个窗口一个；子进程随 `taskkill /T` 一起回收），不误伤同机其它 WebView2；
- 在 teardown 闭包里、`app.exit(0)` **之前**调用，p0 记录 `teardown: terminated app webviews = N`。

作用：野窗口（Tauri 未登记）的 WebView2 不在 Tauri 管理内，不回收它，事件循环收尾会一直等 → 进程退不掉。现在先回收再退出。

### 9.3 残余风险（未验证，等 PM 放行构建后复测）

1. **A 是否彻底解决建窗**：工作线程上 `build()` 走的是「投递 + 阻塞 recv」路径，事件循环此时空闲，理论上能建成功；但 wry 的 WebView2 控制器创建是否还需要 UI 线程泵消息，需真机复测。若仍不成，症状会**降级**为「窗口不出现 + 工作线程卡住」，而 app 仍可正常关闭（B 兜底），不会再出现"整个 app 无响应"。
2. 失败时的下一步方案（未实施）：在 `setup()` 期（已知可用路径）预建工作台窗，或改用非阻塞建窗 API。
3. `open_workbench` 改成异步受理后，**重复点击**可能在建窗在途时再建一个同 label 窗口 → build 报错并记日志，不会崩；如需严格幂等需再加一个 AtomicBool 状态位（本轮未加，避免夹带）。
4. B 的匹配串依赖 exe 名 `deepseek-studio`（基线副本 `deepseek-studio-baseline-*.exe` 也能匹配，因为它以 `deepseek-studio` 开头）。

## 11. hide 顺序修复 + 复测（2026-11-03 01:13，PM 授权「做」）

### 11.1 改动（`src-tauri/src/main.rs`，只动顺序）

CloseRequested 入口原来是「先 `window.hide()`（主窗）」→ 后面那段循环才 `hide other:`（实测间隔 **+289 ms**）。这 289 ms 里 OS 把前台移交给同 app 仍可见的第二个窗 —— 就是 focus hits 与「可见窗 >0」的来源。

改法：在 `label == "main"` 分支里**先遍历其余窗 `hide()`、再 hide 主窗**，让前台没有可移交目标；下方那段循环的 `hide` 保留（幂等）与 `destroy` **未动**（顺序敏感，不合并）。

```
- if label == "main" { let _ = window.hide(); p0_log("hide main (first, ...)"); }
+ if label == "main" {
+     for (other_label, other) in window.app_handle().webview_windows() {
+         if other_label != label { let _ = other.hide(); }
+     }
+     let _ = window.hide();
+     p0_log("hide main (first, ...)");
+ }
```
