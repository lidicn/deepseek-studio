### R-W1（P0，最高优先）：W1 截断重发**绕过 `MAX_ERROR_RETRIES`** → 无限重发

**缺陷**（`src/inject/main-world-interceptor.ts:2056-2072`）：新增的 `else if (truncated)` 分支做了 `errorRetryCount += 1`，但**没有任何一处检查 `errorRetryCount` 的上限**。
- `:2030` 的封顶判断 `verdict.verdict === 'retryable' && errorRetryCount >= MAX_ERROR_RETRIES` 只在**进入该 else-if 链之前**求值，且条件里带着 `verdict.verdict === 'retryable'`。
- 而「2xx + 有字节的截断」恰恰 `verdict === 'ok'`（`response-classifier` 对 SSE 文本 `parseBodyError` 返回 null），**永远命不中那条封顶**。
- 于是：截断 → `errorRetryCount += 1` → 退避 → 重发 → 又截断 → 再 +1 → …**只要服务端持续返回半句，就无限重发**。
- 退避是**有限**的：`errorBackoffMs(attempt)` 有封顶，所以不是「慢慢重试」，是**稳定烧配额**。这正是 `MAX_ERROR_RETRIES=3` 存在的理由——`:234` 与 `continuation-prompt.ts:51-58` 的注释亲手写着「一次服务器错误能消耗整轮预算／错误重试单独封顶 3 次」，还记载过「缺它时一路吃到 MAX_LOOP=25，既烧配额又让用户漫长等待」的历史事故。**W1 把这条防线绕过了。**

**PM 实测证据**（独立探针件，已删除，db 需自己复现）：首轮带工具 + 有哨兵，之后把每条续跑响应都回成 `200 + sseText('半句')`（无哨兵），**15 轮内发出 17 条** chat completion 请求且仍在继续——`MAX_ERROR_RETRIES=3` 一次都没拦住。

**修法要求**（不给代码，按语义收口）：
1. 截断重发必须**受同一个 `errorRetryCount` 预算约束**：预算耗尽走与 `:2030` 同构的停手上报（记 `turn.end finished:false` + `finishStepFlow` + `loopDepth = 0`），**不得**无界重发。
2. 判定顺序要正确：不能继续把截断分支放在 `verdict` 分支链之后导致封顶判断永远看不到它。
3. 预算耗尽后的**最终兜底文案**要明确：不能把半截文本当成功答案下发（保留 W1「不记 completed、不下发半截工具文本」的正向语义）。

**测试必须写成语义反控，不是实现对齐**：
- **反控 A（关键）**：`respond(200, 截半)` **连续喂到预算耗尽**，断言总请求数 **≤ 1 + MAX_ERROR_RETRIES + 少量**（具体上限你按实现定，但必须是**有限且与 3 同阶**，绝不能是 15+）；且 trace 出现 `finished:false` 的收尾、`turn.end` 不再是 `completed`。
- 断言 `continuation.decision` 里 `reason: 'continuation-truncated'` 的条数**不超过预算次数**。
- 保留原有三条正向断言（无 completed / 发生重发 / 不外泄 `<shell_exec>`）。
- 现有 w0/w1 用例之所以拦不住这个 bug，是因为它们只喂了**一次**截断。这是本轮返工的方法论要求：**每条重试/预算类修复，必须有一条「持续失败」的用例。**

### R-W2（P0）：W2 的跨会话过滤挂在**首轮路径**，且 `chat_session_id` 提取键名与真实 body 不符 → 该功能实际未生效

**缺陷①（路径错位）**：过滤加在 `augmentInit`（`:780-808`）。但 `:915` 的注释自己写着「**这里只负责首轮原始请求**」。W2 要防的是**续跑**串味，而续跑走 `autoContinueWithPow` → `:1157 prepareOutgoingBody(body, pending, ...)`（XHR hook）/ fetch 侧同构路径，**根本不经过 `augmentInit`**。⇒ 过滤在真正需要它的地方一次都不执行。

**缺陷②（键名猜测）**：`:789-791` 从 body 里取 `chat_session_id ?? chatSessionId ?? session_id ?? conversation_id`，而 `:812` 的 `captureChatRequest` 用的是 `parsed.chat_session_id`。四个键是猜的，且没有断言证明续跑 body 真带这些键。`normalizeChatSessionKey`（`:1871` 已用）也没复用。**若续跑 body 不带会话 id（沿用首轮 captured body 的变体），`currentSession` 为 undefined → 整个 `if` 跳过 → 不校验**。

**缺陷③（测试是摆设）**：`w2-pending-session-ownership.test.ts` 全文只有一句 `expect(chatUI.appendError.mock.calls).toEqual([])`，文件头注释自己承认「本卡再加一道兜底……验证不崩溃」。**它从未构造「A 的结果迟到 → 被投进 B 的请求」的时序，因此删掉 W2 全部生产代码它照样绿。** 而 PM 卡片 §1 W2 明确要求「单测复现『清在前、回来在后』」。

**修法要求**：

### R-W3（P0）：W3 把「历史由页面承载」的前提搞反了——它承载的是**页端 WebEngine**，不是 TaskLoop 喂给引擎的 prompt
