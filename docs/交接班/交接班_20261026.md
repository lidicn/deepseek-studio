## 1. 不可偏离的设计结论

### 1.1 三轴模型

| 轴 | 含义 | 取值 |
|---|---|---|
| `policyMode` | 允许 Agent 访问多宽的执行范围 | `workspace` / `auto` / `full`（`ask` 为兼容旧值） |
| `approvalClass` | 这类工具是否需要人工确认 | `none` / `mode` / `always` / `hard-deny` |
| `grant` | 用户批准后放行到什么程度 | `once` / `turn` / `session` / `project` / `global` / `temporary` |

三者不能互相顶替：

- `full` 不等于“所有 `always` 工具免审批”。
- 一个 `session` grant 不等于“同一工具名永久放行”。
- `project` 规则不能由审批弹窗偷偷创建。
- `hard-deny` 永远优先于任何 grant、任何档位、任何来源。

### 1.2 `full` 的最终定义

> **执行范围完全放开，安全阀仍然保留。**

- `full` 只影响 `approvalClass=mode` 的工具：普通 `file.*`、普通 `shell.exec`、`mcp.test` 不再逐次确认。
- `approvalClass=always` 的工具在 `full` 下仍必须人工确认。
- `approvalClass=hard-deny` 的工具/动作在 `full` 下仍直接拒绝。
- `full` 不得绕过工作区未配置、origin 白名单、未知工具、敏感路径与磁盘级破坏等红线。

面板文案必须从：

```text
所有工具调用自动执行，无需确认。
```

改为：

```text
文件与命令类工具不再逐次确认；高风险动作仍需确认或硬拒绝。
```

### 1.3 工具分级基准

本节是 A1 的基准表。若源码里出现新增工具，必须显式归入四类之一，不能默认落到 `mode`。

| `approvalClass` | 工具 |
|---|---|
| `mode` | `file.read` / `file.write` / `file.edit` / `file.list` / `file.stat` / `shell.exec` / `mcp.test` |
| `always` | `policy.set` / `workspace.set` / `memory.delete` / `memory.purge` / `memory.unarchive` / `chat-send` / `python.exec` / `mcp.call` / `mcp.save` / `mcp.remove` |
| `none` | 现有只读工具与低风险工具：`echo` / `chat-read` / `skill.list` / `search_files` / `web_fetch` / `web_search` / `memory.save` / `mcp.list` / `mcp.get` / `memory.list` / `memory.listArchived` / `settings.get` / `project.list` / `project.create` / `folder.pick` |
| `hard-deny` | 由硬规则动态判定，不在工具表里放“永久允许”的工具：磁盘格式化、关机/重启、盘根递归删除、敏感凭据路径、未知工具/未知来源 |

说明：

- `memory.save` 本卡仍保持现有低风险口径；若 PM 要把它改成 `mode`，另开任务卡，不能在 A1 里静默改变语义。
- `memory.delete/purge/unarchive` 必须保持 `always`，即使 `policyMode=full`。
- `chat-insert` 是 bot 启动时的内部预授权对象之一；它不得伪装成普通用户 grant。

### 1.4 授权作用域与时间

| grant | 作用对象 | 失效条件 | 是否在审批弹窗一级按钮提供 |
|---|---|---|---|
| `once` | 单次精确调用 | 本次调用结束 | 是 |
| `turn` | 精确调用，当前 turn 内 | turn 结束 / 失败 / 取消 | 第一版不暴露，作为内部可测试值 |
| `session` | `sessionId/botId + workspaceHash + toolId + actionClass + canonicalTarget` | 会话结束、Bot 断开、工作区变化、策略变化、用户撤销、进程重启 | 是 |
| `project` | 用户显式创建的持久规则 | 用户撤销、工作区变化、规则被删除 | 否；只在设置页创建 |
| `global` | 跨项目持久规则 | 用户撤销、规则失效 | 本版不暴露；只保留数据模型，禁止模型自建 |
| `temporary` | 精确目标的高危临时放行 | 10 分钟倒计时结束或用户撤销 | 只在“更多/高级”二次确认中出现；`always` 不得转成普通 `session` |

硬规则：

1. 默认是 `once`。
2. `session` 不以 10 分钟 TTL 为主；10 分钟只留给 `temporary` 高危临时提升。
3. 禁止用 `conversationId + toolId` 当授权 key。对话可恢复、分叉、压缩，key 会串。
4. `always` 工具不得发放 `session` / `project` grant；只能 `once`，或在用户明确进入高级流程后发 `temporary` 精确目标 grant。
5. `outside-workspace` 默认不享受持久 grant；跨工作区访问必须逐次确认，或由用户显式创建 project 规则（本版仍不自动创建）。
6. `SessionAllowlist.addPermanent('chat-insert'/'chat-send')` 必须标记 `source=internal-bot`，审计中与用户授权分开；它不是“用户允许了 chat-send”。
7. `hard-deny` 永远先于任何 grant；任何来源都不能覆盖。

### 1.5 统一授权顺序

所有工具调用必须先经过同一个授权解析器，顺序固定为：

```text
1. 工具登记 / origin / 执行侧
2. hard-deny（磁盘、关机、盘根删除、敏感路径、未知来源）
3. workspace/resource deny（未配置工作区、越界且档位禁止）
4. 显式 deny 规则
5. approvalClass=always 的新鲜人工确认
6. approvalClass=mode 的有效 grant
7. policyMode 对 mode 类的判定
8. approvalClass=none 放行
9. 其余一律 fail-closed
```

解释：

- `always` 的 grant 只能在“精确 `temporary` grant”这一步被消费；不能靠普通 `session` 绕过。
- `mode` 的有效 grant 只对 `canonicalTarget` 生效，不能拿“同工具不同参数”复用。
- `policyMode=full` 不能覆盖第 2、3、4 步，也不能覆盖 `always` 的新鲜确认。

### 1.6 审批弹窗

建议按钮：

- `mode` 类：`[拒绝] [允许一次] [本会话允许此操作]`
- `always` 类：`[拒绝] [允许一次]`；`temporary` 只能通过“更多”进入，且必须展示倒计时、目标与撤销入口。

弹窗必须展示：

- 工具名与动作类别；
- 规范目标（文件路径、argv/cwd、memory id、MCP server/tool）；
- `approvalClass`；
- 当前 `policyMode`；
- grant 失效条件；
- 硬拒绝时不显示“允许”按钮。

## 9. 阶段 B1 · M10-8B `memory.select` 方案 B

### 9.1 结论

采用方案 B：**宿主按当前用户任务预取候选，合并 pinned 全集与相关搜索结果；页端仍用同步格式化函数。**

不得：

- 把异步宿主 RPC 塞进 `prepareOutgoingBody()`；
- 重做 FTS5/倒排；
- 改动 40 行 / 1800 token 预算口径；
- 在重试/首轮原样重发时重新选记忆，破坏重试幂等。

### 9.2 前置设计决策（必须落地，不得含糊）

当前 `captureChatRequest()` 在 XHR/fetch hook 内识别新用户消息，但没有宿主侧同步入口。B1 必须新增一条轻量页→宿主事件，并在首轮请求发送前等待一次有界预取：

```text
memory-select-request:
  requestId
  taskText
  sessionId
  botId?
```

宿主返回：

```text
memory-select-response:
  requestId
  memories: selected rows
  selection: 'related' | 'fallback'
  revision
```

流程：

1. 页端识别到新用户消息后发送 request；
2. 页端在首轮 fetch/XHR 真正发送前等待 response，超时上限建议 120ms；
3. 收到结果后更新 `currentMemories`，再调用现有同步 `prepareOutgoingBody()`；
4. 宿主不可达/超时 → 保持上一帧 `currentMemories`，请求继续，不阻塞；
5. 首轮原样重发、工具结果续跑、auto-resume 不得重新选记忆；
6. feature flag 默认关闭；打开后启用，关闭即回退旧广播行为。

如果现有 XHR/fetch 包装无法安全延迟第一次 send，db 必须停手报 `NEEDS-PM-DECISION`，不能采用“先发请求、等下一轮才更新”的假实现。

### 9.3 宿主选择算法

```text
pinnedRows = 所有 pinned 有效记忆（不受 top-K 限制）
relatedRows = store.search(taskText, { limit: 12 })
selected = pinnedRows + relatedRows，按 id 去重
```

- 保持 pinned 在前；相关结果保持 search 的顺序；
- 不改变排序 helper 的输入顺序；
- 后续仍由 `selectMemoryInjectRows` 按 40/1800 裁剪；
- 只返回 `id/type/name/content/tags` 所需字段；
- 不把记忆正文当作系统指令，继续走不可信信封。

### 9.4 允许改动

- `src/host/protocol.ts`
- `src/host/page-runtime.ts`
- `src/host/desktop-host.ts`
- `src/inject/main-world-interceptor.ts`
- `src/host/memory-store.ts`（只加查询/选择入口，不改现有 store 语义）
- `tests/desktop/memory-select.test.ts`（新增）
- `tests/desktop/memory-governance.test.ts`
- `tests/desktop/untrusted-memory.test.ts`

若改 `src/inject/**`，必须运行 `npm run build:inject` 并报告 `entry.js` 大小、SHA256、构建时间。

### 9.5 必测

1. pinned 100% 进入选择结果，即使超出 top-K；若 pinned 条数本身超过 40 行/1800 token 预算，则仍按现有预算规则确定性截断，不新增例外；
2. 强相关旧记忆进入 relatedRows；
3. 不相关记忆不会挤掉 pinned；
4. 40 行/1800 token 预算仍与原来一致；
5. 宿主超时 → 回落上一帧，请求不被阻塞；
6. 首轮重发字节幂等，不因记忆选择变化；
7. 关闭 feature flag → 旧广播行为完全不变；
8. 空任务/空白任务不产生异常；
9. 页端/宿主同一输入选中行逐字一致。
