### B3. 刷新语义建议

两条都要，但优先级不同：

1. **发送路径优先**：`prepareOutgoingBody` 前做 TTL 刷新（建议 TTL 5s），复用 in-flight Promise，最多等 120–150ms；超时就用旧清单继续发，绝不阻塞对话。
2. **`/` 输入路径次要**：用户输入 `/` 时触发一次刷新，现有 2s 节流钩子可直接用；它只影响 UI 候选，不影响模型。

关键约束：

- fetch 与 XHR 两条路径都要覆盖；
- XHR 只调用一次 `prepareOutgoingBody()`；
- `inFirstAttemptResend === true` 时跳过刷新与二次注入；
- 不要在每轮都强制 `await` 网络请求，否则首字延迟会明显变差。

### C3. U1：续跑轮无哨兵之后怎么结算

【代码】已读 `main-world-interceptor.ts:1601-1627`，实际结算路径是：

1. `httpVerdict === 'fatal'` → `return false`，交外层 `classifyResponse` 出 401/403/4xx 文案，不占首轮预算。
2. `loopState.inAutoContinue` → `return false`，**交 `autoContinueWithPow` 的续跑执行器分类**，页面层不抢结算。
3. 仅首轮（非续跑）才 `escalateFirstAttemptFailure(...)` 并 `return true`，由首轮重发预算处理。

所以"续跑轮无哨兵"不是没人结算，而是**结算责任在续跑执行器**。U1 真正要确认的是：执行器收到 `return false` 后，是否会区分"截断/空流/HTTP 失败"并正确收尾——这段在 `autoContinueWithPow` 相关函数里，不在 1601 这段。

对 M1 的含义：如果只改页面层而不动执行器，仍可能把续跑轮的截断记成正常完成。M1 必须两边一起看。
