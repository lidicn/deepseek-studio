- XHR abort 处理

优先补真测试，不要为了测试方便重写实现。

### 6.2 必测行为

测试必须真实断言以下行为：

1. `memory.select` pending 存在时，聊天 XHR 最多等待约 120ms 后才发送，不是立即发送，也不能无限等待。
2. 等待预算超时后，原聊天请求仍必须发送，并且只发送一次。
3. pending 被 abort 后，等待方及时解除，原请求继续发送，不悬挂。
4. pending reject/抛异常后，等待方及时解除，原请求继续发送，不悬挂。
5. 非聊天 XHR 不等待 `memory.select`，也不触发预取。
6. 首轮原请求因重试而原样重发时，不得重复触发 `memory.select`；必须真实构造 `inFirstAttemptResend=true` 或等价状态。
7. 注入时 feature flag 为 `null`、运行期变为 `true` 后可生效。
8. 关闭 feature flag 时行为与旧逻辑一致。

### 6.3 测试质量要求

- 每条用例必须有行为断言，不能只等待固定时间或只观察 mock 被调用；

### 7.2 目标契约

定义一个小而清晰的结构，例如：

```ts
export interface MemorySaveWarning {
  code: 'fts-sync-failed' | 'eviction-failed';
  message: string;
  detail?: string;
}
```

要求：

1. `SaveMemoryResult` 增加结构化 `partial?: boolean` 和 `warnings?: MemorySaveWarning[]`。
2. FTS 同步失败、淘汰失败不再只写 `console.warn`，而是收集为 warning；主记录成功时允许继续返回 `ok:true`。
3. 所有主记录写入成功返回点都要带上一致的 partial/warnings 语义。
4. 正常保存且无附属失败时，`partial` 必须为 false 或省略，`warnings` 为空，不得误报。
5. 主记录写入失败、唯一约束失败、SQL 主路径失败仍必须 `ok:false`，不得降级为部分成功。
6. `desktop-host.ts` 的成功响应必须透传结构，例如：

```ts
return {
  ok: true,
  data: {
    id: result.id,
    saved: true,
    partial: result.partial === true,
    warnings: result.warnings ?? [],
  },
};
```

7. `ToolResultExtras` 增加最小字段以承接 `partial`/`warnings`。
8. 工具卡状态增加 `partial`：
   - 主记录失败：显示失败；
   - 主记录成功但有 warning：显示“部分成功”；
   - 主记录成功且无 warning：显示成功；
   - 部分成功的工具卡必须展示至少一条失败原因，不得只显示状态。
9. 保留现有错误信息，不吞错，不改变 `ok:false` 的用户可见语义。

### 7.3 必测行为

至少覆盖：

1. 正常保存：`ok:true`、无 partial、无 warning。
2. 主记录成功但 FTS 同步失败：`ok:true`、`partial:true`、包含 `fts-sync-failed`。
3. 主记录成功但淘汰失败：`ok:true`、`partial:true`、包含 `eviction-failed`。
4. 主记录失败或 constraint failure：`ok:false`，不得带“部分成功”UI。
5. 宿主响应确实透传 partial/warnings。
6. 工具卡对 partial 显示“部分成功”和原因。
7. 现有成功路径不出现 warning 误报。
