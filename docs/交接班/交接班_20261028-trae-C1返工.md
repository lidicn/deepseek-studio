## 3. P0 功能阻断

### C1-F1：修复 `memory.select` 自动预取闭环

#### 真机事实

页端包装 `host.sendToolCall` 和 `WebSocket.prototype.send` 后，发新聊天，观测结果始终为：

```json
{"calls":0,"ws":0}
```

trace 为：

```text
turn 1 (1.0s)  DONE
  ├─ request.sent    6.9KB
  ├─ sse(chars): text×4 think×0 tool×0
  ├─ continuation.decision: no-tools -> triggered=false
  └─ turn.end stopReason=completed finished=true
```

手动调用 `memory.select` 可以成功并返回 `fallback`，但自动预取没有触发，不能作为通过证据。

#### 已确认根因

1. `src/desktop/entry.ts:281-287`
   安装时只读取一次 `globalThis.__studioMemorySelect`。
   真机注入时读数为：
   ```text
   boot.hasStudioAtInject=true
   boot.flagAtInject=null
   ```
   因此安装期把 `enabled` 固定成 `false`，后续页端再设置 flag 也不会生效。

2. `src/inject/main-world-interceptor.ts:923-926`
   只有 fetch 路径调用 `awaitMemorySelectBudget(120)`。
   实际聊天走 XHR：`xhr POST /api/v0/chat/completion`。
   `installXhrHooks()` 的 `proto.send` 路径没有对应的有界等待。

#### 必须修改

- `src/desktop/entry.ts`
- `src/inject/main-world-interceptor.ts`
- 对应测试文件

#### 实现要求

1. feature flag 不得在注入安装时一次性读取后永久固定。
   - 允许运行期读取 `globalThis.__studioMemorySelect`；
   - 或提供明确的配置消息更新开关；
   - 必须覆盖“注入时 flag=null，之后变 true 能生效”。
2. XHR 首轮真实聊天请求必须获得与 fetch 等价的有界等待能力。
   - 不得超过既定预算，建议仍为 120ms；
   - 不得阻塞非聊天请求；
   - 不得破坏首轮重发幂等；
   - 不得改变 `XMLHttpRequest.send()` 的公开返回类型；
   - 若要延迟实际 `origSend`，必须处理 `abort`、异常和回调时序，不能留下悬挂请求。
3. 真实聊天请求必须实际触发 `kickMemorySelect(userText)`。
4. 自动调用必须经过：
   ```ts
   host.sendToolCall({
     invocationName: 'memory.select',
     params: { taskText }
   })
   ```
5. 超时或失败继续保留上一帧 `currentMemories`，不得阻塞聊天。

#### 必补测试

1. 注入时 flag=null，之后变 true，自动预取能生效。
2. XHR 首轮聊天发送前执行有界等待。
3. fetch 路径不回归。
4. 超时回落上一帧。
5. 自动调用确实经过 `host.sendToolCall({ invocationName:'memory.select' })`。
6. 非聊天 XHR 不等待、不触发 `memory.select`。
7. 首轮原样重发不重复预取。

#### 验收

- 先跑新增专项单测；
- 再跑 `memory-select` 相关既有测试；
- 跑 `npm run typecheck`；
- 代码级通过后向 PM 申请真机窗口；
- 真机必须观测到自动 `memory.select`，且聊天完成；
- 手动调用成功不算通过。
