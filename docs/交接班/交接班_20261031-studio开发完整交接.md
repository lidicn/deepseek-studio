## 1. 架构地图与关键入口

### 1.1 运行链路

```
Tauri 壳 (src-tauri/src/main.rs)
  └─ 启动 Node sidecar (src-tauri/src/sidecar.rs)
       └─ src/api/main.ts  (npm start / tsx)
            └─ src/host/desktop-host.ts  宿主主对象，聚合所有能力
                 ├─ memory-store.ts        记忆库（SQLite）
                 ├─ mcp-controller.ts      MCP 服务器管理与工具调用
                 ├─ tool-registry.ts       工具注册
                 ├─ authorization.ts       审批三轴 / grant
                 ├─ skill-store.ts         技能目录扫描
                 ├─ page-runtime.ts        页端命令桥（file/shell/image_fetch/...）
                 └─ image-proxy.ts         图片代理（本轮 WIP 新增）

WebView 内注入 (src-tauri/inject/entry.js ← esbuild 生成)
  └─ src/inject/loader.ts          按 origin 白名单装载
```

## 3. 构建、启动、验证流程

### 3.1 关于"不是 npm run 的吗"

用户之前质疑过构建方式，这里明确区分：

- **注入脚本构建**：`npm run build:inject`（= `node esbuild.inject.mjs`），产出 `src-tauri/inject/entry.js`。
- **桌面 debug exe**：需要 `cargo build`，不是 npm 脚本。`npm run build` 只是 `build:inject` 的别名，**不构建 exe**。
- **发布安装包**：才用 `npm run tauri:build`。

`package.json` 实测脚本：

```
typecheck   = tsc --noEmit
test        = vitest run
test:watch  = vitest
start       = tsx src/api/main.ts
build:inject= node esbuild.inject.mjs
build       = npm run build:inject
tauri       = tauri
tauri:dev   = tauri dev
tauri:build = tauri build
eval:golden = tsx tools/eval/run.ts
metrics:report = tsx tools/metrics/report.ts
gate        = tsx tools/gate/run.ts
```

### 3.2 正确的 debug 构建顺序

```powershell
cd E:/NAS/deepseek-studio
npm run build:inject
cd src-tauri
cargo build
```

然后启动：

```powershell
E:/NAS/deepseek-studio/src-tauri/target/debug/deepseek-studio.exe
```

验证：

```powershell
Invoke-RestMethod http://127.0.0.1:8760/health
```

CDP 默认 `9222`；被占用时退回 `9223`（提交 `79c67ee`）。

### 3.3 三条硬规则

1. **`src-tauri/inject/entry.js` 是生成产物**。不跑 `npm run build:inject`，所有 `src/inject/**` 改动都不会生效，看到的永远是旧行为。
2. **exe 比 entry.js 旧 = 当前 exe 不包含注入改动**。改完注入必须重建 entry.js；改了 Rust 必须 `cargo build`。
3. **debug exe 打不开先查两件事**：是否执行过 `cargo build`；`entry.js` 是否比 exe 新。不要先怀疑路径。

### 3.4 页内调试入口

页面控制台可用：

- `__studioSkillPopup()`：查看技能浮层状态。
- `__studioTraceReport()`：导出注入链路 trace。
- `__studioMemorySelect`：`memory.select` 预取的 feature flag（默认关闭）。

手工验证点：

- 输入 `/media` 应出现技能候选。
- 输入 `/media-seach`（故意拼错）应出现"无匹配"提示，不能静默消失。

## 4. 在飞缺陷（按优先级）

### 4.1 P0：media-search 技能"存在但 agent 调不了"

**这是当前最重要、也最容易被误判的缺陷。**

现象：技能文件已经放进技能目录，`/` 面板也能看到候选，但模型在对话中不会主动调用该技能。

根因：**模型提示词里的技能清单只在启动时拉取一次**，之后不刷新。

精确位置（`src/inject/main-world-interceptor.ts`）：

| 行 | 内容 |
| --- | --- |
| `:196` | `let currentSkills: StudioSkillDescriptor[] = [];` |
| `:670` | `formatExplicitSkillsBlock()` |
| `:692` | `formatSkillsBlock()` |
| `:700` | `buildCapabilityPrompt()` |
| `:781` | `prepareOutgoingBody()` |
| `:1224` | XHR 注入路径调用 `prepareOutgoingBody()` |
| `:1252` 附近 | fetch 注入路径 |
| `:2041` | `inFirstAttemptResend = true` |
| `:2444` | 启动时一次性 `currentSkills = ...` |

修复方向：实现 `ensureSkillsFresh()`：

- 带 TTL（例如 5–10 秒）；
- 复用 in-flight Promise，避免并发重复请求；
- **真正发出请求前最多等待 120–200 ms**，拿不到就先用旧清单，不能阻塞对话；
- fetch 与 XHR 两条路径都要先刷新；
- XHR 路径只调用一次 `prepareOutgoingBody()`，不要重复注入；
- `loopState.inFirstAttemptResend === true` 时**不得**二次注入（首轮原样重发语义）。

只修 `/` 浮层列表不够。**即使面板能显示 media-search，只要提示词缓存的 `currentSkills` 不刷新，agent 依然调不到。**

技能目录优先级（`src/host/skill-store.ts:31-33`）：

1. 显式传入目录
2. `STUDIO_SKILLS_DIR`
3. `~/.agents/skills`（存在则用）
4. `~/.config/deepseek-studio/skills`

Junction/symlink 处理在 `skill-store.ts:106-107` 附近（本轮 WIP）。

### 9.2 两个独立问题，不要混为一谈

`image-proxy.ts` 已做公网校验、魔数校验、大小与超时限制，**不能简单"放开所有 URL"**。
