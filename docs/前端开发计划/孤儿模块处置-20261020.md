# 孤儿模块处置（X3）· 2026-10-20

> 对象：`src/ui/workbench/` 下无调用方（或职责重复）的模块。
> 方法：`rg` 逐文件反查引用，不看注释、不看文档，只认真实 import / 调用点。
> 结论先行：**X3 不是单纯清理，顺带修掉了两个会让界面颜色完全失效的真缺口。**

---

## 一、发现的两个真缺口（比清理本身重要）

### 缺口 1：design tokens 从未生效（P0）

`agent.css` 原来把 `--studio-*` 定义为 `var(--wb-bg-0, #0f1115)` 形式，而全仓搜 `--wb-[a-z0-9-]+\s*:`
**只命中一条** `--wb-radius: 10px`（`agent.css:19`）。也就是说 `--wb-bg-0` / `--wb-text-0` /
`--wb-border` / `--wb-primary` 这些被引用的变量**从来没有任何定义处**。

根因：唯一应该写入 token 的 `workbench-theme.ts`（`applyWorkbenchTheme`），唯一调用方是
`workbench-app.ts`，而 `workbench-app.ts` 自身 0 调用方。→ `applyWorkbenchTheme` 从未执行。

后果：`design-tokens.ts` 里 `color.light` / `color.dark` 两套完整配色是死代码，整个工作台
实际跑在 CSS 里的硬编码 fallback 上。改 token 对界面零影响。

### 缺口 2：宿主主题适配器也是孤儿

`host-theme-adapter.ts`（施工计划 §7.4 定义，C2 交付）同样 0 调用方、0 测试。
它与 `workbench-theme` 职责互补但一直没接上：一个负责"探测当前该用什么主题"，
一个负责"把主题写成 CSS 变量"。

## 二、主题闭环（本次新做，非清理）

新增 `src/ui/workbench/theme-toggle.ts`，把上面两半接起来：

- **默认浅色**：无用户选择时按 `host-theme-adapter` 探测（宿主 `data-theme` → `prefers-color-scheme` → `light`）。
- **用户点击顶栏 🌗 切深色**，选择写入 `localStorage['ds-studio-theme']`，下次启动沿用。
- **用户选过后不再跟随系统**：一旦显式选择，立即退订 `matchMedia` 监听。
- **降级**：`localStorage` 读/写抛错（隐私模式、存储被禁）时降级为"仅本次会话生效"，不抛到调用方。

### 一个踩过的坑（已修，测试锁定）

第一版实现无条件写 `document.documentElement.dataset.theme`，结果"跟随系统"失效：
`host-theme-adapter.getTheme()` 的第 1 优先级就是读 `data-theme`，于是它读到自己刚写进去的值，
系统切深色永远透传不进来。

修正后的规则：

| 场景 | 写 `data-theme`？ | 写 CSS 变量？ |
| --- | --- | --- |
| 用户未选择、跟随系统 | 否 | 是 |
| 用户显式选择（点击 / `set()`） | 是 | 是 |
| 启动时发现上次选过 | 是 | 是 |

`data-theme` 的语义被收紧为"用户显式选择的标记"，不再当作通用的主题状态。

### CSS 侧

`agent.css` 的 `--studio-*` 从"引用不存在的 `--wb-*`"改为**与 token 逐值一致的静态兜底**：

- `:root` = `color.light` 逐值（默认浅色）
- `:root[data-theme="dark"]` = `color.dark` 逐值

这样即使 JS 未执行或执行失败，界面仍是可读浅色，不会白屏/黑屏；运行时由
`applyWorkbenchTheme` 写 `documentElement.style` 覆盖兜底值。两份同源（都来自 `design-tokens.ts`），
不会分歧。CSS 与 token 的一致性由 `tests/desktop/theme-toggle.test.ts` 断言具体色值锁定。

## 三、孤儿判定与处置

| 文件 | 实测引用 | 处置 | 理由 |
| --- | --- | --- | --- |
| `workbench-app.ts` | 0 调用方；唯一调用 `mountWorkbenchShell` + `applyWorkbenchTheme` | **删除** | `startWorkbench` 无人用；它的"组装三栏壳"职责与 `agent.html` 静态结构重复，是两套三栏实现 |
| `workbench-composer.ts` | 0 调用方 | **删除** | `agent-panel.ts:66/68/208` 已手写等价逻辑（`canSend`/`canStop` 禁用 + Enter 发送 + stop），留着就是同一职责两套标准 |
| `workbench-left-panel.ts` | 0 调用方 | **保留 + `@deprecated`** | `getLeftPanelBody` / `clearLeftPanel` 是纯 DOM 工具，后端会话/任务列表数据源落地时要重用它；现在删了将来得重写。**一旦被接线，立即去掉标记** |
| `workbench-shell.ts` 的 `createWorkbench()` | 0 调用方 | **删除该导出** | 与 `mountWorkbenchShell` 完全等价（`return mountWorkbenchShell()`），纯冗余别名 |
| `workbench-theme.ts` | 此前仅 `workbench-app.ts` 引用 | **接线启用** | 新增 `theme-toggle.ts` 调用它；`tokensToCssVars` 的唯一消费者从"无人"变成"真实链路" |
| `host-theme-adapter.ts` | 此前 0 调用方 | **接线启用** | 同上，由 `theme-toggle.ts` 调用 |

### 未处置、需后续决策（不擅自删）

`mountWorkbenchShell`（`workbench-shell.ts`）目前**只有测试引用**（`workbench-shell.test.ts` 6 条），
生产链路 `agent-panel.ts` 并不用它——工作台的三栏 DOM 由 `agent.html` 静态提供。

这意味着 `workbench-shell.ts` 整体也处于"只被测试引用"状态。不删的理由：

1. 它是 W2 的核心交付物，`layoutForWidth` / `renderDesktopHint` / 断点纯函数有独立价值；
2. 删它要连带删 6 条测试，超出 X3"处置孤儿 + 闭环主题"的范围；
3. 窄屏布局目前靠 `agent.css` 媒体查询，`setLayout()` 的运行时断点切换**尚未接线**，
   这是一个待决策项（见下）。

**待决策**：`setLayout(width)` 运行时断点要不要接进 `agent-panel.ts`（监听 `resize`）？
接了会与 `agent.css` 的 `@media` 形成两条断点真相源；不接则 `is-compact` / `is-desktop-only`
这些 class 永远不会出现。建议：接，但以 `setLayout` 为唯一真相源，删除对应 `@media` 规则。
本期不做，留给下一轮长任务。
