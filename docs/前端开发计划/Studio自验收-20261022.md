## Codex 核实 · 第 1-2 批复核（2026-10-22）

### C1. 点号 id 对模型「假暴露」——根因是标签名正则，不是闸门（P0）

Studio 断言 `settings.get` / `workspace.set` / `policy.set` 「模型侧不可调、设计如此」，**理由错、结论对**。

实测（`npx tsx` 直跑 `StreamingToolCallParser`，17 个标签逐个喂）：

- 10 个下划线名全部 `PARSED`：`shell_exec` `local_file_read` `local_file_write` `local_file_stat` `memory_save` `python_exec` `mcp_list` `mcp_call` `mcp_test` `mcp_save`
- 7 个点号名全部 `MISSED`：`settings.get` `workspace.set` `policy.set` `skill.list` `file.read` `file.edit` `mcp.remove`

根因：`src/inject/streaming-tool-parser.ts:46` 的开标签正则 `/^<([a-zA-Z_][\w-]*)>/` —— `\w` 等价 `[A-Za-z0-9_]`，**不含 `.`**，所以 `<settings.get>` 匹配不上开标签；也匹配不上闭合标签（:62 同款字符类）；`:66` 的未完成前缀判定要求 `<` 后到结尾全是 `[\w-]`，含 `.` 与 `>` 同样不中。最终走 `else` 分支 `clean += '<'`，**整段标签以纯文本形式流回对话**——这就是「标签发出去了、没执行、正文里显示成原文」的代码级解释。

结论修正：
- 闸门本身不拦：`SUPPORTED_INVOCATION_NAMES = Object.keys(UPSTREAM_TO_STUDIO)`（`src/shared/tool-contract.ts:144`）= 30 键（10 下划线 + 20 点号，含 `mcp.test`/`mcp.save` 两份点号登记）；`isSupportedUpstreamTool` 用 `hasOwnProperty`（同文件 :146-148），点号名**能过闸**。
- 过闸也没用：`page-runtime.ts:396` 的 `mapUpstreamToolInvocation` 之前，标签在页端就被解析器当文本吐出了，根本到不了 WS。
- 净效果：20 个点号工具（`settings.get` `workspace.set` `policy.set` `folder.pick` `memory.delete` …）**模型不可达**；宿主侧真实注册、UI 可用、模型调不到。

## Codex 复核更正（2026-10-23，依据 QD-R4 审计）

**第 313 行「网络中断 → 指数退避重试 3 次，耗尽即停」不成立。**

QD-R4-01 实测：429 之后 **0 次重试**。根因是重试回调重新进入
`autoContinueWithPow` 时，被首行 `pending.length === 0` 守卫挡死——而 `pending`
在续跑请求发出前就被清空了（F8 修复，防 XHR hook 重复注入）。
`MAX_ERROR_RETRIES = 3` 的预算一次都花不出去，用户看到的就是
「工具卡片转完，回复停了」，且状态栏永停在「执行中…」。

附带两条：重试还会白吃一次 `loopDepth`（把工具续跑步数预算耗掉一步）；
错误预算耗尽路径不调用 `finishStepFlow`，`setBusy(false)` 永不执行。

已修（tests/desktop/qd-r4-stream-break-regression.test.ts 转正为回归）：
1. 守卫显式豁免重试入口（`continuationRetryPending`），重试只重发上一份 body；
2. 重试不消耗 `loopDepth`；成功轮重置 `errorRetryCount`（盘面已有）；
3. 错误预算耗尽 / fatal 统一走 `finishStepFlow`，保证 `setBusy(false)` 与错误可见。
