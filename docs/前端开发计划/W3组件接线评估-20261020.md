# W3 组件接线评估（X5）· 2026-10-20

> 对象：`src/ui/workbench/components/` 下 10 个 W3 交付的组件层。
> 问题：它们各自该不该接进运行中的工作台？接哪些？不接的缺什么？
> 方法：逐个反查真实数据源（不看注释承诺，看事件契约与后端填充点）。
> 硬规则：**没有真实数据源的组件一律不接**，接了就是假能力。

## 二、建议接线的 3 个（全部吃 `ToolRunEvent`，不新增任何后端能力）

接线点唯一：`agent-panel.ts` 的 `onToolRun` 回调。当前它只调
`appendToolRun(container, event)`；改造为"先渲染主卡片，再按事件内容追加附属卡"。

具体规则：

| 组件 | 触发条件 | 渲染位置 |
| --- | --- | --- |
| `artifact-card` | `event.artifactPaths?.length > 0` | 主卡片内部下方 |
| `diff-review` | `event.details` 命中白名单字段（`path` / `replacements` / `bytesBefore` / `bytesAfter` / `sha256Before` / `sha256After`） | 主卡片内部下方 |
| `error-card` | `phase` 为 `failed` 或 `denied` 且 `errorCode` 存在 | 主卡片内部下方 |

### 为什么这几个可以接（证据）

`artifactPaths`：`src/host/desktop-host.ts:1461` 的 `extractArtifactPaths(tool, details)`，
X2（commit `cb5d9dd`）已接，只对 `file.edit` 的 `details.path` 收路径，
shell / read / write 无源不填，**不猜**。

`details`：`src/host/desktop-host.ts:1441` 的 `onToolResult` 透传 `result.details`，
而 `EditEngineData`（`src/capabilities/edit-engine.ts:109`）字段与
`diff-review` 的白名单完全重合：`path` / `replacements` / `bytesBefore` /
`bytesAfter` / `sha256Before` / `sha256After` 六个全有。

`errorCode`：`ToolRunEvent.errorCode` 已定义，`src/shared/ui-error-codes.ts` 有中文映射。

**这三个都是"后端已经在发、前端还没显示"的数据，接线属于补显示，不是加能力。**

### 必须遵守的约束

1. 附属卡挂在主卡片**内部**，不新增右栏顶层节点，否则终态去重（按 `data-run-id`）会漏掉附属卡。
2. 附属卡只在事件首次渲染时追加；`started` 到 `succeeded` 更新主卡片时，附属卡随主卡片一起替换，不得重复叠加。
3. `diff-review` 不得显示 diff 正文（后端不发 diff 内容，只发统计与哈希），只显示 path / 替换数 / 字节数 / 哈希。
4. 全仓无 `.wb-*` CSS，本期接线**必须同时补最小样式**，否则是无样式裸元素。

## 三、有数据但不接的 4 个

### `tool-call-card.ts`：与右栏现有卡片重复

右栏 `appendToolRun` 已用 `primitives/tool-run-card`，phase / 时长 / 错误码已内联展示。
`tool-call-card` 拆得更细，但显示的是同一批字段。接上去等于同一职责两套视觉，
改一处忘另一处就会不一致。**留作将来重做右栏时的候选，不作为叠加层。**

### `unknown-tool-card.ts`：接它等于接外壳

`renderToolCallCard` 内部已经调 `renderUnknownTool` 做兜底分支。
要让它生效必须调 `renderToolCallCard`，而那会引入上一条的重复问题。
**结论：不接。未知工具的兜底显示，等右栏整体重做时一起给。**

### `message.ts`：零收益、高回归风险

中栏现有 `.msg-user` / `.msg-assistant` 气泡样式完整（`agent.css`）。
换成 `wb-message` 需要重写整套气泡 CSS，而全仓**没有任何 `.wb-*` 选择器**，
等于把已工作的渲染推倒重来。**收益为零，回归风险高。**

### `empty-state.ts`：暂无场景

右栏与抽屉目前是空 `div`，没有空态需求（没有会话列表，本来就没有东西可空）。
等左栏会话列表接线后，左栏才需要空态。**场景未到，不提前接。**

## 四、无数据源、明确不接的 3 个

### `reasoning.ts`

`AgentLoopEvent`（`src/shared/agent-loop-event.ts`）只有
`user / assistant / tool / status / error / done` 六种，**没有 reasoning 字段**。
注入层 `deepseek-sse-frame-decoder.ts` 确实解码了 `reasoningText`，但那走的是
inject 链路，不经过 `/agent-ws`。工作台拿不到思考过程。

**要接的前置条件**：`AgentLoopEvent` 增加 reasoning 字段，host 侧在 SSE 解码处透传。
这属于协议变更，须单独任务书。

### `approval-card.ts`

组件自身注释已写明"Workbench 无审批通道，本期只读"。
它没有任何数据入口，不接收事件、不接收 state，`renderApprovalCard()` 无参数。
工作台没有审批按钮是**有意设计**（审批在宿主窗口完成），不是缺数据。

**结论：这个组件本身就该保持只读静态。除非将来工作台要嵌审批面板，否则永远不接。**

### `permission-card.ts`

输入是 `{ mode, pending }`。`mode` 有来源（`WorkbenchState.policyMode`），
但 `pending` 在 `WorkbenchState` 里**不存在**，没有任何"等待审批中"的状态位。

组件注释说得对："ack 前只显示 pending，不在本地假装成功"。
但现在连 pending 状态都拿不到，接上去只能永远显示非 pending 的档位名，
而顶栏 `.seg` 已经显示了同样的档位名。**重复且无新增信息。**

**要接的前置条件**：`WorkbenchState` 增加 pending 授权状态，host 在 grant 等待时推送。

## 五、接线顺序建议

若本期要做，建议**一个 commit 接一个**，顺序按数据确定性排：

1. `artifact-card`：X2 刚供数，最确定，测试最好写。
2. `diff-review`：字段齐备，但要注意只显示统计不显示正文。
3. `error-card`：终态兜底，最独立。

**若时间或积分不允许，退而求其次只做第 1 项**：它最独立，且是 X2 投入的直接兑现。
