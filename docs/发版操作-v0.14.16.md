三条教训（都已落判据）：

1. **闸绿 ≠ 那条路能走通**：0.14.13 那次，发布脚本里的 fetch 分支因缓存命中**从未被执行过**；0.14.14 那次，闸**根本不读 workflow 里的脚本内容**；0.14.15 那次，step16 是被引入后**第一次被执行到**（`v0.14.10/11/12` 三个成功 tag 里都没有这一步）。
2. **新增发布链步骤必须自带「第一次被执行到」的验收**——不能假定它在前序失败时也被验证过。
3. **锁自然语言就是锁语言**：0.14.15 的闸红在「断言匹配中文报错原文」，而 runner 报英文 ⇒ 改为只锁我们自己写入的结构标记。

`v0.14.13`／`v0.14.14`／`v0.14.15` 三个 tag 均保留、不删不重打。**重跑已失败的 run 没有意义**：它跑的是 tag 里那份已知的坏代码。

## 版本号

四处同步（`Cargo.toml` 是 crate 号 `0.4.0`，不参与一致性校验，勿改）：

| 文件 | 行 |
|---|---|
| `package.json` | L3 |
| `src-tauri/tauri.conf.json` | L4 |
| `package-lock.json` | L3、L9 |

**抬号后必须重建注入包**：`esbuild.inject.mjs` 把 `package.json` 的 version 编成编译期常量，不重建则 `entry-freshness` 报「陈旧构建」。

```
npm run build:inject     # 双跑同值，报 entry.js 新锚
node tools/audit/entry-freshness.cjs   # 期望 PASS (<新指纹前 8 位>)
```

**抬号后的自检走解析口径，不许用 grep 计数**（计数法拦不住「多处都在但值不一样」，也拦不住「手改 JSON 把文件改坏」）：

```
node -e "const p=require('./package.json'),l=require('./package-lock.json'),t=require('./src-tauri/tauri.conf.json');console.log(p.version,l.version,l.packages[''].version,t.version)"
```

四值必须全等且等于目标版本号，进程退出码 0。

## 发布页正文

- 正文文件：`docs/release-notes-v0.14.16.md`，**必须先于 tag 入库**（workflow 的 notes 校验步是 fail-closed：文件不存在或纯空白 ⇒ 整条 release job 红）。
- 文件名由 tag 动态推导，**不需要改 workflow 里任何路径**。
- 正文只写用户可见行为；未在安装版上逐项手工验证的，必须写明「不作承诺、请把现场发我们」。
- `latest.json` 的 `notes` 是另一条链：剥 markdown → 截 500 字内最近「。」→ 应用内升级弹窗显示的是这份截断纯文本，与网页正文分别验收。

### ★闸红的"未验面"（2026-11-11 GATE#67 实测写实，必读）

`npm run gate` 的阻塞步**第一个失败即停**（`tools/gate/run.ts`：vitest 是第 2 步阻塞，红了 `break`，**后面 14 步阻塞步全部不执行**——含 `entry-freshness` 第 11 步与 `workflow-pwsh-compile` 第 16 步）。信息级步照跑。

⇒ **闸红时，"闸绿"不成立，且后面那些步是"未验"而不是"验过"**。GATE#67 实测：vitest 红在第 2 步 ⇒ entry-freshness 与编译闸**根本没执行**（日志里 `PASS (EA5F5C04)` 零命中）。

⇒ **打 tag 前，若闸红过、或闸的"阻塞级全过"那一行没出现，一律不许打 tag**：必须先让闸**绿到底**（看到 `✅ 阻塞级全过（16 步阻塞 + 6 步信息，…s）` 那一行），否则 fresh（产物与源码同版）与 workflow 脚本可解析这两格都属未验。

⇒ 单独补跑那两格（不替代全量闸，只用于确认未验面已验）：
```
node tools/audit/entry-freshness.cjs      # 期望 PASS (<新指纹前 8 位>)
node tools/audit/workflow-pwsh-compile.cjs # 期望 PASS: blocksParsed=21 blocksSkipped=0 (0 errors)
```


## CI 与草稿

1. 三条 job：`gate` ×2、`cargo-check` ×2、`release` ×1。`release` 最慢（Rust 编译＋打包＋签名＋上传，参考上一发约 489 s）。
2. **报数必须带时长**；`cargo-check` 的 step 日志匿名取不到缓存命中态时只报时长、不写「命中」。
3. `release` 绿后才会有草稿（fail-closed：构建失败时页面上没有 Publish 按钮）。
4. 草稿核对五件：资产 5 枚（`.exe`／`.exe.sig`／`.msi`／`.msi.sig`／`latest.json`）全 200、正文与文件逐字等值、`draft=true`、`tag=v0.14.16`、三向版本一致。
5. **读数纪律**：step 级结论用 `GET /actions/runs/<id>/jobs` 取（匿名可读）；job 日志正文匿名 403，**取不到就说取不到，不许用「大概是同一处」交差**；报「读不到」前先查 `rate_limit.remaining`，**限流与故障分开判**；`git` 通道与 `api.github.com` 通道可用性**分别判**，不写「GitHub 挂了」这种整句；匿名额度 60/h 用尽时读数记「未知」，不记红也不记绿。

## step16 的读数口径（本版重点）

step16 现在会把自己的失败原因写进 `::error::` 注解（**匿名可读**），分三类：

- `draft release for tag … not found (first query: by-id=… list-fallback=…)` ⇒ 草稿没查到；
- `PATCH failed: HTTP=… msg=…` ⇒ 写入失败；
- `body mismatch: expected_len=… actual_len=…` ＋ `firstDiff=… expected_char='…' actual_char='…'` ⇒ 正文不等，**直接给长度与第一个不同字符**。

下一发若仍红，**先读这三类注解**（不用等管理员令牌），再对号入座判真因；不要凭 step 级 exit code 猜。

## Publish（用户的网页动作）

Releases → `v0.14.16 (Draft)` → Edit → 确认正文完整 → **勾上「Set as the latest release」** → Publish。
不勾 Latest ⇒ `releases/latest` 指针不推进 ⇒ 客户端收不到更新提示（已两次踩坑）。
